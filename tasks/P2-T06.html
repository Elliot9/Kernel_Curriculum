P2-T06 · radix tree 與 XArray

一句話:當你的「key」是整數(檔案 offset、ID),而且大量、密集,radix tree / XArray 比紅黑樹和雜湊表都更合適——它用整數的「位數」直接導航。kernel 的 page cache 就用 XArray 把「檔案 offset」對應到「記憶體裡的 page」,這跟你的儲存工作直接相關。

為什麼要先學這個(導讀)

前兩課給了你兩種查找結構:雜湊表(平均 O(1),無序)和紅黑樹(O(log n),有序,以「比較」為基礎)。這一課介紹第三種,專門針對一個特定但極常見的場景:用一個整數索引,快速對應到一個值(指標)。

當 key 是整數、而且大量又密集(例如 0, 1, 2, 3, ... 連續的檔案頁編號,或一堆 ID),radix tree / XArray 有獨特優勢:它不靠「比較大小」(像紅黑樹),也不靠「雜湊」(像雜湊表),而是直接用整數的位元/位數來導航到對應的位置。

為什麼你要特別學它?因為它和你的儲存領域直接相關。kernel 的 page cache——位於 VFS 和 block layer 之間的快取層,快取著檔案的內容頁——核心就是一個 XArray:它把「檔案的 offset(以 page 為單位的索引)」對應到「那一頁資料在記憶體裡的 struct page」。當你讀一個檔案,kernel 先查 page cache(這個 XArray)看那一頁在不在記憶體;在就直接給你(快),不在才去真正讀磁碟。理解 XArray,是你日後讀懂讀寫路徑、快取層(P5)的前置。

這一課還要釐清一個重要的新舊交替:radix tree 是較舊的概念與 API(radix_tree_*),XArray 是它的現代取代介面——新程式碼應該用 XArray。你讀 kernel code 時兩者可能都會見到,但寫新東西要用 XArray。

為什麼這對你是 scope: direct?page cache 用 XArray 索引 page——這是讀寫路徑快取的核心,與你的儲存產品直接相關。

開始之前(前置確認)

  • 依賴:P2-T05(你已學紅黑樹這種「以比較為基礎」的有序結構,這課對比「以整數索引為基礎」的)。
  • 自我檢測: 1. 你能說出「紅黑樹靠比較大小導航、雜湊表靠雜湊函式」嗎?(回顧 P2-T05/P2-T04。)這課的 radix tree 用第三種方式:整數的位數。 2. 你還記得 P1-T04 的「page(分頁)」概念嗎?page cache 快取的就是這些 page,XArray 用 page 索引它們。

1. 場景:用整數索引,對應到大量的值

先明確這個結構解決的問題。設想:你有大量的「整數索引 → 值」對應,而且索引是密集的小整數。例如:

        IDOT["... 大量、密集 ..."]

    NOTE["典型場景:
檔案的第 0,1,2,... 頁 → 對應的記憶體 page

    style NOTE fill:#6fa8b8,color:#10100e

你可能想:「用陣列不就好了?array[index] = 值。」對於密集索引這沒錯,但問題是索引可能很大且稀疏(例如一個大檔案的某幾頁,index 可能到幾百萬,但只有零星幾頁在快取裡)。用一個「涵蓋所有可能 index 的大陣列」會浪費巨量記憶體(大部分是空的)。radix tree 就是來解決「索引空間大、但實際用到的稀疏」這個矛盾——既能像陣列一樣用 index 直接定位,又不必為沒用到的 index 浪費空間。

把這個「大而稀疏」的矛盾畫出來,看兩種做法的記憶體差異:

    SCENARIO["需求:索引可能到 1,000,000,

    SCENARIO --> ARRAY["✗ 平坦大陣列:
配置 array[0..999999]
→ 一百萬格,只有 3 格有值
→ 浪費幾乎全部空間"]
    SCENARIO --> RADIX["✓ radix tree / XArray:
只為 index 3、500、999000

    style RADIX fill:#8a9a5b,color:#10100e

關鍵差異:平坦陣列的空間正比於「索引範圍」(再大再空都要配),radix tree 的空間正比於「實際項目數」——這就是它能處理「大而稀疏」的索引空間的原因。

(這個矛盾很像 P1-T04 多級分頁解決的問題——位址空間巨大但稀疏,用多級表只為用到的部分建表。radix tree 的精神與多級分頁相通。)

2. radix tree 概念:用整數的「位數」導航

radix tree(基數樹)的核心想法:把整數索引拆成幾段,每一段決定樹的一層往哪走——用索引的「位數」來導航,而不是比較大小。

flowchart TB
    IDX["整數索引(例如二進位拆成幾段)
[ 段1 ][ 段2 ][ 段3 ]"]
    IDX --> L1["第1層:用『段1』選一個分支"]
    L1 --> L2["第2層:用『段2』選一個分支"]
    L2 --> L3["第3層(葉):用『段3』找到存放的值"]
    NOTE["關鍵:
① 不比較大小(不像紅黑樹),直接用位數選分支 → 查找路徑長度固定(看索引位數)
② 只為『用到的索引』建立對應的分支
→ 稀疏索引不浪費空間(像多級分頁,P1-T04)"]
    L3 --> NOTE
    style L1 fill:#6fa8b8,color:#10100e
    style L3 fill:#8a9a5b,color:#10100e
    style NOTE fill:#e8a33d,color:#10100e

兩個關鍵特性: - 用位數導航,不比較大小:查找一個索引,就是把它拆段,每段選一個分支,走固定的層數(由索引的位數決定)。不像紅黑樹要一路比較。 - 稀疏友善:只有「實際用到的索引路徑」才建立對應的樹節點。沒用到的索引範圍,連節點都不建——就像 P1-T04 多級分頁只為用到的位址範圍建表。所以「索引空間大但稀疏」時,radix tree 只花正比於「實際項目數」的空間,而非正比於「索引範圍」。

直覺:radix tree 像一棵「按整數的數字一位一位往下找」的樹,介於「陣列的直接索引」和「樹的階層」之間——兼得「用 index 定位」和「稀疏省空間」。

3. XArray:radix tree 的現代取代介面

kernel 早期用 radix tree(API 叫 radix_tree_*)。後來推出 XArray(Extensible Array,可擴充陣列)作為現代的、更好用的取代介面。XArray 在底層仍是 radix tree 的概念,但提供更清爽的 API、更好的功能(如內建鎖、標記等)。

flowchart LR
    OLD["舊:radix tree API
radix_tree_insert/lookup...
(仍在舊程式碼中)"]
    NEW["新:XArray API
xa_load(取)、xa_store(存)...
★ 新程式碼用這個 ★"]
    OLD -->|"現代取代"| NEW
    CONCEPT["概念上都是『整數索引 → 值』
底層都是 radix tree 思想
XArray 介面更清爽、功能更多"]
    NEW --> CONCEPT
    style NEW fill:#8a9a5b,color:#10100e
    style CONCEPT fill:#6fa8b8,color:#10100e

把 XArray 想成「一個概念上的無限大陣列,但只為用到的索引花空間」: - xa_store(&array, index, ptr):把 ptr 存到索引 index(像 array[index] = ptr,但稀疏省空間)。 - xa_load(&array, index):取出索引 index 的值(像 array[index])。

新程式碼一律用 XArray,不要用舊的 radix_tree_*(這是常見誤區:用過時 API 寫新東西)。但讀舊程式碼時可能遇到 radix tree API,知道它們是同一概念即可。

4. page cache:XArray 的招牌應用(你的儲存領域)

這是這一課對你最重要的部分。page cache 是 kernel 在記憶體裡快取檔案內容的機制,它的核心資料結構就是 XArray。

flowchart TB
    READ["你的程式讀檔案的第 N 頁"]
    LOOKUP["kernel 查 page cache 的 XArray:
xa_load(該檔案的 XArray, N)
= 用『page 索引 N』找對應的 struct page"]
    READ --> LOOKUP
    LOOKUP --> HIT{"那一頁在記憶體嗎?"}
    HIT -->|"在(cache hit)"| FAST["直接從記憶體那個 page 給你資料
→ 快(免讀磁碟)"]
    HIT -->|"不在(cache miss)"| SLOW["去真正讀磁碟,
讀進一個新 page,
用 xa_store 存進 XArray(下次就命中)
→ 慢"]
    style LOOKUP fill:#e8a33d,color:#10100e
    style FAST fill:#8a9a5b,color:#10100e
    style SLOW fill:#c2603a,color:#f4ecd8

機制:每個檔案(在 kernel 裡對應一個 address_space)有一個 XArray,索引是「檔案的 offset,以 page 為單位」(第幾頁),值是「那一頁資料在記憶體裡的 struct page 指標」(回顧 P1-T04 的 page)。當你讀檔案: - kernel 先用 xa_load 查那一頁在不在 XArray 裡(在不在記憶體)。 - 命中:直接從記憶體的 page 給你資料,飛快(不碰磁碟)。 - 未命中:去磁碟讀那一頁,讀進記憶體,用 xa_store 記進 XArray,下次就命中。

為什麼用 XArray 而非紅黑樹?(驗收點)因為 page cache 的 key 是「page 索引」——密集的小整數(一個檔案的第 0,1,2,... 頁)。對「整數索引 + 密集」這個場景,XArray 用位數導航,比紅黑樹的逐層比較更直接、更省空間,也比雜湊表更適合「按順序的整數索引」(還能高效地做「範圍查詢」,例如預讀連續幾頁)。這正是 P2-T01 選型思維的體現:針對場景特性選最合適的結構。

對你的意義:page cache 是讀寫路徑的關鍵快取層(P5 會深入)。理解它是一個「offset → page」的 XArray,你就抓住了 kernel 快取檔案內容的核心機制——這直接關係你產品的 I/O 效能(命中 page cache 免去磁碟存取)。

5. 與紅黑樹/雜湊表的取捨

把三種查找結構放在一起,釐清各自的適用場景(綜合 P2-T01 的選型思維):

flowchart TB
    subgraph compare["三種查找結構,各擅長什麼"]
        HASH["雜湊表(P2-T04)
key 任意型別,平均 O(1),無序
適合:純『有沒有/找得到』,不需順序
弱點:最壞 O(n)、不能範圍查詢"]
        RBTREE["紅黑樹(P2-T05)
key 可比較,O(log n),有序
適合:需要排序、範圍、保證最壞
弱點:每次比較有成本、cache 不友善"]
        XARRAY["XArray / radix tree(本課)
key 是整數索引,密集時很高效,有序
適合:整數索引(offset/ID)、範圍、稀疏空間
弱點:key 必須是整數索引"]
    end
    style HASH fill:#6fa8b8,color:#10100e
    style RBTREE fill:#e8a33d,color:#10100e
    style XARRAY fill:#8a9a5b,color:#10100e

選型摘要: - key 是任意型別、只要快速判斷有無:雜湊表。 - key 可比較、需要排序或範圍、需要最壞保證:紅黑樹。 - key 是整數索引(尤其密集、需要範圍):XArray。

page cache 選 XArray,正是因為它的 key 是「整數 page 索引」且需要高效的順序/範圍存取(預讀)——這個場景下 XArray 勝過另外兩者。這再次印證 P2-T01:沒有最好的結構,只有最適合場景的結構。 kernel 在不同地方用不同結構,都是針對該場景的特性。

6. XArray 內建鎖語意:別自己全程加鎖

最後一個實務要點,呼應你 Phase 1 的並行知識(P1-T09)。XArray 內建了鎖語意——它自己處理了多數情況下的並行保護。

    XA["XArray 內建鎖(內部用一把鎖保護結構)"]
    XA --> SIMPLE["簡單操作(xa_load/xa_store):
XArray 自己加鎖保護
→ 你不必為這些操作自己包鎖"]
    XA --> ADVANCED["進階/複合操作:

(需要時依文件操作)"]
    NOTE["★ 常見誤區:以為要自己全程加鎖 ★
對基本操作,XArray 已處理好並行保護;
過度加鎖反而可能 double-lock 或降效能"]
    SIMPLE --> NOTE
    style XA fill:#e8a33d,color:#10100e
    style NOTE fill:#c2603a,color:#f4ecd8

重點:對基本的 xa_load/xa_store,XArray 內部已經加鎖保護,你不需要自己再包一層鎖。這是 XArray 比舊 radix tree 好用的地方之一。「以為要自己全程加鎖」是常見誤區——過度加鎖不只多餘,還可能造成問題(回顧 P1-T09 的死結風險)。當然,進階的複合操作(例如「查了之後根據結果再修改」)有它自己的鎖規則(xas_* 介面),那時要依文件正確處理。但基本存取,放心交給 XArray 的內建保護。

一句話總結:radix tree / XArray 專為「整數索引 → 值」設計,用位數導航、稀疏省空間(精神同多級分頁);XArray 是現代介面,新程式碼用它;它最著名的應用是 page cache(檔案 offset → 記憶體 page,命中免讀磁碟),這跟你的儲存 I/O 效能直接相關;基本操作有內建鎖,不必自己包。針對整數索引這個場景,它勝過雜湊表與紅黑樹——又一個 kernel 因場景制宜的選擇。

常見誤區與踩雷提醒

誤區一:用舊的 radix tree API(radix_tree_*)寫新程式。 應用 XArray(xa_load/xa_store 等)。舊 API 仍在舊程式碼中,但新東西用 XArray。

誤區二:以為要自己全程為 XArray 操作加鎖。 基本的 xa_load/xa_store 已有內建鎖保護,不必自己包。過度加鎖多餘且可能出問題(回顧 P1-T09)。進階複合操作才需依文件處理鎖。

誤區三:混淆 XArray(整數索引→指標)與一般雜湊表的用途。 XArray 專為「整數索引」設計(用位數導航、支援範圍/順序);雜湊表是任意 key、無序。page cache 用 XArray 正因 key 是 page 索引。

誤區四:以為密集整數就該用大陣列。 若索引空間大但稀疏(如大檔案的零星幾頁),大陣列浪費巨量空間。XArray 只為用到的索引花空間,兼得「index 直接定位」與「稀疏省空間」。

延伸與銜接

  • 對應工作場景:直接對應——page cache(VFS→block 之間的快取層,P5)以 XArray 索引 page;理解它是讀懂讀寫路徑快取的前置,直接關係你產品的 I/O 效能。
  • 這課餵給未來的:XArray/page cache → P5 的儲存堆疊與讀寫路徑(page cache 是其中關鍵一層);「稀疏整數索引」精神 → 回收並呼應 P1-T04 多級分頁;選型思維 → P2-T01 的延續。
  • 下一步 → P2-T07 bitmap 與點陣圖在 kernel 的應用:你已經學了幾種「查找/對應」結構。下一課回到一個更底層、源自 P0-T11 位元操作的工具——bitmap(點陣圖):用每一個 bit 代表一個資源的「已用/空閒」狀態,高效地管理大量資源的配置。kernel 用它做 CPU 親和性遮罩(cpumask)、區塊配置等。這跟你的儲存工作直接相關——blk-mq 用 tag(基於 bitmap 的 sbitmap)管理 in-flight 的 I/O request,NVMe 佇列深度也靠類似機制。這是理解 P5 tag 機制的前置。
