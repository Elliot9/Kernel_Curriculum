P2-T04 · 雜湊表與 kernel hlist

一句話:雜湊表用一個函式把 key 直接「算」成存放位置,達成平均 O(1) 的查找——但碰撞會讓它退化。kernel 為了在「大量雜湊桶」場景省記憶體,設計了只用單向頭的 hlist。理解碰撞與負載因子,你才能判斷雜湊表的效能。

為什麼要先學這個(導讀)

回顧 P2-T01:雜湊表的賣點是平均 O(1) 的查找/插入/刪除——比鏈結串列的 O(n) 快得多,而且不像平衡樹要 O(log n)。這讓它成為 kernel 裡「需要快速用 key 找 value」場景的常見選擇(例如 dentry cache——把路徑名快速對應到檔案系統項目)。

但 P2-T01 也警告過:雜湊表的 O(1) 是平均,最壞是 O(n)(碰撞嚴重時退化)。這一課就深入「為什麼會這樣、怎麼緩解」——理解雜湊函式、碰撞處理、負載因子,你才能判斷一個雜湊表在實際場景的效能,也才知道 kernel 何時用它、何時不用(改用有保證的平衡樹,見 P2-T05)。

這一課還會介紹 kernel 特有的雜湊串列 hlist。它是上一課 P2-T02 list_head 的一個變體:為了在「需要極大量雜湊桶」的場景省記憶體,hlist 的「頭」只用一個指標(而非 list_head 的兩個)。理解這個設計權衡,呼應 P2-T01「kernel 為不同場景做不同選擇」的主題。

為什麼這對你是 scope: indirect(間接對應)?因為 kernel 多處用雜湊表(dcache、各種以 key 查找的快取),理解碰撞與負載因子有助於你做效能分析。雖然不像 list_head/container_of 那樣每天直接寫,但讀 kernel code 會遇到 hlist,而雜湊的效能特性影響你對系統行為的判斷。

開始之前(前置確認)

  • 依賴:P2-T01(你知道雜湊表平均 O(1)、最壞 O(n)、負載因子的概念),也建議回顧 P2-T02(hlist 是 list_head 的變體)。
  • 自我檢測: 1. 你能說出「為什麼雜湊表的最壞情況是 O(n)」嗎?(回顧 P2-T01:全部碰撞到同一桶。)這課深入它。 2. 你還記得 P2-T02 侵入式串列的概念嗎?hlist 也是侵入式的。

核心內容

拆成這幾節:(1) 雜湊表的核心:用函式算出位置 → (2) 雜湊函式 → (3) 碰撞與鏈結法 → (4) 負載因子與重雜湊 → (5) 為什麼最壞 O(n) → (6) kernel 的 hlist:省一半指標,最後打通關。

1. 雜湊表的核心:不用「找」,直接「算」出位置

鏈結串列查找要一個個走(O(n)),因為你不知道東西在哪。雜湊表的革命性想法是:用一個函式,把 key 直接「算」成「它該存放的位置」——這樣查找時,同樣的函式算一次就知道去哪拿,不用走訪。

flowchart LR
    KEY["key(例如字串 'apple')"]
    HASH["雜湊函式 hash()
把 key 算成一個數字"]
    INDEX["索引(例如 3)"]
    BUCKET["桶陣列 buckets[]
直接去 buckets[3] 存/取"]
    KEY --> HASH --> INDEX --> BUCKET
    NOTE["查找:同樣 hash('apple')=3,
直接去 buckets[3] 拿 → O(1),不用走訪"]
    BUCKET --> NOTE
    style HASH fill:#e8a33d,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

核心結構:一個桶陣列(bucket array),加一個雜湊函式把 key 映射到陣列索引。存入時,算出索引,放進對應的桶;查找時,算出同一個索引,直接去那個桶找。因為「算索引」是 O(1)、「去陣列某格」也是 O(1)(回顧 P0-T03 陣列按索引存取 O(1)),所以平均查找是 O(1)。

比喻:像圖書館用「書的分類號」直接決定書放哪一櫃。你不用一櫃櫃找(走訪),只要算出分類號(雜湊),直接走到那一櫃(索引)拿書。分類規則(雜湊函式)讓「找書」變成「算位置 + 直接拿」。

2. 雜湊函式:把 key 變成索引

雜湊函式負責把任意 key(字串、數字、結構)轉成一個桶索引(0 到「桶數−1」之間的整數)。好的雜湊函式要滿足:

flowchart TB
    subgraph good["好的雜湊函式的特性"]
        DETERM["確定性:同一個 key
永遠算出同一個索引
(否則存進去就找不回來)"]
        UNIFORM["均勻分布:不同的 key
盡量平均散布到各個桶
(避免擠在少數桶 → 碰撞)"]
        FAST["快速:計算本身要快
(否則 O(1) 的優勢被慢函式抵銷)"]
    end
    style DETERM fill:#6fa8b8,color:#10100e
    style UNIFORM fill:#8a9a5b,color:#10100e
    style FAST fill:#e8a33d,color:#10100e

最關鍵的是均勻分布:如果雜湊函式把很多 key 都算到同一個索引(分布不均),那些 key 就全擠在同一個桶——這就是「碰撞」(下一節),會讓查找退化。一個常見的簡單做法是「先把 key 轉成一個大整數,再對桶數取餘數(模運算)」得到索引,但實際的雜湊函式設計要更講究均勻性。

雜湊函式分布不均是常見問題:它直接導致碰撞集中、效能退化。

3. 碰撞與鏈結法:兩個 key 算到同一個桶怎麼辦

無論雜湊函式多好,碰撞(collision) 終究會發生——兩個不同的 key 算出同一個索引(因為 key 的可能性遠多於桶的數量,鴿籠原理保證必有碰撞)。怎麼處理?最常見的方法是鏈結法(chaining):每個桶不是只存一個元素,而是掛一條鏈結串列,所有算到這個桶的元素都串在這條鏈上。

flowchart TB
    subgraph buckets["桶陣列(每桶掛一條鏈結串列)"]
        B0["buckets[0] → (空)"]
        B1["buckets[1] → 'apple' → 'lemon'
(兩個 key 都算到索引1,串成鏈)"]
        B2["buckets[2] → 'banana'"]
        B3["buckets[3] → (空)"]
    end
    LOOKUP["查找 'lemon':
① hash('lemon')=1 → 去 buckets[1]
② 走那條(通常很短的)鏈,比對找到 'lemon'"]
    buckets --> LOOKUP
    style B1 fill:#e8a33d,color:#10100e
    style LOOKUP fill:#8a9a5b,color:#10100e

鏈結法的運作:存入時,算出桶索引,把元素加到該桶的鏈上(回顧 P2-T02,kernel 用侵入式串列做這條鏈)。查找時,算出桶索引,然後走那條桶內的鏈比對 key。

關鍵:只要碰撞不嚴重,每條鏈都很短(平均長度接近「元素數 ÷ 桶數」),所以「走那條短鏈」幾乎是常數時間,整體維持平均 O(1)。問題出在碰撞嚴重時——那是第 5 節。

4. 負載因子與重雜湊:控制鏈不要變長

「碰撞嚴不嚴重」由一個指標衡量:負載因子(load factor)= 元素總數 ÷ 桶數。它代表「平均每個桶掛幾個元素」。

flowchart TB
    LF["負載因子 = 元素數 ÷ 桶數
(平均每桶的鏈長)"]
    LF --> LOW["負載因子低(例如 0.5):
平均每桶不到一個元素
→ 鏈很短,查找接近 O(1)
(但桶陣列較空,略浪費空間)"]
    LF --> HIGH["負載因子高(例如 5):
平均每桶掛 5 個
→ 鏈變長,查找變慢
(走鏈的成本上升)"]
    HIGH --> REHASH["解法:重雜湊(rehash)
當負載因子超過閾值,
把桶陣列擴大(例如翻倍),
重新分配所有元素 → 鏈再次變短"]
    style LOW fill:#8a9a5b,color:#10100e
    style HIGH fill:#c2603a,color:#f4ecd8
    style REHASH fill:#e8a33d,color:#10100e

直覺:負載因子越高,鏈越長,查找越慢(趨向 O(鏈長))。所以要控制負載因子——當它超過某個閾值(常見如 0.75),就重雜湊(rehash):配置更大的桶陣列,把所有元素重新算索引、重新分配。這讓鏈再次變短,恢復平均 O(1)。(重雜湊本身是 O(n) 的昂貴操作,但像動態陣列擴容一樣攤銷後可接受——回顧 P2-T01 攤銷分析。)

忽略負載因子與重雜湊是常見誤區:一個只增不擴的雜湊表,負載因子會越來越高,鏈越來越長,慢慢退化。

5. 為什麼最壞是 O(n):退化成一條鏈

現在能完整解釋 P2-T01 那個警告了。雜湊表的最壞情況:所有元素都碰撞到同一個桶。

flowchart TB
    WORST["最壞情況:雜湊函式很差,
或遇到惡意構造的 key,
使所有元素都算到同一個桶"]
    WORST --> DEGEN["那個桶的鏈,變成包含『全部 n 個元素』的長鏈
其他桶全空"]
    DEGEN --> RESULT["此時查找 = 走一條長度 n 的鏈
= O(n)
★ 退化成一條鏈結串列,失去雜湊表的優勢 ★"]
    style WORST fill:#c2603a,color:#f4ecd8
    style RESULT fill:#c2603a,color:#f4ecd8

當所有 key 都碰撞到同一桶,那個桶的鏈就包含全部 n 個元素,查找它就退化成「走一條長度 n 的串列」= O(n)。這就是雜湊表「平均 O(1)、最壞 O(n)」的由來。

實務上,好的雜湊函式讓最壞情況極罕見(均勻分布)。但有兩種情況要當心:雜湊函式設計不良(分布不均),或對抗惡意輸入(攻擊者故意構造大量碰撞的 key 來癱瘓系統,這叫雜湊碰撞攻擊)。對「不能容忍最壞 O(n)」的場景,kernel 會改用有保證的平衡樹(回顧 P2-T01 的選型討論,銜接 P2-T05)。

把第 4 節的重雜湊畫成「前後對照」,你會更清楚它如何把長鏈重新攤平:

        BN["桶數=2,元素=6 → 負載因子=3"]

        A3["buckets[3] → f → ..."]

重雜湊本身是 O(n)(要重新分配全部元素),但像動態陣列擴容一樣攤銷後可接受(回顧 P2-T01 攤銷分析)——換來鏈重新變短、查找恢復平均 O(1)。

6. kernel 的 hlist:為大量雜湊桶省一半指標

最後看 kernel 特有的設計。kernel 做雜湊表時,桶陣列裡的鏈用的不是上一課的 list_head,而是一個變體 hlist。為什麼要另一個?關鍵在「桶陣列可能極大」(成千上萬個桶),而每個桶都需要一個「鏈頭」。

回顧 P2-T02:list_head 有兩個指標(next + prev),是雙向環狀。但對雜湊桶的「頭」,kernel 發現:桶陣列有海量個頭,如果每個頭都用兩個指標,光是頭的指標就佔掉大量記憶體。於是 hlist 的頭只用一個指標:

    subgraph compare["list_head vs hlist 的頭"]
        LH["list_head 當頭:
next + prev(2 個指標)
雙向環狀"]
        HL["hlist_head 當頭:
只有 first(1 個指標)
→ 海量桶時省一半頭的記憶體"]
    end
    LH -.“雜湊桶有成千上萬個頭
→ 省指標很划算”.-> HL
    NOTE["hlist_node(鏈上的節點)仍保有
往回指的能力(用特殊技巧),
所以節點刪除仍 O(1);
只有『頭』被精簡成單指標"]
    HL --> NOTE
    style LH fill:#6fa8b8,color:#10100e
    style HL fill:#e8a33d,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

設計權衡: - hlist_head(桶的頭)只有一個 first 指標——指向鏈上第一個節點。因為雜湊桶數量龐大,每個頭省一個指標,總共省下可觀記憶體。 - hlist_node(鏈上的節點) 仍能做到 O(1) 刪除(透過一個指向「前一個節點的 next 指標」的巧妙設計,而非直接 prev 指標)。所以精簡的只是「頭」,節點操作的效率還在。

這是一個典型的 kernel 設計權衡(呼應 P2-T01):在「雜湊桶有海量個頭」這個特定場景,用 hlist 犧牲一點點(頭不再是對稱的雙向),換取大量記憶體節省。list_head(雙向環狀)和 hlist(單向頭)各有適用場景——一般串列用前者,雜湊桶用後者。混淆兩者的適用場景是常見誤區:看到 hlist 就知道「這是雜湊用的、頭省了一個指標」。

一句話總結:雜湊表用雜湊函式把 key 直接算成存放位置,達成平均 O(1),碰撞用鏈結法處理、靠負載因子與重雜湊維持短鏈;但最壞會退化成 O(n)(全碰撞),所以需要保證時改用平衡樹;kernel 的 hlist 則為「海量雜湊桶」場景把頭精簡成單指標來省記憶體——又一個 kernel 因場景制宜的設計權衡。

常見誤區與踩雷提醒

誤區一:以為雜湊表查找一定 O(1)。 那是平均。碰撞嚴重時(差雜湊函式或惡意輸入)退化成 O(n)。要保證最壞情況,用平衡樹(P2-T05)。

誤區二:雜湊函式分布不均。 不均勻會讓碰撞集中在少數桶,鏈變長,效能退化。好的雜湊函式要均勻分布。

誤區三:忽略負載因子與重雜湊。 只增不擴的雜湊表,負載因子持續升高、鏈持續變長、慢慢退化。要監控負載因子,超閾值就重雜湊。

誤區四:混淆 hlist(單向頭、省一半)與 list(雙向環狀)的適用場景。 hlist 為海量雜湊桶省記憶體(頭只一個指標);一般串列用 list_head。看到 hlist 就知道是雜湊相關。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 實作鏈結法雜湊表(驗收點) 實作一個用鏈結法處理碰撞的雜湊表(桶陣列 + 每桶一條鏈結串列,可用你 P0-T12 或 P2-T02 的串列)。提供 insert(key, value)、lookup(key)。插入 1000 筆(key 可用整數或字串),驗證:查找命中率 100%(每筆都找得回來),且能正確處理碰撞(多個 key 落同一桶時,鏈上能區分)。

任務 B — 計算負載因子(驗收點) 承任務 A:給定你的桶數(例如 128)和插入的筆數(1000),計算負載因子(1000 ÷ 128 ≈ 7.8)。觀察:平均每桶鏈長約 7.8,查找一筆平均要走約 7.8 步。寫一句話:如果把桶數增加到 2048,負載因子變多少?查找會變快還是變慢?

任務 C — 觀察退化(體會最壞情況) 故意用一個很爛的雜湊函式(例如永遠回傳 0,讓所有 key 都進 buckets[0]),插入 1000 筆,觀察它退化成一條長鏈,查找變 O(n)(可計時對比好雜湊函式)。寫一句話:這對應第 5 節的什麼情況?

任務 D — 讀懂 hlist 與 list 的差異(驗收點) 閱讀 Bootlin 上 list.h 裡的 hlist 部分(https://elixir.bootlin.com/linux/v6.12/source/include/linux/list.h ),對照 list_head。用一句話說明:hlist_head 為什麼只有一個指標?它適合什麼場景?(提示:海量雜湊桶,每個頭省一個指標。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 實作鏈結法雜湊表,插入 1000 筆後查找命中率 100%、且能處理碰撞。 2. ☐ 用一句話說明 hlist_head 為何只有一個指標、適合大量雜湊桶。 3. ☐ 計算給定容量與筆數的負載因子。

延伸與銜接

  • 對應工作場景:間接對應——kernel 多處用雜湊表(dcache、page 相關查找);理解碰撞與負載因子有助於效能分析。讀 kernel code 會遇到 hlist。
  • 這課餵給未來的:雜湊表的平均/最壞特性 → 理解 kernel 各種快取的效能;hlist → kernel 雜湊相關程式碼;「平均 vs 最壞」的權衡 → 緊接的 P2-T05(為何需要有保證的平衡樹)。
  • 下一步 → P2-T05 二元搜尋樹到紅黑樹:雜湊表平均快但最壞會退化。下一課介紹一個有保證的結構——紅黑樹:它犧牲一點平均速度(O(log n) 而非 O(1)),換來「即使最壞也保證 O(log n)」,而且能有序走訪(雜湊表做不到)。這正是 kernel 在 I/O 排程器、計時器、VMA 管理選紅黑樹的原因。你會學它的性質(不必背證明)和 kernel rbtree 的使用方式——讀 block layer 排程器程式碼會遇到。
