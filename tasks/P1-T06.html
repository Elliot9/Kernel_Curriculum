P1-T06 · context switch 與系統呼叫、使用者/核心邊界

一句話:你的程式不能直接碰硬體或核心資料——中間有一道由 CPU 特權級守衛的牆。要做檔案 I/O、要跟你的 kernel module 溝通,都得透過「系統呼叫」這道受控的閘門跨越這道牆。理解這道牆與跨越它的成本,就是理解你產品「user space app + kernel module」架構的本質。

為什麼要先學這個(導讀)

你的產品架構,一句話描述就是:「一個 user space 應用程式,透過系統呼叫和你自己寫的 kernel module 溝通。」這一課就是要把這句話裡的每個機制講透。

核心概念是一道邊界:CPU 有兩種執行模式——使用者態(user mode)和核心態(kernel mode)。你的應用程式跑在使用者態,權限受限:它不能直接存取硬體、不能碰其他行程的記憶體、不能執行特權指令。而作業系統核心跑在核心態,擁有完全的權限。

這道牆是必要的(回顧 P1-T04 的隔離與保護):它防止任何一支程式(無論是 bug 還是惡意)直接搞壞硬體或別的程式。但你的程式總得做些「需要特權」的事——讀寫檔案、配置記憶體、跟裝置溝通。怎麼辦?透過系統呼叫(system call, syscall):一個受控的閘門,讓使用者態程式「請求」核心代為執行特權操作。

為什麼這對你是 scope: direct?因為: 1. 你產品的核心溝通就是 syscall:user space app 透過系統呼叫(以及你自寫 module 提供的介面)請求 kernel 做事。 2. 這道邊界有成本:每次跨越(user→kernel→user)都有開銷。理解這個成本,正是為什麼高效能資料路徑要追求「零拷貝(zero-copy)」、要減少跨界次數——這是你日後設計資料路徑的關鍵考量(也是 GDS 等技術的動機)。 3. 跨界傳資料有陷阱:核心態不能隨意解參考使用者態的指標(它們屬於不同的保護域),必須用 copy_from_user/copy_to_user(P4)。這個規則的根源就在這一課的邊界概念。

  • 自我檢測: 1. 你能說出「為什麼一支程式不該能直接存取硬體或別的行程記憶體」嗎?(隔離與保護,回顧 P1-T04。) 2. 你寫過呼叫 printf、open、read 的程式嗎?這課會揭露:這些底層其實(部分)透過 syscall 進入 kernel。

核心內容

拆成這幾節:(1) 兩種模式:user mode vs kernel mode → (2) 特權級這道牆 → (3) 系統呼叫:跨牆的閘門(trap)→ (4) 一次 write() 的完整旅程 → (5) libc 函式 ≠ syscall → (6) context switch 與其成本,最後打通關。

1. 兩種執行模式:使用者態與核心態

CPU 在任何時刻,都處於兩種模式之一:

你的程式預設在使用者態,被「關在」一個受限的沙盒裡。這不是懲罰,是保護:正因為應用程式不能直接碰硬體和別人的記憶體,一支程式崩潰或被攻擊,才不會直接危害整個系統。

比喻:使用者態像銀行的「大廳」,核心態像「金庫」。一般客戶(應用程式)只能在大廳活動,不能直接走進金庫拿錢。要存取金庫裡的東西,你得透過櫃台(系統呼叫)提出請求,由有權限的行員(核心)代為處理。

2. 特權級:這道牆由硬體強制

「使用者態不能做特權操作」不是靠軟體自律,而是CPU 硬體強制的。CPU 有「特權級(privilege level)」的概念(x86 上叫 ring),核心態是最高特權(ring 0),使用者態是低特權(ring 3)。

flowchart TB
    TRY["使用者態程式試圖
執行特權操作
(例:直接對硬體下指令、
存取核心記憶體)"]
    HW["CPU 硬體檢查當前特權級"]
    TRY --> HW
    HW --> BLOCK["當前是使用者態(低特權)
→ 硬體拒絕,觸發例外
→ 通常程式被殺(或 segfault)"]
    style TRY fill:#6fa8b8,color:#10100e
    style BLOCK fill:#c2603a,color:#f4ecd8

這就是為什麼你的應用程式無法繞過核心直接亂搞硬體——即使你想,CPU 硬體層級也會擋下來。要做特權操作,唯一合法途徑是「請核心代勞」,而請核心代勞的方式,就是系統呼叫。

3. 系統呼叫:跨牆的受控閘門(trap)

系統呼叫是使用者態程式請求核心服務的機制。關鍵在於它不是普通的函式呼叫——普通函式呼叫只是在使用者態內跳轉,而系統呼叫要跨越特權邊界,從使用者態進入核心態。

這個跨越透過一個特殊的硬體機制完成,叫 trap(或 syscall 指令)。它的作用是:安全、受控地把 CPU 從使用者態切換到核心態,並跳到核心預先設定好的入口點。

    S2["執行特殊的 syscall/trap 指令"]

    S4["核心檢查:這個請求合法嗎?

    S5["核心以完全權限執行該操作
(真正去讀硬體/碰核心資料)"]

執行返回指令"]

    style S7 fill:#8a9a5b,color:#10100e

為什麼是「受控」的閘門很重要:程式不能跳到核心的任意位置(那樣就能繞過檢查為所欲為)。trap 指令只能跳到核心預先設定的固定入口,核心在那裡先檢查請求是否合法、參數是否安全,確認沒問題才執行。這就像銀行櫃台——你不能自己衝進金庫,只能在櫃台提出請求,由行員審核後代辦。

比喻:trap 像按下櫃台的服務鈴。你(使用者態)不能自己進金庫,但你按鈴、遞上填好的單子(系統呼叫編號 + 參數),行員(核心)接手、審核、用他的權限去金庫辦事,辦完把結果遞回給你。整個過程你從未真正進入金庫,但你的需求被安全地滿足了。

4. 一次 write() 的完整旅程

把第 3 節落地成一個具體例子:當你的程式呼叫 write(fd, buf, n) 想把資料寫進檔案,完整發生了什麼:

    B["② wrapper 把系統呼叫編號(write 的號碼)
和參數(fd, buf 的位址, n)放進約定暫存器

分派到處理 write 的核心函式
檢查 fd 合法、參數安全"]
    E["⑤ 核心執行寫入
(把 buf 的資料交給檔案系統/驅動,
最終可能寫到裝置)
※ 注意:核心要讀 user 的 buf,
須用 copy_from_user,不能直接解參考"]

注意第⑤步那個註記:核心要讀使用者態的 buf,不能直接解參考那個指標。為什麼?因為 buf 是使用者態程式的虛擬位址(回顧 P1-T04),它屬於使用者的位址空間/保護域;核心若隨意解參考它,可能讀到錯的東西或被惡意指標攻擊。所以核心必須用專門的 copy_from_user() 函式來安全地把資料從使用者空間搬進核心空間。

把這個「為什麼不能直接解參考、要用 copy_from_user」畫出來,因為它是你寫 module 時天天遇到的鐵則:

這個規則(P4 會詳細用到)的根源,就是這一課的「使用者/核心是不同保護域」。 你寫 module 跟 user space app 交換資料時,天天會用到它。

5. 釐清:呼叫 libc 函式 ≠ 系統呼叫

一個重要的誤解要澄清:你呼叫的很多函式(像 printf、malloc)不是系統呼叫,而是 libc 提供的「包裝(wrapper)」,它們在使用者態做一些事,必要時才真正發出系統呼叫進入核心。

flowchart TB
    subgraph nosys["不一定觸發 syscall 的"]
        PRINTF["printf(...)
先在使用者態的緩衝區
組織字串、可能暫存
→ 累積夠了才用 write syscall 真正輸出"]
        MALLOC["malloc(小塊)
可能從 libc 已向核心要來的
記憶體池裡直接切一塊
→ 不必每次都進核心"]
    end
    subgraph yessys["真正的 syscall(trap 進核心)"]
        WRITE["write / read / openat /
mmap / ..."]
    end
    PRINTF -.“必要時才呼叫”.-> WRITE
    style PRINTF fill:#6fa8b8,color:#10100e
    style WRITE fill:#c2603a,color:#f4ecd8

為什麼這個區別重要?因為系統呼叫有成本(第 6 節),libc 會盡量「批次化、緩衝」來減少進核心的次數。例如 printf 不是每次都立刻 syscall,而是先在使用者態緩衝,湊一批再用一次 write 送出——這減少了昂貴的跨界次數。理解「哪些是真 syscall、哪些只是 libc wrapper」,你才能推理程式的效能,也才知道用 strace(專門追蹤真正的 syscall 的工具)看到的是什麼。

6. context switch:切換執行中的 task,以及它的成本

最後一塊:context switch(上下文切換)——CPU 從執行一個 task(行程/執行緒)切換到執行另一個。這發生在:時間片用完(被搶佔)、task 等待 I/O 而讓出、或更高優先權的 task 要跑。

「切換」要做什麼?CPU 只有一套暫存器(回顧 P1-T01),但要輪流跑多個 task,所以切換時必須保存當前 task 的狀態、載入下一個 task 的狀態:

flowchart TB
    S1["決定從 task A 切換到 task B
(時間片到 / A 等 I/O / B 優先權更高)"]
    S2["保存 A 的上下文:
所有暫存器、PC(RIP)、堆疊指標(RSP)等
存到 A 的核心資料結構"]
    S3["載入 B 的上下文:
把 B 之前保存的暫存器、PC、SP 還原
(若 B 是不同行程,還要切換位址空間
= 換分頁表 → TLB 可能 flush!)"]
    S4["CPU 從 B 上次中斷的地方繼續執行"]
    S1 --> S2 --> S3 --> S4
    COST["成本來源:
① 保存/載入大量暫存器狀態
② 若跨行程:換位址空間 + TLB flush(回顧 P1-T04)
③ 切換後 cache/TLB 對新 task 是冷的,要重新暖機"]
    S4 --> COST
    style S2 fill:#e8a33d,color:#10100e
    style S3 fill:#e8a33d,color:#10100e
    style COST fill:#c2603a,color:#f4ecd8

為什麼切換有成本,這張圖說清楚了:不只是保存/載入暫存器(這已經要花時間),如果切換到不同行程,還要換整個位址空間(換分頁表),這會讓 TLB 失效(回顧 P1-T04 第 7 節),切換後 TLB 和 cache 對新 task 都是「冷的」,需要重新暖機——這些隱藏成本加起來不容忽視。

這和系統呼叫的成本一起,構成「跨界與切換都不免費」的整體認知——這正是為什麼你產品的高效能資料路徑要盡量減少 syscall 次數、減少不必要的拷貝(零拷貝)、減少 context switch。GDS(GPUDirect Storage)這類技術的核心動機,就是讓資料從儲存裝置直接到 GPU,繞過「進核心、拷貝到使用者態、再拷貝給 GPU」這條充滿跨界與拷貝的傳統路徑。你現在懂了那個「貴」在哪裡。

一句話總結:CPU 用特權級築起使用者/核心的牆來保護系統,系統呼叫(trap)是跨牆的唯一受控閘門,而跨界與 context switch 都有實實在在的成本——這道牆與其成本,既是你產品「user space app + kernel module」架構的本質,也是你日後追求零拷貝、減少跨界的高效能資料路徑設計的根本動機。

常見誤區與踩雷提醒

誤區一:以為呼叫 libc 函式就是系統呼叫。 多數 libc 函式是 wrapper,在使用者態做事,必要時才 trap 進核心。真正的 syscall 是 trap 指令。用 strace 看到的才是真 syscall。

誤區二:低估 user↔kernel 切換的成本。 每次跨界都有開銷;context switch(尤其跨行程,含 TLB flush)更貴。這正是零拷貝、減少 syscall 次數要避免的——也是 GDS 等技術的動機。

誤區三:以為核心態能直接解參考任意使用者指標。 不行。使用者指標屬於使用者的位址空間/保護域,核心須用 copy_from_user/copy_to_user 安全搬運(P4)。直接解參考可能讀到錯的東西或被惡意指標攻擊。

誤區四:把 context switch 想成「只是換暫存器」。 還包括(跨行程時)換位址空間、TLB flush、以及切換後 cache/TLB 對新 task 是冷的要重新暖機。隱藏成本不少。

評分量表: - 60(及格):能複述使用者/核心邊界概念。 - 80(熟練):能完成 syscall lab。 - 100(精通):能對應到自家產品的 user/kernel 分界與其溝通成本,並解釋為何高效能路徑要減少跨界。

延伸與銜接

  • 對應工作場景:直接對應——你產品的核心架構就是 user space app 透過系統呼叫/自寫 module 與 kernel 溝通;理解此邊界與成本是設計零拷貝資料路徑的關鍵。
  • 這課餵給未來的:user/kernel 邊界 → P4 寫 module 時的 copy_from_user/copy_to_user、字元裝置的 read/write;跨界成本 → 零拷貝資料路徑、GDS(P7);context switch → P1-T07 排程決定何時切換。
  • 下一步 → P1-T07 CPU 排程:你已經知道 context switch 是「切換 task」的機制。下一課回答「誰來決定切換到哪個 task、何時切換」——這就是 CPU 排程器的工作。理解排程目標與演算法(公平?吞吐?低延遲?),是日後讀懂 Linux 的 EEVDF 排程器(P3-T12)、以及理解你的 kthread/workqueue 何時會被排到執行的前置。
