P3-T05 · kernel 編碼風格與 checkpatch

一句話:kernel 有一套嚴格而具體的編碼風格(tab=8、命名、大括號擺放),不是美學潔癖,而是讓全球數千名開發者讀同一份程式碼時不必各自適應。checkpatch.pl 幫你自動檢查,而一則好的 commit message 解釋的是「為什麼改」而非「改了什麼」。

為什麼要先學這個(導讀)

寫得出 module 之後,下一步是寫得符合規範。這聽起來次要,但其實是門檻:無論是你公司內部的 code review,還是日後向 kernel upstream 貢獻,不合規的程式碼會直接被擋下來。

kernel coding style 為什麼這麼嚴格?因為 kernel 是全球數千名開發者協作的專案,程式碼會被無數人閱讀、修改、維護幾十年。如果每個人用自己的風格,讀別人的程式碼就要不斷切換腦袋。一致的風格讓任何人讀任何一段 kernel code 都不必重新適應——縮排一致、命名一致、結構一致。這對協作的價值遠超過「個人偏好」。

kernel 提供 checkpatch.pl 這個腳本,自動檢查你的程式碼是否符合風格(縮排、行寬、命名、各種慣例)。它會列出 errors 和 warnings,你修正它們,程式碼就達到基本規範。

這一課還包含 commit message 規範——這常被新手忽視,但極重要。一則好的 commit message 解釋的是「為什麼做這個改動」(動機、解決什麼問題),而不是流水帳般描述「改了哪幾行」(那看 diff 就知道)。

為什麼這對你是 scope: direct?因為無論內部 code review 或向 upstream 貢獻,一致風格都是基本門檻。你產品的 module 程式碼若要被同事 review、若要部分回饋給社群,都得過這關。這一課也為 P3-T15「第一個 patch」鋪路。

開始之前(前置確認)

  • 依賴:P3-T03(你有 module 程式碼可以拿來檢查)。
  • 自我檢測: 1. 你寫 P3-T03/P3-T04 的 module 時,用的是 tab 還是空白縮排?行寬有沒有控制?這課會檢查這些。 2. 你寫過 git commit message 嗎?這課教 kernel 風格的寫法。
  • 工具:kernel 原始碼樹裡的 scripts/checkpatch.pl(https://elixir.bootlin.com/linux/v6.12/source/scripts/checkpatch.pl ）。

核心內容

拆成這幾節:(1) 為何一致風格重要 → (2) 主要風格規則 → (3) checkpatch.pl 用法 → (4) 常見警告與判斷 → (5) commit message 規範,最後打通關。

1. 為何一致風格重要:協作的潤滑劑

先建立心態:kernel coding style 不是「某人的美學偏好」,而是大規模協作的潤滑劑。

flowchart TB
    PROBLEM["kernel:數千開發者、數十年維護、無數人讀同一份程式碼"]
    PROBLEM --> WITHOUT["若各用各的風格:
讀每段程式碼都要切換腦袋
(這人用 4 空白、那人用 tab、
大括號擺法各異...)
→ 認知負擔大,易出錯"]
    PROBLEM --> WITH["統一風格:
任何人讀任何程式碼都不必重新適應
→ 降低認知負擔,專注在邏輯本身"]
    style WITHOUT fill:#c2603a,color:#f4ecd8
    style WITH fill:#8a9a5b,color:#10100e

核心:一致性 > 個人偏好。 即使你個人偏好別的風格,在 kernel(或任何大型協作專案)裡,遵守統一風格的價值遠超過堅持己見。「以為風格可有可無」是常見誤區——upstream 和多數公司的 review 會直接擋下不合規的程式碼。把它當成「協作的基本禮儀」。

2. 主要風格規則

kernel coding style 的主要規則(完整見官方文件,這裡是最常踩的):

flowchart TB
    subgraph rules["kernel coding style 主要規則"]
        TAB["縮排:用 tab,且 tab = 8 格
(不是空白!不是 4 格!)
→ 深縮排逼你拆分過深的巢狀"]
        WIDTH["行寬:傳統 80 欄(現較寬鬆,但仍以可讀為準)"]
        BRACE["大括號:函式的 { 另起一行;
其他(if/for/while)的 { 接在同一行"]
        NAME["命名:小寫 + 底線(snake_case),
不用駝峰;名稱簡潔有意義"]
        COMMENT["註解:用 /* */ 風格;
解釋『為什麼』而非『做什麼』"]
    end
    style TAB fill:#e8a33d,color:#10100e
    style BRACE fill:#6fa8b8,color:#10100e

幾個最常踩的: - 縮排用 tab,tab = 8 格(常見誤區:用空白、或用 4 格)。8 格的深縮排是刻意的——它讓「巢狀太深」變得明顯難看,逼你重構(kernel 風格認為超過 3 層巢狀就該考慮拆函式)。 - 大括號:函式的開括號 { 另起一行;控制結構(if/for/while)的 { 接在條件同一行。 - 命名:snake_case(小寫加底線),不用駝峰(camelCase)。 - 行寬:傳統 80 欄(現代較寬鬆,但仍以可讀為原則)。

這些規則你不必死背——checkpatch.pl(下一節)會幫你抓出違規。但理解「為什麼」(尤其 tab=8 逼你重構深巢狀)能讓你寫出更合規的程式碼。

把「tab=8 如何逼你重構」這個用意畫出來:

flowchart TB
    DEEP["巢狀很深的程式碼(if 裡 for 裡 if 裡...)"]
    DEEP --> TAB8["用 tab=8 縮排"]
    TAB8 --> WIDE["每深一層就右移 8 格
→ 深巢狀很快撞到行寬、變得明顯難看"]
    WIDE --> PRESSURE["★ 這股『難看』的壓力,逼你重構 ★
(把深巢狀抽成獨立函式、提早 return 減少縮排)"]
    PRESSURE --> RESULT2["結果:kernel 程式碼傾向『淺巢狀、小函式』
(風格不只是外觀,還引導出更好的結構)"]
    style TAB8 fill:#6fa8b8,color:#10100e
    style PRESSURE fill:#e8a33d,color:#10100e
    style RESULT2 fill:#8a9a5b,color:#10100e

3. checkpatch.pl 用法

checkpatch.pl 是 kernel 原始碼樹 scripts/ 裡的腳本,自動檢查程式碼是否合規。對你的 out-of-tree module,常用:

flowchart LR
    CMD["scripts/checkpatch.pl --file --no-tree your_module.c"]
    CMD --> OUTPUT["輸出:
ERROR:... (必須修)
WARNING:... (應該修,部分需判斷)
+ 每個問題的行號與說明"]
    OUTPUT --> FIX["逐一修正
(目標:0 errors,
warnings 降到可解釋的最低)"]
    style CMD fill:#6fa8b8,color:#10100e
    style FIX fill:#8a9a5b,color:#10100e

要點: - --file:檢查一個完整檔案(而非 patch)。對你的 module 原始碼用這個。 - --no-tree:告訴它你不在 kernel 原始碼樹裡跑(out-of-tree module 用)。 - 輸出分 ERROR(必須修)和 WARNING(應該修,但部分需要判斷)。每個都附行號和說明。

也可以檢查一個 git patch(checkpatch.pl your.patch),這在 P3-T15 送 patch 時用。

4. 常見警告與判斷:別盲目消除

一個重要的態度:不是所有 checkpatch 警告都該無腦消除。多數該修,但有些需要判斷。

flowchart TB
    WARNINGS["checkpatch 警告"]
    WARNINGS --> CLEAR["多數:明確該修
(用空白非 tab、行尾空白、
缺 MODULE_LICENSE、printk 沒換行...)"]
    WARNINGS --> JUDGE["少數:需判斷
(例如某些『行太長』的警告,
硬拆反而更難讀;
或某些慣例在特定情境不適用)"]
    JUDGE --> PRINCIPLE["原則:理解每個警告在說什麼,
該修的修,需保留的能解釋為什麼
★ 不盲目消除、也不全部忽略 ★"]
    style CLEAR fill:#8a9a5b,color:#10100e
    style JUDGE fill:#e8a33d,color:#10100e
    style PRINCIPLE fill:#6fa8b8,color:#10100e

常見誤區:盲目消除 checkpatch 警告而不理解——大多數警告該修(縮排、行尾空白、命名等),但少數需要判斷(例如硬把一行拆短反而更難讀)。正確態度是:理解每個警告的意義,該修的修,真的需要保留的(罕見)要能解釋為什麼。目標是「0 errors,warnings 降到可解釋的最低」(驗收標準),而非「機械式清零」。

5. commit message 規範:解釋「為什麼」

最後一個常被忽視但極重要的主題:commit message。kernel(和多數嚴謹專案)對 commit message 有規範:

flowchart TB
    subgraph format["kernel commit message 結構"]
        SUBJECT["主旨行(subject):
簡短(約 50 字內)、一句話講這個改動做什麼
常帶子系統前綴,如 'nvme: fix ...'"]
        BLANK["(空一行)"]
        BODY["內文(body):
★ 解釋『為什麼』做這個改動 ★
(問題是什麼、為何這樣解、有什麼影響)
而非流水帳描述『改了哪幾行』(看 diff 就知道)"]
        SIGN["署名(如 Signed-off-by,送 upstream 時)"]
        SUBJECT --> BLANK --> BODY --> SIGN
    end
    style SUBJECT fill:#6fa8b8,color:#10100e
    style BODY fill:#e8a33d,color:#10100e

關鍵原則:commit message 解釋「為什麼」,不是「改了什麼」。 - 主旨行:一句話、簡短,說這個 commit 做什麼(常帶子系統前綴)。 - 內文:解釋動機——你在解決什麼問題、為什麼用這個方法、有什麼影響或副作用。這是給未來的人(包括你自己)看的:diff 能告訴他們「改了什麼」,但只有 commit message 能告訴他們「為什麼要改」。

常見誤區:commit message 寫成流水帳而非「為何改」——「修改了 foo 函式,增加了 bar 變數」是流水帳(看 diff 就知道);「foo 在高並行下會 race,因為...,故加鎖保護」才是有價值的 message(解釋為什麼)。一則好的 commit message 在幾年後還能讓人理解這個改動的來龍去脈。

把「流水帳 vs 好 message」並排對照:

flowchart TB
    subgraph bad2["✗ 流水帳(看 diff 就知道,沒價值)"]
        B_1["主旨:改了 foo.c"]
        B_2["內文:把 foo() 加了一個參數,
新增 bar 變數,改了第 42 行"]
    end
    subgraph good2["✓ 解釋為什麼(幾年後仍有價值)"]
        G_1["主旨:foo: fix race on shared counter"]
        G_2["內文:多執行緒同時呼叫 foo() 時,
counter 的讀-改-寫會交錯遺失更新(P1-T08),
導致統計值偏低。改用 spinlock 保護該臨界區。"]
    end
    bad2 -.“diff 已說明『改了什麼』,
message 要說『為什麼改』”.-> good2
    style B_2 fill:#c2603a,color:#f4ecd8
    style G_2 fill:#8a9a5b,color:#10100e

打通關:把編碼風格收攏成一個心智模型

flowchart TB
    WHY["核心心態:一致性 > 個人偏好
(大規模協作的潤滑劑,不是美學潔癖)"]
    WHY --> STYLE["主要規則:tab=8、命名 snake_case、
大括號擺放、行寬、註解解釋為什麼"]
    STYLE --> CHECK["工具:checkpatch.pl --file --no-tree
→ 0 errors,warnings 降到可解釋的最低"]
    CHECK --> JUDGE["★ 不盲目消除:理解每個警告,該修的修 ★"]
    WHY --> COMMIT["commit message:主旨行 + 內文
★ 解釋『為什麼改』而非流水帳『改了什麼』★"]
    JUDGE --> BAR["= 內部 review 與 upstream 貢獻的基本門檻"]
    COMMIT --> BAR
    style WHY fill:#6fa8b8,color:#10100e
    style CHECK fill:#e8a33d,color:#10100e
    style BAR fill:#8a9a5b,color:#10100e

一句話總結:kernel coding style 是大規模協作的潤滑劑(一致性 > 個人偏好):tab=8、snake_case、固定的大括號擺放,用 checkpatch.pl 檢查到 0 errors(但理解每個警告、不盲目消除),並寫解釋「為什麼改」而非「改了什麼」的 commit message——這些是內部 review 與 upstream 貢獻的基本門檻,也為你的第一個 patch 鋪路。

常見誤區與踩雷提醒

誤區一:用空白而非 tab、行寬超限。 kernel 用 tab(=8 格)縮排。用空白、或用 4 格 tab,checkpatch 會抓。

誤區二:commit message 寫成流水帳而非「為何改」。 diff 已說明「改了什麼」;commit message 要解釋「為什麼改」(動機、問題、影響)。

誤區三:以為風格可有可無。 upstream 與多數公司 review 會擋下不合規程式碼。一致風格是協作門檻,不是選配。

誤區四:盲目消除 checkpatch 警告而不理解。 多數警告該修,但少數需判斷(硬拆反而更難讀的情況)。理解每個警告,該修的修,需保留的能解釋。

動手實作

環境:Linux 終端機,純檢查/編輯,無系統風險(checkpatch 是使用者態腳本)。

任務 A — 對你的 module 跑 checkpatch(驗收點) 拿 P3-T03 或 P3-T04 的 module 原始碼,跑:

scripts/checkpatch.pl --file --no-tree your_module.c

（scripts/checkpatch.pl 在 kernel 原始碼樹裡。）看它報出的 errors 和 warnings。逐一修正(理解每個在說什麼)。目標:0 errors,warnings 降到可解釋的最低。驗收:檢查後 0 errors、warnings 降到最低。

任務 B — 故意製造違規再修(體會用) 故意把 module 裡某段縮排改成空白(或 4 格)、某行加到很長、行尾留空白,重跑 checkpatch,看它如何抓出這些。然後改回合規。體會 checkpatch 抓什麼。

任務 C — 寫一則合規 commit message(驗收點) 為你 module 的一個假想改動(例如「加上 queue_depth 參數」),寫一則合規的 commit message: - 主旨行:簡短、一句話(可帶前綴)。 - 空一行。 - 內文:解釋為什麼做這個改動(不是流水帳)。 驗收:產出含「主旨行 + 內文說明動機」的合規 commit message。

任務 D — 理解 tab=8 的用意 寫一兩句話:為什麼 kernel 用 tab=8 的深縮排?(提示:讓巢狀太深變得明顯難看,逼你重構/拆函式。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ module 程式碼經 checkpatch.pl --file --no-tree 檢查後 0 errors、warnings 降到可解釋的最低。 2. ☐ 產出一則含「主旨行 + 內文說明動機」的合規 commit message。

評分量表: - 60(及格):能跑 checkpatch。 - 80(熟練):能修正並理解多數警告。 - 100(精通):能寫出可送 upstream 等級的 patch 與 commit message。
