P3-T07 · kernel 記憶體管理(二)—— kmalloc / slab(SLUB) / vmalloc / GFP flags

一句話:kmalloc 配小塊且實體連續、vmalloc 配大塊但只虛擬連續、slab 快取重複利用同型別物件——而比「用哪個」更致命的是「用哪個 GFP flag」:在持有 spinlock 或中斷 context 裡用了會睡眠的 GFP_KERNEL,整個系統就死結。

為什麼要先學這個(導讀)

上一課 P3-T06 講的是「以頁為單位」的底層配置。但你寫 module 時,大多數時候要的不是整頁,而是小物件——一個結構、一個緩衝區,幾十到幾百 bytes。這一課講上層的配置器,以及一個會直接造成系統死結的關鍵規則。

幾個工具: - kmalloc/kfree/kzalloc:配置小塊記憶體,實體連續(像使用者態的 malloc,但在核心、且實體連續)。 - slab / SLUB:物件快取——對「反覆配置/釋放同一型別物件」的場景,slab 預先把頁切成該型別大小的格子、重複利用,避免每次都從 buddy 切。(版本提醒:現在只剩 SLUB——SLAB 在 6.8 已移除、SLOB 在 6.4 移除。你不會再看到「選 SLAB 還是 SLUB」,只有 SLUB。) - vmalloc/vfree:配大塊,虛擬連續但實體不連續(用分頁表把分散的實體頁拼成連續的虛擬位址)。 - GFP flags:這是最關鍵的——配置時傳的旗標,決定配置的行為,尤其「能不能睡眠」。

為什麼這對你是 scope: direct?兩個層面: 1. 你 I/O 路徑會大量配置小物件(用 slab/kmalloc)與 DMA buffer(需實體連續,所以用 kmalloc/page 而非 vmalloc)。 2. GFP context 規則在中斷/工作佇列中至關重要:你的 I/O 完成處理常在中斷 context,那裡用錯 GFP flag(用了會睡眠的 GFP_KERNEL)會死結。這是這一課最重要、最致命的一課。

開始之前(前置確認)

  • 依賴:P3-T06(buddy system、page 配置;slab 從 buddy 拿頁)。
  • 自我檢測: 1. 你還記得 P3-T06 的「實體連續」與「虛擬位址」嗎?這課的 kmalloc(實體連續)vs vmalloc(僅虛擬連續)直接對比。 2. 你還記得 P1-T07 的「睡眠/阻塞」(行程讓出 CPU 等待)嗎?GFP flag 的核心就是「這次配置能不能睡眠等記憶體」。
  • 環境:QEMU 虛擬機。配置實驗只在 VM。

核心內容

拆成這幾節:(1) kmalloc:配小塊、實體連續 → (2) slab/SLUB:物件快取 → (3) 自訂 slab 快取 → (4) vmalloc:虛擬連續、實體不連續 → (5) GFP flags:能不能睡眠 → (6) 致命規則:持鎖/中斷 context 不可用 GFP_KERNEL,最後打通關。

1. kmalloc:配小塊、實體連續

最常用的配置函式是 kmalloc——配置一塊指定大小的記憶體,回傳指標。它像使用者態的 malloc,但有兩個關鍵差異:

要點: - kmalloc(size, gfp):配 size bytes,回傳指標。第二個參數是 GFP flag(第 5 節)。 - 實體連續:kmalloc 配到的記憶體在實體記憶體上是連續的(底層從 slab/buddy 拿)。這對 DMA 很重要(裝置需要連續實體位址,P6)——這是 kmalloc 和 vmalloc 的關鍵分野(第 4 節)。 - kzalloc:配置 + 清零(像使用者態 calloc)。 - kfree(ptr):釋放(資源配對,回顧 P0-T06 malloc/free——這裡是 kmalloc/kfree)。

kmalloc 適合「中小型、需要實體連續」的配置。它有大小上限(不適合配超大塊——那用 vmalloc)。

2. slab / SLUB:物件快取,重複利用

kmalloc 底層靠 slab 配置器(現在的實作是 SLUB)。slab 解決一個效能問題:反覆配置/釋放「同一型別」的物件。

flowchart TB
    PROBLEM["問題:某型別物件(如 I/O 請求結構)被反覆配置/釋放
若每次都從 buddy 切一頁再切小、釋放再還,很浪費"]
    PROBLEM --> SLAB["slab 的解法:
① 從 buddy 拿幾頁(P3-T06)
② 切成『該物件大小』的一格格
③ 維護空閒格清單,配置=取一格,釋放=還一格"]
    SLAB --> BENEFIT["好處:
① 配置/釋放極快(就是取/還清單上的格子)
② 同型別物件集中,cache 友善(P1-T02)
③ 釋放的物件可保留部分初始化狀態,重用更快"]
    style PROBLEM fill:#c2603a,color:#f4ecd8
    style SLAB fill:#e8a33d,color:#10100e
    style BENEFIT fill:#8a9a5b,color:#10100e

slab 的核心想法:為「某型別物件」預先準備一塊切好格子的記憶體,反覆利用。它從 buddy 拿頁(P3-T06),切成該物件大小的格子,維護空閒格清單——配置就是取一格、釋放就是還一格,極快(不必每次找 buddy)。同型別物件集中存放也對 cache 友善(回顧 P1-T02)。

kmalloc 底層用一組「通用大小」的 slab 快取(8、16、32、64... bytes 的快取),你 kmalloc(30) 它就從「32 bytes 的快取」給你一格。

版本提醒(重要,當現況教):歷史上 kernel 有三個 slab 配置器(SLAB、SLOB、SLUB),但現在只剩 SLUB——SLOB 在 6.4 移除、SLAB 在 6.8 移除。所以「仍以為有 SLAB 可選」是過時的誤區;現在 slab 配置器就是 SLUB,沒得選。(這是當初 spec 標記要驗證的版本敏感點,已確認:6.8 起 SLUB-only。)

3. 自訂 slab 快取:kmem_cache_create

對「你自己頻繁配置的特定型別」,可以建一個專屬的 slab 快取,而非用 kmalloc 的通用快取。用 kmem_cache_create:

    ALLOC["kmem_cache_alloc(cache, gfp)
從這個快取配一個物件"]
    FREE["kmem_cache_free(cache, obj)
還回去"]
    DESTROY["kmem_cache_destroy(cache)
銷毀快取(在 exit 時,要先釋放所有物件)"]

    style CREATE fill:#6fa8b8,color:#10100e
    style ALLOC fill:#8a9a5b,color:#10100e

何時用自訂快取(而非 kmalloc)?當你有一個頻繁配置/釋放的特定結構(例如你 I/O 路徑裡某個請求物件),專屬快取讓這型別的物件集中管理、配置更快、cache 行為更好、還能在 /proc/slabinfo 看到它的統計。流程:init 時 kmem_cache_create、用時 kmem_cache_alloc/kmem_cache_free、exit 時 kmem_cache_destroy(銷毀前要確保所有物件都釋放了——資源配對,回顧 P0-T06)。

連到你的產品:你 I/O 路徑裡反覆配置的請求/描述結構,適合用自訂 slab 快取,提升配置效能與可觀測性。

當你需要大塊記憶體,而 kmalloc(要實體連續)可能因「找不到夠大的連續實體區塊」而失敗,這時用 vmalloc:

關鍵分野(驗收點): - kmalloc:實體連續。適合中小塊、以及 DMA(裝置需連續實體位址)。 - vmalloc:僅虛擬連續,實體分散。它用分頁表(回顧 P1-T04)把分散在實體各處的頁,映射成一段連續的虛擬位址給你用。能配更大的塊(因為不需要連續的實體區塊),但較慢(有額外分頁表開銷)、且不適合 DMA(實體不連續,裝置沒法用)。

兩個常見誤區: - 以為 kmalloc 給的虛擬連續就一定實體連續——kmalloc 確實實體連續,但別把這歸功於「虛擬連續」;vmalloc 也虛擬連續卻實體不連續。要記住差別在實體連續性。 - 對 DMA 用 vmalloc 記憶體——實體不連續,裝置無法正確存取。DMA buffer 要用 kmalloc 或 page 配置(實體連續)。

還有 kvmalloc:先試 kmalloc(實體連續),失敗就退而用 vmalloc——適合「最好實體連續、但不強求,只要拿到夠大的塊」的場景。

5. GFP flags:這次配置能不能睡眠?

現在進入這一課最關鍵的概念:GFP flags(get-free-pages flags)。你配置時都要傳一個——它決定配置的行為,核心問題是「這次配置能不能睡眠(阻塞等待)」。

為什麼配置要「睡眠」?因為如果當下沒有足夠的空閒記憶體,kernel 可能需要做一些耗時的事來騰出記憶體(回收快取、把頁換出到磁碟等),這些要花時間——意味著呼叫配置的這條執行流可能被阻塞、睡眠等待(回顧 P1-T07 睡眠的概念)。

兩個最重要的: - GFP_KERNEL:可以睡眠。記憶體不足時允許阻塞、回收、等待。這是最常用的——但只能用在「可睡眠的 context」(一般的行程 context,例如 syscall 處理、workqueue)。 - GFP_ATOMIC:不可睡眠。絕不阻塞,記憶體不夠就立刻失敗(回傳 NULL)。用在不可睡眠的 context(中斷處理、持有 spinlock 時)。代價是成功率較低(因為不能等待回收)。

「能不能睡眠」取決於你在什麼 context 呼叫配置——這就是下一節的致命規則。

6. 致命規則:持 spinlock / 中斷 context 不可用 GFP_KERNEL

這是整課最重要、最容易造成系統死結的一條規則,務必刻進骨子裡。

規則:在「不可睡眠的 context」(持有 spinlock、或在中斷 context)裡,絕對不可以用會睡眠的 GFP_KERNEL——要用 GFP_ATOMIC。

flowchart TB
    SCENARIO["你持有一個 spinlock(P3-T08 會詳述),
或正在中斷處理常式裡"]
    SCENARIO --> WRONG["✗ 呼叫 kmalloc(size, GFP_KERNEL)"]
    WRONG --> SLEEP["GFP_KERNEL 可能睡眠(等記憶體回收)
→ 這條執行流被阻塞、讓出 CPU"]
    SLEEP --> DEADLOCK["★ 災難 ★
持 spinlock 時睡眠 → 別的 CPU 想拿這鎖會一直忙等,
而持鎖者睡著了不釋放 → 死結
(中斷 context 睡眠更是直接違法、當機)"]
    SCENARIO --> RIGHT["✓ 呼叫 kmalloc(size, GFP_ATOMIC)"]
    RIGHT --> NOSLEEP["GFP_ATOMIC 絕不睡眠
→ 不阻塞,要嘛立刻拿到、要嘛立刻失敗(NULL)
→ 不會死結"]
    style WRONG fill:#c2603a,color:#f4ecd8
    style DEADLOCK fill:#c2603a,color:#f4ecd8
    style RIGHT fill:#8a9a5b,color:#10100e

為什麼持 spinlock 睡眠會死結(這個邏輯 P3-T08 會更完整,先建立直覺):spinlock 是「忙等」的鎖——別的 CPU 想拿這把鎖時,會原地空轉等你釋放(P3-T08)。如果你持著鎖卻睡著了(因為 GFP_KERNEL 去等記憶體回收),你就不會釋放鎖;而別的 CPU 在那邊空轉等你,永遠等不到——死結。中斷 context 睡眠更糟(直接違反規則、當機)。

這條規則延伸到所有「可能睡眠的操作」:持有 spinlock 或在中斷 context 時,不只 GFP_KERNEL,任何可能睡眠的函式都不能呼叫——包括 mutex_lock(可睡眠,P3-T08)、copy_from_user(可能觸發缺頁而睡眠,回顧 P1-T06)等。這是 kernel 程式設計的核心紀律之一。

判斷方法:問自己「我現在在什麼 context?能不能睡眠?」—— - 行程 context、沒持 spinlock(如 syscall 處理、workqueue):可睡眠 → 用 GFP_KERNEL。 - 持 spinlock、或中斷 context:不可睡眠 → 用 GFP_ATOMIC。

(驗收點:正確回答「持有 spinlock 時要用哪個 GFP flag」= GFP_ATOMIC,並說明原因。)這條規則直接關係你的工作——你的 I/O 完成路徑常在中斷/軟中斷 context,那裡配置記憶體必須用 GFP_ATOMIC,否則系統死結。

一句話總結:kmalloc 配小塊且實體連續(可給 DMA)、底層是 SLUB 物件快取(SLAB 已於 6.8 移除)、vmalloc 配大塊但僅虛擬連續(不適合 DMA);而最致命的是 GFP flag——GFP_KERNEL 可睡眠(行程 context)、GFP_ATOMIC 不可睡眠(中斷/持 spinlock),在不可睡眠的 context 用了會睡眠的 GFP_KERNEL 就死結。你的 I/O 完成中斷路徑配置記憶體,必須用 GFP_ATOMIC。

常見誤區與踩雷提醒

誤區一(最致命):在原子/中斷 context 或持有 spinlock 時用 GFP_KERNEL。 GFP_KERNEL 可能睡眠 → 持鎖睡眠不釋放鎖 → 死結;中斷 context 睡眠直接違法/當機。這些 context 要用 GFP_ATOMIC。延伸:這些 context 也不可呼叫 mutex_lock、copy_from_user 等任何可能睡眠的函式。

誤區二:以為 kmalloc 給的虛擬連續就一定實體連續(混淆連續性)。 kmalloc 確實實體連續,但要記住關鍵差別在實體連續性:vmalloc 也虛擬連續卻實體分散。

誤區三:對 DMA 用 vmalloc 記憶體。 vmalloc 實體不連續,裝置無法正確存取。DMA buffer 要用 kmalloc 或 page 配置(實體連續)。

誤區四:仍以為有 SLAB 可選。 SLAB 在 6.8 已移除、SLOB 在 6.4 移除。現在 slab 配置器只剩 SLUB,沒得選。

誤區五:配置失敗未檢查回傳。 kmalloc/kmem_cache_alloc 失敗回傳 NULL(GFP_ATOMIC 尤其容易失敗,因為不能等)。務必檢查(回顧 P0-T06)。

動手實作

環境:QEMU 虛擬機。配置實驗只在 VM。

任務 A — kmalloc / kzalloc(驗收點) 寫一個 module,用 kmalloc(64, GFP_KERNEL) 配一塊、寫入讀回、kfree;再用 kzalloc(64, GFP_KERNEL) 配一塊,驗證內容全為 0(kzalloc 會清零),kfree。檢查回傳是否 NULL。驗收:kmalloc/kzalloc 配置成功,且 kzalloc 內容為 0。

任務 B — 自訂 slab 快取(驗收點) 在 module 裡 kmem_cache_create 建一個專屬快取(對某個你定義的 struct),用 kmem_cache_alloc 配幾個物件、kmem_cache_free 釋放,exit 時 kmem_cache_destroy。(可在 /proc/slabinfo 看到你的快取。)驗收:自訂 slab 快取配置/釋放物件成功。

任務 C — GFP flag 的判斷(驗收點,核心) 回答並寫下:「持有 spinlock 時,配置記憶體要用哪個 GFP flag?為什麼?」驗收:答 GFP_ATOMIC,並說明原因(GFP_KERNEL 可能睡眠,持鎖睡眠會死結)。 再寫一句:中斷 context 呢?(同樣 GFP_ATOMIC,因為中斷 context 不可睡眠。)

任務 D — kmalloc vs vmalloc(驗收點) 用 vmalloc 配一塊較大的記憶體、寫入讀回、vfree。寫一句話說明 kmalloc 與 vmalloc 在實體連續性上的差異,以及這對 DMA 的意涵。驗收:能說出 kmalloc 實體連續(可 DMA)、vmalloc 僅虛擬連續(不適合 DMA)。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ kmalloc/kzalloc 配置並驗證 kzalloc 內容為 0。 2. ☐ 建立自訂 slab 快取配置/釋放物件成功。 3. ☐ 正確回答「持有 spinlock 時要用哪個 GFP flag」(GFP_ATOMIC)並說明原因。 4. ☐ 說出 kmalloc 與 vmalloc 在實體連續性上的差異及對 DMA 的意涵。

評分量表: - 60(及格):能用 kmalloc/vmalloc。 - 80(熟練):能正確選 GFP flag 並建自訂快取。 - 100(精通):能完整解釋 context 與配置器/連續性的關係並對應到 DMA。

延伸與銜接

  • 對應工作場景:直接對應——你產品的 I/O 路徑會大量配置/釋放小物件(用 slab)與 DMA buffer(需實體連續);GFP context 規則在中斷/工作佇列中至關重要。
  • 這課餵給未來的(關鍵):GFP/context 規則 → P3-T08 鎖與 context(「持 spinlock 不可睡眠」的完整版)、P3-T10 中斷與下半部(中斷 context 的限制);kmalloc 實體連續 → P6 DMA buffer;slab → 你 I/O 路徑的物件配置。
  • 下一步 → P3-T08 kernel 同步(一)——spinlock、mutex、semaphore 與選型:這一課反覆提到「持有 spinlock 不可睡眠」「中斷 context 不可用 mutex」——下一課就完整講清楚這些鎖:spinlock(忙等、不可睡眠、適合短臨界區與中斷)、mutex(可睡眠、不可用於中斷)、semaphore,以及它們的 context 限制。你會徹底搞懂「鎖 × context × 能否睡眠」的所有合法/非法組合——這是你 I/O 完成路徑(常在中斷 context、與行程 context 共享資料)選鎖的關鍵,選錯直接系統死結。
