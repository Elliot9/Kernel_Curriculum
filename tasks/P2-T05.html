P2-T05 · 二元搜尋樹到紅黑樹

一句話:二元搜尋樹查找快,但遇到壞輸入會「長歪」成一條鏈、退化成 O(n)。紅黑樹用幾條巧妙的規則,保證樹永遠「夠平衡」、查找永遠 O(log n)——這是 kernel 在 I/O 排程器、計時器、記憶體區域管理選它的原因。

為什麼要先學這個(導讀)

上一課 P2-T04 的雜湊表平均快(O(1)),但最壞會退化(O(n))。這一課介紹一個有保證的結構——紅黑樹:它的查找/插入/刪除保證是 O(log n),即使在最壞情況下。代價是平均速度比雜湊表稍慢,但換來兩個雜湊表給不了的東西:最壞情況的保證,以及有序走訪(能按大小順序遍歷所有元素)。

這正是 kernel 為什麼在某些場景選紅黑樹而非雜湊表(回顧 P2-T01 的選型討論):當你不能容忍偶爾的 O(n) 卡頓(例如 I/O 排程要穩定),或需要按順序處理(例如計時器要按到期時間排序),紅黑樹的「保證 + 有序」就勝過雜湊表的「平均快但不保證、無序」。

這一課的路徑是:先理解二元搜尋樹(BST) 為何查找快、又為何會退化;再理解平衡如何解決退化;然後認識紅黑樹用哪些規則維持平衡(只在概念層,不需背證明);最後學 kernel 的 rbtree 怎麼用——特別是一個會讓你意外的設計:kernel 不給你現成的「插入」函式,要你自己寫搜尋與連結,它只提供「再平衡」。

為什麼這對你是 scope: direct?因為 mq-deadline 和 BFQ 這兩個 I/O 排程器、kernel 的計時器、以及記憶體區域(VMA)管理,都用紅黑樹。你讀 block layer 的排程器程式碼時會直接遇到 rb_node、rb_insert_color、rb_erase。理解它,你才讀得懂這些與你儲存工作高度相關的程式碼。

開始之前(前置確認)

  • 依賴:P2-T01(你知道平衡樹 O(log n)、有保證、能有序走訪,以及與雜湊表的取捨)。
  • 自我檢測: 1. 你能說出「為什麼雜湊表最壞 O(n)、而我們有時需要保證」嗎?(回顧 P2-T04/P2-T01。)這課的紅黑樹就是那個「保證」。 2. 你理解「樹」這種有父子節點的結構嗎?(每個節點可有左右子節點。)這課從二元搜尋樹講起。

核心內容

拆成這幾節:(1) 二元搜尋樹:為何查找快 → (2) 退化問題:長歪成一條鏈 → (3) 平衡的概念 → (4) 紅黑樹的五條規則 → (5) kernel rbtree 的三步插入 → (6) 為什麼 kernel 只給再平衡,最後打通關。

1. 二元搜尋樹(BST):為什麼查找快

二元搜尋樹是一棵每個節點最多有左、右兩個子節點的樹,並遵守一個規則:左子樹的所有值 < 節點的值 < 右子樹的所有值。

flowchart TB
    R["50"]
    L["30"]
    RR["70"]
    LL["20"]
    LR["40"]
    R --> L
    R --> RR
    L --> LL
    L --> LR
    NOTE["規則:左 < 根 < 右
(每個節點都成立)
50 的左子樹(30,20,40)全 < 50
右子樹(70)全 > 50"]
    style R fill:#e8a33d,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

這個「左小右大」的規則讓查找變快。要找一個值,從根開始:比根小就往左、比根大就往右,每一步排除掉一半的可能:

flowchart TB
    S1["要找 40,從根 50 開始"]
    S2["40 < 50 → 往左,到 30
(右半邊全部排除)"]
    S3["40 > 30 → 往右,到 40
(又排除一半)"]
    S4["找到 40 ✓"]
    S1 --> S2 --> S3 --> S4
    NOTE["每一步排除一半 → 查找約 O(樹高)
若樹平衡(高度約 log n)→ O(log n)"]
    S4 --> NOTE
    style S2 fill:#e8a33d,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

因為每一步都排除一半,查找的步數約等於樹的高度。如果樹長得「矮胖」(平衡),高度約是 log n,查找就是 O(log n)——很快。但「如果平衡」是關鍵前提,下一節看它不平衡時的災難。

2. 退化問題:BST 會「長歪」成一條鏈

BST 的致命弱點:它的形狀取決於插入順序。如果你按已經排序的順序插入(例如依序插入 10, 20, 30, 40, 50),會發生什麼?

flowchart TB
    subgraph good["理想:平衡的 BST(高度 ≈ log n)"]
        G["矮胖,查找 O(log n)"]
    end
    subgraph bad["災難:依序插入 10,20,30,40,50"]
        N10["10"] --> N20["20"] --> N30["30"] --> N40["40"] --> N50["50"]
    end
    NOTE["每個新值都比前一個大 → 一直往右掛
樹『長歪』成一條斜線(等於一條鏈結串列!)
高度 = n → 查找退化成 O(n)"]
    bad --> NOTE
    style good fill:#8a9a5b,color:#10100e
    style NOTE fill:#c2603a,color:#f4ecd8

按排序順序插入時,每個新值都比前一個大,於是一直往右掛,樹變成一條只往右的斜線——這根本就是一條鏈結串列!高度變成 n,查找退化成 O(n),BST 的優勢全失。

這是 BST 的根本問題:它不保證平衡,最壞輸入(排序資料)會讓它退化。而「排序資料」在真實世界很常見(例如按時間順序到來的事件)。所以裸 BST 在 kernel 不能用——你需要一個「無論怎麼插入都保持平衡」的樹。這就是下一節的平衡樹。

「用未平衡 BST,最壞輸入下退化成 O(n)」是常見誤區——必須用會自我平衡的變體。

3. 平衡的概念:強迫樹保持矮胖

平衡樹(self-balancing tree) 的核心想法:在每次插入/刪除後,自動調整樹的形狀,確保它始終「夠矮胖」(高度維持在 O(log n)),不讓它長歪成鏈。

flowchart LR
    INSERT["插入/刪除一個節點"]
    CHECK["檢查:樹有沒有變得太歪
(某條路徑太長)?"]
    REBALANCE["若太歪 → 透過『旋轉』等操作
重新調整節點的排列
讓樹恢復矮胖"]
    INSERT --> CHECK --> REBALANCE
    RESULT["結果:無論插入順序如何,
樹高始終 ≈ log n → 查找永遠 O(log n)"]
    REBALANCE --> RESULT
    style REBALANCE fill:#e8a33d,color:#10100e
    style RESULT fill:#8a9a5b,color:#10100e

調整的核心手段叫「旋轉(rotation)」——一種保持「左小右大」規則、但改變樹形狀(降低高度)的局部操作。你不需要掌握旋轉的細節;只要理解:平衡樹在每次修改後做一點額外的調整工作,換取「高度永遠是 log n」的保證。

有好幾種平衡樹(AVL、紅黑樹等),它們用不同的規則和調整策略達成平衡。kernel 選的是紅黑樹——下一節看它的規則,以及第 6 節末會提到為什麼是紅黑樹而非 AVL。

4. 紅黑樹的五條規則(概念層,不必背證明)

紅黑樹是一種平衡樹,它給每個節點塗上「紅」或「黑」,並遵守五條規則。這些規則合起來,巧妙地保證樹「夠平衡」。你不需要背證明,只要理解「這些規則合起來保證了平衡」這個結論:

flowchart TB
    subgraph rules["紅黑樹的五條規則"]
        R1["① 每個節點不是紅就是黑"]
        R2["② 根節點是黑"]
        R3["③ 紅節點的子節點都是黑
(不能有兩個紅節點相鄰)"]
        R4["④ 從任一節點到其下方所有葉子,
經過的『黑節點數』都相同"]
        R5["⑤ (葉子端的 NULL 視為黑)"]
    end
    KEY["這五條合起來的效果:
最長路徑 ≤ 最短路徑的兩倍
→ 樹不會太歪 → 高度保證 O(log n)"]
    rules --> KEY
    style R3 fill:#6fa8b8,color:#10100e
    style R4 fill:#6fa8b8,color:#10100e
    style KEY fill:#e8a33d,color:#10100e

直覺理解(不必深究): - 規則 ③(紅節點不相鄰)和規則 ④(每條路徑的黑節點數相同)是關鍵。它們合起來限制了「最長路徑」不能超過「最短路徑」的兩倍——因為路徑上不能連續紅、且黑節點數固定。 - 「最長 ≤ 最短的兩倍」就意味著樹不會像 BST 那樣長歪成鏈(那會讓某條路徑無限長)。樹被強制維持在「夠矮胖」,高度保證 O(log n)。

每次插入/刪除可能破壞這些規則,紅黑樹就透過重新塗色 + 旋轉來修復,讓規則重新成立(從而維持平衡)。這個「修復」就是 kernel rb_insert_color 做的事(下一節)。

比喻:紅黑樹的規則像「蓋房子的建築法規」——你不必懂結構力學的證明,只要遵守那幾條規定(樑柱間距、承重限制),蓋出來的房子就保證不會歪倒。紅黑樹遵守那五條規則,就保證「不會歪成一條鏈」。

5. kernel rbtree 的三步插入

現在看實務:kernel 提供 struct rb_node(內嵌到你的資料 struct,跟 P2-T02 的 list_head 一樣是侵入式)和一組 API。但插入的方式會讓你意外——它是三個步驟,而且前兩步要你自己寫:

flowchart TB
    STEP1["① 搜尋插入點(你自己寫)
從根開始,比較你的 key 與各節點,
往左或往右走,找到該插入的空位
(因為 kernel 不知道你的 key 怎麼比較)"]
    STEP2["② 連結節點(你自己寫,用 kernel 提供的小函式)
把新節點掛到找到的位置
(rb_link_node)"]
    STEP3["③ 再平衡(呼叫 kernel 的 rb_insert_color)
kernel 重新塗色 + 旋轉,
修復紅黑樹規則,恢復平衡"]
    STEP1 --> STEP2 --> STEP3
    style STEP1 fill:#6fa8b8,color:#10100e
    style STEP2 fill:#e8a33d,color:#10100e
    style STEP3 fill:#8a9a5b,color:#10100e

這三步是 kernel rbtree 的標準插入慣用法(驗收點之一),務必記住順序:先搜尋插入點 → 連結節點 → 呼叫 rb_insert_color 再平衡。查找和刪除類似(刪除用 rb_erase,它內部會處理再平衡)。中序走訪這棵樹,會得到排序好的結果(因為 BST 的左小右大規則)——這是紅黑樹「有序」優勢的體現。

「插入後忘記呼叫再平衡」是常見 bug:如果你只做了前兩步(搜尋 + 連結)卻沒呼叫 rb_insert_color,那棵樹就退化成一棵沒有平衡保證的普通 BST,可能長歪。第三步不能省。

6. 為什麼 kernel 只給「再平衡」,要你自己寫搜尋?

第 5 節那個「前兩步自己寫」的設計常讓初學者困惑——為什麼 kernel 不直接提供一個 rb_insert(tree, key) 全包?這背後有 kernel 的設計哲學:

flowchart TB
    Q["為何 kernel 不提供全包的 rb_insert?"]
    Q --> R1["原因①:kernel 不知道你的『key 怎麼比較』
你的節點可能按 sector 編號排、按時間排、
按任意自訂規則排
→ 『搜尋插入點』的比較邏輯只有你知道"]
    Q --> R2["原因②:效率與彈性
讓你自己寫搜尋,你能順便做別的事
(如檢查重複、就地更新),
不必為了通用而犧牲效率"]
    R1 --> DESIGN["所以 kernel 切分職責:
『跟你的資料相關的』(搜尋、比較)→ 你寫
『純紅黑樹機制的』(再平衡)→ kernel 提供"]
    R2 --> DESIGN
    style R1 fill:#6fa8b8,color:#10100e
    style DESIGN fill:#e8a33d,color:#10100e

核心原因:「怎麼比較你的 key」是只有你知道的事(回顧 P0-T07 callback、P2-T01 選型——kernel 的通用機制不可能預知你的特定資料怎麼排序)。你的紅黑樹可能按 sector 編號排、按到期時間排、按任意規則排。所以 kernel 把「跟你資料相關的部分」(搜尋插入點、比較)留給你,只提供「純紅黑樹機制的部分」(再平衡這個與資料無關的、複雜的塗色旋轉演算法)。這是一種職責切分:通用機制歸 kernel,資料相關邏輯歸你——這個哲學貫穿 kernel(你會在很多 kernel API 看到同樣的分工)。

為什麼 kernel 選紅黑樹而非 AVL?(進階) AVL 樹更嚴格地平衡(查找略快),但插入/刪除時需要更多旋轉來維持嚴格平衡。紅黑樹平衡得「鬆」一點(查找略慢一點點),但插入/刪除的調整較少。kernel 的場景常是「插入刪除頻繁」(如 I/O 排程不斷加入/移除請求),所以選了「插入刪除成本較低」的紅黑樹——又是一個基於場景的攤銷取捨(呼應 P2-T01)。

打通關:把紅黑樹收攏成一個心智模型

排序輸入會長歪成鏈 → O(n)★"]

    GUARANTEE --> KERNEL["kernel rbtree 三步插入:

    style KERNEL fill:#e8a33d,color:#10100e

一句話總結:二元搜尋樹查找快但會因壞輸入退化成鏈;紅黑樹用五條塗色規則保證樹永遠平衡(高度 O(log n)),提供雜湊表沒有的「最壞保證 + 有序走訪」;kernel 的 rbtree 用「搜尋→連結→再平衡」三步插入,並把『資料相關的比較』留給你、只提供『純機制的再平衡』——這正是 I/O 排程器、計時器、VMA 選它的原因。

常見誤區與踩雷提醒

誤區一:用未平衡的裸 BST,最壞輸入下退化成 O(n)。 排序資料會讓 BST 長歪成鏈。kernel 場景必須用會自我平衡的紅黑樹(rbtree),不能用裸 BST。

誤區二:以為 kernel 提供現成的「插入」函式。 kernel 只提供再平衡(rb_insert_color)和刪除(rb_erase);「搜尋插入點」和「連結」要你自己寫(因為比較邏輯只有你知道)。

誤區三:插入後忘記呼叫再平衡。 只做「搜尋 + 連結」卻不呼叫 rb_insert_color,樹就退化成沒有平衡保證的普通 BST,可能長歪。三步缺一不可。

誤區四:以為紅黑樹要背那五條規則的證明。 不必。只要理解「這些規則合起來保證樹平衡(高度 O(log n))」這個結論,以及怎麼用 kernel 的 API。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 用 kernel rbtree 風格 API 建樹並有序走訪(驗收點) 依 kernel 紅黑樹文件(https://docs.kernel.org/core-api/rbtree.html )的範例,在使用者態用 kernel rbtree 風格 API(可取得 user space 移植版,或詳讀文件範例)。插入 10 個鍵(故意用打亂的順序),然後中序走訪,確認得到排序好的結果。驗收:中序走訪輸出是排序的。

任務 B — 正確寫出三步插入(驗收點) 在任務 A 裡,確保你的插入函式正確實作三步:① 從根搜尋插入點(用你的 key 比較)→ ② 用 rb_link_node 連結 → ③ 呼叫 rb_insert_color 再平衡。寫出這三步並能說明每步在做什麼。驗收:三步順序正確且能解釋。

任務 C — 體會「忘記再平衡」的後果(體會用) 故意把任務 B 的第三步(rb_insert_color)拿掉,按排序順序插入 10 個鍵,觀察樹退化(可印出樹高或結構,看到它變成一條斜線)。寫一句話:這對應第 2 節 BST 的什麼問題?第三步為什麼重要?

任務 D — 說明最壞保證(驗收點) 用一句話說明:紅黑樹相對「未平衡 BST」,在最壞情況下的查找有什麼保證?(答案:即使最壞也是 O(log n),而未平衡 BST 最壞 O(n)。)

評分量表: - 60(及格):能複述紅黑樹的性質與用途。 - 80(熟練):能讀懂 kernel rbtree 使用範例。 - 100(精通):能解釋為何 kernel 選紅黑樹而非 AVL(插入/刪除攤銷取捨)。

延伸與銜接

  • 對應工作場景:直接對應——mq-deadline/BFQ I/O 排程器、計時器、VMA 都用紅黑樹;讀 block layer 排程器程式碼會遇到 rb_node、rb_insert_color、rb_erase。
  • 這課餵給未來的:紅黑樹 → P5 的 I/O 排程器(mq-deadline/BFQ);侵入式 rb_node + container_of(回收 P2-T03)→ 樹節點反推外層 struct;「保證 vs 平均」的選型 → 理解 kernel 各處的結構選擇。
  • 下一步 → P2-T06 radix tree 與 XArray:你已經學了「以比較為基礎」的樹(紅黑樹)。下一課介紹一個以整數索引為基礎的結構——radix tree / XArray:它特別適合「用一個整數(如檔案 offset、ID)快速對應到一個指標」的場景。這跟你的儲存領域直接相關——page cache(VFS 到 block 之間的快取層)就是用 XArray 把「檔案 offset(以 page 為單位)」對應到「記憶體裡的 page」。理解它是讀懂讀寫路徑快取的前置。
