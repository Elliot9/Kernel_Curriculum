P1-T03 · 快取一致性與對齊的硬體意義

一句話:多核心時代,每個核心有自己的 cache,於是冒出兩個問題:一個核心改了資料,別人怎麼知道(cache coherence)?以及一個陰險的效能殺手——兩個執行緒寫「不同變數」卻因為它們擠在同一條 cache line 上而互相拖累(false sharing)。這直接關係你產品的多核擴展性。

為什麼要先學這個(導讀)

上一課 P1-T02 講的是單核心的 cache。但你的伺服器是多核心的,而多核心讓 cache 的故事多了一個關鍵轉折:每個核心有它自己的 L1/L2 cache。

這立刻產生一個問題:如果核心 A 和核心 B 都把同一個變數 x 載入各自的 cache,然後 A 把 x 改成新值——B 的 cache 裡還是舊的 x,怎麼辦?如果不處理,B 會用到過時的資料,程式就錯了。硬體解決這個問題的機制,叫快取一致性(cache coherence)。

更陰險的是另一個問題:因為 cache 以「整條 line(64 bytes)」為單位管理(回顧 P1-T02),兩個完全不同的變數,只要它們在記憶體上靠得夠近、落在同一條 cache line 上,當兩個核心各自頻繁寫其中一個,硬體的一致性機制會讓這條 line 在兩個核心間不斷「搶來搶去」,造成巨大的效能損失——即使這兩個變數根本無關。這叫 false sharing(偽共享)。

為什麼這對你是 scope: direct(直接對應工作)?因為 kernel 為了多核效能,有大量設計專門在對付這些問題:per-CPU 變數(每個核心一份,避免互搶)、____cacheline_aligned(把資料對齊到 cache line 邊界,避免 false sharing)、NVMe 多佇列(每個核心一條 I/O 佇列,正是為了避開 cache 競爭)。這些你產品會直接接觸的設計,動機全在這一課。看懂 false sharing,你才懂為什麼 kernel 要費那麼大勁做 per-CPU。

這一課也是你那條「記憶體順序/可見性」主線的起點(P1-T03 → P1-T10 → P3-T11 → P6-T03):這裡先建立「多核心下,一個核心的寫入何時、如何讓別的核心看見」的硬體直覺。

開始之前(前置確認)

  • 依賴:P1-T02(你已懂 cache line 64 bytes、cache 一次載入一整條)。
  • 自我檢測: 1. 你能說出「為什麼 CPU 一次載入 64 bytes 而非單一 byte」嗎?(空間局部性 + cache line)這課整個建立在 cache line 上。 2. 你寫過多執行緒程式嗎?(用 pthread 開兩個執行緒。)這課的實驗需要。

核心內容

拆成這幾節:(1) 多核心的難題:各有 cache → (2) cache coherence 與 MESI 概念 → (3) false sharing 的機制 → (4) 用對齊/padding 解決 → (5) 釐清:coherence ≠ 記憶體順序 → (6) 連到 kernel:per-CPU 與 cache line 對齊,最後打通關。

1. 多核心的難題:同一個變數,各核心 cache 裡各一份

這就是多核心 cache 的核心難題:同一份資料在多個核心的 cache 裡有副本,其中一個被改了,其他的就過時了。如果硬體不管,多核心程式的共享資料會充滿這種「我看到的和你看到的不一樣」的錯亂。

硬體的解法是讓各核心的 cache 之間「互相通氣」,維持一個共識:任何時刻,大家對同一塊資料的認知要一致。這個機制就是 cache coherence。

2. cache coherence 與 MESI(概念層級)

cache coherence 協定讓各核心的 cache 互相監聽、協調,確保「不會有兩個核心同時握著同一塊資料的不同有效值」。最經典的協定叫 MESI,名字來自 cache line 的四個狀態。你不需要精通細節,只要建立概念直覺:

flowchart TB
    subgraph mesi["MESI:一條 cache line 在某核心 cache 中的四種狀態"]
        M["Modified(已修改)
我改過了,只有我有最新版,
記憶體是舊的"]
        E["Exclusive(獨佔)
只有我有這份,且和記憶體一致"]
        S["Shared(共享)
多個核心都有這份唯讀副本,
都和記憶體一致"]
        I["Invalid(無效)
我這份已過時,不能用
(被別人改了)"]
    end

核心精神:當一個核心要「寫」一條 cache line,它必須先取得這條 line 的「獨佔/修改」權,並讓其他核心持有的這條 line 副本變成「Invalid」(失效)。 看一次寫入如何引發協調:

結論:coherence 保證了「正確性」——B 不會永遠用著過時的 x,它的舊副本會被作廢、被迫重新取得最新值。但注意那個「廣播、作廢、重新取得」的過程有成本,而這個成本正是下一節 false sharing 災難的來源。

3. false sharing:兩個無關變數的暗中互鬥

現在揭露那個陰險的效能殺手。關鍵前提來自 P1-T02:cache 以整條 line(64 bytes)為單位。所以一致性協定也是以 cache line 為單位運作的——它作廢的是「整條 line」,不是「單個變數」。

設想兩個變數 a 和 b,它們在記憶體上相鄰,落在同一條 cache line 上。核心 A 拼命寫 a,核心 B 拼命寫 b。它們寫的是不同變數,邏輯上毫無關係,應該互不干擾才對。但是:

flowchart TB
    LINE["一條 cache line(64 bytes)
同時裝著 a 和 b"]
    S1["核心 A 寫 a:
取得整條 line 獨佔
→ 讓 B 的這條 line 失效(Invalid)"]
    S2["核心 B 想寫 b:
發現自己的 line 被作廢了
→ 重新取得整條 line 獨佔
→ 反過來讓 A 的失效"]
    S3["核心 A 又要寫 a:
發現又被作廢了
→ 再次搶回..."]
    S4["這條 line 在 A、B 間
無止盡地『乒乓』來回
每次都付出協調成本"]
    LINE --> S1 --> S2 --> S3 --> S4
    style S4 fill:#c2603a,color:#f4ecd8

這就是 false sharing:a 和 b 明明是不同變數、邏輯上無關,卻因為共處一條 cache line,使得「寫 a」和「寫 b」透過一致性協定互相作廢對方的 cache,造成這條 line 在兩個核心間瘋狂乒乓。結果是:兩個執行緒各自寫各自的變數,卻慢得像在搶同一個東西——明明沒有真正的共享,卻有共享的代價,所以叫「偽共享」。

它的陰險在於:程式碼看起來完全正確(你確實在操作不同變數),沒有任何 race、沒有 bug,只是莫名其妙地慢。不懂 false sharing 的人會百思不得其解。

4. 解法:用對齊/padding 把它們分到不同 cache line

既然 false sharing 的根源是「兩個變數擠在同一條 cache line」,解法就直接:把它們分開到不同的 cache line 上。手段是「對齊」或「填充(padding)」——讓每個變數獨佔一條 line。

flowchart TB
    subgraph before["false sharing(壞):同一條 line"]
        direction LR
        L1["cache line
[ a ][ b ][...空...]
a、b 共處一條 → 乒乓"]
    end
    subgraph after["對齊後(好):各佔一條 line"]
        direction LR
        L2["cache line 1
[ a ][...padding 填滿 64B...]"]
        L3["cache line 2
[ b ][...padding 填滿 64B...]"]
    end
    before -->|"用 alignas(64) 或 padding
把 a、b 推到不同 line"| after
    style L1 fill:#c2603a,color:#f4ecd8
    style L2 fill:#8a9a5b,color:#10100e
    style L3 fill:#8a9a5b,color:#10100e

具體做法(C11):用 alignas(64) 強制變數對齊到 cache line 邊界,或在 struct 成員間插入 padding 把它們撐開超過 64 bytes:

#include <stdalign.h>
struct counters {
    alignas(64) long a;   // a 對齊到 64,獨佔一條 line
    alignas(64) long b;   // b 也對齊到 64,落在下一條 line
};

這樣 A 寫 a、B 寫 b 就各自動各自那條 line,不再互相作廢——乒乓消失,效能恢復。代價是多用了一些記憶體(每個變數撐到佔一條 line),但換來多核心下的效能,通常非常值得。

(回顧 P0-T04 的對齊與 padding——當時是為了「滿足硬體對齊要求」,這裡是為了「避免 false sharing」。同一個 padding 工具,不同的目的。)

5. 關鍵釐清:coherence 不等於「記憶體順序」

這是一個極重要、也極容易混淆的點,單獨拉出來,而且它是你那條「記憶體順序」主線的關鍵伏筆。

cache coherence 保證的是:對單一一塊資料,所有核心最終會看到一致的值(不會有人永遠卡在舊值)。

但 coherence 不保證:多個不同變數的寫入,在別的核心眼中以什麼順序出現。

→ 可能 B 先看到 y 的新值,才看到 x 的!"]
    COH -.“這是兩件事!”.-> ORD
    NEXT["『多變數的寫入順序如何被別人看見』
由記憶體模型(memory model)決定
→ 這是 P1-T10 的主題"]
    ORD --> NEXT
    style COH fill:#6fa8b8,color:#10100e
    style ORD fill:#e8a33d,color:#10100e
    style NEXT fill:#8a9a5b,color:#10100e

換句話說:即使每個變數各自都是一致的(coherence),CPU 和編譯器仍可能重排不同變數的讀寫順序,讓另一個核心看到「不符合程式碼順序」的結果。這就是為什麼光有 coherence 還不夠,還需要 memory ordering / memory barrier——那是 P1-T10 的主題,也是 kernel 同步、以及你 DMA 工作(描述子必須在按門鈴前對裝置可見)的核心。

現在你只要牢牢記住這個區別:coherence 管「單一資料的副本一致」,ordering 管「多個資料的寫入順序如何被看見」,兩者是不同的問題。混淆它們是並行程式設計的常見錯誤根源。

6. 連到 kernel:per-CPU 變數與 cache line 對齊

把這一課的硬體現實,連到你產品會直接碰到的 kernel 設計:

這三個都是你日後會直接接觸的: - per-CPU 變數:kernel 大量使用「每核一份」的資料來避免共享成本。你寫 kernel 程式碼會遇到 this_cpu_* 之類的 API。 - ____cacheline_aligned:kernel 原始碼裡常見的標註,就是第 4 節的對齊手法,專門避免 false sharing。 - NVMe 多佇列(multi-queue):這是你產品的核心!現代 NVMe 與 kernel 的 blk-mq 框架讓每個 CPU 核心有自己的 I/O 佇列,正是為了讓多核心並行送 I/O 時,不互相爭搶同一條佇列的 cache line。你現在懂了它背後的硬體動機。

一句話總結:多核心讓每個核心各有 cache,於是需要 coherence 維持「單一資料的一致」,但這個以 cache line 為單位的機制,會讓擠在同一條 line 的無關變數產生 false sharing;kernel 用 per-CPU、cache line 對齊、NVMe 多佇列來迴避這些成本——而 coherence 並不保證多變數的可見順序,那要等 P1-T10 的 memory ordering。

常見誤區與踩雷提醒

誤區一:以為「兩執行緒寫不同變數就互不影響」。 若兩變數落在同一條 cache line,仍會 false sharing,互相拖累。要確保它們在不同 line(對齊/padding)。

誤區二:以為 cache coherence 保證了記憶體順序。 這是兩回事(第 5 節)。coherence 管單一資料的副本一致;多變數的可見順序由 memory model 決定(P1-T10)。混淆這點是並行 bug 的常見根源。

誤區三:對 false sharing 視而不見,只盯著演算法。 程式邏輯完全正確卻莫名很慢,多核心場景下要懷疑 false sharing。它不是 bug(沒有 race),是效能問題。

誤區四:過度 padding 浪費記憶體。 對齊到 cache line 會讓每個變數佔滿 64 bytes。只對「多核心高頻寫、且確實會 false sharing」的熱點這樣做,不要無腦對所有變數加 alignas(64)。

動手實作

環境:Linux 終端機,使用者態,多核心機器,安全,不需 root、不動系統。需要 pthread。

任務 A — 重現 false sharing

#include <stdio.h>
#include <pthread.h>
#include <time.h>
#define ITER 100000000L

struct { long a; long b; } shared;   // a、b 相鄰,極可能同一條 cache line

void *inc_a(void *_) { for (long i=0;i<ITER;i++) shared.a++; return 0; }
void *inc_b(void *_) { for (long i=0;i<ITER;i++) shared.b++; return 0; }

int main(void) {
    pthread_t t1, t2;
    clock_t start = clock();
    pthread_create(&t1, 0, inc_a, 0);
    pthread_create(&t2, 0, inc_b, 0);
    pthread_join(t1, 0); pthread_join(t2, 0);
    // 注意:clock() 量的是 CPU 時間總和;用 time ./prog 看實際牆鐘時間更直觀
    printf("done\n");
    return 0;
}

用 gcc -O2 prog.c -o prog -lpthread && time ./prog 跑,記下時間(看 real 那行)。

任務 B — 用對齊消除 false sharing,比較 把 struct 改成讓 a、b 分到不同 cache line:

#include <stdalign.h>
struct { alignas(64) long a; alignas(64) long b; } shared;

其餘不變,重新編譯、time ./prog。比較兩個版本的時間——對齊版應明顯較快。寫一句話:用 cache line 乒乓解釋為什麼。

任務 C(思考)— 連到你的產品 寫一兩句話:NVMe 多佇列「每個 CPU 一條 I/O 佇列」的設計,如何用這一課的概念解釋它為什麼對多核心效能重要?(提示:避免多核心爭搶同一佇列資料結構的 cache line。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 重現 false sharing:兩執行緒各自累加落在同一 cache line 的兩個 counter,量測時間。 2. ☐ 將兩 counter 以 alignas(64) 或 padding 分到不同 cache line 後,時間明顯下降。 3. ☐ 能解釋原因(cache line 乒乓 / coherence 以 line 為單位作廢)。

評分量表: - 60(及格):能複述 coherence 概念。 - 80(熟練):能重現並解釋 false sharing。 - 100(精通):能連結到 kernel 的 per-CPU 變數、cache line 對齊設計與 NVMe 多佇列,並清楚區分 coherence 與 memory ordering。

延伸與銜接

  • 對應工作場景:直接對應——kernel 的 per-CPU 資料結構、____cacheline_aligned、NVMe 多佇列(每核一隊)都是為了避開 false sharing 與 cache 競爭。這是你產品多核擴展性的硬體基礎。
