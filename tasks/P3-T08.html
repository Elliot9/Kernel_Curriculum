P3-T08 · kernel 同步(一)—— spinlock、mutex、semaphore 與選型

一句話:kernel 比使用者態更需要嚴格同步——多核 + 中斷 + 搶佔讓共享狀態處處有 race。spinlock 忙等、不可睡眠、適合短臨界區與中斷;mutex 可睡眠、不可用於中斷。選錯鎖、或在持鎖時做了會睡眠的事,系統直接死結。

為什麼要先學這個(導讀)

這一課把你 Phase 1 的並行知識(P1-T08 race、P1-T09 鎖、P1-T10 memory ordering)帶進 kernel,而 kernel 的環境比使用者態更嚴酷,規則也更嚴格。

為什麼 kernel 需要比使用者態更嚴格的同步?因為 kernel 是一個極端並行的環境,共享狀態同時面對三種「執行流」: - 多核心:多個 CPU 同時跑核心程式碼,可能同時碰同一資料(回顧 P1-T03 多核心 cache)。 - 中斷:中斷隨時可能打斷正在執行的程式碼,中斷處理常式可能碰同一資料。 - 搶佔(preemption):kernel 可被設定成可搶佔,一個 task 執行核心程式碼時可能被切換(回顧 P1-T07)。

這三者疊加,讓「未受保護的共享狀態」在 kernel 裡 race 的機會遠多於使用者態。所以 kernel 有一套豐富的鎖,而選哪個鎖、在什麼 context 用,規則嚴格到選錯就系統死結。

核心的兩個鎖: - spinlock:忙等(拿不到就原地空轉)、不可睡眠、適合短臨界區與中斷 context。 - mutex:可睡眠(拿不到就讓出 CPU 睡眠等待)、不可用於中斷 context。

為什麼這對你是 scope: direct?因為你的 I/O 完成路徑常在中斷/軟中斷 context,與行程 context 共享資料。在這裡選錯鎖(例如在中斷 context 用了會睡眠的 mutex、或中斷與行程共享資料卻沒用 spin_lock_irqsave)會直接造成系統死結。這一課是你產品並行正確性的關鍵。它也接續了 P3-T07 那個「持 spinlock 不可睡眠」的規則,給出完整的解釋。

核心內容

1. 為何 kernel 需要更嚴格的同步:三種並行來源

先看清 kernel 的並行為何比使用者態複雜:

    RESULT["三者疊加 → 共享狀態 race 的機會遠多於使用者態
→ 需要更豐富的鎖 + 更嚴格的 context 規則"]

關鍵新增的是中斷這個維度。使用者態你只擔心執行緒之間(P1-T08);kernel 還要擔心「中斷處理常式」會在任何時刻打斷你、碰你正在改的資料。這帶來一個使用者態沒有的問題:如果一段程式碼和中斷處理常式共享資料,而你在改資料時中斷來了、中斷處理常式也要改同一資料——race。這需要特殊處理(第 5 節 spin_lock_irqsave)。

2. spinlock:忙等、不可睡眠、短臨界區

spinlock(自旋鎖) 是 kernel 最基本的鎖。它的特性:拿不到鎖就「原地空轉(spin)」等待,而不是睡眠。

flowchart TB
    SPIN["spin_lock(&lock):想取得鎖"]
    SPIN --> GOT{"鎖空閒嗎?"}
    GOT -->|"是"| ENTER["取得鎖,進入臨界區"]
    GOT -->|"否(別人持有)"| BUSY["★ 原地空轉(busy-wait)★
這個 CPU 不停地檢查鎖是否釋放,
不睡眠、不讓出 CPU"]
    BUSY --> GOT
    ENTER --> WORK["臨界區:操作共享資料(要短!)"]
    WORK --> UNLOCK["spin_unlock(&lock):釋放"]
    style BUSY fill:#e8a33d,color:#10100e
    style WORK fill:#8a9a5b,color:#10100e

特性與適用: - 忙等(busy-wait):拿不到鎖,CPU 原地空轉檢查,不睡眠。 - 適合短臨界區:因為忙等會浪費 CPU(空轉),所以臨界區必須短——快進快出。臨界區若很長,別的 CPU 空轉等很久,浪費(常見誤區:臨界區過長卻用 spinlock)。 - 可用於中斷 context:因為它不睡眠,所以可以在「不能睡眠的 context」(中斷處理常式)裡用——這是它最重要的用途之一。 - 不可睡眠:持有 spinlock 時,絕對不能做任何會睡眠的事(下一節解釋為什麼)。

spinlock 適合「短、快、可能在中斷 context」的保護。

3. 為什麼持 spinlock 不可睡眠:死結的機制

這是 P3-T07 那條規則的完整解釋,也是 kernel 同步最重要的直覺之一。

規則:持有 spinlock 時,絕對不可以睡眠(不可呼叫 kmalloc(GFP_KERNEL)、mutex_lock、copy_from_user 等任何可能睡眠的函式)。為什麼?

flowchart TB
    HOLD["CPU-A 持有 spinlock,進入臨界區"]
    HOLD --> SLEEP["CPU-A 在臨界區裡做了會睡眠的事
(如 kmalloc(GFP_KERNEL) 去等記憶體)
→ CPU-A 睡眠、讓出 CPU,但★仍持有鎖★"]
    SLEEP --> OTHER["此時 CPU-B 想拿同一個 spinlock"]
    OTHER --> BUSY2["spinlock 是忙等:CPU-B 原地空轉等鎖釋放"]
    BUSY2 --> DEADLOCK["★ 死結 ★
CPU-A 睡著了不會釋放鎖,
CPU-B 空轉永遠等不到
(更糟:若 A 等的資源要 B 處理,雙重卡死)"]
    style SLEEP fill:#e8a33d,color:#10100e
    style DEADLOCK fill:#c2603a,color:#f4ecd8

死結的邏輯: 1. CPU-A 持有 spinlock,在臨界區裡睡眠(去等某個東西),但仍持有鎖。 2. CPU-B 想拿同一個 spinlock,因為 spinlock 是忙等,CPU-B 原地空轉等待。 3. CPU-A 睡著了不會釋放鎖,CPU-B 永遠空轉等不到——死結。

(對比:mutex 是睡眠等待,所以「持 mutex 時睡眠」不會這樣死結——但 spinlock 的忙等特性讓「持鎖睡眠」變成災難。)

這就是為什麼:持 spinlock 時不可用 GFP_KERNEL(會睡眠,回顧 P3-T07)、不可 mutex_lock(mutex 會睡眠)、不可 copy_from_user(可能缺頁而睡眠,回顧 P1-T06)。持 spinlock = 進入「絕對不可睡眠」模式,直到釋放。這條紀律違反就死結,是 kernel 開發最常見的嚴重 bug 之一。

4. mutex:可睡眠、不可用於中斷 context

mutex(互斥鎖) 是另一個基本鎖,跟使用者態的 mutex(P1-T09)概念一致:拿不到鎖就睡眠等待(讓出 CPU,不空轉)。

flowchart TB
    MUTEX["mutex_lock(&m):想取得鎖"]
    MUTEX --> GOT2{"鎖空閒嗎?"}
    GOT2 -->|"是"| ENTER2["取得鎖,進入臨界區"]
    GOT2 -->|"否"| SLEEP2["★ 睡眠等待 ★
讓出 CPU 去睡,
等鎖釋放時被喚醒(不空轉)"]
    ENTER2 --> WORK2["臨界區:可較長,可做會睡眠的事
(因為 mutex 本身就是可睡眠 context)"]
    style SLEEP2 fill:#6fa8b8,color:#10100e
    style WORK2 fill:#8a9a5b,color:#10100e

特性與適用: - 可睡眠:拿不到鎖就睡眠(讓出 CPU),不浪費 CPU 空轉。 - 適合較長臨界區:因為不忙等,臨界區可以較長,甚至在臨界區裡做會睡眠的事(如 kmalloc(GFP_KERNEL))——因為持 mutex 本身就在可睡眠的 context。 - ★ 不可用於中斷 context ★:因為 mutex 取不到鎖時會睡眠,而中斷 context 不可睡眠(中斷處理要快、不能讓出 CPU 去睡)。在中斷處理常式裡 mutex_lock 是違法的(常見誤區)。

mutex vs spinlock 的核心抉擇:會睡眠/臨界區長 → mutex(但不能在中斷);要在中斷 context、或臨界區極短 → spinlock(但持鎖期間不可睡眠)。

(還有 semaphore:更通用的計數型同步原語,可允許 N 個持有者;mutex 可看作 N=1 的特例的優化版。實務上互斥用 mutex 較多,semaphore 用在需要計數的場景。)

5. spinlock 與中斷:spin_lock_irqsave

第 1 節提到的「中斷與行程 context 共享資料」問題,需要一個特殊的 spinlock 變體。先看問題:

flowchart TB
    SCENARIO["行程 context 的程式碼 P 和中斷處理常式 I
共享一個資料,都用 spinlock 保護"]
    SCENARIO --> PROBLEM["P 拿了 spinlock,進入臨界區改資料...
此時中斷來了,在『同一個 CPU』上跑 I"]
    PROBLEM --> ITRY["I 也要拿同一個 spinlock"]
    ITRY --> DEADLOCK2["★ 死結 ★
I 空轉等鎖,但鎖在被打斷的 P 手上;
P 要等 I 跑完才能繼續、才能釋放鎖
→ 同一 CPU 上互相卡死"]
    style PROBLEM fill:#e8a33d,color:#10100e
    style DEADLOCK2 fill:#c2603a,color:#f4ecd8

問題:行程 context 的 P 持有 spinlock 時,同一個 CPU 上來了中斷、跑中斷處理常式 I,而 I 也要拿同一把鎖——I 空轉等鎖,但鎖在「被中斷打斷的 P」手上,P 要等 I 跑完才能繼續釋放鎖——同一 CPU 上互相卡死。

解法:spin_lock_irqsave——取得 spinlock 的同時,關閉本 CPU 的中斷(並保存原本的中斷狀態),釋放時 spin_unlock_irqrestore 還原:

flowchart TB
    IRQSAVE["spin_lock_irqsave(&lock, flags)
① 關閉本 CPU 中斷(保存狀態到 flags)
② 取得 spinlock"]
    IRQSAVE --> SAFE["臨界區:本 CPU 不會被中斷打斷
→ 中斷處理常式不會在此時插進來搶鎖
→ 不會發生上面的同 CPU 死結"]
    SAFE --> RESTORE["spin_unlock_irqrestore(&lock, flags)
① 釋放 spinlock
② 還原中斷狀態(回到 flags 記錄的)"]
    style IRQSAVE fill:#e8a33d,color:#10100e
    style SAFE fill:#8a9a5b,color:#10100e

規則:當一個 spinlock 會同時被「行程 context」和「中斷 context」取得時,行程 context 這邊要用 spin_lock_irqsave(關中斷,避免被中斷打斷後死結)。如果這把鎖只在行程 context 用、或只在中斷 context 用,就不必。

常見誤區:中斷與行程 context 共享資料卻只用 spin_lock(沒關中斷)——會發生上述同 CPU 死結。判斷依據:這把鎖會不會被中斷處理常式拿?會 → 行程端用 spin_lock_irqsave。(驗收點:說明何時必須用 spin_lock_irqsave 而非 spin_lock。)

這直接關係你的工作:你的 I/O 完成處理常在中斷 context,若它和行程 context 的程式碼共享資料(很常見),保護那資料的 spinlock 在行程端就必須 spin_lock_irqsave。

6. 鎖 × context × 睡眠的選型總表

把所有規則整合成一張選型決策——這是這一課的核心產出:

flowchart TB
    Q1{"臨界區裡需要睡眠嗎?
(如 kmalloc(GFP_KERNEL)、
等 I/O、較長操作)"}
    Q1 -->|"需要睡眠"| MUTEX_PATH["用 mutex(可睡眠)
★ 但確認不在中斷 context ★
(中斷 context 不可睡眠 → 不能用 mutex)"]
    Q1 -->|"不需睡眠、臨界區短"| Q2{"這把鎖會被中斷處理常式取得嗎?"}
    Q2 -->|"會(行程+中斷共享)"| IRQSAVE_PATH["行程端用 spin_lock_irqsave
(關中斷,避免同 CPU 死結)"]
    Q2 -->|"不會(只在行程 / 只在中斷)"| SPIN_PATH["用一般 spin_lock"]
    RULE["★ 鐵則:持任何 spinlock 期間,絕不可睡眠 ★
(不可 GFP_KERNEL、mutex_lock、copy_from_user)"]
    SPIN_PATH --> RULE
    IRQSAVE_PATH --> RULE
    style MUTEX_PATH fill:#6fa8b8,color:#10100e

    style RULE fill:#c2603a,color:#f4ecd8

完整的合法/非法組合(精通目標): - 中斷 context 能用 mutex 嗎? ✗ 否(mutex 可睡眠,中斷不可睡眠)。中斷 context 要用 spinlock。 - 持 spinlock 能 kmalloc(GFP_KERNEL) 嗎? ✗ 否(會睡眠,持 spinlock 不可睡眠 → 死結)。要用 GFP_ATOMIC。 - 持 spinlock 能 mutex_lock 嗎? ✗ 否(mutex 會睡眠)。 - 行程+中斷共享的 spinlock,行程端用 spin_lock 夠嗎? ✗ 否,要 spin_lock_irqsave(關中斷)。 - 可睡眠、臨界區較長、純行程 context → mutex。 - 短臨界區、或中斷 context → spinlock(持鎖期間不可睡眠)。

這張表是你日後寫 module 同步的決策依據。選錯——尤其在你的 I/O 中斷路徑——就是系統死結。

打通關:把 kernel 同步(一)收攏成一個心智模型

一句話總結:kernel 因多核 + 中斷 + 搶佔需要嚴格同步——spinlock 忙等不可睡眠(持鎖期間絕不可做任何會睡眠的事,否則別的 CPU 忙等死結),mutex 可睡眠但不可用於中斷 context,行程與中斷共享的 spinlock 行程端要用 spin_lock_irqsave 關中斷;這張「鎖×context×睡眠」選型表是你 I/O 完成路徑的生死線,選錯就系統死結。

常見誤區與踩雷提醒

誤區一(最致命):持有 spinlock 時睡眠。 呼叫 kmalloc(GFP_KERNEL)、mutex_lock、copy_from_user 等會睡眠的函式 → 持鎖睡眠不釋放 → 別的 CPU 忙等死結。持 spinlock = 絕對不可睡眠模式。

誤區二:在中斷 context 用 mutex。 mutex 可睡眠,而中斷 context 不可睡眠 → 違法。中斷 context 要用 spinlock。

誤區三:中斷與行程 context 共享資料卻只用 spin_lock(沒關中斷)。 行程端持鎖時被中斷打斷,中斷處理常式搶同一鎖 → 同 CPU 死結。這種共享要用 spin_lock_irqsave。

誤區四:臨界區過長卻用 spinlock。 spinlock 忙等,長臨界區讓別的 CPU 空轉浪費。長臨界區(或需睡眠)用 mutex;spinlock 只用於短臨界區。

動手實作

環境:QEMU 虛擬機。鎖的實驗只在 VM。

任務 A — spinlock 與 mutex 各保護一個計數器(驗收點) 寫一個 module,開幾個 kernel 執行緒(kthread)並行對共享計數器累加: - 一個版本用 spinlock(spin_lock/spin_unlock)保護。 - 一個版本用 mutex(mutex_lock/mutex_unlock)保護。 驗證兩者結果都正確(等於預期總和)。驗收:spinlock 與 mutex 各正確保護計數器,結果正確。

任務 B — 回答 context 規則(驗收點,核心) 寫下並回答: 1. 「中斷 context 能否用 mutex?」→ 否,為什麼?(mutex 可睡眠,中斷不可睡眠。) 2. 「持有 spinlock 能否 kmalloc(GFP_KERNEL)?」→ 否,為什麼?(GFP_KERNEL 會睡眠,持 spinlock 睡眠會死結。) 驗收:兩題都答對並能說明原因。

任務 C — spin_lock_irqsave(驗收點) 在 module 裡示範 spin_lock_irqsave(&lock, flags) / spin_unlock_irqrestore(&lock, flags) 的用法。寫一句話:何時必須用 spin_lock_irqsave 而非 spin_lock?驗收:能說明(當鎖會被中斷處理常式取得、即行程與中斷共享時)。

任務 D(體會,謹慎)— 為什麼持鎖睡眠是錯的 用文字(不要真的在 production 觸發)說明:如果在持有 spinlock 時呼叫一個會睡眠的函式,為什麼會死結?(對照第 3 節的機制。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 spinlock 與 mutex 各正確保護一個被多執行緒/多 context 存取的計數器,結果正確。 2. ☐ 正確回答「中斷 context 能否用 mutex」(否)與「持 spinlock 能否 kmalloc(GFP_KERNEL)」(否)並說明原因。 3. ☐ 說明何時必須用 spin_lock_irqsave 而非 spin_lock。

評分量表: - 60(及格):能用兩種鎖。 - 80(熟練):能正確依 context 選型。 - 100(精通):能完整推理鎖 × context × 睡眠的所有合法/非法組合。

  • 這課餵給未來的(你的並行主線):P1-T08 race → P1-T09 鎖 → 本課(kernel 鎖選型)→ P3-T10 中斷與下半部(context 限制的延伸);spinlock/mutex → P3-T09 進階同步原語;「持鎖不可睡眠」→ 貫穿你所有 kernel 程式碼。lockdep(P3-T14)會自動偵測你違反這些規則。
  • 下一步 → P3-T09 kernel 同步(二)——atomic、RW lock、seqlock、per-CPU、completion:你已經會用基本的 spinlock/mutex。下一課介紹進階同步原語:atomic_t/refcount_t(原子型別,引用計數)、read-write 鎖(讀多寫少優化)、seqlock(讀者不阻塞寫者)、per-CPU 變數(每核一份、避免共享、消除鎖,回顧 P1-T03)、completion(等待事件完成)。這些直接對應你的工作:blk-mq 的 per-CPU 軟佇列、I/O 物件的引用計數、等待 DMA/GPU 完成的事件同步。
