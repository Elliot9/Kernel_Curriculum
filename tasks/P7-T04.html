P7-T04 · in-kernel lib/raid6 實作與 SIMD 演算法選擇

一句話:kernel 不是只有一份 parity 程式碼——lib/raid6/algos.c 內含多個 SIMD 實作(SSE2/AVX2/AVX512/NEON…),開機時跑 benchmark、選最快的那個(dmesg 的 raid6: using algorithm ...)。這是你 GPU offload 的「CPU 參考實作」與正確性基準:GPU 算出的 P/Q 必須和 lib/raid6 一致。

為什麼要先學這個(導讀)

P7-T03 你懂了 RAID-6 的數學(P/Q syndrome、GF 乘法、兩碟還原)。這一課看 kernel 怎麼實作它——lib/raid6/。這對你產品有雙重意義:它是你的「CPU 參考實作」對照組(GPU offload 的效益要拿它當基準),也是正確性基準(GPU 算出的結果必須和它一致)。

最有意思的設計:kernel 不是只有一份 parity 程式碼。lib/raid6/algos.c 內含多個 SIMD 實作——針對不同 CPU 指令集(x86 的 SSE2/AVX2/AVX512、ARM 的 NEON…)各有一份,開機時跑 benchmark、選最快的那個。你可以在 dmesg 看到它選了哪個(raid6: using algorithm ...)。

幾個要看的部件: - lib/raid6/algos.c:多 SIMD 實作的列表 + 開機 benchmark 擇優邏輯。 - include/linux/raid/pq.h:介面(P/Q 計算、還原的函式宣告)。 - lib/raid6/recov.c:還原(失效碟還原)的入口。 - gen_syndrome 路徑:產生 P/Q 的路徑。

還有一個關鍵的觀念釐清:這和 GPU offload 的關係——它們不是互斥的兩種東西,而是同一個數學在不同硬體上的加速。lib/raid6 用 CPU 的 SIMD 加速;你的產品用 GPU 加速。理解 kernel 怎麼做 SIMD 加速,你才能評估 GPU offload 的效益(快多少)與正確性(結果一致)。

為什麼這對你是 scope: direct?如上——這是你產品 GPU offload 的對照組與正確性基準。理解 lib/raid6,你才知道「offload 到底省了什麼、結果對不對」。

(這一課是 P5-T06 讀原始碼經驗的又一次應用——lib/raid6 比 NVMe 驅動小,但同樣用「從一個函式切入」的讀碼法。)

1. lib/raid6 的角色:被 raid5.c 呼叫的 parity 引擎

lib/raid6 的角色:它是被 raid5.c 呼叫的「parity 計算引擎」。raid5.c(P7-T01)處理 stripe,需要算 P/Q 時,呼叫 lib/raid6 的介面(pq.h 宣告的函式,如 gen_syndrome 算 P/Q、recovery 還原)。lib/raid6 實作 P7-T03 的數學(XOR + GF 乘法),用 SIMD 加速。

分工:raid5.c 管「RAID 邏輯」(stripe、狀態機、I/O 協調);lib/raid6 管「純數學計算」(P/Q、還原）。這個分工對你很重要——你 offload 時,就是把「lib/raid6 的計算」換成 GPU 算(在 P7-T01 的 raid5.c 呼叫點介入)。raid5.c 的 RAID 邏輯不變,只換掉計算引擎。

2. 多 SIMD 實作:同一數學的多個版本

lib/raid6 最有意思的設計:同一個 P/Q 計算,有多個針對不同 SIMD 指令集的實作。

    IMPLS --> WHY8
    NOTE48["★ 常見誤區:以為只有單一 parity 實作 ★

lib/raid6 有多個實作(同數學、不同指令集):純 C(int1/int2…,後備)、x86 SIMD(sse2/avx2/avx512,一次算 16/32/64 byte）、ARM 的 neon、其他架構的 SIMD…

為何多版本:不同 CPU 支援不同指令集,各指令集的寬度/效能不同。所以每個都實作一次,執行期選最適合這台機器的(第 3 節)。GF 乘法用 SIMD 的向量查表(如 x86 的 PSHUFB)一次算多 byte(回顧 P7-T03 的可平行性——SIMD 是 CPU 上的平行)。

常見誤區:以為只有單一 parity 實作——實為多 SIMD 版本 + 執行期擇優。這個設計讓 kernel 在任何 CPU 上都能跑出該 CPU 最好的 parity 效能。

(對照你產品:lib/raid6 用 CPU SIMD 平行;你用 GPU 平行——同一數學、不同硬體的加速,第 6 節。)

程式碼位置(驗收點:在 algos.c 指出執行期擇優的邏輯位置):algos.c 裡有個選擇函式(如 raid6_select_algo()),就是執行期 benchmark 擇優的邏輯所在。

這個「執行期 benchmark 擇優」是個漂亮的工程模式:不在編譯期猜哪個快,而在執行期實測——因為「哪個 SIMD 最快」取決於實際的 CPU,只有跑了才知道。

gen_syndrome 路徑:raid5.c 要算 P/Q 時,呼叫 raid6_call.gen_syndrome(...)(raid6_call 是開機選定的那個實作,第 3 節;這是 pq.h 宣告的介面)。選定的 SIMD 實作執行:P = XOR、Q = ⊕ gⁱ·Dᵢ(GF 乘法 + XOR,用 SIMD 向量化一次處理一整排 byte,P7-T03)。算完寫到 parity chunk。

常見誤區:混淆 gen_syndrome(產生 P/Q)與 recovery(還原)——這是兩條不同的路徑: - gen_syndrome:正常寫入時,從資料算出 P/Q。 - recovery(第 5 節):碟失效時,從 P/Q + 其餘資料還原失效資料。

兩者用不同的函式、不同的數學路徑(產生 vs 解聯立)。讀碼時要分清你在看哪一條。對你產品:gen_syndrome 是「寫入時算 parity」的 offload 對象;recovery 是「degraded/rebuild 時還原」的 offload 對象(P7-T01)——兩者都可 offload,但路徑不同。

recov.c 的還原(驗收點:在 recov.c/pq.h 指出還原與介面的入口並說明其作用):recov.c 是還原入口,依「失效幾顆、哪幾顆」選還原方法——一顆資料碟失效用 P 還原(就是 RAID-5 的 XOR 救援,P7-T02)、兩顆資料碟失效解 GF 二元聯立(P7-T03)、還有資料+Q、資料+P 等各種情形。recov 也有 SIMD 實作(recov_ssse3.c 等）+ 擇優(還原同樣可向量化加速)。

6. 與 GPU offload 的關係:同一數學,不同硬體

最後,釐清這一課對你產品最重要的觀念:lib/raid6 和 GPU offload 不是互斥的——是同一數學在不同硬體上的加速。

lib/raid6 與 GPU offload 的關係(常見誤區:以為 GPU offload 與 lib/raid6 互斥):它們不是互斥,而是同一數學在不同硬體上的加速: - lib/raid6:在 CPU 上加速——SIMD 一次算 16~64 byte + 開機擇優。 - 你的產品:在 GPU 上加速——數千 thread,每個算一個(或一組)byte(逐 byte 獨立,P7-T02/P7-T03)。

關係:加速器的選擇——可互補(小 I/O 用 CPU、大批量用 GPU)或取代(GPU 算所有 parity,CPU 省下來做別的)。這正是你產品的設計空間:什麼時候用 GPU、什麼時候用 CPU SIMD。

最關鍵的一點:正確性基準——GPU 算的 P/Q 必須和 lib/raid6 一致(同一數學、同樣的 0x11D/g={02}、同樣的結果)。所以 lib/raid6 是你驗證 GPU kernel 正確性的對照組:寫好 GPU parity kernel,拿同一批資料,GPU 算的 P/Q 要和 lib/raid6 算的逐 byte相同——這是你產品正確性的驗證方法。

常見誤區與踩雷提醒

誤區一:以為只有單一 parity 實作。 lib/raid6 有多個 SIMD 版本(SSE2/AVX2/AVX512/NEON/純 C…)+ 執行期擇優。

誤區二:忽略 dmesg 開機訊息已標明選用的演算法。 dmesg | grep raid6 直接告訴你這台機器選了哪個實作,不必猜。

誤區三:混淆 gen_syndrome(產生 P/Q)與 recovery(還原)。 gen_syndrome 是寫入時從資料算 P/Q;recovery(recov.c)是碟失效時從 P/Q + 其餘資料還原。兩條不同路徑、函式。

誤區四:以為 GPU offload 與 lib/raid6 互斥。 是同一數學在不同硬體上的加速(CPU SIMD vs GPU),可互補或取代。且 GPU 結果必須和 lib/raid6 一致(正確性基準)。

動手實作

環境:Linux(看 dmesg)+ Bootlin 讀碼(安全)。

任務 A — dmesg 找選用的演算法(驗收點) 在 Linux 上 dmesg | grep raid6(或 journalctl -k | grep raid6),找出 raid6 實際選用的 SIMD 演算法(如 raid6: using algorithm avx2x4 gen() ...)。驗收:在 dmesg 找出並回報 raid6 實際選用的 SIMD 演算法。(若 dmesg 沒有,可能 raid6 模組未載入;modprobe raid6_pq 或建一個 RAID-6 陣列觸發。)

任務 B — algos.c 的擇優邏輯(驗收點) 在 lib/raid6/algos.c(https://elixir.bootlin.com/linux/v6.12/source/lib/raid6/algos.c ）中,找出執行期 benchmark 擇優的邏輯位置(如 raid6_select_algo——偵測支援、benchmark、選最快)。驗收:在 algos.c 指出執行期擇優的邏輯位置。

任務 C — recov.c / pq.h 的還原與介面入口(驗收點) 在 recov.c(https://elixir.bootlin.com/linux/v6.12/source/lib/raid6/recov.c ）指出還原入口、在 pq.h(https://elixir.bootlin.com/linux/v6.12/source/include/linux/raid/pq.h ）指出介面宣告(gen_syndrome、recovery 函式)。驗收:在 recov.c/pq.h 指出還原與介面的入口並說明其作用。

任務 D(連結)— 與你的 GPU offload 寫一兩句話:lib/raid6 和你產品的 GPU offload 是什麼關係?你會怎麼用 lib/raid6 驗證 GPU kernel 的正確性?(提示:同一數學不同硬體;GPU 算的 P/Q 要和 lib/raid6 逐 byte 一致。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 在 dmesg 找出並回報 raid6 實際選用的 SIMD 演算法。 2. ☐ 在 algos.c 指出執行期擇優的邏輯位置。 3. ☐ 在 recov.c/pq.h 指出還原與介面的入口並說明其作用。

評分量表: - 60(及格):能找到選用演算法。 - 80(熟練):能解讀擇優機制與還原入口。 - 100(精通):能說明 lib/raid6 的 SIMD 加速與 GPU offload 在架構上的對應與取捨。

延伸與銜接

  • 對應工作場景:直接對應——這是你產品的「CPU 參考實作」對照組;理解 kernel 怎麼做 SIMD 加速,才能評估 GPU offload 的效益與正確性基準。
  • 這課餵給未來的(XOR→parity→GPU 平行主線):P7-T02 XOR → P7-T03 GF 數學 → 本課 lib/raid6(CPU SIMD 實作)→ P7-T06 CUDA(GPU 實作,要和 lib/raid6 結果一致)。SIMD 擇優的工程模式 → 你產品「何時用 CPU/GPU」的設計。
  • 下一步 → P7-T05 GPUDirect Storage(GDS)/cuFile 與上游 P2PDMA 的銜接:你懂了 parity 數學(P7-T02/P7-T03)和 kernel 的 CPU 實作(本課)。下一課回到資料路徑——怎麼把 NVMe 的資料送到 GPU 去算 parity。GPUDirect Storage(GDS) 是 NVIDIA 的現成方案:NVMe → GPU 記憶體直通 DMA,不繞 host(建立在你 P6-T05 學的 P2PDMA 之上)。關鍵的版本事實(我已查證):CUDA 12.8 起 GDS 在 x86_64 改用上游 PCI P2PDMA,不再依賴 nvidia-fs.ko/nvme.ko patch;但重大限制——GDS NVMe-P2PDMA 不支援 RAID0/multipath,且啟用 KASLR 時會失敗。對你的 RAID 產品,這些限制可能迫使你走自訂 P2PDMA 路徑而非現成的 GDS——這是直接影響架構選型的決策。
