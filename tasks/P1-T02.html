P1-T02 · 記憶體階層與快取

一句話:記憶體存取的成本不是均等的——快取命中和跑一趟主記憶體,可能差幾十到幾百倍。理解這個鴻溝,以及 CPU 用「cache」來填補它的機制,你就懂了為什麼「同樣的計算量,資料擺法不同,速度天差地別」。

為什麼要先學這個(導讀)

上一課 P1-T01 結尾留了一個伏筆:CPU 運算用暫存器,資料平時在記憶體,而「記憶體比暫存器慢」。這一課要告訴你,這個「慢」誇張到會顛覆你的直覺。

寫高階語言時,你大概有個隱含假設:「讀一個變數就是讀一個變數,成本都差不多。」這個假設大錯特錯,而且這個錯誤會讓你寫出慢上數倍卻不知為何的程式。真相是:CPU 和主記憶體之間有個巨大的速度鴻溝,於是工程師在中間塞了好幾層快取(cache)——容量一層比一層小、但速度一層比一層快。你的資料在不在快取裡,決定了存取它是「飛快」還是「龜速」。

為什麼這對你是 scope: indirect(間接對應工作)?因為你的產品在高效能 I/O 與 parity 計算路徑上,對 cache 行為極度敏感。一個對 cache 不友善的資料結構或走訪順序,可能讓你的吞吐量腰斬。而下一課 P1-T03 的 false sharing、以及 kernel 的 per-CPU 設計、____cacheline_aligned,全都建立在這一課的 cache 概念上。先把「cache 如何運作、為什麼資料佈局影響效能」弄懂,後面那些優化手法你才知道在優化什麼。

開始之前(前置確認)

  • 依賴:P1-T01(你已知 CPU 用暫存器運算、資料在記憶體、兩者有速度差)。
  • 自我檢測: 1. 你還記得 P0-T03 陣列是「連續記憶體」嗎?這課會用二維陣列的記憶體排列來做實驗。 2. 你能用一個簡單的計時方式量測程式執行時間嗎?(clock() 或 time ./prog,這課要量兩種走訪的時間差。)

核心內容

拆成這幾節:(1) 速度鴻溝有多大 → (2) 記憶體階層金字塔 → (3) 局部性:cache 為何有效 → (4) cache line:一次搬一整條 → (5) hit/miss 的代價 → (6) 招牌實驗:row-major vs column-major,最後打通關。

1. 速度鴻溝:暫存器與主記憶體差幾百倍

先用一個「把 CPU 時間放大到人類尺度」的比喻,讓你感受這個鴻溝。假設 CPU 存取暫存器要「1 秒」,那麼各層的相對時間大約是(數量級示意,非精確值):

(伸手拿桌上的筆)"]
    L1["L1 快取:約 1-3 秒
(打開抽屜拿東西)"]
    L2["L2 快取:約 10 秒
(走到隔壁房間拿)"]
    L3["L3 快取:約 40 秒
(走到樓下拿)"]
    MEM["主記憶體 RAM:約 數百秒
(開車去隔壁城市拿)"]
    DISK["磁碟(傳統):相當於數個月-數年
(搭船橫渡大洋去拿)"]
    REG --> L1 --> L2 --> L3 --> MEM --> DISK
    style REG fill:#8a9a5b,color:#10100e
    style MEM fill:#e8a33d,color:#10100e
    style DISK fill:#c2603a,color:#f4ecd8

重點不是精確數字,而是數量級的差異:從暫存器到主記憶體,差了兩三個數量級。這意味著:如果 CPU 每次運算都要等主記憶體,它大部分時間都在發呆等資料。cache 的存在,就是為了讓 CPU 盡量少跑那趟遙遠的主記憶體。

比喻的極限:上面的「秒數」是為了讓你感受比例,別當成真實數字記。真實的延遲會因硬體世代而異,而且現代 CPU 有亂序執行等技巧來「藏住」部分延遲。但核心事實不變:越靠近 CPU 的儲存越快越小,越遠的越慢越大,差距是數量級的。

2. 記憶體階層:速度與容量的金字塔

把這些儲存層級疊起來,形成一個金字塔——這就是「記憶體階層(memory hierarchy)」:

flowchart TB
    subgraph pyramid["記憶體階層(上快下慢、上小下大)"]
        REG["暫存器(最快、最小,十幾個)"]
        L1["L1 cache(極快,數十 KB)"]
        L2["L2 cache(很快,數百 KB)"]
        L3["L3 cache(快,數 MB,常多核共享)"]
        RAM["主記憶體 RAM(慢,數十 GB)"]
        DISK["磁碟/SSD(最慢,數百 GB-TB)"]
        REG --- L1 --- L2 --- L3 --- RAM --- DISK
    end
    style REG fill:#8a9a5b,color:#10100e
    style RAM fill:#e8a33d,color:#10100e
    style DISK fill:#c2603a,color:#f4ecd8

設計哲學是:讓「最常用的資料」待在「最快的層」。CPU 要資料時,先問 L1,沒有再問 L2,再問 L3,最後才去主記憶體。每往下一層,慢一個數量級。cache(L1/L2/L3)是這個策略的核心——它們自動保留「最近用過、最可能再用」的資料,讓 CPU 大多數時候在快的層就拿到。

而 cache 之所以「有效」,靠的是一個關於程式行為的觀察,叫局部性——下一節說。

3. 局部性:為什麼 cache 猜得準

cache 容量很小,裝不下全部資料。它怎麼知道該留哪些?靠一個經驗法則:程式的記憶體存取有局部性(locality),分兩種:

flowchart TB
    subgraph locality["局部性:程式存取記憶體的兩個傾向"]
        TEMP["時間局部性
(temporal locality)
剛用過的東西,
很可能馬上又用
例:迴圈變數 i 每圈都用"]
        SPAT["空間局部性
(spatial locality)
用了某個位址,
很可能接著用它附近的
例:走訪陣列 arr[0],arr[1],arr[2]..."]
    end
    style TEMP fill:#6fa8b8,color:#10100e
    style SPAT fill:#8a9a5b,color:#10100e

  • 時間局部性:剛存取過的資料,短期內很可能再被存取。所以 cache 「留住最近用過的」是個好賭注。
  • 空間局部性:存取了某位址,接下來很可能存取它附近的位址(因為陣列是連續的、程式碼是循序的)。所以 cache 「連同附近一起載入」也是好賭注——這直接導出下一節的 cache line。

cache 就是賭這兩個傾向成立。對絕大多數程式,它賭對了,所以 cache 命中率很高。但你寫的程式有沒有局部性,決定了 cache 幫不幫得上你——第 6 節的實驗會血淋淋地展示「破壞空間局部性」的代價。

4. cache line:cache 一次搬一整條,不是一個 byte

這是本課最關鍵的機制細節,也是後面實驗和 false sharing(P1-T03)的基礎。

當 CPU 因為 cache miss 要去主記憶體拿資料,它不是只拿你要的那幾個 byte,而是拿一整條「cache line」(通常 64 bytes)。也就是說,你讀一個 4-byte 的 int,CPU 會把包含它的那整條 64 bytes 一起載入 cache。

flowchart TB
    REQ["CPU 要讀 arr[0](4 bytes)"]
    MISS["cache miss(不在 cache 裡)"]
    REQ --> MISS
    FETCH["去主記憶體,
★ 載入包含它的整條 cache line(64 bytes)★
= arr[0]~arr[15](假設 int 4 bytes)"]
    MISS --> FETCH
    NEXT["接下來讀 arr[1]~arr[15]:
已經在 cache 裡了 → 全部命中,飛快"]
    FETCH --> NEXT
    style FETCH fill:#e8a33d,color:#10100e
    style NEXT fill:#8a9a5b,color:#10100e

這就是空間局部性的硬體實現:因為 CPU 連同「附近的 64 bytes」一起載入,所以當你循序走訪陣列(arr[0], arr[1], arr[2]...),只有每 16 個元素(64/4)才 miss 一次去拿,其餘 15 個都直接命中。一次 miss 的成本,被攤平到 16 次存取上。

反過來,如果你跳著存取(每次跳很遠,跨過 cache line),那每次存取都 miss、都要跑一趟主記憶體,cache 完全幫不上忙——這正是下面實驗要展示的災難。

64 bytes 這個數字要記住:常見 CPU 的 cache line 大小是 64 bytes。kernel 的 ____cacheline_aligned、避免 false sharing 的 padding,用的就是這個數字(P1-T03 詳述)。

5. hit 與 miss 的代價

把命中與失誤的成本對比清楚:

flowchart LR
    ACCESS["CPU 要一個資料"]
    ACCESS --> Q{"在 cache 裡嗎?"}
    Q -->|"命中 hit"| HIT["直接從 cache 拿
極快(幾個週期)"]
    Q -->|"失誤 miss"| MISS["去下一層(慢得多),
載入整條 cache line,
再給 CPU
慢數十到數百倍"]
    style HIT fill:#8a9a5b,color:#10100e
    style MISS fill:#c2603a,color:#f4ecd8

一個程式快不快,常常不是看它做多少運算,而是看它的 cache 命中率。一個 miss 連連的程式,CPU 大半時間在等記憶體,再少的運算也快不起來。這顛覆了新手「程式碼少 = 快」的直覺——cache 行為常常才是效能的主宰。

6. 招牌實驗:row-major vs column-major

現在用一個經典實驗,讓你親眼量到 cache 的威力。走訪一個大的二維陣列,用兩種順序,計時。

先理解 C 的二維陣列在記憶體裡怎麼擺。int m[N][N] 是列優先(row-major):同一列(row)的元素連續排列,一列接一列。

flowchart TB
    subgraph rowmajor["int m[3][3] 在記憶體的實際排列(row-major)"]
        direction LR
        R0["m[0][0] m[0][1] m[0][2]"] --- R1["m[1][0] m[1][1] m[1][2]"] --- R2["m[2][0] m[2][1] m[2][2]"]
    end
    NOTE["同一列的元素在記憶體中相鄰;
跨到下一列要跳 N 個元素"]
    rowmajor --> NOTE
    style R0 fill:#8a9a5b,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

現在比較兩種走訪順序對 cache 的影響:

flowchart TB
    subgraph good["✓ row-major 走訪:for i, for j → m[i][j]"]
        G1["照記憶體排列順序走
(m[0][0],m[0][1],m[0][2],m[1][0]...)"]
        G2["每條 cache line 載入後,
裡面的元素被連續用完
→ 高命中率,飛快"]
        G1 --> G2
    end
    subgraph bad["✗ column-major 走訪:for j, for i → m[i][j]"]
        B1["跳著走
(m[0][0],m[1][0],m[2][0]...)
每次跳 N 個元素,跨 cache line"]
        B2["每次存取幾乎都 miss,
載入整條 line 卻只用其中一個
→ 低命中率,龜速(常慢數倍)"]
        B1 --> B2
    end
    style G2 fill:#8a9a5b,color:#10100e
    style B2 fill:#c2603a,color:#f4ecd8

關鍵洞察:兩種走訪做的運算完全一樣(都是把 N×N 個元素都碰一遍),但 row-major 順著記憶體排列走(契合空間局部性 + cache line),column-major 跳著走(破壞局部性)。結果 row-major 常快上數倍。這就是「同樣計算量、資料存取順序不同、速度天差地別」最赤裸的證明。

對你工作的意義:設計處理大量資料的迴圈與資料結構時(你的 parity 計算、I/O 緩衝走訪),讓存取順著記憶體、契合 cache line,是免費的巨大效能。反之,一個對 cache 不友善的存取模式,會悄悄吃掉你的吞吐量。

一句話總結:記憶體存取成本極不均等,CPU 靠多層 cache 與「一次載入整條 cache line」來填補與主記憶體的鴻溝;因此你的資料怎麼擺、用什麼順序存取,直接決定 cache 命中率、進而主宰效能——在高效能 I/O 路徑上,對 cache 友善是免費的數倍加速。

常見誤區與踩雷提醒

誤區一:以為記憶體存取成本均等。 快取命中與跑一趟主記憶體可差數十到數百倍。「讀一個變數」的成本,取決於它在不在 cache。

誤區二:忽略 cache line 一次載入一整條。 CPU 不是逐 byte 拿,而是一次 64 bytes。這既是「循序存取很快」的原因,也是 false sharing(P1-T03)的根源。

誤區三:以為「程式碼少 = 快」。 運算量少不代表快;cache 行為常常才是主宰。一個 miss 連連的「精簡」程式,可能慢過一個 cache 友善的「囉嗦」程式。

誤區四:寫多維陣列迴圈時搞錯走訪順序。 在 C(row-major)裡,內層迴圈應該走「列內」(變動最右的索引),才順著記憶體。把順序寫反(column-major 走訪)會大幅降速。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 量測 row-major vs column-major

#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#define N 2048
static int m[N][N];
int main(void) {
    clock_t t1 = clock();
    long sum1 = 0;
    for (int i = 0; i < N; i++)        // row-major:順著記憶體
        for (int j = 0; j < N; j++)
            sum1 += m[i][j];
    clock_t t2 = clock();
    long sum2 = 0;
    for (int j = 0; j < N; j++)        // column-major:跳著走
        for (int i = 0; i < N; i++)
            sum2 += m[i][j];
    clock_t t3 = clock();
    printf("row-major   : %.3f 秒\n", (double)(t2-t1)/CLOCKS_PER_SEC);
    printf("column-major: %.3f 秒\n", (double)(t3-t2)/CLOCKS_PER_SEC);
    return 0;
}

用 gcc -O2 prog.c -o prog && ./prog 跑(注意:兩個迴圈做的運算量完全相同)。觀察 column-major 明顯較慢(常 2-8 倍)。寫一句話:用空間局部性 + cache line 解釋為什麼。

任務 B — 確認 cache line 大小

getconf LEVEL1_DCACHE_LINESIZE     # 印出 L1 data cache line 大小,通常 64

確認你機器的 cache line 是 64 bytes(這是任務 A 裡「每 16 個 int 才 miss 一次」的依據,也是 P1-T03 padding 用的數字)。

任務 C(思考)— 為什麼 row-major 大約每 16 次才 miss? 寫一句話推算:cache line 64 bytes,int 4 bytes,那麼一條 cache line 裝幾個 int?row-major 走訪時,大約每幾次存取才發生一次 miss?(答案:16 個 int / 條,約每 16 次 miss 一次。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 對 N×N(N≥1024)矩陣,量測 row-major 與 column-major 走訪時間,確認 row-major 明顯較快(通常數倍)。 2. ☐ 能用空間局部性 + cache line 解釋這個時間差。 3. ☐ 能說出常見 cache line 大小為 64 bytes。

評分量表: - 60(及格):能複述記憶體階層。 - 80(熟練):能用局部性解釋實驗結果(為何 row-major 快)。 - 100(精通):能據此提出資料結構/走訪順序的最佳化建議,並連結到高效能 I/O 路徑。

延伸與銜接

  • 對應工作場景:間接對應——高效能 I/O 與 parity 計算路徑對 cache 行為敏感;cache 友善的資料佈局與存取順序是免費的效能。下一課的 false sharing 與 kernel 的 per-CPU 設計都由此延伸。
  • 這課餵給未來的:cache line(64 bytes)→ P1-T03 false sharing 與對齊;局部性 → 設計高效能資料結構;「記憶體比暫存器慢」的量化 → 理解為何 kernel 處處在意 cache。
  • 下一步 → P1-T03 快取一致性與對齊的硬體意義:你已經懂單核心的 cache。但現代 CPU 是多核心,每個核心有自己的 cache——那麼當兩個核心都快取了同一塊資料,一個改了,另一個怎麼知道?這就是「快取一致性(cache coherence)」。下一課還會揭露一個陰險的效能殺手 false sharing(兩個執行緒寫不同變數卻互相拖累),它直接關係到你產品的多核心擴展性與 kernel 的 per-CPU 設計。
