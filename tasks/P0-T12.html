P0-T12 · Phase 0 整合驗收(出關門檻)

一句話:不再學新語法,而是把 Phase 0 學到的指標、struct、手動記憶體管理、函式指標,全部用在三個經典專案上——動態陣列、鏈結串列、簡易配置器。三者都要通過 valgrind 零錯誤。做得出來,你就準備好踏進 kernel 的世界了。

🚪 這是出關門檻

這是 Phase 0 的關卡(gate)。本 task 達到 80 分(三個專案完成且 valgrind 乾淨),才算真正掌握了進入 Phase 1 所需的 C 與系統基礎。

為什麼設這道關?因為從 Phase 1 開始,你會進入虛擬記憶體、kernel 邊界、並行——那些主題預設你已經能熟練操作指標和手動記憶體。如果指標和 malloc/free 還不是你的肌肉記憶,Phase 1 會變成災難。這道關就是確保地基夠穩。

  • 動態陣列會逼你面對 realloc、容量管理、和「擴容後指標可能改變」——這是 P0-T05 heap、P0-T06 記憶體管理的綜合應用。
  • 鏈結串列是 kernel 最核心的資料結構(P2-T01 的 list_head 你會天天用),手刻一次,你才真正懂節點、指標接續、和刪除時的陷阱。

  • 依賴:整個 Phase 0(P0-T01 ~ P0-T11)。
  • 這一課不教新東西,而是檢驗你能否整合運用。動手前,確認這些都已是你的直覺: 1. 指標的取址 / 解參考 / 運算(P0-T02、P0-T03)。 2. malloc/free/realloc 的規矩、四種記憶體錯誤(P0-T06)。 3. struct 的定義與成員存取(P0-T04)。 4. 用 valgrind --leak-check=full 讀報告(P0-T06)。

核心內容:三個專案的設計

下面給每個專案的結構與關鍵步驟圖,但刻意不給完整程式碼——這是驗收關卡,程式碼要你自己寫。圖幫你建立正確的心智模型,寫碼是你的任務。

專案一:可自動擴容的動態陣列

C 的原生陣列大小固定(P0-T03)。動態陣列(像 C++ 的 vector、JS 的 Array)能隨元素增加自動長大。設計:

flowchart TB
    STRUCT["struct dyn_array {
  int *data;  // 指向 heap 上的一塊
  size_t size;  // 目前有幾個元素
  size_t capacity; // 目前配置了幾格
}"]
    style STRUCT fill:#6fa8b8,color:#10100e

核心是 push(在尾端加一個元素)時的「容量檢查與擴容」流程:

flowchart TB
    PUSH["push(arr, value)"]
    Q{"size == capacity?
(滿了嗎?)"}
    PUSH --> Q
    Q -->|"否,還有空間"| ADD["data[size] = value
size++"]
    Q -->|"是,滿了"| GROW["擴容:
new_cap = capacity × 2
(常見策略:翻倍)"]
    GROW --> REALLOC["realloc(data, new_cap × sizeof(int))"]
    REALLOC --> CHECK{"realloc 回傳 NULL?
(失敗?)"}
    CHECK -->|"是"| FAIL["處理失敗
(別覆蓋舊指標!見誤區)"]
    CHECK -->|"否"| UPDATE["data = 新指標
capacity = new_cap"]
    UPDATE --> ADD
    style GROW fill:#e8a33d,color:#10100e
    style FAIL fill:#c2603a,color:#f4ecd8
    style ADD fill:#8a9a5b,color:#10100e

為什麼翻倍擴容? 如果每次只 +1,push N 個元素要 realloc N 次(每次都可能複製整塊),總成本很高。翻倍策略讓 realloc 的次數降到約 log₂(N),攤平後每次 push 的平均成本是常數——這是個漂亮的工程取捨,值得你理解(而非死記)。

驗收要求:從容量 0 開始,連續 push 1000 個元素,全部能讀回正確值,且過程中自動擴容;最後 free,valgrind 零洩漏。

專案二:單向鏈結串列(增、刪、查)

鏈結串列不要求連續記憶體——每個節點各自 malloc,用一個指標串到下一個。這是 kernel 最重要的資料結構。

flowchart LR
    HEAD["head 指標"] --> N1["節點1
data | next"]
    N1 --> N2["節點2
data | next"]
    N2 --> N3["節點3
data | next"]
    N3 --> NULL["NULL
(串尾)"]
    style N1 fill:#8a9a5b,color:#10100e
    style NULL fill:#24221d,color:#cfc6b0


flowchart TB
    STRUCT["struct node {
  int data;
  struct node *next; // 指向下一個節點
}"]
    style STRUCT fill:#6fa8b8,color:#10100e

最容易出錯的是「刪除節點」的指標接續。要刪除節點 B(在 A 之後、C 之前),關鍵是先讓 A 的 next 跳過 B 指向 C,再 free B——順序錯了會出大事:

flowchart TB
    S1["刪除前:A → B → C"]
    S2["步驟1:用一個指標記住 B
(待會要 free 它)
★ 不能先 free,否則就找不到 C 了 ★"]
    S3["步驟2:A->next = B->next
(讓 A 直接指向 C,跳過 B)"]
    S4["步驟3:free(B)
(現在 B 已經沒人指向,安全釋放)"]
    S5["刪除後:A → C(B 已釋放)"]
    S1 --> S2 --> S3 --> S4 --> S5
    style S2 fill:#e8a33d,color:#10100e
    style S4 fill:#c2603a,color:#f4ecd8
    style S5 fill:#8a9a5b,color:#10100e

為什麼順序這麼重要? 如果你先 free(B),再想讀 B->next 去接 A 和 C,那就是 use-after-free(P0-T06)——B 已經釋放,B->next 讀到的是垃圾,你就永遠接不回 C(整條串列後半段洩漏)。必須先用 A->next = B->next 把橋接好(或先存下 B->next),最後才 free B。

flowchart LR
    subgraph wrong["✗ 錯誤順序"]
        W1["free(B)"] --> W2["B->next 讀到垃圾
→ 接不回 C
→ 後半串列洩漏 + UAF"]
    end
    subgraph right["✓ 正確順序"]
        R1["A->next = B->next
(先橋接)"] --> R2["free(B)
(後釋放)"]
    end
    style W2 fill:#c2603a,color:#f4ecd8
    style R1 fill:#8a9a5b,color:#10100e

驗收要求:做 100 次隨機增 / 刪後,走訪結果正確,且 valgrind 零洩漏(代表每個刪除都正確 free、沒有漏接)。

專案三:極簡記憶體配置器(free list)

這是三個裡最有挑戰、也最能讓你「看穿 malloc/free 內部」的。你要管理一塊大記憶體(可以是一個大的 static 陣列,或一次 malloc 的大區塊),自己實作 my_alloc / my_free,維護一個「空閒區塊清單(free list)」記錄哪些片段還空著。

flowchart TB
    POOL["一大塊你管理的記憶體 pool"]
    POOL --> SPLIT["切成若干區塊,
每塊前面放一個 header
(記錄這塊多大、是否空閒、下一個空閒塊在哪)"]
    style POOL fill:#6fa8b8,color:#10100e
    style SPLIT fill:#e8a33d,color:#10100e

my_alloc(n) 的流程(最簡單的 first-fit 策略):

flowchart TB
    A["my_alloc(n)"]
    B["走訪 free list,
找第一個『夠大(>= n)』的空閒塊"]
    A --> B
    C{"找到了嗎?"}
    B --> C
    C -->|"否"| FAIL["回傳 NULL(空間不足)"]
    C -->|"是"| D{"這塊比 n 大很多?"}
    D -->|"是"| SPLIT["切割:前 n 給使用者,
剩餘的留在 free list 當較小的空閒塊"]
    D -->|"否,大小差不多"| WHOLE["整塊給使用者"]
    SPLIT --> MARK["標記為已使用,
從 free list 移除(或調整)"]
    WHOLE --> MARK
    MARK --> RET["回傳這塊資料區的指標"]
    style SPLIT fill:#e8a33d,color:#10100e
    style RET fill:#8a9a5b,color:#10100e

my_free(p) 把區塊還回 free list。進階(衝 100 分):合併相鄰空閒塊(coalescing)以對抗碎片化——當你 free 一塊,若它前後相鄰的塊也是空閒的,就合併成一個更大的空閒塊:

flowchart TB
    S1["my_free(p):把 p 那塊標記為空閒"]
    S2{"它前面相鄰的塊也空閒?"}
    S1 --> S2
    S2 -->|"是"| M1["與前塊合併成一塊更大的"]
    S2 -->|"否"| S3{"它後面相鄰的塊也空閒?"}
    M1 --> S3
    S3 -->|"是"| M2["與後塊合併"]
    S3 -->|"否"| DONE["放回 free list"]
    M2 --> DONE
    NOTE["合併能對抗『碎片化』:
避免記憶體被切成一堆
用不上的小碎塊"]
    DONE --> NOTE
    style M1 fill:#e8a33d,color:#10100e
    style M2 fill:#e8a33d,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

為什麼這是 SLUB 的暖身? kernel 的記憶體配置器(P3-T13 的 SLUB)解決的正是同一類問題——如何高效地把一大塊記憶體切給無數請求、又能回收重用、還要對抗碎片。你手刻的這個迷你版,讓你之後讀 SLUB 時,知道它在優化什麼問題。

驗收要求:能 alloc / free,且能重用已釋放的區塊(free 一塊後,下次 alloc 同樣大小應該能拿到那塊,證明你的 free list 真的在運作)。

一句話總結:這三個專案不是練習題,是你的 kernel 預演——動態陣列教你緩衝區與容量、鏈結串列是 kernel 的命脈資料結構、配置器讓你看穿記憶體管理的內部。能把它們寫到 valgrind 零錯誤,代表你已具備 kernel 開發最基本的記憶體紀律。這就是出關的真正含義。

常見誤區與踩雷提醒

動態陣列: - 擴容後忘記更新指標或容量。realloc 可能回傳一個全新的位址(舊的已失效)。必須 data = realloc(...) 更新指標,並更新 capacity。沿用舊指標 = use-after-free。 - 沒處理 realloc 失敗。realloc 失敗回傳 NULL,但舊區塊仍然有效。若你寫 data = realloc(data, ...) 而它回傳 NULL,你就同時失去了舊指標(洩漏)。正解:先用暫時指標接 realloc 結果,確認非 NULL 再賦值給 data。

鏈結串列: - 刪除節點時的指標接續錯誤(如核心內容詳述):必須先橋接 A->next = B->next,後 free(B)。順序錯 = UAF + 後半串列洩漏。 - 刪除頭節點的特例:刪 head 時要更新 head 指標本身,容易漏掉。 - 走訪時 free 當前節點卻還用它的 next:同樣是 UAF。要 free 一個節點前,先把它的 next 存到別的變數。

配置器: - 未對齊(呼應 P0-T04):配給使用者的區塊起始位址最好對齊(例如對齊到 8),否則使用者拿去放 struct 可能遇到對齊問題。 - 未處理碎片:只切不合併,記憶體會碎成一堆小塊,最後明明總空間夠卻配不出一塊夠大的。合併相鄰空閒塊可緩解。 - header 的記憶體也要算進去:每塊前面的 header 佔空間,計算時別忘了。

動手實作(這就是驗收任務本身)

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。全程用 gcc -g 編譯以便 valgrind 報行號。

任務一:動態陣列 實作 struct dyn_array 與 da_init / da_push / da_get / da_free。寫測試:從空陣列連續 da_push 1000 個值(例如 push i 進去),然後逐一 da_get(i) 驗證等於 i。用 valgrind --leak-check=full 跑,要 0 errors / 0 leaks。

任務二:鏈結串列 實作 struct node 與 list_push_front / list_remove(刪除指定值的節點)/ list_print / list_free。寫測試:做 100 次隨機的「插入一個隨機值」或「刪除一個隨機值」,中間穿插走訪檢查順序/內容正確。valgrind 0 errors / 0 leaks(這特別考驗你每個 remove 都正確 free)。

任務三:簡易配置器 用一塊大區塊(static char pool[POOL_SIZE] 或一次 malloc)實作 my_alloc / my_free,維護 free list(first-fit 即可)。寫測試:alloc 幾塊、free 其中一塊、再 alloc 同樣大小,驗證拿回的是剛剛 free 的那塊(證明重用)。衝 100 分:加入相鄰空閒塊合併,並寫測試展示碎片被合併。

整合驗收:三個專案各自的測試都通過,且三者都 valgrind 乾淨。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 動態陣列:從容量 0 連續 push 1000 元素皆可讀回正確值且過程自動擴容;valgrind 0 errors / 0 leaks。 2. ☐ 鏈結串列:100 次隨機增刪後走訪結果正確;valgrind 0 errors / 0 leaks。 3. ☐ 配置器:能 alloc/free 且能重用已釋放區塊;valgrind 乾淨。

評分量表(這是出關門檻,需達 80): - 60:兩個專案完成且大致正確。 - 80(出關門檻 🚪):三個專案都完成,且全部 valgrind 零錯誤、零洩漏。達此分數方可進入 Phase 1。 - 100:配置器能處理碎片合併(coalescing),並能清楚解釋設計取捨(first-fit vs best-fit、翻倍擴容的攤平成本、對齊的考量等)。
