P3-T15 · 整合驗收 + 第一個 patch — 寫一個含並行與除錯的完整 module

一句話:把整個 Phase 3 學的——module 骨架、slab 配置、spinlock/atomic、workqueue、正確的 GFP/context——綜合成一個真正完整的 module,並用 KASAN + lockdep 驗證到零報告;再走完一次真實的 kernel patch 流程。這是你日後在公司開發 production module 的縮影。

🚪 這是 Phase 3 出關門檻

這是 Phase 3 的關卡(gate),也是整個課程目前最重的整合驗收。本 task 達 80 分——能獨立寫出並除錯一個正確處理同步與 context 的 module——才算真正掌握了核心 kernel 開發能力,方可進入 Phase 4(裝置驅動)。

為什麼這道關這麼重要?因為 Phase 3 是「成為通用型 kernel developer」的核心。前面 14 課你分別學了架構、module、記憶體、同步、中斷、除錯——但「分開學會」和「綜合起來獨立做出一個正確的並行 module」是兩回事。真實的 kernel 開發(包括你的產品)要求你同時正確處理所有這些面向:配對的資源管理、正確的鎖選型、正確的 GFP/context、用工具驗證無 bug。這道關確保你具備這個綜合能力。

為什麼是「完整 module + 第一個 patch」(導讀)

這一課有兩個產出,都直接對應你的職涯:

產出一:一個完整的並行 module。 不是 hello-world,而是一個麻雀雖小五臟俱全的真實 module: - 一個 misc 裝置(一種簡單的字元裝置,讓使用者態能跟它互動——P4 會深入裝置,這裡先用最簡單的形式)。 - 內部用 workqueue 處理請求(回顧 P3-T10:可睡眠的下半部)。 - 用 spinlock / atomic 保護共享狀態(回顧 P3-T08/P3-T09)。 - 全程正確的 GFP/context 使用(回顧 P3-T07/P3-T08)。 - 用 KASAN + lockdep 驗證到零報告(回顧 P3-T14)。

這正是你公司 production module 的縮影——它綜合了並行、延後工作、記憶體配置、正確的 context 處理,並經過嚴格驗證。

產出二:走完一次真實的 kernel patch 流程。 對 kernel 樹做一個微小但真實的改進(例如修一個 checkpatch 警告、拼字、文件問題),用 git format-patch 產出合規的 patch、寫合規的 commit message(回收 P3-T05)。這讓你具備向 upstream 貢獻的流程能力——即使這裡只是練習產出(不必真寄),流程本身是你日後回饋社群、或在公司用 patch 協作的基礎。

第一個正確性面向:資源配對(回顧 P0-T06 malloc/free、P3-T03 init/exit 配對)。module 可反覆載入/卸載,每次都要乾淨。

關鍵紀律:exit 要反序、完整地釋放 init 配置的一切。尤其在有 workqueue 時有個微妙的順序問題:卸載時要先停止新請求進來、flush/cancel 所有 work(等它們做完)、才釋放 work 會用到的資源——否則「work 還在跑、它用的資源已被釋放」就是 use-after-free(KASAN 會抓到,回顧 P3-T14)。這個「正確的關閉順序」是真實 module 的常見難點,也是整合驗收的重點。

3. 並行設計:鎖與 context 的正確選擇

第二個正確性面向:並行(回顧 P3-T08/P3-T09)。這個 module 有共享狀態(請求佇列、計數),要正確保護。

flowchart TB
    SHARED["共享狀態:請求佇列、in-flight 計數等"]
    SHARED --> CHOICE{"怎麼保護?(回顧 P3-T08 選型)"}
    CHOICE --> SPIN["佇列的增刪 → spinlock
(短臨界區;若 work 在中斷類 context 也碰它,
考慮 spin_lock_irqsave)"]
    CHOICE --> ATOMIC2["計數 → atomic_t / refcount_t
(免鎖,refcount 管請求物件生命週期 P3-T09)"]
    SPIN --> RULE2["★ 鐵則(P3-T07/T08):持 spinlock 期間不可睡眠 ★
→ 持鎖時不可 kmalloc(GFP_KERNEL)、不可 mutex
→ 配置請求物件要在『進臨界區之前』做好"]
    style SPIN fill:#e8a33d,color:#10100e
    style ATOMIC2 fill:#6fa8b8,color:#10100e
    style RULE2 fill:#c2603a,color:#f4ecd8

並行設計的要點: - 佇列的增刪用 spinlock(短臨界區)。若處理也在中斷類 context 碰佇列,行程端用 spin_lock_irqsave(P3-T08)。 - 計數用 atomic_t;請求物件的生命週期用 refcount_t(P3-T09),確保「還有人用就不釋放」。 - 鐵則(回顧 P3-T07/P3-T08):持 spinlock 期間絕不可睡眠——所以「配置請求物件(kmalloc(GFP_KERNEL),會睡眠)」要在進臨界區之前做好,不能在持 spinlock 時配置。這是 GFP/context 正確性的具體體現,lockdep 會幫你抓違規(P3-T14)。

正確的鎖選型 + 正確的 GFP/context,是這個 module 通過 lockdep 零報告的關鍵。

4. workqueue:把重活延後到可睡眠 context

第三個面向:延後處理(回顧 P3-T10)。實際的請求處理(可能耗時、可能要睡眠)放 workqueue。

flowchart TB
    SUBMIT["進入點(行程 context):
配好請求、加入佇列後,schedule_work() 排入"]
    SUBMIT --> WORKER2["workqueue worker(行程 context,★可睡眠★):"]
    WORKER2 --> W1["① 用 spinlock 從佇列取出請求(短臨界區)"]
    W1 --> W2["② 釋放鎖後,做實際處理
(可睡眠的操作:msleep 模擬、或真實 I/O)"]
    W2 --> W3["③ 處理完,refcount_dec 釋放請求物件
(歸零才真的 kfree/kmem_cache_free)"]
    NOTE2["為什麼用 workqueue:
實際處理可能睡眠 → 不能在中斷/持鎖 context 做
→ workqueue 的行程 context 可睡眠(P3-T10)
(取佇列那一小步用鎖,處理那一大步不持鎖)"]
    W3 --> NOTE2
    style WORKER2 fill:#8a9a5b,color:#10100e
    style NOTE2 fill:#6fa8b8,color:#10100e

workqueue 的設計要點: - worker 在行程 context(可睡眠),所以實際處理可以做會睡眠的事(回顧 P3-T10)。 - 「取佇列」用鎖(短),「處理」不持鎖(長、可能睡眠)——別持著 spinlock 做耗時/睡眠的處理(那違反鐵則、且讓別人空轉)。先在臨界區裡快速取出請求、釋放鎖,再從容處理。 - 這正是你產品的模式:I/O 完成的重活(parity、GPU)在 workqueue 處理,而非中斷 context。

常見誤區與踩雷提醒

誤區一:context/GFP/鎖規則綜合踩雷。 回顧 P3-T07/P3-T08/P3-T10:持 spinlock 不可睡眠(配置要在臨界區前)、中斷 context 不可用 mutex、重活放可睡眠的 workqueue。綜合起來別錯。lockdep 會幫你抓。

誤區二:卸載時關閉順序錯誤 → use-after-free。 要先停新請求進來、flush/cancel work(等做完)、才釋放 work 用的資源。否則 work 還在跑、資源被釋放,KASAN 會報 UAF。

誤區三:patch 用附件而非 inline、或被郵件客戶端改壞格式。 真寄要用 git send-email(純文字 inline)。練習產出 git format-patch 檔即可。

誤區四:commit message 不合規。 主旨行 + 內文解釋「為什麼改」(回收 P3-T05),不是流水帳。

誤區五:未先讀 MAINTAINERS 找對收件者。 真要寄 patch 時須先找對 maintainer(讀 MAINTAINERS 檔)。此處僅練習產出,不必真寄。

動手實作(這就是出關驗收任務)

環境:QEMU 虛擬機(開 KASAN + lockdep 的 debug kernel)+ 一份 kernel git 樹。module 只在 VM 測試。

任務(出關門檻):完整 module + 第一個 patch

Part 1 — 寫一個完整的並行 module(驗收點 1、2) 寫一個 misc 裝置 module: - 註冊一個 misc 裝置,使用者態能對它送請求(用 write 或 ioctl)。 - 收到請求時(行程 context):配置一個請求物件(kmalloc/slab,GFP_KERNEL),用 spinlock 加入共享佇列、用 atomic/refcount 更新計數,然後 schedule_work() 把處理排入 workqueue。 - workqueue worker(行程 context):用鎖取出請求、釋放鎖後做處理(放個 msleep 模擬可睡眠工作)、refcount_dec 釋放請求。 - 正確的關閉順序(exit:先停請求 → flush work → 釋放資源 → 銷毀 slab)。 驗收: - module 通過功能測試(送多個請求都正確處理)。 - 正確使用至少一種鎖 + workqueue,且 GFP/context 選擇全部正確。

Part 2 — KASAN + lockdep 驗證(驗收點 1) 在開 CONFIG_KASAN + CONFIG_PROVE_LOCKING 的 kernel 上,跑你的 module(並行送請求、反覆載入/卸載)。 驗收:KASAN + lockdep 開啟下 0 報告。(有報告就修到乾淨。)

Part 3 — 第一個 patch(驗收點 3) 對 kernel 樹找一個微小真實的改進(用 checkpatch.pl 找一個 checkpatch/拼字/文件問題),改好、git commit(合規 commit message)、git format-patch 產出 patch、checkpatch.pl <patch> 驗證。 驗收:產出一個通過 checkpatch.pl 的 git format-patch 檔,含合規 commit message。(練習用,不必真寄。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ module 通過功能測試,且在 KASAN + lockdep 開啟下 0 報告。 2. ☐ 正確使用至少一種鎖 + workqueue,且 GFP/context 選擇全部正確。 3. ☐ 產出一個通過 checkpatch.pl 的 git format-patch 檔,含合規 commit message。

評分量表(出關門檻,需達 80): - 60:module 可運作。 - 80(出關門檻 🚪):module 通過 KASAN/lockdep 且 patch 合規。達此分數方可進入 Phase 4。 - 100:module 設計乾淨可維護,能解釋每個同步/context 決策,patch 達可送 upstream 水準。

延伸與銜接

  • 對應工作場景:直接對應——這是你日後在公司開發 production module 的縮影,也讓你具備向 upstream 貢獻的流程能力。
  • 這課收束了:整個 Phase 3——架構、module、記憶體、同步、中斷、排程、除錯——綜合成「獨立做出一個正確的並行 module」的能力。
  • 下一步 → P4-T01 進入 Phase 4(裝置驅動與 Device Model):恭喜你通過 Phase 3,成為能獨立開發、除錯並行 module 的 kernel developer!你在這裡寫的 misc 裝置,只是裝置的最簡單形式。Phase 4 深入「裝置驅動」:Linux 如何抽象裝置與匯流排(Device Model)、怎麼寫字元裝置和區塊裝置驅動、以及 PCI 子系統(你的 NVMe SSD、GPU 都掛在 PCI 上)。這是你產品「自寫 kernel module 操作硬體」的正式起點——從這裡開始,你的 module 要真正跟硬體裝置打交道了。

🚪 出關提醒:確認你能獨立寫出一個 misc 裝置 module(workqueue + spinlock/atomic + 正確 GFP/context),在 KASAN + lockdep 下零報告,並產出一個合規的 git format-patch(80 分門檻),再進入 Phase 4。這個「綜合所有 Phase 3 能力、做出正確的並行 module」的本事,是後面裝置驅動、block layer、DMA 工作的根基——你已經是真正的 kernel developer 了。
