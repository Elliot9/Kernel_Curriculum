P6-T01 · DMA 基礎與 DMA API(coherent vs streaming)

一句話:DMA 讓裝置自己搬資料、不佔用 CPU——但代價是你要面對第三種位址:dma_addr_t(裝置看到的位址),它不是實體位址、更不能被 CPU 解參考,中間可能有 IOMMU 轉譯。配置 DMA buffer 用 coherent(長期共享、免同步)或 streaming(單次傳輸、需指定方向)兩種映射。

為什麼要先學這個(導讀)

歡迎來到 Phase 6——你產品資料路徑的核心:DMA、IOMMU、以及 NVMe↔GPU 直通(P2PDMA)。Phase 5 你學了「資料怎麼在 host 和 NVMe 之間流動」(SQ/CQ、PRP/SGL);這個階段補上最後一塊:裝置實際怎麼 DMA 存取那些記憶體。

先理解 DMA(Direct Memory Access,直接記憶體存取) 是什麼:讓裝置自己直接讀寫主記憶體,不需要 CPU 一個位元組一個位元組地搬。回顧 P5-T05:NVMe 裝置 DMA 讀 SQ 的命令、DMA 寫資料到記憶體、DMA 寫完成項到 CQ——這些「裝置自己搬」就是 DMA。沒有 DMA,CPU 要親自搬每一筆 I/O 資料,完全跑不動高速儲存。

但 DMA 帶來一個你必須徹底理解的東西——第三種位址。這是你「位址的真相」主線的高潮(回顧 P0-T05 指標、P1-T04 虛擬 vs 實體、P3-T06 線性映射;現在加上裝置的視角)。系統裡有三種位址: - 虛擬位址(virtual):CPU 程式看到的位址(經 MMU 分頁轉譯,P1-T04)。 - 實體位址(physical):記憶體實際的位址(MMU 轉譯後的結果)。 - 匯流排/DMA 位址(bus/DMA address,dma_addr_t):裝置看到的位址——裝置做 DMA 時用的位址。中間可能有 IOMMU 轉譯(P6-T04),所以它不一定等於實體位址。

核心鐵則(貫穿整個 Phase 6):dma_addr_t 不是實體位址、也不是 CPU 可解參考的指標——它是給裝置用的,中間可能有 IOMMU 轉譯。把 dma_addr_t 當實體位址、或拿來 CPU 解參考,是 DMA 程式設計最危險的錯誤之一。

DMA API 提供兩種映射方式: - coherent(一致性)映射(dma_alloc_coherent):長生命週期、CPU 與裝置都能看到最新值、免手動同步。 - streaming(串流)映射(dma_map_single/dma_map_page):單次傳輸、需指定方向、效率好但要管同步(P6-T02)。

為什麼這對你是 scope: direct?因為你產品的 NVMe DMA buffer、餵給 GPU 的資料區,都靠 DMA API 配置/映射——搞錯位址語意(把 dma_addr_t 當實體位址)會造成資料毀損或安全問題。這一課是整個 Phase 6、以及你產品資料路徑的地基。

三種位址: - 虛擬位址(virtual):CPU 程式看到的位址(經 MMU 分頁轉譯,P1-T04)。你 kmalloc 拿到的指標就是虛擬位址。 - 實體位址(physical):記憶體實際的位址(MMU 轉譯虛擬位址後的結果,P1-T04/P3-T06)。 - 匯流排/DMA 位址(dma_addr_t):裝置看到的位址——裝置做 DMA 時用的。中間可能有 IOMMU 轉譯(P6-T04),所以不一定等於實體位址。

關鍵理解:這三者是「同一塊記憶體」的三種視角——CPU 透過虛擬位址看它、記憶體實際在實體位址、裝置透過 DMA 位址看它,各自經過各自的轉譯(MMU 給 CPU、IOMMU 給裝置)。這就是你「位址的真相」主線的終點:位址不是絕對的數字,是「誰在看、經過什麼轉譯」的結果。

DMA API 的工作就是:給你一塊記憶體,同時給你「CPU 用的虛擬位址」和「裝置用的 dma_addr_t」——你把 dma_addr_t 告訴裝置(寫進命令/描述子),裝置用它做 DMA;你用虛擬位址讓 CPU 存取同一塊記憶體。

這是整個 Phase 6 最重要的鐵則,務必刻進骨子裡。

鐵則:dma_addr_t 不能被 CPU 解參考,也不是實體位址。 為什麼(常見誤區:把 dma_addr_t 當實體位址或拿來 CPU 解參考): - 它是「裝置的視角」:可能經 IOMMU 轉譯(P6-T04)——在 CPU 的位址空間裡,這個數字根本不指向那塊記憶體。CPU 解參考它 = 存取錯誤位址 → 當機或讀到垃圾。 - 即使沒 IOMMU(dma_addr 剛好等於實體位址),CPU 也要用虛擬位址存取記憶體,不是實體位址(回顧 P1-T04:CPU 一律透過虛擬位址)。

正確用法: - dma_addr_t → 給裝置用(寫進命令、描述子、NVMe 的 PRP/SGL,P5-T05)。 - CPU 存取同一塊記憶體 → 用 DMA API 同時給你的「虛擬位址」。

DMA API 給你一對:dma_alloc_coherent 回傳一個虛擬位址(給 CPU)和一個 dma_addr_t(給裝置,透過參數回傳)。你絕不混用它們——虛擬位址給 CPU、dma_addr_t 給裝置。

(驗收點:回答「dma_addr_t 能不能用 CPU 解參考」=否,並說明原因。)這個鐵則對你產品至關重要——你把 NVMe 資料 buffer 的 dma_addr_t 寫進 NVMe 命令(PRP/SGL),那是給裝置用的;你絕不能拿那個 dma_addr_t 在 kernel 裡當指標解參考。

4. coherent 映射:長期共享、免同步

DMA API 的第一種映射:coherent(一致性,又稱 consistent)映射。特性:CPU 和裝置都能看到最新值,不需要手動同步——適合長生命週期、雙方頻繁存取的記憶體。

coherent 映射(dma_alloc_coherent): - 一次配置 + 映射:回傳 CPU 用的虛擬位址(函式回傳值)和 裝置用的 dma_addr_t(透過 dma_handle 參數回傳)——正是第 3 節說的那一對。 - 特性:CPU 和裝置看到的始終一致——底層保證 cache 一致性(CPU 寫了裝置馬上看得到,反之亦然),不需要手動同步(對比 streaming,第 5 節)。 - 適合:長生命週期、CPU 與裝置都頻繁存取的結構。例:NVMe 的 SQ/CQ 佇列本身(回顧 P5-T05)——host 和裝置都要持續讀寫,用 coherent 最省心。 - 釋放:dma_free_coherent。

coherent 的代價:它可能用較慢的記憶體(為了保證一致性,某些架構用非快取記憶體),所以不適合「一次性、大量」的傳輸(那用 streaming)。它適合「需要長期、雙向、頻繁存取且要省心」的場景。

(驗收點:用 dma_alloc_coherent 配置 buffer,印出 CPU 虛擬位址與 dma_addr_t 並解釋兩者為何不同。)

5. streaming 映射與方向

第二種映射:streaming(串流)映射——把已存在的記憶體(如一塊 kmalloc 的 buffer)做單次 DMA 傳輸的映射。效率好,但要管同步、要指定方向。

streaming 映射(dma_map_single/dma_map_page): - 把已存在的記憶體映射成裝置可 DMA 的位址(回傳 dma_addr_t)。 - 必須指定方向(direction):DMA_TO_DEVICE(CPU→裝置)、DMA_FROM_DEVICE(裝置→CPU)、DMA_BIDIRECTIONAL(雙向)。方向讓底層知道怎麼處理 cache。 - 裝置用回傳的 dma_addr_t 做這一次 DMA。 - 傳輸完成後必須 dma_unmap_single(否則映射洩漏)。

重點:映射期間,記憶體「歸裝置」——CPU 不該隨意存取(要存取需 dma_sync_*,P6-T02);unmap 後才完全還給 CPU。

兩個常見誤區: - 用 vmalloc/stack 記憶體做 streaming DMA——vmalloc 實體不連續、stack 記憶體不適合 DMA(回顧 P3-T07:DMA 要實體連續)。要用 kmalloc 的記憶體或 page。 - coherent 與 streaming 誤用:短單次傳輸卻用 coherent(浪費)、或長期共享卻用 streaming(要一直 map/unmap/sync,麻煩且易錯)。

怎麼選(驗收點:說明 coherent 與 streaming 的適用場景差異): - coherent:長生命週期、雙方頻繁存取、要省心(如 SQ/CQ 佇列本身)。 - streaming:單次/短期傳輸、效率優先(如一次 I/O 的資料 buffer)。

你產品的資料路徑:NVMe 的 SQ/CQ 佇列用 coherent(長期、雙向),每次 I/O 的資料 buffer 用 streaming(單次傳輸,且來自 bio_vec 的分散片段,P6-T02 scatter-gather)。

6. dma_set_mask:裝置可定址範圍

最後一塊:裝置能定址多大的位址空間?用 dma_set_mask_and_coherent 告訴 kernel。

dma_set_mask_and_coherent(dev, DMA_BIT_MASK(n)) 告訴 kernel「這個裝置能定址 n-bit 的位址空間」。為什麼重要: - 有些裝置只能定址有限範圍(舊裝置可能只 32-bit = 4GB)。 - kernel 據此決定:能不能直接 DMA、或要不要用 bounce buffer(裝置定址不到的高位址 buffer，先 DMA 到裝置能到的低位址、再複製——慢但能 work)。

常見誤區:忘了設 dma_set_mask_and_coherent——裝置定址範圍會用保守的預設(可能 32-bit），導致高位址 buffer 觸發 bounce(慢)或失敗。現代裝置(如你的 NVMe）通常能 64-bit，probe 裡要設好 dma_set_mask_and_coherent(dev, DMA_BIT_MASK(64))，讓它能直接 DMA 到任何位址、避免 bounce。

這對你產品效能相關:正確設定 mask，NVMe 才能直接 DMA 到高位址記憶體,不繞 bounce buffer(那會多一次複製、拖慢)。

打通關:把 DMA 基礎與 DMA API 收攏成一個心智模型

一句話總結:DMA 讓裝置自己搬資料(不佔 CPU），代價是要面對第三種位址 dma_addr_t（裝置的視角，可能經 IOMMU 轉譯）——鐵則是它不是實體位址、不能 CPU 解參考（給裝置用，CPU 用 DMA API 給的虛擬位址存取同塊記憶體）；配置 DMA buffer 用 coherent（長期雙向免同步，如 SQ/CQ）或 streaming（單次傳輸、指定方向、要 unmap，不能用 vmalloc/stack），並用 dma_set_mask 設定裝置可定址範圍避免 bounce。

常見誤區與踩雷提醒

誤區一(最危險,貫穿全階段):把 dma_addr_t 當實體位址或拿來 CPU 解參考。 它是裝置的視角,可能經 IOMMU 轉譯,在 CPU 位址空間裡不指向那塊記憶體。給裝置用;CPU 存取同塊記憶體要用 DMA API 給的虛擬位址。

誤區二:用 vmalloc/stack 記憶體做 streaming DMA。 vmalloc 實體不連續、stack 不適合 DMA(回顧 P3-T07 DMA 要實體連續)。用 kmalloc 記憶體或 page。

誤區三:忘了設 dma_set_mask_and_coherent。 裝置定址範圍用保守預設(可能 32-bit),高位址 buffer 觸發 bounce(慢)或失敗。現代裝置 probe 裡設 64-bit mask。

誤區四:coherent 與 streaming 誤用。 短單次傳輸用 coherent(浪費)、或長期共享用 streaming(一直 map/unmap/sync,麻煩易錯)。長期雙向用 coherent;單次傳輸用 streaming。

動手實作

環境:QEMU 虛擬機(PCI driver + DMA 實驗只在 VM)。 參考 DMA API HOWTO(https://docs.kernel.org/core-api/dma-api-howto.html ）。

任務 A — dma_alloc_coherent 並比較位址(驗收點) 在(QEMU 中的)PCI driver 上,用 dma_alloc_coherent 配置一塊 coherent DMA buffer。pr_info 印出 CPU 虛擬位址(回傳值)和 dma_addr_t(dma_handle),比較兩者。驗收:成功配置 buffer,印出 CPU 虛擬位址與 dma_addr_t 並能解釋兩者為何不同。(提示:虛擬給 CPU、dma_addr 給裝置;有/沒 IOMMU 影響它們的關係。)

任務 B — streaming 映射(驗收點) 用 kmalloc 配一塊 buffer,dma_map_single(dev, vaddr, size, DMA_TO_DEVICE) 做一次 streaming 映射,(概念上)讓裝置用回傳的 dma_addr,然後 dma_unmap_single(... DMA_TO_DEVICE)。驗收:正確完成一次 dma_map_single+dma_unmap_single(指定正確方向)。

任務 C — dma_addr_t 能不能解參考(驗收點,核心) 寫一段文字回答:dma_addr_t 能不能用 CPU 解參考?為什麼? 驗收:答「否」並說明原因(裝置視角、可能經 IOMMU 轉譯、不是 CPU 位址空間的有效指標)。

任務 D — coherent vs streaming(驗收點) 寫一段話:coherent 和 streaming 映射各適合什麼場景?驗收:說明 coherent(長期雙向免同步,如 SQ/CQ)與 streaming(單次傳輸,如每次 I/O buffer)的適用差異。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 dma_alloc_coherent 成功配置 buffer,印出 CPU 虛擬位址與 dma_addr_t 並能解釋兩者為何不同。 2. ☐ 正確完成一次 dma_map_single+dma_unmap_single(指定正確方向)。 3. ☐ 回答「dma_addr_t 能不能用 CPU 解參考」(否)及原因。 4. ☐ 說明 coherent 與 streaming 的適用場景差異。

評分量表: - 60(及格):能配置 coherent buffer。 - 80(熟練):能正確使用 coherent 與 streaming 並設 mask。 - 100(精通):能完整解釋三種位址與 IOMMU 轉譯對 dma_addr_t 的影響。

延伸與銜接

  • 對應工作場景:直接對應——你產品的 NVMe DMA buffer、餵給 GPU 的資料區都靠 DMA API 配置/映射;搞錯位址語意會造成資料毀損或安全問題。
  • 這課餵給未來的(位址的真相主線高潮):P0-T05 指標 → P1-T04 虛擬/實體 → P3-T06 線性映射 → 本課三種位址 + dma_addr_t → P6-T04 IOMMU(dma_addr_t 的轉譯者)。coherent/streaming → P6-T02 scatter-gather DMA;DMA 方向/同步 → P6-T02。
  • 下一步 → P6-T02 scatter-gather 與 DMA 同步:你會用 coherent/streaming 映射單一 buffer 了。但你產品的資料常分散在多個片段(回顧 P5-T02 bio_vec)——下一課學 scatter-gather DMA:用 dma_map_sg 對一串分散的記憶體片段做一次 DMA(struct scatterlist/sg_table),以及 streaming 映射在 CPU 和裝置交替存取時的 dma_sync_*(cache 一致性)。這直接對應你的日常:NVMe 的 PRP/SGL 與 bio_vec 的分散片段,正是經 scatter-gather 映射做 DMA。還會看到 IOMMU 如何把分散片段「合併」成連續的 DMA 視圖——一個關鍵的陷阱(映射後的數量可能變少)。
