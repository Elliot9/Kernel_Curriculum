P0-T09 · C 型別系統、整數提升與帶號陷阱

一句話:C 在你背後偷偷做整數型別轉換,而其中「帶號與無號混用」的規則反直覺到會讓 -1 > 0 成立。在你的儲存工作裡,sector、offset、length 全是整數,搞錯這個就是真實的資料災難。

為什麼要先學這個(導讀)

在 JS 裡只有一種數字型別(number),你從不煩惱「這是 32 位元還是 64 位元、帶號還是無號」。PHP 也幫你藏起大部分整數細節。

C 不一樣。C 有一整族整數型別(char、short、int、long、各種 unsigned 版本……),每種有不同的大小和範圍。更麻煩的是:當你把不同型別混在一個運算式裡,C 會依一套隱晦的規則,自動把它們轉成同一型別再運算——而這個自動轉換,常常產生你完全沒預期的結果。

最惡名昭彰的就是帶號(signed)vs 無號(unsigned)的混用。它能讓這種荒謬的事成立:

if (-1 > 0U)   // 這個條件竟然為「真」!

為什麼這課對你是 scope: direct(直接對應工作)?因為儲存系統的核心全是整數:磁碟的 sector 編號、I/O 的 offset、資料的 length、緩衝區大小……這些幾乎都用無號型別(像 size_t、sector_t)表示。一旦你不小心把一個帶號的值(例如某個回傳 -1 表示錯誤的函式結果)和這些無號值混在一起比較或運算,就可能觸發這套詭異規則,算出一個天文數字般的錯誤 offset、或讓一個「應該為負就停」的迴圈永遠跑不完。這不是理論——這是 kernel 與儲存程式碼裡真實、反覆出現的 bug 類別。這課讓你看穿它。

1. C 的整數家族

C 有一族整數型別,差別在「佔幾個 byte」(決定能表示的範圍)與「帶不帶號」(能不能表示負數)。常見的(在典型 64 位元 Linux/x86-64 上):

型別 大小 帶號範圍 無號範圍(unsigned 版)
char 1 byte -128 ~ 127 0 ~ 255
short 2 bytes -32768 ~ 32767 0 ~ 65535
int 4 bytes 約 ±21 億 0 ~ 約 42.9 億
long 8 bytes 約 ±9.2×10¹⁸ 0 ~ 約 1.8×10¹⁹

重要警告:這些大小不是 C 標準保證的,會因平台而異(例如 long 在 Windows 64 位元是 4 bytes,在 Linux 64 位元是 8 bytes)。標準只保證「最小範圍」和「大小排序」(char ≤ short ≤ int ≤ long)。這個「大小不固定」本身就是坑——第 8 節會給你解法(stdint.h)。

2. 帶號 vs 無號:同一份 bits,兩種解讀

一塊記憶體裡就是一串 bits。「帶號」或「無號」決定了怎麼解讀這串 bits——尤其是最高位(most significant bit)。

以 8 bits 為例,假設這串 bits 是 11111111: - 當成無號(unsigned char):它是 255。 - 當成帶號(signed char,用二補數表示法):它是 -1。

flowchart TB
    BITS["同一串 bits:11111111"]
    BITS -->|"當 unsigned 解讀"| U["255
(所有 bit 都算正貢獻)"]
    BITS -->|"當 signed 解讀(二補數)"| S["-1
(最高位代表負號權重)"]
    style U fill:#6fa8b8,color:#10100e
    style S fill:#c2603a,color:#f4ecd8

這和 P0-T02 的指標型別概念完全一致:bits 本身沒有意義,型別決定怎麼解讀它。記住「同一份 bits、不同解讀」這個畫面——它是後面所有陷阱的根。

二補數(two's complement)是什麼? 它是電腦表示帶號整數的標準方法。你現在不需要完全掌握它的運算,只要記住結論:在帶號型別裡,最高位是 1 時代表這是個負數;而同樣的 bits 用無號解讀則是個大正數。這個「最高位的雙重身分」是 -1 和「最大正數」共用同一串 bits 的原因。

3. 整數提升(integer promotion):小型別先升成 int

C 有一條規則:比 int 小的整數型別(char、short),在參與運算前,會先被自動「提升」成 int。

char a = 100, b = 100;
int r = a + b;   // a、b 各自先提升成 int,再相加 → 200(沒有溢位)

如果沒有這個提升,100 + 100 = 200 會超出 char 的範圍(-128~127)而溢位。但因為兩者先升成 int 才相加,結果 200 安然無恙。

這條規則大多時候幫你避免小型別溢位,是「善意」的。但它也意味著:你的小整數運算,實際上幾乎都在 int 的世界裡進行。記住這點,因為它和下一條規則疊加時會更複雜。

4. 一般算術轉換:混用時,誰轉成誰?

當運算式裡有兩種不同型別(且至少有一個 ≥ int),C 用一套叫「一般算術轉換(usual arithmetic conversions)」的規則,把它們轉成同一型別再算。簡化的優先順序:

(int + long → 都變 long)"]
    Q1 --> R2["大小相同、一帶號一無號?
→ ★帶號的轉成無號的★
(int + unsigned int → 都變 unsigned)"]
    R2 --> DANGER["這條是萬惡之源:

    style R2 fill:#c2603a,color:#f4ecd8
    style DANGER fill:#c2603a,color:#f4ecd8

最關鍵、最坑的是 R2:當帶號和無號大小相同時,帶號的那個會被轉成無號。這聽起來無害,但結合第 2 節的「同 bits 不同解讀」,就會炸出下一節的招牌陷阱——一個負數被轉成無號,會變成一個巨大的正數。

5. 招牌陷阱:-1 > 0U 為什麼成立

現在把前面的零件組起來,解剖這個經典:

if (-1 > 0U) {   // 直覺:-1 怎麼可能大於 0?但這條件為「真」!
    printf("這行竟然會印出來\n");
}

逐步拆解:

核心:-1 被轉成無號後,變成那個型別的最大值(因為 -1 的 bits 是全 1,無號解讀就是最大)。於是「-1 > 0」實際上是「最大值 > 0」,當然為真。

這就是為什麼,把帶號值和無號值混在一起比較,是 C 最危險的陷阱之一。在你的儲存工作裡,假如有個函式回傳 int(用 -1 表示錯誤),你卻拿它去和一個 size_t(無號)的長度比較,-1 會變成天文數字,你的「錯誤檢查」就會得到完全相反的結果。

6. 致命實例:size_t 倒數迴圈變成無窮迴圈

這個坑在真實程式碼裡反覆害人,而且和你的領域高度相關(size_t 是表示大小/長度的標準無號型別)。看這個「想從尾巴往前數到 0」的迴圈:

size_t i;
for (i = n - 1; i >= 0; i--) {   // 想從 n-1 倒數到 0
    // ... 處理 arr[i] ...
}

它永遠不會結束。為什麼?因為 i 是 size_t(無號),而無號數永遠 >= 0——它不可能變成負數。當 i 是 0、再 i--,它不會變成 -1,而是「繞回」成那個無號型別的最大值(一個天文數字),於是 i >= 0 永遠成立,迴圈無窮跑下去(並且 arr[巨大數] 還會越界亂存取)。

flowchart TB
    S1["i 是 size_t(無號),目前 i = 0"]
    S2["迴圈尾 i--
無號數 0 減 1 不會變 -1"]
    S3["而是『繞回』成最大值
(例如 18446744073709551615)"]
    S4["檢查 i >= 0:
無號數永遠 >= 0 → 真"]
    S5["迴圈繼續 → 無窮迴圈
+ arr[巨大數] 越界存取"]
    S1 --> S2 --> S3 --> S4 --> S5

    style S3 fill:#c2603a,color:#f4ecd8
    style S5 fill:#c2603a,color:#f4ecd8

正解有幾種,理解原理後任選:

// 解法 A:迴圈變數用帶號型別(若 n 不會大到超過帶號範圍)
for (ssize_t i = n - 1; i >= 0; i--) { ... }

// 解法 B:改變條件,不依賴「無號變負」
for (size_t i = n; i > 0; i--) {
    size_t idx = i - 1;   // 用 i-1 當真正的索引
    // ... 處理 arr[idx] ...
}

解法 B 很常見:讓 i 從 n 跑到 1(條件 i > 0,對無號安全),迴圈內用 i - 1 當索引。

7. 溢位:帶號是「未定義行為」,無號是「繞回」

當運算結果超出型別能表示的範圍,帶號和無號的下場截然不同——這個區別在 P0-T10(未定義行為)會更深入,這裡先建立認識:

flowchart TB
    OF["整數運算結果超出範圍(溢位)"]
    OF --> U["無號溢位:
定義良好,『繞回』(wrap around)
最大值 +1 → 0
(像時鐘 12 點 +1 回到 1)"]
    OF --> S["帶號溢位:
★未定義行為(UB)★
編譯器可假設它『不會發生』
→ 可能產生你完全無法預測的結果"]
    style U fill:#6fa8b8,color:#10100e
    style S fill:#c2603a,color:#f4ecd8

  • 無號溢位:C 標準明確定義為「對 2ⁿ 取模」,也就是繞回。UINT_MAX + 1 保證等於 0。這是可靠、可預期的。
  • 帶號溢位:是未定義行為(undefined behavior, UB)。這意味著 C 標準不規定會發生什麼——程式可能算出怪值、可能崩潰,而且編譯器在最佳化時會假設「帶號溢位永不發生」,基於這個假設做的優化可能讓你的程式行為變得極難理解。這是 P0-T10 的核心主題,現在先記住:帶號溢位是 UB,要極力避免;無號溢位雖有定義,但「繞回」常常也不是你要的(見第 6 節的迴圈)。

8. 解法:用 stdint.h 寫死位元寬度

第 1 節說過,int/long 的大小因平台而異——這對「需要精確控制位元數」的場合(硬體暫存器、磁碟格式、網路協定,全是你的領域)是不可接受的。

<stdint.h> 提供寬度明確的型別,在任何平台都是固定大小:

型別 保證大小 用途
int8_t / uint8_t 正好 1 byte 精確的位元組
int16_t / uint16_t 正好 2 bytes
int32_t / uint32_t 正好 4 bytes
int64_t / uint64_t 正好 8 bytes sector 編號、大 offset

規矩:凡是「大小必須精確」的場合(對應硬體、磁碟、協定,或任何你在意確切位元數的地方),一律用 stdint.h 的固定寬度型別,不要用裸的 int/long。 你日後讀 kernel 程式碼,會看到大量 u8/u16/u32/u64(kernel 自己的等價物)——道理一樣,就是為了「大小確定」。

一句話總結:C 的整數運算不是你以為的「就照數學算」——它在背後依型別自動轉換,而帶號/無號混用會讓負數變成天文數字。在你那個 sector / offset / length 滿天飛的儲存世界,養成「比較與運算前先確認兩邊型別一致、精確寬度用 stdint.h」的紀律,能擋掉一整類最難纏的 bug。

常見誤區與踩雷提醒

誤區一:把帶號和無號值直接比較。 if (signed_val > unsigned_val)——帶號值會被轉成無號,若它是負數就變成巨大正數,比較結果與你預期相反。比較前確保兩邊型別一致(必要時明確轉型並檢查範圍)。

誤區二:用無號型別寫倒數到 0 的迴圈。 for (size_t i = n-1; i >= 0; i--) 是無窮迴圈(無號永遠 >= 0)。用帶號型別,或改寫條件為 i > 0 並以 i-1 當索引。

誤區三:以為帶號溢位會「繞回」。 無號溢位才有定義會繞回;帶號溢位是未定義行為,別依賴它的任何「結果」。(P0-T10 詳述。)

誤區四:在需要精確大小時用裸 int/long。 它們的大小因平台而異。對應硬體/磁碟/協定時,用 stdint.h 的 uint32_t/uint64_t 等。

誤區五:忘記 char 的帶號性也是平台相關的。 「裸 char」是帶號還是無號,其實因平台/編譯器而異。要明確時,寫 signed char 或 unsigned char。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 親眼看 -1 > 0U

#include <stdio.h>
int main(void) {
    if (-1 > 0U)
        printf("驚:-1 > 0U 成立!\n");
    printf("-1 當無號看 = %u\n", (unsigned)-1);   // 印出最大值
    return 0;
}

觀察條件成立、且 (unsigned)-1 是個天文數字。寫一句話:用第 5 節的轉換規則解釋為什麼。

任務 B — 重現並修好無窮迴圈(在 VM 裡,可隨時 Ctrl-C) 先寫錯的版本,親眼確認它停不下來(印出的 i 變成天文數字後立刻 Ctrl-C):

size_t n = 5;
for (size_t i = n - 1; i >= 0; i--)
    printf("%zu\n", i);   // 倒數到 0 後繞回成巨大數,無窮跑

再用第 6 節的解法 B 改對,確認它正確從 4 印到 0 後停止。寫一句話說明你改了什麼、為什麼有效。

任務 C — 觀察無號繞回 vs 整數提升

#include <stdio.h>
#include <stdint.h>
int main(void) {
    uint8_t u = 255;
    u = u + 1;                 // 無號繞回:255 + 1 → 0
    printf("255 + 1 (uint8) = %u\n", u);

    unsigned char a = 200, b = 200;
    int r = a + b;             // 整數提升:各自升 int 再加 → 400(不繞回)
    printf("200 + 200 (提升後) = %d\n", r);
    return 0;
}

解釋兩個結果為何不同:前者在 uint8_t 裡繞回,後者因整數提升在 int 裡運算所以是 400。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 寫程式展示 -1 > 0U 為真,並用轉換規則正確解釋(帶號轉無號變最大值)。 2. ☐ 重現 size_t 倒數無窮迴圈,並改寫成正確版本,能說明修正原理。 3. ☐ 用 uint8_t 展示無號繞回(255+1=0),並用 unsigned char 相加展示整數提升(200+200=400 而非繞回),能解釋兩者差異。

評分量表: - 60(及格):知道帶號/無號的存在與基本差異。 - 80(熟練):能預測並避開帶號/無號混用的陷阱,正確使用 stdint.h。 - 100(精通):能完整推導一般算術轉換如何作用於一個混合運算式,並連結到儲存領域(sector/offset/length)的真實 bug。

  • 對應工作場景:直接對應。sector 編號、offset、length 全是整數,且多用無號型別(sector_t、size_t);帶號/無號混用的 bug 在區塊層、DMA 長度計算中真實存在且難抓。stdint.h/kernel 的 u32/u64 是你日後天天用的。
  • 這課餵給未來的:帶號溢位是 UB → P0-T10 未定義行為的核心案例;固定寬度型別 → 之後讀 NVMe 結構(P0-T04 對齊 + 這課的寬度,合起來才能精準描述硬體欄位)。
  • 下一步 → P0-T10 未定義行為(UB)與編譯器最佳化:這課尾巴提到「帶號溢位是 UB,編譯器會假設它不發生」。下一課正面拆解這個讓無數人栽跟頭的概念——為什麼「UB」不只是「結果不確定」,而是會讓編譯器刪掉你的程式碼(例如刪掉你的 NULL 檢查)。這是 C 與 kernel 最危險、也最迷人的角落。
