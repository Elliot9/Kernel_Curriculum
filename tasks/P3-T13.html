P3-T13 · kernel 除錯(一)—— printk/動態除錯、Oops/panic 判讀、ftrace

一句話:當你的 module 解參考了 NULL,kernel 不會 segfault——它印出一份 Oops(call trace + 暫存器 dump)。學會讀那串 dump、用 addr2line 把位址對回程式碼行,你就能定位崩潰;再加上 printk 動態除錯和 ftrace 追蹤函式,這是你 debug 自家 module 的日常工具。

為什麼要先學這個(導讀)

你已經會寫 module、懂記憶體/同步/中斷了。但寫程式必然會出 bug,而在 kernel 裡 debug 跟在使用者態完全不同(回顧 P3-T03:無 libc、在核心空間、錯誤即影響全系統)。這一課和下一課(P3-T14)就是 kernel 除錯——你日後 debug 自家 module 的日常工具。

這一課的幾個工具: - printk / 動態除錯:最基本的「印訊息看狀態」(回顧 P3-T03 的 printk),加上動態除錯(dynamic debug)——讓你能在執行時開關 pr_debug 訊息,不必重編。 - Oops / panic 判讀:當 module 出錯(例如解參考 NULL),kernel 會印出一份診斷——Oops(較輕,當前 task 出錯但系統可能還活著)或 panic(致命,系統停止)。學會讀它的 call trace(呼叫堆疊)和暫存器 dump,用 addr2line/decode_stacktrace 把位址對回你的程式碼行——這是定位崩潰的核心技能。 - ftrace:kernel 內建的函式追蹤器,能記錄「哪些函式被呼叫、呼叫順序、各花多久」——用來理解執行路徑、找效能問題。

為什麼這對你是 scope: direct?因為這是你日後 debug 自家 module 當機/效能問題的日常工具。你的 module 在核心空間,一個 bug 就是一份 Oops——判讀 call trace 是 kernel 開發的基本功。你會在 QEMU 裡故意觸發一個 NULL 解參考、看 Oops、把它定位到出錯行。這一課也用到你 P1-T11 建好的環境和 P3-T02 的 CONFIG_DEBUG_INFO(addr2line 需要符號)。

開始之前(前置確認)

  • 依賴:P3-T03(printk、module、dmesg)、P1-T11(QEMU + gdb 環境)。也用到 P3-T02(CONFIG_DEBUG_INFO)、P1-T01(暫存器、stack)。
  • 自我檢測: 1. 你還記得 P1-T01 的暫存器、stack、call stack 嗎?Oops 的 dump 就是這些東西在崩潰當下的快照。 2. 你還記得 P3-T02 的 CONFIG_DEBUG_INFO(編入除錯符號)嗎?addr2line 把崩潰位址對回程式碼行,需要它。
  • 環境:QEMU 虛擬機(觸發 Oops、ftrace 都在 VM)。

核心內容

拆成這幾節:(1) printk log level → (2) 動態除錯 → (3) Oops vs panic → (4) 讀 call trace → (5) addr2line:位址對回程式碼行 → (6) ftrace,最後打通關。

1. printk log level:控制訊息可見性

回顧 P3-T03:printk/pr_info 把訊息送到核心 log buffer,用 dmesg 看。這一課補充 log level(訊息等級) 的控制——因為「看不到 debug 訊息」常常只是等級設定問題。

flowchart TB
    LEVELS["printk 等級(由急到不急):
pr_emerg / pr_alert / pr_crit / pr_err /
pr_warn / pr_notice / pr_info / pr_debug"]
    LEVELS --> FILTER["核心有個『console log level 門檻』
(/proc/sys/kernel/printk)
→ 只有等級『比門檻更急』的訊息
才會即時顯示在 console"]
    FILTER --> ISSUE["★ 常見問題:pr_debug / pr_info 看不到 ★
因為等級低於門檻被過濾
→ 調整 /proc/sys/kernel/printk 門檻,
或用 dmesg 看(buffer 裡都有)"]
    style LEVELS fill:#6fa8b8,color:#10100e
    style ISSUE fill:#e8a33d,color:#10100e

要點: - printk 訊息有等級(pr_emerg 最急 ... pr_debug 最不急)。 - 核心有個 console log level 門檻(/proc/sys/kernel/printk)——只有比門檻更急的訊息才即時顯示在 console。 - 常見誤區:printk 等級設定不當看不到訊息——pr_debug/pr_info 可能因低於門檻被過濾。解法:調整門檻,或用 dmesg(log buffer 裡都有,不受 console 門檻影響)。

(dmesg 看的是整個 log buffer,所以即使 console 沒即時顯示,dmesg 通常還是看得到——這是為什麼 debug 時主要靠 dmesg。)

2. 動態除錯:執行時開關 debug 訊息

pr_debug 預設常常不輸出(避免大量 debug 訊息淹沒)。動態除錯(dynamic debug) 讓你能在執行時精細地開關特定的 pr_debug,不必重編 module:

flowchart TB
    PRDEBUG["pr_debug(...) / dev_dbg(...)
(預設可能不輸出)"]
    PRDEBUG --> DYNDBG["動態除錯(CONFIG_DYNAMIC_DEBUG):
透過 /sys/kernel/debug/dynamic_debug/control
在執行時開關特定的 pr_debug"]
    DYNDBG --> GRANULAR["可精細控制:
按檔案、按行號、按函式、按模組
開啟/關閉某些 pr_debug
→ 只開你正在 debug 的部分,不淹沒"]
    style PRDEBUG fill:#6fa8b8,color:#10100e
    style DYNDBG fill:#8a9a5b,color:#10100e
    style GRANULAR fill:#e8a33d,color:#10100e

動態除錯(需 CONFIG_DYNAMIC_DEBUG)的價值:執行時、精細地開關 pr_debug——可以按檔案、行號、函式、模組來開。這樣你能「只開正在 debug 的那部分」的 debug 訊息,而不是要嘛全關、要嘛被海量訊息淹沒。透過 /sys/kernel/debug/dynamic_debug/control 控制。

這比「在 code 裡加一堆 printk、重編、載入」高效得多——你的 module 裡用 pr_debug 寫好診斷訊息,平時不輸出(零成本),要 debug 時動態開啟對應的。

3. Oops vs panic:兩種崩潰

當 kernel 程式碼出錯(例如你的 module 解參考 NULL、存取非法位址),kernel 會產生診斷。分兩種嚴重程度:

flowchart TB
    ERROR["kernel/module 出錯(如 NULL 解參考、非法存取)"]
    ERROR --> OOPS["Oops(較輕):
當前 task/context 出錯,
kernel 印出診斷(call trace + 暫存器)、
殺掉出錯的 task,但★系統可能還繼續運行★"]
    ERROR --> PANIC["panic(致命):
錯誤嚴重到系統無法繼續
(或在關鍵 context 出錯)
→ kernel 印出訊息後★停止整個系統★"]
    OOPS --> CAUTION["★ 重要:Oops 後系統未必正常 ★
出錯的 task 可能持著鎖沒釋放、
留下不一致狀態 → 系統可能不穩定
→ 出 Oops 後應重啟(別當沒事繼續用)"]
    style OOPS fill:#e8a33d,color:#10100e
    style PANIC fill:#c2603a,color:#f4ecd8
    style CAUTION fill:#c2603a,color:#f4ecd8

  • Oops:較輕。當前 task/context 出錯,kernel 印出診斷(call trace + 暫存器 dump)、殺掉出錯的 task,系統可能還繼續運行。
  • panic:致命。錯誤嚴重到系統無法繼續(或在關鍵 context、中斷裡出錯),kernel 印出訊息後停止整個系統。

重要(常見誤區:以為 Oops 後系統一定正常):Oops 後系統未必正常——出錯的 task 可能持著鎖沒釋放(P3-T08)、留下不一致的狀態,系統可能不穩定。出 Oops 後應該重啟(在 QEMU 裡就是重啟 VM),別當沒事繼續用。這也是為什麼你只在 VM 測試——Oops/panic 在 VM 裡只是重啟,在主機上可能搞垮系統。

無論 Oops 或 panic,核心都會印出一份診斷 dump——下一節學怎麼讀它最關鍵的部分:call trace。

4. 讀 call trace:崩潰時的呼叫堆疊

Oops/panic 的 dump 裡,最有用的是 call trace(呼叫堆疊)——它顯示「崩潰當下,函式是怎麼一層層呼叫進來的」(回顧 P1-T01 的 call stack)。

flowchart TB
    DUMP["Oops dump 包含:"]
    DUMP --> REASON["① 錯誤原因 + 出錯位址
(如 'BUG: kernel NULL pointer dereference at ...')"]
    DUMP --> REGS["② 暫存器 dump(崩潰當下各暫存器的值,回顧 P1-T01)"]
    DUMP --> TRACE["③ ★ Call Trace ★(最有用):
從崩潰點往回的函式呼叫鏈
my_buggy_func+0x.../my_module
← some_caller+0x...
← ... 一層層往上"]
    TRACE --> READ["怎麼讀:
最上面(或標記出錯的)那個常是崩潰點;
往下是呼叫它的函式們
→ 看到你 module 的函式名 = 定位到你的程式碼"]
    style TRACE fill:#e8a33d,color:#10100e
    style READ fill:#8a9a5b,color:#10100e

dump 的三部分: - 錯誤原因 + 出錯位址:例如 "kernel NULL pointer dereference"(解參考了 NULL)和出錯的位址。 - 暫存器 dump:崩潰當下各 CPU 暫存器的值(回顧 P1-T01)。 - Call Trace(最有用):從崩潰點往回的函式呼叫鏈——每一行是一個函式 + 偏移(如 my_func+0x1a/0x40 [my_module],代表 my_module 裡的 my_func 函式偏移 0x1a 處)。

怎麼讀:找到你 module 的函式名(call trace 會標出函式屬於哪個模組,如 [my_module]),那就是定位到你的程式碼的線索。崩潰點通常在 trace 頂端附近;往下是呼叫鏈(誰呼叫了它)。但 trace 給的是「函式+偏移」,你還需要把它對回確切的程式碼行——那就是下一節的 addr2line。

5. addr2line:把位址對回程式碼行

call trace 給你「函式 + 偏移」(如 my_func+0x1a),但你想知道「到底是哪一行出錯」。addr2line(或 decode_stacktrace.sh) 把那個位址/偏移,對應回原始碼的檔案與行號——前提是 kernel/module 編譯時帶了除錯符號(CONFIG_DEBUG_INFO,回顧 P3-T02)。

flowchart TB
    TRACE2["call trace:my_func+0x1a/0x40 [my_module]"]
    TRACE2 --> NEED["前提:module 編譯時帶除錯符號
(CONFIG_DEBUG_INFO + module 沒 strip)"]
    NEED --> TOOL["工具:
addr2line -e my_module.o 0x1a
或 scripts/decode_stacktrace.sh(更方便,
自動處理整個 trace)"]
    TOOL --> RESULT["→ 輸出:my_module.c:123
★ 原來是第 123 行出錯 ★
(回顧 P0-T01:沒符號就只有冷冰冰的位址,
有符號才有檔案行號)"]
    style NEED fill:#e8a33d,color:#10100e
    style RESULT fill:#8a9a5b,color:#10100e

流程: - 前提:module 編譯時有除錯符號(CONFIG_DEBUG_INFO,且 module 沒被 strip 掉符號)。常見誤區:不會把 call trace 位址對應回原始碼——往往是因為沒符號;有符號才能對回行號(完全呼應 P0-T01:沒 -g 就只有位址、有 -g 才有行號)。 - 工具:addr2line -e <object> <位址> 把位址對回檔案:行號;或更方便的 scripts/decode_stacktrace.sh(自動處理整個 trace)。 - 結果:my_module.c:123——定位到確切的出錯行。

這就是判讀 Oops 的完整流程(驗收點:觸發 NULL 解參考 Oops,從 call trace 用 decode_stacktrace/addr2line 定位到哪個函式/哪一行):看 dump → 找 call trace 裡你 module 的函式 → 用 addr2line/decode_stacktrace 對回程式碼行 → 找到 bug。這是你日後 debug module 崩潰的核心技能。

把這條「從崩潰到原始碼行」的流程畫成管線:

flowchart LR
    OOPS2["module 崩潰 → dmesg 出現 Oops"]
    OOPS2 --> FIND2["找 Call Trace 裡你 module 的函式
(my_func+0x1a [my_module])"]
    FIND2 --> DECODE["decode_stacktrace.sh / addr2line
(需 CONFIG_DEBUG_INFO 符號)"]
    DECODE --> LINE["→ my_module.c:123(確切出錯行)"]
    LINE --> FIX2["看那一行 → 找到 bug → 修"]
    style FIND2 fill:#6fa8b8,color:#10100e
    style DECODE fill:#e8a33d,color:#10100e
    style LINE fill:#8a9a5b,color:#10100e

6. ftrace:追蹤函式呼叫

最後一個工具:ftrace——kernel 內建的函式追蹤器,記錄「哪些函式被呼叫、呼叫順序、各花多久」。用來理解執行路徑、找效能瓶頸(不是找崩潰,是看「程式怎麼跑的」)。

flowchart TB
    FTRACE["ftrace(kernel 內建,透過 /sys/kernel/tracing 或 trace-cmd)"]
    FTRACE --> TRACERS["主要 tracer:
function tracer:記錄哪些 kernel 函式被呼叫
function_graph tracer:像呼叫圖,
顯示函式進入/離開、巢狀關係、各花多久"]
    TRACERS --> USE["用途:
① 理解某操作(如一次 syscall/IO)走過哪些函式
② 找哪個函式花最多時間(效能)
③ 確認你的程式碼有沒有走到預期路徑"]
    USE --> CAUTION2["★ 注意:範圍開太大會淹沒輸出 ★
用 filter 只追你關心的函式/子系統
(trace-cmd / KernelShark 可圖形化分析)"]
    style FTRACE fill:#6fa8b8,color:#10100e
    style USE fill:#8a9a5b,color:#10100e
    style CAUTION2 fill:#e8a33d,color:#10100e

ftrace 的能力: - function tracer:記錄哪些 kernel 函式被呼叫。 - function_graph tracer:像一張呼叫圖——顯示函式的進入/離開、巢狀關係、各花多久。用它追一次操作(如一次 syscall、一次 I/O)走過的函式路徑。 - 透過 /sys/kernel/tracing(debugfs)操作,或用 trace-cmd/KernelShark 圖形化分析。

常見誤區:ftrace 開太大範圍淹沒輸出——kernel 函式呼叫極頻繁,全追會產生海量資料。用 filter 只追你關心的函式/子系統。

對你的工作:ftrace 幫你理解「一次 I/O 在 kernel 裡走過哪些函式」、「哪個環節慢」——對 debug 你 I/O 路徑的效能問題很有用。(驗收點:用 function_graph 擷取一段函式呼叫序列並說明。)

打通關:把 kernel 除錯(一)收攏成一個心智模型

flowchart TB
    DEBUG["kernel 除錯(一):診斷 module 的崩潰與行為"]
    DEBUG --> PRINTK2["printk + log level:看狀態
(看不到訊息常是等級門檻問題;用 dmesg)"]
    PRINTK2 --> DYN["動態除錯:執行時精細開關 pr_debug(不重編)"]
    DEBUG --> CRASH["崩潰診斷:Oops(較輕,系統可能還活)
vs panic(致命,系統停)
★ Oops 後應重啟(狀態可能不一致)★"]
    CRASH --> TRACE3["讀 call trace:找你 module 的函式(崩潰點+呼叫鏈)"]
    TRACE3 --> ADDR["★ addr2line/decode_stacktrace:位址→程式碼行 ★
(需 CONFIG_DEBUG_INFO,呼應 P0-T01 的 -g)"]
    DEBUG --> FTRACE2["ftrace:追函式呼叫(function_graph)
理解執行路徑/找效能瓶頸(filter 避免淹沒)"]
    style CRASH fill:#e8a33d,color:#10100e
    style ADDR fill:#8a9a5b,color:#10100e
    style FTRACE2 fill:#6fa8b8,color:#10100e

一句話總結:kernel 除錯的日常工具——printk(注意 log level 門檻、用 dmesg)與動態除錯(執行時開關 pr_debug)看狀態;崩潰時 kernel 印 Oops(較輕,但系統未必正常、應重啟)或 panic(致命),讀 call trace 找你 module 的函式、再用 addr2line/decode_stacktrace(需 CONFIG_DEBUG_INFO)對回程式碼行定位 bug;ftrace 則追函式呼叫理解路徑與效能。判讀 call trace 是你 debug module 的基本功。

常見誤區與踩雷提醒

誤區一:printk 等級設定不當看不到訊息。 pr_debug/pr_info 可能低於 console 門檻被過濾。調 /proc/sys/kernel/printk,或用 dmesg(buffer 裡都有)。

誤區二:以為 Oops 後系統一定正常。 Oops 後出錯 task 可能持鎖未釋放、狀態不一致,系統可能不穩定。出 Oops 後應重啟(VM 裡重啟即可)。

誤區三:不會把 call trace 位址對應回原始碼。 需要 CONFIG_DEBUG_INFO(符號)+ addr2line/decode_stacktrace。沒符號就只有冷冰冰的位址(呼應 P0-T01 沒 -g)。

誤區四:ftrace 開太大範圍淹沒輸出。 kernel 函式呼叫極頻繁,全追產生海量資料。用 filter 只追關心的函式/子系統。

動手實作

環境:QEMU 虛擬機(觸發 Oops、ftrace 都在 VM)。 確認 kernel 帶 CONFIG_DEBUG_INFO(P3-T02)。

任務 A — 觸發 NULL 解參考 Oops 並定位(驗收點,核心) 寫一個 module,在某函式裡故意解參考 NULL(例如 int *p = NULL; *p = 1;)。在 QEMU 裡 insmod 觸發 Oops。然後: 1. 從 dmesg 找到 Oops 的 call trace,找出你 module 的函式名。 2. 用 decode_stacktrace.sh(或 addr2line -e your_module.ko <偏移>)把出錯位址對回程式碼行。 驗收:觸發 NULL 解參考 Oops,從 call trace 正確指出是哪個函式/哪一行。 觸發後重啟 VM(Oops 後狀態可能不一致)。

任務 B — ftrace function_graph(驗收點) 用 ftrace 的 function_graph tracer 擷取一段函式呼叫序列(例如追某個系統呼叫,或你 module 裡某函式的呼叫路徑)。用 filter 限制範圍(避免淹沒)。驗收:用 function_graph 擷取一段函式呼叫序列並說明它代表什麼。

任務 C — 動態除錯讓 pr_debug 可見(驗收點) 在 module 裡加 pr_debug 訊息,確認預設看不到;然後用動態除錯(/sys/kernel/debug/dynamic_debug/control)或調整 printk level,讓 pr_debug 顯示出來。驗收:調整後 pr_debug 可見。

任務 D(連結)— 為什麼需要 CONFIG_DEBUG_INFO 寫一句話:為什麼把 call trace 對回程式碼行需要 CONFIG_DEBUG_INFO?(連結 P0-T01 的 -g、P1-T11 的 gdb 符號。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 觸發一次 NULL 解參考 Oops,從 call trace 正確指出是哪個函式/哪一行(用 decode_stacktrace/addr2line)。 2. ☐ 用 ftrace function_graph 擷取一段函式呼叫序列並說明。 3. ☐ 調整 printk level 使 pr_debug 可見。

評分量表: - 60(及格):能用 printk 與看 dmesg。 - 80(熟練):能判讀 Oops 並定位。 - 100(精通):能用 ftrace 分析函式路徑與延遲。
