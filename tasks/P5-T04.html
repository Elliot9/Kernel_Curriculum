P5-T04 · I/O 排程器(mq-deadline / BFQ / Kyber / none)

一句話:I/O 排程器決定請求的順序與合併——在慢速裝置上,排序能大幅減少尋道、提升吞吐;但在超高速 NVMe 上,重量級排程反而是負擔,所以常用 none(不排程,直接派發)。選對排程器是效能調校的一環,影響的不只吞吐,更是延遲與公平。

為什麼要先學這個(導讀)

P5-T03 你看到 blk-mq 的軟佇列那層會做 I/O 排程。這一課深入:有哪些I/O 排程器、各自的取捨、以及怎麼選。

先理解為什麼需要 I/O 排程:當多個 I/O 請求進來,直接照「先來後到」派發未必最好。排程器可以: - 合併(merge):把相鄰的請求併成一個(回顧 P5-T02 bio→request 合併)——減少請求數。 - 排序(sort):重排請求順序,讓裝置更有效率(對 HDD 這超重要——減少磁頭尋道;對 SSD 影響小但仍有合併效益)。 - 公平(fairness):確保不同行程/任務都能拿到 I/O,不被某個 I/O 大戶餓死。 - 延遲(latency):控制請求的等待時間,避免某些請求等太久。

主要的排程器(blk-mq 時代): - mq-deadline:給每個請求一個期限(deadline),避免請求飢餓——簡單、可預測。 - BFQ(Budget Fair Queueing):重視公平和互動友善(桌面場景:讓互動程式的 I/O 優先)。 - Kyber:輕量、重視低延遲,用 token 限流。 - none:不排程——直接派發。高速 NVMe 常用這個。

為什麼這對你是 scope: direct?因為你產品在 NVMe 上的延遲/吞吐表現,和排程器選擇相關。一個關鍵反直覺:對超高速 NVMe,常見建議是 none 或輕量的 mq-deadline——因為裝置本身夠快,重量級排程器(BFQ)的 CPU 開銷反而拖慢整體。理解這些取捨,你才能為產品做正確的效能調校。

(這一課回收 P2-T05:mq-deadline 用紅黑樹按 sector 排序請求——你練的紅黑樹在這裡用上。)

核心內容

拆成這幾節:(1) 為什麼需要 I/O 排程 → (2) mq-deadline:期限避免飢餓 → (3) BFQ:公平與互動 → (4) Kyber:低延遲 → (5) none:高速裝置的選擇 → (6) 切換與量測,最後打通關。

1. 為什麼需要 I/O 排程:四個目標

I/O 排程器在「請求進來」和「派發給裝置」之間做加工。它追求四個(有時衝突的)目標:

flowchart TB
    REQUESTS["多個 I/O 請求進來"]
    REQUESTS --> SCHED3["I/O 排程器:決定派發的順序與組合"]
    SCHED3 --> MERGE4["① 合併:相鄰請求併成一個(P5-T02)→ 減少請求數"]
    SCHED3 --> SORT2["② 排序:重排順序讓裝置更有效率
(HDD:減少磁頭尋道,巨大效益;SSD:效益小)"]
    SCHED3 --> FAIR2["③ 公平:不同行程都拿到 I/O,不被大戶餓死"]
    SCHED3 --> LAT["④ 延遲:控制等待時間,避免請求等太久"]
    NOTE19["這四個目標常衝突:
追求吞吐(排序/合併)可能犧牲個別請求的延遲;
追求公平可能犧牲吞吐
→ 不同排程器在這些目標間做不同取捨"]
    MERGE4 --> NOTE19

    style NOTE19 fill:#8a9a5b,color:#10100e

四個目標:合併(減少請求數)、排序(裝置效率——HDD 減少尋道效益巨大、SSD 效益小)、公平(不被 I/O 大戶餓死)、延遲(控制等待時間)。

關鍵(常見誤區:以為排程器只影響吞吐):這四個目標常衝突——追求吞吐(排序/合併)可能犧牲個別請求的延遲;追求公平可能犧牲吞吐。所以排程器對延遲與公平性的影響,往往比對吞吐更顯著。不同排程器在這些目標間做不同取捨,沒有「最好」的,只有「最適合某工作負載」的。

歷史脈絡:在 HDD 時代,排序(減少磁頭機械尋道)效益巨大,所以排程器很重要、很複雜。在 SSD/NVMe 時代,沒有機械尋道,排序的效益大減——這就是為什麼高速裝置常用 none(第 5 節)。

2. mq-deadline:用期限避免飢餓

mq-deadline 是一個簡單、可預測的排程器。核心想法:給每個請求一個期限(deadline),確保沒有請求等太久(避免飢餓)。

flowchart TB
    DEADLINE3["mq-deadline:每個請求帶一個 deadline(期限)"]
    DEADLINE3 --> SORT3["平時:用紅黑樹(P2-T05)按 sector 排序請求
→ 盡量按裝置位址順序派發(效率)"]
    DEADLINE3 --> EXPIRE["但若有請求快到期(等太久):
優先派發它,避免飢餓
(讀和寫各有不同的 deadline,讀通常較急)"]
    SORT3 --> BALANCE["= 在『效率排序』和『避免飢餓』之間平衡
簡單、行為可預測"]
    EXPIRE --> BALANCE
    style DEADLINE3 fill:#6fa8b8,color:#10100e
    style BALANCE fill:#8a9a5b,color:#10100e

mq-deadline 的機制: - 平時:用紅黑樹(回收 P2-T05!)按 sector 排序請求,盡量按裝置位址順序派發(效率)。 - 但設期限:每個請求有 deadline,若某請求快到期(等太久了),就優先派發它,避免飢餓。讀和寫各有不同 deadline(讀通常較急,因為應用常在等讀結果)。

mq-deadline 在「效率排序」和「避免飢餓」之間取得簡單的平衡,行為可預測。它是很多場景的合理預設,對 NVMe 也常是 none 之外的合理選擇(輕量、保證不飢餓)。

3. BFQ:公平與互動友善

BFQ(Budget Fair Queueing) 是重視公平和互動體驗的排程器,主要為桌面/互動場景設計。

    BFQ2["BFQ:預算式公平佇列"]
    BFQ2 --> FAIR3["核心:給每個行程一個 I/O『預算』
→ 公平分配 I/O 頻寬,沒有行程被餓死
(類似 CPU 排程的公平,P1-T07,但對 I/O)"]
    BFQ2 --> INTERACTIVE2["互動友善:
偵測互動型 I/O(如開啟程式、捲動)
→ 給它們較高優先,讓桌面感覺流暢"]
    FAIR3 --> COST["代價:★ 較重(複雜的記帳)★
CPU 開銷較大
→ 對超高速 NVMe,這個開銷可能反而拖慢整體吞吐"]
    INTERACTIVE2 --> COST
    style BFQ2 fill:#6fa8b8,color:#10100e
    style COST fill:#c2603a,color:#f4ecd8

BFQ 的特點: - 公平:給每個行程一個 I/O「預算」,公平分配 I/O 頻寬(類比 P1-T07 CPU 排程的公平,但對象是 I/O)。 - 互動友善:偵測互動型 I/O(開啟程式、捲動),給它們較高優先,讓桌面流暢。

代價(關鍵):BFQ 較重——它做複雜的記帳(預算追蹤),CPU 開銷較大。對超高速 NVMe,這個開銷可能反而拖慢整體吞吐(裝置本身夠快,排程器的 CPU 成本成為瓶頸)。所以 BFQ 適合桌面/互動、且裝置不是極快的場景;對你的高效能 NVMe 伺服器場景,BFQ 通常不是好選擇。

4. Kyber:輕量、低延遲

Kyber 是一個輕量的排程器,重視低延遲,專為快速裝置設計。

    KYBER["Kyber:輕量、低延遲導向"]
    KYBER --> TOKEN["機制:用 token 限流
限制同時派發的讀/寫請求數,
動態調整以維持目標延遲
(讀和寫分開控制)"]
    TOKEN --> GOAL2["目標:保持低延遲
(不讓太多請求同時擠在裝置,造成延遲尖峰)"]
    KYBER --> LIGHT["★ 輕量 ★(比 BFQ 簡單得多)
→ 適合快速裝置(開銷小、又能控延遲)"]
    style KYBER fill:#6fa8b8,color:#10100e
    style LIGHT fill:#8a9a5b,color:#10100e

Kyber 的機制:用 token 限流——限制同時派發的讀/寫請求數,動態調整以維持目標延遲(讀和寫分開控制)。想法:不讓太多請求同時擠在裝置,避免延遲尖峰。

Kyber 比 BFQ 輕量得多,適合快速裝置——開銷小,又能控制延遲。它是「高速裝置上想要一點延遲控制、但不要 BFQ 那麼重」時的選擇。對你的 NVMe 場景,Kyber 是 none/mq-deadline 之外、想要延遲控制時的一個選項。

5. none:高速裝置的選擇

none 就是不排程——請求直接派發給裝置,不做排序(合併仍可能在更底層發生)。這在高速 NVMe 上常是最佳選擇,而這很反直覺。

flowchart TB
    NONE["none:不做 I/O 排程,直接派發"]
    NONE --> WHY2["為什麼高速 NVMe 常用 none(反直覺):"]
    WHY2 --> R1b["① NVMe 沒有機械尋道(不像 HDD)
→ 排序減少尋道的效益『消失了』"]
    WHY2 --> R2b["② NVMe 內部自己有高度並行(多佇列、多通道)
→ 裝置自己會調度,軟體再排程是多餘"]
    WHY2 --> R3b["③ NVMe 快到每秒百萬 IOPS
→ 排程器的 CPU 開銷成為瓶頸(P5-T03 同理)
→ 不排程、直接派發反而最快、延遲最低"]
    style NONE fill:#e8a33d,color:#10100e
    style R3b fill:#8a9a5b,color:#10100e

為什麼高速 NVMe 常用 none(驗收點:說明為何高速 NVMe 常選 none): - 沒有機械尋道:NVMe 不像 HDD 有磁頭,排序減少尋道的效益消失了。 - 裝置內部已高度並行:NVMe 自己有多佇列、多通道,內部會調度——軟體層再排程是多餘的。 - 裝置快到 CPU 成瓶頸:NVMe 每秒百萬 IOPS,排程器的 CPU 開銷反而成為瓶頸(同 P5-T03 的道理:裝置快到讓軟體成為瓶頸)。

所以對 NVMe,不排程(none)、直接派發,反而最快、延遲最低。這是「裝置特性決定軟體策略」的典型:HDD 時代複雜排程很值得,NVMe 時代簡單(甚至不排程)才對。

常見誤區:對高速 NVMe 仍套用重量級排程器——對 NVMe 套 BFQ 這種重量級排程器,常常降低效能。常見建議:NVMe 用 none(極致吞吐/延遲)或 mq-deadline(想要不飢餓的保證)。你產品調校時,從這兩個試起。

最後是實務:怎麼切換排程器、怎麼量測比較。

  • 切換(per-device):cat /sys/block/<dev>/queue/scheduler 看可選的([中括號] 是當前);echo <排程器> > /sys/block/<dev>/queue/scheduler 切換。常見誤區:切換排程器影響範圍誤判——scheduler 是 per-device(每個區塊裝置各自設定),改一個不影響別的。
  • 量測(用 fio):對同一裝置、同一工作負載,切換不同排程器各跑一次 fio,比較延遲和吞吐/IOPS。
  • 分析:依你的工作負載(讀寫比、隨機/順序、並行度)選最適合的。

這是效能調校的標準做法:不要憑感覺,要量測。對你產品,在目標 NVMe 上用代表性的工作負載(模擬你的 RAID I/O 模式)量測 none vs mq-deadline,看哪個延遲/吞吐更好(驗收點:用 fio 對至少兩種排程器量測並比較)。

一句話總結:I/O 排程器在合併/排序/公平/延遲間做取捨(影響延遲與公平往往大於吞吐)——mq-deadline 用期限避免飢餓(紅黑樹排序)、BFQ 公平互動但較重、Kyber 輕量低延遲、none 不排程直接派發;高速 NVMe 常用 none 或 mq-deadline(因無機械尋道、裝置自己並行、要避免 CPU 開銷),別套重量級的 BFQ;切換是 per-device,調校要用 fio 量測為準。

常見誤區與踩雷提醒

誤區一:對高速 NVMe 仍套用重量級排程器。 對 NVMe 套 BFQ 常降低效能。常見建議:NVMe 用 none(極致吞吐/延遲)或 mq-deadline(要不飢餓保證)。

誤區二:以為排程器只影響吞吐。 排程器對延遲與公平性的影響往往比吞吐更顯著。四個目標常衝突,選擇是權衡。

誤區三:切換排程器影響範圍誤判。 scheduler 是 per-device(每個區塊裝置各自設定)。改一個裝置不影響別的。

驗收檢核點(量化,逐項通過): 1. ☐ 成功在 /sys/block/<dev>/queue/scheduler 切換排程器並用 cat 確認。 2. ☐ 用 fio 對至少兩種排程器量測並比較延遲/吞吐。 3. ☐ 說明為何高速 NVMe 常選 none。

評分量表: - 60(及格):能切換排程器。 - 80(熟練):能量測並比較。 - 100(精通):能依負載特性論證排程器選擇。

延伸與銜接

  • 對應工作場景:直接對應——你產品在 NVMe 上的延遲/吞吐表現與排程器選擇相關;理解取捨有助於效能調校。
  • 這課餵給未來的:排程器取捨 → 你產品的效能調校;fio 量測方法 → 你日後驗證任何 I/O 變更;none 的道理(裝置快→軟體簡化)→ 呼應 P5-T03 blk-mq、預告 P5-T05 NVMe 的高並行。紅黑樹排序 → 回收 P2-T05。
  • 下一步 → P5-T05 NVMe 協定基礎(控制器/命名空間、SQ/CQ、doorbell、PRP/SGL):你已經掌握 block layer 的物件、多佇列、排程。下一課深入裝置端的協定——NVMe,你產品的核心。你會學:控制器 vs 命名空間、提交/完成佇列(SQ/CQ)(就是 blk-mq 硬體佇列對應的那個,P5-T03)、doorbell 暫存器(在 BAR 裡,回收 P4-T04/P3-T11)、命令/完成項的格式與 phase bit、以及 PRP/SGL(描述資料記憶體位置,和 P5-T02 的 bio_vec/scatter-gather 呼應,也是 P6 DMA 的關鍵)。這直接對應你的工作:你產品把 NVMe queue I/O 餵給 GPU,理解 SQ/CQ、doorbell、PRP/SGL 是理解這條資料路徑的根本。(我已查證 NVMe 規格現況:Base Spec 2.3 於 2025-08 發布,2.1 是穩定教學參考。)
