P1-T01 · CPU 執行模型與暫存器

一句話:CPU 不是魔法,它就是一台「不斷重複『取指令→解碼→執行』」的機器,而暫存器是它手邊那幾個超高速的小抽屜。看懂這個迴圈和那幾個抽屜,你才讀得懂 kernel panic 時噴出的那串 register dump。

為什麼要先學這個(導讀)

歡迎來到 Phase 1。Phase 0 你學的是「C 這個語言」,從這裡開始,你要學的是「這台機器與作業系統如何運作」。這是從「會寫程式」到「懂系統」的轉折。

而轉折的第一步,是看清 CPU 到底在做什麼。在 P0-T01 你已經知道,你的 C 程式最終會被編譯成機器碼——一串 CPU 指令。但 CPU 是怎麼執行這串指令的?它如何知道下一條要做哪個?運算時資料放在哪裡?

答案出奇地簡單:CPU 永遠在重複一個三步驟迴圈(取指令、解碼、執行),而它運算時用的不是記憶體,是幾個叫暫存器(register)的超高速儲存格。

為什麼你需要懂這個?最直接的理由是除錯 kernel。當 kernel 出錯(panic),它會噴出一大串「register dump」——RAX=...、RSP=...、RIP=...。如果你不知道這些暫存器是什麼、RSP 為什麼是堆疊指標、參數放在哪幾個暫存器,那串 dump 對你就是亂碼。看 stack trace、理解一次函式呼叫怎麼用暫存器傳參,全都建立在這一課。這是你日後除錯自家 kernel module 的基本功。

開始之前(前置確認)

  • 依賴:P0-T12(你已完成 Phase 0,能熟練操作指標與記憶體)。
  • 自我檢測: 1. 你還記得 P0-T01 用 objdump -d 看過組合語言嗎?這課要更深入讀它。 2. 你還記得 P0-T05 的 stack(堆疊)和函式呼叫時長出/縮回的 stack frame 嗎?這課從硬體角度再看一次。

核心內容

拆成這幾節:(1) CPU 的本質:取指-解碼-執行迴圈 → (2) 暫存器是什麼、為什麼快 → (3) 幾個關鍵暫存器的角色 → (4) 暫存器 ≠ 記憶體 → (5) 呼叫慣例:函式如何用暫存器傳參 → (6) 讀一段真實的反組譯,最後打通關。

1. CPU 的本質:一個永不停止的三步驟迴圈

CPU 的核心工作,可以濃縮成一個不斷重複的迴圈,叫 fetch-decode-execute(取指令-解碼-執行):

flowchart LR
    F["① Fetch 取指令
從記憶體讀出
『下一條指令』
(PC/IP 指著它)"]
    D["② Decode 解碼
看懂這條指令
要做什麼
(加法?搬資料?跳轉?)"]
    E["③ Execute 執行
真正做那件事
(用暫存器運算/
讀寫記憶體)"]
    F --> D --> E
    E -->|"PC 前進到下一條
迴圈重來"| F
    style F fill:#6fa8b8,color:#10100e
    style D fill:#e8a33d,color:#10100e
    style E fill:#8a9a5b,color:#10100e

就這樣,每秒數十億次。一支程式「跑起來」,本質上就是 CPU 把它的機器碼指令,一條接一條地走完這個迴圈。

關鍵角色是那個「指著下一條指令」的東西,叫 程式計數器(Program Counter, PC),在 x86-64 上叫 指令指標(Instruction Pointer),暫存器名是 RIP。每執行完一條指令,RIP 就自動前進,指向下一條;遇到跳轉(if、迴圈、函式呼叫),就是把 RIP 改成別的位址。

比喻:CPU 像一個照著食譜做菜的廚師,RIP 是他手指按著的「目前這一行」。他做完一步,手指往下移一行;遇到「跳到步驟 7」就把手指移過去。整本食譜(程式)他就這樣一行一行執行完。

2. 暫存器:CPU 手邊的超高速小抽屜

CPU 執行運算時,需要地方暫放資料(要相加的兩個數、運算的中間結果)。它不直接用記憶體——記憶體相對 CPU 太慢了(下一課 P1-T02 會量化這個差距)。它用的是暫存器(register):位於 CPU 內部的、數量很少但速度極快的儲存格。

    REG -.“慢得多”.-> MEM["記憶體(RAM)

    style MEM fill:#6fa8b8,color:#10100e

數量「少」是重點:x86-64 大約只有十幾個通用暫存器。它們是 CPU 的「工作檯面」——檯面很小,放不下整個程式的資料,所以資料平時住在記憶體,要用時才搬上檯面(load)、用完搬回去(store)。這個「載入-運算-存回」的節奏,你在反組譯裡會一直看到(mov 載入、運算、mov 存回)。

比喻:暫存器像廚師的「料理檯面」,記憶體像「冰箱與儲藏室」。檯面就那麼大,只能放正在處理的幾樣食材;大量食材放冰箱(記憶體),要用時拿到檯面(載入暫存器),處理完放回去(存回記憶體)。廚師的刀工(運算)只在檯面上進行。

3. 幾個關鍵暫存器的角色

x86-64 的通用暫存器有 RAX、RBX、RCX、RDX、RSI、RDI、RBP、RSP、R8~R15 等。大部分是「通用」的(隨運算使用),但有幾個有特殊角色,你一定要認得:

指著『下一條要執行的指令』
= 食譜上手指按的那行"]
        RSP["RSP(堆疊指標)
指著 stack 的頂端
= P0-T05 那疊便利貼的最上面"]
        RBP["RBP(基底指標)
常指著當前 stack frame 的基底
(輔助定位區域變數)"]
        RAX["RAX
慣例上放『函式回傳值』"]
    end
    style RIP fill:#e8a33d,color:#10100e
    style RSP fill:#c2603a,color:#f4ecd8
    style RAX fill:#8a9a5b,color:#10100e

最重要的兩個: - RIP:第 1 節說過,指著下一條指令。kernel panic 的 dump 裡,RIP 告訴你「當機時 CPU 正要執行哪條指令」——這是 debug 的第一線索。 - RSP:堆疊指標,永遠指著 stack 的頂端。回顧 P0-T05——stack 是放區域變數、函式呼叫記錄的地方;RSP 就是那疊便利貼最上面那張的位置。函式呼叫時 stack 長大(RSP 移動),回傳時縮回(RSP 移回)。

(註:RAX 等名字的 R 開頭代表 64 位元版本;同一個暫存器的低 32 位元叫 EAX、低 16 位元叫 AX——這是歷史演進的命名,看反組譯時會遇到,知道它們是同一個暫存器的不同寬度即可。)

4. 關鍵釐清:暫存器不是記憶體,沒有記憶體位址

這是新手一個重要的誤解點,單獨拉出來講。

你在 P0-T02 學過:記憶體裡每個東西有位址,可以用指標指向它。但暫存器不在記憶體裡,它沒有記憶體位址,你不能用指標指向一個暫存器。

flowchart LR
    subgraph mem["記憶體裡的東西"]
        V["變數 x
有位址 0x1004
→ 可以 &x、可以用指標指"]
    end
    subgraph reg["暫存器"]
        R["RAX
沒有記憶體位址
→ 不能 &RAX、不能用指標指"]
    end
    style V fill:#8a9a5b,color:#10100e
    style R fill:#c2603a,color:#f4ecd8

暫存器是 CPU 內部的、用「名字」(RAX、RSP…)指定的儲存格,不是記憶體位址空間的一部分。「取一個暫存器的位址」這件事沒有意義。

為什麼這個釐清重要? 因為「位址」是 kernel 世界的核心概念(這是你那條「位址的真相」主線的一部分,從 P0-T05 延續,將在 P1-T04 虛擬記憶體、最終在 P6-T01 DMA 達到高潮)。搞清楚「什麼東西有位址、什麼沒有」是這條線的基礎。暫存器沒有記憶體位址——記住這一點。

5. 呼叫慣例:函式呼叫如何用暫存器傳參

這是本課最實用的部分。當你呼叫 foo(a, b, c),參數怎麼傳給 foo?回傳值怎麼拿回來?答案由一套呼叫慣例(calling convention)規定。x86-64 Linux 用的是 System V ABI,規則(簡化)是:

flowchart TB
    subgraph args["整數/指標參數:依序放這些暫存器"]
        A1["第1個參數 → RDI"]
        A2["第2個參數 → RSI"]
        A3["第3個參數 → RDX"]
        A4["第4個參數 → RCX"]
        A5["第5個參數 → R8"]
        A6["第6個參數 → R9"]
        A7["第7個以後 → 放到 stack 上"]
    end
    RET["回傳值 → RAX"]
    args --> RET
    style A1 fill:#6fa8b8,color:#10100e
    style RET fill:#8a9a5b,color:#10100e

所以呼叫 foo(a, b, c) 時,編譯器產生的機器碼會:把 a 放進 RDI、b 放進 RSI、c 放進 RDX,然後 call foo;foo 算完把結果放進 RAX,呼叫者從 RAX 取回。

用一張流程圖看一次完整呼叫:

flowchart TB
    S1["呼叫端:foo(10, 20)"]
    S2["把 10 放進 RDI
把 20 放進 RSI"]
    S3["call foo
(把返回位址壓進 stack,
RIP 跳到 foo 的開頭)"]
    S4["foo 執行:
從 RDI/RSI 取出參數運算
結果放進 RAX"]
    S5["ret
(從 stack 取回返回位址,
RIP 跳回呼叫端的下一行)"]
    S6["呼叫端從 RAX 取回回傳值"]
    S1 --> S2 --> S3 --> S4 --> S5 --> S6
    style S2 fill:#6fa8b8,color:#10100e
    style S4 fill:#e8a33d,color:#10100e
    style S6 fill:#8a9a5b,color:#10100e

為什麼你要懂這個? 因為當你 debug、看反組譯或 register dump 時,你能據此「讀出」函式被呼叫時的參數:看 RDI、RSI 就知道前兩個參數是什麼。這在排查 kernel 問題時極有用——例如某函式 crash,看暫存器就能推測它被傳了什麼參數。

比喻:呼叫慣例像公司內部「交接文件」的固定規矩——第一份放 1 號抽屜、第二份放 2 號抽屜、結果放在「產出」抽屜。每個人都遵守同一套規矩,所以任何人接手都知道去哪個抽屜找對應的東西。RDI/RSI/RAX 就是這些約定好的抽屜。

6. 讀一段真實的反組譯

把前面所有概念落地:看一段 objdump -d 的輸出長什麼樣、怎麼對照。假設有個簡單函式:

int add(int a, int b) {
    return a + b;
}

objdump -d 反組譯後,add 大概長這樣(簡化、可能因編譯器/優化而異):

flowchart TB
    L1["add:"]
    L2["mov eax, edi   ; 把第1個參數(在 edi=rdi 低32位)搬進 eax"]
    L3["add eax, esi   ; 加上第2個參數(esi=rsi 低32位)"]
    L4["ret            ; 回傳(結果已在 eax=rax)"]
    L1 --> L2 --> L3 --> L4
    NOTE["對照第5節:
參數在 RDI/RSI(這裡用低32位 EDI/ESI)
回傳值在 RAX(這裡用低32位 EAX)
完全符合 System V 呼叫慣例"]
    L4 --> NOTE
    style L2 fill:#6fa8b8,color:#10100e
    style L3 fill:#6fa8b8,color:#10100e
    style NOTE fill:#e8a33d,color:#10100e

看懂了嗎?三行組語完美對應你學的:參數從 EDI/ESI(即 RDI/RSI 的 32 位部分)來,運算,結果放 EAX(RAX 的 32 位部分)然後 ret。這就是「讀組語」的入門——你不需要會寫組語,但要能對照著認出「參數在哪、回傳在哪、控制流怎麼走」。

一句話總結:CPU 就是一台跑「取指-解碼-執行」迴圈的機器,用少數超高速暫存器當工作檯面;搞懂幾個關鍵暫存器的角色與呼叫慣例,你就能讀懂 kernel panic 的 register dump、看懂 stack trace、從反組譯認出參數與控制流。 這是你日後除錯 kernel 的地基。

常見誤區與踩雷提醒

誤區一:把暫存器當成記憶體位址。 暫存器在 CPU 內部,沒有記憶體位址,不能用指標指向(第 4 節)。它們用名字(RAX、RSP…)指定,不是位址空間的一部分。

誤區二:忽略呼叫慣例,看不懂參數怎麼傳。 參數不是憑空傳遞的,而是依 System V ABI 放進 RDI/RSI/RDX… 或 stack。不懂這個,就讀不出反組譯/dump 裡的參數。

誤區三:混淆 RSP 與一般暫存器。 RSP 是堆疊指標,有特殊用途(指著 stack 頂端,函式呼叫時自動移動)。把它當一般暫存器隨意覆蓋,會破壞 stack、導致崩潰。

誤區四:以為 RAX、EAX、AX 是不同暫存器。 它們是同一個暫存器的不同寬度檢視(64/32/16 位)。看反組譯時別把它們當成三個不同的東西。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 反組譯一支含函式呼叫的程式

int add(int a, int b) { return a + b; }
int main(void) {
    int r = add(10, 20);
    return r;
}

gcc -O0 -g prog.c -o prog     # -O0 讓組語更貼近原始碼,易讀
objdump -d prog | less        # 找到 add: 和 main: 兩段

在 main 那段裡,找出:呼叫 add 之前,10 和 20 被搬進了哪兩個暫存器?(應該是 edi/esi 一類。)在 add 那段裡,找出回傳值放進了哪個暫存器(eax)。

任務 B — 對照三個驗收點 針對任務 A 的反組譯,明確回答三件事(這就是驗收點): 1. 哪個暫存器是堆疊指標?(找 rsp 的使用,例如 push/pop/sub rsp 等。) 2. 前幾個整數參數放在哪些暫存器?(rdi/rsi/rdx…) 3. 回傳值在哪個暫存器?(rax)

任務 C — 觀察 RSP 隨呼叫變化(概念) 在反組譯裡找 call 指令前後,觀察是否有 push(壓 stack)或 sub rsp, N(為區域變數在 stack 上騰空間)的動作。寫一句話:這如何呼應 P0-T05 講的「函式呼叫時 stack frame 長出來」?

驗收與自我評分

驗收檢核點(量化,逐項通過): 對一支含一次函式呼叫的 C 程式反組譯,正確指出: 1. ☐ 哪個暫存器是堆疊指標(RSP)。 2. ☐ 前幾個整數參數放在哪些暫存器(x86-64 System V:RDI/RSI/RDX…)。 3. ☐ 回傳值在哪個暫存器(RAX)。

評分量表: - 60(及格):能把 C 與組語對照起來看。 - 80(熟練):能解讀組語的控制流(跳轉、呼叫、返回)。 - 100(精通):能完整說明一次函式呼叫如何用暫存器與堆疊傳遞參數、返回值與返回位址。

延伸與銜接

  • 對應工作場景:基礎能力——除錯 kernel panic 的 register dump、看 stack trace、用 gdb 檢視暫存器時都需要。你日後排查自家 module 的崩潰,第一步常常就是讀 RIP/RSP 和暫存器內容。
  • 這課餵給未來的:暫存器/stack 概念 → P1-T06 context switch(切換時要保存/還原所有暫存器);「暫存器無位址」→ 你那條「位址的真相」主線(P1-T04→P6-T01);呼叫慣例 → 理解 syscall 如何傳參。
  • 下一步 → P1-T02 記憶體階層與快取:你已經知道 CPU 運算用暫存器、資料平時在記憶體,而且「記憶體比暫存器慢」。下一課就量化這個「慢」有多誇張(數十到數百倍),並揭露 CPU 如何用 cache(快取) 來縮小這個鴻溝——以及為什麼你的資料結構怎麼擺,會直接決定程式快慢。這對你的高效能 I/O 路徑是關鍵。
