P3-T01 · kernel 架構總覽與原始碼樹佈局

一句話:Linux 是「單體核心 + 可載入模組」——所有東西跑在同一個核心位址空間裡,但功能可以模組化地動態載入/卸載。先建立這張全景圖、知道每個子系統住在原始碼樹的哪個目錄,你才知道自己產品要改的東西在哪一層。

為什麼要先學這個(導讀)

歡迎來到 Phase 3——整個課程的重頭戲,也是內容量最大的階段。前面三個階段你建立了 C 功底(P0)、系統心智模型(P1)、kernel 資料結構的讀碼能力(P2)。從這裡開始,你要真正進入 kernel 內部:理解它的架構、親手寫 kernel module、深入記憶體管理、同步、中斷、除錯。

但在動手之前,要先有一張全景地圖。Linux kernel 是個龐大的東西(數千萬行程式碼),如果沒有整體架構的概念,你會在原始碼樹裡迷路。這一課就是建立那張地圖:kernel 的整體架構是什麼?有哪些主要子系統?它們住在原始碼樹的哪些目錄?

核心概念是 Linux 的架構選擇:單體核心(monolithic kernel)+ 可載入核心模組(loadable kernel module, LKM)。「單體」意思是整個核心(行程管理、記憶體管理、檔案系統、網路、驅動……)跑在同一個核心位址空間裡,彼此能直接呼叫。但「單體」不等於「不能模組化」——透過 LKM,功能可以編成獨立模組,在執行時動態載入/卸載(你的驅動、檔案系統都能這樣)。這是一個重要的設計取捨,跟「微核心(microkernel)」相對。

為什麼這對你是 scope: direct?因為你的產品橫跨好幾層:user space 應用程式、block layer、NVMe driver、你自己寫的 module。先建立全景圖,你才知道「我要改的東西在哪一層、跟哪些子系統互動」。這一課也讓你學會用 Bootlin Elixir 在原始碼樹裡導航——這是你日後讀 kernel code 的基本功(呼應 P2-T08)。

開始之前(前置確認)

  • 依賴:P2-T08(你已能讀懂 kernel 資料結構、用 Bootlin 導航)。
  • 自我檢測: 1. 你還記得 P1-T06 的「user space 與 kernel space 的邊界」嗎?這課把這個邊界放到整體架構裡看。 2. 你能接受「整個 kernel 跑在同一個位址空間、彼此直接呼叫」這個概念嗎?(這就是「單體」。)
  • 工具:準備好 Bootlin Elixir(https://elixir.bootlin.com/linux/v6.12/source ）——這課要在原始碼樹裡導航。

核心內容

1. 單體核心 + 可載入模組:Linux 的架構

Linux 的核心架構,一句話是「單體核心,但可模組化」。先看「單體」是什麼:

        VFS["檔案系統(VFS)"]

        DRIVERS["裝置驅動"]

    style MODULES fill:#e8a33d,color:#10100e

「單體」的意思:所有核心功能(排程、記憶體、檔案系統、網路、block layer、驅動)都跑在同一個核心位址空間裡,可以彼此直接呼叫函式——不需要跨位址空間的通訊。這跟使用者態程式各自獨立的位址空間(回顧 P1-T04/P1-T05)形成對比:核心內部是一整塊,大家共享同一個空間。

「但可模組化」的意思:你不必把所有東西都編進核心映像。功能可以編成 LKM,在執行時用 insmod 動態載入、rmmod 卸載。但關鍵:LKM 載入後,也跑在同一個核心位址空間——它不是隔離的沙盒,而是「成為核心的一部分」。這就是為什麼 P1-T11 反覆強調「module 的 bug 會搞垮整個系統」:它跟核心其他部分共享位址空間,沒有保護牆。

「單體」不等於「不能模組化」是關鍵澄清(常見誤解):Linux 既是單體(共享位址空間)、又支援模組化(動態載入)——兩者不衝突。你的驅動、檔案系統都能是 LKM,但它們載入後是核心的一部分。

2. 單體 vs 微核心:設計取捨

Linux 選了單體,但還有另一條路——微核心(microkernel)。理解這個取捨,你才知道 Linux 的架構為什麼這樣選。

flowchart TB
    subgraph mono["單體核心(Linux)"]
        M["核心功能都在核心空間,直接呼叫
優點:快(無跨空間通訊開銷)
缺點:一個元件出錯可能影響整個核心
(共享位址空間)"]
    end
    subgraph micro["微核心"]
        MK["核心只保留最小功能,
驅動/檔案系統等放到使用者態各自的行程
優點:隔離性好(一個服務崩潰不影響核心)
缺點:服務間要靠訊息傳遞通訊 → 較慢"]
    end
    style M fill:#8a9a5b,color:#10100e
    style MK fill:#6fa8b8,color:#10100e

取捨的核心: - 單體(Linux):所有東西在核心空間直接呼叫 → 效能好(沒有跨位址空間通訊的開銷),但隔離性差(一個元件的 bug 可能拖垮整個核心)。 - 微核心:核心極小,驅動/檔案系統等放到使用者態獨立行程 → 隔離性好(一個服務崩潰不影響核心),但較慢(服務間要訊息傳遞,有通訊開銷)。

「以為微核心一定較好」是常見誤區——它隔離性好,但效能代價在很多場景(尤其高效能 I/O,正是你的領域)不可接受。Linux 選單體,正是為了效能;它用 LKM 取得「模組化」的好處,但不採用微核心的「跨空間隔離」(因而保住效能)。這個取捨沒有絕對對錯,是針對「通用、高效能」目標的選擇。

跟你產品最相關的是 block layer(區塊裝置 I/O、blk-mq、I/O 排程)和裝置驅動(尤其 NVMe driver)。你前面學的東西分散在這些子系統:虛擬記憶體(P1-T04)在記憶體管理、行程/執行緒(P1-T05)在行程管理、你即將學的 SLUB(P3-T07)也在記憶體管理。每個子系統有自己的原始碼目錄(下一節),理解這個分區,你讀 code 時就知道往哪個目錄找。

記住這三個路徑(務必能正確說出): - block/:block layer 核心——blk-mq(P2-T07 tag 的家)、I/O 排程器(P2-T05 紅黑樹的用戶)、bio/request 處理。這是你 I/O 路徑的上層。 - drivers/nvme/host/:NVMe 主機端驅動,跟 NVMe SSD 溝通。直接關係你的產品。 - drivers/md/:md = multiple devices,即軟體 RAID 的實作(RAID 0/1/5/6)。這是你產品的核心領域——你日後要修改 block layer/驅動/DMA 來做軟體 RAID,這個目錄是你的主戰場之一。

把這三個目錄放進「一次 I/O 從上到下」的流動裡,你更能看出它們的位置關係:

整張全景:使用者態(你的 app 和其他所有程式,各自獨立位址空間)在上,透過 syscall 介面(回顧 P1-T06 那道受控閘門)跨越邊界,進入核心態(單體核心的各子系統 + 你載入的 LKM,共享同一核心位址空間)。你的產品橫跨這條線:user space app 在上,自寫 module 在下(核心空間),兩者透過 syscall 或你 module 提供的介面溝通。

這張圖把 P0–P3 學的都串起來了:位址空間隔離(P1)、syscall 邊界(P1)、單體核心(本課)、你即將寫的 LKM(P3 後續)。你終於看見自己產品在整個系統裡的位置。

常見誤區與踩雷提醒

誤區一:把「單體核心」誤解為「不能模組化」。 Linux 是單體(共享位址空間)且支援模組化(LKM 動態載入)。兩者不衝突。LKM 載入後也在核心空間(不是隔離沙盒)。

誤區二:以為微核心一定較好。 微核心隔離性好但有通訊開銷、較慢。Linux 選單體是為了效能(尤其高效能 I/O,你的領域)。取捨無絕對對錯,看目標。

誤區三:找不到子系統時亂猜目錄。 用 Bootlin Elixir 的符號搜尋(輸入函式/struct 名跳到定義),比瞎找快得多。

誤區四:以為 LKM 像使用者態程式一樣安全隔離。 LKM 在核心位址空間,bug 會影響整個系統(回顧 P1-T11)。這是為什麼自寫 module 只在 QEMU 測試。

動手實作

環境:Bootlin Elixir 線上瀏覽 + 可選 clone 原始碼,純閱讀/導航,無系統風險。
