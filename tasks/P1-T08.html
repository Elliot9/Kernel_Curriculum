P1-T08 · 並行基礎與 race condition

一句話:當兩個執行緒同時對一個共享變數 count++,結果可能小於你預期——因為 count++ 不是一步完成的,它是「讀-改-寫」三步,而這三步會在兩個執行緒間交錯,讓更新悄悄遺失。這是並行程式設計所有痛苦的起點。

為什麼要先學這個(導讀)

這一課是你「並行與同步」主線的起點(本課 → P1-T09 → P3-T08 → P3-T10),也是理解 kernel 為何需要那麼多鎖與同步機制的動機。

回顧 P1-T05:同一行程內的多個執行緒共享記憶體。這帶來便利(輕鬆共享資料),但也埋下一個致命的陷阱:當多個執行緒「同時」讀寫同一塊共享資料,而你沒有任何協調,結果會出錯——而且錯得時有時無、難以重現。 這種錯誤叫 race condition(競爭條件)。

最經典、也最能說明問題的例子是:兩個執行緒各自對同一個全域變數 count 加一百萬次。你以為最後 count 會是兩百萬,但實際跑出來往往小於兩百萬,而且每次跑的結果還不一樣。為什麼?因為 count++ 這個你以為「一步完成」的操作,其實是三步(讀出值、加一、寫回),而兩個執行緒的這些步驟會交錯進行,導致部分更新被覆蓋、遺失。

為什麼這對你是 scope: direct?因為 kernel 是一個極度並行的環境——多核心同時跑、隨時可能被中斷打斷、可能被搶佔。任何被多個執行流(執行緒、中斷處理常式)共享的狀態,都可能 race。你的 user space app 是多執行緒的,你的 kernel module 跑在這個並行環境裡。race condition 不是「偶爾才會踩到的邊角案例」,而是並行程式設計的核心難題,理解它是後面所有同步機制(P1-T09 的鎖、P3 的 kernel 同步)的前提。

開始之前(前置確認)

  • 依賴:P1-T07(你已理解多個 task 被排程並行/輪流執行)、P1-T05(執行緒共享記憶體)。
  • 自我檢測: 1. 你能說出「為什麼同一行程的兩個執行緒能看到對方對全域變數的修改」嗎?(回顧 P1-T05:共享位址空間。)這課的 race 正源於此。 2. 你還記得 P1-T01 說 CPU 運算是「把記憶體的值載入暫存器、運算、存回」嗎?這課會看到 count++ 底層正是這三步。

核心內容

拆成這幾節:(1) 並行與共享狀態的危險 → (2) count++ 其實是三步 → (3) 交錯如何導致更新遺失 → (4) race condition 的定義 → (5) critical section 與原子性的需求,最後打通關。

1. 並行與共享狀態:便利的另一面是危險

回顧 P1-T05:多執行緒共享同一個位址空間,所以它們能直接讀寫同一個全域變數、同一塊 heap。這很方便——執行緒之間不需要特別的機制就能共享資料。

但「同時讀寫同一塊資料」正是危險所在:

→ 若沒有協調,它們的操作會交錯

要理解為什麼「同時改」會出錯,關鍵是看清 count++ 在 CPU 層級到底是幾個動作——這是下一節的重點,也是整課的核心。

2. 關鍵真相:count++ 不是一步,是三步

你寫 count++,看起來是「一個動作」。但回顧 P1-T01:CPU 不能直接在記憶體上做運算,它必須把值載入暫存器、運算、再存回記憶體。所以 count++ 在 CPU 層級其實是三個獨立的步驟:

flowchart LR
    SRC["你寫:count++"]
    SRC --> STEP1["① 讀(load):
把 count 目前的值
從記憶體載入暫存器"]
    STEP1 --> STEP2["② 改(add):
在暫存器裡把值 +1"]
    STEP2 --> STEP3["③ 寫(store):
把暫存器的新值
存回 count 的記憶體"]
    style STEP1 fill:#6fa8b8,color:#10100e
    style STEP2 fill:#e8a33d,color:#10100e
    style STEP3 fill:#8a9a5b,color:#10100e

這就是所謂的「讀-改-寫(read-modify-write)」。重點來了:這三步之間,執行緒可能被打斷(回顧 P1-T07:排程器可以在任何時候搶佔一個執行緒,切換到另一個)。也就是說,執行緒 1 可能才做完「讀」,還沒「寫」,就被切換到執行緒 2——而執行緒 2 此時讀到的,是還沒被更新的舊值。這個「中間被打斷」的可能性,正是災難的種子。

3. 交錯如何導致更新遺失:逐步看災難

現在把兩個執行緒的「讀-改-寫」放在一起,看一個會丟失更新的交錯順序。假設 count 初始為 0,兩個執行緒各要 count++ 一次,理想結果應該是 2:

    INIT["初始:count = 0"]
    S1["執行緒1:讀 count → 暫存器得到 0"]
    S2["★ 此時被切換到執行緒2 ★"]
    S3["執行緒2:讀 count → 也得到 0
(因為執行緒1還沒寫回!)"]
    S4["執行緒2:+1 → 暫存器是 1"]
    S5["執行緒2:寫回 → count = 1"]
    S6["★ 切換回執行緒1 ★
它的暫存器還是剛才讀的 0"]
    S7["執行緒1:+1 → 暫存器是 1
(基於它讀到的舊值 0!)"]
    S8["執行緒1:寫回 → count = 1
(覆蓋了執行緒2寫的 1)"]

    style S8 fill:#c2603a,color:#f4ecd8

看懂這個交錯了嗎?問題的核心在 S3:執行緒 2 讀到的是執行緒 1「還沒寫回」的舊值 0。於是兩個執行緒都基於「0」去加一,各自算出 1、各自寫回 1——兩次 ++ 的效果,變成只加了一次。一次更新被覆蓋、遺失了。

對照一下「沒出錯」的交錯,你會更清楚問題出在哪——差別只在「有沒有在對方讀之前就寫回」:

    subgraph bad["✗ 出錯的交錯(更新遺失)"]

        BB["T2 讀 → 0(T1還沒寫!)"]
        BC["T1 寫 1,T2 也寫 1"]
        BD["結果 = 1(少加一次)"]
        BA --> BB --> BC --> BD
    end

關鍵體悟:正確與否,純粹取決於「排程剛好怎麼切換」——而那是你無法控制的。 你不能祈禱排程剛好錯開;你必須用同步機制強制「讀-改-寫」不被打斷。這就引出下一課的鎖。

把這個放大到「各加一百萬次」:大量的這種交錯會發生,所以最終結果會明顯小於兩百萬,而且因為交錯的時機是隨機的(取決於排程),每次跑的結果都不一樣。

比喻:兩個店員同時盤點同一個庫存數字。店員 A 看到庫存是 100,正要改成 101(進貨一件),但還沒寫下,就去接電話。這時店員 B 也看到庫存 100(A 還沒寫),改成 101 寫下。A 回來,把他記得的「101」寫下——庫存還是 101,但實際上進了兩件貨,應該是 102。一件貨憑空消失在帳上。問題就出在「兩人同時基於同一個舊數字操作」。

4. race condition 的定義

現在可以正式定義了:

flowchart TB
    DEF["race condition(競爭條件):
程式的結果取決於多個執行緒
『恰好以什麼順序交錯執行』
而這個順序是不確定的"]
    DEF --> PROP1["特徵① 結果不可預測
(同樣的程式,每次跑可能不同)"]
    DEF --> PROP2["特徵② 時有時無、難重現
(取決於排程時機,可能跑一千次才錯一次)
→ 極難 debug"]
    DEF --> PROP3["特徵③ 源於『未受保護的共享可變狀態』
(多執行緒 + 共享 + 有人寫)"]
    style DEF fill:#c2603a,color:#f4ecd8
    style PROP2 fill:#e8a33d,color:#10100e

race condition 最可怕的是特徵②:它時有時無。你的程式可能在測試時跑一萬次都正確,上線後在某個特定的時機交錯下才出錯一次。這種 bug 極難重現、極難 debug。這就是為什麼並行程式設計如此困難,也是為什麼我們需要嚴謹的同步機制——不能靠「測起來沒事」,要從原理上保證正確。

要判斷「會不會 race」,關鍵看是否三個條件同時成立。下圖幫你快速辨識哪些情況安全、哪些危險:

    Q["有沒有 race 風險?"]
    Q --> C1{"是多執行緒/
多執行流共享嗎?"}
    C1 -->|"否(只有一個執行流)"| SAFE1["✓ 安全(沒有並行存取)"]

    C3 -->|"有(鎖/原子)"| SAFE3["✓ 安全(已保護,P1-T09)"]

記住這條判斷鏈:「多執行流 + 共享 + 有寫 + 沒保護」四者齊備才有 race。 缺任何一個都安全——這也指出了消除 race 的各種方向(不共享、唯讀、或加保護)。

(這呼應了 P1-T08 之後 P1-T10 會強調的:volatile 關鍵字不能解決 race——它不保證原子性。很多新手以為加個 volatile 就好了,這是錯的,後面會詳述。)

5. critical section 與原子性的需求

既然問題出在「讀-改-寫三步會被交錯打斷」,解法的方向就清楚了:讓這三步「不可分割地」一起完成,中間不被其他執行緒插入。

這引出兩個關鍵概念:

flowchart TB
    subgraph concepts["解決 race 的兩個核心概念"]
        CS["臨界區(critical section):
存取共享資源的那段程式碼
(例:count++ 這段)
→ 需要保護,確保同時只有一個執行緒在執行"]
        ATOM["原子性(atomicity):
一個操作『要嘛全部完成,要嘛完全沒做』
中間不會被打斷、不會被看到中間狀態
→ 我們需要讓 count++ 變成原子的"]
    end
    CS -.“讓臨界區一次只有一人進入,
就達成了該段的原子效果”.-> ATOM
    style CS fill:#6fa8b8,color:#10100e
    style ATOM fill:#e8a33d,color:#10100e

  • 臨界區(critical section):程式中「存取共享資源」的那段程式碼。count++ 就是一個臨界區。要避免 race,必須確保同一時間只有一個執行緒能進入臨界區(這叫互斥,mutual exclusion)。
  • 原子性(atomicity):「原子」意指不可分割。一個原子操作要嘛完整發生、要嘛沒發生,絕不會被打斷到一半、也不會讓別人看到它的中間狀態。如果 count++ 是原子的,那「讀-改-寫」就會一氣呵成,不會發生第 3 節那種交錯。

這一課只是建立「需求」——我們需要互斥/原子性來保護共享狀態。「怎麼做到」是下一課 P1-T09 的主題(用鎖 mutex 把臨界區圍起來,確保一次一人進入)。先深刻理解「為什麼需要」,你才會珍惜並正確使用那些機制。

比喻:臨界區像一間只能容納一人的試衣間,原子性像「換衣服這件事要在門關上的狀態下完整做完」。如果沒有門鎖(同步機制),兩個人同時擠進去(交錯存取),就會一團亂。鎖(下一課)就是那扇門的鎖——一次只放一個人進去,出來了下一個才能進。

一句話總結:多執行緒共享狀態 + count++ 其實是可被打斷的「讀-改-寫」三步,導致更新在交錯中遺失,這就是 race condition——它結果不可預測、時有時無、極難 debug;解法是讓臨界區互斥、讓操作原子,而具體的工具(鎖)是下一課的主題。在高度並行的 kernel 裡,任何未受保護的共享可變狀態都是 race 的溫床。

常見誤區與踩雷提醒

誤區一:以為 count++ 是一步完成的。 它是「讀-改-寫」三步(回顧 P1-T01 CPU 不能直接在記憶體運算),三步間可被切換打斷,導致 race。這是整課最核心的認知。

誤區二:以為 race「偶爾才發生所以不嚴重」。 race 時有時無、難重現,正是它最危險之處——可能測試一萬次都對,上線才在特定時機出錯。不能靠「測起來沒事」,要從原理保證正確。

誤區三:以為加 volatile 就解決 race。 volatile 不保證原子性,不能解決 race(這個 P1-T10 會詳述)。它只是告訴編譯器「別把這個變數快取在暫存器、每次都從記憶體讀」,但「讀-改-寫」仍是三步、仍可被打斷。要解決 race 需要真正的同步機制(鎖、原子操作)。

誤區四:以為「唯讀共享」也需要鎖。 race 的前提是「有人寫」。如果所有執行緒都只讀一個共享資料、沒有人寫,那不會 race(大家讀到的都是同一個不變的值)。需要保護的是「共享的可變狀態」。

動手實作

環境:Linux 終端機,使用者態,多核心機器最易重現,安全,不需 root、不動系統。需要 pthread。

任務 A — 重現更新遺失(本課的核心實驗)

#include <stdio.h>
#include <pthread.h>
#define N 1000000
long counter = 0;             // 共享變數,故意不加保護

void *worker(void *_) {
    for (int i = 0; i < N; i++)
        counter++;            // 讀-改-寫,無保護 → race
    return NULL;
}
int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %ld (預期 2000000)\n", counter);
    return 0;
}

用 gcc -O2 prog.c -o prog -lpthread && ./prog 跑。觀察 counter 小於 2000000。多跑幾次(./prog 連跑五次),觀察每次結果都不一樣——這就是 race 的「不可預測、時有時無」。

任務 B — 精確解釋一次更新遺失 針對任務 A,用你自己的話寫出「兩個執行緒的讀-改-寫如何交錯,導致一次 ++ 遺失」的具體步驟(就像第 3 節那張圖)。這是驗收的核心——要能精確指出三步如何交錯。

任務 C(觀察)— 為什麼結果每次不同? 寫一句話解釋:為什麼任務 A 每次跑的結果不一樣?(提示:交錯的時機取決於排程,而排程的時機是不確定的。)這也順帶解釋了為什麼 race bug 這麼難重現。

任務 D(預告下一課)— 思考解法 先別實作,只思考並寫下:如果要讓 counter++ 不再遺失更新,你需要什麼樣的機制?(提示:讓「讀-改-寫」這段臨界區,同時只有一個執行緒能執行。)下一課 P1-T09 你會用 mutex 真正修好它。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 兩執行緒各對共享 counter 累加 1,000,000 次,最終結果穩定地小於 2,000,000。 2. ☐ 能精確指出 counter++ 的讀-改-寫三步如何交錯導致更新遺失。

評分量表: - 60(及格):能重現問題(結果小於預期)。 - 80(熟練):能精確解釋讀-改-寫如何交錯導致更新遺失。 - 100(精通):能預判哪些操作需要保護(辨識共享的可變狀態 = 潛在臨界區)。

延伸與銜接

  • 對應工作場景:直接對應——kernel 是高度並行環境(多核 + 中斷 + 搶佔),任何共享狀態都可能 race;這是 P3 同步機制的動機。你的多執行緒 app 與 kernel module 都活在這個並行現實裡。
  • 這課餵給未來的(你的並行主線):race/臨界區/原子性 → P1-T09 鎖與互斥 → P3-T08/P3-T10 kernel 同步(spinlock/mutex 選型、lockdep);「count++ 非原子」→ P1-T10 原子操作。
  • 下一步 → P1-T09 鎖、互斥與條件變數:你已經深刻理解「為什麼需要保護共享狀態」。下一課就給你工具:mutex(互斥鎖)——把臨界區鎖起來,確保一次只有一個執行緒進入,真正修好這課的 race。你還會學到 condition variable(讓執行緒高效等待某個條件)、實作經典的 producer-consumer,以及並行程式設計最惡名昭彰的陷阱——死結(deadlock) 及其四個成因與避免方法。
