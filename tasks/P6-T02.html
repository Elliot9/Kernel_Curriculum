P6-T02 · scatter-gather 與 DMA 同步

一句話:你的資料常分散在多個記憶體片段(bio_vec)——用 dma_map_sg 對一串 scatterlist 一次映射做 DMA。兩個致命細節:映射後要用「回傳的映射數」走訪(IOMMU 可能把片段合併,數量變少),以及 streaming 映射上 CPU 與裝置交替存取時必須用 dma_sync_* 維持 cache 一致性。

為什麼要先學這個(導讀)

P6-T01 你會用 coherent/streaming 映射單一 buffer 了。但你產品的資料很少是「一塊連續記憶體」——它常分散在多個片段(回顧 P5-T02 的 bio_vec:一次 I/O 的資料分散在多個頁)。這一課學怎麼對「一串分散片段」做一次 DMA——scatter-gather。

核心工具與概念: - struct scatterlist / sg_table:描述「一串分散的記憶體片段」的結構——每個 entry 是一個片段(page + offset + 長度)。這就是 P5-T02 的 bio_vec 在 DMA 層的對應。 - dma_map_sg / dma_unmap_sg:對整串 scatterlist 一次映射/解映射——讓裝置能一次 DMA 存取這些分散片段。 - dma_sync_*:streaming 映射上,當 CPU 和裝置交替存取同一塊記憶體時,要用 dma_sync_single_for_cpu/dma_sync_single_for_device 維持 cache 一致性。 - IOMMU 合併:IOMMU 能把「分散的實體片段」對裝置呈現成「連續的 DMA 視圖」——所以 dma_map_sg 回傳的映射數可能少於你給的原始 entry 數(一個致命陷阱)。

為什麼這對你是 scope: direct?因為NVMe 的 PRP/SGL 與 bio_vec 的分散片段,正是經 scatter-gather 映射做 DMA(回顧 P5-T05:bio_vec → PRP/SGL → 裝置 DMA)。這是你資料路徑的日常——你產品把 bio 的分散資料片段映射成裝置可 DMA 的形式,餵給 NVMe/GPU。這一課的兩個陷阱(映射數、sync),漏了就是間歇性資料錯誤。

1. 為何需要 scatter-gather

先理解問題:你要 DMA 的資料,常不在一塊連續記憶體,而是分散在多個片段。

    DATA2["你要 DMA 的資料(例如一次 I/O 的 16KB)"]
    DATA2 --> SCATTERED["實際分散在多個記憶體片段:
頁 A 的一段、頁 B 的一段、頁 C 的一段
(因為記憶體分頁管理,P1-T04;就是 bio_vec,P5-T02)"]
    SCATTERED --> OPTIONS["怎麼 DMA 這些分散片段?"]
    OPTIONS --> BAD2["✗ 笨方法:對每個片段各做一次 DMA 映射 + 傳輸
→ 多次映射/傳輸,開銷大、慢"]
    OPTIONS --> GOOD3["✓ scatter-gather:把『一串片段』一次映射(dma_map_sg)
→ 裝置一次 DMA 就能存取所有片段
(gather:聚集分散的片段成一次操作)"]
    style SCATTERED fill:#6fa8b8,color:#10100e
    style GOOD3 fill:#8a9a5b,color:#10100e

scatter-gather(分散-聚集) 解決「資料分散在多個片段」的 DMA。你的資料分散(回顧 P5-T02:bio_vec,因為記憶體分頁,一塊邏輯資料落在多個頁)。與其對每個片段各做一次 DMA(多次映射、慢),scatter-gather 把一串片段一次映射(dma_map_sg)——裝置一次 DMA 就能存取所有片段。

這正是你產品的場景:一次 I/O 的資料(來自 bio_vec)分散在多個頁,你用 scatter-gather 把它們一次映射,讓 NVMe(或 GPU)一次 DMA 存取。NVMe 的 SGL(Scatter-Gather List,P5-T05) 就是這個概念在 NVMe 協定層的體現——而 dma_map_sg 是你在 kernel 裡建立它的工具。

2. scatterlist 與 dma_map_sg

核心結構和函式:struct scatterlist(描述片段)和 dma_map_sg(一次映射整串)。

flowchart TB
    SGLIST["struct scatterlist 陣列(或 sg_table):一串片段
每個 entry:page + offset + length
(= bio_vec 的對應,P5-T02)"]
    SGLIST --> SETUP["建立:sg_init_table + sg_set_page(把每個片段填進去)
(或從 bio 的 bio_vec 直接轉成 scatterlist)"]
    SETUP --> MAPSG["dma_map_sg(dev, sglist, nents, direction)
一次映射整串 → 每個 entry 得到 dma_addr + 長度
(回傳『實際映射的 entry 數』,第3節!)"]
    MAPSG --> DEVICE7["裝置用這些 dma_addr(及長度)一次 DMA 存取所有片段
(對 NVMe:轉成 SGL/PRP,P5-T05)"]
    DEVICE7 --> UNMAPSG["dma_unmap_sg(dev, sglist, nents, direction)
★ 傳輸完必須 unmap(否則 IOMMU 映射洩漏)★"]

    style MAPSG fill:#e8a33d,color:#10100e
    style UNMAPSG fill:#8a9a5b,color:#10100e

流程: - struct scatterlist 陣列(或 sg_table):一串片段,每個 entry 是 page + offset + length(就是 P5-T02 bio_vec 的對應)。用 sg_init_table + sg_set_page 建立,或從 bio 的 bio_vec 轉成 scatterlist。 - dma_map_sg(dev, sglist, nents, direction):一次映射整串——每個 entry 得到一個 dma_addr 和長度(裝置用)。回傳「實際映射的 entry 數」(第 3 節的關鍵!)。 - 裝置用這些 dma_addr 一次 DMA 存取所有片段(對 NVMe:轉成 SGL/PRP,P5-T05)。 - dma_unmap_sg:傳輸完必須 unmap(常見誤區:忘記 unmap 造成 IOMMU 映射洩漏)。

dma_map_sg 是「streaming 映射」的 scatter-gather 版(回顧 P6-T01:streaming = 單次傳輸、需方向),所以一樣要指定方向、一樣要 unmap、一樣有 sync 問題(第 4 節)。

3. 致命陷阱:用回傳的映射數,不是原始數

這是 scatter-gather DMA 最容易出錯、最隱蔽的陷阱。

    INPUT["你給 dma_map_sg 一個有 N 個 entry 的 scatterlist
(例:N=5 個分散片段)"]
    INPUT --> MAP4["dma_map_sg(dev, sglist, 5, dir)"]
    MAP4 --> COALESCE["★ IOMMU 可能把相鄰片段『合併』★(第6節)

2 段連續的 DMA 位址
→ dma_map_sg 回傳 2(不是 5!)"]
    COALESCE --> WRONG6["✗ 錯誤:走訪時用『原始的 5』
→ 走過頭、讀到無效的 entry → 錯誤/當機"]
    COALESCE --> RIGHT6["✓ 正確:走訪時用『dma_map_sg 回傳的數(2)』
用 for_each_sg 配合回傳值走訪映射後的 entry"]
    NOTE27["★ 鐵則:映射後用『回傳的映射數』,不是傳入的原始 nents ★
(unmap 時則用『原始的 nents』—— 注意這個不對稱!)"]
    RIGHT6 --> NOTE27
    style COALESCE fill:#e8a33d,color:#10100e
    style WRONG6 fill:#c2603a,color:#f4ecd8
    style NOTE27 fill:#8a9a5b,color:#10100e

陷阱(常見誤區:dma_map_sg 後使用「原始 entry 數」而非「回傳的映射數」): - 你給 dma_map_sg 一個有 N 個 entry 的 scatterlist。 - IOMMU 可能把相鄰片段「合併」(第 6 節)——例如 5 個實體分散的片段,IOMMU 映射成 2 段連續的 DMA 位址。 - 所以 dma_map_sg 回傳 2,不是 5! - 走訪映射後的 entry,要用「回傳的映射數(2)」,用 for_each_sg 配合回傳值走訪。用原始的 5 會走過頭、讀到無效 entry → 錯誤/當機。

鐵則(驗收點:對含至少 3 段的 scatterlist 成功 dma_map_sg 並用回傳的映射數走訪):映射後用「回傳的映射數」,不是傳入的原始 nents。

注意一個不對稱:dma_unmap_sg 時則用原始的 nents(不是映射後的數)——因為 unmap 要還原整個原始的 scatterlist。這個「map 用回傳數走訪、unmap 用原始數」的不對稱很容易搞錯,要記牢。

這對你產品直接相關:你把 bio_vec 轉成 scatterlist、dma_map_sg,然後要把映射結果轉成 NVMe 的 SGL/PRP——這時必須用回傳的映射數走訪,否則你建的 SGL 會錯(多出無效 entry),裝置 DMA 就毀損資料。

4. 為何需要 dma_sync:cache 一致性

streaming 映射(含 dma_map_sg)有一個 coherent 映射沒有的問題:cache 一致性。當 CPU 和裝置交替存取同一塊 streaming 映射的記憶體,要用 dma_sync_* 維持一致。

flowchart TB
    PROBLEM8["問題根源:CPU 有 cache(P1-T02)
CPU 寫資料 → 可能還在 CPU cache 裡,沒寫回主記憶體
裝置 DMA 讀主記憶體 → 讀到『還沒被 CPU 寫回的舊值』"]
    PROBLEM8 --> COHERENT_NOTE["coherent 映射:底層保證一致(免 sync,P6-T01)"]
    PROBLEM8 --> STREAMING_NOTE["★ streaming 映射:不自動保證 ★
CPU 與裝置交替存取時,要手動 dma_sync_* 維持一致"]
    STREAMING_NOTE --> CASES["兩種方向的問題:
① CPU 寫 → 裝置讀:CPU 的寫要先『flush』到記憶體(裝置才讀得到新值)
② 裝置寫 → CPU 讀:CPU 的 cache 要先『invalidate』(才讀得到裝置寫的新值,不是 cache 舊值)"]
    style PROBLEM8 fill:#c2603a,color:#f4ecd8
    style STREAMING_NOTE fill:#e8a33d,color:#10100e
    style CASES fill:#6fa8b8,color:#10100e

問題根源(回顧 P1-T02 cache):CPU 有 cache——CPU 寫的資料可能還在 cache 裡、沒寫回主記憶體;裝置 DMA 讀主記憶體,會讀到「還沒被 CPU 寫回的舊值」。反之,裝置 DMA 寫了主記憶體,CPU 的 cache 裡可能還是舊值。

  • coherent 映射:底層保證一致,免 sync(回顧 P6-T01)。
  • streaming 映射:不自動保證——CPU 與裝置交替存取時,要手動 dma_sync_*。

兩種方向的問題: - CPU 寫 → 裝置讀:CPU 的寫要先 flush 到記憶體(裝置才讀得到新值)。 - 裝置寫 → CPU 讀:CPU 的 cache 要先 invalidate(才讀得到裝置寫的新值,不是 cache 舊值)。

dma_sync_* 就是做這些 cache 操作的工具,讓「交替存取 streaming 記憶體」的雙方看到正確的資料。

5. dma_sync 的正確順序

dma_sync_* 有「歸誰」的語意——for_cpu(交給 CPU)和 for_device(交還裝置),順序很重要。

flowchart TB
    MAPPED["一塊 streaming 映射的記憶體(映射期間『歸裝置』)"]
    MAPPED --> SYNC_CPU["① dma_sync_single_for_cpu(dev, dma_addr, size, dir)
『把記憶體交給 CPU』
→ invalidate CPU cache,確保 CPU 接下來讀到裝置寫的新值"]
    SYNC_CPU --> CPU_ACCESS["② CPU 存取這塊記憶體(讀/寫)
(此時記憶體『歸 CPU』,裝置不該碰)"]
    CPU_ACCESS --> SYNC_DEV["③ dma_sync_single_for_device(dev, dma_addr, size, dir)
『把記憶體交還裝置』
→ flush CPU cache,確保 CPU 的寫對裝置可見"]
    SYNC_DEV --> DEV_ACCESS["④ 裝置接著 DMA 這塊(此時『歸裝置』)"]
    NOTE28["★ 心智模型:streaming 映射的記憶體像『借還』★
for_cpu = CPU 借走(先讓 CPU 看到正確值)
for_device = 還給裝置(先讓裝置看到 CPU 的修改)
★ 借用期間,另一方不該存取 ★"]
    DEV_ACCESS --> NOTE28
    style SYNC_CPU fill:#6fa8b8,color:#10100e
    style SYNC_DEV fill:#e8a33d,color:#10100e
    style NOTE28 fill:#8a9a5b,color:#10100e

正確順序(驗收點:正確示範一次 dma_sync_single_for_cpu→CPU 存取→dma_sync_single_for_device 並說明理由): 1. dma_sync_single_for_cpu:「把記憶體交給 CPU」——invalidate CPU cache,確保 CPU 接下來讀到裝置寫的新值。 2. CPU 存取這塊記憶體(此時歸 CPU,裝置不該碰)。 3. dma_sync_single_for_device:「把記憶體交還裝置」——flush CPU cache,確保 CPU 的寫對裝置可見。 4. 裝置接著 DMA(此時歸裝置)。

心智模型:streaming 映射的記憶體像「借還」——for_cpu = CPU 借走(先讓 CPU 看到正確值)、for_device = 還給裝置(先讓裝置看到 CPU 的修改)。借用期間,另一方不該存取。

兩個常見誤區: - streaming 映射期間 CPU 直接讀寫卻不 dma_sync_*——CPU 讀到 stale 值、或裝置看到舊資料。要存取就先 sync。 - 映射後又改動 buffer 內容卻未重新 sync——改了要再 for_device 才讓裝置看到。

(注意:dma_map_sg 對應的是 dma_sync_sg_for_cpu/dma_sync_sg_for_device,同樣語意但對整串。)

最後解釋第 3 節那個「映射數變少」的原因——IOMMU 合併。這也預告 P6-T04 的 IOMMU。

IOMMU 合併(驗收點:解釋為何映射數可能少於原始 entry 數): - IOMMU(P6-T04)是裝置端的位址轉譯器,能把分散的實體片段,映射成裝置看到的「連續」DMA 位址。 - 所以 5 個實體分散的片段,經 IOMMU 可能對裝置呈現成 1~2 段連續的 DMA 位址 → dma_map_sg 回傳的映射數變少(第 3 節)。

好處:裝置看到連續位址,DMA 更簡單(不必處理那麼多段);對 NVMe,更少的 SGL/PRP entry → 更省。

這正是 P6-T01 鐵則「dma_addr_t 不是實體位址」的具體原因:IOMMU 轉譯後,裝置看到的 DMA 位址,和實體位址完全不同(實體分散 → DMA 連續)。你現在親眼看到「為什麼 dma_addr_t 不能當實體位址」——因為 IOMMU 在中間做了合併/轉譯。P6-T04 會深入 IOMMU 的轉譯與保護。

對你產品:有 IOMMU 時,你的 bio_vec 分散片段經 dma_map_sg 可能被合併成更少的連續 DMA 段,你據此(用回傳的映射數)建 NVMe 的 SGL——更省、更快。但你必須用回傳數走訪,否則出錯。

一句話總結:你的資料分散在多個片段(bio_vec),用 scatterlist + dma_map_sg 一次映射做 DMA（streaming 的 SG 版，對 NVMe 轉成 SGL/PRP）；兩個致命細節——走訪映射結果要用「回傳的映射數」（IOMMU 合併會讓數量變少，但 unmap 用原始 nents，不對稱），以及 streaming 映射上 CPU/裝置交替存取要用 dma_sync_*（for_cpu 借給 CPU → 存取 → for_device 還給裝置）維持 cache 一致性。IOMMU 把分散實體片段呈現成連續 DMA 視圖，正是 dma_addr_t ≠ 實體位址的具體原因。

常見誤區與踩雷提醒

誤區一:dma_map_sg 後使用「原始 entry 數」而非「回傳的映射數」。 IOMMU 合併後映射數可能變少。走訪映射結果用回傳數(for_each_sg 配回傳值);但 unmap 用原始 nents(不對稱,要記牢)。

誤區二:streaming 映射期間 CPU 直接讀寫卻不 dma_sync_*。 CPU 讀到 stale 值、或裝置看到舊資料。要存取就先 for_cpu,存取完 for_device 還給裝置。

誤區三:映射後又改動 buffer 內容卻未重新 sync。 改了要再 dma_sync_*_for_device 才讓裝置看到新內容。

誤區四:忘記 unmap 造成 IOMMU 映射洩漏。 dma_map_sg 後傳輸完必須 dma_unmap_sg(用原始 nents),否則 IOMMU 映射洩漏。

動手實作

環境:QEMU 虛擬機(實驗只在 VM)。

任務 A — dma_map_sg 與映射數(驗收點,核心) 建立一個含至少 3 段 buffer 的 scatterlist(sg_init_table + sg_set_page/sg_set_buf),dma_map_sg(dev, sg, 3, DMA_TO_DEVICE)。用 for_each_sg 配合回傳的映射數 走訪映射後的 entry(印出每段的 dma_addr 和長度)。驗收:對含至少 3 段的 scatterlist 成功 dma_map_sg 並用回傳的映射數(非原始數)走訪。 完成後 dma_unmap_sg(用原始 nents)。

任務 B — dma_sync 順序(驗收點) 對一塊 streaming 映射的 buffer,示範一次:dma_sync_single_for_cpu → CPU 存取(讀或寫)→ dma_sync_single_for_device 的順序。寫一段話說明每一步的理由。驗收:正確示範順序並說明理由(for_cpu 讓 CPU 看到裝置寫的新值;for_device 讓裝置看到 CPU 的修改)。

任務 C — 解釋 IOMMU 合併(驗收點) 寫一段話:為什麼 dma_map_sg 回傳的映射數可能少於你傳入的原始 entry 數?驗收:解釋(IOMMU 把分散的實體片段合併成連續的 DMA 視圖,所以映射後的段數變少)。

任務 D(連結)— 對應你的資料路徑 寫一兩句話:你產品的 bio_vec 分散片段,如何經 scatterlist → dma_map_sg → NVMe 的 SGL/PRP?走訪映射結果時要注意什麼?(提示:用回傳的映射數建 SGL,否則多出無效 entry。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 對含至少 3 段的 scatterlist 成功 dma_map_sg 並用回傳的映射數(非原始數)走訪。 2. ☐ 正確示範一次 dma_sync_single_for_cpu→CPU 存取→dma_sync_single_for_device 的順序並說明理由。 3. ☐ 解釋為何映射數可能少於原始 entry 數(IOMMU 合併)。

評分量表: - 60(及格):能用 dma_map_sg。 - 80(熟練):能正確處理映射數與 sync。 - 100(精通):能解釋 IOMMU 合併與 cache 一致性對 SG DMA 的完整影響。

延伸與銜接

  • 對應工作場景:直接對應——NVMe 的 PRP/SGL 與 bio_vec 的分散片段正是經 scatter-gather 映射做 DMA;這是你資料路徑的日常。
  • 這課餵給未來的(I/O 物件流動主線):P5-T02 bio_vec → 本課 scatterlist/dma_map_sg → P5-T05 SGL/PRP(已學)的 kernel 實作;dma_sync cache 一致性 → 回收 P1-T02;IOMMU 合併 → P6-T04 IOMMU(深入轉譯與保護)。
  • 下一步 → P6-T03 DMA 屏障與按門鈴(doorbell)的正確順序:你會把分散資料映射給裝置 DMA 了。下一課是 DMA 正確性最易出錯之處——把你 P3-T11 的「記憶體屏障命門」落實到 DMA:用 dma_wmb/dma_rmb 確保「描述子/資料對裝置可見」先於「按門鈴」(回顧 P5-T05 NVMe 提交流程的屏障)。漏一個屏障,裝置先看到門鈴、後看到描述子 → 讀到半寫資料 → 間歇性資料毀損,且極難重現。這正是你產品提交 NVMe 命令、處理完成項時的正確性核心。
