P3-T10 · 中斷與延後工作(hardirq / softirq / tasklet / workqueue / threaded IRQ)

一句話:中斷處理要「快進快出」——上半部(ISR)只做最緊急的、不可睡眠;耗時或會睡眠的重活(像你的 parity 計算、GPU 提交)必須延後到下半部,而其中只有 workqueue 能睡眠。選錯延後機制,系統死結或中斷延遲爆炸。

為什麼要先學這個(導讀)

這一課回到「中斷」這個 kernel 特有的維度(P3-T08 已經讓你見識到它讓同步變複雜),深入中斷處理的結構——而它直接決定你 I/O 完成路徑該怎麼寫。

核心概念是上半部/下半部(top half / bottom half)模型。當硬體中斷發生(例如 NVMe 完成一個 I/O),CPU 會跳去執行中斷處理常式(ISR,上半部)。但 ISR 有嚴格限制: - 在中斷 context,不可睡眠(回顧 P3-T08:不可 mutex、不可 GFP_KERNEL、不可任何會睡眠的事)。 - 要快:ISR 執行時,可能擋住其他中斷、增加系統延遲。所以 ISR 應該只做最緊急的事(例如確認中斷、記下「有事發生」),然後盡快返回。

那些「耗時的、或會睡眠的」工作怎麼辦?延後到下半部處理。kernel 有幾種下半部機制: - softirq:高頻、原子 context、不可睡眠。 - tasklet:建在 softirq 上,不可睡眠(已逐漸淘汰,新程式不該用)。 - workqueue:在行程 context 執行,可睡眠——能做耗時、會阻塞的工作。 - threaded IRQ:把中斷處理放到一個專屬核心執行緒裡(可睡眠)。

為什麼這對你是 scope: direct?因為這是你 I/O 完成路徑的核心抉擇:NVMe I/O 完成中斷後,你要做 parity 計算、提交給 GPU——這些是耗時、會睡眠的重活,絕對不能在 ISR(中斷 context)裡做。它們必須延後到可睡眠的下半部(workqueue 或 threaded IRQ)。選錯機制(例如想在 tasklet 裡睡眠)會死結;ISR 做太多會拖垮中斷延遲。這一課讓你選對。

開始之前(前置確認)

  • 依賴:P3-T08(中斷 context 不可睡眠、鎖的 context 規則)。也用到 P3-T07(GFP context)、P1-T06(中斷如何打斷執行)。
  • 自我檢測: 1. 你還記得 P3-T08 說「中斷 context 不可睡眠、不可用 mutex」嗎?這課的上半部就在中斷 context,下半部的 workqueue 則跳出中斷 context 變成可睡眠。 2. 你還記得 P3-T09 的 completion 嗎?它常和「下半部完成後通知」搭配。

核心內容

拆成這幾節:(1) 中斷與 ISR:快進快出 → (2) 上半部/下半部模型 → (3) softirq:高頻原子 → (4) tasklet:已淘汰 → (5) workqueue:可睡眠的下半部 → (6) 選型:你的 I/O 完成路徑,最後打通關。

1. 中斷與 ISR:為什麼要快進快出

硬體裝置(網卡、磁碟、NVMe SSD)需要通知 CPU「我有事了」(資料到了、I/O 完成了),靠的是硬體中斷(hardware interrupt, hardirq):

flowchart LR
    DEVICE["硬體裝置(如 NVMe)
完成一個 I/O"]
    IRQ["發出硬體中斷
通知 CPU"]
    CPU["CPU 暫停手邊工作,
跳去執行該中斷的 ISR
(中斷處理常式,上半部)"]
    DEVICE --> IRQ --> CPU
    NOTE["★ ISR 在『中斷 context』執行 ★
① 不可睡眠(P3-T08)
② 執行時可能擋住其他中斷、增加延遲
→ 必須快進快出"]
    CPU --> NOTE
    style CPU fill:#e8a33d,color:#10100e
    style NOTE fill:#c2603a,color:#f4ecd8

ISR(上半部)的兩個鐵律: - 不可睡眠(回顧 P3-T08):中斷 context 不能阻塞、不能讓出 CPU 去睡。所以不可 mutex_lock、不可 kmalloc(GFP_KERNEL)、不可任何會睡眠的事。 - 要快:ISR 執行時可能擋住其他中斷、增加整體延遲。ISR 應該只做最緊急的事(確認/應答中斷、記錄狀態、排入下半部),然後盡快返回。

常見誤區:ISR 內做大量工作而不延後——這會增加中斷延遲,影響整個系統的回應性。ISR 要短,重活延後。

2. 上半部/下半部模型:把工作分兩段

既然 ISR 要快又不能睡眠,但有些工作耗時或需要睡眠,解法是把中斷處理分兩段:

flowchart TB
    IRQ["硬體中斷發生"]
    IRQ --> TOP["上半部(top half = ISR):
★ 快、中斷 context、不可睡眠 ★
只做最緊急的:
確認中斷、記下『有事』、排入下半部
→ 盡快返回"]
    TOP --> SCHEDULE["排程一個下半部"]
    SCHEDULE --> BOTTOM["下半部(bottom half):
稍後執行耗時/可睡眠的工作
(實際處理資料、複雜邏輯)"]
    NOTE["分兩段的好處:
ISR 快速返回(不擋中斷),
重活在下半部從容處理(部分機制還可睡眠)"]
    BOTTOM --> NOTE
    style TOP fill:#e8a33d,color:#10100e
    style BOTTOM fill:#8a9a5b,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

模型: - 上半部(ISR):中斷一來立刻執行,快、不可睡眠,只做最緊急的事,然後排程一個下半部、盡快返回。 - 下半部:稍後執行真正的、耗時的處理。依機制不同,有些下半部還能睡眠(workqueue)。

這讓「中斷要快」和「處理要完整」兩個需求兼顧:ISR 快速應答硬體、返回;重活延後到下半部慢慢做。接下來看下半部的幾種機制,關鍵差異在「能不能睡眠」。

3. softirq:高頻、原子 context、不可睡眠

softirq(軟中斷) 是最底層的下半部機制,設計給高頻、效能關鍵的場景(例如網路、block I/O 的核心路徑)。

flowchart TB
    SOFTIRQ["softirq:最底層的下半部"]
    SOFTIRQ --> CHAR["特性:
① 高頻、低開銷(效能關鍵路徑用)
② 在『原子 context』執行 → ★ 不可睡眠 ★
③ 數量固定(kernel 預定義那幾種,一般 module 不自己加)"]
    CHAR --> WHO["誰用:網路收發、block layer(blk-mq 的完成處理部分)、計時器等核心子系統"]
    style SOFTIRQ fill:#e8a33d,color:#10100e
    style WHO fill:#6fa8b8,color:#10100e

特性: - 高頻、低開銷:適合效能關鍵、頻繁觸發的下半部。 - 原子 context、不可睡眠:雖然不是硬中斷 context,但 softirq 仍在「原子 context」執行,不可睡眠(不可 mutex、不可 GFP_KERNEL)。 - 數量固定:softirq 是 kernel 預定義的那幾種(網路、block、計時器等),一般 module 不自己新增 softirq——你會用上層的 tasklet 或 workqueue。

softirq 是 block layer(你的領域)I/O 完成處理的底層機制之一,但你寫 module 通常不直接寫 softirq,而是用建在它之上的機制或 workqueue。

4. tasklet:建在 softirq 上,但已淘汰

tasklet 是建立在 softirq 之上的下半部機制,曾經很常用,但現在已逐漸淘汰——這是一個重要的「現況」提醒:

flowchart TB
    TASKLET["tasklet:建在 softirq 上的下半部"]
    TASKLET --> CHAR2["特性:
① 也在原子 context → ★ 不可睡眠 ★(跟 softirq 一樣)
② 比 softirq 易用(動態建立,同一 tasklet 不會在多核並行)"]
    CHAR2 --> DEPRECATED["★ 但已逐漸淘汰 ★
新程式碼不該用 tasklet
→ 改用 workqueue,或(需原子的)用 BH workqueue 等替代"]
    style TASKLET fill:#c2603a,color:#f4ecd8
    style DEPRECATED fill:#e8a33d,color:#10100e

要點: - tasklet 也不可睡眠(在原子 context,跟 softirq 一樣)。 - 它已被視為過時——kernel 社群正在移除 tasklet,新程式碼不該用 tasklet(常見誤區:仍優先選 tasklet)。 - 替代:需要可睡眠 → 用 workqueue;需要原子的快速下半部 → 用其他現代機制(如 BH workqueue 等)。

這是一個「LDD3 等舊資料會教 tasklet,但現況已淘汰」的點——你看舊教材會看到 tasklet,但寫新 module 要用 workqueue。(呼應整個課程「舊書看概念、API 對照現況」的原則。)

5. workqueue:可睡眠的下半部(你的重活去處)

workqueue(工作佇列) 是最重要的下半部機制,因為它在行程 context 執行,所以可以睡眠——這正是你的耗時/阻塞重活的去處。

flowchart TB
    WORKQUEUE["workqueue:在『行程 context』執行的下半部"]
    WORKQUEUE --> CHAR3["★ 關鍵特性:可睡眠 ★
因為在行程 context(由 kernel 工作執行緒跑),
可以 mutex_lock、kmalloc(GFP_KERNEL)、
做耗時/阻塞的工作"]
    CHAR3 --> HOW["用法:
① 定義一個 work(INIT_WORK + 處理函式)
② 在 ISR(上半部)裡 schedule_work() 排入
③ kernel 的工作執行緒稍後在行程 context 執行你的處理函式"]
    HOW --> THREADED["相關:threaded IRQ(request_threaded_irq)
把中斷處理直接放到一個專屬核心執行緒(可睡眠)
→ 另一種『把中斷重活放到可睡眠 context』的方式"]
    style CHAR3 fill:#8a9a5b,color:#10100e
    style HOW fill:#6fa8b8,color:#10100e
    style THREADED fill:#e8a33d,color:#10100e

關鍵特性與用法: - 可睡眠:workqueue 的工作由 kernel 的工作執行緒(在行程 context)執行,所以可以 mutex_lock、kmalloc(GFP_KERNEL)、做耗時或阻塞的事。這是它和 softirq/tasklet 的根本差異(那些不可睡眠)。 - 用法:定義一個 work(用 INIT_WORK 綁定處理函式)→ 在 ISR(上半部)裡用 schedule_work() 把它排入 → kernel 工作執行緒稍後在行程 context 執行你的處理函式。 - threaded IRQ(request_threaded_irq):另一種方式——把中斷處理直接放到一個專屬的核心執行緒裡執行(也在可睡眠 context)。適合「中斷處理本身就需要睡眠/較重」的驅動。

這就是你 I/O 完成路徑的關鍵:NVMe I/O 完成中斷的 ISR(上半部)只做最緊急的(確認完成、記錄),然後 schedule_work 把「parity 計算、GPU 提交」這些重活排入 workqueue,在可睡眠的行程 context 從容處理(可以等 GPU、可以配記憶體)。

把你的 NVMe 完成路徑「上半部 vs 下半部」的分工畫清楚:

flowchart TB
    NVMEIRQ["NVMe 發出 I/O 完成中斷"]
    NVMEIRQ --> TH["上半部 ISR(中斷 context,不可睡眠):
確認/應答中斷、記下哪個 I/O 完成、schedule_work、返回(快)"]
    TH --> BH["下半部 workqueue(行程 context,可睡眠):"]
    BH --> P1["parity 計算 / 提交給 GPU(可能耗時)"]
    P1 --> P2["wait_for_completion 等 GPU 算完(P3-T09,可睡眠)"]
    P2 --> P3["完成後續(更新狀態、釋放物件)"]
    NOTE4["★ 重活全在下半部(可睡眠)★;ISR 只做最緊急的
→ 中斷延遲短、且不違反『中斷 context 不可睡眠』"]
    BH --> NOTE4

6. 選型:你的 I/O 完成路徑該怎麼分配

把所有機制整合成選型,並落到你的具體場景:

flowchart TB
    Q1{"這段工作需要睡眠嗎?
(等 I/O、等 GPU、kmalloc(GFP_KERNEL)、mutex...)"}
    Q1 -->|"需要睡眠"| WQ["★ 用 workqueue(或 threaded IRQ)★
在行程 context、可睡眠
→ 你的 parity 計算、GPU 提交放這裡"]
    Q1 -->|"不需睡眠、要快"| Q2{"在 ISR 裡(最緊急的)?"}
    Q2 -->|"是,最緊急"| TOPHALF["放上半部 ISR:確認中斷、記錄、排下半部"]
    Q2 -->|"不睡眠但可延後的快速處理"| SOFTIRQ_PATH["softirq(核心子系統)/ 現代原子下半部機制
(★ 不要用已淘汰的 tasklet ★)"]
    style WQ fill:#8a9a5b,color:#10100e
    style TOPHALF fill:#e8a33d,color:#10100e
    style SOFTIRQ_PATH fill:#6fa8b8,color:#10100e

你的 NVMe I/O 完成路徑的典型分配: - 上半部(ISR):NVMe 中斷一來,只做最緊急的——確認/應答中斷、記錄「哪個 I/O 完成了」、把後續處理排入下半部。快、不睡眠。 - 下半部(workqueue):parity 計算、提交給 GPU、等 GPU 完成——這些會睡眠/耗時的重活,放 workqueue(可睡眠的行程 context)。可搭配 P3-T09 的 completion 等 GPU 算完。

選型鐵則: - 要睡眠/耗時 → workqueue 或 threaded IRQ(可睡眠)。 - 最緊急、不睡眠 → 上半部 ISR。 - 快速、不睡眠、可延後 → softirq(核心子系統)/現代原子下半部;別用 tasklet(已淘汰)。

選錯的後果(常見誤區):在 ISR 或 softirq/tasklet(不可睡眠)裡做會睡眠的事(等 GPU、GFP_KERNEL)→ 死結或當機;ISR 做太多 → 中斷延遲爆炸,拖垮系統。(驗收點:正確回答「tasklet/softirq 能否睡眠」=否、「workqueue 能否睡眠」=是。)

    IRQ["硬體中斷(如 NVMe I/O 完成)"]
    IRQ --> TOPHALF["上半部 ISR:★ 快、中斷 context、不可睡眠 ★

    TOPHALF --> BOTTOM["下半部:延後處理,機制差在『能否睡眠』"]
    BOTTOM --> SOFTIRQ2["softirq:高頻原子、不可睡眠(核心子系統用)"]
    BOTTOM --> TASKLET2["tasklet:不可睡眠、★已淘汰,新程式別用★"]
    BOTTOM --> WQ2["★ workqueue:行程 context、可睡眠 ★

    WQ2 --> YOURS["★ 你的 I/O 完成:ISR 只記錄+排程,

    style WQ2 fill:#8a9a5b,color:#10100e

一句話總結:中斷處理分上半部(ISR,快、中斷 context、不可睡眠,只做最緊急的)和下半部(延後處理);下半部機制差在能否睡眠——softirq/tasklet 不可睡眠(tasklet 已淘汰)、workqueue 在行程 context 可睡眠;你的 NVMe I/O 完成路徑該讓 ISR 只記錄+排程,把會睡眠的 parity 計算/GPU 提交放進 workqueue,否則死結或中斷延遲爆炸。

常見誤區與踩雷提醒

誤區一:在中斷 context(含 softirq/tasklet)睡眠或呼叫會睡眠的 API。 這些是原子/不可睡眠 context,睡眠是違法的(會死結/當機)。要睡眠的工作放 workqueue(行程 context)。

誤區二:ISR 內做大量工作而不延後。 增加中斷延遲、影響系統回應。ISR 只做最緊急的,重活延後到下半部。

誤區三:仍優先選 tasklet。 tasklet 已逐漸淘汰,新程式碼應用 workqueue(可睡眠)或現代的原子下半部機制(BH workqueue 等)。

誤區四:workqueue 與 tasklet 的「可否睡眠」混淆。 workqueue 在行程 context 可睡眠;tasklet/softirq 在原子 context 不可睡眠。這是選型的核心依據。

動手實作

環境:QEMU 虛擬機。實驗只在 VM。

任務 A — workqueue 執行可睡眠工作(驗收點) 寫一個 module,定義一個 work(INIT_WORK 綁一個處理函式),在 module init 裡(或模擬的觸發點)用 schedule_work() 排入。處理函式裡放一個 msleep(100)(模擬會睡眠的工作),pr_info 印出執行訊息。驗證:工作在行程 context 執行、msleep 不會造成崩潰。驗收:workqueue 成功在行程 context 執行含 msleep 的工作且不崩潰。

任務 B — 回答 context 規則(驗收點,核心) 寫下並回答: 1. 「tasklet / softirq 中能否睡眠?」→ 否,為什麼?(原子 context。) 2. 「workqueue 中能否睡眠?」→ 是,為什麼?(行程 context。) 驗收:兩題都答對並能說明。

任務 C — 說明為何 ISR 要短(驗收點) 寫一句話:為什麼 ISR(上半部)要盡量短、把重活延後?驗收:能說明(ISR 在中斷 context、執行時擋其他中斷增加延遲;且不可睡眠)。

任務 D(連結)— 設計你的 I/O 完成路徑 寫一兩句話:NVMe I/O 完成後,你要做 parity 計算和 GPU 提交(會睡眠)。這些該放上半部還是下半部?用什麼機制?(提示:會睡眠 → workqueue/threaded IRQ;ISR 只做記錄+排程。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 成功用 workqueue 在行程 context 執行一段含 msleep 的工作且不崩潰。 2. ☐ 正確回答「tasklet/softirq 中能否睡眠」(否)與「workqueue 中能否睡眠」(是)。 3. ☐ 說明為何 ISR 要盡量短、把重活延後。

評分量表: - 60(及格):能用 workqueue。 - 80(熟練):能正確區分各下半部機制的 context。 - 100(精通):能依「是否需睡眠、頻率、延遲要求」為 I/O 完成處理選對機制。

延伸與銜接

  • 對應工作場景:直接對應——NVMe I/O 完成中斷後,parity 計算/GPU 提交等重活必須延後到可睡眠 context(workqueue/threaded IRQ),選錯會死結或拖垮中斷延遲。
  • 這課餵給未來的(你的並行主線):上半部/下半部、context 限制 → P5 NVMe 驅動的中斷處理、P7 parity/GPU 的延後提交;workqueue + completion(回收 P3-T09)→ 等 GPU 完成;這是 P1-T08→P1-T09→P3-T08→本課 並行主線的延續。
  • 下一步 → P3-T11 memory barrier 與 Linux Kernel Memory Model(LKMM):你已經掌握 kernel 的同步與中斷。下一課回到你那條「記憶體順序」主線(P1-T03→P1-T10→本課),把 P1-T10 建立的「重排會發生」直覺,變成 kernel 裡的實際工具:smp_mb/smp_wmb/smp_rmb、smp_load_acquire/smp_store_release、READ_ONCE/WRITE_ONCE,以及 LKMM。這是 lock-free、RCU,以及你 DMA 正確性的根——描述子/資料必須在按 doorbell 前對 NVMe 裝置可見,否則裝置讀到舊資料導致資料毀損。
