P3-T04 · module 進階(EXPORT_SYMBOL、模組參數、模組堆疊、簽章)

一句話:真實的產品很少是單一 module——它們互相呼叫對方的函式(用 EXPORT_SYMBOL_GPL 匯出)、接收載入時的參數(用 module_param 調行為)、有載入順序的相依。這一課讓你的 module 從「孤立的 hello-world」變成「能協作、可配置的真實元件」。

為什麼要先學這個(導讀)

P3-T03 你寫了第一個孤立的 module。但真實世界——包括你的產品——的 module 不是孤立的:

  • 多個 module 協作:你的產品可能由幾個 module 組成,一個提供共用功能、其他呼叫它。這需要 module 匯出符號(把自己的函式公開給別的 module 用)。
  • 可配置:你常需要在載入 module 時調整它的行為(例如設定佇列深度、debug 等級)。這用模組參數——insmod mod.ko queue_depth=64 這樣傳值。
  • 有相依:如果 module B 用了 module A 的函式,那 A 必須先載入。這是模組相依,kernel 用 depmod/modprobe 管理。

為什麼這對你是 scope: direct?因為產品常由多個協作 module 組成(例如核心邏輯 + 各種策略模組),而模組參數是調整產品行為的常見手段(運維時不重編就能調佇列深度、開關 debug)。理解符號匯出與相依,你才能設計多 module 的產品架構;理解模組參數,你才能讓產品可配置。

這一課也會碰到模組簽章——現代 kernel 可要求 module 有有效簽章才能載入(安全機制),這跟你產品的部署環境有關。

開始之前(前置確認)

  • 依賴:P3-T03(你會寫、編、載入單一 module)。
  • 自我檢測: 1. 你還記得 P3-T03 的 MODULE_LICENSE("GPL") 和「GPL-only 符號」嗎?這課的 EXPORT_SYMBOL_GPL 就是製造 GPL-only 符號的那一端。 2. 你還記得 P3-T02 的 depmod、/lib/modules、Module.symvers 嗎?這課深入模組相依。
  • 環境:QEMU 虛擬機。所有載入只在 VM 裡。

核心內容

拆成這幾節:(1) EXPORT_SYMBOL:把函式公開給別的 module → (2) GPL vs 非 GPL 匯出 → (3) 模組參數 module_param → (4) 模組相依與載入順序 → (5) Module.symvers 與符號版本 → (6) 模組簽章,最後打通關。

1. EXPORT_SYMBOL:把函式公開給別的 module 用

預設情況下,一個 module 裡的函式只有它自己看得到——別的 module 不能呼叫。要讓 module A 的函式能被 module B 呼叫,A 必須用 EXPORT_SYMBOL(或 EXPORT_SYMBOL_GPL)把那個函式「匯出」到核心的符號表。

flowchart TB
    subgraph modA["module A(提供者)"]
        FUNC["int do_work(int x) { ... }
EXPORT_SYMBOL_GPL(do_work);
← 把 do_work 公開到核心符號表"]
    end
    SYMTABLE["核心符號表
(記錄哪些符號可被其他 module 使用)"]
    subgraph modB["module B(使用者)"]
        CALL["extern int do_work(int);
... do_work(42); ...
← 呼叫 A 匯出的函式"]
    end
    FUNC -->|"匯出到"| SYMTABLE
    SYMTABLE -->|"B 載入時,核心解析這個符號"| CALL
    style FUNC fill:#8a9a5b,color:#10100e
    style SYMTABLE fill:#e8a33d,color:#10100e
    style CALL fill:#6fa8b8,color:#10100e

運作: - module A 用 EXPORT_SYMBOL_GPL(do_work) 把 do_work 公開到核心符號表。 - module B 宣告 extern 後直接呼叫 do_work。 - B 載入時,核心解析這個符號——在符號表裡找到 A 匯出的 do_work,把 B 的呼叫連到 A 的實作。

關鍵:這要求 A 先載入(否則 B 載入時找不到 do_work 符號,載入失敗)。這就是下面要講的「模組相依與載入順序」。

連到你的產品:這正是「多 module 協作」的機制。你可以把產品的共用功能放在一個 module 裡匯出,其他策略/驅動 module 呼叫它——模組化、可分別更新。

把「多 module 堆疊」的樣子畫出來——你產品可能就是這種分層結構:

flowchart TB
    subgraph stack["模組堆疊(module stacking)"]
        TOP2["策略/驅動 module B、C(上層)
呼叫 A 匯出的符號"]
        CORE2["核心共用 module A(下層)
EXPORT_SYMBOL_GPL 匯出共用函式"]
        TOP2 --> CORE2
    end
    LOAD["載入順序:必須先 A 後 B/C
(B/C 相依於 A 的符號;modprobe 自動依 depmod 排序)"]
    stack --> LOAD
    style CORE2 fill:#8a9a5b,color:#10100e
    style TOP2 fill:#6fa8b8,color:#10100e
    style LOAD fill:#e8a33d,color:#10100e

2. EXPORT_SYMBOL vs EXPORT_SYMBOL_GPL:授權的關卡

匯出符號有兩個版本,差別在誰能使用這個符號——這直接連到 P3-T03 的 MODULE_LICENSE:

flowchart TB
    subgraph versions["兩種匯出"]
        PLAIN["EXPORT_SYMBOL(foo)
→ 任何 module 都能用 foo
(不論授權)"]
        GPL["EXPORT_SYMBOL_GPL(foo)
→ ★ 只有宣告 GPL 授權的 module 能用 ★
(MODULE_LICENSE("GPL"))"]
    end
    NOTE["很多核心核心功能用 EXPORT_SYMBOL_GPL 匯出
→ 非 GPL module 不能用它們
(這是 P3-T03 說『非 GPL 無法用 GPL-only 符號』的另一端)"]
    GPL --> NOTE
    style PLAIN fill:#6fa8b8,color:#10100e
    style GPL fill:#e8a33d,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

  • EXPORT_SYMBOL:任何 module 都能用這個符號。
  • EXPORT_SYMBOL_GPL:只有宣告 GPL 授權的 module(MODULE_LICENSE("GPL"))能用。這是核心對「使用某些深層功能」設的授權關卡——很多核心核心 API 都是 GPL-only 匯出的。

常見誤區:EXPORT_SYMBOL 與 EXPORT_SYMBOL_GPL 混用導致符號無法使用——如果 A 用 EXPORT_SYMBOL_GPL 匯出,而 B 不是 GPL module,B 就用不了(載入時符號解析失敗)。設計多 module 產品時,要想清楚授權與匯出方式的搭配。一般在 GPL 專案內部,用 EXPORT_SYMBOL_GPL 是常見選擇。

3. 模組參數:載入時調行為

模組參數讓你在載入 module 時傳入值,調整它的行為,不必重新編譯。用 module_param 宣告:

static int queue_depth = 32;            // 預設值
module_param(queue_depth, int, 0644);   // 宣告為參數(型別 int,sysfs 權限 0644)
MODULE_PARM_DESC(queue_depth, "I/O 佇列深度");   // 說明

static int __init my_init(void) {
    pr_info("queue_depth = %d\n", queue_depth);   // 用參數
    return 0;
}

載入時傳值:insmod mymod.ko queue_depth=64

flowchart LR
    DECLARE["module_param(queue_depth, int, 0644)
+ 預設值 32"]
    INSMOD["insmod mymod.ko queue_depth=64
(載入時傳入)"]
    READ["module 內 queue_depth == 64
(若不傳則用預設 32)"]
    DECLARE --> INSMOD --> READ
    SYSFS["0644 = 也出現在 /sys/module/mymod/parameters/
(可在執行時讀,部分可寫)"]
    READ --> SYSFS
    style INSMOD fill:#e8a33d,color:#10100e
    style READ fill:#8a9a5b,color:#10100e

要點: - module_param(名稱, 型別, 權限):宣告一個參數。型別可以是 int、charp(字串)等;還有 module_param_array 給陣列。 - MODULE_PARM_DESC:給參數寫說明(modinfo 看得到)。 - 載入時 insmod mod.ko 參數名=值 傳入;不傳則用程式裡的預設值。 - 那個權限(0644)讓參數出現在 /sys/module/<模組>/parameters/,可在執行時查看(部分可寫)。

常見誤區:用了 MODULE_PARM(LDD3 書裡的舊寫法,已淘汰)——要用 module_param。(這呼應 spec 提醒:LDD3 是經典但 API 釘在舊版,概念對、但具體 API 要對照新版。)

連到你的產品:佇列深度、debug 等級、各種策略開關——這些都適合做成模組參數,讓運維能不重編就調整產品行為。

4. 模組相依與載入順序

第 1 節提到:若 B 用 A 的符號,A 必須先載入。這就是模組相依。

flowchart TB
    DEPEND["module B 用了 module A 匯出的符號
→ B 相依於 A"]
    DEPEND --> WRONG["✗ 先 insmod B:
核心找不到 A 的符號 → 載入失敗
(unknown symbol)"]
    DEPEND --> RIGHT["✓ 先 insmod A,再 insmod B:
B 載入時 A 的符號已在符號表 → 成功"]
    MODPROBE["modprobe B:
自動讀相依資訊,先載 A 再載 B
(比手動 insmod 聰明)"]
    RIGHT --> MODPROBE
    style WRONG fill:#c2603a,color:#f4ecd8
    style RIGHT fill:#8a9a5b,color:#10100e
    style MODPROBE fill:#e8a33d,color:#10100e

兩種載入方式的差別: - insmod:直接載入指定的 .ko,不處理相依。所以你得自己按正確順序(先 A 後 B),否則先載 B 會失敗(找不到符號)。 - modprobe:自動處理相依——它讀 depmod 算出的相依資訊(回顧 P3-T02),先載入被依賴的 module(A)再載入 B。

depmod 在 make modules_install 時跑(P3-T02),它掃描所有模組的符號,算出「誰依賴誰」,記錄下來。modprobe 靠這個資訊自動排序載入。

常見誤區:載入順序錯誤(被依賴者要先載)——用 insmod 時要注意順序,或乾脆用 modprobe 讓它自動處理。模組堆疊(module stacking) 就是這種「一層疊一層」的相依結構(例如你的策略 module 疊在核心 module 上)。

5. Module.symvers 與符號版本

一個你會遇到的相依細節:符號版本。kernel 為了確保「module 用的符號,跟它編譯時的 kernel 版本相符」,給每個匯出符號算一個版本碼,記在 Module.symvers 裡。

flowchart TB
    SYMVERS["Module.symvers:
記錄每個匯出符號的『版本碼』
(反映符號的介面簽名)"]
    SYMVERS --> CHECK["載入 module 時,核心檢查:
module 期望的符號版本
== 核心提供的符號版本?"]
    CHECK --> OK["相符 → 載入"]
    CHECK --> FAIL["不符 → ★ disagrees about version of symbol ★
拒絕載入
(module 是給別的 kernel 編的)"]
    style SYMVERS fill:#6fa8b8,color:#10100e
    style FAIL fill:#c2603a,color:#f4ecd8

用意:防止你把「給 kernel 版本 X 編的 module」載入到「kernel 版本 Y」——如果符號的介面變了(參數、型別不同),硬載會崩潰。符號版本碼讓核心在載入時就擋下不相容的 module。

常見誤區:Module.symvers 不一致導致符號版本不符(disagrees about version of symbol)——通常發生在「module 跟正在跑的 kernel 不是一起編的」。解法:用對應的 kernel 標頭/build 環境重編你的 module。(這也呼應 P1-T11/P3-T02:module 要跟它要載入的 kernel 用同一套 build 環境編。)

6. 模組簽章:現代 kernel 的安全關卡

最後一個主題:模組簽章(module signing)。現代 kernel 可設定 CONFIG_MODULE_SIG,要求 module 帶有有效的數位簽章才能載入——這是防止載入未授權/被竄改 module 的安全機制。

flowchart TB
    SIGN["CONFIG_MODULE_SIG(模組簽章機制)"]
    SIGN --> HOW["module 用一把私鑰簽章,
核心用對應的公鑰驗證"]
    HOW --> ENFORCE{"CONFIG_MODULE_SIG_FORCE?"}
    ENFORCE -->|"開啟(強制)"| FORCE["未簽章/簽章無效的 module
★ 拒絕載入 ★"]
    ENFORCE -->|"未強制"| WARN["未簽章 module 仍可載入,
但會 taint 核心(回顧 P3-T03)"]
    style SIGN fill:#6fa8b8,color:#10100e
    style FORCE fill:#c2603a,color:#f4ecd8
    style WARN fill:#e8a33d,color:#10100e

運作: - module 用一把私鑰簽章,核心用對應的公鑰驗證。 - 若 CONFIG_MODULE_SIG_FORCE 開啟(強制),未簽章或簽章無效的 module 拒絕載入。 - 若未強制,未簽章 module 仍可載入,但會 taint 核心(回顧 P3-T03 的 taint)。

連到你的產品:如果你產品要部署到「啟用了強制模組簽章」的環境(例如某些 secure boot 系統),你的 module 就必須正確簽章。開發時在 QEMU 裡通常不強制,但理解這個機制,你才能應對部署環境的要求。

打通關:把 module 進階收攏成一個心智模型

flowchart TB
    SINGLE["從孤立 module(P3-T03)→ 能協作、可配置的真實元件"]
    SINGLE --> EXPORT["EXPORT_SYMBOL(_GPL):把函式公開給別的 module
→ 多 module 協作(你產品的架構)"]
    EXPORT --> GPL["_GPL 版只給 GPL module 用
(別混用 → 符號解析失敗)"]
    SINGLE --> PARAM["module_param:載入時傳值調行為(不重編)
→ 佇列深度/debug 等級(你產品的可配置性)"]
    EXPORT --> DEPEND["相依:用符號者(B)需被依賴者(A)先載
insmod 要自己排序;modprobe 自動處理(靠 depmod)"]
    DEPEND --> SYMVERS["Module.symvers 符號版本:
擋下『給別的 kernel 編的 module』"]
    SINGLE --> SIGN["模組簽章 CONFIG_MODULE_SIG:

    style EXPORT fill:#e8a33d,color:#10100e
    style PARAM fill:#8a9a5b,color:#10100e
    style SIGN fill:#6fa8b8,color:#10100e

一句話總結:真實產品的 module 互相協作(用 EXPORT_SYMBOL_GPL 匯出函式、按相依順序載入,modprobe 自動排序)、可配置(用 module_param 載入時調行為)、受版本與簽章把關;掌握這些,你的 module 就從孤立的 hello-world,變成能組成多 module 產品、可運維配置的真實元件。

常見誤區與踩雷提醒

誤區一:用了 MODULE_PARM(LDD3 舊寫法,已淘汰)。 要用 module_param。LDD3 概念正確但 API 釘在舊版,具體 API 對照新版文件。

誤區二:EXPORT_SYMBOL 與 EXPORT_SYMBOL_GPL 混用導致符號無法使用。 _GPL 匯出的符號只有 GPL module 能用。非 GPL module 用它會符號解析失敗。設計時想清楚授權與匯出搭配。

誤區三:載入順序錯誤(被依賴者要先載)。 用 insmod 時要先載 A 再載 B(B 用 A 的符號);或用 modprobe 自動處理相依。

誤區四:Module.symvers 不一致導致符號版本不符。 disagrees about version of symbol 通常因 module 跟運行的 kernel 不是一起編的。用對應 kernel build 環境重編 module。

動手實作

環境:QEMU 虛擬機。所有載入只在 VM 裡。

任務 A — 跨 module 匯出/使用符號(驗收點) 寫兩個 module: - module A:定義一個函式(如 int my_add(int,int)),用 EXPORT_SYMBOL_GPL(my_add) 匯出。 - module B:extern 宣告後呼叫 my_add,在 dmesg 印出結果。 （兩者都 MODULE_LICENSE("GPL")。)在 QEMU 裡: - 先 insmod B → 觀察失敗(unknown symbol my_add)。 - 先 insmod A,再 insmod B → 成功,dmesg 看到結果。 驗收:B 成功呼叫 A 的函式;先載 B 失敗、先載 A 再載 B 成功,能解釋相依。

任務 B — 模組參數(驗收點) 給一個 module 加一個 int 參數(如 count),用 module_param 宣告、MODULE_PARM_DESC 說明。insmod mod.ko count=5,在 module 內 pr_info 印出讀到的值。驗收:傳入整數參數且 module 內讀到正確值(5)。 也試 insmod 不傳參數,確認用預設值;用 modinfo mod.ko 看參數說明。

任務 C — 解釋 EXPORT_SYMBOL 差異(驗收點) 用一句話說出 EXPORT_SYMBOL 與 EXPORT_SYMBOL_GPL 的差異。驗收:能說出差異(後者只給 GPL module 用)。

任務 D(觀察)— modprobe 自動處理相依 若環境允許(把 A、B 裝到 /lib/modules 並 depmod),試 modprobe B,觀察它自動先載入 A。對比任務 A 手動 insmod 要自己排序。寫一句話:modprobe 比 insmod 多做了什麼?

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ module B 成功呼叫 module A 匯出的函式並在 dmesg 看到結果;先載 B 失敗、先載 A 再載 B 成功,能解釋相依。 2. ☐ insmod 時傳入整數參數且 module 內讀到正確值。 3. ☐ 說出 EXPORT_SYMBOL 與 EXPORT_SYMBOL_GPL 差異。

評分量表: - 60(及格):能傳參數。 - 80(熟練):能跨 module 匯出/使用符號。 - 100(精通):能解釋符號版本與簽章機制。
