P0-T08 · 前處理器與巨集

一句話:巨集是「在編譯之前發生的純文字尋找與取代」。它沒有型別、不懂運算,只會盲目地貼字串——它的威力與陷阱,全都來自這個「盲目」。看懂巨集,你才讀得懂滿是巨集的 kernel 原始碼。

為什麼要先學這個(導讀)

回想 P0-T01 的第一階段:前處理(preprocessing)。當時我們說它「把 #include 貼上、把 #define 的縮寫展開」。這一課就是深入那個階段——因為 kernel 把巨集用得鋪天蓋地。

為什麼 kernel 這麼愛巨集?兩個原因:

  1. 零成本:巨集是純文字替換,沒有函式呼叫的開銷(不必跳轉、不必建 stack frame、不必傳參數)。對效能極度敏感的核心程式碼,這很有吸引力。
  2. 不管型別 = 泛型:因為巨集只是「盲目貼字串」,它不在乎你給的是 int、struct 還是指標。所以一個巨集可以同時作用在各種型別上,達成 C 函式做不到的「泛型」效果。

代價是:正因為巨集只是「盲目貼字串」,它有一堆反直覺的陷阱。最有名的 kernel 巨集 container_of(P0-T04 提過的 offsetof 就是它的基石,Phase 2 會深入)就是一團看起來像天書的巨集。如果你不先理解巨集「純文字替換」的本質,那些巨集對你就是亂碼。這課替你打底。

1. 物件式巨集:給常數取名字

#define MAX_USERS 100

前處理器在編譯之前,把原始碼裡所有的 MAX_USERS 文字,替換成 100。

關鍵理解:它不是「變數」。它沒有型別、不佔記憶體。編譯器真正看到的程式碼裡,根本沒有 MAX_USERS 這個詞——只有 100。

flowchart LR
    SRC["你的原始碼
if (n < MAX_USERS)"]
    PP["前處理器:
把所有 MAX_USERS
替換成 100"]
    OUT["編譯器看到的
if (n < 100)
(沒有 MAX_USERS 這個詞)"]
    SRC --> PP --> OUT
    style PP fill:#e8a33d,color:#10100e
    style OUT fill:#8a9a5b,color:#10100e

比喻:像 Word 的「全部取代」。你按下取代,文件裡所有 MAX_USERS 都變成 100,然後才送去印刷(編譯)。印刷機從沒看過 MAX_USERS 這個詞。

2. 函式式巨集:看起來像函式,其實是貼字串

#define SQUARE(x) ((x) * (x))
int a = SQUARE(5);   // 展開成 ((5) * (5)) = 25

它看起來像函式呼叫,但前處理器只是把 SQUARE(5) 這段文字,換成 ((5) * (5))。沒有真的「呼叫」任何東西、沒有跳轉、沒有 stack frame。

下圖點出巨集和函式最關鍵的差異——發生的時間點不同:

    subgraph macro["巨集:編譯【之前】就被文字替換掉"]
        M1["原始碼 SQUARE(5)"] -->|"前處理:純文字取代"| M2["((5)*(5))"] -->|"編譯器只看到這個"| M3["機器碼
(沒有任何函式呼叫)"]
    end
    subgraph func["函式:編譯後,執行【當下】才呼叫"]
        F1["原始碼 square(5)"] -->|"編譯成"| F2["一個 call 指令"] -->|"執行時"| F3["跳進函式、建 frame、回傳"]
    end
    style M2 fill:#e8a33d,color:#10100e
    style F2 fill:#6fa8b8,color:#10100e

注意那堆括號 ((x) * (x))——它們不是裝飾,是保命的。第 4 節會讓你看到不加會死得多慘。

3. gcc -E:巨集的 X 光機

當你被一個複雜巨集搞糊塗,最好的工具就是親眼看它展開成什麼:

gcc -E yourfile.c | grep -A2 你關心的部分
# 或直接看整個展開後的檔案:
gcc -E yourfile.c -o yourfile.i

-E 讓 gcc 只做到前處理就停(回顧 P0-T01 的四階段)。展開後的檔案裡,所有巨集都被攤平成最終的文字。

flowchart LR
    SRC["含巨集的 .c"]
    E["gcc -E"]
    I[".i:所有巨集已展開成
最終的純文字
(你能親眼驗證它變成什麼)"]
    SRC --> E --> I
    style E fill:#e8a33d,color:#10100e
    style I fill:#8a9a5b,color:#10100e

記住這招:之後讀 kernel 那些複雜巨集(container_of 等),gcc -E 是你的 X 光機,讓你看穿巨集的真面目。

4. 陷阱一:括號——被運算優先序咬

#define SQUARE(x) x * x        // 沒括號的危險版本
int r = SQUARE(1 + 2);          // 你以為是 9

因為純文字替換,SQUARE(1 + 2) 變成 1 + 2 * 1 + 2。乘法優先,算出來是 5,不是 9!

flowchart TB
    A["SQUARE(1 + 2)
用 #define SQUARE(x) x * x"]
    B["純文字替換:x → 1 + 2
變成 1 + 2 * 1 + 2"]
    C["運算優先序:* 先算
1 + (2*1) + 2 = 5
✗ 不是預期的 9"]
    A --> B --> C
    A2["正解:#define SQUARE(x) ((x) * (x))"]
    B2["替換:((1+2) * (1+2))"]
    C2["= 3 * 3 = 9 ✓"]
    A2 --> B2 --> C2
    style C fill:#c2603a,color:#f4ecd8
    style C2 fill:#8a9a5b,color:#10100e

正解是每個參數、整體都包括號:#define SQUARE(x) ((x) * (x))。展開成 ((1+2) * (1+2)) = 9。這就是為什麼前面的巨集括號那麼多——它們在防止「替換後的文字」被運算優先序拆錯。

5. 陷阱二:多敘述巨集——用 do { } while(0) 包

當巨集要做不只一件事:

// 壞的寫法
#define LOG_AND_INC(x)  printf("%d\n", x); x++

用在 if 裡會出事:

if (debug)
    LOG_AND_INC(count);
// 展開成:
if (debug)
    printf("%d\n", count); count++;   // count++ 跑出了 if 的控制範圍!


flowchart TB
    A["if (debug) LOG_AND_INC(count);"]
    B["展開:
if (debug)
  printf(...); ← if 只管這一句
count++; ← 變成『無論如何都執行』"]
    C["後果:即使 debug 為假,
count++ 照樣執行
✗ 邏輯錯誤"]
    A --> B --> C
    style C fill:#c2603a,color:#f4ecd8

if 在沒有大括號時只管到第一個敘述,所以 count++ 漏了出去、變成無條件執行。標準解法是用 do { } while(0) 把多個敘述包成「語法上的一個敘述」:

#define LOG_AND_INC(x)  do { printf("%d\n", x); (x)++; } while(0)

為什麼是 do...while(0) 而不是直接用 { }? 因為 do{}while(0) 整體是「一個需要分號結尾的敘述」,能完美融入 if/else 語法。如果只用 { },那麼 if (c) {...}; else ... 裡,大括號後面那個分號會被當成一個空敘述,把 if 和 else 拆斷,造成編譯錯誤。do{}while(0) 巧妙避開這點。這個慣用法在 kernel 巨集裡無所不在。

6. 陷阱三:副作用——參數被求值多次

#define SQUARE(x) ((x) * (x))    // 即使括號都對的正確版本
int i = 3;
int r = SQUARE(i++);   // 展開成 ((i++) * (i++)),i 被自增兩次!

因為 x 在巨集本體裡出現兩次,替換後 i++ 就出現兩次、執行兩次。結果與你預期(算 3 的平方)完全不同,而且 i 最後變成 5 而非 4。

flowchart TB
    A["SQUARE(i++) where i=3"]
    B["x 在本體出現 2 次
→ 替換成 ((i++) * (i++))"]
    C["i++ 執行兩次:
i 從 3 變 4 變 5
乘出來的值也不是 9"]
    A --> B --> C
    CONTRAST["對比:若 SQUARE 是真函式,
參數 i++ 只求值一次
(傳進去的是 3,i 變 4)"]
    C -.“這就是巨集 vs 函式的關鍵差異”.-> CONTRAST
    style C fill:#c2603a,color:#f4ecd8
    style CONTRAST fill:#6fa8b8,color:#10100e

這是巨集 vs 函式的關鍵差異:函式的參數只求值一次(算好值才傳進去);巨集的參數在展開後出現幾次,就求值幾次。規矩:別把有副作用的運算式(i++、會改變狀態的函式呼叫)傳進巨集。

7. #(字串化)與 ##(token 黏接)

兩個特殊的巨集運算子,你要認得:

  • #x(字串化 stringize):把參數變成字串字面值。 c #define STR(x) #x STR(hello) // 變成 "hello"
  • ##(token 黏接 paste):把兩個 token 黏成一個。 c #define MAKE(name) my_##name MAKE(func) // 變成 my_func

flowchart LR
    subgraph stringize["# 字串化"]
        S1["STR(hello)"] --> S2[""hello"
(變成字串)"]
    end
    subgraph paste["## 黏接"]
        P1["my_##name
(name=func)"] --> P2["my_func
(黏成一個識別字)"]
    end
    style S2 fill:#6fa8b8,color:#10100e
    style P2 fill:#8a9a5b,color:#10100e

kernel 常用 ## 來自動產生變數名 / 函式名(例如一系列命名規律的函式)。你現在先知道它們存在、大概做什麼;之後在 kernel 看到 ## 就不會愣住。

打通關:把巨集收攏成一個心智模型

巨集的一切——威力與所有陷阱——都源自同一個本質:它是編譯前的盲目文字替換。

一句話總結:記住「巨集是盲目文字替換」這一句,三大陷阱你就能自己推導出來——括號是防替換後被拆錯、do{}while(0) 是防多敘述漏出、別傳副作用是防多次求值。而 gcc -E 永遠是你看穿任何複雜巨集(包括 kernel 那些)的 X 光機。

常見誤區與踩雷提醒

誤區一:巨集參數沒包好括號,被運算優先序咬。 #define SQUARE(x) x*x 遇上 SQUARE(1+2) 算出 5 不是 9。正解:每個參數、整體都包括號 ((x)*(x))。

誤區二:多敘述巨集沒用 do{}while(0) 包。 在 if 後面會讓第二個敘述「漏出去」變成無條件執行。多敘述巨集一律用 do{}while(0)。

誤區三:巨集參數有副作用,被求值多次。 SQUARE(i++) 會讓 i++ 執行兩次。別把 i++、函式呼叫等有副作用的運算式傳進巨集。

誤區四:把巨集當成有型別檢查的函式。 巨集沒有型別概念,傳什麼進去它都照貼。這帶來泛型的便利,但也意味著編譯器不會幫你擋「型別用錯」的錯誤。複雜邏輯若不需要泛型/零成本,用真函式更安全。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 製造括號陷阱,再用 gcc -E 看穿它

#define BAD_SQ(x) x * x
#define GOOD_SQ(x) ((x) * (x))
int main(void) {
    printf("%d\n", BAD_SQ(1 + 2));   // 印出 5(被咬)
    printf("%d\n", GOOD_SQ(1 + 2));  // 印出 9(正確)
    return 0;
}

然後 gcc -E 看這兩行展開成什麼,親眼確認 BAD_SQ(1+2) 變成了 1 + 2 * 1 + 2。

任務 B — 寫一個安全的 MAX,並思考副作用

#define MAX(a, b) ((a) > (b) ? (a) : (b))

測試 MAX(1 + 2, 3) 回傳 3。然後思考並寫下(不必真的執行造成困惑):為什麼 MAX(x++, y) 是危險的?(提示:a 在本體出現兩次。)

任務 C — do-while(0) 包裝 把一個含兩條敘述的巨集(例如「印出再自增」)用 do{}while(0) 包好,寫一個 if (cond) MACRO(); else printf("no"); 確認它能正確編譯、且第二條敘述不會漏出 if。再試試不包(直接用 {})會不會編譯錯誤,體會為什麼要 do{}while(0)。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 寫出 MAX(a,b) 並對 MAX(1+2, 3) 回傳 3,且能解釋 MAX(x++, y) 為何危險(參數多次求值)。 2. ☐ 把一個含兩條敘述的巨集用 do{}while(0) 包裝,使其在 if(c) MACRO(); else ...; 中正確編譯。 3. ☐ 能口述 #(字串化)與 ##(黏接)各做什麼。

評分量表: - 60(及格):能用巨集。 - 80(熟練):能辨識並避開巨集的三大陷阱(括號、多敘述、副作用)。 - 100(精通):能用 gcc -E 拆解 container_of 這類複雜巨集的展開,並解釋其運作。
