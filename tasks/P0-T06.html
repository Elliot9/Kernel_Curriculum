P0-T06 · 手動記憶體管理與常見記憶體錯誤

一句話:沒有垃圾回收器替你收尾。你向系統借的每一塊記憶體,都要親手還;還早了、還兩次、忘了還,都會出事。這一課教你借與還的規矩,以及四種會咬人的錯誤各長什麼樣——因為在 kernel 裡,這些錯誤不會給你 segfault 的溫柔警告,而是直接 panic 或默默損毀資料。

為什麼要先學這個(導讀)

這是你和高階語言正式分手的時刻。

PHP、JS 有垃圾回收器(GC):你建立物件、用完不管,GC 會在背後判斷「沒人用了」並自動回收。你從沒寫過「釋放記憶體」這種程式碼,因為從來不需要——記憶體管理對你是隱形的。

C 把這個責任完整、赤裸裸地交還給你。你用 malloc 向系統借一塊 heap 記憶體(回顧 P0-T05,heap 就是這塊由你掌控生命週期的區),就必須在用完後用 free 還回去。沒有人會幫你。而一旦你管錯了,後果不是 JS 那種溫和的 undefined,而是程式崩潰、記憶體洩漏、或最陰險的——時好時壞、極難重現的詭異 bug。

為什麼第一階段就要痛苦地面對這個?因為 kernel 是這個世界裡記憶體管理最嚴苛的地方。kernel 沒有 GC,沒有使用者態那層保護網。在 kernel 裡,一個 use-after-free 不會只是讓你的程式崩潰——它可能默默損毀別的子系統的資料、或讓整台機器當掉。Phase 3 你會學到 KASAN 這個專門抓 kernel 記憶體錯誤的工具,而這一課,就是要先讓你親手製造這些錯誤、親眼看它們的樣子、學會用工具抓它們——你才知道 KASAN 在抓什麼、為什麼非抓不可。

開始之前(前置確認)

  • 依賴:P0-T05(你已懂 heap 是動態配置區、其生命週期由你掌控、stack 變數短命)。
  • 自我檢測: 1. 你能說出「heap 和 stack 的記憶體,生命週期有什麼不同」嗎?(stack 隨函式回傳消失;heap 活到你 free 為止) 2. 你還記得 P0-T02 的「野指標」和 P0-T05 的「懸空指標」嗎?這課的 use-after-free 與它們同源。
  • 需要工具:valgrind(sudo apt install valgrind)。

核心內容

拆成這幾節:(1) 借與還:malloc/free 的四條規矩 → (2) free 完設 NULL 為何關鍵 → (3)~(6) 四種記憶體錯誤逐一拆解(UAF / double-free / leak / overflow)→ (7) valgrind 怎麼抓,最後打通關。

1. 借與還:malloc 與 free 的四條規矩

#include <stdlib.h>

int *p = malloc(sizeof(int) * 10);   // ① 向系統借 10 個 int 的空間
if (p == NULL) {                      // ② 借不到要檢查!
    // 處理失敗(記憶體不足)
    return -1;
}
p[0] = 42;                            // 用它
// ... 用完 ...
free(p);                              // ③ 還回去
p = NULL;                             // ④ 還完立刻把指標設 NULL

四條規矩,缺一不可:

每個 malloc 都要有

free(p); p = NULL;

比喻:malloc 像跟圖書館借書,free 像還書。借了不還(洩漏),館藏愈來愈少;還了又跑去翻那本書(use-after-free),但書已經在別人手上、內容變了;同一本書還兩次(double-free),櫃台的紀錄會錯亂。

比喻的極限:圖書館的書是實體、唯一的;記憶體更像「一塊塊可重複出借的空間」——你 free 之後,系統很快會把同一塊空間借給別人。所以 use-after-free 的危險不只是「書不見了」,而是「你以為還在翻自己的書,其實正在讀寫別人的書」——可能讀到別人的資料,或寫壞別人的資料。

2. 「free 完設 NULL」為什麼是保命習慣

規矩④看起來多餘,其實它一次預防了兩種最常見的錯誤。原理是:free(NULL) 是 C 標準保證的「合法無動作」,而對 NULL 解參考會「明確崩潰」(易抓)而非「默默讀垃圾」(難抓)。

flowchart TB
    FREE["free(p) 之後"]
    FREE --> CHOICE{"有沒有 p = NULL?"}
    CHOICE -->|"沒設 NULL(危險)"| BAD["p 仍指向那塊已歸還的記憶體
(這種指標叫 dangling)"]
    BAD --> BAD1["不小心 *p → use-after-free
(默默讀寫別人的記憶體,難抓)"]
    BAD --> BAD2["不小心再 free(p) → double-free
(破壞 heap 管理結構)"]
    CHOICE -->|"有設 NULL(安全)"| GOOD["p = NULL"]
    GOOD --> GOOD1["不小心 *p → 對 NULL 解參考
立刻明確崩潰(易抓,當場現形)"]
    GOOD --> GOOD2["不小心再 free(p) → free(NULL)
C 保證:合法無動作,平安"]
    style BAD fill:#c2603a,color:#f4ecd8
    style GOOD fill:#8a9a5b,color:#10100e

所以「free(p); p = NULL;」要練成肌肉記憶——它把兩種難抓的潛在錯誤,轉化成「要嘛安全無事、要嘛當場明確崩潰」。

3. 錯誤一:use-after-free(釋放後使用)

free(p);
printf("%d", *p);   // 錯:p 指向的記憶體已歸還,內容不再屬於你

free 之後,那塊記憶體可能被系統拿去借給程式的其他部分。你再去讀寫它:

flowchart TB
    T1["free(p):那塊記憶體還給系統
(但 p 還指著那個位址)"]
    T2["系統把同一塊記憶體
借給程式別處的 q"]
    T3["你執行 *p:讀/寫那塊
= 讀到 q 的資料,或寫壞 q 的資料"]
    T4["q 的資料莫名其妙變了
→ 遠處出現詭異 bug,難以追到源頭"]
    T1 --> T2 --> T3 --> T4
    style T1 fill:#e8a33d,color:#10100e
    style T3 fill:#c2603a,color:#f4ecd8
    style T4 fill:#c2603a,color:#f4ecd8

這就是為什麼規矩④要「free 完設 NULL」——之後若不小心用到 *p,因為 p 是 NULL,會立刻明確崩潰(好抓),而不是默默讀到別人的資料(難抓)。

4. 錯誤二:double-free(重複釋放)

free(p);
free(p);   // 錯:同一塊還兩次,破壞 heap 的內部管理結構

heap 內部有一套「管理結構」記錄哪些區塊借出、哪些空閒(回想 P0-T05 提到的、以及你在 P0-T12 會親手做的配置器)。同一塊 free 兩次,會把這套管理結構弄亂,可能導致後續的 malloc/free 行為錯亂,甚至被攻擊者利用。

同樣地,若第一次 free 後把 p 設 NULL,第二次就變成 free(NULL)——C 標準保證它是合法無動作,災難自動避免。

5. 錯誤三:memory leak(記憶體洩漏)

int *p = malloc(100);
p = malloc(200);   // 錯:第一塊的位址被覆蓋,再也 free 不到 → 永久洩漏

你 malloc 了卻沒 free,或把「唯一指向它的指標」覆蓋掉,那塊記憶體就永遠回不來了——沒有任何指標指向它,你連 free 它的機會都沒有。

flowchart TB
    A["int *p = malloc(100)
p 指向 100-byte 區塊 A"]
    B["p = malloc(200)
p 改指向新區塊 B"]
    C["區塊 A 還在記憶體裡佔著空間
但沒有任何指標指向它
→ 永遠 free 不到 = 洩漏"]
    A --> B --> C
    style A fill:#8a9a5b,color:#10100e
    style C fill:#c2603a,color:#f4ecd8

短程式看不出問題,但長時間執行的程式(伺服器、或……作業系統 kernel)會愈洩愈多,記憶體佔用持續上升,最終耗盡記憶體導致系統出問題。這是 kernel 開發特別在意洩漏的原因:kernel 一開機就跑到關機,一點一滴的洩漏會累積成災難。

6. 錯誤四:buffer overflow(緩衝區溢位)

int *p = malloc(sizeof(int) * 5);   // 借 5 個 int(索引 0~4 合法)
p[5] = 99;   // 錯:索引 5 已超出,踩到隔壁的記憶體

7. valgrind:你的記憶體錯誤偵測器

你不必只靠肉眼抓這些錯誤。valgrind 這個工具會在程式執行時監控每一次記憶體存取,幫你抓出洩漏、越界、use-after-free,並告訴你發生在哪一行。

    B --> C["valgrind 監控每次記憶體存取"]
    C --> D1["洩漏:漏了幾 bytes、

    C --> D2["非法存取:讀/寫了

gcc -g prog.c -o prog
valgrind --leak-check=full ./prog

這是 Phase 3 的 KASAN 在使用者態的對應物——先在這裡學會看這類報告(哪一行、什麼錯、漏多少),之後看 kernel 的 KASAN 報告就不會陌生。兩者的精神一致:讓記憶體錯誤「現形」,而不是潛伏成難追的 bug。

打通關:把記憶體管理收攏成一個心智模型

把這課收攏成「一塊 heap 記憶體的生命週期」這一條主線:

flowchart TB
    BORROW["malloc 借入
(算對大小 + 檢查 NULL)"]
    USE["使用
(只在 [0, 大小) 範圍內讀寫
← 越界 = overflow)"]
    RETURN["free 還回
(每個 malloc 對應一個 free
← 不還 = leak,還兩次 = double-free)"]
    NULLIFY["p = NULL
(之後誤用會明確崩潰,

    BORROW --> USE --> RETURN --> NULLIFY

(kernel 裡對應 KASAN)"]
    GUARD -.監控整條生命週期.-> USE

一句話總結:每一塊 heap 記憶體都有「借入→使用→歸還」的生命週期,四種錯誤分別對應在這條線的不同點上犯規,而「free 完設 NULL」+「valgrind 把關」是你的兩道防線。 把這條生命週期內化,你就不是「背四種錯誤」,而是理解它們為何發生、發生在哪。kernel 開發的記憶體紀律,就是把這條線守得滴水不漏。

常見誤區與踩雷提醒

誤區一:free 後沒把指標設 NULL。 這是 use-after-free 和 double-free 的共同溫床。養成「free(p); p = NULL;」的肌肉記憶——free(NULL) 合法無動作,所以設 NULL 後即使再 free 也安全。

誤區二:只 malloc 不 free,或弄丟指標。 每個 malloc 心裡都要立刻想「它的 free 在哪?」。特別小心在迴圈裡 malloc、或用新位址覆蓋舊指標(舊的就洩漏了)。

誤區三:malloc 的大小算錯。 忘了 sizeof、或字串忘了給 \0 留位置(要 malloc(len + 1),回顧 P0-T03)。算錯就是埋下越界的種子。

誤區四:釋放非 malloc 來的指標。 只能 free 你從 malloc/calloc/realloc 拿到的指標。free 一個指向 stack 變數、或指向某塊記憶體中間(而非開頭)的指標,是未定義行為。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。需要 valgrind。

任務 A — 故意製造錯誤,再用 valgrind 抓出來 寫一支「有問題」的程式,刻意包含一個洩漏和一個 use-after-free:

#include <stdlib.h>
#include <stdio.h>
int main(void) {
    int *leak = malloc(sizeof(int) * 10);   // 故意:之後不 free → 洩漏
    leak[0] = 1;

    int *p = malloc(sizeof(int));
    *p = 5;
    free(p);
    printf("%d\n", *p);   // 故意:use-after-free(free 後還讀 *p)

    return 0;   // leak 始終沒被 free
}

用 valgrind --leak-check=full ./prog 跑,讀它的報告:它會指出「Invalid read(use-after-free)」發生在哪一行,以及「definitely lost: 40 bytes」(那 10 個 int)是在哪一行 malloc 的。對照報告裡的行號,確認你能看懂它在說什麼。

任務 B — 修正,直到 valgrind 乾淨 把上面的程式改對:移除 use-after-free(在 free 前印,或乾脆 free(p); p=NULL; 後不再用)、補上 free(leak)。重跑 valgrind,目標是看到:

All heap blocks were freed -- no leaks are possible
ERROR SUMMARY: 0 errors from 0 contexts

任務 C — 體會 double-free 與 NULL 的保護 寫一段 free(p); free(p);(在 VM 裡),觀察它崩潰或被 valgrind 報 double-free。然後改成 free(p); p=NULL; free(p);,觀察它不再出錯(因為第二次是 free(NULL))。寫一句話說明規矩④如何救了你。

驗收與自我評分

驗收檢核點(量化,逐項通過): 提供一支含 1 處 leak + 1 處 use-after-free 的程式—— 1. ☐ 用 valgrind --leak-check=full 跑出報告,指出兩處的根因與行號。 2. ☐ 修正後,valgrind 報 0 errors 且 all heap blocks were freed。 3. ☐ 能示範 free(p); p=NULL; 如何讓後續誤觸的 free(p) 變安全。

評分量表: - 60(及格):能在 valgrind 協助下修好錯誤。 - 80(熟練):能在讀程式碼時,不靠工具就預判哪裡會有記憶體錯誤,並說出是四種中的哪一種。 - 100(精通):能說明這些錯誤在 kernel 中為何更致命(無使用者態保護、可能默默損毀他人資料),並把 valgrind 對應到 KASAN。
