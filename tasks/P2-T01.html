P2-T01 · Big-O 與資料結構選型思維

一句話:Big-O 告訴你「當資料量變大,操作會慢多少」。但 kernel 的選型不只看 Big-O——它還看常數因子、cache 行為、最壞情況。理解這套完整的判斷,你才懂為什麼 kernel 在不同子系統用不同的資料結構。

為什麼要先學這個(導讀)

歡迎來到 Phase 2。前兩個階段你打下了 C 與系統的底子;這個階段的任務是讓你能讀懂 kernel 原始碼裡那些無所不在的資料結構——list_head、container_of、紅黑樹、XArray、bitmap。讀完 Phase 2,這些 kernel code 裡反覆出現的東西,對你會「一眼可讀」。

但在認識具體的資料結構之前,要先建立一個判斷框架:怎麼評估一個資料結構的好壞?怎麼決定什麼場景該用什麼?這就是這一課——複雜度分析(Big-O)與選型思維。

為什麼這個框架重要?因為 kernel 不是隨便挑資料結構的。它在 I/O 排程器用紅黑樹、在 page cache 用 XArray、在很多地方用侵入式鏈結串列——每個選擇背後都有理由。理解這些理由,需要你會問:這個操作多快?資料量大時會怎樣?最壞情況如何?有沒有隱藏成本?

不過有個關鍵警告貫穿這一課:Big-O 不是全部。新手常犯的錯是「只看漸進複雜度,選了理論上最快的,結果實際更慢」——因為忽略了常數因子和 cache 行為(回顧 P1-T02)。kernel 工程師對這點極度敏感。這一課會教你完整的判斷,不只是背複雜度表。

開始之前(前置確認)

  • 依賴:P1-T07(你已具備基本的演算法思維,手算過排程)。
  • 自我檢測: 1. 你還記得 P0-T03 陣列是連續記憶體、P0-T12 你手刻過動態陣列和鏈結串列嗎?這課要分析它們的複雜度。 2. 你還記得 P1-T02 的 cache、cache line、為何資料佈局影響效能嗎?這課會告訴你「為什麼 Big-O 不是全部」。

核心內容

拆成這幾節:(1) Big-O 的直覺 → (2) Big-O / Ω / Θ → (3) 常見結構的操作複雜度 → (4) 攤銷分析:動態陣列擴容 → (5) Big-O 的陷阱一:常數因子與 cache → (6) 陷阱二:平均 vs 最壞 → (7) 據情境選型,最後打通關。

1. Big-O 的直覺:資料量變大時,會慢多少?

Big-O 回答一個問題:當輸入資料量 n 變大,這個操作要做的工作量,以什麼速度增長? 它不關心精確的時間(那會因機器而異),只關心「增長的趨勢」。

flowchart TB
    subgraph growth["常見的增長趨勢(n 變大時)"]
        O1["O(1) 常數
不管 n 多大,工作量固定
(像:查陣列第 5 個元素)"]
        OLOGN["O(log n) 對數
n 翻倍,工作只多一點
(像:平衡樹查找)"]
        ON["O(n) 線性
n 翻倍,工作翻倍
(像:走訪整個串列找東西)"]
        ONLOGN["O(n log n)
(像:好的排序演算法)"]
        ON2["O(n²) 平方
n 翻倍,工作變四倍
(像:雙層迴圈兩兩比較)"]
    end
    style O1 fill:#8a9a5b,color:#10100e
    style OLOGN fill:#6fa8b8,color:#10100e
    style ON fill:#e8a33d,color:#10100e
    style ON2 fill:#c2603a,color:#f4ecd8

直覺感受差異:假設 n = 100 萬。 - O(1):不管多大,1 個動作。 - O(log n):約 20 個動作(log₂ 一百萬 ≈ 20)。 - O(n):一百萬個動作。 - O(n²):一兆個動作(慢到不可行)。

重點:Big-O 是「趨勢」,它丟掉常數和低階項——O(2n + 100) 簡化成 O(n),因為 n 夠大時,那個 2 和 100 相對不重要。這個簡化很有用(讓你看清增長趨勢),但也藏著陷阱(第 5 節:那個被丟掉的常數,在小 n 時其實很重要)。

2. Big-O、Ω、Θ:上界、下界、緊界

嚴格一點,有三個符號,描述不同的「界」:

flowchart TB
    BIGO["O(f(n)) 上界
『最多這麼慢』
(成長不超過 f(n) 的速度)"]
    OMEGA["Ω(f(n)) 下界
『至少這麼慢』
(成長不低於 f(n) 的速度)"]
    THETA["Θ(f(n)) 緊界
『就是這麼快慢』
(上下界都是 f(n),增長率確定)"]
    BIGO -.“最常用,因為我們最關心『最壞會多慢』”.-> THETA
    style BIGO fill:#e8a33d,color:#10100e
    style OMEGA fill:#6fa8b8,color:#10100e
    style THETA fill:#8a9a5b,color:#10100e

實務上最常用 Big-O,因為我們通常最關心「最壞情況會多慢」(上界)。Ω 講下界(最好情況也至少這麼慢),Θ 講「上下界一致,增長率確定」。你日常溝通說「這是 O(n) 的」,通常意思就是「它線性增長」。你不需要糾結這三者的數學細節,記住 Big-O = 上界 = 最關心的「最壞多慢」就夠了。

3. 常見結構的操作複雜度

這是 Phase 2 的「地圖」——你即將深入學的每個結構,在這裡先看它們的複雜度全貌。針對「查找、插入、刪除」三種操作:

幾個關鍵對比,先記在心裡(後面各課會深入): - 陣列:按索引查找超快(O(1)),但中間插入/刪除慢(O(n),要搬移)。 - 鏈結串列:查找慢(O(n)),但「已知位置」的插入/刪除快(O(1),只改指標)——這正是 P2-T02 kernel list_head 的賣點。 - 雜湊表:平均超快(O(1)),但最壞會退化(O(n))——這個「平均 vs 最壞」的差異是第 6 節的重點。 - 平衡樹:都是 O(log n),不快不慢但穩定有保證,且能有序走訪——這是 kernel 在需要排序的場景(I/O 排程器)選它的原因。

4. 攤銷分析:動態陣列擴容為什麼「平均」是 O(1)

這是一個重要又微妙的概念,而且你已經實作過它(P0-T12 的動態陣列)。問題:動態陣列 push 一個元素,複雜度是多少?

flowchart TB
    Q["動態陣列 push 一個元素:複雜度?"]
    Q --> CASE1["大多數時候:還有空間
→ 直接放,O(1)"]
    Q --> CASE2["偶爾:滿了要擴容
→ 配置兩倍空間 + 複製全部舊元素
→ 這一次是 O(n)!"]
    CASE1 --> AMORT
    CASE2 --> AMORT["攤銷分析:把『偶爾的昂貴』
平攤到『大量的便宜』上"]
    style CASE2 fill:#c2603a,color:#f4ecd8
    style AMORT fill:#e8a33d,color:#10100e

單次 push 最壞是 O(n)(剛好遇到擴容,要複製全部)。但這很罕見——只在容量翻倍的那一刻發生。攤銷分析(amortized analysis) 問的是:「連續做 n 次 push,總成本除以 n,平均每次多少?」

flowchart LR
    A["push n 個元素
用『翻倍擴容』策略"]
    B["擴容只發生在
容量 = 1,2,4,8,...,n 時
(約 log n 次)"]
    C["所有擴容的複製成本總和
= 1+2+4+...+n ≈ 2n
(等比級數,總和約是最後一項的兩倍)"]
    D["總成本 ≈ n 次放入 + 2n 次複製 = 3n
÷ n = 平均每次 O(1)"]
    A --> B --> C --> D
    style C fill:#6fa8b8,color:#10100e
    style D fill:#8a9a5b,color:#10100e

結論:動態陣列 push 的「攤銷複雜度」是 O(1),即使單次最壞是 O(n)。關鍵數學在第三步:翻倍擴容讓所有複製的總成本是等比級數(1+2+4+...+n ≈ 2n),平攤到 n 次 push 上就是常數。這就是為什麼翻倍擴容是好策略(回顧 P0-T12 當時就提過這點)——它讓昂貴的擴容夠罕見,平攤後便宜。

忽略攤銷是常見誤區:只看「單次最壞 O(n)」會以為動態陣列很慢,其實它平攤後跟「直接放」一樣快。

5. 陷阱一:Big-O 不是全部——常數因子與 cache

這是 kernel 選型最重要、也最反新手直覺的一點,呼應 P1-T02 的 cache 知識。

Big-O 丟掉了常數因子。但在實際機器上,常數因子和 cache 行為常常主宰小到中等資料量的效能。一個經典例子:

flowchart TB
    SCENARIO["小 N 時:O(n) 陣列 vs O(log n) 平衡樹,誰快?"]
    SCENARIO --> ARR["陣列(O(n) 查找):
連續記憶體,完美契合 cache line(P1-T02)
走訪時 cache 命中率高,常數因子極小"]
    SCENARIO --> TREE["平衡樹(O(log n) 查找):
節點散落各處(各自 malloc),
每跳一個節點可能 cache miss
常數因子大"]
    ARR --> RESULT["小 N 時,陣列的『O(n) 但 cache 友善』
常常勝過樹的『O(log n) 但 cache 不友善』
→ 漸進複雜度輸,實際更快"]
    TREE --> RESULT
    style ARR fill:#8a9a5b,color:#10100e
    style TREE fill:#c2603a,color:#f4ecd8
    style RESULT fill:#e8a33d,color:#10100e

為什麼?陣列是連續記憶體,走訪它時,cache line 一次載入多個元素(回顧 P1-T02),命中率高,實際很快。樹的節點各自配置、散落各處,每跳一個節點可能就是一次 cache miss(慢數十倍)。所以對小 n,「O(n) 但 cache 友善的陣列」常常贏過「O(log n) 但 cache 不友善的樹」——漸進複雜度說樹快,但實際陣列快。

這就是為什麼 kernel 工程師選型不只看 Big-O。他們會問:資料量通常多大?在不在 cache?常數因子如何?有時為了 cache 友善,寧可用漸進複雜度「較差」的結構。「只看 Big-O 就選理論最快的」是新手最常見的選型錯誤。

6. 陷阱二:平均 vs 最壞——別把「平均」當「保證」

另一個關鍵區分:很多結構的「平均」和「最壞」複雜度差很多,選型時要看你的場景在意哪個。

    subgraph hash["雜湊表(P2-T04)"]
        AVG["平均:O(1)
(雜湊均勻分布時)"]
        WORST["最壞:O(n)
(所有 key 都碰撞到同一桶,
退化成一條鏈結串列)"]
    end
    NOTE["對『一般情況』雜湊表超快;
但對『不能容忍偶爾很慢』的場景
(如即時系統、對抗惡意輸入),
O(n) 的最壞可能不可接受
→ 這時平衡樹的『保證 O(log n)』更安全"]
    hash --> NOTE
    style AVG fill:#8a9a5b,color:#10100e
    style WORST fill:#c2603a,color:#f4ecd8
    style NOTE fill:#e8a33d,color:#10100e

雜湊表平均 O(1),但最壞 O(n)(碰撞嚴重時,退化成一條鏈)。對大多數情況,平均 O(1) 很棒;但若你的場景不能容忍偶爾的 O(n)(例如延遲敏感、或可能面對惡意構造的輸入),那雜湊表的最壞情況可能是問題,此時「保證 O(log n)」的平衡樹反而更可靠。

這就是為什麼 kernel 有些地方用紅黑樹而非雜湊表——它要的是「保證的最壞情況」,不是「通常很快但偶爾很慢」。把「平均」當「最壞」是常見誤區:選型時要清楚你的場景能不能承受最壞情況。

7. 據情境選型:兩個練習

把前面所有判斷綜合起來,看兩個具體情境怎麼選(這也是驗收點):

flowchart TB
    subgraph s1["情境A:頻繁在『中間』插入/刪除"]
        A_TRY["陣列?中間插入要搬移後面全部 → O(n),不好"]
        A_PICK["✓ 鏈結串列:已知位置插入/刪除 O(1)(改指標)
(= kernel list_head 的場景)"]
    end
    subgraph s2["情境B:頻繁『隨機查找』"]
        B_TRY["鏈結串列?查找要一個個走 → O(n),不好"]
        B_PICK["✓ 雜湊表(平均 O(1))
或平衡樹(保證 O(log n)、可有序走訪)
看是否需要『有序』與『最壞保證』"]
    end
    style A_PICK fill:#8a9a5b,color:#10100e
    style B_PICK fill:#8a9a5b,color:#10100e

選型的思考流程: - 情境 A(頻繁中間插入/刪除):陣列要搬移(O(n)),所以選鏈結串列(已知位置 O(1))。這正是 kernel 為何到處用 list_head(P2-T02)。 - 情境 B(頻繁隨機查找):鏈結串列要逐一走(O(n)),所以選雜湊表(平均 O(1))或平衡樹(O(log n) 但有保證、可排序)。選哪個,取決於你是否需要「有序」和「最壞保證」。

選型沒有單一答案,要綜合:操作模式(查找多還是插入多?)、資料量(小 n 看常數因子)、是否需要有序、能否容忍最壞情況、cache 友善度。 這就是 kernel 在不同子系統用不同結構的原因——它針對每個場景的特性做了權衡。

一句話總結:Big-O 描述資料量變大時的增長趨勢,是選型的起點;但真正的選型還要看攤銷、常數因子與 cache 行為(小 N 時陣列常勝樹)、以及平均與最壞的差別——kernel 正是綜合這些,才在不同子系統選了不同的資料結構。學會這套完整判斷,你就能理解 Phase 2 接下來每個結構『為什麼在那裡』。

常見誤區與踩雷提醒

誤區一(最重要):只看漸進複雜度,忽略常數因子與 cache。 小到中等 n 時,cache 友善的陣列(O(n))常勝過 cache 不友善的樹(O(log n))。kernel 選型對此極敏感。別「只看 Big-O 選理論最快的」。

誤區二:把「平均」當「最壞」。 雜湊表平均 O(1) 但最壞 O(n)。對不能容忍偶爾很慢的場景,要看最壞情況,可能該選有保證的平衡樹。

誤區三:忽略攤銷。 動態陣列單次 push 最壞 O(n),但攤銷 O(1)。只看單次最壞會誤判它很慢。

誤區四:以為「複雜度低 = 一定快」。 複雜度是趨勢,不是絕對時間。實際快慢還受常數、cache、資料量、硬體影響。複雜度是重要參考,不是唯一標準。

動手實作

環境:紙筆 + 任何程式語言,安全,無系統風險。

任務 A — 製作複雜度對照表(驗收點) 做一張表,列出陣列、鏈結串列、雜湊表、平衡樹在「查找、插入、刪除」的平均與最壞複雜度。(提示:陣列查找分「按索引」O(1) 和「按值」O(n);雜湊表平均 O(1) / 最壞 O(n);鏈結串列的插入刪除要分「已知位置」與「需先查找」。)這張表是你 Phase 2 後續的參考地圖。

任務 B — 兩個情境的選型(驗收點) 針對兩個情境,各選一個合適的結構並寫出理由: 1. 「頻繁在資料中間插入和刪除」——選什麼?為什麼? 2. 「頻繁做隨機查找(給 key 找 value)」——選什麼?為什麼?(並說明:如果還需要『按順序走訪』,會偏好哪個?)

任務 C — 實測「Big-O 不是全部」(選做但強烈建議) 寫一個小實驗:對 n 個整數,分別用「在排序陣列裡線性查找」和「真的去查一棵樹/或用二分搜尋」,在小 n(如 100)和大 n(如 100 萬)下計時。觀察:小 n 時,簡單的線性陣列掃描可能因 cache 友善而不輸甚至更快。寫一句話連結到 P1-T02 的 cache。

任務 D — 解釋攤銷 用你自己的話(可配一個小算式)解釋:為什麼動態陣列用「翻倍擴容」時,push 的攤銷複雜度是 O(1),即使單次最壞是 O(n)?(提示:等比級數 1+2+4+...+n ≈ 2n。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 完成對照表:陣列/鏈結串列/雜湊表/平衡樹在「查找/插入/刪除」的平均與最壞複雜度。 2. ☐ 給定「頻繁中間插入」與「頻繁隨機查找」兩情境,各選出合適結構並說明理由。

評分量表: - 60(及格):能背出常見結構的複雜度。 - 80(熟練):能據情境選型(說出為什麼)。 - 100(精通):能用攤銷觀念解釋動態陣列擴容成本,並能說明「為何 Big-O 不是選型的全部」(常數/cache/最壞)。
