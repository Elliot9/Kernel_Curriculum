P5-T02 · block layer 核心物件(bio / bio_vec / request / request_queue)

一句話:block layer 用 bio 描述一次區塊 I/O,而 bio 裡的 bio_vec 陣列指向多個分散的記憶體片段(scatter-gather)——這正是後續 DMA 映射的來源。多個 bio 會被合併成 request 派發。這些就是你產品天天操作的 I/O 物件。

為什麼要先學這個(導讀)

P5-T01 你看了整條儲存堆疊。這一課深入 block layer 的核心資料結構——一個 I/O 在 block layer 裡到底長什麼樣。這些就是你產品操作的 I/O 物件,你用 P2 練的讀碼能力(list_head、container_of)終於要用在真實的 block layer 結構上。

幾個核心物件: - struct bio:描述一次 block I/O 請求——要讀/寫哪個裝置、從哪個 sector 開始、資料在哪些記憶體、完成時呼叫誰。它是 block layer 的「I/O 工作單」。 - struct bio_vec:bio 裡的一個元素,描述一個記憶體片段(一個頁裡的一段)。一個 bio 有一個 bio_vec 陣列——意思是一次 I/O 的資料可以分散在多個記憶體片段(scatter-gather,分散-聚集)。這對你極關鍵:這些分散片段正是後續 DMA scatter-gather 映射(P6)的來源。 - struct request:block layer 把一個或多個 bio 組織成 request——這是派發給驅動的單位。 - struct request_queue:一個區塊裝置的請求佇列(blk-mq 架構下的核心,P5-T03)。

還有一個基礎單位概念:sector(磁區)——block layer 的位址單位,慣例是 512 bytes(即使裝置實際 block 可能是 4KB,sector 在 block layer 介面上仍慣用 512B 為單位)。

為什麼這對你是 scope: direct?因為你產品操作的就是這些 I/O 物件:你的軟體 RAID 要把一個 bio 拆成對多個 NVMe 的 bio、算 parity;bio_vec 的分散片段正是你做 DMA scatter-gather 映射(把資料餵給 GPU)的來源。讀懂這些結構,是讀懂、修改 block layer 的基礎。

(這一課大量讀真實 kernel 結構定義——include/linux/blk_types.h,正是 P2-T08 教你的「讀懂真實 kernel 資料結構」能力的用武之地。)

開始之前(前置確認)

  • 依賴:P5-T01(儲存堆疊、block layer 位置)、P2-T02(list_head——request 用串列)、P2-T03(container_of——從成員反推結構)。也用到 P2-T08(讀真實 kernel 結構)、P3-T06(page、實體位址)。
  • 自我檢測: 1. 你還記得 P2-T08 教的「讀 kernel 結構:認招牌、查定義、看內嵌成員」嗎?這課就用它讀 bio/bio_vec。 2. 你還記得 P3-T06 的 page、實體位址嗎?bio_vec 指向的就是記憶體頁裡的片段。
  • 工具:Bootlin 看 include/linux/blk_types.h(https://elixir.bootlin.com/linux/v6.12/source/include/linux/blk_types.h ）。
  • 環境:Linux/閱讀原始碼 + QEMU(觀察 I/O 只在 VM)。

核心內容

拆成這幾節:(1) bio:一次 I/O 的工作單 → (2) bio 的關鍵欄位 → (3) bio_vec:scatter-gather → (4) sector vs block → (5) request 與 request_queue → (6) bio → request 的合併,最後打通關。

1. bio:一次 I/O 的工作單

struct bio 是 block layer 的核心——它描述一次 block I/O。當上層(檔案系統,或 O_DIRECT 直接)要讀/寫裝置,就建立一個 bio 來描述這次 I/O。

(I/O 的『工作單』)"]
    BIO --> WHAT["它說明:
① 對哪個裝置(bi_bdev)
② 讀還是寫、什麼操作(bi_opf)
③ 從哪個 sector 開始(bi_iter 裡)
④ 資料在哪些記憶體(bi_io_vec 陣列,第3節)
⑤ 完成時呼叫誰(bi_end_io 回呼)"]
    WHAT --> LIFE["生命:上層建立 bio → 提交給 block layer(submit_bio)
→ 經過合併/排程 → 驅動處理 → 完成時呼叫 bi_end_io"]
    style BIO fill:#e8a33d,color:#10100e
    style LIFE fill:#8a9a5b,color:#10100e

bio 是一張「I/O 工作單」:它說明對哪個裝置、做什麼操作(讀/寫)、從哪個 sector 開始、資料在哪些記憶體、完成時通知誰。生命週期:上層建立 bio → submit_bio 提交給 block layer → 經合併/排程 → 驅動處理 → 完成時呼叫 bi_end_io 回呼(這是 P0-T07 callback 又一例——「I/O 完成了,呼叫你登記的函式」)。

你的軟體 RAID 就在操作 bio:一個上層的 bio(對 RAID 陣列的 I/O)會被你的 md 邏輯拆成多個 bio(對各個底層 NVMe 裝置),並計算 parity。讀懂 bio 是這一切的起點。

讀 bio 結構,認得幾個關鍵欄位(驗收點:至少正確說明 4 個關鍵欄位的用途):

四個(以上)關鍵欄位: - bi_iter:迭代器,含起始 sector(bi_sector)、剩餘大小等——說明「這次 I/O 在裝置上的位置與長度」。(用迭代器是因為一個 bio 處理過程中位置會推進。) - bi_io_vec:指向 bio_vec 陣列——說明「資料在哪些記憶體片段」(第 3 節,scatter-gather 的核心)。 - bi_opf:操作 + 旗標——讀(REQ_OP_READ)還是寫(REQ_OP_WRITE),加上各種 flag(如 REQ_FUA 強制落盤、以及 P5-T07 會講的 REQ_ATOMIC)。 - bi_end_io:完成回呼——I/O 做完時 block layer 呼叫它(P0-T07 callback)。你在這裡處理「這個 I/O 完成了」(對你的產品:一個底層 NVMe I/O 完成,觸發 parity 後續)。 - bi_bdev:對哪個區塊裝置。

讀這些欄位時,正是 P2-T08 的能力:打開 blk_types.h,認出每個欄位的型別與用途。建議你動手逐欄註解一遍 bio 定義。

3. bio_vec:scatter-gather(分散-聚集)

這是這一課對你最關鍵的概念。一個 bio 的資料不一定在一段連續記憶體——它可以分散在多個記憶體片段,由 bio_vec 陣列描述。這叫 scatter-gather(分散-聚集)。

    BIO2["一個 bio(一次 I/O,例如讀 12KB)"]
    BIO2 --> VECS["bi_io_vec:一個 bio_vec 陣列"]
    subgraph vecarray["bio_vec 陣列(每個 = 一個記憶體片段)"]
        V1["bio_vec[0]:頁 A 的某段(4KB)"]
        V2["bio_vec[1]:頁 B 的某段(4KB)"]
        V3["bio_vec[2]:頁 C 的某段(4KB)"]
    end
    VECS --> vecarray
    MEANING2["意思:這次 12KB I/O 的資料,
分散在『頁 A、頁 B、頁 C』三個不連續的記憶體片段
(scatter-gather:把分散的片段聚集成一次 I/O)"]
    vecarray --> MEANING2
    DMA3["★ 對你極關鍵 ★
這些分散片段 = 後續 DMA scatter-gather 映射(P6)的來源
裝置要能『一次 I/O 讀寫多個分散的記憶體片段』
→ DMA 引擎依這個 scatter-gather list 搬資料"]
    MEANING2 --> DMA3
    style VECS fill:#e8a33d,color:#10100e
    style DMA3 fill:#8a9a5b,color:#10100e

bio_vec 的每個元素描述一個記憶體片段(一個頁 page + offset + 長度,回顧 P3-T06 的 page)。一個 bio 的 bi_io_vec 是這些片段的陣列——所以一次 I/O 的資料可以分散在多個不連續的記憶體片段。

為什麼會分散?因為記憶體是分頁管理的(P1-T04/P3-T06),一塊「看起來連續」的 user 緩衝區,實體上可能落在多個不連續的頁。scatter-gather 讓 block layer/裝置能「一次 I/O 處理多個分散片段」,不必要求實體連續。

對你產品極關鍵(常見誤區:以為一個 bio 對應一段連續記憶體):不對——bi_io_vec 可指向多個分散片段。而這些分散片段正是後續 DMA scatter-gather 映射(P6)的來源:當你要把資料 DMA 給裝置/GPU,裝置的 DMA 引擎需要一張 scatter-gather list(描述「要搬哪些分散的記憶體片段」),而這張 list 就是從 bio 的 bio_vec 來的。所以理解 bio_vec = 理解你 DMA 資料來源的結構。(P5-T07 會提到 phyr 這個 scatterlist 的潛在後繼,但概念一致。)

(驗收點:解釋 bio_vec 如何表達 scatter-gather。)

4. sector vs block:單位的慣例

一個容易混淆的基礎:block layer 用 sector(磁區) 當位址單位,慣例是 512 bytes——但裝置實際的 block 可能更大(常見 4KB)。

block layer 介面上 sector 仍慣用 512B
→ 一個 4KB 裝置 block = 8 個 512B sector"]

    NOTE14 --> CONFUSE["★ 常見誤區:混淆 sector(512B 慣例)與裝置實際 block ★
算位址/大小時要清楚『現在用的是哪個單位』
(bi_sector 是 512B 單位;裝置 block 可能是 4KB)"]
    BLOCK7 --> CONFUSE
    style SECTOR fill:#e8a33d,color:#10100e
    style CONFUSE fill:#c2603a,color:#f4ecd8

sector 是 block layer 介面的位址單位,慣例 512 bytes——bio 的 bi_sector 表示「第幾個 512B sector」。即使裝置實際 block 是 4KB,block layer 介面上 sector 仍慣用 512B(一個 4KB 裝置 block = 8 個 512B sector)。

常見誤區:混淆 sector(512B 慣例)與裝置實際 block 大小——算 I/O 位址/大小時,要清楚「現在用的是哪個單位」。bi_sector 是 512B 單位;裝置的邏輯/實體 block 可能是 4KB。搞混會算錯位址、錯位。寫 block layer 程式碼時這個單位陷阱很常見,要特別小心(也呼應 P0-T04 對齊——裝置 I/O 常要求對齊到實際 block 大小)。

5. request 與 request_queue

bio 是「上層提交的 I/O」,但派發給驅動的單位是 request。block layer 把一個或多個 bio 組織成 request。

    QUEUE2 --> DRIVER6["驅動從 queue 取 request 處理

    NOTE15["bio vs request(常見誤區:以為兩者是同一物):
bio = 上層提交的 I/O 描述
request = block layer 組織後、派發給驅動的單位

    REQUEST3 --> NOTE15
    style REQUEST3 fill:#e8a33d,color:#10100e
    style NOTE15 fill:#c2603a,color:#f4ecd8

  • struct request:block layer 把 bio 組織成 request——這是派發給驅動的單位。一個 request 可含一個或多個合併的 bio(第 6 節)。
  • struct request_queue:一個區塊裝置的請求佇列。在 blk-mq 架構下(P5-T03),這實際是多佇列的(per-CPU 軟佇列 + 硬體派發佇列)。驅動從 queue 取 request 處理(NVMe driver 的 nvme_queue_rq,P5-T06)。

常見誤區:以為 bio 與 request 是同一物——不是:bio 是上層提交的 I/O 描述,request 是 block layer 組織後、派發給驅動的單位,而 bio 會被合併進 request(下一節)。這個區分對讀 block layer 程式碼很重要——你會看到 bio 在上半段(提交、合併),request 在下半段(排程、派發給驅動)。

6. bio → request 的合併

block layer 一個重要的最佳化:把相鄰的 bio 合併成一個 request(merge),減少派發給裝置的請求數。

flowchart TB
    SUBMIT2["陸續提交的 bio:
bio A(sector 100~107)
bio B(sector 108~115)← 緊接 A 之後"]
    SUBMIT2 --> CHECK6{"block layer 檢查:
新 bio 和佇列裡現有的 request
在裝置上『相鄰/可合併』嗎?"}
    CHECK6 -->|"相鄰(可合併)"| MERGE2["合併:把 bio B 併入含 bio A 的 request
→ 一個 request 涵蓋 sector 100~115
(一次派發處理更大塊,效率更好)"]
    CHECK6 -->|"不相鄰"| NEW2["建立新的 request"]
    BENEFIT3["合併的好處:
① 減少派發給裝置的請求數(每個請求有開銷)
② 更大的連續 I/O 對裝置更友善
(對 NVMe:更少的 SQ entry、更少 doorbell)"]
    MERGE2 --> BENEFIT3
    SPLIT["反向也有:bio 拆分(split)
若一個 bio 太大或跨越裝置限制(如 atomic 邊界,P5-T07),
會被拆成多個"]
    style MERGE2 fill:#8a9a5b,color:#10100e
    style BENEFIT3 fill:#e8a33d,color:#10100e

合併(merge):當新提交的 bio 和佇列裡現有 request 在裝置上相鄰(sector 連續),block layer 把它們合併成一個更大的 request。好處:減少派發給裝置的請求數(每個請求有開銷)、更大的連續 I/O 對裝置更友善(對 NVMe:更少的 SQ entry、更少 doorbell)。

拆分(split):反向也有——若一個 bio 太大、或跨越某個裝置限制(例如 P5-T07 的 atomic write 邊界、或 scatter-gather 段數上限),會被拆成多個。

(驗收點:描述 bio→request 的合併概念。)合併/拆分是 block layer 在「上層的 I/O 需求」和「裝置的能力/效率」之間做的最佳化——這也是 I/O 排程器(P5-T04)的職責之一。對你產品:理解合併,你才知道你提交的 bio 到裝置時可能已被組合過,以及如何控制這個行為。

一句話總結:block layer 用 bio 描述一次 I/O(起始 sector、操作、完成回呼),而 bio 的 bio_vec 陣列指向多個分散的記憶體片段(scatter-gather)——正是後續 DMA 映射的來源;sector 慣例 512B(≠ 裝置實際 block);多個相鄰 bio 會被合併成 request(派發給驅動的單位,與 bio 不同物)。這些就是你產品操作的 I/O 物件——軟體 RAID 拆 bio 算 parity、用 bio_vec 做 DMA scatter-gather 餵 GPU。

常見誤區與踩雷提醒

誤區一:以為一個 bio 對應一段連續記憶體。 bi_io_vec 是 bio_vec 陣列,可指向多個分散片段(scatter-gather)。這些分散片段是 DMA scatter-gather 映射(P6)的來源。

誤區二:混淆 sector(512B 慣例)與裝置實際 block 大小。 bi_sector 是 512B 單位;裝置實際 block 可能是 4KB(一個 = 8 sector)。算位址/大小時要清楚單位,否則錯位。

誤區三:以為 bio 與 request 是同一物。 bio 是上層提交的 I/O 描述;request 是 block layer 組織後派發給驅動的單位。bio 會被合併進 request。讀碼時 bio 在上半段、request 在下半段。

延伸與銜接

  • 對應工作場景:直接對應——你產品操作的就是這些 I/O 物件;bio_vec 的分散片段正是後續 DMA scatter-gather 映射的來源。
  • 這課餵給未來的(I/O 物件流動主線):P5-T01 堆疊 → 本課 bio/request → P5-T03 blk-mq(request 在多佇列裡)→ P5-T05 NVMe(request → SQ entry)→ P5-T06 NVMe driver(nvme_queue_rq 處理 request)→ P6-T02 DMA(bio_vec → scatter-gather 映射)。bio_vec → P6 scatter-gather DMA;bi_end_io → 回收 P0-T07 callback、P3-T10 完成處理。
  • 下一步 → P5-T03 多佇列 block layer(blk-mq):你懂了 bio/request 這些 I/O 物件。下一課看它們怎麼被多佇列地管理——blk-mq。核心是兩層佇列:per-CPU 的 software staging queue(每核一個暫存佇列,避免多核爭搶,回收 P1-T03/P3-T09 per-CPU)+ hardware dispatch queue(對應裝置的佇列)。還有 tag(sbitmap) 管理 in-flight request(回收 P2-T07!)。這直接對應你的工作:blk-mq 的每個硬體佇列 1:1 對應 NVMe 的 SQ/CQ 對——理解 blk-mq 是理解你產品 I/O 並行模型的關鍵。
