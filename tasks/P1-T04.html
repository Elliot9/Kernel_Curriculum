P1-T04 · 虛擬記憶體、MMU、分頁與 TLB

一句話:每支程式都以為自己獨佔整個記憶體,從位址 0 開始——這是一個由硬體(MMU)+ 作業系統聯手製造的精緻幻覺。看穿這個幻覺,理解「虛擬位址其實不是真正的實體位址」,你就握住了整個 kernel 記憶體管理的鑰匙,也避開了日後 DMA 工作最大的陷阱。

為什麼要先學這個(導讀)

這是 Phase 1 最重要的一課,值得你投入最多時間(含 lab,12–15 小時)。

回顧 P0-T05,你看過一支程式的記憶體佈局(text/data/heap/stack)。當時有個你可能沒多想的細節:在你印出的位址裡,不同程式的同一種變數,位址看起來很像——好像每支程式都活在「自己從 0 開始的記憶體」裡。沒錯,而且這正是真相:每支程式看到的位址,都是「虛擬位址」,是一個假象。

實情是:你的程式用的位址(虛擬位址),和記憶體條上真正的位置(實體位址),是兩回事。中間有一個硬體叫 MMU(記憶體管理單元),在程式每次存取記憶體時,即時把虛擬位址「翻譯」成實體位址。作業系統則負責設定這個翻譯的規則(分頁表)。於是每支程式都能擁有「我獨佔整個位址空間、從 0 開始」的乾淨幻覺,彼此隔離、互不干擾。

為什麼這對你是 scope: direct、而且是整個課程最關鍵的前置之一?兩個理由:

  1. 這是 P3 kernel 記憶體管理的地基。kernel 如何管理記憶體、user space 與 kernel space 如何劃分位址,全建立在虛擬記憶體上。

  2. 這是 P6 DMA 最大陷阱的源頭,也是你那條「位址的真相」主線的關鍵高潮前奏。當你做 DMA(讓裝置直接讀寫記憶體),你會發現:裝置看到的位址,和 CPU 看到的虛擬位址、甚至和實體位址,都可能不一樣。一個指標(虛擬位址)對 CPU 有意義,但你不能把它直接交給硬體裝置——裝置不經過你程式的 MMU 翻譯。不懂虛擬/實體位址的區分,你在 DMA 會把錯的位址交給裝置,造成資料寫到錯誤的地方(對儲存產品是災難)。這一課就是這條認知鏈的起點(本課 → P3-T06 → P6-T01 → P6-T04)。

核心內容

拆成這幾節:(1) 幻覺:每支程式都以為獨佔記憶體 → (2) 為什麼需要虛擬記憶體 → (3) 分頁:把記憶體切成固定大小的頁 → (4) 分頁表:虛擬→實體的對照表 → (5) MMU:硬體即時翻譯 → (6) 多級分頁:省下巨大的表 → (7) TLB:翻譯的快取 → (8) page fault 的三種成因,最後打通關。

1. 幻覺:每支程式都以為自己獨佔整個記憶體

先看這個會讓你愣住的實驗結果。同時跑兩支不同的程式,各自印出某個變數的位址——你可能會看到兩支程式印出相同的位址,但它們明明是不同的程式、用的是不同的記憶體!

    subgraph proc_a["程式 A 眼中"]
        VA["變數 x
虛擬位址 0x5000"]
    end
    subgraph proc_b["程式 B 眼中"]
        VB["變數 y
虛擬位址 0x5000(竟然一樣!)"]
    end
    subgraph phys["真正的實體記憶體"]
        PA["實體位址 0x12000
(A 的 x 真正在這)"]
        PB["實體位址 0x88000
(B 的 y 真正在這)"]
    end
    VA -.“MMU 翻譯”.-> PA
    VB -.“MMU 翻譯”.-> PB
    NOTE["同一個虛擬位址 0x5000,
在 A 和 B 裡被翻譯到
完全不同的實體位址

這就是核心真相:你程式裡的每個位址,都是「虛擬位址」——一個只在你這支程式的脈絡裡有意義的編號。它不是記憶體條上的真實位置。每支程式都有自己獨立的「虛擬位址空間」,所以兩支程式的 0x5000 互不相干,各自被翻譯到不同的實體位置。

從現在起,你對「位址」的理解要升級:程式裡看到的 = 虛擬位址(假象);記憶體條上真實的 = 實體位址。兩者靠 MMU 翻譯連起來。

2. 為什麼需要這個幻覺:隔離、保護、抽象

製造這個幻覺要付出硬體和軟體成本,為什麼值得?三個關鍵好處:

flowchart TB
    subgraph why["虛擬記憶體的三大好處"]
        ISO["① 隔離(isolation)
每支程式有自己的位址空間
→ A 的 bug 不會踩壞 B 的記憶體
→ 一支當掉不會拖垮別人"]
        PROT["② 保護(protection)
可標記某些頁『唯讀』『不可執行』
→ 防止意外/惡意改寫
(回顧 P0-T05 的唯讀 text 區)"]
        ABS["③ 抽象(abstraction)
程式不必管實體記憶體多大、
哪些被佔用 → 都當自己有完整空間
(甚至可比實體記憶體大,靠 swap)"]
    end
    style ISO fill:#8a9a5b,color:#10100e
    style PROT fill:#6fa8b8,color:#10100e
    style ABS fill:#e8a33d,color:#10100e

對你最重要的是隔離:這正是「user space 程式」和「kernel」能分開、且一支使用者程式崩潰不會搞垮整台機器的基礎。也是為什麼你產品的 user space app 和 kernel module 之間,有一道需要 copy_from_user 之類機制才能跨越的邊界(P1-T06、P4)——它們活在不同的位址空間保護域裡。

3. 分頁:把記憶體切成固定大小的「頁」

要做虛擬→實體的翻譯,如果「每個 byte 都記一條對照」,對照表會大到放不下。所以實際做法是分頁(paging):把記憶體切成固定大小的塊,以「塊」為單位翻譯。

  • 虛擬位址空間切成等大的 頁(page),常見大小 4 KB。
  • 實體記憶體切成等大的 頁框(frame),同樣 4 KB。
  • 翻譯的單位是「哪個虛擬頁 → 哪個實體頁框」,不是逐 byte。

flowchart LR
    subgraph virt["虛擬位址空間(切成頁,各 4KB)"]
        VP0["虛擬頁 0"]
        VP1["虛擬頁 1"]
        VP2["虛擬頁 2"]
    end
    subgraph physical["實體記憶體(切成頁框,各 4KB)"]
        PF5["頁框 5"]
        PF2["頁框 2"]
        PF9["頁框 9"]
    end
    VP0 -->|"映射到"| PF5
    VP1 -->|"映射到"| PF2
    VP2 -->|"映射到"| PF9
    NOTE["翻譯以『頁』為單位;
頁內的偏移(offset)直接照搬"]
    style VP0 fill:#6fa8b8,color:#10100e
    style PF5 fill:#8a9a5b,color:#10100e
    style NOTE fill:#e8a33d,color:#10100e

一個虛擬位址被拆成兩部分:頁號(page number)(這是第幾頁)+ 頁內偏移(offset)(在這頁裡的第幾個 byte)。翻譯時只需把「虛擬頁號」換成「實體頁框號」,offset 部分原封不動照搬。

4. 分頁表:虛擬→實體的對照表

「哪個虛擬頁 → 哪個實體頁框」這份對照關係,記錄在一個叫分頁表(page table)的資料結構裡。每支程式有自己的分頁表(這就是為什麼每支程式的同一虛擬位址能映到不同實體位置)。

翻譯一個虛擬位址的流程:

flowchart TB
    VA["虛擬位址
例:0x5004"]
    SPLIT["拆成兩部分:
頁號 = 0x5(第5頁)
偏移 = 0x004(頁內第4 byte)"]
    VA --> SPLIT
    LOOKUP["查分頁表:
第5頁 → 映射到 實體頁框 0x12"]
    SPLIT --> LOOKUP
    COMBINE["組合實體位址:
頁框 0x12 的基底 + 偏移 0x004
= 實體位址 0x12004"]
    LOOKUP --> COMBINE
    style SPLIT fill:#6fa8b8,color:#10100e
    style LOOKUP fill:#e8a33d,color:#10100e
    style COMBINE fill:#8a9a5b,color:#10100e

注意 offset(0x004)從頭到尾不變,只有「頁號 → 頁框號」這一步要查表。分頁表的每個條目(page table entry, PTE)除了記錄對應的實體頁框,還記錄這頁的權限位元(可讀?可寫?可執行?)——這就是第 2 節「保護」的實作,也是第 8 節 page fault 的判斷依據。

5. MMU:硬體即時做翻譯(不是軟體!)

一個關鍵且常被誤解的點:這個翻譯是由硬體 MMU(Memory Management Unit)即時完成的,不是作業系統用軟體一次次算的。

flowchart LR
    CPU["CPU 要存取
虛擬位址 0x5004"]
    MMU["MMU(硬體)
自動查分頁表、
翻成實體位址"]
    MEM["實體記憶體
0x12004"]
    CPU -->|"送出虛擬位址"| MMU
    MMU -->|"翻成實體位址去存取"| MEM
    NOTE["每一次記憶體存取都經過 MMU,
硬體速度完成,程式無感
(OS 只負責『設定』分頁表內容,
不參與每次翻譯)"]
    style MMU fill:#e8a33d,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

分工要分清: - 作業系統(軟體):負責建立和維護分頁表的內容(決定哪個虛擬頁映到哪個實體框、設定權限)。 - MMU(硬體):負責程式每次存取記憶體時,即時依分頁表把虛擬位址翻成實體位址。

這個分工是效能關鍵:翻譯每秒發生數十億次,必須由硬體做才夠快;OS 只在「設定規則」和「出狀況時」(page fault)介入。誤以為「分頁表查找是軟體做的」是常見錯誤——絕大多數翻譯是純硬體,軟體只在 miss/fault 時才被叫來。

6. 多級分頁:不要為整個位址空間準備一張巨表

這裡有個現實問題。64 位元的虛擬位址空間極其巨大,如果用「一張平坦的大表」記錄每一頁的映射,這張表本身會大到荒謬(即使程式只用到一點點記憶體,表還是要涵蓋整個空間)。

解法是多級分頁(multi-level paging):把分頁表做成樹狀的多層結構,只有「真正用到的部分」才需要建立對應的下層表。

flowchart TB
    VA["虛擬位址拆成多段索引
[L1 索引][L2 索引][L3 索引][L4 索引][偏移]"]
    VA --> L1["第1級表
(頂層,只有一個)"]
    L1 -->|"用 L1 索引找到"| L2["第2級表
(只在用到的分支才存在)"]
    L2 -->|"用 L2 索引"| L3["第3級表"]
    L3 -->|"用 L3 索引"| L4["第4級表
(最底層,指向實體頁框)"]
    L4 -->|"+ 偏移"| PHYS["實體位址"]
    NOTE["關鍵省空間:
程式沒用到的位址範圍,
對應的下層表『根本不必建立』
→ 稀疏的位址空間只花少量表空間"]
    style L1 fill:#6fa8b8,color:#10100e
    style L4 fill:#8a9a5b,color:#10100e
    style NOTE fill:#e8a33d,color:#10100e

直覺:大部分程式的位址空間是稀疏的(只用了零散幾塊:code、heap、stack,中間大片空白)。多級分頁讓你「只為用到的區域建立表」,空白區域連表都不用建。這把分頁表的空間成本從「涵蓋整個 64 位元空間」降到「正比於實際使用量」。x86-64 目前用 4 級(或 5 級)分頁。

代價是:一次翻譯要走好幾層表(每層查一次記憶體)。這聽起來很慢——確實,所以才需要下一節的 TLB 來救。

7. TLB:翻譯結果的快取

第 6 節的多級分頁有個效能問題:每翻譯一個虛擬位址,要走 4 層表,等於多次記憶體存取才換來一次翻譯。而記憶體存取很慢(回顧 P1-T02)。如果每次存取記憶體前都要先做 4 次記憶體存取來翻譯,那就太慢了。

解法是 TLB(Translation Lookaside Buffer,翻譯後備緩衝區):一個專門快取「最近用過的虛擬頁→實體框翻譯結果」的小型超高速硬體快取。它就是「翻譯的 cache」(概念上呼應 P1-T02 的 cache,只是快取的是翻譯結果而非資料)。

flowchart TB
    VA["CPU 要翻譯虛擬位址"]
    VA --> Q{"TLB 裡有這頁的
翻譯結果嗎?"}
    Q -->|"TLB 命中(hit)"| HIT["直接拿到實體框號
極快(免走分頁表)"]
    Q -->|"TLB 失誤(miss)"| MISS["走多級分頁表翻譯
(慢,多次記憶體存取)"]
    MISS --> FILL["把這次的翻譯結果
存進 TLB(下次就命中)"]
    style HIT fill:#8a9a5b,color:#10100e
    style MISS fill:#c2603a,color:#f4ecd8
    style FILL fill:#e8a33d,color:#10100e

因為局部性(回顧 P1-T02:程式傾向反覆存取鄰近的頁),TLB 命中率通常很高,所以絕大多數翻譯都走 TLB 的快速路徑,只有少數 miss 才需要走完整的分頁表。

TLB 失效(flush)的成本:當切換到另一支程式(換了分頁表),原本 TLB 裡的翻譯就不再適用,要清掉(flush)。清空後 TLB 要重新「暖機」(累積新的翻譯),這段期間 miss 率高、變慢。這就是為什麼 context switch(P1-T06)有隱藏成本之一——不只是換暫存器,還可能讓 TLB 失效。忽略 TLB flush 的成本是常見誤區。

8. page fault:翻譯失敗時發生什麼

當 MMU 翻譯一個虛擬位址,發現「這頁有問題」——這時硬體會觸發一個叫 page fault(分頁錯誤/缺頁)的事件,把控制權交給作業系統來處理。page fault 有三種常見成因:

flowchart TB
    PF["MMU 翻譯時發現問題 → 觸發 page fault → OS 介入"]
    PF --> C1["① 缺頁(not present)
這頁目前不在實體記憶體
(可能被換到磁碟 swap,或還沒配置)
→ OS 把它載入/配置,再重試"]
    PF --> C2["② 權限錯誤(protection)
這頁存在,但你做了不被允許的事
(例:寫一個唯讀頁)
→ 視情況可能是合法(COW)或錯誤(segfault)"]
    PF --> C3["③ 無效位址(invalid)
這個虛擬位址根本沒映射任何東西
(例:解參考野指標、NULL)
→ 通常 OS 殺掉程式(segfault)"]
    style C1 fill:#6fa8b8,color:#10100e
    style C2 fill:#e8a33d,color:#10100e
    style C3 fill:#c2603a,color:#f4ecd8

關鍵理解:page fault 不一定是「錯誤」。成因①(缺頁)是虛擬記憶體正常運作的一部分——它讓 OS 能「按需載入」(demand paging)、能用磁碟當記憶體的延伸(swap)、能做 copy-on-write(回顧 P1-T05 會講的 fork)。只有成因③(無效位址,像你解參考 NULL 或野指標——回顧 P0-T02)才是真正的程式錯誤,導致 segfault。

這也終於從硬體層面解釋了 P0-T02 那個「對 NULL 解參考會崩潰」:NULL(位址 0)在分頁表裡沒有有效映射,MMU 翻譯時觸發「無效位址」page fault,OS 就殺掉你的程式。

打通關:把虛擬記憶體收攏成一個心智模型

flowchart TB
    ILLUSION["核心:程式用的是『虛擬位址』(幻覺)
≠ 記憶體條上的『實體位址』"]
    ILLUSION --> WHY["為什麼:隔離 + 保護 + 抽象"]
    ILLUSION --> HOW["怎麼做:分頁(切成 4KB 的頁/框)"]
    HOW --> TABLE["分頁表記錄 虛擬頁→實體框 + 權限
(每支程式一份)"]
    TABLE --> MMU["MMU 硬體每次存取即時翻譯
(OS 只設定表,不參與每次翻譯)"]
    TABLE --> MULTI["多級分頁:樹狀,只為用到的區域建表(省空間)"]
    MMU --> TLB["TLB 快取翻譯結果(避免每次走多級表)
切換程式要 flush(隱藏成本)"]
    MMU --> FAULT["翻譯出問題 → page fault
(缺頁=正常按需載入;無效=segfault)"]
    FAULT --> TRUTH["★『虛擬≠實體』是你『位址的真相』主線的關鍵
→ P6 DMA:裝置看到的位址又是另一回事★"]
    style ILLUSION fill:#e8a33d,color:#10100e
    style MMU fill:#6fa8b8,color:#10100e
    style TRUTH fill:#c2603a,color:#f4ecd8

一句話總結:「每支程式獨佔記憶體」是 MMU 硬體 + OS 分頁表聯手製造的幻覺;程式用虛擬位址,MMU 每次存取即時翻成實體位址,TLB 快取翻譯、page fault 處理例外。牢牢記住「虛擬位址不是實體位址」——這是 kernel 記憶體管理的地基,更是你日後 DMA 工作中『不能把 CPU 的虛擬位址直接交給裝置』那個致命陷阱的源頭。

常見誤區與踩雷提醒

誤區一(最關鍵):混淆虛擬位址與實體位址。 程式裡的指標都是虛擬位址,不是記憶體條上的真實位置。這個混淆是 P6 DMA 主題最大陷阱的開端——你不能把一個虛擬位址(指標)直接交給硬體裝置,因為裝置不經過你程式的 MMU 翻譯。

誤區二:以為分頁表查找是軟體做的。 絕大多數翻譯由 MMU 硬體即時完成;OS 只負責設定分頁表內容,並在 page fault(miss)時才介入。

誤區三:忽略 TLB flush 的成本。 切換程式(換分頁表)會使 TLB 失效,需要重新暖機,這是 context switch 隱藏成本之一。

誤區四:以為 page fault 都是錯誤。 缺頁(成因①)是虛擬記憶體正常運作(按需載入、swap、COW)。只有無效位址(成因③)才是真正的程式錯誤(segfault)。

誤區五:以為虛擬位址空間大小受限於實體記憶體。 不是。虛擬空間可以遠大於實體記憶體(靠 swap 把暫時不用的頁換到磁碟)。實體記憶體是「目前真正裝得下的」,虛擬空間是「程式以為自己有的」。

動手實作

環境:概念實驗在 Linux 使用者態(安全,不需 root);lab 在 MIT 6.1810 的 xv6 環境(教學用作業系統,在 QEMU 裡跑,不碰你的主機)。

任務 A — 親眼見證虛擬位址的幻覺 寫一支極簡程式,印出一個全域變數的位址,然後同時跑兩個這支程式的實例(例如開兩個終端各跑一次,或用 fork——但 fork 的位址空間是 COW 複製,概念上仍各自獨立)。

#include <stdio.h>
#include <unistd.h>
int global = 0;
int main(void) {
    printf("PID %d: &global = %p\n", getpid(), (void*)&global);
    sleep(30);   // 暫停,讓你有時間同時跑另一個實例對照
    return 0;
}

觀察:兩個獨立執行的實例,可能印出相同的虛擬位址——但它們是不同的 process,用的是不同的實體記憶體。寫一句話解釋:為什麼相同的虛擬位址不會互相干擾?

任務 B(核心)— 完成 MIT 6.1810 page-table lab 依 https://pdos.csail.mit.edu/6.1810/2023/labs/pgtbl.html 的指引,在 xv6 裡完成 page-table lab(操作分頁表)。這是把「分頁表」從抽象概念變成你親手碰過的東西的關鍵。完成後通過它的測試。

任務 C — 畫出完整翻譯流程 不靠工具,在紙上畫出「一個虛擬位址 → 經(多級)分頁表 → 實體位址」的完整流程,包含 TLB 命中與失誤兩個分支。這是驗收點之一。

任務 D — 解釋 page fault 三成因 寫一段話,說明 page fault 的三種常見成因(缺頁 / 權限 / 無效),並指出哪一種是「正常運作」、哪一種是「程式錯誤」。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 畫出一條虛擬位址經多級分頁表轉成實體位址的完整流程(含 TLB 命中/失誤分支)。 2. ☐ 完成 6.1810 pgtbl lab 並通過其測試。 3. ☐ 解釋 page fault 的三種常見成因(缺頁、權限、無效),並區分哪些是正常、哪個是錯誤。

評分量表: - 60(及格):能複述虛擬→實體的轉換流程。 - 80(熟練):能完成 lab 並解釋分頁表運作。 - 100(精通):能說明多級分頁如何節省空間、TLB 為何必要,並預示 kernel 的位址空間設計與 DMA 的位址問題。

延伸與銜接

  • 對應工作場景:直接對應——這是 P6 DMA(虛擬/實體/匯流排位址三者之分)與 P3 kernel 記憶體管理最重要的前置。你做 DMA 時「不能把虛擬位址直接給裝置」這個鐵則,根源就在這一課。
  • 這課餵給未來的(你的「位址的真相」主線):本課(虛擬≠實體)→ P3-T06 kernel 的位址空間與各種位址轉換函式 → P6-T01 DMA 位址(dma_addr_t,裝置看的位址,CPU 不能解參考)→ P6-T04 高潮。分頁/保護 → P1-T06 user/kernel 邊界、P4 copy_from_user。
  • 下一步 → P1-T05 行程 vs 執行緒:你已經懂「每支程式有自己的虛擬位址空間」。下一課用這個基礎,精準切開兩個你列為核心缺口的概念——行程(process)與執行緒(thread):行程是「擁有獨立位址空間的資源容器」,執行緒是「共享位址空間的排程單位」。理解它們共享什麼、不共享什麼,直接決定了你產品裡「哪些地方需要加鎖同步」。
