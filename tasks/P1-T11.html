P1-T11 ·【環境里程碑】建置 QEMU/KVM kernel 開發環境

一句話:從原始碼編譯一個 Linux kernel、在 QEMU 虛擬機裡開機、接上 GDB 在 start_kernel 設中斷點——這條鏈是你日後開發與除錯自家 kernel module 每天都會用的工作迴圈,也是你能安全測試 module 的隔離環境。絕不在你的主機上測試 module。

為什麼要先學這個(導讀)

這是 Phase 1 的收尾,也是一個里程碑:你要親手搭建日後的「kernel 開發實驗室」。

到目前為止,你寫的程式都跑在使用者態(回顧 P1-T06 的使用者/核心邊界)。從 Phase 3 開始,你要寫真正進入核心態的程式碼——kernel module。但核心態程式碼有個可怕的特性:它沒有使用者態那層保護網(回顧 P0-T06、P1-T04 的隔離只保護「行程之間」,不保護核心本身)。一個 module 裡的 bug——野指標、記憶體錯誤——不會只是讓你的程式 segfault,而是可能直接搞垮整台機器、損毀檔案系統、甚至造成資料遺失。

所以你絕對不能在你日常用的主機上載入(insmod)自己寫的 module。你需要一個拋棄式的隔離環境:一個跑在虛擬機(QEMU)裡的 Linux,在裡面載入 module、測試、就算搞當了也只是重啟那個虛擬機,你的主機毫髮無傷。這就是本課要建的東西。

為什麼這對你是 scope: direct?因為: 1. 這是你 Phase 3+ 的日常工作環境。你之後寫的每一個 module、做的每一次除錯,都在這個環境裡進行。 2. 這是安全底線。你公司產品的 module,也應該在這類隔離環境裡開發測試,而不是直接上生產機器。 3. GDB 源碼級除錯讓你能像除錯一般程式那樣(回顧 P0-T01 的 gdb),在 kernel 程式碼裡設中斷點、單步、看變數——這是排查 kernel 問題的利器。

這一課比較「工程實作」導向,但每一步背後的原理,你前面都學過了。

開始之前(前置確認)

  • 依賴:P1-T04(理解分頁有助於理解開機過程中記憶體如何被設置)。也用到 P0-T01(編譯、Makefile、gdb)的一切。
  • 自我檢測: 1. 你還記得 P0-T01 怎麼用 gdb 設中斷點、單步、看變數嗎?這課把同樣的 gdb 動作用在 kernel 上。 2. 你還記得 P0-T01 的 Makefile / 編譯流程嗎?編譯 kernel 是它的工業級放大版(用 Kbuild)。
  • 心態:這課步驟多、第一次做容易卡關(設定缺項、版本問題)。卡住是正常的,耐心查文件。一旦搭好,你就有了長期可用的環境。
  • 最重要的安全前提:本課所有「載入 module」「測試核心程式碼」的動作,只在 QEMU 虛擬機裡做,絕不在你的主機。這不是建議,是鐵則。

核心內容

拆成這幾節:(1) 全局藍圖:這條鏈在做什麼 → (2) 取得 kernel 原始碼 → (3) 設定 .config → (4) 編譯 → (5) initramfs:最小根檔案系統 → (6) QEMU 開機 → (7) 接上 GDB 源碼級除錯,最後打通關。

1. 全局藍圖:從原始碼到可除錯的虛擬機

先看整條鏈,再逐站實作。你要做的,是把「一堆 kernel 原始碼」變成「一個能在 QEMU 裡開機、且能被 GDB 從外面除錯的系統」:

兩個產物名詞先認識: - vmlinux:編譯出的未壓縮 kernel,含符號資訊(給 GDB 用,讓它知道「這個位址對應哪個函式/變數」)。 - bzImage:壓縮過的、可開機的 kernel 映像(QEMU 拿它來開機)。

2. 取得 kernel 原始碼:選一個 LTS 版本

從 https://www.kernel.org/ 下載一個 LTS(長期支援) 的 6.x 版本。為什麼選 LTS?因為它穩定、修補維護期長,適合學習與產品基礎(不像最新版可能有未穩定的東西)。

解壓後你會看到 kernel 龐大的原始碼樹(kernel/、mm/、drivers/、fs/、block/ 等子目錄——你未來會在這些目錄裡讀程式碼、寫東西)。

3. 設定 .config:決定編譯哪些功能

kernel 有成千上萬個可開關的設定選項(支援哪些硬體、哪些檔案系統、哪些功能)。這些選項記錄在一個叫 .config 的檔案裡。你不可能手動一個個設,所以從一個合理的預設開始,再調整:

flowchart TB
    DEFCONFIG["make defconfig
產生一個合理的預設 .config
(針對你的架構,如 x86-64)"]
    MENUCONFIG["make menuconfig
(選用)用選單介面微調
開關特定選項"]
    KEY["關鍵:確認這幾類選項有開:
① QEMU 用得到的虛擬裝置 + 檔案系統
(否則開不了機 / 掛載不了根)
② CONFIG_DEBUG_INFO
(編入除錯符號,GDB 才能源碼級除錯)
③ 必要時關閉位址隨機化相關,
讓 GDB 符號對得上"]
    DEFCONFIG --> MENUCONFIG --> KEY
    style DEFCONFIG fill:#6fa8b8,color:#10100e
    style KEY fill:#e8a33d,color:#10100e

.config 是整個 build 的「設定真相」。最常見的卡關點就在這裡(誤區會詳述): - 缺了 QEMU 對應的虛擬裝置驅動或檔案系統支援 → kernel 開機後找不到裝置、掛載不了根檔案系統 → 開不了機。 - 沒開 CONFIG_DEBUG_INFO → 編出的 kernel 沒有除錯符號 → GDB 連上了卻看不到函式名、設不了源碼中斷點。

(.config 本質上就是一大堆 CONFIG_XXX=y/m/n 的開關,y=編進 kernel、m=編成可載入模組、n=不編。這是 P0-T08 前處理器 #ifdef 的大規模應用——kernel 用這些設定在編譯時決定包含哪些程式碼。)

4. 編譯:make 的工業級放大版

設定好 .config,就可以編譯了。這是 P0-T01 那個編譯流程 + Makefile 的工業級放大版(kernel 的 build 系統叫 Kbuild):

    A["make -j$(nproc)
(用所有 CPU 核心平行編譯,加速)"]
    B["Kbuild 依 .config
編譯需要的數千個檔案
(回顧 P0-T01:只編需要的,靠相依關係)"]
    C["產出:
vmlinux(含符號,給 GDB)
bzImage(壓縮,給 QEMU 開機)"]
    A --> B --> C
    style A fill:#6fa8b8,color:#10100e
    style C fill:#e8a33d,color:#10100e

第一次編譯整個 kernel 會花不少時間(幾分鐘到幾十分鐘,看機器)。但之後若只改少數檔案,Kbuild 只重編改動的部分(回顧 P0-T01 的增量編譯)——這就是為什麼當年要學 Makefile 的相依關係。

回顧連結:還記得 P0-T01 那個 8 行的小 Makefile 嗎?當時說它是「那座大山的第一塊石頭」。現在你就站在那座大山(Kbuild)前面了。原理一樣:目標依賴來源、看時間戳記決定重建範圍,只是規模從一個檔案變成幾萬個。

5. initramfs:給 kernel 一個最小的根檔案系統

編好 kernel 還不夠——kernel 開機後需要一個根檔案系統(root filesystem),裡面至少要有一個能執行的程式(否則開機到一半發現「沒有任何程式可跑」就會 panic)。最輕量的做法是用 initramfs(一個被打包、開機時載入記憶體的最小檔案系統)配上 BusyBox(一個把幾百個常用命令塞進單一執行檔的迷你工具箱)。

flowchart TB
    WHY["kernel 開機後需要:
一個根檔案系統 + 至少一個可執行程式
(否則 panic:沒東西可跑)"]
    WHY --> BUSYBOX["BusyBox:
一個執行檔提供 shell + 幾百個命令
(ls/cat/mount...),極小巧"]
    BUSYBOX --> INITRAMFS["打包成 initramfs:
一個壓縮檔,開機時被載入記憶體
當作最初的根檔案系統"]
    INITRAMFS --> RESULT["開機後你就有一個
可互動的 shell
(能在裡面 insmod 你的 module 測試)"]
    style WHY fill:#c2603a,color:#f4ecd8
    style INITRAMFS fill:#e8a33d,color:#10100e
    style RESULT fill:#8a9a5b,color:#10100e

initramfs 在開機中的角色:開機時,kernel 把 initramfs 解壓到記憶體,當作最初的根檔案系統,並執行裡面約定的初始程式(通常是個 /init 腳本,最終給你一個 shell)。對你的用途,這個最小環境就夠了——你只需要一個能 insmod module、能看 dmesg 輸出的 shell。(真實系統開機後會再從 initramfs 切換到磁碟上的正式根檔案系統,但學習/測試用的最小環境,停在 initramfs 的 shell 就夠。)

6. QEMU 開機:在虛擬機裡跑你的 kernel

現在把編好的 kernel(bzImage)和 initramfs 交給 QEMU(一個虛擬機軟體),讓它啟動一個虛擬機來跑你的 kernel:

flowchart LR
    QEMU["qemu-system-x86_64
-kernel bzImage
-initrd initramfs
-append 開機參數
(+ 視需要的虛擬裝置)"]
    BOOT["QEMU 啟動虛擬機
→ 載入你的 kernel
→ kernel 初始化
→ 載入 initramfs
→ 給你 shell"]
    SAFE["★ 一切在虛擬機內 ★
就算 module 搞當機,
只是重啟這個 VM,
主機毫髮無傷"]
    QEMU --> BOOT --> SAFE
    style QEMU fill:#6fa8b8,color:#10100e
    style BOOT fill:#8a9a5b,color:#10100e
    style SAFE fill:#e8a33d,color:#10100e

(可選的 KVM 加速:如果你的主機 CPU 支援虛擬化,加上 KVM 能讓虛擬機接近原生速度;沒有也能跑,只是慢些。)

成功的話,你會在終端機看到 kernel 開機訊息一行行刷過,最後出現一個 shell 提示符——這就是你的 kernel 開機成功了。這個 shell 跑在你剛編的 kernel 上,在一個完全隔離的虛擬機裡。這就是你日後測試 module 的安全沙盒:在這個 shell 裡 insmod your_module.ko,測試,看 dmesg,搞當了就重啟 QEMU。

7. 接上 GDB:對 kernel 做源碼級除錯

最後一塊,也是最強大的:讓 GDB 連上 QEMU 裡的 kernel,像除錯一般程式那樣除錯 kernel(回顧 P0-T01 的 gdb 基本動作)。

QEMU 提供一個「GDB stub」——用 -s -S 參數開啟: - -s:開一個 GDB 可連的除錯埠。 - -S:開機時先暫停,等 GDB 連上、下指令才開始跑(這樣你能在 kernel 最早期就設中斷點)。

flowchart TB
    Q["qemu ... -s -S
(-s 開除錯埠;-S 開機先凍結等待)"]
    G["另一個終端:
gdb vmlinux
(載入含符號的 vmlinux,
GDB 才認得函式名)"]
    CONNECT["在 gdb 裡:
target remote :1234
(連上 QEMU 的除錯埠)"]
    BP["break start_kernel
(在 kernel 的進入點之一設中斷點)"]
    CONT["continue
→ QEMU 開始跑,
命中中斷點時停下"]
    INSPECT["此時可:
單步、print 變數、看 backtrace
(就像 P0-T01 除錯一般程式)"]
    Q --> G --> CONNECT --> BP --> CONT --> INSPECT
    style Q fill:#6fa8b8,color:#10100e
    style BP fill:#e8a33d,color:#10100e
    style INSPECT fill:#8a9a5b,color:#10100e

關鍵點: - 必須用含符號的 vmlinux(不是 bzImage)——GDB 靠它把記憶體位址對應回「start_kernel 這個函式、第幾行、哪個變數」。沒符號(沒開 CONFIG_DEBUG_INFO),GDB 只能給你冷冰冰的位址(呼應 P0-T01「沒有 -g 就看不到行號變數」)。 - vmlinux 要和 QEMU 跑的 kernel 完全一致——否則符號對不上(GDB 以為某函式在某位址,實際不是)。 - 位址隨機化(KASLR) 可能讓符號位址對不上,除錯時通常要關閉它(透過開機參數),GDB 才能正確定位。

能在 start_kernel 停下、印出一個變數,代表你的源碼級 kernel 除錯環境完全打通——這是本課的最高成就,也是你日後排查自家 module 疑難雜症的終極武器。

一句話總結:這條「原始碼→設定→編譯→initramfs→QEMU→GDB」的鏈,給你一個隔離、可重複、可源碼級除錯的 kernel 實驗室;.config(含除錯符號與 QEMU 裝置支援)是成敗關鍵,而最重要的鐵則是——自寫 module 永遠只在這個虛擬機裡測試,絕不碰你的主機。這是你 Phase 3 之後的日常工作環境,也是安全開發產品 module 的基礎。

常見誤區與踩雷提醒

誤區一(最危險的鐵則):在主機上直接 insmod 自寫 module。 極度危險——module 的 bug 可能搞垮整台機器、損毀檔案系統、遺失資料。自寫 module 務必只在 QEMU 虛擬機裡測試。 這是不可妥協的安全底線,也適用於你公司產品的 module 開發。

誤區二:.config 缺少 QEMU 對應的裝置/檔案系統選項。 導致 kernel 開機後找不到裝置、掛載不了根檔案系統 → 開不了機。確認虛擬裝置驅動與所需檔案系統有編進去。

誤區三:忘記開 CONFIG_DEBUG_INFO。 沒有除錯符號,GDB 連上了也看不到函式名、設不了源碼中斷點(呼應 P0-T01 沒 -g 的窘境)。

誤區四:GDB 用的 vmlinux 與運行的 kernel 不符,或沒關位址隨機化。 符號會對不上(GDB 定位錯誤)。確保 vmlinux 與 QEMU 跑的 kernel 完全一致,並視需要關閉 KASLR。

誤區五:用 bzImage 給 GDB 載入符號。 bzImage 是壓縮的開機映像,GDB 要的是含符號的 vmlinux。兩者用途不同,別搞混。

動手實作

環境:你的開發主機(用來編譯與跑 QEMU)。所有 kernel 測試都在 QEMU 虛擬機內,絕不在主機核心上做。 編譯與跑 QEMU 本身不需特殊權限。

任務 A — 編譯一個 6.x LTS 並在 QEMU 開機到 shell 1. 從 kernel.org 下載一個 6.x LTS,解壓。 2. make defconfig(x86-64),make -j$(nproc) 編譯。 3. 用 BusyBox 做一個最小 initramfs(網路上有許多現成步驟,參考 admin-guide:https://docs.kernel.org/admin-guide/ 與 Kbuild 文件 https://docs.kernel.org/kbuild/ )。 4. 用 qemu-system-x86_64 -kernel <bzImage> -initrd <initramfs> -append "console=ttyS0" -nographic 開機。 驗收:看到 kernel 開機訊息,最後進入一個可互動的 shell。

任務 B — 接上 GDB,在 start_kernel 設中斷點 1. 確認編譯時開了 CONFIG_DEBUG_INFO(否則重新設定 .config 再編)。 2. QEMU 加上 -s -S 啟動(開機凍結等待)。 3. 另開終端:gdb vmlinux → target remote :1234 → break start_kernel → continue。 4. 命中中斷點後,print 至少一個變數(例如某個全域),用 backtrace 看呼叫堆疊。 驗收:GDB 在 start_kernel 停下,並能印出至少一個變數。(若符號對不上,檢查是否關閉 KASLR、vmlinux 是否相符。)

任務 C — 寫成一鍵腳本(衝 100 分) 把「編譯(若需要)→ 啟動 QEMU → (另開)連 GDB」的流程寫成一個可重複執行的腳本。並在腳本註解裡用一兩句話說明 initramfs 在開機中扮演的角色。 驗收:腳本可重複跑起整套環境。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 成功編譯指定 6.x LTS 並在 QEMU 開機到 shell。 2. ☐ 以 qemu -s -S + gdb vmlinux 連上,在 start_kernel 設中斷點、命中後印出至少一個變數。 3. ☐ 將整套流程寫成一鍵腳本可重複執行。

評分量表: - 60(及格):能讓自編的 kernel 在 QEMU 開機。 - 80(熟練):能用 GDB 連上做源碼級除錯(設中斷點、看變數)。 - 100(精通):能寫成可重複的腳本,並說明 initramfs 在開機中的角色。

延伸與銜接

  • 對應工作場景:直接對應——這是你日後開發/除錯自家 kernel module 的標準工作環境;公司產品的 module 也應在此類隔離環境測試。這個環境會陪伴你整個 Phase 3 之後的旅程。
  • 這課餵給未來的:整個開發/除錯環境 → P3 開始的所有 kernel module 開發與除錯;「只在 VM 測試」的紀律 → 你產品 module 開發的安全規範;GDB 源碼級除錯 → 排查 kernel panic、追 bug。
  • 下一步 → P2-T01 進入 Phase 2:恭喜你完成 Phase 1!你現在既有了 CPU/OS 的完整心智模型(計算結構、虛擬記憶體、行程執行緒、並行同步),又有了能實際動手的 kernel 開發環境。Phase 2 是進入 kernel 原始碼世界的橋樑——你會開始讀懂 kernel 的核心慣用法與資料結構(像那個無所不在的 list_head、神奇的 container_of 巨集),學會在龐大的 kernel 原始碼裡導航。你在 Phase 0/1 打下的 C 功底與系統觀念,從這裡開始會直接套用在真實的 kernel 程式碼上。
