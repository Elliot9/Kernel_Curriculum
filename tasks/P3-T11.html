P3-T11 · memory barrier 與 Linux Kernel Memory Model(LKMM)

一句話:把 P1-T10 那個「編譯器和 CPU 會重排記憶體存取」的恐懼,變成 kernel 裡的實際工具——smp_wmb/smp_rmb、READ_ONCE/WRITE_ONCE、acquire/release。這是 lock-free、RCU,以及你 DMA 正確性的根:描述子必須在按 doorbell 前對 NVMe 裝置可見,否則裝置讀到舊資料、資料毀損。

為什麼要先學這個(導讀)

這一課是你那條「記憶體順序/可見性」主線的關鍵一站(P1-T03 coherence≠ordering → P1-T10 重排直覺 → 本課 kernel 實戰 → P6-T03 DMA),也是你 DMA 工作正確性的核心。

回顧 P1-T10:你建立了一個重要又燒腦的認知——「程式碼順序 = 執行/可見順序」是錯覺,編譯器和 CPU 都會重排記憶體存取,在多核心下讓別人看到違反直覺的順序。那一課只求「直覺 + 恐懼」。這一課把那份恐懼,變成 kernel 裡的實際工具:

  • READ_ONCE/WRITE_ONCE:防止編譯器對共享變數做某些危險的最佳化(把它當你明確要求的「就讀一次/寫一次記憶體」)。
  • memory barrier:smp_mb(全屏障)、smp_wmb(寫屏障)、smp_rmb(讀屏障)——強制某些記憶體操作的順序不被重排。
  • acquire/release:smp_load_acquire/smp_store_release——成對的順序語意(回顧 P1-T10 第 6 節)。
  • LKMM(Linux Kernel Memory Model):kernel 對「記憶體操作順序」的形式化模型,定義了這些工具的精確語意。

為什麼這對你是 scope: direct、而且是 DMA 正確性的命門?因為當你做 DMA:你在記憶體裡準備好一個描述子(告訴 NVMe 裝置「要做什麼 I/O」),然後寫一個暫存器「按門鈴(doorbell)」通知裝置開工。你必須保證描述子的內容在門鈴之前就對裝置可見——如果 CPU 重排了這兩個寫入(門鈴的寫入先傳播到裝置、描述子還沒),裝置會去讀還沒寫好的垃圾描述子,執行錯誤的 I/O——對儲存產品,這是資料毀損。防止這個,就要 memory barrier(以及 P6 的 dma_wmb)。這一課讓你掌握這個命門。

開始之前(前置確認)

  • 依賴:P1-T10(重排直覺、barrier 概念、acquire/release 入門、volatile 不夠)、P3-T09(原子操作)。強烈建議重看 P1-T10——這課是它的 kernel 實戰版。
  • 自我檢測: 1. 你還記得 P1-T10 的 store-buffer 範例(兩執行緒可能都讀到舊值)、以及「barrier 強制順序」嗎?這課用 kernel 的 barrier 工具做同樣的事。 2. 你還記得 P1-T10 說「volatile 不是 barrier、不保證原子」嗎?這課的 READ_ONCE/WRITE_ONCE 是 kernel 的正確工具(不是 volatile)。
  • 心態:這課和 P1-T10 一樣燒腦。目標是「會用 kernel 的 barrier 工具、懂為什麼 DMA 需要它」,不求精通 LKMM 的形式化細節。
  • 環境:QEMU 虛擬機。實驗只在 VM。

核心內容

拆成這幾節:(1) 兩種重排:編譯器與 CPU → (2) READ_ONCE / WRITE_ONCE → (3) memory barrier:smp_mb/wmb/rmb → (4) acquire / release → (5) 命門:DMA 描述子必須在門鈴前可見 → (6) LKMM 的角色,最後打通關。

1. 兩種重排:編譯器與 CPU(快速回顧 + kernel 視角)

先快速複習 P1-T10 的核心,放到 kernel 脈絡:你的記憶體操作會被兩層重排。

關鍵(回顧 P1-T10):編譯器重排(編譯時調換,單核也有)和 CPU 重排(執行時可見順序變動,多核顯現)。kernel 的工具分別對付:READ_ONCE/WRITE_ONCE 主要管編譯器層;smp_* barrier 管 CPU 層(也含編譯器屏障效果)。理解「有兩層、各有工具」,你才知道何時用哪個。

2. READ_ONCE / WRITE_ONCE:管住編譯器

第一個工具,對付編譯器層的重排與危險最佳化。問題:編譯器看到你反覆讀一個共享變數,可能「聰明地」把它快取在暫存器、只讀一次(它以為值不會變)——但在並行下,別的執行流可能改了那個變數,你卻用著快取的舊值。

flowchart TB
    PROBLEM["共享變數 flag,你寫 while(!flag);
編譯器可能優化成『只讀一次 flag、存暫存器、無限迴圈』
(它不知道別的執行流會改 flag)→ 永遠看不到 flag 變 1"]
    PROBLEM --> SOLUTION["WRITE_ONCE(flag, 1)：寫方明確『就寫這一次到記憶體』
READ_ONCE(flag)：讀方明確『就從記憶體讀這一次』
→ 阻止編譯器把存取優化掉/快取在暫存器"]
    SOLUTION --> NOT_VOLATILE["★ 這是 kernel 的正確工具,不是 volatile ★
(回顧 P1-T10:volatile 語意不同、不該用於並行)
READ_ONCE/WRITE_ONCE 精確表達『這是一次對共享記憶體的存取』"]
    style PROBLEM fill:#c2603a,color:#f4ecd8
    style SOLUTION fill:#8a9a5b,color:#10100e
    style NOT_VOLATILE fill:#e8a33d,color:#10100e

READ_ONCE/WRITE_ONCE 的作用:告訴編譯器「這是一次明確的、對共享記憶體的讀/寫,別把它優化掉、別快取在暫存器、別拆分」。它防止的是編譯器的最佳化(驗收點:READ_ONCE/WRITE_ONCE 防的是哪類編譯器最佳化——把共享變數存取優化掉/快取/重排這類)。

關鍵(回顧 P1-T10 的誤區):這不是 volatile(常見誤區:以為 volatile 等於 READ_ONCE)。READ_ONCE/WRITE_ONCE 是 kernel 為並行存取設計的正確工具,語意精確;volatile 語意不同、不該用於 kernel 並行。存取無鎖保護的共享變數時,用 READ_ONCE/WRITE_ONCE。

(注意:READ_ONCE/WRITE_ONCE 只管編譯器,不提供 CPU 層的順序保證——那要 barrier,下一節。)

3. memory barrier:smp_mb / smp_wmb / smp_rmb

第二個工具,對付 CPU 層的重排。memory barrier 強制「屏障兩側的記憶體操作順序不被 CPU 重排」(回顧 P1-T10 第 5 節)。kernel 有幾種:

flowchart TB
    subgraph barriers["kernel 的 SMP 記憶體屏障"]
        MB["smp_mb()  全屏障
屏障前的所有讀寫,都在屏障後的所有讀寫之前完成/可見"]
        WMB["smp_wmb() 寫屏障
屏障前的所有『寫』,都在屏障後的『寫』之前對別人可見
(只管寫的順序)"]
        RMB["smp_rmb() 讀屏障
屏障前的所有『讀』,都在屏障後的『讀』之前完成
(只管讀的順序)"]
    end
    PAIR["★ 寫屏障與讀屏障通常成對使用 ★
寫方用 smp_wmb 確保寫的順序,
讀方用 smp_rmb 確保讀的順序
→ 兩邊配合才保證跨 CPU 的可見順序"]
    barriers --> PAIR
    style WMB fill:#e8a33d,color:#10100e
    style RMB fill:#6fa8b8,color:#10100e
    style PAIR fill:#8a9a5b,color:#10100e

三種: - smp_mb()(全屏障):屏障前的所有讀寫,都在屏障後的所有讀寫之前完成/可見。最強。 - smp_wmb()(寫屏障):只管「寫」——屏障前的寫都在屏障後的寫之前對別人可見。 - smp_rmb()(讀屏障):只管「讀」——屏障前的讀都在屏障後的讀之前完成。

關鍵:寫屏障和讀屏障通常成對使用——寫方用 smp_wmb 確保「先寫資料、後寫旗標」的順序對別人可見;讀方用 smp_rmb 確保「先讀旗標、後讀資料」的順序。兩邊配合,才能保證跨 CPU 的可見順序正確(這正是 producer-consumer 旗標範例要做的,動手實作會練)。

(smp_ 前綴代表「只在多核心(SMP)時才插入真正的屏障;單核編譯時退化成只有編譯器屏障」——因為單核沒有 CPU 層的跨核重排問題。)

4. acquire / release:成對的順序語意

第三個工具,是更高階、更好理解的成對語意(回顧 P1-T10 第 6 節):smp_store_release / smp_load_acquire。

    subgraph producer["生產方"]
        P1["WRITE_ONCE(data, 42);  ← 準備資料"]
        P2["smp_store_release(&ready, 1);
★ release:保證『之前的所有寫(data=42)』
都在這個 ready=1 之前完成且可見 ★"]
        P1 --> P2
    end
    subgraph consumer["消費方"]
        C1["if (smp_load_acquire(&ready)) {
★ acquire:保證『之後的所有讀』
都在看到 ready=1 之後才進行 ★"]
        C2["  use(data);  ← 保證讀到 42(不會讀到舊 data)"]
        C1 --> C2
    end
    producer -.“release 配 acquire”.-> consumer
    BENEFIT["比裸 smp_wmb/smp_rmb 更好理解、更不易錯:
release『發布』+ acquire『取得』成對,
保證『看到旗標 → 一定看到旗標前的所有資料』"]
    consumer --> BENEFIT
    style P2 fill:#8a9a5b,color:#10100e
    style C1 fill:#6fa8b8,color:#10100e
    style BENEFIT fill:#e8a33d,color:#10100e

語意(回顧 P1-T10): - smp_store_release(&flag, v)(release):保證「在它之前的所有寫」都已完成並可見,才讓這個寫生效。像「我發布前,確保所有準備工作都做完並公開」。 - smp_load_acquire(&flag)(acquire):保證「在它之後的所有讀」都在看到這個值之後才進行。像「我確認拿到入場券後,才開始看裡面的東西」。

acquire/release 比裸的 smp_wmb/smp_rmb 更好理解、更不易出錯——成對使用,直接保證「消費方一旦看到旗標,就一定看到旗標前的所有資料」。這也正是鎖背後的魔法(回顧 P1-T10:mutex 的 lock 帶 acquire、unlock 帶 release)。寫 lock-free 程式碼時,acquire/release 是常用且清楚的工具。

5. 命門:DMA 描述子必須在門鈴前對裝置可見

現在來到這一課對你最關鍵的應用——也是你 DMA 工作的正確性命門。把前面的工具,用到「CPU 和裝置之間」。

DMA 的典型流程:你在記憶體準備一個描述子(描述要做的 I/O),然後寫一個暫存器「按門鈴(doorbell)」通知裝置「有新工作,去讀描述子」。

flowchart TB
    STEP1["① CPU 在記憶體寫好描述子
(要讀/寫哪個位址、多少資料...)"]
    STEP2["② CPU 寫 doorbell 暫存器
(通知 NVMe 裝置:有新工作,去讀描述子)"]
    STEP1 --> STEP2
    DANGER["★ 危險:若這兩個寫入被重排 ★
(門鈴的寫入先對裝置可見,描述子還沒寫好/還沒可見)
→ 裝置收到門鈴,去讀描述子,讀到的是垃圾/舊資料
→ 執行錯誤的 I/O → ★ 資料毀損 ★(對儲存產品是災難)"]
    STEP2 --> DANGER
    FIX["✓ 解法:在『寫描述子』和『按門鈴』之間插入寫屏障
(SMP 間用 smp_wmb;對裝置/DMA 用 dma_wmb,P6 詳述)
→ 保證裝置看到門鈴時,描述子一定已寫好且可見"]
    DANGER --> FIX
    style STEP1 fill:#6fa8b8,color:#10100e
    style DANGER fill:#c2603a,color:#f4ecd8
    style FIX fill:#8a9a5b,color:#10100e

命門(驗收點:用文字解釋為何 DMA 描述子必須在按門鈴前對裝置可見):如果「寫描述子」和「按門鈴」這兩個記憶體操作被重排,使得裝置先看到門鈴、描述子卻還沒寫好(或還沒對裝置可見),裝置就會去讀一個還沒準備好的垃圾描述子,執行完全錯誤的 I/O——對你的儲存產品,這意味著資料被寫到錯誤的地方、或讀到錯誤的資料,即資料毀損。

解法:在「寫描述子」和「按門鈴」之間插入寫屏障,強制「描述子的寫入」在「門鈴的寫入」之前對裝置可見。SMP 之間用 smp_wmb;但對裝置/DMA,要用專門的 dma_wmb/dma_rmb(這預告 P6——裝置 DMA 的可見性比 CPU 之間更複雜,有專門的 DMA 屏障)。

把「加了屏障後的正確順序」畫成時間線,對照前面的災難:

flowchart LR
    A1["寫描述子(到記憶體)"]
    A1 --> BAR2["─── dma_wmb()/smp_wmb() ───
(屏障:確保描述子先對裝置可見)"]
    BAR2 --> A2["寫 doorbell(通知裝置)"]
    A2 --> DEV["裝置收到門鈴 → 去讀描述子
★ 保證讀到已寫好的描述子(不是垃圾)★"]
    style BAR2 fill:#e8a33d,color:#10100e
    style DEV fill:#8a9a5b,color:#10100e

這就是為什麼這一課是 DMA 正確性的根:沒有正確的屏障,你的 DMA 描述子和門鈴可能亂序,裝置讀到舊資料,資料毀損。你現在懂了那個必須插屏障的理由——這個認知會在 P6 變成具體的 dma_wmb 實作。

常見誤區: - 以為有了鎖就永遠不必管 barrier——lock-free 結構、以及裝置/DMA 存取仍需要 barrier(鎖只保證鎖保護的臨界區之間,不管 CPU↔裝置的可見順序)。 - 漏掉「資料寫入」與「旗標/門鈴寫入」之間的屏障——就是上面這個命門,裝置會先看到門鈴後看到資料,讀到舊資料。

6. LKMM 的角色

最後認識 LKMM(Linux Kernel Memory Model)——kernel 對「記憶體操作順序」的形式化模型。

    LKMM["LKMM:Linux Kernel Memory Model

kernel 的記憶體操作(READ_ONCE/WRITE_ONCE、
barrier、acquire/release、原子操作)
的『精確順序語意』
→ 在所有 CPU 架構上的共同保證"]
    WHAT --> WHY["為什麼需要:
不同 CPU 架構重排規則不同(P1-T10),
LKMM 給出一個『架構無關』的模型,
讓你判斷一段 lock-free 程式碼是否正確
(不必為每個架構各想一遍)"]
    WHY --> TOOL["附帶工具:可用形式化檢查器驗證小段並行程式碼
(進階;一般先會用 barrier 工具即可)"]
    style LKMM fill:#6fa8b8,color:#10100e
    style WHY fill:#e8a33d,color:#10100e

LKMM 是 kernel 記憶體順序的「權威規則書」:它形式化定義了 READ_ONCE/barrier/acquire-release/原子操作的精確語意,在所有 CPU 架構上的共同保證。因為不同架構重排規則不同(回顧 P1-T10:x86 嚴格、ARM 寬鬆),LKMM 給出一個架構無關的模型,讓你能判斷「一段 lock-free 程式碼在任何架構上是否正確」,而不必為每個架構各推一遍。它還附帶形式化檢查工具(可驗證小段並行程式碼)。

對你的程度:你不需要精通 LKMM 的形式化細節。目標是:知道它存在、是記憶體順序的權威規則書;會用 barrier/acquire-release 這些工具;懂為什麼 DMA 需要屏障。 真正深入 LKMM 是進階主題;遇到複雜的 lock-free 設計時,再回頭查 LKMM 文件(tools/memory-model/Documentation/)。

一句話總結:把 P1-T10 的「重排恐懼」變成 kernel 工具——READ_ONCE/WRITE_ONCE 管編譯器(不是 volatile)、smp_wmb/smp_rmb(成對)與 acquire/release 管 CPU 重排;而命門是 DMA:描述子必須在按門鈴前對裝置可見,否則裝置讀垃圾描述子導致資料毀損(SMP 用 smp_wmb,對裝置用 dma_wmb)。LKMM 是這一切的架構無關權威規則書。

常見誤區與踩雷提醒

誤區一:以為有了鎖就永遠不必管 barrier。 lock-free 結構、以及裝置/DMA 存取仍需 barrier。鎖只保證臨界區之間,不管 CPU↔裝置的可見順序。

誤區二:以為 volatile 等於 READ_ONCE。 語意不同。READ_ONCE/WRITE_ONCE 是 kernel 為並行存取設計的正確工具;volatile 不該用於 kernel 並行(回顧 P1-T10)。

誤區三:漏掉「資料寫入」與「旗標/門鈴寫入」之間的屏障。 裝置/讀方可能先看到旗標、後看到資料 → 讀到舊資料。DMA 場景這就是資料毀損。要在資料寫入和門鈴之間插寫屏障。

誤區四:誤用過強或過弱的屏障。 過強(到處 smp_mb)傷效能;過弱(該用全屏障卻只用單向)不保證正確。理解每種屏障管什麼(讀/寫/全),用對應的。

動手實作

環境:QEMU 虛擬機。實驗只在 VM。

任務 A — producer-consumer 旗標加屏障(驗收點) 寫一個 module(或先在使用者態用 C11 atomics 練,再對應到 kernel)實作: - producer:WRITE_ONCE(data, 42),然後 smp_wmb()(或 smp_store_release(&ready, 1)),設旗標。 - consumer:讀旗標(smp_load_acquire(&ready) 或 配 smp_rmb()),旗標成立後讀 data,驗證讀到 42。 驗收:正確插入 write/read 屏障(或 store-release/load-acquire),使資料可見性正確(consumer 看到旗標就一定看到 data=42)。

任務 B — 解釋 DMA 命門(驗收點,核心) 用文字解釋:為什麼 DMA 描述子必須在按門鈴(doorbell)前對裝置可見? 如果不保證會發生什麼?驗收:能解釋(若重排使裝置先看到門鈴、描述子未就緒,裝置讀垃圾描述子 → 資料毀損)。

任務 C — 說明 READ_ONCE/WRITE_ONCE 防什麼(驗收點) 寫一句話:READ_ONCE/WRITE_ONCE 防止的是哪類編譯器最佳化?驗收:能說出(防止編譯器把共享變數存取優化掉/快取在暫存器/拆分,即管編譯器層而非 CPU 層)。

任務 D(閱讀)— LKMM 速覽 瀏覽 LKMM 的速查表(tools/memory-model/Documentation/cheatsheet.txt,https://elixir.bootlin.com/linux/v6.12/source/tools/memory-model/Documentation/cheatsheet.txt ）。不求全懂,目標是知道「kernel 有這份記憶體順序的權威規則書」。寫一句話你的理解。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 對 producer-consumer 旗標範例,正確插入 write/read 屏障(或 store-release/load-acquire)使資料可見性正確。 2. ☐ 用文字解釋「為何 DMA 描述子必須在按門鈴前對裝置可見」。 3. ☐ 說出 READ_ONCE/WRITE_ONCE 防止的是哪類編譯器最佳化。

評分量表: - 60(及格):能照樣加屏障。 - 80(熟練):能解釋 acquire/release 與裝置可見性。 - 100(精通):能讀 LKMM 文件並判斷一段 lock-free 程式是否需要屏障。
