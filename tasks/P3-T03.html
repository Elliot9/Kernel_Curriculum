P3-T03 · 第一個 Loadable Kernel Module(init/exit、Kbuild、printk)

一句話:kernel module 不是普通的使用者態程式——它沒有 main、沒有 libc、跑在核心位址空間裡,一個 bug 就能搞垮整個系統。但它正是你公司產品的核心交付物形式,而它的骨架其實只有幾行:一個 init 函式、一個 exit 函式、用 printk 跟核心說話。

為什麼要先學這個(導讀)

這是一個里程碑:你要親手寫第一個 kernel module(LKM)。前面所有的鋪墊——C 功底、系統概念、kernel 架構、編譯設定——都是為了這一刻。而且這直接對應你的工作:你公司產品的核心交付物,就是 kernel module。

kernel module 跟你寫過的所有程式都不一樣,有幾個關鍵差異要先在心裡擺正: - 沒有 main():module 用 module_init(載入時跑)和 module_exit(卸載時跑)兩個進入點,不是 main。 - 沒有 libc:你不能用 printf、malloc、fopen 這些標準函式庫(它們是使用者態的)。module 在核心裡,只能用 kernel 提供的 API(例如用 printk 而非 printf、用 kmalloc 而非 malloc,P3-T07)。 - 跑在核心位址空間:它不是隔離的使用者態行程,而是「成為核心的一部分」(回顧 P3-T01 單體核心)。一個 bug——野指標、記憶體錯誤——就可能搞垮整個系統。

這就是為什麼 P1-T11 反覆強調的鐵則在這裡正式生效:自寫 module 絕對只在 QEMU 虛擬機裡測試,絕不在你的主機。 這一課你會第一次真正載入自己寫的核心程式碼。

為什麼這對你是 scope: direct?因為這就是你日後所有 kernel 工作的起點。你產品的驅動、軟體 RAID 邏輯,全都以 module 的形式存在。這個 hello-world 骨架,是你之後每一個 module 的基礎。

開始之前(前置確認)

  • 依賴:P3-T02(你會編譯/設定 kernel,理解 =m 模組)。也用到 P3-T01(module 在核心空間)、P1-T11(QEMU 環境)。
  • 自我檢測: 1. 你還記得 P3-T01 說「LKM 載入後跑在核心位址空間、無隔離」嗎?這是為什麼 module 的 bug 這麼危險、為什麼只在 VM 測試。 2. 你還記得 P0-T01 的 Makefile 與編譯嗎?module 用一個特別的 Kbuild Makefile。
  • 最重要的前提:這一課你會第一次 insmod 自己寫的 module。只在 QEMU 虛擬機裡做。 在主機上載入有 bug 的 module 可能損毀系統/資料。這是不可妥協的鐵則。

核心內容

拆成這幾節:(1) module 不是普通程式 → (2) 骨架:module_init / module_exit → (3) printk 與 log level → (4) out-of-tree 的 Kbuild Makefile → (5) 載入/卸載循環 → (6) MODULE_LICENSE 與 taint,最後打通關。

1. module 不是普通程式:三個根本差異

先把 module 跟你熟悉的使用者態程式並排,看清差異——這決定了你寫 module 的所有習慣:

    end
    subgraph module["kernel module(全新)"]
        M["用 module_init/module_exit(無 main)

這三個差異要刻進習慣: - 無 main:用 module_init/module_exit 指定載入/卸載時跑的函式。 - 無 libc:printf→printk、malloc→kmalloc(P3-T07)、檔案操作→VFS API。用使用者態的函式庫會編譯失敗或行為錯誤(常見誤區:以為 module 是普通程式)。 - 在核心空間、無保護網:錯誤即影響全系統。這是 VM-only 鐵則的根源。

比喻:寫使用者態程式像在自己家的廚房做菜——搞砸了頂多自己這頓飯難吃。寫 kernel module 像在公共自來水廠裡動工——你接的每根管子都直通整個城市的供水,一個閥門裝錯,全城都遭殃。所以你只在「測試用的模型廠」(QEMU)裡練手,絕不直接動真正的供水廠(你的主機)。

2. 骨架:module_init 與 module_exit

一個最小的 module,核心就是兩個函式 + 兩個註冊巨集:

#include <linux/module.h>
#include <linux/init.h>

static int __init hello_init(void)   // 載入時執行
{
    pr_info("hello: module loaded\n");
    return 0;                          // 回傳 0 = 載入成功
}

static void __exit hello_exit(void)  // 卸載時執行
{
    pr_info("hello: module unloaded\n");
}

module_init(hello_init);   // 註冊:insmod 時呼叫 hello_init
module_exit(hello_exit);   // 註冊:rmmod 時呼叫 hello_exit
MODULE_LICENSE("GPL");


flowchart LR
    INSMOD["insmod hello.ko"] --> INIT["呼叫 hello_init()
(你的初始化:配資源、註冊裝置等)
回傳 0 成功 / 負數失敗"]
    INIT --> RUNNING["module 載入中
(留在核心裡,等待事件/被使用)"]
    RUNNING --> RMMOD["rmmod hello"]
    RMMOD --> EXIT["呼叫 hello_exit()
(你的清理:釋放資源、註銷裝置等)"]
    style INIT fill:#8a9a5b,color:#10100e
    style EXIT fill:#e8a33d,color:#10100e

要點: - hello_init 在 insmod 時執行,做初始化(回傳 0 表成功;回傳負的錯誤碼表失敗,module 不會載入)。 - hello_exit 在 rmmod 時執行,做清理。 - module_init/module_exit 巨集把你的函式註冊為進入點。 - __init/__exit 是給 kernel 的提示(__init 的程式碼在初始化後可釋放以省記憶體)。

關鍵原則(呼應 P0-T06 的資源配對):init 裡配置/註冊的東西,exit 裡要全部對應地釋放/註銷。 module 可以反覆 insmod/rmmod,每次都要乾淨——這跟 malloc/free 配對是同一個紀律,只是規模放到了核心資源。

3. printk 與 log level:module 怎麼說話

module 不能用 printf(無 libc)。它用 printk 把訊息輸出到核心訊息緩衝區,你用 dmesg 命令查看。

(kernel log buffer)"]
    DMESG["dmesg 命令
(查看核心訊息)"]

printk 有訊息等級(log level),從緊急到除錯。實務上用包裝好的巨集更方便:

flowchart TB
    subgraph levels["printk 等級(由高到低,常用包裝)"]
        ERR["pr_err()   — 錯誤(KERN_ERR)"]
        WARN["pr_warn()  — 警告"]
        INFO["pr_info()  — 一般資訊(最常用)"]
        DBG["pr_debug() — 除錯(預設可能不顯示,需開動態除錯,P3-T13)"]
    end

    style INFO fill:#8a9a5b,color:#10100e
    style DEV fill:#6fa8b8,color:#10100e

要點: - 用 pr_info/pr_err/pr_warn 等包裝(比裸 printk + 等級常數清楚)。 - 訊息結尾要加 \n(常見誤區:沒加換行,訊息會黏連在一起)。 - pr_debug 預設可能不顯示,要開動態除錯(P3-T13)。 - 寫驅動時優先用 dev_info/dev_err(P4),會自動標示是哪個裝置。

dmesg 是你 module 開發的眼睛——load/unload 訊息、錯誤、debug 輸出都從這裡看(回顧 P1-T11 你也是用它看開機訊息)。

4. out-of-tree 的 Kbuild Makefile

你的 module 不在 kernel 原始碼樹裡(叫 out-of-tree 模組),要用一個特別的 Makefile 來編,它借用 kernel 的 build 系統(Kbuild):

obj-m += hello.o          # 告訴 Kbuild:把 hello.c 編成模組 hello.ko

all:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean


flowchart TB
    OBJM["obj-m += hello.o
= 核心指令:把 hello.c 編成 .ko 模組
(對比 P3-T02 的 =m,但這是 out-of-tree)"]
    MAKEC["make -C  M=$(PWD) modules
= 借用已編好的 kernel 的 build 系統,
在你的目錄(M=$(PWD))編你的模組"]
    KO["產出 hello.ko
(可 insmod 的模組檔)"]
    OBJM --> MAKEC --> KO
    style OBJM fill:#e8a33d,color:#10100e
    style KO fill:#8a9a5b,color:#10100e

關鍵理解: - obj-m += hello.o:告訴 Kbuild「把 hello.c 編成模組 hello.ko」(obj-m 就是「object as module」)。 - make -C <kernel build 路徑> M=$(PWD) modules:-C 切到 kernel 的 build 目錄(借用它的 build 系統與標頭檔),M=$(PWD) 告訴它「要編的模組在我這個目錄」。 - 產出 hello.ko,這就是你能 insmod 的模組檔。

(這跟 P0-T01 的小 Makefile、P1-T11/P3-T02 的 kernel 編譯一脈相承——都是 make,只是這裡是「借 kernel 的 build 系統編一個外部模組」。)

5. 載入/卸載循環:insmod / rmmod / modprobe / lsmod

四個你天天用的命令(全部在 QEMU 裡執行):

    subgraph commands["module 管理命令(在 VM 裡)"]
        INSMOD["insmod hello.ko
= 載入這個 .ko 檔(直接指定檔案)
→ 觸發 module_init"]
        RMMOD["rmmod hello
= 卸載這個模組
→ 觸發 module_exit"]
        MODPROBE["modprobe hello
= 載入模組 + 自動處理相依

        LSMOD["lsmod
= 列出目前載入的模組"]
    end
    style INSMOD fill:#8a9a5b,color:#10100e
    style RMMOD fill:#e8a33d,color:#10100e

典型開發循環: 1. 在 VM 裡 insmod hello.ko → dmesg 看到 "module loaded"。 2. lsmod | grep hello → 確認它載入了。 3. rmmod hello → dmesg 看到 "module unloaded"。 4. 改 code → 重編(make)→ 回到步驟 1。

insmod 直接載入一個 .ko 檔;modprobe 更聰明(從 /lib/modules 找、自動處理相依——P3-T04 會深入)。開發時你常用 insmod(直接指定剛編好的 .ko)。

6. MODULE_LICENSE 與 taint:為什麼一定要宣告授權

最後一個重要細節:每個 module 應該宣告 MODULE_LICENSE。這不只是形式:

flowchart TB
    LICENSE["MODULE_LICENSE("GPL");"]
    LICENSE --> WHY1["① 宣告授權(法律/合規)"]
    LICENSE --> WHY2["② 決定能否使用 GPL-only 的核心符號
(很多 kernel 函式只給 GPL 模組用,P3-T04)"]
    NOLICENSE["若不宣告(或宣告非 GPL):
★ 核心被『汙染(taint)』★
dmesg 出現 taint 警告;
且無法使用 GPL-only 符號
(可能連載入都受影響或功能受限)"]
    LICENSE -.“缺少則”.-> NOLICENSE
    style LICENSE fill:#8a9a5b,color:#10100e
    style NOLICENSE fill:#c2603a,color:#f4ecd8

關鍵: - MODULE_LICENSE("GPL") 宣告 module 的授權。 - 缺少它(或宣告非 GPL 授權)會「汙染(taint)」核心——dmesg 會出現 taint 警告,表示核心載入了非自由或未宣告授權的程式碼。這在回報 bug 時是個訊號(社群通常不處理被汙染核心的問題)。 - 更實際的:很多 kernel 函式是 GPL-only 的(用 EXPORT_SYMBOL_GPL 匯出,P3-T04),非 GPL module 不能用它們。

常見誤區:忘記 MODULE_LICENSE("GPL"),導致 taint 或無法使用 GPL-only 符號。養成習慣:每個 module 都加上(連同 MODULE_AUTHOR、MODULE_DESCRIPTION 一起)。你會在動手實作裡故意拿掉它,觀察 taint 警告。

一句話總結:kernel module 沒有 main、沒有 libc、跑在核心空間(bug 即危及全系統,故只在 QEMU 測),骨架是 module_init/module_exit(資源配對釋放),用 printk→dmesg 溝通,用 out-of-tree Kbuild Makefile 編譯,並務必宣告 MODULE_LICENSE("GPL")。這個 hello-world 骨架,是你公司產品每一個 module 的起點。

常見誤區與踩雷提醒

誤區一(鐵則):在 host 上 insmod 自寫 module。 務必只在 QEMU 虛擬機。module 在核心空間,bug 可能損毀系統/資料(回顧 P1-T11/P3-T01)。不可妥協。

誤區二:以為 module 是普通使用者態程式。 它無 main、無 libc、在核心空間。用 printf/malloc 會失敗;要用 printk/kmalloc 等 kernel API。

誤區三:忘記 MODULE_LICENSE("GPL")。 導致核心 taint、且無法使用 GPL-only 符號(P3-T04)。每個 module 都加。

誤區四:printk/pr_info 訊息沒加 \n。 訊息會黏連在一起。每則訊息結尾加換行。

誤區五:init 配置了資源,exit 沒對應釋放。 module 可反覆載入/卸載,每次都要乾淨(資源配對,如 P0-T06 malloc/free)。exit 要釋放 init 配的所有東西。

動手實作

環境:QEMU 虛擬機(P1-T11 建好的)。所有 insmod/rmmod 只在 VM 裡。絕不在主機。

任務 A — hello-world module(驗收點) 寫第 2 節那個 hello module(hello_init 印一則、hello_exit 印另一則,記得 MODULE_LICENSE("GPL") 和訊息加 \n)。寫第 4 節的 Kbuild Makefile。編譯出 hello.ko。在 QEMU 裡: - insmod hello.ko → dmesg 確認出現 init 訊息。 - rmmod hello → dmesg 確認出現 exit 訊息。 驗收:insmod 後 dmesg 有 init 訊息、rmmod 後有 exit 訊息。

任務 B — lsmod 驗證(驗收點) insmod hello.ko 後,lsmod | grep hello 確認看得到你的模組。驗收:lsmod 能看到該模組。

任務 C — 故意移除 MODULE_LICENSE 觀察 taint(驗收點) 把 MODULE_LICENSE("GPL") 那行註解掉,重編、載入,觀察 dmesg 出現的 taint 警告(類似 "module verification failed" 或 "tainting kernel")。寫一句話解釋 taint 是什麼、為什麼會發生。驗收:能觀察到 taint 警告並解釋。 然後把授權加回去。

任務 D — 解釋核心空間執行的意涵 寫一兩句話:module 跑在核心位址空間(無 libc、錯誤即影響全系統)這件事,對你寫 code 的習慣有什麼影響?(提示:為什麼只在 VM 測、為什麼不能用使用者態函式、為什麼要格外小心記憶體錯誤。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ module 成功 insmod 後 dmesg 出現 init 訊息、rmmod 後出現 exit 訊息。 2. ☐ lsmod 能看到該模組。 3. ☐ 故意移除 MODULE_LICENSE 觀察 taint 警告並解釋。

評分量表: - 60(及格):能載入/卸載並印 log。 - 80(熟練):能寫出乾淨的 Makefile 與 module。 - 100(精通):能解釋 module 在核心位址空間執行的意涵(無 libc、錯誤即影響全系統)。
