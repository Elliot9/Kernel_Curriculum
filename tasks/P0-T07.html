P0-T07 · 函式指標與 callback

一句話:指標不只能指向資料,也能指向「一段程式碼」。把一組函式指標裝進一個 struct,你就得到了 kernel 用來實現「物件導向式多型」的核心手法——你寫的每一個驅動,都會填這樣一張表。

為什麼要先學這個(導讀)

在 JS 裡,你天天傳函式:arr.map(x => x * 2)、button.onclick = handler、setTimeout(fn, 1000)。函式是「一等公民」,可以當參數、當回傳值、塞進物件。你早就熟悉這個概念,只是從沒想過它在底層怎麼運作。

C 也能做到同樣的事,工具叫函式指標(function pointer)。原理和你已學的指標完全一樣:函式編譯後是一段機器碼,住在 text 區(回顧 P0-T05),有個起始位址。函式指標就是「存放這個位址的變數」。透過它,你可以「呼叫一個事先不知道是哪個」的函式。

為什麼這對 kernel 至關重要?因為 kernel 是純 C 寫的,沒有 class、沒有繼承、沒有 virtual method。但 kernel 偏偏需要「多型」——同一個 read() 系統呼叫,對普通檔案、對你的裝置、對網路 socket,要執行完全不同的程式碼。kernel 怎麼做到?

答案就是函式指標:每個裝置驅動填一張「函式指標表」(例如 file_operations),裡面放各自的 read / write / open 實作。當使用者對某個裝置呼叫 read,kernel 就透過那張表裡的 .read 函式指標,呼叫到「這個裝置專屬的」read。這就是 kernel 的「物件導向」,而它的全部魔法就是函式指標。 看懂函式指標,你才看得懂半個 kernel。

開始之前(前置確認)

  • 依賴:P0-T06(你已掌握指標的核心觀念、解參考)。
  • 自我檢測: 1. 你在 JS 裡寫過 callback(setTimeout(fn, ...)、arr.sort(compareFn))嗎?那個「把函式當參數傳」的感覺,就是這課的目標,只是換成 C 的寫法。 2. 你還記得 P0-T05 說「程式碼住在 text 區、有位址」嗎?函式指標就是存那個位址。

核心內容

拆成這幾節:(1) 函式也有位址 → (2) 宣告一個函式指標(拆解嚇人語法)→ (3) 透過函式指標呼叫 → (4) callback:把函式當參數傳 → (5) 高潮:函式指標 struct = kernel 的物件 → (6) file_operations 的 dispatch 流程,最後打通關。

1. 函式也有位址

int add(int a, int b) { return a + b; }

int main(void) {
    printf("add 的位址 = %p\n", (void*)add);  // 函式名 add 就是它的位址
    return 0;
}

就像陣列名會退化成指向開頭的指標(P0-T03),函式名也代表函式的位址。add 和 &add 在 C 裡等價——都是那段機器碼在 text 區的起始位址。

既然函式有位址,你就能用一個變數存這個位址——那個變數就是函式指標。

2. 宣告一個函式指標:拆解這個嚇人的語法

函式指標的宣告語法,是 C 裡最容易嚇退新手的部分。我們一層一層拆:

int (*fp)(int, int);

由內而外讀:

    L4["int (*fp)(int, int)

那對括號 (*fp) 絕對不能少。 它是分水嶺: - int (*fp)(int); → fp 是「指向函式的指標」(正確) - int *fp(int); → 完全不同!這是宣告一個「回傳 int* 的函式 fp」

差別在於 * 是先和 fp 結合(加括號 → 指標),還是先和回傳型別結合(不加括號 → 回傳指標的函式)。這個坑下面誤區還會強調。

4. callback:把函式當參數傳

這就是你熟悉的 JS callback,換成 C。一個函式可以接受另一個函式當參數,在需要時呼叫它:

// 一個排序函式,接受「怎麼比較」當參數
void sort_with(int *arr, int n, int (*compare)(int, int)) {
    // ... 排序邏輯中,每當需要比較兩個元素,就呼叫 compare(a, b) ...
}


flowchart TB
    GENERIC["sort_with:知道『怎麼排序』
但不知道『你想怎麼比較』"]
    GENERIC -->|"你把比較函式當參數傳進去"| CB["compare 函式指標"]
    CB --> EX1["傳升冪比較 → 排成升冪"]
    CB --> EX2["傳降冪比較 → 排成降冪"]

達成不同行為"]
    EX1 --> NOTE
    EX2 --> NOTE
    EX3 --> NOTE
    style GENERIC fill:#6fa8b8,color:#10100e
    style NOTE fill:#e8a33d,color:#10100e

標準庫的 qsort 就是這樣設計的——它知道「怎麼排序」,但不知道「怎麼比較你的資料」,所以要你傳一個比較函式進去。這讓 qsort 一套程式碼能排任何型別的資料。這就是 callback 的核心價值:把「通用流程」和「可變的細節」分離。

5. 高潮:把一組函式指標裝進 struct = kernel 的「物件」

這是本課最重要的觀念,請慢讀。

把多個函式指標裝進一個 struct:

struct operations {
    int (*add)(int, int);
    int (*sub)(int, int);
};

int my_add(int a, int b) { return a + b; }
int my_sub(int a, int b) { return a - b; }

int main(void) {
    struct operations ops = { .add = my_add, .sub = my_sub };
    printf("%d\n", ops.add(3, 4));   // 透過 struct 成員呼叫 → 7
    printf("%d\n", ops.sub(9, 2));   // → 7
    return 0;
}

看出來了嗎?ops 這個 struct 就像一個「物件」,ops.add(...) 就像呼叫「物件的方法」。但底層沒有任何 class 機制——只是「一個裝著函式指標的 struct」。

kernel 把這個手法用到極致。最經典的就是 file_operations:

// kernel 裡(簡化版)
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    // ... 還有幾十個函式指標 ...
};

每個裝置驅動建立自己的 file_operations,填入自己的 read / write / open 函式。這就是「介面與實作分離」:file_operations 是介面(承諾「我有 read/write/open」),每個驅動是實作(各自填入不同內容)。

6. file_operations 的 dispatch:一次 read 怎麼找到「你的」read

關鍵在中間那步:kernel 不需要知道「是哪個驅動」。它只認 file_operations 這個介面、透過 .read 函式指標呼叫,執行期自然跳到「這個裝置填的那個 read」。換一個裝置,同樣的 read() 呼叫就跳到另一個驅動的 read——這正是物件導向「多型」的本質,只是用 C 的函式指標手刻出來。

你日後寫字元裝置 / 區塊裝置驅動(Phase 4),做的第一件事之一,就是填一張這樣的函式指標表。今天你理解了它的原理,到時候就不是照抄範本,而是知道每個欄位為什麼存在。

一句話總結:函式指標讓「程式碼」也能像資料一樣被存放與傳遞;而『一組函式指標裝進 struct』就是 kernel 在沒有 class 的情況下,實現「介面/實作分離」與「多型」的全部祕密。 你之後在 kernel 裡看到的每一張 *_operations 表,都是這個心智模型的實例。

常見誤區與踩雷提醒

誤區一:函式指標宣告的括號漏了。

int (*fp)(int);   // 正確:fp 是「指向函式的指標」
int *fp(int);     // 完全不同!這是宣告一個「回傳 int* 的函式 fp」

那對 (*fp) 的括號是分水嶺。漏了,意思就從「函式指標變數」變成「回傳指標的函式宣告」。編譯器可能不報錯(因為兩者都是合法宣告),但你的意圖全錯了。

誤區二:以為要寫 &func 才能取得函式位址。 函式名本身就是位址,func 和 &func 等價;呼叫時 fp(x) 和 (*fp)(x) 也等價。C 對函式指標的取址與呼叫特別寬容,兩種寫法都對,別困惑。

誤區三:callback 的簽章不符卻硬塞。 如果一個函式指標宣告為 int (*)(int, int),你卻塞一個 int (*)(int) 進去並呼叫,是未定義行為(參數對不上,stack 會亂)。傳 callback 時,函式的參數與回傳型別必須和指標宣告完全一致。

誤區四:忘記 ops 結構裡沒填的函式指標是 NULL。 如果你建立一個 file_operations 只填了 .read,沒填的成員預設是 NULL。kernel 在呼叫前通常會檢查「這個函式指標是不是 NULL」,但你自己設計 ops 表時,要記得「沒填 = NULL = 呼叫會崩潰」,該檢查就檢查。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 用標準庫 qsort 傳 callback

#include <stdlib.h>
#include <stdio.h>
int cmp(const void *a, const void *b) {   // qsort 要求的比較函式簽章
    return (*(int*)a) - (*(int*)b);       // 升冪
}
int main(void) {
    int arr[5] = {3, 1, 4, 1, 5};
    qsort(arr, 5, sizeof(int), cmp);      // 把 cmp 當 callback 傳給 qsort
    for (int i = 0; i < 5; i++) printf("%d ", arr[i]);  // 1 1 3 4 5
    return 0;
}

(qsort 的比較函式用 const void* 是為了通用任何型別,你在裡面轉回 int*——這個「通用指標 void」的手法,回顧 P0-T02 誤區提過,之後在 kernel 也常見。)進階*:再寫一個降冪的 cmp_desc,只換傳入的 callback,不動 qsort,看陣列變降冪——親身體會「一套流程、不同 callback、不同結果」。

任務 B — 自己的 ops 結構 完成本課那個 struct operations,填入 my_add/my_sub,透過 struct 成員呼叫,驗證結果。然後故意不填 .sub,呼叫 ops.sub(...) 看會怎樣(在 VM 裡:對 NULL 函式指標呼叫 → 崩潰),體會誤區四。

任務 C — 讀懂 kernel 的 file_operations 打開 kernel 原始碼的 include/linux/fs.h(用 Bootlin Elixir:https://elixir.bootlin.com/linux/v6.12/source/include/linux/fs.h ),找到 struct file_operations。先別怕那幾十個成員——挑出 .read 或 .write,用本課第 2 節的「由內而外讀法」說出它的型別:它是個指向什麼樣函式的指標?(這就是你之後寫驅動要填的東西。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用標準 qsort 傳入自寫比較函式,對 5 個整數正確升冪排序;並能換一個 callback 得到降冪。 2. ☐ 定義 struct ops { int (*add)(int,int); int (*sub)(int,int); },填入實作後透過 struct 成員呼叫得到正確結果。 3. ☐ 能用「由內而外讀法」讀懂並解釋 file_operations 中任一函式指標成員的型別。
