P7-T01 · Linux 軟體 RAID(md / dm-raid)與 raid5.c 概覽

一句話:你公司做的就是軟體 RAID——Linux 的 md 子系統(drivers/md/)實作它,而 raid5.c 一份程式碼同時處理 RAID-4/5/6。理解它的「條帶(stripe)處理」和「parity 計算呼叫點」,是理解(並改進/offload)你產品的基礎。從「一個 stripe 怎麼被處理」切入,別被龐大程式碼淹沒。

為什麼要先學這個(導讀)

歡迎來到 Phase 7——最後一個階段,把前面所有東西組成你的產品。你走過了 C 功底、系統概念、kernel 機制、裝置驅動、block/NVMe、DMA/P2PDMA;現在把它們收斂到你產品的本體:軟體 RAID + parity 計算 + GPU offload。

第一課,跟每個階段一樣,先建立全景——這次是你產品所在的子系統:Linux 軟體 RAID。

Linux 有兩個管理軟體 RAID 的介面,但底層共用同一套 RAID 邏輯: - md(multiple devices):傳統的軟體 RAID,用 mdadm 管理。 - dm-raid:透過 device-mapper 框架管理 RAID,但底層用的是同一套 md 的 RAID 個性(personality)程式碼。

RAID 的層級(你應該已熟悉概念,這裡對應到 Linux): - RAID 0(條帶化,無冗餘)、RAID 1(鏡像)、RAID 5(單 parity,容忍一碟失效)、RAID 6(雙 parity,容忍兩碟失效)、RAID 10(鏡像+條帶)。

核心程式碼:drivers/md/raid5.c——它一份程式碼同時處理 RAID-4/5/6(它們的 parity 機制相關)。關鍵概念: - 條帶(stripe)、chunk、parity 配置:資料怎麼跨多顆碟分布。 - stripe cache 與寫入路徑:read-modify-write vs reconstruct-write(RAID 寫入的兩種策略)。 - degraded / rebuild 狀態:一顆碟失效後的降級運行與重建。

為什麼這對你是 scope: direct(產品本體)?因為你公司做的就是軟體 RAID。理解 md / raid5.c 的條帶與 parity 路徑,是理解、改進、或 offload(把 parity 計算搬到 GPU)你產品的基礎。這一課是 Phase 7 的地圖——後面 P7-T02/P7-T03 深入 parity 數學、P7-T04 看 kernel 的 parity 實作、P7-T05/P7-T06 把 parity offload 到 GPU。

(讀 raid5.c 是你 P5-T06 讀 NVMe 驅動經驗的延續——同樣龐大、同樣要「從單一路徑切入」。)

RAID 層級:RAID 0(條帶、無冗餘)、RAID 1(鏡像)、RAID 5(單 parity P,容忍一碟)、RAID 6(雙 parity P+Q,容忍兩碟)、RAID 10(鏡像+條帶)。

你產品的核心是 RAID-5/6 的 parity:RAID-5 的 P 是資料的 XOR(P7-T02);RAID-6 的 P+Q 是 XOR + GF(2⁸) Reed-Solomon(P7-T03)。這些 parity 計算是計算密集的,正是你要 offload 到 GPU 的部分(P7-T05/P7-T06)。

理解這個,你就抓到 Phase 7 的主軸:RAID-5/6 的 parity 數學(P7-T02/P7-T03)→ kernel 怎麼算(P7-T04)→ 怎麼搬到 GPU 算(P7-T05/P7-T06)。而你的「XOR→parity→GPU 平行」主線(從 P0-T11 開始)正在這裡收束。

3. 條帶 stripe / chunk:資料怎麼跨碟分布

RAID 的核心概念:資料以 chunk 為單位,跨多顆碟組成 stripe(條帶)。

    DISKS["假設 RAID-5,4 顆碟(D0 D1 D2 + P)"]
    DISKS --> STRIPE3["一個 stripe(條帶)= 跨所有碟的『同一橫排』
每顆碟在這個 stripe 上貢獻一個 chunk"]
    STRIPE3 --> LAYOUT["stripe 0:[資料chunk@D0][資料chunk@D1][資料chunk@D2][parity@D3]

(RAID-5 把 parity 分散到各碟,避免單一 parity 碟成瓶頸)"]
    LAYOUT --> PARITY3["★ 關鍵:一個 stripe 的 parity chunk
= 該 stripe 所有資料 chunk 的 XOR(P7-T02)★
→ parity 計算是『per-stripe』的"]
    style STRIPE3 fill:#6fa8b8,color:#10100e
    style PARITY3 fill:#e8a33d,color:#10100e

  • chunk:每顆碟上的一塊(RAID 條帶化的單位)。
  • stripe(條帶):跨所有碟的「同一橫排」——每顆碟在這個 stripe 上貢獻一個 chunk。
  • parity 配置:RAID-5 把 parity 輪轉(rotate)到不同碟(stripe 0 的 parity 在 D3、stripe 1 在 D2……),避免單一 parity 碟成為寫入瓶頸。

關鍵:一個 stripe 的 parity chunk = 該 stripe 所有資料 chunk 的 XOR(P7-T02)。所以 parity 計算是 per-stripe 的——這是理解 raid5.c(以 stripe 為處理單位)和 parity offload(每個 stripe 的 parity 可獨立、平行計算)的基礎。

對你產品:你要 offload 的就是「每個 stripe 的 parity 計算」——而 stripe 之間獨立、stripe 內逐 byte 獨立,這雙重的獨立性正是 GPU 平行的來源(P7-T02 會深入)。

4. 寫入路徑:read-modify-write vs reconstruct-write

RAID-5/6 寫入有個重要的效能議題:寫入放大。改一小塊資料,parity 也要更新,有兩種策略。

flowchart TB
    WRITE4["要寫入一個 stripe 裡的一部分資料(不是整個 stripe)"]

    CHOICE3 --> RMW["① read-modify-write(RMW):

→ 適合『只改一小部分』(讀的少)"]

→ 適合『改一大部分』(反正要讀的多)"]
    RMW --> AMP["★ 寫入放大(常見誤區:忽略它)★
改一小塊資料,卻要額外讀寫 parity(和相關資料)
→ 一次邏輯寫入,變成多次實體 I/O
(這是 RAID-5/6 寫入效能的關鍵成本)"]

    style RMW fill:#6fa8b8,color:#10100e
    style RECON fill:#8a9a5b,color:#10100e

兩種寫入策略: - read-modify-write(RMW):讀「舊資料 + 舊 parity」→ 算新 parity(新 parity = 舊 parity ⊕ 舊資料 ⊕ 新資料,用 XOR 的性質,P7-T02)。適合只改一小部分(讀的少)。 - reconstruct-write:讀「該 stripe 其餘所有資料」→ 用全部資料重算 parity。適合改一大部分。

raid5.c 會依「改動的比例」選擇哪種策略(讀的少的那種)。

常見誤區:忽略 RAID-5/6 的寫入放大(read-modify-write)——改一小塊資料,卻要額外讀寫 parity(和相關資料），一次邏輯寫入變成多次實體 I/O。這是 RAID-5/6 寫入效能的關鍵成本。對你產品:寫入放大意味著 parity 計算頻繁觸發——這正是「offload 到 GPU 能減輕 CPU 負擔」的動機(parity 算得多、又計算密集)。

5. raid5.c 的 stripe 處理

進入程式碼——raid5.c 以 stripe 為處理單位,用 stripe cache 管理進行中的 stripe。

flowchart TB
    BIO4["上層 bio 進來(對 RAID 陣列的讀/寫,P5-T02)"]
    BIO4 --> MAP5["raid5.c:把 bio 對應到它涉及的 stripe(s)
(算出涉及哪些 stripe、哪些 chunk)"]
    MAP5 --> CACHE["stripe cache:管理進行中的 stripe
(struct stripe_head 代表一個進行中的 stripe)
→ 一個 stripe 的所有操作(讀缺的、算 parity、寫)在這協調"]
    CACHE --> STATE["stripe 狀態機:
① 缺哪些資料?要先讀進來
② 算 parity(★ 呼叫 parity 計算,連結 lib/raid6,P7-T04 ★)
③ 寫資料 + parity 到各碟"]
    STATE --> PARITYCALL["★ parity 計算的呼叫點(驗收要找的)★
raid5.c 在處理 stripe 時呼叫 lib/raid6 的
gen_syndrome(算 P/Q)等 → 這是你 offload 的切入點"]

    style STATE fill:#e8a33d,color:#10100e
    style PARITYCALL fill:#8a9a5b,color:#10100e

raid5.c 的處理(用 P5-T06 的單一路徑切入法): - 上層 bio 進來 → 對應到它涉及的 stripe(s)。 - stripe cache:用 struct stripe_head 代表一個進行中的 stripe，協調它的所有操作。 - stripe 狀態機:① 缺哪些資料先讀進來 → ② 算 parity(呼叫 parity 計算，連結 lib/raid6，P7-T04）→ ③ 寫資料 + parity 到各碟。

parity 計算的呼叫點(驗收點:在 raid5.c 中指出 parity 計算被呼叫的大致位置)：raid5.c 在處理 stripe 時呼叫 lib/raid6 的 gen_syndrome(算 P/Q）等。這是你 offload 的切入點——你要把 parity 計算搬到 GPU，就是在這個呼叫點，把「呼叫 CPU 的 lib/raid6」換成「呼叫你的 GPU parity 計算」。

常見誤區:被 raid5.c 的龐大程式碼淹沒——它很大、處理很多狀態。從「一個 stripe 怎麼被處理」切入(回顧 P5-T06 讀碼策略):追一個 stripe 從「bio 進來」到「算 parity、寫出」，你就抓到主幹，不會在無關的程式碼裡迷路。

6. degraded 與 rebuild:碟失效後

RAID 的價值在容錯——一顆碟失效後的 degraded(降級) 運行與 rebuild(重建)。

    NORMAL["正常運行:所有碟都在"]
    NORMAL --> FAIL["一顆碟失效"]
    FAIL --> DEGRADED["★ degraded(降級)狀態 ★

degraded(即時還原)和 rebuild(大量重算)都顯著影響效能

    style DEGRADED fill:#e8a33d,color:#10100e
    style REBUILD fill:#c2603a,color:#f4ecd8

  • degraded(降級):一顆碟失效後，陣列仍可運行（RAID-5 容忍一顆、RAID-6 兩顆），但讀失效碟的資料要用其餘資料 + parity 即時還原（P7-T02），效能下降。
  • rebuild(重建)：換上新碟後，用其餘碟的資料 + parity 重算出失效碟的全部內容，寫到新碟。重建期間效能進一步下降；且若重建期間又壞一顆（超過容錯）→ 資料遺失。

常見誤區:以為 rebuild 期間效能不受影響——degraded(即時還原）和 rebuild(大量重算）都顯著影響效能（驗收點:模擬一顆碟失效，觀察並描述 degraded→rebuild 過程）。

對你產品:degraded 的即時還原、rebuild 的大量重算，都是 parity 運算（還原 = 用 parity 反推資料，P7-T02/P7-T03）。所以 parity offload 到 GPU 不只幫助寫入時的 parity 產生，也能加速 degraded/rebuild 時的還原計算——對你產品是全面的效益。

常見誤區與踩雷提醒

誤區一:混淆 md 與 dm-raid。 它們是不同的管理介面,但 RAID 核心邏輯(條帶、parity、rebuild)共用同一套 personality 程式碼。改 raid5.c 兩者都受影響。

誤區二:忽略 RAID-5/6 的寫入放大(read-modify-write)。 改一小塊資料卻要額外讀寫 parity,一次邏輯寫入變多次實體 I/O。這是 RAID-5/6 寫入效能的關鍵成本,也是 offload parity 的動機。

誤區三:以為 rebuild 期間效能不受影響。 degraded(即時還原)和 rebuild(大量重算)都顯著影響效能。兩者都是 parity 運算。

誤區四:被 raid5.c 的龐大程式碼淹沒。 從「一個 stripe 怎麼被處理」切入(回顧 P5-T06),追一個 stripe 從 bio 進來到算 parity、寫出,抓住主幹。

動手實作

環境:QEMU 虛擬機 + loop device 或 null_blk(建 RAID 陣列實驗只在 VM)。

任務 A — 建 RAID-6 陣列(驗收點) 用 loop device(losetup)或 null_blk 造幾個虛擬「碟」,用 mdadm --create 建一個 RAID-6 陣列。從 /proc/mdstat 確認狀態(層級、碟數、同步狀態)。看 /sys/block/mdX/md/ 的屬性。驗收:用 mdadm 建立一個 RAID-6 陣列並從 /proc/mdstat 確認狀態。

任務 B — 模擬碟失效與 rebuild(驗收點) 用 mdadm --fail 故意標記一顆碟失效,觀察 /proc/mdstat 進入 degraded;移除失效碟、加入新碟(mdadm --remove/--add),觀察 rebuild 過程(/proc/mdstat 顯示重建進度)。驗收:模擬一顆碟失效,觀察並描述 degraded→rebuild 過程。

任務 C — 在 raid5.c 找 parity 呼叫點(驗收點) 在 drivers/md/raid5.c(https://elixir.bootlin.com/linux/v6.12/source/drivers/md/raid5.c ）中,用 P5-T06 的讀碼法(從 stripe 處理切入),找出 parity 計算被呼叫的大致位置(搜尋 syndrome/xor/呼叫 lib/raid6 的地方)。驗收:在 raid5.c 中指出 parity 計算被呼叫的大致位置(連結 lib/raid6)。

任務 D(連結)— 你 offload 的切入點 寫一兩句話:你要把 parity 計算 offload 到 GPU,大致會在 raid5.c 的哪個環節介入?(提示:stripe 處理時呼叫 parity 計算的那一點;P7-T05/P7-T06 會深入。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 mdadm 建立一個 RAID-6 陣列並從 /proc/mdstat 確認狀態。 2. ☐ 模擬一顆碟失效,觀察並描述 degraded→rebuild 過程。 3. ☐ 在 raid5.c 中指出 parity 計算被呼叫的大致位置(連結 lib/raid6)。

評分量表: - 60(及格):能用 mdadm 建陣列。 - 80(熟練):能解釋 stripe/parity 與寫入路徑。 - 100(精通):能在 raid5.c 中追條帶處理並對應到 parity 計算。
