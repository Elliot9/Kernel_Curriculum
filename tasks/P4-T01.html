P4-T01 · Linux Device Model(device / driver / bus / class / kobject / sysfs)

一句話:Linux 用一個統一模型描述「裝置、驅動、匯流排」三者的關係——裝置掛在匯流排上、驅動登記想認領的裝置、匯流排在兩者間做媒合(match),媒合成功就呼叫驅動的 probe。你在 /sys 看到的一切、你寫的每個驅動,都建立在這個模型上。

為什麼要先學這個(導讀)

歡迎來到 Phase 4——你的 module 從這裡開始真正跟硬體裝置打交道。P3-T15 你寫的 misc 裝置只是最簡單的形式;這個階段要學裝置驅動的完整骨架,而第一步是理解 Linux 用什麼模型來組織「裝置與驅動」。

核心問題:系統裡有成千上萬種硬體(NVMe SSD、GPU、網卡、USB 裝置……),掛在各種匯流排上(PCI、USB、I2C……)。Linux 需要一個統一的方式來描述「有哪些裝置、誰是它的驅動、它掛在哪條匯流排」,並自動把裝置和對的驅動配對起來。這就是 Linux Device Model(裝置模型)。

它的幾個核心抽象: - struct device:代表一個「裝置」(一個 NVMe 控制器、一個 GPU)。 - struct device_driver:代表一個「驅動」(能操作某類裝置的程式碼)。 - struct bus_type:代表一條「匯流排」(PCI、USB……),負責在它上面的裝置與驅動之間媒合(match)。 - struct class:代表一類「功能相近的裝置」(如所有區塊裝置、所有網路裝置),跨匯流排分類。 - kobject / kset:這個模型底層的「物件」基礎,提供引用計數和 sysfs 呈現。 - sysfs(/sys):把整個模型以檔案系統的形式呈現給使用者態——你 ls /sys/bus/pci/devices 看到的就是它。

為什麼這對你是 scope: direct?因為你的 NVMe SSD 和 GPU 都是透過這個模型被列舉、綁定到驅動的。你日後查 /sys 下的裝置資訊、寫你產品的驅動、理解「為什麼插上一個 NVMe 就自動有驅動接管」——全都建立在這個模型上。這一課是後面所有驅動課(P4-T02 字元驅動、P4-T04 PCI 驅動)的地基。

(書本提醒:這階段的 PCI 章節在 Madieu《Mastering Linux Device Driver Development》(9781789342048)Ch.11,不在只含字元驅動的 2e。)

開始之前(前置確認)

  • 依賴:P3-T15(你能獨立寫一個正確的並行 module)。也會用到 P0-T07(函式指標/ops 結構——probe/remove 就是 callback)、P3-T09(refcount——kobject 的引用計數)。
  • 自我檢測: 1. 你還記得 P0-T07 的「ops 結構/callback」嗎?裝置模型裡 driver 的 probe/remove 就是你提供給 kernel 的 callback。 2. 你還記得 P3-T09 的 refcount_t(引用計數,還有人用就不釋放)嗎?kobject 的引用計數是同一個概念,管理裝置物件的生命週期。
  • 環境:Linux(瀏覽 /sys)+ QEMU 虛擬機(module 實驗只在 VM)。

核心內容

拆成這幾節:(1) 三個主角:device / driver / bus → (2) match → probe → remove 流程 → (3) class:跨匯流排的功能分類 → (4) kobject:模型的物件基礎與引用計數 → (5) sysfs:把模型呈現成檔案 → (6) uevent 與 udev,最後打通關。

1. 三個主角:device、driver、bus

裝置模型的核心是三者的關係:裝置(device)掛在匯流排(bus)上,驅動(driver)登記在匯流排上,匯流排負責媒合兩者。

        DRIVERS["登記在這條匯流排上的驅動們
struct device_driver:
nvme 驅動、顯卡驅動..."]

三個主角: - struct device:一個具體的裝置實例(你機器上那一個 NVMe 控制器)。它記錄裝置在匯流排上的身份(例如 PCI 的 vendor/device ID)。 - struct device_driver:一個驅動,聲明它能認領哪類裝置(透過一個 ID 表),並提供 probe/remove 等 callback。 - struct bus_type:一條匯流排(PCI、USB……)。它最重要的職責是提供 match 函式——判斷「某個 driver 能不能認領某個 device」。

關鍵理解:device 和 driver 是分開登記的,由 bus 在中間媒合。系統開機列舉硬體時,把找到的裝置註冊成 device;驅動載入時,把自己註冊成 device_driver;bus 則不斷嘗試把「還沒有驅動的 device」和「能認領它的 driver」配對。這個解耦讓「裝置」和「驅動」可以獨立存在、動態配對——這正是「插上 NVMe 就自動有驅動接管」的機制。

2. match → probe → remove 流程

裝置與驅動如何從「各自存在」到「綁定運作」?靠 match → probe 流程。這是這一課最核心的機制。

flowchart TB
    REGISTER["一個 device 被註冊到匯流排
(或一個 driver 被註冊到匯流排)"]
    REGISTER --> MATCH2["匯流排對『未綁定的 device』
和『已註冊的 driver』
逐一呼叫 match 函式
(PCI:比對 driver 的 id_table 與 device 的 vendor/device ID)"]
    MATCH2 --> SUCCESS{"match 成功?
(driver 聲稱能認領這個 device)"}
    SUCCESS -->|"否"| WAIT["這個 device 暫時沒有驅動
(等到對的 driver 載入再 match)"]
    SUCCESS -->|"是"| PROBE["★ 呼叫 driver 的 probe(device) ★
driver 在這裡:初始化裝置、
配置資源、把裝置準備好可用
(probe 成功 → device 與 driver 正式綁定)"]
    PROBE --> RUNNING["裝置運作中(driver 接管)"]
    RUNNING --> REMOVE["裝置移除 / driver 卸載時:
呼叫 driver 的 remove(device)
(釋放 probe 配的資源,與 probe 配對)"]
    style MATCH2 fill:#e8a33d,color:#10100e
    style PROBE fill:#8a9a5b,color:#10100e
    style REMOVE fill:#6fa8b8,color:#10100e

流程: 1. 註冊:device 或 driver 被註冊到匯流排。 2. match:匯流排對「未綁定的 device」和「已註冊的 driver」逐一呼叫 match 函式。PCI 的 match 就是比對「driver 的 ID 表」和「device 的 vendor/device ID」(這在 P4-T04 會具體做)。 3. probe:match 成功 → 匯流排呼叫 driver 的 probe(device)。driver 在 probe 裡初始化這個裝置、配置資源、把它準備到可用狀態。probe 成功代表 device 與 driver 正式綁定(probe 就是你 P0-T07 學的 callback,由 kernel 在 match 成功時呼叫)。 4. remove:裝置移除或 driver 卸載時,呼叫 remove(device),釋放 probe 配置的資源(與 probe 配對,回顧 P0-T06/P3-T15 的資源配對紀律)。

常見誤區:以為 probe 一定會被呼叫——不對,probe 只在 match 成功後才被呼叫。如果沒有 driver 聲稱能認領某個 device(match 都失敗),那個 device 就停在「沒有驅動」狀態,probe 不會被呼叫。這是新手寫驅動時「為什麼我的 probe 沒被呼叫」的常見原因——通常是 ID 表沒對上(match 失敗)。

(驗收點之一:用文字說明一次 driver-device match→probe 的流程。)

3. class:跨匯流排的功能分類

bus 是按「實體連接方式」分類(PCI 上的、USB 上的)。但有時你想按「功能」分類——所有的區塊裝置、所有的網路裝置、所有的輸入裝置——不管它們掛在哪條匯流排。這就是 struct class。

        USB2["USB bus:USB 隨身碟、USB 網卡"]
    end
    subgraph classes["按 class(功能)分類,跨匯流排"]
        BLOCK_CLASS["block class:所有區塊裝置
(PCI 上的 NVMe + USB 上的隨身碟...)"]
        NET_CLASS["net class:所有網路裝置
(PCI 網卡 + USB 網卡...)"]
    end
    PCI2 -.“同一個裝置,
既在某 bus 上,
也屬於某 class”.-> BLOCK_CLASS
    USB2 -.-> BLOCK_CLASS
    style PCI2 fill:#6fa8b8,color:#10100e
    style BLOCK_CLASS fill:#8a9a5b,color:#10100e

class 提供跨匯流排的功能視角:一個 NVMe SSD 既掛在 PCI bus 上(實體連接),也屬於 block class(功能:它是區塊裝置);一個 USB 隨身碟掛在 USB bus 上,但也屬於 block class。class 讓「不管接在哪,功能相同的裝置」能被統一看待——這在 sysfs 裡對應 /sys/class/(下一節)。

對你的領域:你的 NVMe 在 /sys/bus/pci/(它是 PCI 裝置)也在 /sys/class/block/(它是區塊裝置)。bus 和 class 是看同一批裝置的兩個角度。

把「一個裝置從開機被發現到 /dev 出現節點」的完整生命週期串成一條線(整合本課所有環節):

    BOOT3 --> REG5["找到裝置 → 註冊成 struct device(掛 bus)"]

4. kobject:模型的物件基礎與引用計數

裝置模型底層,所有這些物件(device、driver、bus、class)都建立在一個更基礎的東西上:kobject。它提供兩個關鍵能力:引用計數和 sysfs 呈現。

flowchart TB
    KOBJECT["kobject(kernel object):模型的基礎物件"]
    KOBJECT --> REFCOUNT2["① 引用計數(回顧 P3-T09 refcount):
記錄這個物件現在有幾個地方在引用
→ 歸零才釋放
(裝置可能被多處引用:驅動、開啟的檔案、sysfs...)"]
    KOBJECT --> SYSFS_REP["② sysfs 呈現:
每個 kobject 對應 /sys 下的一個目錄
(這就是為什麼裝置/驅動都能在 /sys 看到)"]
    KSET["kset:一組相關 kobject 的集合
(對應 /sys 下的一層目錄結構)"]
    KOBJECT --> KSET
    style KOBJECT fill:#6fa8b8,color:#10100e
    style REFCOUNT2 fill:#e8a33d,color:#10100e
    style SYSFS_REP fill:#8a9a5b,color:#10100e

kobject 的兩個能力: - 引用計數:每個 kobject 內含一個引用計數(就是 P3-T09 的 refcount 概念)。裝置物件可能同時被多處引用——驅動持有它、開啟的檔案指向它、sysfs 顯示它……引用計數確保「還有人用就不釋放、最後一個放手才釋放」,避免 use-after-free(回顧 P0-T06)。 - sysfs 呈現:每個 kobject 對應 /sys 下的一個目錄——這是為什麼裝置、驅動、匯流排都能在 /sys 裡看到(下一節)。 - kset:一組相關 kobject 的集合,對應 /sys 下的一層目錄結構。

常見誤區:忽略 kobject 引用計數導致過早釋放——如果你在還有人引用時就釋放了物件,就是 use-after-free。kobject 的引用計數(kobject_get/kobject_put)就是管理這個生命週期。多數時候裝置模型框架會幫你處理,但你要理解「裝置物件的生命週期由引用計數管理」這件事(驗收點之一:說明 kobject 引用計數如何運作)。

5. sysfs:把模型呈現成檔案

sysfs(掛在 /sys)是裝置模型的「使用者態介面」——它把整個模型(裝置、驅動、匯流排、類別)以檔案系統的形式呈現出來,讓你能用 ls/cat/echo 瀏覽和互動。

        CLASS_DIR["/sys/class/
按功能:/sys/class/block/ 下是所有區塊裝置"]
        DEVICES_DIR["/sys/devices/
裝置的實際階層(實體拓樸)"]
    end
    ATTR["每個裝置目錄下有『屬性檔(attribute)』
一個檔 = 一個值
cat 讀值、echo 寫值
(背後是 driver 提供的 show/store 函式)"]
    sysfs --> ATTR
    PRINCIPLE["★ sysfs 設計原則:一檔一值、小而精 ★
(不是拿來傳大量資料的;那用字元裝置 P4-T02)"]

    style BUS_DIR fill:#6fa8b8,color:#10100e
    style ATTR fill:#e8a33d,color:#10100e

/sys 的主要目錄對應模型的不同視角:/sys/bus/(按匯流排,如 /sys/bus/pci/devices/)、/sys/class/(按功能,如 /sys/class/block/)、/sys/devices/(裝置的實體階層)。

每個裝置目錄下有屬性檔(sysfs attribute)——一個檔對應一個值,cat 讀、echo 寫。背後是 driver 提供的 show(讀時呼叫)和 store(寫時呼叫)函式(又是 callback,P0-T07)。例如你 cat /sys/block/nvme0n1/size 讀到的容量,就是某個 show 函式回傳的。

關鍵設計原則(常見誤區:把 sysfs 當成存大量資料的介面):sysfs 屬性應該一檔一值、小而精——它是用來「看一個狀態、設一個參數」的,不是用來傳大量資料的(大量資料用字元裝置 P4-T02 的 read/write,或 mmap P4-T03)。另一個誤區是 show/store 未正確處理長度與格式(寫進來的字串要解析、讀出去的要格式化,並注意緩衝區長度)。

(驗收點:在 sysfs 建立一個可讀寫屬性,cat/echo 能正確讀回/改值。)

6. uevent 與 udev:裝置事件如何通知使用者態

最後一塊:當裝置出現/消失,使用者態怎麼知道?靠 uevent 和 udev。

flowchart LR
    EVENT["裝置事件發生
(插入新裝置、移除裝置、probe 完成...)"]
    EVENT --> UEVENT["kernel 發出 uevent
(一個事件通知,描述『什麼裝置、發生什麼』)"]
    UEVENT --> UDEV["使用者態的 udev 守護程式
收到 uevent"]
    UDEV --> ACTION["udev 依規則動作:
在 /dev 建立裝置節點、
設定權限、跑相關程式..."]
    style UEVENT fill:#e8a33d,color:#10100e
    style UDEV fill:#8a9a5b,color:#10100e

機制(概念層): - uevent:當裝置狀態改變(新裝置出現、probe 完成、裝置移除),kernel 發出一個 uevent——一個描述「什麼裝置、發生什麼事」的事件通知。 - udev:使用者態的守護程式,監聽 uevent。收到後依規則動作:最常見的是在 /dev 下建立對應的裝置節點(例如新插的 NVMe 出現 /dev/nvme0n1)、設定權限、觸發相關程式。

這就是「插上一個 USB 隨身碟,/dev 下立刻冒出對應節點」的機制:kernel 列舉到裝置 → match→probe → 發 uevent → udev 收到 → 建立 /dev 節點。你 P4-T02 寫字元裝置時,會用 device_create 觸發這個流程,讓 udev 自動建出 /dev 節點(而不必手動 mknod)。

(驗收點之一:說明 uevent 如何運作。)

一句話總結:Linux Device Model 用 device(裝置)/driver(驅動)/bus(匯流排)三者解耦——bus 用 match 媒合 device 與 driver,成功才呼叫 driver 的 probe 初始化裝置(probe 不必然被呼叫,需 match 成功),remove 配對釋放;class 提供跨匯流排的功能分類,kobject 提供引用計數與 sysfs 呈現,uevent/udev 則把裝置事件通知使用者態自動建 /dev 節點。你的 NVMe/GPU 都透過這個模型被列舉、綁定驅動。

常見誤區與踩雷提醒

誤區一:把 sysfs 當成存大量資料的介面。 sysfs 屬性應一檔一值、小而精(看一個狀態、設一個參數)。大量資料用字元裝置(P4-T02)的 read/write 或 mmap(P4-T03)。

誤區二:忽略 kobject 引用計數導致過早釋放。 裝置物件可能被多處引用,引用計數(kobject_get/kobject_put)確保歸零才釋放。在還有人引用時釋放就是 use-after-free(回顧 P0-T06)。

誤區三:以為 probe 一定會被呼叫。 probe 只在 bus 上 match 成功後才被呼叫。沒有 driver 聲稱能認領某 device(match 失敗),probe 就不會被呼叫——這常是「probe 沒被呼叫」的原因(通常 ID 表沒對上)。

誤區四:sysfs 屬性的 show/store 未處理長度與格式。 寫進來的字串要解析、讀出去的要格式化,並注意緩衝區長度。別假設輸入格式正確。

環境:Linux(瀏覽 /sys)+ QEMU 虛擬機(module 實驗只在 VM)。

任務 A — 瀏覽 /sys 對照模型 在 Linux 上瀏覽: - ls /sys/bus/pci/devices/(所有 PCI 裝置——找找你的 NVMe/網卡)。 - ls /sys/class/block/(所有區塊裝置)。 - 挑一個裝置,ls 它的目錄、cat 幾個屬性檔(如 vendor、device)。 對照本課的模型:bus、class、device、屬性檔。寫幾句你的觀察。

任務 B — 註冊 device/driver,觀察 probe(驗收點) 在 module 裡註冊一個簡單的 device 和對應的 driver(可用 platform device/driver,P4-T05 會深入 platform;這裡用它做最簡單的 probe 示範)。讓 match 成功,觀察 probe 被呼叫(在 probe 裡 pr_info,dmesg 確認)。驗收:driver 在對應 device 出現時 probe 被呼叫(dmesg 可見)。

任務 C — 建立 sysfs 可讀寫屬性(驗收點) 為你的 device 建立一個 sysfs 屬性檔(用 DEVICE_ATTR 或 sysfs_create_file),實作 show(讀時回傳一個值)和 store(寫時更新那個值)。測試:cat 讀回、echo 改值再 cat 確認變了。驗收:sysfs 屬性 cat/echo 能正確讀回/改值。 注意 show/store 正確處理長度與格式。

任務 D — 說明 match→probe 流程(驗收點) 用文字說明一次 driver-device 的 match → probe 流程:device 和 driver 怎麼被媒合?probe 何時被呼叫?驗收:能正確描述 match→probe 流程。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 註冊的 driver 在對應 device 出現時 probe 被呼叫(dmesg 可見)。 2. ☐ 在 sysfs 建立一個可讀寫屬性,cat/echo 能正確讀回/改值。 3. ☐ 用文字說明一次 driver-device match→probe 的流程。

評分量表: - 60(及格):能建立 sysfs 屬性。 - 80(熟練):能解釋 device model 與 probe 流程。 - 100(精通):能說明 kobject 引用計數與 uevent 如何運作。

延伸與銜接

  • 對應工作場景:直接對應——NVMe/GPU 都透過此模型被列舉與綁定驅動;你看 /sys 下的裝置資訊、寫 driver 都建立在此。
  • 這課餵給未來的:device model + probe/remove → P4-T02 字元驅動(註冊裝置)、P4-T04 PCI 驅動(probe 裡 enable device、map BAR);kobject 引用計數 → 裝置物件生命週期;sysfs → 你產品暴露狀態/參數的介面;device_create/udev → P4-T02 自動建 /dev 節點。
  • 下一步 → P4-T02 字元裝置驅動(file_operations / cdev / 註冊):你懂了裝置模型的全景。下一課寫第一個真正的裝置驅動——字元裝置:實作 open/read/write/release(file_operations,又是一組 callback,P0-T07)、註冊裝置號與 cdev、在 /dev 建立節點。關鍵是 copy_to_user/copy_from_user——你絕不能直接解參考使用者態指標(安全漏洞/當機),且這些函式可能睡眠(不可在持 spinlock 時呼叫,回顧 P3-T08)。這直接對應你產品:user space app 很可能透過字元裝置 + ioctl/mmap 與你的 module 溝通(設定佇列、提交工作)。
