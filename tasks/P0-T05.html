P0-T05 · 行程記憶體佈局

一句話:你的程式跑起來時,它的記憶體被分成幾個用途不同的「區」——程式碼一區、全域變數一區、會長大的 heap 一區、會伸縮的 stack 一區。知道每個變數住哪一區,你就能預測它的生命週期,也就讀得懂「為什麼回傳區域變數的指標是災難」。

為什麼要先學這個(導讀)

在 JS/PHP 裡,你不關心變數「住哪」。垃圾回收器(GC)替你管理一切——東西沒人用了,它自動清掉。你從來沒被迫想過「這個變數活多久?誰負責回收它?它住在記憶體哪一塊?」

C 沒有 GC。變數活多久、住在哪、誰回收,全是你的責任。要扛起這個責任,你得先有一張地圖:一支執行中的程式,它的記憶體到底被分成哪些區、各區的脾氣(生命週期、能不能寫、預設值)是什麼。

這張地圖之所以關鍵,有三個原因:

  1. 它解釋了一個 C 新手必踩的致命坑——「回傳指向區域變數的指標」為什麼是災難(因為那塊記憶體在函式結束的瞬間就失效了)。這個坑在 kernel 裡同樣致命,而且更難 debug。
  2. 它是理解 Phase 1 虛擬記憶體的基礎。每個行程都有自己的這張地圖(自己的位址空間),而 kernel 負責維護它們。
  3. 它連到 user/kernel 邊界。kernel 本身也是一塊有佈局的記憶體;理解「使用者程式的位址空間長怎樣」,是之後理解「kernel 空間 vs 使用者空間」的前置。

開始之前(前置確認)

  • 依賴:P0-T04(你已懂變數在記憶體有位址、struct 的佈局)。
  • 自我檢測: 1. 你能用 %p 印出一個變數的位址嗎?(這課靠「比較位址大小」來推斷變數住哪一區) 2. 你還記得 P0-T02 的「野指標 / 懸空」概念嗎?這課會解釋它的根本成因。

核心內容

拆成這幾節:(1) 一張佈局地圖 → (2)~(6) 逐區解說(text/rodata、data、BSS、heap、stack)→ (7) stack 的生命週期與懸空指標 → (8) heap 與 stack 為何相向生長,最後打通關。

1. 一張地圖:執行中程式的記憶體分區

當你的程式被載入執行,它的記憶體(行程的「位址空間」)被分成幾個區段。慣例上由低位址到高位址排列:

2. text 與 rodata:唯讀的程式碼與常數

text(程式碼區):存放你編譯出來的機器碼指令(回顧 P0-T01,這就是連結後可執行檔裡的那些 CPU 指令)。它是唯讀的——程式不能在執行時修改自己的指令。

為什麼唯讀? 防止意外或惡意竄改程式碼。如果程式能改自己的指令,一個 bug 或攻擊就可能把程式改成做壞事。硬體層級的唯讀保護,讓「程式碼」這塊不可寫。

rodata(read-only data,唯讀資料):字串字面值("hello")、const 修飾的常數。也是唯讀。

這解釋了一個經典崩潰:

char *s = "hi";    // "hi" 這個字串字面值住在唯讀的 rodata
s[0] = 'H';        // 崩潰!你想改一塊唯讀記憶體

3. data:有初值的全域變數

data 區:存放有給初始值的全域變數和 static 變數。例如:

int g = 42;            // 全域,有初值 → data 區
static int s = 7;      // static,有初值 → data 區

它們的初值(42、7)會被存進執行檔裡,程式載入時複製到記憶體的 data 區。這些變數從程式開始到結束都存在(生命週期 = 整個程式),不像區域變數會隨函式來去。

4. BSS:沒初值的全域變數(啟動時歸零)

BSS 區:存放沒給初始值的全域 / static 變數。例如:

int g;                 // 全域,無初值 → BSS
static int arr[1000];  // static,無初值 → BSS

BSS 有個聰明的設計:它不佔執行檔的空間。想想看——一個一萬個元素的全域陣列,如果沒給初值,難道要在執行檔裡存一萬個 0 嗎?沒必要。所以執行檔裡只記「BSS 需要多大」,程式啟動時由系統一次把整塊 BSS 清成 0。

        BSS_F["BSS:只存『需要多大』

    style BSS_F fill:#6fa8b8,color:#10100e

這也解釋了 C 的一個你可能背過的規則:全域變數預設是 0,但區域變數預設是垃圾值。為什麼待遇不同?因為全域變數在 BSS 會被啟動時歸零,而區域變數在 stack 不會(stack 空間是重複使用的,上面殘留著前一個函式留下的舊資料)。規則背後是「住在哪一區」的差異。

5. heap:你親手管理的動態區

heap(堆積):你用 malloc 動態配置的記憶體住這裡。它的特點:

  • 生命週期由你掌控:從 malloc 配置,活到你 free 它為止。不像區域變數隨函式消失,heap 上的東西「函式回傳了也還在」——這正是它的用途。
  • 向高位址方向長大:你每多 malloc 一塊,heap 往高位址延伸。
  • 責任全在你:沒有 GC,忘了 free 就洩漏(這是下一課 P0-T06 的主題)。

heap 是「需要活得比某個函式久」的資料的家。下一課會深入它的管理;這課你只要記住它在地圖上的位置和「生命週期由你掌控」這個本質。

6. stack:自動、快速,但短命

stack(堆疊):區域變數、函式參數、函式呼叫的記錄住這裡。它的特點:

  • 自動管理:你不需要手動配置/釋放區域變數,進出函式時 stack 自動長出/縮回。
  • 向低位址方向長大:和 heap 相向而行(第 8 節解釋為什麼)。
  • 短命:這是重點,下一節專門講。

每次呼叫一個函式,stack 上就長出一塊空間,叫 stack frame,專門放這次呼叫的區域變數和參數。函式一回傳,這塊 frame 立刻縮回去。

        F2["foo 的 frame

    end
    subgraph ret["foo 回傳後"]
        R1["main 的 frame"]
        R2["foo 的 frame 已縮回

比喻:stack 像一疊便利貼。呼叫函式 = 在最上面貼一張新便利貼,寫上這次的區域變數。函式回傳 = 撕掉最上面那張。撕掉之後,那張便利貼上寫的東西就沒了——而且那個位置很快會被下一張便利貼覆蓋。

7. 致命坑:回傳指向區域變數的指標

第 6 節的「短命」直接導致 C 新手最致命的錯誤之一。看這段:

int *make_bad(void) {
    int local = 42;
    return &local;     // 災難:回傳一張即將被撕掉的便利貼的地址
}

local 住在 make_bad 的 stack frame。函式一回傳,frame 縮回,local 失效。呼叫者拿到的指標,指向一塊「已經不再屬於它」的記憶體——這就是懸空指標(dangling pointer)(回顧 P0-T02 提過的概念,這裡看到它的根本成因)。

逐步看災難怎麼發生:

flowchart TB
    S1["make_bad 執行中:
local=42 住在 make_bad 的 frame
回傳 &local(那塊的位址)"]
    S2["make_bad 回傳:
它的 frame 縮回
local 那塊記憶體不再屬於任何人"]
    S3["呼叫者拿到指標 p,指向那塊已失效的記憶體
(此刻可能還『碰巧』讀到 42)"]
    S4["下次任何函式呼叫,
新的 frame 覆蓋了那塊記憶體
→ p 指向的值變成別的東西"]
    S5["時好時壞、極難重現的 bug"]
    S1 --> S2 --> S3 --> S4 --> S5
    style S2 fill:#e8a33d,color:#10100e
    style S4 fill:#c2603a,color:#f4ecd8
    style S5 fill:#c2603a,color:#f4ecd8

最陰險的是 S3→S4:剛回傳時,那塊記憶體可能還沒被覆蓋,所以 p 讀起來「好像」還是 42,程式看似正常。但下次有別的函式呼叫覆蓋了它,值就變了。這種「有時對、有時錯」的 bug 最難抓。

正解:要回傳「活得比函式久」的東西,得用 heap(malloc),因為 heap 的記憶體不隨函式回傳而消失:

int *make_good(void) {
    int *p = malloc(sizeof(int));   // 配置在 heap
    *p = 42;
    return p;     // 安全:heap 的東西函式回傳後仍存在
}                 // ……但呼叫者要負責 free(下一課的主題)

8. heap 向上、stack 向下:為什麼相向?

回到地圖:heap 從中間往高位址長,stack 從高位址往低處長,兩者相向,中間留一大片空白。

flowchart TB
    H["heap 起點(較低)"]
    Hgrow["heap 向上長大 ↑↑↑"]
    GAP["⋮ 共享的空白緩衝區 ⋮
(誰需要就用誰的)"]
    Sgrow["stack 向下長大 ↓↓↓"]
    S["stack 起點(較高)"]
    H --> Hgrow --> GAP --> Sgrow --> S
    style GAP fill:#24221d,color:#cfc6b0
    style Hgrow fill:#8a9a5b,color:#10100e
    style Sgrow fill:#e8a33d,color:#10100e

為什麼這樣設計? 好處是「彈性共享」:兩者從兩端往中間長,共用中間那片空白,不必預先切死「heap 只能用這麼多、stack 只能用那麼多」。哪邊需要多一點,就往中間多吃一點。

壞處:萬一其中一個長到撞上另一個——stack 暴衝(例如無窮遞迴,一直貼便利貼貼到撞進 heap),就出事,這叫 stack overflow(沒錯,那個著名網站的名字就來自這個經典崩潰)。

打通關:把佈局收攏成一個心智模型

把五個區段按「生命週期 + 能不能寫 + 誰管理」收攏成一張表/圖,這就是你看待程式記憶體的心智模型:

flowchart TB
    subgraph longlife["活整個程式(全域生命週期)"]
        TEXT["text/rodata:唯讀,放程式碼與常數"]
        DATA["data:可寫,有初值的全域"]
        BSS["BSS:可寫,無初值全域,啟動歸零"]
    end
    subgraph youmanage["你掌控生命週期"]
        HEAP["heap:malloc 配置,活到 free
(忘了 free → 洩漏)
能跨函式存活 ← 用來回傳長壽資料"]
    end
    subgraph autolife["隨函式來去(短命)"]
        STACK["stack:區域變數,函式回傳即失效
(回傳它的指標 → 懸空)"]
    end
    style TEXT fill:#6fa8b8,color:#10100e
    style HEAP fill:#8a9a5b,color:#10100e
    style STACK fill:#e8a33d,color:#10100e

一句話總結這個心智模型:東西住在哪一區,就決定了它活多久、能不能改、誰負責清理。 「回傳區域變數指標 = 懸空」是因為 stack 短命;「要長壽資料就用 heap」是因為 heap 由你掌控生命週期;「全域預設為 0」是因為 BSS 啟動歸零。所有這些「規則」,追到底都是「住在哪一區」的必然結果——這正是把零散規則變成一個連貫理解的關鍵。

常見誤區與踩雷提醒

誤區一:以為區域變數的位址固定不變。 區域變數住 stack,每次函式呼叫的 frame 位置可能不同(尤其有遞迴、或不同呼叫路徑時)。別把區域變數的位址記下來「下次再用」。

誤區二(致命):回傳指向區域變數的指標。 如第 7 節,函式回傳後 stack frame 失效,指標變懸空,造成時好時壞的 bug。要回傳長壽資料,用 heap 配置。這個坑在 kernel 裡同樣致命。

誤區三:混淆 BSS 與 data。 int g = 5;(有初值)在 data 區;int g;(無初值)在 BSS,啟動時被歸零。理解這個區別,你才懂為什麼「全域變數預設為 0,但區域變數預設是垃圾」。

誤區四:試圖修改字串字面值。 char *s = "hi"; s[0]='H'; 會崩潰,因為 "hi" 在唯讀的 rodata。要可改,用 char s[] = "hi";(複製到可寫區)。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 用位址推斷分區

#include <stdio.h>
#include <stdlib.h>
int g_init = 42;        // data 區
int g_uninit;           // BSS 區
int main(void) {
    static int s = 7;   // data 區
    int local = 1;      // stack
    int *heap = malloc(sizeof(int));  // heap
    printf("text (main)    : %p\n", (void*)main);
    printf("data (g_init)  : %p\n", (void*)&g_init);
    printf("bss  (g_uninit): %p\n", (void*)&g_uninit);
    printf("heap           : %p\n", (void*)heap);
    printf("stack(local)   : %p\n", (void*)&local);
    free(heap);
    return 0;
}

觀察印出的位址:text/data/bss 的位址較低且相近,heap 在中間,stack 的位址明顯高很多。對照第 1 節的地圖,確認每個變數落在哪一區。

任務 B — 看執行檔的區段大小,並驗證 BSS 特性

gcc -o prog prog.c
size prog        # 印出 text data bss 三欄的 bytes 數

然後做這個實驗:把 g_uninit 改成一個大陣列 int g_uninit[1000];,重編後再 size——觀察 bss 欄變大(多了約 4000 bytes),但 data 欄沒變。這親眼證明了第 4 節說的「未初始化的大陣列只佔 BSS、不佔執行檔空間」。再把它改成有初值的 int g_uninit[1000] = {1};,重編後看——這次連執行檔本身都變大了(初值要存進檔案)。

任務 C — 製造懸空指標(在 VM 裡觀察) 寫出第 7 節的 make_bad,在 main 裡接住它的回傳值,立刻印一次(可能還是 42),然後呼叫另一個會用到 stack 的函式(隨便印點東西),再印一次那個指標的值——觀察它可能變了。寫一句話解釋:為什麼第一次「碰巧對」,第二次卻變了?

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 宣告 1 個全域、1 個 static、1 個區域、1 個 malloc 配置的變數,印出四者位址後正確分類其所屬區段。 2. ☐ 用 size prog 讀出 text/data/bss 三欄數值,並透過「把全域陣列改大」的實驗,解釋哪個變數影響了 bss(且未影響 data)。 3. ☐ 能解釋「回傳區域變數指標」為何產生懸空指標(連結到 stack frame 的生命週期)。

評分量表: - 60(及格):能分類各變數住哪一區。 - 80(熟練):能畫出完整佈局圖,解釋 stack/heap 的生長方向與生命週期差異。 - 100(精通):能連結到虛擬記憶體與行程位址空間(預告 Phase 1),並完整解釋懸空指標的成因與正解。
