P5-T06 · Linux NVMe 驅動原始碼(drivers/nvme/host/)

一句話:把 NVMe 協定對到真實程式碼——drivers/nvme/host/pci.c 是 PCIe 傳輸層、core.c 是控制器核心;命令提交入口是 nvme_queue_rq,而 nvme_queue(一對 SQ/CQ)1:1 對應 blk-mq 硬體佇列。從「一次 I/O」單一路徑切入,別被龐大原始碼淹沒。

🚪 這是 Phase 5 出關門檻

這是 Phase 5 的關卡(gate)。本 task 達 80 分——能在 NVMe 驅動原始碼中追一次 I/O 並解釋佇列對應——才算掌握了你產品核心領域的程式碼閱讀能力,方可進入 Phase 6(DMA)。

為什麼設這道關?因為 這是你工作中最常閱讀/修改的程式碼之一。你的產品可能要修改或旁路 NVMe 驅動,把 queue I/O 導向 GPU。如果你不能在這份龐大的原始碼裡定位關鍵流程、追一次 I/O 的提交/完成路徑、理解佇列對應,你就無法在你的核心領域工作。這道關確保你具備這個能力——它也是前面所有功課(資料結構、blk-mq、NVMe 協定、PCI)的綜合兌現。

為什麼是「讀 NVMe 驅動原始碼」(導讀)

P5-T05 你懂了 NVMe 協定(SQ/CQ、doorbell、PRP/SGL)。這一課把協定對到真實的 Linux NVMe 驅動原始碼——你工作中最常碰的程式碼。

drivers/nvme/host/ 的結構: - pci.c:PCIe 傳輸層——NVMe over PCIe 的實作(用 P4-T04 的 pci_driver、BAR、MSI-X)。命令提交、佇列管理、中斷處理在這。 - core.c:控制器核心/通用層——控制器狀態機、identify、namespace 掃描等,跨傳輸層(PCIe/TCP/RDMA)通用的部分。 - nvme.h:核心結構定義。

關鍵的對應(這一課的核心): - nvme_queue:驅動裡代表一對 SQ/CQ(P5-T05)的結構。 - 它 1:1 對應 blk-mq 硬體佇列(P5-T03)——這把你 Phase 5 學的兩端(blk-mq 的硬體佇列、NVMe 的 SQ/CQ)在程式碼裡接起來了。 - nvme_queue_rq:命令提交入口——blk-mq 要派發一個 request 時,呼叫驅動的這個函式(就是 P5-T03 的 queue_rq ops,P0-T07 callback),它把 request 轉成 NVMe 命令、放進 SQ、按 doorbell。

最重要的讀碼策略(常見誤區:被龐大原始碼淹沒):NVMe 驅動程式碼很多,不要試圖一次讀完。從「一次 I/O 的提交/完成」這條單一路徑切入——追一個 read/write 怎麼從 nvme_queue_rq 進去、變成 SQ 命令、按 doorbell、裝置完成、CQ 處理、bi_end_io 回呼。沿著這一條路,你會碰到所有關鍵結構,而不會在無關的程式碼裡迷路。

為什麼這對你是 scope: direct?如上——這是你最常讀/改的程式碼,你產品可能修改或旁路它把 I/O 導向 GPU。這道出關門檻確保你能在這裡工作。

(這一課是 P2-T08「讀真實 kernel 子系統」能力的終極應用——用 Bootlin 交叉參照、認結構、追路徑。)

開始之前(前置確認)

  • 依賴:P5-T05(NVMe 協定:SQ/CQ、doorbell、PRP/SGL)、P5-T03(blk-mq 硬體佇列)、P4-T04(PCI/BAR/MSI-X)。也用到 P2-T08(讀真實 kernel 原始碼)、P3-T13/P3-T14(ftrace/kgdb 追路徑)。
  • 自我檢測: 1. 你還記得 P5-T05 的「SQ/CQ、按 doorbell 提交、CQ + phase bit 完成」嗎?這課看驅動怎麼實作這些。 2. 你還記得 P2-T08 的讀碼法(從單一路徑切入、用 Elixir 交叉參照、認結構)嗎?這課是它的終極應用。
  • 工具:Bootlin(drivers/nvme/host/pci.c、core.c、nvme.h)、ftrace/kgdb(回顧 P3-T13/P3-T14)。
  • 環境:QEMU -device nvme(模擬 NVMe)+ 帶 debug info 的 NVMe 驅動。所有實驗只在 VM。

核心內容

拆成這幾節:(1) 原始碼樹結構 → (2) nvme_queue 對應 blk-mq 硬體佇列 → (3) 提交路徑:nvme_queue_rq → (4) 完成路徑:CQ 處理 → (5) 初始化/identify/namespace 掃描 → (6) 讀碼策略:單一路徑切入,最後打通關。

分工: - pci.c:PCIe 傳輸層——「怎麼透過 PCIe 跟這個 NVMe 裝置溝通」。用 P4-T04 的 pci_driver、BAR、MSI-X;實作 nvme_queue、提交 nvme_queue_rq、中斷處理。你產品(PCIe NVMe)最常動這裡。 - core.c:控制器核心/通用層——NVMe 控制器/命名空間的通用邏輯(狀態機、identify、namespace 掃描),不分傳輸層(PCIe、TCP、RDMA 共用)。 - nvme.h:核心結構定義(nvme_dev、nvme_queue、nvme_command 等)。

常見誤區:混淆 pci.c 與 core.c——pci.c 是「PCIe 傳輸怎麼做」,core.c 是「NVMe 通用邏輯」。NVMe 支援多種傳輸(PCIe/TCP/RDMA),通用的放 core.c、PCIe 專屬的放 pci.c。你讀碼時要知道自己在哪一層。

這是這一課的核心對應——把你 Phase 5 學的兩端接起來。

核心對應(驗收點:說明 blk-mq 硬體佇列與 nvme_queue(SQ/CQ 對)的 1:1 對應): - nvme_queue 是驅動裡代表一對 SQ/CQ(P5-T05)的結構。 - 它 1:1 對應一個 blk-mq 硬體佇列(P5-T03)。 - nvme_queue 內含:SQ 的記憶體(命令環)+ SQ doorbell、CQ 的記憶體(完成環)+ CQ doorbell、目前的 phase 與 head/tail 指標、對應的 MSI-X 中斷向量(P4-T04)。

所以整條對應鏈是:CPU N → blk-mq 硬體佇列 N → nvme_queue N → NVMe SQ/CQ 對 N(常見「每核一個」)。這就是 P5-T03 說的「blk-mq 硬體佇列 1:1 對應 NVMe SQ/CQ」在程式碼裡的實體——nvme_queue 是那個對應的載體。這把你 Phase 5 學的 blk-mq(P5-T03)和 NVMe 協定(P5-T05)在驅動程式碼裡接起來了。

常見誤區:忽略 NVMe 驅動把硬體佇列建在 blk-mq 之上——NVMe 驅動不是自己另搞一套佇列,而是實作 blk-mq 的介面(blk_mq_ops),把它的 nvme_queue 對應到 blk-mq 硬體佇列。理解這個「建在 blk-mq 之上」的關係,是讀懂驅動的關鍵。

提交路徑(驗收點:正確指出命令提交入口 nvme_queue_rq 與其所屬檔案 pci.c): - blk-mq 要派發一個 request → 呼叫驅動的 nvme_queue_rq(在 pci.c,這是 blk_mq_ops.queue_rq,P0-T07 callback)。 - nvme_queue_rq 裡做一次提交:① 從 request(P5-T02)取 I/O 資訊 → ② 建立 NVMe 命令(64-byte,P5-T05)→ ③ 把 bio_vec(P5-T02)轉成 PRP/SGL(P5-T05) → ④ 命令寫進 SQ → ⑤ 屏障(dma_wmb,回收 P3-T11 命門!)→ ⑥ 寫 SQ doorbell(P4-T04)。 - 裝置 DMA 讀 SQ 命令、執行。

看這條路徑,你 Phase 5 的所有功課都兌現了:request(P5-T02)、PRP/SGL 轉換(P5-T05)、doorbell(P4-T04/P5-T05)、屏障(P3-T11)。第 3 步「bio_vec → PRP/SGL」正是你產品資料路徑的關鍵一環(你可能在這附近介入,把資料導向 GPU)。

4. 完成路徑:CQ 處理

提交之後,完成端——裝置做完、發中斷、驅動處理 CQ。

flowchart TB
    DEVICE6["裝置執行完 → DMA 寫完成項(16-byte)進 CQ → 發 MSI-X 中斷(P4-T04)"]
    DEVICE6 --> ISR3["驅動的中斷 handler(ISR,上半部,P3-T10):"]
    ISR3 --> CQPROC["處理 CQ:
① 看 CQ 當前位置的完成項
② 檢查 phase bit(P5-T05)== 期望值?
  是 → 新完成項,處理;否 → 沒有新的,停
③ 對每個完成項:找到對應的 request、標記完成
④ 推進 CQ head、寫 CQ doorbell
⑤ 呼叫 request 的完成 → 最終 bio 的 bi_end_io(P5-T02/P0-T07)"]
    CQPROC --> DEFER["★ 重活延後(P3-T10)★
ISR 只做最緊急的(認完成);
耗時處理(你產品的 parity/GPU)延後到 workqueue"]
    style ISR3 fill:#e8a33d,color:#10100e
    style CQPROC fill:#6fa8b8,color:#10100e
    style DEFER fill:#8a9a5b,color:#10100e

完成路徑: - 裝置執行完 → DMA 寫完成項(16-byte)進 CQ → 發 MSI-X 中斷(P4-T04)。 - 驅動的中斷 handler(ISR,上半部,P3-T10)處理 CQ:① 看當前完成項 → ② 檢查 phase bit(P5-T05)判斷是否新完成項 → ③ 對每個新完成項,找到對應的 request、標記完成 → ④ 推進 CQ head、寫 CQ doorbell → ⑤ 呼叫 request 完成 → 最終 bio 的 bi_end_io(P5-T02/P0-T07 callback)。

重活延後(回收 P3-T10):ISR 只做最緊急的(認出完成、推進佇列);耗時的處理延後到 workqueue。對你產品:NVMe I/O 完成後的 parity 計算、GPU 提交這些重活,就在這個「延後」環節——ISR 認出「某個底層 NVMe I/O 完成了」,把後續(算 parity、提交 GPU)排到 workqueue 做(回顧 P3-T10 的設計)。這是你產品介入完成路徑的地方。

(這條路徑你會用 ftrace/kgdb 實際追一遍——驗收要求擷取一次提交路徑的關鍵函式序列。)

讀碼策略(回收 P2-T08,並對應這一課的所有誤區): - 不要從頭讀到尾(常見誤區:被龐大原始碼淹沒)——會迷路。 - 從「一次 I/O」單一路徑切入:提交(nvme_queue_rq → 寫 SQ + doorbell)、完成(中斷 handler → phase bit → bi_end_io)。沿這一條路,碰到的結構才去查。 - 用工具:Bootlin 交叉參照(點函式/結構跳定義,P2-T08;常見誤區:追程式碼不用 Elixir 交叉參照而迷路)、ftrace function_graph 追實際呼叫序列(P3-T13)、kgdb 在 nvme_queue_rq 設中斷點看變數(P3-T14)。

這套方法是你日後讀任何龐大 kernel 子系統的通用法。NVMe 驅動只是第一個真正大的——掌握「單一路徑 + 交叉參照 + 動態追蹤」,你就能啃下任何 kernel 程式碼。對你產品:你要修改/旁路這份驅動把 I/O 導向 GPU,而你介入的點(nvme_queue_rq 附近的提交、完成處理的延後)正是這條單一路徑上的關鍵環節。

常見誤區與踩雷提醒

誤區一:被龐大原始碼淹沒。 不要從頭讀到尾。從「一次 I/O 提交/完成」單一路徑切入(nvme_queue_rq → SQ/doorbell;中斷 → phase bit → bi_end_io),碰到的結構才去查。

誤區二:混淆 PCIe 傳輸層(pci.c)與通用核心(core.c)。 pci.c 是「PCIe 怎麼跟裝置溝通」;core.c 是「NVMe 通用邏輯」(跨 PCIe/TCP/RDMA)。你產品(PCIe NVMe)最常動 pci.c。

誤區三:忽略 NVMe 驅動把硬體佇列建在 blk-mq 之上。 驅動實作 blk-mq 介面(blk_mq_ops),nvme_queue 1:1 對應 blk-mq 硬體佇列(也就是 SQ/CQ)。不是另搞一套佇列。

誤區四:追程式碼不用 Elixir 交叉參照而迷路。 用 Bootlin 點函式/結構跳定義(回顧 P2-T08)、用 ftrace/kgdb 追實際路徑。光用眼睛在數千行裡找會迷路。

動手實作(出關驗收任務)

環境:QEMU -device nvme(模擬 NVMe)+ 帶 debug info 的 NVMe 驅動。所有實驗只在 VM。 用 Bootlin 對照原始碼。

任務(出關門檻):在 NVMe 驅動原始碼中追一次 I/O

  1. 定位提交入口:在 drivers/nvme/host/pci.c(https://elixir.bootlin.com/linux/v6.12/source/drivers/nvme/host/pci.c ）找到命令提交入口 nvme_queue_rq,確認它所屬的檔案,並讀懂它做的事(取 request、建命令、轉 PRP/SGL、寫 SQ、doorbell)。

  2. 說明佇列對應:在原始碼中找到 nvme_queue 結構(pci.c/nvme.h),用文字說明它如何 1:1 對應 blk-mq 硬體佇列(也就是一對 SQ/CQ)。

  3. 追一次提交路徑:在 QEMU 裡(-device nvme),用 ftrace function_graph(回顧 P3-T13)或 kgdb(回顧 P3-T14)對一次 I/O 擷取從 nvme_queue_rq 開始的關鍵函式序列。

驗收檢核點: - (1) 在原始碼中正確指出命令提交入口(nvme_queue_rq)與其所屬檔案(pci.c)。 - (2) 用文字說明 blk-mq 硬體佇列與 nvme_queue(SQ/CQ 對)的 1:1 對應。 - (3) 用 ftrace/kgdb 擷取一次提交路徑的關鍵函式序列。
