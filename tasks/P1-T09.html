P1-T09 · 鎖、互斥與條件變數

一句話:鎖(mutex)讓臨界區「一次只有一人進入」,修好上一課的 race;條件變數讓執行緒高效地「等待某個條件成立」;而當兩個執行緒以不同順序搶兩把鎖,就會卡死成死結——理解這三件事,你就掌握了同步的核心工具與最大陷阱。

為什麼要先學這個(導讀)

上一課 P1-T08 讓你深刻理解了問題:共享狀態在並行下會 race。這一課給你解法:同步機制。

核心工具是 mutex(互斥鎖):把臨界區「圍起來」,確保同一時間只有一個執行緒能進入。回想 P1-T08 的試衣間比喻——mutex 就是那扇門的鎖,一次只放一個人進去。用它把 count++ 圍起來,race 就消失了,因為「讀-改-寫」三步在鎖的保護下會一氣呵成,不被別人插入。

但同步不只是「加鎖」這麼簡單。你還會遇到: - 有時執行緒需要等待某個條件(例如「等緩衝區有資料才能取」),光有鎖不夠,需要 條件變數(condition variable)。 - 用鎖會帶來一個新的、惡名昭彰的陷阱——死結(deadlock):兩個執行緒互相等對方手裡的鎖,永遠卡死。

為什麼這對你是 scope: direct?因為 kernel 的同步機制(mutex、spinlock、semaphore)直接建立在這些概念上。你寫 kernel module 保護共享資料時,要在這些鎖之間選型;kernel 還有專門偵測死結的工具 lockdep(P3)。這一課建立的「鎖、條件變數、死結」概念,是你日後在 kernel 裡做正確同步的基礎。你產品的多執行緒 app 也必須用這些工具保護共享狀態。

開始之前(前置確認)

  • 依賴:P1-T08(你已深刻理解 race condition、臨界區、為何需要互斥與原子性)。
  • 自我檢測: 1. 你能解釋「為什麼 count++ 在並行下會遺失更新」嗎?(讀-改-寫三步交錯。)這課就是要修好它。 2. 你還記得「臨界區」和「原子性」的定義嗎?(回顧 P1-T08 第 5 節。)mutex 就是用來保護臨界區的。

核心內容

拆成這幾節:(1) mutex:互斥鎖修好 race → (2) 鎖的紀律(忘記解鎖、error path)→ (3) 條件變數:高效等待 → (4) producer-consumer:bounded buffer → (5) 死結與四條件 → (6) 固定加鎖順序避免死結 → (7) 鎖的粒度,最後打通關。

1. mutex:互斥鎖,一次只有一人進入臨界區

mutex(mutual exclusion,互斥鎖) 是最基本的同步工具。它有兩個動作:lock(上鎖) 和 unlock(解鎖)。規則是:同一時間只有一個執行緒能持有這把鎖;當一個執行緒持有鎖時,其他想 lock 同一把鎖的執行緒會被擋住(阻塞),直到持鎖者 unlock。

用它把臨界區圍起來,就能保證「一次只有一人進入」:

    subgraph protected["用 mutex 保護 count++"]
        L["pthread_mutex_lock(&m)
← 想進臨界區先取得鎖"]
        CS["count++
(臨界區:讀-改-寫,
此刻只有我在做,不被插入)"]
        U["pthread_mutex_unlock(&m)
← 做完釋放鎖"]
        L --> CS --> U
    end

看一次兩執行緒競爭的流程,理解為什麼 race 消失了:

    S1["執行緒1:lock(m) 成功,持有鎖"]
    S2["執行緒2:想 lock(m)
→ 鎖已被持有 → 被阻塞,等待"]
    S3["執行緒1:完整做完 count++

關鍵:鎖讓臨界區「序列化」了——本來會交錯的讀-改-寫,現在被迫一個做完才換下一個。第 3 節 P1-T08 的更新遺失,根源是「執行緒 2 讀到執行緒 1 還沒寫回的舊值」;有了鎖,執行緒 2 根本進不來,直到執行緒 1 寫回並解鎖,所以它讀到的永遠是最新值。race 消失。

2. 鎖的紀律:忘記解鎖與 error path

鎖很有效,但用錯會製造新問題。最常見的紀律問題:

flowchart TB
    subgraph bugs["鎖的常見紀律錯誤"]
        FORGET["忘記解鎖:
lock 後某條路徑沒 unlock
→ 別的執行緒永遠等不到鎖(卡死)"]
        ERRPATH["error path 漏解鎖:
lock 後,中途出錯提早 return,
卻忘了在 return 前 unlock
→ 同樣鎖永遠不釋放"]
    end
    style FORGET fill:#c2603a,color:#f4ecd8
    style ERRPATH fill:#c2603a,color:#f4ecd8

特別是 error path 漏解鎖:

pthread_mutex_lock(&m);
if (something_failed) {
    return -1;        // ✗ 災難:沒 unlock 就 return,鎖永遠卡住
}
// ...
pthread_mutex_unlock(&m);

正確做法是確保所有離開臨界區的路徑(包括錯誤提早返回)都有 unlock。這在 kernel 程式碼裡是常見的 bug 來源(kernel 甚至發展出 goto 錯誤處理慣例、以及自動清理機制來對付它)。

核心原則:每個 lock 都要有對應的 unlock,且涵蓋所有退出路徑。 這呼應 P0-T06 的「每個 malloc 對應一個 free」——資源的取得與釋放要配對,鎖也是一種資源。

3. 條件變數:高效地等待某個條件

有時執行緒需要等待某個條件成立才能繼續。例如「等緩衝區有資料才能取」。一個笨方法是忙碌等待(busy-wait):

while (buffer_is_empty()) { }   // ✗ 笨方法:空轉,瘋狂佔用 CPU 檢查

這浪費大量 CPU——執行緒不停地「看一下、還沒、再看一下」,空轉燒 CPU 卻什麼也沒做。條件變數(condition variable) 解決這個問題:它讓執行緒睡眠等待,直到別的執行緒「通知」條件可能成立了才被喚醒。

flowchart TB
    subgraph cv["條件變數:睡著等,不空轉"]
        WAIT["執行緒:條件不成立
→ wait(cond):釋放鎖並睡眠
(不佔 CPU)"]
        SIGNAL["另一個執行緒:讓條件成立後
→ signal(cond):喚醒等待者"]
        WAKE["被喚醒的執行緒:
重新取得鎖,再檢查條件
(成立就繼續,否則再睡)"]
        WAIT -.被通知.-> WAKE
        SIGNAL --> WAKE
    end
    style WAIT fill:#6fa8b8,color:#10100e
    style SIGNAL fill:#e8a33d,color:#10100e
    style WAKE fill:#8a9a5b,color:#10100e

條件變數總是和 mutex 搭配使用,典型用法:

pthread_mutex_lock(&m);
while (!condition)                    // 用 while 不是 if(下面解釋)
    pthread_cond_wait(&cond, &m);     // 原子地:釋放鎖 + 睡眠;被喚醒時重新持鎖
// 此時 condition 成立,且持有鎖,可安全操作共享資料
pthread_mutex_unlock(&m);

為什麼用 while 而非 if 檢查條件? 因為執行緒被喚醒後,條件不保證仍然成立(可能有別的執行緒搶先把資源用掉了,或發生了「偽喚醒」)。所以醒來要重新檢查條件,不成立就再睡——用 while 迴圈才能做到「醒來再驗一次」。用 if 只檢查一次,可能在條件其實不成立時往下走,造成 bug。這是條件變數最經典的正確用法。

4. producer-consumer:用鎖與條件變數實作 bounded buffer

把鎖和條件變數組合起來,實作一個經典又實用的並行模式:生產者-消費者(producer-consumer) 配上一個容量有限的緩衝區(bounded buffer)。

場景:一些執行緒(生產者)往緩衝區放資料,另一些(消費者)從緩衝區取資料。緩衝區容量有限,所以:滿了,生產者要等(等消費者取走騰出空間);空了,消費者要等(等生產者放入)。

    end
    PROD["生產者
放資料"] -->|"滿了就 wait
(等『不滿』條件)"| BUF
    BUF -->|"空了就 wait
(等『不空』條件)"| CONS["消費者
取資料"]
    NOTE["用 1 把 mutex 保護緩衝區(臨界區),
2 個條件變數:
『不滿』(放入後 signal 給生產者)
『不空』(取出後 signal 給消費者)"]
    system --> NOTE
    style BUF fill:#e8a33d,color:#10100e
    style NOTE fill:#6fa8b8,color:#10100e

運作邏輯: - 生產者:lock → 若緩衝區滿,wait「不滿」條件 → 放入資料 → signal「不空」(通知消費者有東西了)→ unlock。 - 消費者:lock → 若緩衝區空,wait「不空」條件 → 取出資料 → signal「不滿」(通知生產者有空間了)→ unlock。

這個模式直接對應你的工作:你的 I/O 路徑就是典型的生產者-消費者——例如一端產生 I/O 請求、另一端處理它們,中間用佇列(緩衝區)銜接。理解 bounded buffer,你就理解了這類資料流的同步骨架。kernel 裡大量使用類似的「佇列 + 同步」結構。

5. 死結(deadlock)與它的四個成因

鎖解決了 race,但引入了並行程式設計最惡名昭彰的陷阱:死結(deadlock)——多個執行緒互相等待對方持有的資源,結果全部永遠卡住。

最經典的場景:兩個執行緒,兩把鎖,以不同順序取得:

① lock(B) 成功
② 想 lock(A)...等待"]

    T1 -.“等執行緒2手上的 B”.-> T2
    T2 -.“等執行緒1手上的 A”.-> T1
    RESULT["互相等待 → 兩個都永遠卡死
(誰都不肯放手,誰都拿不到第二把)"]
    deadlock --> RESULT

死結的發生,需要同時滿足四個條件(經典的 Coffman 條件)。理解它們,因為「破壞任一個」就能避免死結:

    subgraph four["死結的四個必要條件(全滿足才會死結)"]
        C1["① 互斥(mutual exclusion)

(鎖的本質,難消除)"]
        C2["② 持有並等待(hold and wait)

        C3["③ 不可搶奪(no preemption)
資源不能被強行奪走,
只能由持有者主動釋放"]
        C4["④ 循環等待(circular wait)
形成一個環:
A 等 B 持有的、B 等 A 持有的"]
    end
    style C1 fill:#6fa8b8,color:#10100e
    style C2 fill:#6fa8b8,color:#10100e
    style C3 fill:#6fa8b8,color:#10100e

關鍵:這四個條件必須「同時」成立才會死結;破壞其中任何一個,死結就不會發生。 最常用、最實用的破壞點是第④個「循環等待」——下一節說明怎麼破壞它。

6. 破解死結:固定加鎖順序

破壞「循環等待」最簡單有效的方法:規定所有執行緒都以「相同的固定順序」取得鎖。

flowchart TB
    subgraph fix["固定加鎖順序:永遠先 A 後 B"]
        T1["執行緒1:
lock(A) → lock(B)"]
        T2["執行緒2:
lock(A) → lock(B)
(也是先 A 後 B,不再相反)"]
    end
    WHY["為什麼有效:
若執行緒2也要先拿 A,
那它在拿到 A 之前不會去碰 B
→ 不可能形成『1等B、2等A』的環
→ 破壞了循環等待條件"]
    fix --> WHY
    style T1 fill:#8a9a5b,color:#10100e
    style T2 fill:#8a9a5b,color:#10100e
    style WHY fill:#e8a33d,color:#10100e

原理:如果規定「永遠先拿 A 再拿 B」,那就不可能出現「執行緒 1 拿了 A 等 B、執行緒 2 拿了 B 等 A」的環——因為執行緒 2 要拿 B 之前,必須先拿到 A,而 A 在執行緒 1 手上,所以執行緒 2 會卡在「等 A」,但它還沒拿任何鎖(沒有 hold and wait 的環),執行緒 1 因此能順利拿到 B、做完、釋放,執行緒 2 再接手。循環被打破。

這就是「固定加鎖順序」原則:在你的程式裡,為所有的鎖定義一個全域的取得順序,所有執行緒都遵守。違反固定加鎖順序(不同地方以不同順序取鎖)是死結最常見的成因。 kernel 對此極其嚴格,還有 lockdep 工具自動偵測「加鎖順序不一致」的潛在死結(P3)。

7. 鎖的粒度:粗與細的權衡

最後一個重要概念:鎖的粒度(granularity)——你用一把鎖保護「多大範圍」的資料?

flowchart TB
    Q{"鎖的粒度?"}
    Q -->|"粗粒度(coarse):
一把大鎖保護所有共享資料"| COARSE["優點:簡單、不易出錯、不易死結
缺點:序列化嚴重
(大家都搶這一把,並行度低)"]
    Q -->|"細粒度(fine):
很多小鎖各保護一小塊"| FINE["優點:並行度高
(操作不同資料的執行緒不互相擋)
缺點:複雜、易出錯、易死結
(多把鎖 → 加鎖順序問題)"]
    style COARSE fill:#6fa8b8,color:#10100e
    style FINE fill:#e8a33d,color:#10100e

這是一個經典權衡: - 粗粒度鎖(一把大鎖管全部):簡單、安全,但所有執行緒都得搶同一把鎖,並行度低——退化成「大家排隊一個一個來」,失去多核心的好處。 - 細粒度鎖(多把小鎖各管一塊):並行度高(操作不同資料的執行緒可同時進行),但複雜得多——多把鎖意味著更容易違反加鎖順序、更容易死結、更難維護。

沒有絕對的對錯,要看場景權衡。 一般原則:先用粗粒度確保正確,有效能瓶頸再考慮細化。kernel 的演進史就是一部「鎖粒度不斷細化」的歷史(從早期的大內核鎖 BKL,到如今高度細粒度的鎖)——這是為了在多核心上擴展效能,代價是巨大的複雜度。你日後為產品的共享資料選鎖時,也要做這個權衡。

一句話總結:mutex 透過「一次一人進入臨界區」修好 race,條件變數讓執行緒高效等待條件(producer-consumer 是其經典組合),但鎖引入了死結這個大陷阱——破壞「循環等待」(固定加鎖順序)是最實用的解法,而鎖粒度則是「簡單安全 vs 高並行」的權衡;這些正是你日後在 kernel 裡選鎖、避死結的基礎。

常見誤區與踩雷提醒

誤區一:兩鎖以不同順序取得 → 死結。 這是死結最常見的成因(違反固定加鎖順序)。解法:為所有鎖定義全域固定的取得順序,所有執行緒遵守。

誤區二:忘記解鎖,或 error path 漏解鎖。 lock 後若某條路徑(尤其中途出錯提早 return)沒 unlock,鎖永遠卡住,別的執行緒餓死。確保所有退出路徑都解鎖。

誤區三:用 busy-wait 取代條件變數。 while(!condition){} 空轉燒 CPU。要等條件用條件變數(睡眠等待 + 被喚醒),別空轉。

誤區四:條件變數用 if 而非 while 檢查條件。 被喚醒後條件不保證仍成立(可能被搶先、或偽喚醒),要用 while 迴圈醒來重新檢查。用 if 可能在條件不成立時往下走,造成 bug。

誤區五:鎖粒度過大(序列化)或過小(難維護、易死結)。 粗粒度簡單但並行度低;細粒度並行度高但複雜易死結。先求正確(粗),有瓶頸再謹慎細化。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。需要 pthread。

任務 A — 用 mutex 修好 P1-T08 的 race 拿 P1-T08 任務 A 的程式,在 counter++ 外面加上 mutex:

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
void *worker(void *_) {
    for (int i = 0; i < N; i++) {
        pthread_mutex_lock(&m);
        counter++;
        pthread_mutex_unlock(&m);
    }
    return NULL;
}

跑,確認結果穩定等於 2000000(多跑幾次都一樣)。對比 P1-T08 沒加鎖時的隨機小於 2000000——這就是鎖的威力。

任務 B — 實作 bounded buffer(producer-consumer) 實作一個容量為 N 的環形緩衝區,用 1 把 mutex + 2 個條件變數(「不滿」「不空」)。開幾個生產者執行緒、幾個消費者執行緒,生產者放入連續整數、消費者取出並累計。驗收:不丟資料、不死結、不 busy-wait(消費者空時要 cond_wait 睡眠而非空轉)。記得條件檢查用 while。

任務 C — 製造一個死結,再修好它 故意寫一個必然死結的雙鎖程式:

// 執行緒1:lock(A); sleep(1); lock(B); ...
// 執行緒2:lock(B); sleep(1); lock(A); ...   ← 相反順序

(加 sleep 是為了讓死結幾乎必然發生。)在 VM 裡跑,觀察程式卡死(兩執行緒都不結束)。然後寫出死結的四個條件如何在此滿足,再修正:讓執行緒 2 也以「先 A 後 B」的順序取鎖,確認程式不再卡死。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 加 mutex 後 P1-T08 的結果穩定等於 2,000,000。 2. ☐ 實作容量為 N 的 bounded buffer,多 producer/consumer 下不丟資料、不死結、不 busy-wait。 3. ☐ 寫出一個必然死結的雙鎖程式並說明四條件,再以固定加鎖順序修正。

評分量表: - 60(及格):能用鎖修好 race。 - 80(熟練):能實作 producer-consumer(bounded buffer)。 - 100(精通):能分析鎖粒度取捨,並預示 kernel 的鎖選型(mutex/spinlock/semaphore)。

延伸與銜接

  • 對應工作場景:直接對應——kernel 的 mutex/spinlock/semaphore 選型、死結預防(lockdep,見 P3)直接建立在這些概念上。你產品的多執行緒 app 也要用這些工具保護共享狀態。
  • 這課餵給未來的(你的並行主線):鎖/死結 → P3-T08 kernel 鎖機制與選型、P3-T10 進階同步、lockdep;producer-consumer → 你的 I/O 佇列同步;「鎖只是同步的一種」→ P1-T10 原子操作與 lock-free 的入門。
  • 下一步 → P1-T10 原子操作、memory ordering 與 memory barrier:你已經會用鎖保護臨界區。但鎖有成本(取得/釋放、可能阻塞)。下一課進入更底層、也更燒腦的主題:原子操作(不用鎖就能安全地 ++)、以及一個會顛覆你直覺的事實——編譯器和 CPU 會「重排」你的記憶體存取順序,使得多執行緒看到的順序不符合你寫的程式碼。這需要 memory barrier 來駕馭。這課只求建立正確直覺與「敬畏感」,但它是 kernel lock-free 結構、以及你 DMA 工作(描述子必須在按門鈴前對裝置可見)的根。
