P5-T01 · 儲存堆疊總覽與 Linux Storage Stack Diagram

一句話:從 user 的一次 read()/write() 到實體 NVMe,資料要穿過好幾層——VFS、page cache、檔案系統、block layer、I/O 排程、驅動、裝置。先有這張全景圖,你才知道自己產品要在哪一層動刀;而你的高效能路徑很可能用 O_DIRECT 繞過 page cache,直達 block/NVMe。

為什麼要先學這個(導讀)

歡迎來到 Phase 5——這是你產品的核心領域:block layer、儲存堆疊、NVMe。前面四個階段(C 功底、系統概念、kernel 機制、裝置驅動)都是為了讓你能在這裡讀懂、修改 block layer 與 NVMe 驅動。而第一步,跟 P3-T01 一樣,是先建立全景地圖。

核心問題:當 user 程式做一次 read() 或 write(),資料怎麼從應用程式一路到達實體 NVMe SSD?中間經過哪些層?這就是 Linux 儲存堆疊(storage stack)。由上而下大致是:

  • VFS(虛擬檔案系統):統一的檔案抽象——不管底下是哪種檔案系統,user 都用同一套 open/read/write。
  • page cache(頁快取):在記憶體裡快取檔案內容,加速重複存取(回顧 P2-T06 XArray 就是 page cache 的索引)。
  • 檔案系統(ext4、XFS……):把「檔案 + offset」翻譯成「裝置上的哪些區塊」。
  • block layer(區塊層):管理對區塊裝置的 I/O——把請求組織成 bio/request、排程、派發。這是你產品的主戰場。
  • I/O 排程器:決定 I/O 請求的順序/合併。
  • 裝置驅動(NVMe driver):把請求送給實際的硬體。
  • 裝置(NVMe SSD):真正存資料的地方。

一個對你極關鍵的概念:buffered I/O vs O_DIRECT。一般的 I/O 是 buffered——經過 page cache(快取、可能延後寫入)。但用 O_DIRECT 開檔,I/O 繞過 page cache,直接在使用者緩衝區和裝置之間傳輸。你產品的高效能/零拷貝路徑很可能走 O_DIRECT——因為你要把 NVMe 的資料直接餵給 GPU,不想經過 page cache 的複製。

為什麼這對你是 scope: direct?如上——先有全景才知道自己在哪一層動刀,而 O_DIRECT 繞過 page cache 直達 block/NVMe 正是你資料路徑的特性。這一課是整個 Phase 5 的地圖。

2. VFS:統一檔案抽象

最上層是 VFS(Virtual File System,虛擬檔案系統)。它的職責:提供統一的檔案介面,讓 user 不管底下是 ext4、XFS、還是別的檔案系統,都用同一套 open/read/write/close。

    USER4 --> VFS6["VFS:統一介面層
把通用的檔案操作,
分派給『該檔案所屬檔案系統』的實作"]

(像 file_operations,但在檔案系統層級)"]
    VFS6 --> NOTE12
    style VFS6 fill:#e8a33d,color:#10100e
    style NOTE12 fill:#8a9a5b,color:#10100e

VFS 是一個抽象層:它定義「檔案系統該提供哪些操作」(一套 ops 介面,又是 P0-T07 的 ops 結構模式),各個檔案系統(ext4、XFS)提供自己的實作。user 的 read/write 先到 VFS,VFS 再分派給該檔案所屬的檔案系統。

這個抽象的價值:user 程式、以及上層的 page cache 機制,不必管底下是哪種檔案系統——統一介面。這跟 P4-T02 的字元裝置 file_operations 是同一個精神,只是在檔案系統層級。

3. page cache 的角色

page cache(頁快取) 是 VFS 之下的關鍵一層:它在記憶體裡快取檔案的內容(以頁為單位),讓重複存取的檔案資料不必每次都讀裝置。

flowchart TB
    READ2["user read 一個檔案的某段"]
    READ2 --> CHECK5{"那段內容在 page cache 裡嗎?
(用 XArray 索引:檔案 offset → 快取頁,P2-T06)"}
    CHECK5 -->|"在(cache hit)"| HIT["直接從記憶體回傳 → 快!不碰裝置"]
    CHECK5 -->|"不在(cache miss)"| MISS["從裝置讀進來、放進 page cache、再回傳
(下次同段就 hit)"]
    WRITE3["user write:
通常先寫進 page cache(標記 dirty),
稍後再由 kernel 批次寫回裝置(writeback)
→ 寫入看起來很快(其實還沒落盤)"]
    style HIT fill:#8a9a5b,color:#10100e
    style MISS fill:#6fa8b8,color:#10100e
    style WRITE3 fill:#e8a33d,color:#10100e

page cache 的運作(回顧 P2-T06:它用 XArray 索引「檔案 offset → 快取頁」): - 讀:先看 page cache 有沒有(cache hit → 直接從記憶體回,快;miss → 從裝置讀進來、快取起來)。 - 寫:通常先寫進 page cache(標記 dirty),稍後由 kernel 批次寫回裝置(writeback)——所以寫入看起來很快(其實資料還在記憶體、還沒落盤)。

page cache 大幅加速重複存取,也讓寫入能批次化。但它有兩個代價:佔記憶體,以及一致性/持久性的延遲(寫了不代表落盤,要 fsync 才保證)。這帶出下一節對你最關鍵的選擇:要不要經過 page cache。

4. buffered vs O_DIRECT:經不經過 page cache

這是這一課對你最關鍵的概念。預設的 I/O 是 buffered(經過 page cache);但用 O_DIRECT 開檔,I/O 繞過 page cache。

flowchart TB
    subgraph buffered["buffered I/O(預設,經 page cache)"]
        B1["user 緩衝區 ←→ page cache ←→ 裝置
讀:可能 cache hit(快);寫:先進 cache 稍後 writeback
好處:快取加速、寫入批次化
代價:多一次複製(cache↔user)、佔記憶體、持久性延遲"]
    end
    subgraph direct["O_DIRECT(繞過 page cache)"]
        D1["user 緩衝區 ←→ 裝置(直接傳輸,不經 cache)
好處:無 cache 複製、不佔 cache 記憶體、行為可預測
代價:沒有快取加速、要求對齊、user 自己管快取
★ 高效能/零拷貝路徑常用 ★"]
    end
    buffered -.“O_DIRECT 繞過 page cache”.-> direct
    style B1 fill:#6fa8b8,color:#10100e
    style D1 fill:#8a9a5b,color:#10100e

兩者差異(驗收點:說明 buffered I/O 與 O_DIRECT 在是否經過 page cache 上的差異): - buffered(預設):經 page cache。讀可能 cache hit(快)、寫先進 cache 稍後 writeback。好處是快取加速、寫入批次化;代價是多一次複製(page cache ↔ user 緩衝區)、佔記憶體、持久性延遲。 - O_DIRECT:繞過 page cache,直接在 user 緩衝區和裝置之間傳輸。好處是沒有 cache 那次複製、不佔 cache 記憶體、行為可預測;代價是沒有快取加速、要求對齊(緩衝區與 offset 要對齊裝置區塊)、且 user 程式要自己管理快取策略。

對你產品的關鍵(常見誤區:以為所有 I/O 都經 page cache):不是——O_DIRECT 繞過。你的高效能/零拷貝路徑很可能走 O_DIRECT:因為你要把 NVMe 的資料直接餵給 GPU(透過 DMA,P6),經過 page cache 的複製反而是累贅。O_DIRECT 讓資料直達裝置,配合 mmap(P4-T03)/DMA,達成你要的零拷貝資料流。理解這個取捨,你才知道產品該用哪條路。

(另一個常見誤區:忽略 page cache 對效能與一致性的影響——它既是加速器也是「寫了不一定落盤」的來源,要 fsync 才保證持久。)

5. block layer 的位置:你的主戰場

block layer(區塊層) 在檔案系統之下、驅動之上。它的職責:管理對區塊裝置的 I/O——把上層的讀寫需求,組織成標準的 I/O 物件(bio/request,P5-T02),排隊、合併、派發給驅動。

① 把需求包成 bio(P5-T02)

④ 經 I/O 排程器(P5-T04)排序
⑤ 派發給驅動"]
    BLOCK5 --> BELOW["下層(裝置驅動,P5-T06):送給硬體"]
    NOTE13["★ 這是你產品的主戰場 ★
軟體 RAID(drivers/md/)在這一層附近運作:
把一個 I/O 拆成對多個底層裝置的 I/O + parity
(P3-T01 的全景:你動的就是 block/ 和 drivers/md/)"]
    BLOCK5 --> NOTE13

    style NOTE13 fill:#8a9a5b,color:#10100e

block layer 在堆疊中的位置(驗收點:指出 block layer 在整個堆疊中的位置):在檔案系統(或 O_DIRECT 直接進來)之下、裝置驅動之上。它把上層的區塊讀寫需求,組織成 bio/request、做多佇列管理(blk-mq)、排程、派發。

這是你產品的主戰場(回顧 P3-T01 全景:你動 block/ 和 drivers/md/):你的軟體 RAID 邏輯在這一層附近運作——把一個上層 I/O 拆成對多個底層 NVMe 裝置的 I/O,並計算 parity(交給 GPU)。後續 P5-T02/P5-T03 會深入 block layer 的物件與多佇列機制。

常見誤區:混淆檔案系統層與 block 層的職責——檔案系統管「檔案↔區塊的翻譯、目錄結構、metadata」;block layer 管「對區塊裝置的 I/O 組織與派發」。檔案系統說「我要裝置的第 1000~1007 區塊」,block layer 負責把這個需求高效地送到裝置。兩層職責不同,別混。

6. 一次 read() 穿越各層

把全景落實到「一次具體的 read() 怎麼走」——這是這一課要你能描述的:

    R1["user:read(fd, buf, 4096)(P1-T06 syscall 進 kernel)"]
    R1 --> R2["VFS:分派給該檔案的檔案系統"]
    R2 --> R3{"buffered 還是 O_DIRECT?"}

hit → 直接 copy_to_user 回傳(結束,不碰下層!)

    R5 --> R6
    R6 --> R7["block layer:包成 bio/request、blk-mq 佇列、排程"]
    R7 --> R8["NVMe driver:提交給裝置(SQ + doorbell,P5-T05)"]
    R8 --> R9["裝置讀資料 → DMA 回記憶體 → 完成中斷(P5-T05)"]

一次 read() 的旅程:user read() → VFS 分派 → (buffered:查 page cache,hit 就直接回、不碰下層;miss 或 O_DIRECT:往下)→ 檔案系統算出 sector → block layer 包成 bio/request、排程 → NVMe driver 提交(SQ + doorbell,P5-T05)→ 裝置讀、DMA 回記憶體、完成中斷 → 往上回傳給 user。

關鍵觀察:buffered 的 cache hit 根本不會碰到下層(block layer、驅動、裝置)——這就是 page cache 加速的本質。而 O_DIRECT 每次都走完整條路到裝置(沒有快取捷徑),所以行為可預測、但沒有快取加速。你產品若用 O_DIRECT,每次 I/O 都真的到 NVMe——這正是你要的(你要直接控制資料流到 GPU,不要 cache 介入)。

把「兩條路徑各走多遠」並排畫出來,加速的本質就一目了然:

常見誤區與踩雷提醒

誤區一:以為所有 I/O 都經 page cache。 O_DIRECT 繞過 page cache,直接在 user 緩衝區和裝置之間傳輸。你的高效能/零拷貝路徑很可能走 O_DIRECT。

誤區二:混淆檔案系統層與 block 層的職責。 檔案系統管「檔案↔區塊翻譯、目錄、metadata」;block layer 管「對區塊裝置的 I/O 組織與派發」。職責不同。

誤區三:忽略 page cache 對效能與一致性的影響。 page cache 既加速(cache hit)又延後持久性(寫了不一定落盤,要 fsync)。用 O_DIRECT 則無快取、行為可預測但無加速。理解取捨。

動手實作

環境:Linux(觀察 I/O,使用者態,安全)+ QEMU(若做 module 只在 VM)。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 畫出含至少 6 層的儲存堆疊圖並標註各層職責。 2. ☐ 說明 buffered I/O 與 O_DIRECT 在是否經過 page cache 上的差異。 3. ☐ 指出 block layer 在整個堆疊中的位置。

評分量表: - 60(及格):能複述各層。 - 80(熟練):能畫出完整路徑圖。 - 100(精通):能解釋 page cache/O_DIRECT 取捨並對應到自家資料路徑。

延伸與銜接

  • 對應工作場景:直接對應——你產品的高效能/零拷貝路徑很可能走 O_DIRECT 繞過 page cache 直達 block/NVMe;先有全景才知道自己在哪一層動刀。
  • 這課餵給未來的(你的 I/O 物件流動主線起點):整條堆疊 → P5-T02 block layer 的核心物件(bio/request)、P5-T03 blk-mq、P5-T05 NVMe 協定、P5-T06 NVMe 驅動;O_DIRECT/零拷貝 → P6 DMA、P4-T03 mmap;page cache → 回收 P2-T06 XArray。
  • 下一步 → P5-T02 block layer 核心物件(bio / bio_vec / request / request_queue):你有了全景。下一課深入 block layer 的核心資料結構——一個 I/O 在這裡長什麼樣:bio(描述一次 block I/O)、bio_vec(分散的記憶體片段,scatter-gather 的雛形——這正是後續 DMA 映射的來源!)、request、request_queue,以及一個 bio 如何被合併成 request。這些就是你產品操作的 I/O 物件——你用 P2-T02 list_head、P2-T03 container_of 練的讀碼能力,終於要用在真實的 block layer 結構上了。
