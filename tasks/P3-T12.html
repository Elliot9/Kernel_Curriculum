P3-T12 · 行程排程器內部(EEVDF,CFS 為歷史脈絡)

一句話:Linux 現行的預設排程器是 EEVDF(自 6.6 起取代了用了十幾年的 CFS)——它用「virtual deadline + lag」決定誰先跑,在公平之外更照顧延遲。理解它和 task_struct、runqueue、搶佔,你才知道你的 kthread/workqueue 何時被排到、I/O 延遲受什麼影響。

為什麼要先學這個(導讀)

回顧 P1-T07:你學過排程的概念(目標、演算法、RR/MLFQ、搶佔)。這一課看 Linux 實際的排程器內部——而這裡有個重要的「現況」:Linux 的預設排程器已經不是 CFS 了。

很多資料(包括一些書)還在講 CFS(Completely Fair Scheduler),它從 2007 年起當了十幾年的預設 fair-class 排程器。但自 Linux 6.6 起,EEVDF(Earliest Eligible Virtual Deadline First)取代了 CFS,成為 fair class 的預設排程器。所以這一課以 EEVDF 為現況教,CFS 作為歷史脈絡理解(它的很多概念被 EEVDF 沿用或改進)。

這一課要建立的: - task_struct:kernel 裡代表一個 task(行程/執行緒,回顧 P1-T05)的描述子——排程器排的就是它。 - 排程類別(scheduling classes):kernel 不只一個排程器,而是分「類別」(即時 rt、fair、idle 等),各有策略,有優先順序。 - EEVDF:現行 fair class 的演算法——用 virtual deadline 和 lag 決定誰先跑。 - runqueue:每個 CPU 的「可執行 task 佇列」。 - 搶佔(preemption):何時一個 task 被換下、由 CONFIG_PREEMPT* 決定。

為什麼這對你是 scope: indirect(間接對應)?因為理解排程器,你才知道你的 kthread / workqueue(回顧 P3-T10)何時被排到執行、優先權如何影響你 I/O 與 parity 工作的延遲。例如:你的 parity 計算 work 在 workqueue 裡,它何時被排到 CPU 跑、會不會被別的 task 搶佔、延遲多少——這些受排程器影響。雖然不像鎖/DMA 那樣每天直接寫,但理解它幫你推理 I/O 延遲。

開始之前(前置確認)

  • 依賴:P1-T07(排程概念:目標、RR/MLFQ、搶佔、time slice)、P3-T09(並行原語)。
  • 自我檢測: 1. 你還記得 P1-T07 的搶佔、time slice、公平 vs 延遲的權衡嗎?EEVDF 就是這些概念的真實實作與演進。 2. 你還記得 P1-T05 的「task 是排程單位」嗎?這課的 task_struct 就是那個 task 在 kernel 裡的樣子。
  • 環境:Linux(觀察工具)+ QEMU 虛擬機(module 實驗只在 VM)。

核心內容

拆成這幾節:(1) task_struct:被排程的東西 → (2) 排程類別的階層 → (3) CFS 的核心想法(歷史脈絡)→ (4) EEVDF:現況與它的改進 → (5) runqueue 與搶佔 → (6) nice 是比例分配,不是嚴格優先權,最後打通關。

1. task_struct:kernel 裡被排程的那個東西

回顧 P1-T05:在 Linux,行程和執行緒統一是 task。在 kernel 裡,每個 task 由一個 task_struct 結構描述——這是 kernel 最核心的結構之一,記錄了一個 task 的一切。

flowchart TB
    TASK["struct task_struct(每個 task 一個)"]
    TASK --> WHAT["記錄這個 task 的:
① 身份:pid、comm(程式名)
② 狀態:執行中/睡眠/...
③ 排程資訊:屬於哪個排程類別、優先權/nice、
   EEVDF 的 virtual time/lag 等
④ 記憶體:指向它的位址空間(P1-T05)
⑤ 開啟的檔案、信號... 等等"]
    WHAT --> CURRENT["在 kernel 程式碼裡,『current』指向
『當前正在這個 CPU 上執行的 task 的 task_struct』
→ current->pid、current->comm 取得當前 task 資訊"]
    style TASK fill:#6fa8b8,color:#10100e
    style CURRENT fill:#e8a33d,color:#10100e

task_struct 是排程器操作的對象——排程器就是在決定「下一個讓哪個 task_struct 上 CPU」。其中和排程相關的欄位包括:屬於哪個排程類別、優先權/nice 值、以及 EEVDF 用的 virtual time/lag 等。

一個你會直接用到的:current——在 kernel 程式碼裡,current 是個特殊的東西,指向「當前正在這個 CPU 上執行的 task 的 task_struct」。你在 module 裡可以用 current->pid、current->comm 取得「現在是誰在執行我這段程式碼」(驗收點:在 module 印出 current->comm 與 current->pid)。

2. 排程類別的階層:不只一個排程器

關鍵概念:Linux 不是只有一個排程器,而是有多個排程類別(scheduling classes),各管不同優先程度的 task,且有嚴格的優先順序:

flowchart TB
    subgraph classes["排程類別(由高到低優先,高的先被考慮)"]
        STOP["stop class(最高,系統內部用,如 CPU 熱插拔)"]
        DEADLINE["deadline class(SCHED_DEADLINE,有截止期限的即時)"]
        RT["rt class(即時 SCHED_FIFO/SCHED_RR,固定優先權)"]
        FAIR["fair class(SCHED_NORMAL,一般 task)
★ 這裡用 EEVDF(原本 CFS)★"]
        IDLE["idle class(最低,系統閒置時)"]
    end
    NOTE["排程器先看最高優先的類別有沒有可跑的 task;
有就跑它,沒有才往下一個類別看
→ 即時 task(rt/deadline)永遠優先於一般 task(fair)"]
    classes --> NOTE
    style FAIR fill:#e8a33d,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

階層(由高到低):stop → deadline → rt → fair → idle。排程器先看最高優先的類別有沒有可跑的 task,有就跑、沒有才往下看。所以即時類別(rt/deadline)的 task 永遠優先於一般類別(fair)的 task。

大多數一般 task(你的程式、kthread、workqueue 的工作)在 fair class(SCHED_NORMAL)——而 fair class 的演算法,就是這一課的主角:原本是 CFS,現在是 EEVDF。(即時類別 rt/deadline 用於有嚴格時間要求的場景;混淆 real-time class 與 fair class 是常見誤區——它們是不同類別、不同策略。)

3. CFS 的核心想法(歷史脈絡)

要理解 EEVDF,先懂它取代的 CFS(這是歷史脈絡,幫助理解演進)。CFS(Completely Fair Scheduler) 從 2007 年起當了十幾年的 fair class 排程器,核心想法是「完全公平」:

flowchart TB
    CFS["CFS(2007–6.6,現為歷史):模擬『理想的完全公平 CPU』"]
    CFS --> IDEA["核心想法:
記錄每個 task 累積的『virtual runtime(vruntime)』
= 它已經用了多少 CPU 時間(經權重調整)
→ 永遠挑 vruntime 最小的(用得最少的)先跑
→ 追求大家用的 CPU 時間趨於相等(公平)"]
    IDEA --> LIMIT["CFS 的不足:
對『公平』做得好,但對『延遲需求』表達不夠
(有些 task 不要多少 CPU,但需要『快速回應』)
→ 要靠額外的 latency-nice 補丁等手段"]
    style CFS fill:#6fa8b8,color:#10100e
    style LIMIT fill:#e8a33d,color:#10100e

CFS 的精神:記錄每個 task 的 virtual runtime(vruntime)——它累積用了多少 CPU 時間(經 nice 權重調整),然後永遠挑 vruntime 最小的(用得最少的)先跑,讓大家用的 CPU 時間趨於相等(回顧 P1-T07 的公平目標)。它用紅黑樹(P2-T05)按 vruntime 排序 task。

但 CFS 有個不足:它把「公平」做得很好,但對「延遲需求」表達不夠——有些 task 不需要多少 CPU 總量,但需要「需要時能快速被排到」(低延遲),CFS 只能靠額外的補丁(latency-nice)勉強處理。這個不足,正是 EEVDF 要改進的。

4. EEVDF:現況與它的改進

EEVDF(Earliest Eligible Virtual Deadline First) 自 Linux 6.6 起取代 CFS,成為 fair class 的預設排程器。它仍追求公平(沿用 vruntime/lag 的精神),但多了「virtual deadline」來處理延遲:

flowchart TB
    EEVDF["EEVDF(6.6 起,現行 fair class 預設)"]
    EEVDF --> LAG["① lag(落後量):
每個 task『應得的 CPU 時間』減去『實際拿到的』
→ lag 為正 = 它拿少了、『有資格(eligible)』該補
(這是公平的衡量,沿用 CFS 的精神)"]
    EEVDF --> DEADLINE2["② virtual deadline(虛擬截止期):
依 task 的 time slice 算一個『虛擬截止時間』
→ 在『有資格』的 task 中,挑 virtual deadline 最早的先跑"]
    LAG --> RESULT["結果:
既保證公平(靠 lag/eligibility),
又能讓『需要低延遲』的 task(較短 time slice → 較早的 deadline)
更快被排到 → 比 CFS 更好地兼顧公平與延遲"]
    DEADLINE2 --> RESULT
    style EEVDF fill:#e8a33d,color:#10100e
    style RESULT fill:#8a9a5b,color:#10100e

EEVDF 的兩個關鍵概念(驗收點:說明 EEVDF 相對 CFS 的差異重點): - lag(落後量):一個 task「應得的 CPU 時間」減「實際拿到的」。lag 為正代表它拿少了、「有資格(eligible)」優先補上——這是公平的衡量(沿用 CFS 精神)。 - virtual deadline(虛擬截止期):依 task 的 time slice 算一個虛擬截止時間。EEVDF 在「有資格的 task」中,挑 virtual deadline 最早的先跑。

效果:既保證公平(靠 lag/eligibility),又能讓需要低延遲的 task 更快被排到(低延遲需求 → 較短 time slice → 較早的 deadline → 更快被選中)。這正是 EEVDF 相對 CFS 的改進——把「延遲」內建進演算法,不再需要 CFS 那些 latency 補丁。

重要的現況提醒(常見誤區:仍以為預設排程器是 CFS):6.6 起預設已是 EEVDF。你看舊書/舊資料會講 CFS,要知道那是前一代,現況是 EEVDF。(這呼應整個課程「以現況為準」的原則;CFS 文件仍有價值,因為很多基礎概念 EEVDF 沿用。)

5. runqueue 與搶佔

兩個配套概念。runqueue:每個 CPU 有自己的「可執行 task 佇列」,排程器從本 CPU 的 runqueue 挑下一個跑。

flowchart TB
    subgraph runqueues["每個 CPU 一個 runqueue"]
        RQ0["CPU 0 的 runqueue:它的可執行 task
(各排程類別的 task 結構)"]
        RQ1["CPU 1 的 runqueue:..."]
    end
    PICK["排程器在本 CPU 的 runqueue 上,
按類別階層 + EEVDF 規則挑下一個 task 跑"]
    runqueues --> PICK
    PREEMPT["搶佔(preemption):
何時把當前 task 換下、讓別的上?
由 CONFIG_PREEMPT* 設定決定:
不同設定 → kernel 可被搶佔的程度不同"]
    PICK --> PREEMPT
    style PICK fill:#6fa8b8,color:#10100e
    style PREEMPT fill:#e8a33d,color:#10100e

  • runqueue:每 CPU 一個可執行 task 佇列(per-CPU,呼應 P3-T09 per-CPU 的精神——避免多核爭搶同一佇列)。排程器在本 CPU 的 runqueue 上挑 task。
  • 搶佔(preemption):何時把當前 task 換下(回顧 P1-T07)。kernel 能不能被搶佔、何時搶佔,由 CONFIG_PREEMPT* 設定決定——有「不可搶佔」「自願搶佔」「完全可搶佔」「即時(PREEMPT_RT)」等不同設定。常見誤區:以為 kernel 一定可搶佔——其實取決於 CONFIG_PREEMPT*。搶佔程度影響延遲:可搶佔性高 → 高優先 task 能更快插隊(低延遲),但有額外開銷。

對你的意義:搶佔設定影響你 I/O/parity 工作的延遲。例如可搶佔的 kernel 讓你的高優先工作能更快被排到,但若你的工作在不可搶佔的區段(如持 spinlock),它就不會被搶佔。

6. nice 是比例分配,不是嚴格優先權

最後一個重要釐清,關於 nice 值。nice 是調整 fair class task 優先程度的傳統手段(範圍約 -20 到 +19,越低越「不謙讓」、越優先)。但它的語意常被誤解:

flowchart TB
    NICE["nice 值(fair class):-20(最優先)~ +19(最謙讓)"]
    NICE --> WRONG["✗ 誤解:把 nice 當『嚴格優先權』
(以為 nice 低的會完全壓制 nice 高的)"]
    NICE --> RIGHT["✓ 正確:fair class 是『比例分配』
nice 影響的是『拿到 CPU 時間的比例權重』
→ nice 低的拿『較大比例』的 CPU,
但 nice 高的仍會分到一些(不會完全餓死)"]
    CONTRAST["對比:真正的『嚴格優先權』在 rt class
(高優先 rt task 會完全壓制低優先的)
→ 別把 fair 的 nice 和 rt 的優先權混為一談"]
    RIGHT --> CONTRAST
    style WRONG fill:#c2603a,color:#f4ecd8
    style RIGHT fill:#8a9a5b,color:#10100e
    style CONTRAST fill:#e8a33d,color:#10100e

關鍵(常見誤區:把 nice 值當成嚴格優先權):fair class(EEVDF/CFS)是比例分配——nice 影響的是「拿到 CPU 時間的比例權重」,不是「絕對的先後」。nice 低的 task 拿較大比例的 CPU,但 nice 高的仍會分到一些,不會被完全餓死。

對比:真正的「嚴格優先權」在 rt class(即時)——高優先的 rt task 會完全壓制低優先的。所以別把「fair class 的 nice」和「rt class 的優先權」混為一談(這也回到第 2 節:不同排程類別,不同策略)。

對你的意義:如果你想讓某個 I/O/parity 工作「絕對優先」,調 nice(fair class)只是調比例,不保證絕對優先;真要嚴格優先得用 rt class(但 rt 有其風險,例如餓死別的 task,要謹慎)。

常見誤區與踩雷提醒

誤區一:仍以為預設排程器是 CFS。 自 6.6 起 fair class 預設是 EEVDF。舊書/資料講 CFS 是前一代;現況是 EEVDF(沿用部分 CFS 概念)。

誤區二:把 nice 值當成嚴格優先權。 fair class 是比例分配——nice 影響 CPU 時間的比例權重,nice 高的仍分到一些(不會完全餓死)。嚴格優先在 rt class。

誤區三:混淆 real-time class 與 fair class。 它們是不同排程類別、不同策略(rt 固定優先權、會壓制;fair 比例分配)。一般 task 在 fair;rt 用於嚴格時間需求。

誤區四:以為 kernel 一定可搶佔。 取決於 CONFIG_PREEMPT* 設定(不可搶佔/自願/完全/即時)。搶佔程度影響延遲與開銷。
