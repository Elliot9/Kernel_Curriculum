P0-T01 · 開發環境與編譯流程

一句話:搞懂當你打下 gcc hello.c 並按下 Enter 的那一刻,電腦到底偷偷做了哪四件事。這四件事的放大版,就是你日後編譯整個 Linux kernel 的流程。

為什麼要先學這個(導讀)

你寫 PHP 或 JS 的時候,從來不需要「編譯」。你存檔、重新整理瀏覽器,程式就跑了。背後有一個直譯器(interpreter)即時讀你的原始碼、即時執行——你寫的文字,直譯器一行一行邊讀邊做。

Go 稍微近一點——你會 go build——但它把整條流程包成一個指令,中間發生什麼你看不到,也不需要看到。

C 不一樣,而且這個不一樣不是細節,是世界觀的差異。C 的原始碼在執行前,會先被一連串工具「翻譯」成 CPU 能直接執行的機器碼(一堆 0 與 1 的指令)。這條翻譯線有四個階段,每個階段都有明確的輸入和產物、都可能出錯、都可以單獨停下來檢查。

為什麼你第一課就要懂這個?三個理由:

  1. 它是後面一切的基礎。編譯 Linux kernel、把你的程式碼變成一個能掛進核心的模組(module),全都是這條翻譯線的工業級放大版。kernel 不是「跑起來的直譯腳本」,它是被編譯成一大塊機器碼、在開機時被載入記憶體執行的東西。
  2. 它讓你會看錯誤。C 的編譯錯誤訊息對新手像天書,但其實每個錯誤都來自某個特定階段。知道是哪一階段出錯,你就知道往哪裡找問題。最經典的混淆——「編譯錯誤」vs「連結錯誤」——這課會幫你一刀切清。
  3. 它建立你的「機械觀」。高階語言把太多東西藏起來,養成「程式是魔法」的直覺。kernel 開發要求相反的心態:每件事都是可解釋的機械步驟。把 hello.c 怎麼變成可執行檔弄清楚,是戒掉「魔法直覺」的第一步。

開始之前(前置確認)

這是第一課,沒有前置 task。但請確認你手上有一台 Linux 環境(實體機、虛擬機、或 WSL2 都可以),並能打開終端機。自我檢測:

  1. 你能在終端機打 gcc --version 並看到版本輸出嗎?(沒有的話:sudo apt install build-essential)
  2. 你知道「終端機裡的當前目錄」是什麼意思嗎?(打 pwd 會告訴你你現在在哪個資料夾)
  3. 你用過任何文字編輯器(vim / nano / VS Code)存一個檔案嗎?

三題都「是」,就可以開始。

核心內容

這課的核心拆成這幾個小節:(1) 直譯 vs 編譯的根本差異 → (2) 四階段總覽地圖 → (3)~(6) 逐站深入(前處理／編譯／組譯／連結)→ (7) 編譯錯誤 vs 連結錯誤 → (8) Makefile → (9) gdb 入門,最後用一張總圖打通關。

1. 直譯 vs 編譯:同一支程式,兩種「被執行」的方式

先把最根本的差異講清楚,因為這決定了你為什麼要學後面所有東西。

直譯(你熟悉的 JS/PHP):有一個「直譯器」程式,它讀你的原始碼,一邊讀一邊執行。你的原始碼從頭到尾都是「文字」,執行時才被直譯器理解。好處是改完馬上能跑;代價是每次執行都要重新理解一遍,較慢,而且你得隨身帶著那個直譯器(瀏覽器、PHP runtime)。

編譯(C):有一條「翻譯線」,在執行之前就把你的原始碼一次翻譯成 CPU 能直接執行的機器碼,存成一個獨立的可執行檔。之後執行的是那個機器碼檔,CPU 直接跑,不需要任何直譯器在場。好處是快、獨立;代價是每次改完都要重新翻譯一遍。

比喻:直譯像「現場口譯」——講者(你的程式碼)說一句,口譯員(直譯器)即時翻一句給聽眾。編譯像「事先把整本書翻譯成另一種語言出版」——翻譯只做一次,之後讀者直接讀譯本,不需要口譯員在場。

比喻的極限:這個對比抓住了「翻譯時機」的差異,但別過度推論成「編譯一定比直譯好」。現代 JS 引擎有 JIT(即時編譯)等技術,界線其實是模糊的。對我們的目的而言,重點只有一個:C 走的是「執行前先翻譯成機器碼」這條路,而那條路有四個你必須理解的階段。

2. 四階段總覽:一張地圖

先給你整條翻譯線的地圖,再逐站講解。當你打 gcc hello.c -o hello,gcc 其實是個總指揮,它依序調動四個工具,把原始碼一路變成可執行檔:

每一站的「停車鍵」——gcc 提供旗標讓你在任一階段停下來、檢查那一站的產物:

這張表是這課的骨架。 接下來四節,我們一站一站把車停下來,打開產物親眼看。

3. 階段①:前處理(Preprocessing)

它在做什麼:處理所有以 # 開頭的指令。最常見的兩個: - #include <stdio.h> 會被整份貼上 stdio.h 這個檔案的全部內容。 - #define MAX 100 會把後面所有出現的 MAX 文字,換成 100。

注意:這一階段純粹是文字操作——剪貼、取代。它完全不懂 C 的語法,不檢查對錯,只是機械地處理 # 開頭的東西。

flowchart TB
    SRC["hello.c
#include <stdio.h>
int main(void){
  printf(...);
}"]
    STEP1["把 #include 那一行
替換成 stdio.h 的全部內容
(幾百~上千行)"]
    STEP2["把所有 #define 的縮寫
展開成它定義的文字"]
    OUT["hello.i
(沒有任何 # 指令了,
全是攤開的純 C 文字,
常從幾行暴增到上千行)"]
    SRC --> STEP1 --> STEP2 --> OUT
    style SRC fill:#8a9a5b,color:#10100e
    style OUT fill:#e8a33d,color:#10100e

比喻:這就像你寫信時用了很多「詳見附件 A」。前處理器做的事,就是把附件 A 的全文直接剪貼到信裡該出現的位置,並把你定義的所有縮寫(「本公司」=「○○股份有限公司」)展開成全稱。處理完之後,信裡不再有任何「縮寫」或「詳見某處」——全部是攤開的、完整的文字。

比喻的極限:剪貼附件聽起來無害,但 #include 是純文字貼上,不檢查內容對不對。如果被貼進來的標頭檔本身有錯,錯誤會在你「貼進來之後」才被下一階段抓到,而且錯誤行號會指向展開後的位置(可能是第 873 行),不是你原始碼裡那短短一行 #include。這是初學者看 C 編譯錯誤常一頭霧水的根源之一。

親眼看它(worked example):

gcc -E hello.c -o hello.i
wc -l hello.c hello.i      # 比較行數

你會看到 hello.c 可能只有 6 行,但 hello.i 暴增到幾百上千行——那些多出來的全是被 #include <stdio.h> 貼進來的內容(printf 的宣告等等)。打開 hello.i 翻到最後,你會在一堆陌生的宣告之後,找到你自己那幾行 main。

4. 階段②:編譯(Compilation)

它在做什麼:把前處理後的純 C 程式碼,翻譯成組合語言(assembly)。

組合語言是什麼?它是「人還勉強看得懂的 CPU 指令」——每一行對應一個 CPU 動作,像 mov(搬資料)、add(相加)、call(呼叫一個函式)。它介於「人類語言」和「機器的 0/1」之間。

flowchart LR
    subgraph layers["三層語言,由高到低"]
        direction TB
        L1["C 語言
int x = a + b;
(接近人類思維)"]
        L2["組合語言
mov eax, [a]
add eax, [b]
(一行一個 CPU 動作)"]
        L3["機器碼
10001011 00000101...
(CPU 直接吃的 0/1)"]
        L1 -->|"② 編譯"| L2
        L2 -->|"③ 組譯"| L3
    end
    style L1 fill:#8a9a5b,color:#10100e
    style L2 fill:#6fa8b8,color:#10100e
    style L3 fill:#24221d,color:#cfc6b0

比喻:如果 C 是「中文」、機器碼是「電報的點與線」,那組合語言就是「注音符號」——它是介於人類語言和機器訊號之間的中間層。一個注音對應一個發音動作,人還是讀得出來,但它已經非常接近「機器實際發出的東西」了。

親眼看它(worked example):

gcc -S hello.c -o hello.s

打開 hello.s,你會看到一個 main: 標籤,底下是一串 mov、call、ret 之類的指令。你現在完全不需要看懂每一行——這課的目標只是讓你認得「喔,我的 C 程式被翻成這種東西了,這就是組合語言的長相」。你會注意到裡面有個 call printf——記住這個,下一節會用到。

5. 階段③:組譯(Assembly)

它在做什麼:把組合語言(文字)翻成機器碼(真正的 0 與 1),產出一個 .o 檔,叫目的檔(object file)。這時候已經是 CPU 看得懂的二進位指令了。

但這裡有個關鍵:.o 檔還不能執行。 為什麼?

回想上一節 hello.s 裡那行 call printf。你的 hello.c 用了 printf,但 printf 的程式碼根本不在你的檔案裡——它住在 C 標準函式庫裡(別人早就寫好、編譯好的)。所以你的 .o 檔目前的狀態是:「我這裡要呼叫一個叫 printf 的東西……但我不知道它在哪個位址。」

flowchart TB
    OBJ["hello.o(目的檔)"]
    HAS["✓ 有:你自己 main 的機器碼"]
    HOLE["✗ 缺:printf 在哪?
留了一個『待填位址』的空缺
(這種未解決的引用叫 unresolved symbol)"]
    OBJ --> HAS
    OBJ --> HOLE
    CANT["→ 因為有空缺,所以還不能執行"]
    HOLE --> CANT
    style HAS fill:#8a9a5b,color:#10100e
    style HOLE fill:#c2603a,color:#f4ecd8
    style CANT fill:#c2603a,color:#f4ecd8

這個「不知道在哪」的空缺,要靠下一階段(連結)補上。

親眼看它(worked example):

gcc -c hello.c -o hello.o     # 編譯 + 組譯,但不連結
file hello.o                  # 會說這是 "relocatable" 物件檔(可重定位 = 還沒定好位址)
objdump -d hello.o            # 反組譯:把機器碼「反翻譯」回組合語言給你看

objdump -d 會顯示 main 的機器碼對照組合語言。你會看到那個對 printf 的呼叫,它的目標位址此刻是空的或佔位的——這就是「待填的空缺」的鐵證。

比喻:.o 是一份「還沒裝訂、缺了引用頁」的書稿。內文(你的 main)都印好了,但凡是寫到「(此處引用《printf 大全》第 X 頁)」的地方,頁碼還是空白——因為你手上沒有那本書,填不了頁碼。

6. 階段④:連結(Linking)

它在做什麼:把你的 .o 檔,跟它用到的函式庫(例如包含 printf 的 C 標準庫)拼接起來,把所有「我不知道在哪」的空缺,填上真正的位址,最後產出一個完整的、可以執行的檔案。

負責這件事的工具叫連結器(linker)。它做的核心動作叫符號解析(symbol resolution):把每一個「未解決的引用」(像 printf),對應到它真正的「定義」所在的位址。

        LIB["C 標準庫

    end
    LINKER["連結器
(symbol resolution)"]
    subgraph after["連結後"]
        EXE["hello(可執行檔)

    end
    OBJ --> LINKER
    LIB --> LINKER
    LINKER -->|"把 ??? 換成 0x4521"| EXE

    style LINKER fill:#e8a33d,color:#10100e
    style EXE fill:#8a9a5b,color:#10100e

比喻:連結器就像最後的編輯。你的 .o 是缺頁碼的書稿,編輯去資料庫找到《printf 大全》的真正位置,把書稿裡所有「(此處引用…第 X 頁)」的空白頁碼全部補齊,然後把你的書稿和它引用的內容釘成一本可以出版的完整書。出版後的書(可執行檔)裡,不再有任何「待補」的空白。

親眼看它(worked example):

gcc hello.o -o hello     # 連結(gcc 會自動帶上 C 標準庫)
./hello                  # 執行!

7. 編譯錯誤 vs 連結錯誤:一刀切清

這是初學者最常混淆、也最值得單獨拉出來講的一節。「編譯錯誤」和「連結錯誤」是不同階段的不同問題,訊息長相不同,解法也完全不同。

flowchart TB
    Q["程式 build 失敗了"]
    Q --> T1{"錯誤訊息長怎樣?"}
    T1 -->|"expected ';'
undeclared identifier
type mismatch"| C1["編譯錯誤
(階段②)
= 你的語法/型別寫錯了"]
    T1 -->|"undefined reference to 'foo'"| C2["連結錯誤
(階段④)
= 語法都對,但找不到
某個函式/變數的『本體』"]
    C1 --> F1["解法:回去檢查那一行的
語法、拼字、型別、有沒有宣告"]
    C2 --> F2["解法:檢查那個函式的本體
有沒有被一起編譯/連結進來
(別去改語法!語法是對的)"]
    style C1 fill:#6fa8b8,color:#10100e
    style C2 fill:#c2603a,color:#f4ecd8
    style F2 fill:#e8a33d,color:#10100e

對照表:

編譯錯誤 連結錯誤
發生階段 ② 編譯 ④ 連結
典型訊息 expected ';'、undeclared identifier undefined reference to 'foo'
真正的意思 你寫的 C 文法/型別不對 文法都對,但某個東西找不到「本體」
比喻 句子文法錯了 句子沒錯,但你引用的那本書根本不存在
該怎麼修 改那一行的語法 確認本體有被編譯進來,別動語法

記住這個分流:看到 undefined reference,你的第一反應應該是「哪個函式的本體沒被連結進來?」——而不是去逐字檢查語法。多少新手在 undefined reference 前面盯著完全正確的語法看半小時,就是因為不知道這是連結階段的錯。

8. Makefile:不要每次都手打那串指令

當你的專案從一個檔案變成三個、五個檔案,每次手動 gcc a.c b.c c.c -o prog 會很痛苦,而且「只改了一個檔案卻要把全部重新編譯」很浪費時間。Make 這個工具就是來解決這件事的。

你在一個叫 Makefile 的檔案裡寫好「規則」,Make 會自動判斷哪些檔案改了、只重新編譯需要的部分。

Makefile 的核心觀念:相依圖

Make 的運作建立在一張「誰依賴誰」的圖上。一個最小的兩檔案專案:

# Makefile —— 注意:每條指令前面必須是「Tab」字元,不是空格!
hello: main.o util.o
    gcc main.o util.o -o hello

main.o: main.c util.h
    gcc -c main.c

util.o: util.c util.h
    gcc -c util.c

clean:
    rm -f *.o hello

讀法:每個區塊是「目標: 它依賴的檔案」,下一行(必須 Tab 縮排)是「怎麼從那些依賴產生這個目標」。畫成圖:

flowchart TB
    hello["hello(最終可執行檔)"]
    mainO["main.o"]
    utilO["util.o"]
    mainC["main.c"]
    utilC["util.c"]
    utilH["util.h"]
    hello --> mainO
    hello --> utilO
    mainO --> mainC
    mainO --> utilH
    utilO --> utilC
    utilO --> utilH
    style hello fill:#e8a33d,color:#10100e
    style utilH fill:#6fa8b8,color:#10100e

Make 怎麼決定「只重編需要的」

Make 看檔案的修改時間戳記。規則是:「如果某個目標,比它依賴的任何檔案還舊,就代表依賴變了、目標過期了,要重跑那條規則。」

flowchart TB
    START["你執行 make"]
    Q1{"util.c 比 util.o 新嗎?
(util.c 被改過?)"}
    START --> Q1
    Q1 -->|"是"| RE1["重新編譯 util.o"]
    Q1 -->|"否"| SKIP1["跳過 util.o(沒過期)"]
    RE1 --> Q2{"util.o 或 main.o
比 hello 新嗎?"}
    SKIP1 --> Q2
    Q2 -->|"是"| RE2["重新連結 hello"]
    Q2 -->|"否"| DONE["什麼都不用做"]
    style RE1 fill:#e8a33d,color:#10100e
    style RE2 fill:#e8a33d,color:#10100e
    style DONE fill:#8a9a5b,color:#10100e

注意一個漂亮的連鎖效果:如果你只改了 util.h,因為 main.o 和 util.o 都依賴它,所以兩個都會重編,然後 hello 重連結。但如果你只改 main.c,就只有 main.o 重編。Make 自動算出這個最小重建範圍——這正是它的價值。

這跟 kernel 有什麼關係? Linux kernel 的 build 系統(叫 Kbuild)本質上就是一套巨大、精巧的 Makefile 體系。kernel 有幾萬個檔案,你改一個檔案重編,它不會把整個 kernel 重編一遍——靠的就是這套相依關係。你在 Phase 3 編譯 kernel、寫第一個 module 時,寫的就是(簡化版的)Makefile。今天這個 8 行的小範例,是那座大山的第一塊石頭。

9. gdb 入門:暫停時間,看程式內部

當程式行為不如預期,你需要的不是「盯著程式碼猜」,而是一個能讓程式暫停、一行一行往下走、隨時查看變數值的工具。這就是除錯器 gdb。

常見誤區與踩雷提醒

誤區一:把「編譯」當成整條流程的全部。 人們隨口說「編譯程式」,但嚴格講,「編譯」只是階段②。整條線是「前處理 → 編譯 → 組譯 → 連結」。為什麼這個區分重要?因為當出錯時,你必須知道錯在哪一站才能對症下藥。把 undefined reference(連結階段)當成語法問題去改,就會白忙半天。

誤區二:以為 .o 檔可以直接執行。 .o 是半成品。它有機器碼,但留著「待連結」的空缺(像對 printf 的呼叫)。沒連結就想執行,系統會拒絕。把 .o 想成「還沒裝訂、缺了引用頁碼的書稿」。

誤區三:Makefile 用空格縮排。 這是 C 新手最惱人的坑之一。Makefile 規定指令行必須用 Tab 字元縮排,用空格會得到一個莫名其妙的錯誤(missing separator)。很多編輯器預設把 Tab 自動轉成空格——寫 Makefile 時要關掉這個設定,或確認你打的真的是 Tab。

誤區四:忘記 -g 就想用 gdb 看變數名。 沒有 -g,執行檔裡沒有行號和變數名資訊,gdb 只能給你冷冰冰的機器位址,沒辦法說「第 12 行、變數 x = 5」。要除錯,編譯時記得加 -g。

動手實作

環境:任何 Linux 終端機。全程不需要 root,也不會動到系統。

任務 A — 親眼走過四個階段 1. 寫一個 hello.c,印出 "Hello, kernel journey"。 2. 依序執行,每一步都打開產物看看: bash gcc -E hello.c -o hello.i # 看 .i 暴增的行數:wc -l hello.c hello.i gcc -S hello.c -o hello.s # 打開 hello.s,找到 call printf gcc -c hello.c -o hello.o # file hello.o(會說 relocatable) objdump -d hello.o # 反組譯,看那個待填的 printf 呼叫 gcc hello.o -o hello # 連結成可執行檔 ./hello # 執行 3. 寫下一句話:hello.i 為什麼比 hello.c 長那麼多?

任務 B — 兩檔案專案 + Makefile 1. 建立 util.h(宣告 int add(int, int);)、util.c(實作它)、main.c(呼叫並印出結果)。 2. 寫本課那個 Makefile,執行 make,確認產生可執行檔且輸出正確。 3. 觀察增量編譯:只改 util.c 存檔,再 make 一次——觀察它只重編了 util.o,沒重編 main.o,然後重連結。接著改 util.h,再 make——這次 main.o 和 util.o 都會重編(因為兩者都依賴它)。

任務 C — 製造一個連結錯誤,親眼認得它 在 main.c 裡呼叫一個你宣告了但沒實作的函式(例如在 util.h 宣告 int sub(int,int); 但 util.c 裡不寫它的本體),然後 build。你會看到 undefined reference to 'sub'。確認:這是連結錯誤,不是編譯錯誤(語法完全正確,只是找不到本體)。然後補上本體,再 build 成功。

任務 D — 用 gdb 走一遍 (這裡為了讓 gdb 範例簡單,跳過 Makefile,直接一行把兩個 .c 編成帶除錯資訊的執行檔。)

gcc -g main.c util.c -o prog   # -g 帶入除錯資訊;一次編譯多檔以簡化示範
gdb ./prog

在 gdb 裡依序做:break main(設中斷點)、run(執行到中斷點)、next(單步往下,至少 3 行)、print 變數名(印出某變數值)、quit。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 能對 gcc -S 與 gcc -c 的產物各說出至少一個具體差異(前者產出文字組合語言 .s,後者產出二進位目的檔 .o)。 2. ☐ 建立含 main.c + util.c + util.h 的專案,make 後產生可執行檔且輸出正確;並能說出「只改 util.c」與「改 util.h」時,重建範圍有何不同。 3. ☐ 能認出 undefined reference 是連結錯誤(而非編譯錯誤),並說明該往哪裡找問題。 4. ☐ 用 gdb 在 main 設中斷點並單步至少 3 行,印出一個區域變數值。

評分量表: - 60(及格):能編譯並執行一支程式。 - 80(熟練):能解釋四階段各自的輸入與產物,能分清編譯錯誤 vs 連結錯誤,會用 Makefile 與 gdb 的基本動作。 - 100(精通):能徒手寫多檔案 Makefile 並解釋其相依/增量重建邏輯,能解釋連結階段到底在「填補」什麼(符號解析)。
