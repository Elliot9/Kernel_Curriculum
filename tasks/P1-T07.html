P1-T07 · CPU 排程

一句話:CPU 只有有限個核心,但要跑的 task 永遠更多,於是需要一個「排程器」決定誰先跑、跑多久。它在「公平、吞吐、低延遲」之間永遠在取捨——沒有完美方案,只有適合場景的權衡。

為什麼要先學這個(導讀)

上一課 P1-T06 講了 context switch 是「切換 task」的機制。這一課回答更上層的問題:誰來決定切換到哪個 task、何時切換? 這就是 CPU 排程器(scheduler) 的工作。

設想:你的機器上同時有幾十、幾百個可執行的 task(行程/執行緒),但 CPU 核心就那幾個。排程器必須不斷決定:「下一個時間片,讓哪個 task 上 CPU?讓它跑多久?」這個決策影響一切——系統感覺起來流暢還是卡頓、批次工作能多快完成、互動程式回應快不快。

關鍵洞察是:排程沒有「最佳解」,只有「取捨」。你想讓互動程式回應快(低延遲),就得頻繁切換、讓它們插隊,但這犧牲了吞吐量(切換有成本);你想最大化吞吐,就少切換、讓 task 跑久一點,但互動程式會卡。排程器的設計,本質上是在這些互相衝突的目標間找平衡。

為什麼這對你是 scope: indirect(間接對應)?因為理解排程原理,是日後讀懂 Linux 的 EEVDF 排程器(P3-T12)的前置;也讓你理解你的 kthread / workqueue(kernel 裡的工作執行緒)何時會被排到執行——這影響你 kernel module 的行為與延遲。

開始之前(前置確認)

  • 依賴:P1-T06(context switch 是切換機制)、P1-T05(task 是排程單位)。
  • 自我檢測: 1. 你能說出「為什麼 context switch 有成本」嗎?(回顧 P1-T06:保存/載入狀態、可能 TLB flush。)排程要切換,所以切換成本是排程的考量之一。 2. 你直覺上覺得「該讓哪個程式先跑」有標準答案嗎?讀完這課你會明白為什麼沒有。

核心內容

拆成這幾節:(1) 排程的目標與指標 → (2) FIFO:先到先做 → (3) SJF:短的先做 → (4) RR:輪流跑(時間片)→ (5) 優先權與 starvation → (6) MLFQ:兼顧互動與批次,最後打通關。

1. 排程的目標與指標:互相衝突的願望

要評價一個排程演算法好不好,先要有衡量標準。幾個關鍵指標:

        RESP["回應時間(response)

→ 互動程式在意這個(別讓我等)"]
        FAIR["公平性(fairness)

        THRU["吞吐量(throughput)

關鍵:這些目標常常互相衝突。 例如要回應時間短(互動好),就得頻繁切換讓各 task 都能快速上場一下,但頻繁切換的成本會降低吞吐量。要週轉時間短,可能要讓短工作插隊,但這可能對長工作不公平。排程演算法的本質,就是在這些衝突的願望間選擇一個權衡。 接下來幾節的每個演算法,都是某種權衡的代表。

2. FIFO(先到先做):最簡單,但有大問題

FIFO(First-In-First-Out,先到先服務):誰先到就先跑,跑完才換下一個。簡單直覺,像排隊結帳。

flowchart LR
    subgraph fifo["FIFO:按到達順序,一個跑完才下一個"]
        direction LR
        A["工作A(需 100 秒)
先到,先跑"] --> B["工作B(需 1 秒)
後到,得等 A 跑完"] --> C["工作C(需 1 秒)
再等"]
    end
    PROBLEM["問題:若一個超長工作排在前面,
後面一堆短工作全被卡住
= 護航效應(convoy effect)"]
    fifo --> PROBLEM
    style A fill:#c2603a,color:#f4ecd8
    style PROBLEM fill:#c2603a,color:#f4ecd8

FIFO 的致命問題叫護航效應(convoy effect):如果一個耗時很長的工作排在前面,後面所有短工作都得苦等它跑完,即使那些短工作只要一瞬間。就像超市結帳,前面一個人推了滿滿一車(長工作),後面只買一瓶水的人(短工作)全被卡住。這讓平均週轉時間和回應時間都很糟。

3. SJF(短的先做):週轉時間最佳,但不切實際

SJF(Shortest Job First,最短工作優先):每次選「預計最短」的工作先跑。這能得到最佳的平均週轉時間(數學上可證明)。

flowchart LR
    subgraph sjf["SJF:短工作先跑"]
        direction LR
        B["工作B(1秒)"] --> C["工作C(1秒)"] --> A["工作A(100秒)
最長,最後跑"]
    end
    GOOD["短工作不再被長工作卡住
→ 平均週轉時間最佳"]
    BAD["兩個問題:
① 怎麼知道工作要跑多久?(未來難預測)
② 長工作可能一直被插隊 → starvation(餓死)"]
    sjf --> GOOD
    sjf --> BAD
    style B fill:#8a9a5b,color:#10100e
    style BAD fill:#c2603a,color:#f4ecd8

SJF 理論上很美,但有兩個現實問題:(1) 你怎麼事先知道一個工作要跑多久?未來執行時間通常無法準確預測。(2) 如果短工作源源不絕地來,長工作可能永遠排不到、被餓死(starvation)。所以 SJF 更多是理論基準,實務上難直接用。

4. RR(輪流跑):用時間片換取公平與回應

RR(Round-Robin,輪轉):給每個 task 一小段固定的 時間片(time slice / quantum),時間到就搶佔(preempt)它、換下一個,輪流進行。這是兼顧公平與回應時間的經典做法。

flowchart TB
    subgraph rr["RR:每個 task 跑一個時間片就換"]
        direction LR
        T1["A 跑一片"] --> T2["B 跑一片"] --> T3["C 跑一片"] --> T4["A 再跑一片"] --> T5["B 再..."]
    end
    GOOD["每個 task 很快都能上場一下
→ 回應時間好(互動程式不會等太久)
→ 公平(輪流)"]
    rr --> GOOD
    style T1 fill:#6fa8b8,color:#10100e
    style GOOD fill:#8a9a5b,color:#10100e

時間片大小是關鍵權衡:

flowchart TB
    Q{"時間片設多大?"}
    Q -->|"太大"| BIG["趨近 FIFO:
回應時間變差
(每個 task 占用太久)"]
    Q -->|"太小"| SMALL["切換太頻繁:
context switch 成本(P1-T06)
吃掉大量 CPU → 吞吐量降低"]
    Q -->|"適中"| JUST["平衡:回應夠快,
切換成本可接受"]
    style BIG fill:#c2603a,color:#f4ecd8
    style SMALL fill:#c2603a,color:#f4ecd8
    style JUST fill:#8a9a5b,color:#10100e

這直接呼應 P1-T06:因為 context switch 有成本,時間片不能太小(否則大部分時間都花在切換,而非做事);但太大又回到 FIFO 的回應問題。RR 的藝術就在選一個適中的時間片。搶佔(preemption) 是 RR 的核心機制——排程器能在時間片用完時「強制中斷」當前 task,這需要硬體計時器中斷的支持(時間到就觸發中斷,讓排程器奪回控制權)。

5. 優先權與 starvation:不是所有 task 都平等

實務上,不同 task 重要性不同(系統關鍵任務 vs 背景下載)。優先權(priority) 排程讓高優先權的 task 先跑。但純粹的優先權有個危險:

flowchart TB
    PRIO["純優先權排程:永遠先跑最高優先權的"]
    PRIO --> PROBLEM["問題:若高優先權 task 源源不絕,
低優先權 task 永遠輪不到
→ starvation(餓死)"]
    PROBLEM --> FIX["緩解:aging(老化)
等越久的 task,優先權逐漸提升
→ 最終總會輪到,不會永遠餓死"]
    style PROBLEM fill:#c2603a,color:#f4ecd8
    style FIX fill:#8a9a5b,color:#10100e

starvation(餓死) 是排程的經典陷阱:某些 task 永遠排不到 CPU。解法之一是 aging(老化)——讓等待越久的 task 優先權慢慢升高,保證它最終會被排到。把優先權當成絕對、不做 aging,容易導致餓死,這是常見誤區。

6. MLFQ:不知道工作長短,也能兼顧互動與批次

前面的演算法各有缺陷:FIFO 有護航、SJF 要預知未來、RR 對所有 task 一視同仁(沒區分互動與批次)。MLFQ(Multi-Level Feedback Queue,多級回饋佇列) 是一個聰明的綜合方案,它不需要預知工作長短,卻能近似「短/互動工作優先」的效果。

核心機制:設多個優先權佇列,用 task 的「行為」來動態調整它在哪一級:

    subgraph mlfq["MLFQ:多個優先權佇列,依行為升降"]
        Q_HIGH["高優先權佇列
(時間片短)
新工作從這裡開始"]
        Q_MID["中優先權佇列
(時間片中)"]
        Q_LOW["低優先權佇列
(時間片長)"]
    end
    Q_HIGH -->|"用完整個時間片還沒做完
(像是 CPU 密集的批次工作)
→ 降級"| Q_MID
    Q_MID -->|"又用完整個時間片
→ 再降級"| Q_LOW
    NOTE["反之:還沒用完時間片就主動讓出
(像是等 I/O 的互動工作)
→ 留在高優先權"]
    Q_LOW -.- NOTE
    style Q_HIGH fill:#e8a33d,color:#10100e
    style Q_LOW fill:#6fa8b8,color:#10100e
    style NOTE fill:#8a9a5b,color:#10100e

精妙之處在「用行為推斷工作類型」: - 互動工作(像等鍵盤、等網路的程式)通常跑一下下就主動讓出 CPU 去等 I/O——MLFQ 看到「它沒用完時間片就讓出」,推斷它是互動型,讓它留在高優先權,所以它下次能很快被排到、回應快。 - CPU 密集的批次工作(像大量計算)會把整個時間片用滿——MLFQ 看到「它老是用完整片」,推斷它是批次型,把它降級到低優先權(但給更長的時間片),所以它不會頻繁打斷互動工作,但輪到時能一次跑久一點。

這樣 MLFQ 不必預知任何工作要跑多久,純粹觀察行為就近似達成了「互動優先、批次讓步」——同時照顧了回應時間(互動)和吞吐量(批次)。(實務上還會配合 aging:定期把所有工作提回高優先權,避免長工作被永久餓死。)這就是為什麼 MLFQ 的思想深深影響了真實作業系統的排程器設計。

一句話總結:排程的本質是在公平、吞吐、回應時間等衝突目標間取捨;從 FIFO 到 SJF 到 RR 到 MLFQ,每個演算法都是一種權衡,而 MLFQ 用「觀察行為」巧妙地不必預知工作長短就兼顧了互動與批次——這些原理是你日後讀懂 Linux EEVDF 排程器、以及理解 kthread/workqueue 何時被排到的基礎。

常見誤區與踩雷提醒

誤區一:以為排程器追求單一目標。 排程在 fairness / throughput / latency 之間取捨,沒有同時最佳化全部的方案。評價一個排程器要看它針對什麼場景做了什麼權衡。

誤區二:忽略搶佔與時間片對互動延遲的影響。 時間片太大,互動程式要等很久才上場(回應差);太小,切換成本(回顧 P1-T06)吃掉吞吐。時間片大小是關鍵權衡。

誤區三:把優先權當成絕對。 純優先權排程會讓低優先權 task 餓死(starvation)。需要 aging 等機制保證它們最終被排到。

誤區四:以為 SJF 可以直接用。 SJF 需要預知工作執行時間(通常做不到),且會餓死長工作。它主要是理論基準;實務上用 MLFQ 等「用行為推斷」的方法近似。

動手實作

環境:紙筆或任何程式語言皆可,純計算,無系統風險。

任務 A — 手算 RR 的週轉時間(驗收點) 給定四個工作(假設同時到達,時間 0): - A 需要 8 個時間單位 - B 需要 4 個 - C 需要 4 個 - D 需要 2 個

用 RR、時間片 = 2 排程。在紙上畫出執行順序(A,B,C,D,A,B,C,A...這樣輪),算出每個工作的完成時間和平均週轉時間。(提示:每輪每個還沒做完的工作跑 2 單位,做完的就退出。)這是驗收的核心——務必手算一遍。

任務 B — 對比 FIFO 和 SJF 同樣四個工作,分別用 FIFO(按 A,B,C,D 順序)和 SJF(短的先)排,各算平均週轉時間。比較三種(含任務 A 的 RR)的結果,寫一句話:哪種週轉時間最短?哪種回應時間最好?印證「不同演算法、不同權衡」。

任務 C — 解釋 MLFQ 如何兼顧兩種工作 用一段話(不用程式)解釋:MLFQ 如何在「不知道工作要跑多久」的前提下,讓一個「等鍵盤輸入的互動程式」和一個「狂算數字的批次程式」各得其所?(提示:用「是否用完整個時間片」來推斷工作類型。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 給定一組工作(到達時間+執行長度),正確手算 RR(指定 time slice)的完成順序與平均週轉時間。 2. ☐ 能用一段話解釋 MLFQ 如何同時照顧互動型與批次型工作。

評分量表: - 60(及格):能複述各演算法。 - 80(熟練):能手算排程(RR 的完成順序與週轉時間)。 - 100(精通):能說明這些原理如何對應到 Linux 排程器(連結 P3-T12 的 EEVDF)。
