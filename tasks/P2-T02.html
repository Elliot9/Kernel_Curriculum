P2-T02 · kernel 侵入式鏈結串列 list_head

一句話:kernel 不用你 P0-T12 手刻的那種「節點存資料指標」的串列,而是把串列節點內嵌在資料 struct 裡——這叫「侵入式」。這個翻轉的設計,讓 kernel 省去額外配置、達成 O(1) 刪除,而它是 kernel 裡最常見的資料結構,bio、request、裝置清單全用它。

為什麼要先學這個(導讀)

如果你只能從 Phase 2 記住一個資料結構,就是這個 struct list_head。它在 kernel 原始碼裡無所不在——你日後讀的幾乎每個子系統都有它。讀懂它,kernel code 對你的可讀性會大幅提升;讀不懂它,你會在每個串列走訪前卡住。

回顧 P0-T12,你手刻過傳統鏈結串列:一個 struct node 裡有 data 和 next 指標,節點本身是為了「串接」而存在的容器,資料放在裡面(或節點存一個指向資料的指標)。

kernel 的做法反過來:它不為串接另外造節點,而是把一個小小的「串接零件」(struct list_head)直接嵌進你本來就有的資料 struct 裡。資料 struct 自己變成了串列的節點。這叫侵入式串列(intrusive list)——串列「侵入」到資料結構內部。

這個翻轉帶來幾個對 kernel 極重要的好處(後面詳述):不需要為串接額外配置記憶體(回顧 P0-T06,kernel 裡每次 malloc 都是成本與風險)、O(1) 刪除(不需先查找)、一個 struct 能同時掛在多個串列上。

為什麼這對你是 scope: direct?因為你產品和 block layer 裡的核心結構——bio(區塊 I/O 請求)、request、md(軟體 RAID)的裝置清單——全都用 list_head 串接。讀這些程式碼,list_for_each_entry、list_add、list_del 會反覆出現。這一課讓你徹底看懂它們。

開始之前(前置確認)

  • 依賴:P2-T01(你知道鏈結串列適合 O(1) 的已知位置插入/刪除)、P0-T08(巨集——list_head 的 API 大量用巨集)、P0-T12(你手刻過傳統串列,這課對比它)。
  • 自我檢測: 1. 你還記得 P0-T12 傳統串列「刪除節點要先橋接再 free」嗎?這課看 kernel 怎麼用環狀雙向設計簡化它。 2. 你還記得 P0-T04 struct 成員在記憶體裡的佈局(成員有固定 offset)嗎?下一課 P2-T03 的 container_of 會用到,這課先埋伏筆。

核心內容

拆成這幾節:(1) 傳統 vs 侵入式:翻轉的設計 → (2) struct list_head 的雙向環狀結構 → (3) 初始化 → (4) list_add / list_del → (5) 為什麼刪除是 O(1) → (6) list_for_each_entry 走訪 → (7) 走訪中刪除的陷阱與 _safe,最後打通關。

1. 傳統 vs 侵入式:誰包含誰?

這是整課的核心翻轉,先看清楚。

傳統串列(你在 P0-T12 做的):節點是主角,資料是配角。

struct node {
    int data;            // 資料在節點裡
    struct node *next;   // 或:節點存一個指向外部資料的指標
};

侵入式串列(kernel 的做法):資料 struct 是主角,串接零件嵌在裡面。

struct my_data {
    int value;                // 你本來就有的資料欄位
    char name[32];            // 你本來就有的資料欄位
    struct list_head list;    // ★ 嵌入一個串接零件 ★
};

關鍵差異:在侵入式設計裡,那個 struct list_head list 成員,才是真正被串起來的東西。串列把各個 my_data 裡的 list 成員串成一圈,而不是串 my_data 本身。這聽起來有點繞——「串的是成員,不是整個 struct」——但這正是它威力與下一課 container_of 存在的原因(我們會需要「從 list 成員反推回整個 my_data」)。

比喻:傳統串列像「為了串珠子,另外買了串珠線(節點),把珠子(資料)穿上去」。侵入式串列像「每顆珠子出廠時就自帶一個小掛環(list_head 成員),直接用掛環把珠子彼此扣起來」——不需要額外的線,掛環是珠子的一部分。

2. struct list_head:極簡的雙向環狀設計

struct list_head 本身極其簡單,就兩個指標:

struct list_head {
    struct list_head *next;   // 指向下一個 list_head
    struct list_head *prev;   // 指向上一個 list_head
};

注意:next/prev 指向的是其他的 list_head(其他 struct 內嵌的那個成員),不是指向整個資料 struct。這些 list_head 串成一個雙向、環狀的圈:

(一個獨立的 list_head,
當作串列的錨點)"]
    N1["data1.list"]
    N2["data2.list"]
    N3["data3.list"]
    HEAD -->|next| N1 -->|next| N2 -->|next| N3 -->|next| HEAD
    HEAD -.prev.- N3
    N3 -.prev.- N2
    N2 -.prev.- N1
    N1 -.prev.- HEAD
    style HEAD fill:#e8a33d,color:#10100e
    style N1 fill:#8a9a5b,color:#10100e

兩個設計選擇,各有理由: - 雙向(next + prev):能往兩個方向走,而且讓「刪除一個節點」變得超簡單(第 5 節)——因為從一個節點就能直接找到它的前後鄰居。 - 環狀(尾巴接回頭):最後一個的 next 指回 head,head 的 prev 指向最後一個。沒有「NULL 結尾」的特例,讓很多操作的程式碼更統一(不必每次都判斷「是不是到尾了」)。head 本身是一個不含資料的 list_head,純粹當「圈的起點/錨點」。

對比 P0-T12 你的單向、NULL 結尾串列:kernel 的雙向環狀設計,程式碼更統一(少很多特例判斷)、刪除更快(下面看)。

3. 初始化:別忘了

用之前必須初始化——讓那個 list_head 的 next 和 prev 都先指向自己(代表「空圈,只有我」)。kernel 提供兩種方式:

「空串列」的狀態是:head 的 next 和 prev 都指向 head 自己(一個只有錨點、沒有資料節點的圈)。忘記初始化(回顧 P0-T02 野指標的危險)會讓 next/prev 是垃圾值,第一次操作就崩潰——這是新手常見 bug。

4. list_add 與 list_del:加入與移除

兩個核心操作。list_add(new, head) 把 new 這個 list_head 加到 head 之後(成為第一個元素);list_del(entry) 把 entry 從它所在的串列移除。

list_add 就是調整四個指標,把新節點「縫」進環裡。(還有 list_add_tail(new, head) 加到尾端——因為環狀,加到尾端就是插在 head 之前,一樣簡單。)

刪除更精彩,看下一節為什麼是 O(1)。

5. 為什麼刪除是 O(1):雙向設計的回報

回顧 P0-T12,你的單向串列要刪除一個節點 B,得先找到它的前一個節點 A(才能把 A 的 next 接到 B 的 next),而「找前一個」在單向串列裡要從頭走(O(n))。

kernel 的雙向設計讓這個問題消失:每個節點都知道自己的 prev 和 next,所以給定要刪的節點,直接就能接合它的前後鄰居,不需要查找:

flowchart TB
    S1["要刪除節點 B(已經有 B 的指標)
原本:A ↔ B ↔ C"]
    S2["因為 B 知道自己的 prev(A)和 next(C):
B->prev->next = B->next
(讓 A 的 next 直接指向 C)
B->next->prev = B->prev
(讓 C 的 prev 直接指向 A)"]
    S3["結果:A ↔ C(B 被跳過)
全程沒有任何『查找』 → O(1)"]
    S1 --> S2 --> S3
    CONTRAST["對比 P0-T12 單向串列:
要刪 B 得先 O(n) 找到 A;
kernel 雙向設計直接用 B->prev 拿到 A
→ 刪除降到 O(1)"]
    S3 --> CONTRAST
    style S2 fill:#e8a33d,color:#10100e
    style S3 fill:#8a9a5b,color:#10100e

這就是「為什麼刪除是 O(1)」的答案:雙向串列裡,每個節點都握有前後鄰居的指標,所以刪除任何一個節點都只是「讓它的前後鄰居互相接上」——四個指標調整,與串列長度無關。再加上侵入式設計(你手上拿到的資料 struct 就內嵌著它的 list_head,不需要查找它在串列哪個位置),刪除真正做到 O(1)。這對 kernel 極重要:kernel 常需要從各種串列中快速移除元素(例如完成的 I/O request),O(1) 刪除是效能關鍵。

6. list_for_each_entry:走訪並取回你的資料

走訪是最常見的操作,但這裡有個侵入式設計帶來的「轉折」:串列串的是 list_head 成員,但你真正想操作的是外層的資料 struct。怎麼從「走到的 list_head」拿回「外層的 my_data」?

kernel 提供 list_for_each_entry 巨集,幫你一步到位:

struct my_data *entry;
list_for_each_entry(entry, &head, list) {
    // 每一圈,entry 自動是「下一個 my_data」(不是 list_head!)
    printf("%d %s\n", entry->value, entry->name);
}

關鍵理解:list_for_each_entry 走訪時,每一圈都把「當前的 list_head 成員」反推回「外層的資料 struct 指標」,直接給你 entry。這個「反推」靠的就是下一課的主角 container_of——這也是為什麼 P2-T03 緊接在後:你已經看到侵入式串列需要一個「從成員回到外層」的機制,container_of 就是它。(那個 list 參數,就是告訴巨集「list_head 成員在你 struct 裡叫什麼名字」,好讓它算 offset。)

7. 走訪中刪除的陷阱:必須用 _safe 版本

最後一個極重要的實務陷阱,呼應 P0-T06 的 use-after-free。

如果你在走訪串列的同時刪除節點,普通的 list_for_each_entry 會出事。為什麼?因為它靠「當前節點的 next」決定下一圈走到哪——但如果你把當前節點 list_del 並 free 掉了,它的 next 就失效了(指向已釋放記憶體),下一圈就讀到垃圾:

        W3["迴圈要找下一個:讀 B->next
但 B 已被 free → use-after-free!
(回顧 P0-T06)"]

規則:走訪中要刪除節點,一律用 list_for_each_entry_safe。 它多用一個暫存變數,在處理當前節點之前就先把「下一個」記下來,所以即使當前節點被刪除釋放,迴圈仍能正確走到下一個。這個 _safe 慣用法在 kernel 裡非常常見——看到它,你就知道「這段迴圈裡會刪除節點」。

比喻:像在拆一串燈泡。普通走訪是「走到這顆,看它連到的下一顆」——但如果你把這顆拆了丟掉,就不知道下一顆在哪了。_safe 版是「走到這顆時,先記住下一顆在哪,再放心拆這顆」。

一句話總結:kernel 的 list_head 是侵入式、雙向、環狀的串列——把串接零件嵌進資料 struct,換來免額外配置、O(1) 刪除、一物可掛多串列;走訪用 list_for_each_entry(靠 container_of 從成員反推外層),邊走邊刪必用 _safe 版。這是 kernel 最常見的結構,讀懂它,bio/request/裝置清單的程式碼就通了。

常見誤區與踩雷提醒

誤區一:把侵入式串列當成傳統「存指標」的串列。 kernel 的 list_head 是內嵌在資料 struct 裡的成員,串的是成員不是整個 struct。理解這點,才看得懂走訪為何需要 container_of 反推。

誤區二:走訪中刪除節點卻用普通 list_for_each_entry。 刪除+free 當前節點後,它的 next 失效,下一圈 use-after-free(回顧 P0-T06)。邊走邊刪一律用 list_for_each_entry_safe。

誤區三:忘記初始化。 用前必須 LIST_HEAD(靜態)或 INIT_LIST_HEAD(動態)初始化,否則 next/prev 是垃圾值,第一次操作就崩潰(回顧 P0-T02 野指標)。

誤區四:以為刪除要先查找(像單向串列)。 雙向設計下,節點知道自己的 prev/next,刪除直接接合前後鄰居,O(1),不需查找。這正是雙向設計的回報。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 在使用者態用 kernel 風格 list_head 取得 kernel list.h 的精簡版(網路上有許多 user space 移植版,或參考 https://elixir.bootlin.com/linux/v6.12/source/include/linux/list.h 自己抽出 list_head、INIT_LIST_HEAD、list_add、list_del、list_for_each_entry、container_of)。定義一個自訂 struct 內嵌 list_head:

struct item {
    int value;
    struct list_head list;   // 內嵌的串接零件
};

建立 5 個 item,用 list_add(或 list_add_tail)串起來,用 list_for_each_entry 走訪印出每個的 value。驗收:正確印出 5 個值。

任務 B — 走訪中安全刪除(用 _safe) 在任務 A 的基礎上,用 list_for_each_entry_safe 走訪,刪除其中中間的一個節點(例如 value 為某值的),並 free 它(若是動態配置的)。確認:走訪不崩潰、刪除後再走一遍串列結果正確、無洩漏(可用 valgrind,回顧 P0-T06)。驗收:安全刪除中間節點,不崩潰不洩漏。 然後故意改用普通的 list_for_each_entry 做同樣的刪除,觀察可能的崩潰或錯誤——體會為何要 _safe。

任務 C — 解釋 O(1) 刪除(驗收點) 用一句話解釋:為什麼 kernel list_head 的刪除是 O(1),而你 P0-T12 的單向串列刪除(若要刪指定節點)可能需要 O(n)?(提示:雙向 vs 單向,節點知不知道自己的 prev。)

任務 D(進階)— 逐行註解 list_add 從 Bootlin 找到 list_add 的實作(它呼叫內部的 __list_add),逐行註解那四個指標調整在做什麼。對照第 4 節的圖。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 kernel 風格 list_head 把 5 個自訂 struct 串起並用 list_for_each_entry 正確走訪印出。 2. ☐ 在走訪中安全刪除中間 1 個節點(用 _safe 版)且不崩潰、不洩漏。 3. ☐ 用一句話解釋為何刪除是 O(1)。

評分量表: - 60(及格):能使用 list API。 - 80(熟練):能讀懂巨集實作(list_add、走訪)。 - 100(精通):能解釋為何侵入式設計對 kernel 記憶體管理有利(免額外配置、O(1) 刪除、一物多串列)。

延伸與銜接

  • 對應工作場景:直接對應——bio、request、md 裝置清單等大量 kernel 結構都用 list_head 串接;讀你產品 / block layer 程式碼必備。_safe 走訪、list_add/list_del 你會反覆見到。
  • 這課餵給未來的:list_head → 整個 kernel(尤其 P5 的 bio/request 串接);走訪需要的「從成員反推外層」→ 緊接的 P2-T03 container_of;侵入式設計理念 → P2-T04 的 hlist(雜湊用的侵入式串列變體)。
  • 下一步 → P2-T03 container_of 慣用法:這一課你看到了一個懸念——list_for_each_entry 走訪時,如何從「串列裡的 list_head 成員」反推回「外層的資料 struct」?這個「從成員指標回到外層 struct 指標」的魔法,就是 container_of 巨集。它是 kernel 最核心的慣用法之一,不只用在串列,幾乎每個 callback 都靠它從通用結構取回自己的私有資料(例如從 bio 取回你 driver 的私有結構)。下一課徹底拆解它。
