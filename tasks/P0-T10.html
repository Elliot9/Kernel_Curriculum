P0-T10 · 未定義行為(UB)與編譯器最佳化

一句話:「未定義行為(UB)」不是「結果隨機」,而是「你向編譯器做了一個它信以為真的承諾——一旦你違背,它基於那個承諾做的最佳化,會把你的程式碼變成你完全認不出的樣子,包括刪掉你以為一定會執行的檢查」。

為什麼要先學這個(導讀)

這是 C 最反直覺、也最危險的概念,而它在 kernel 裡是真實的當機與安全漏洞來源。

在 JS/PHP 裡,幾乎每個操作都有「確定會發生的事」。除以零?得到 Infinity。陣列越界?得到 undefined。語言替每種情況都定義了行為,你不會踩到「沒有定義」的地帶。

C 不是這樣。C 為了極致的效能,故意留下一堆「未定義行為(undefined behavior, UB)」的地帶——這些操作,C 標準明白宣告「我不規定會發生什麼」。常見的 UB 包括:對 NULL 解參考、陣列越界存取、帶號整數溢位(回顧 P0-T09)、use-after-free(回顧 P0-T06)、讀取未初始化的變數……

新手最大的誤解是:「UB 就是結果不確定嘛,大不了算錯一個值。」錯得離譜。 UB 真正可怕的地方在於它和編譯器最佳化的交互作用:編譯器會假設「UB 永遠不會發生」,並基於這個假設去改寫、刪除你的程式碼。結果可能是:你寫的一個明明白白的 NULL 檢查,被編譯器整段刪掉;你的迴圈邊界檢查消失;程式在 -O0(不優化)時正常,一開 -O2(優化)就詭異崩潰。

為什麼這對你是 scope: direct?因為 kernel 一定是開最佳化編譯的(-O2 起跳)。你在使用者態用 -O0 測試「看起來沒事」的 UB,進到 kernel 開了優化就會爆。而且 P0-T09 講的帶號溢位、你在儲存領域處理的各種邊界,都是 UB 的高發區。看懂 UB,你才知道為什麼 kernel 程式碼對這些事如此戰戰兢兢。

開始之前(前置確認)

  • 依賴:P0-T09(帶號溢位是 UB 的一個例子,這課把它一般化)。
  • 自我檢測: 1. 你還記得 P0-T06 的 use-after-free、P0-T02 的 NULL 解參考嗎?這些都是 UB,這課解釋它們「為何不只是崩潰那麼簡單」。 2. 你能用 gcc -O0 和 gcc -O2 編譯同一支程式嗎?這課靠對比這兩者來展示 UB 的威力。

核心內容

拆成這幾節:(1) 三種「不確定」要分清 → (2) UB 的真正定義:你給編譯器的承諾 → (3) 招牌案例:編譯器刪掉你的 NULL 檢查 → (4) 為什麼 -O0 正常、-O2 爆炸 → (5) strict aliasing 這個隱形 UB → (6) UBSan:抓 UB 的工具,最後打通關。

1. 三種「不確定」:implementation-defined / unspecified / undefined

C 標準其實把「不是百分百固定」的行為分成三個嚴重程度,先分清楚,別混為一談:

  • implementation-defined:編譯器決定,但保證有個確定行為且寫在文件裡。例如 sizeof(int)、char 的帶號性。你查文件就知道結果。相對安全。
  • unspecified:標準允許幾種做法,編譯器選一種,但不保證告訴你選哪種,也可能每次不同。例如一個運算式裡多個函式呼叫的求值順序。
  • undefined behavior(UB):標準完全不規定。這是最危險的一級,本課的主角。「什麼都可能發生」是字面意思——包括程式看似正常、算出怪值、崩潰、或編譯器把你的程式碼改得面目全非。

這課聚焦最危險的 UB。 記住:UB 不是「編譯器選一個結果」(那是 unspecified),而是「編譯器假設它不會發生,並據此重寫你的程式」。

2. UB 的真正定義:一個你對編譯器許下的承諾

理解 UB 的關鍵心法,是把它想成契約:

當你寫下一段「只要不觸發 UB 就正確」的程式碼,你等於向編譯器承諾:「我保證這裡永遠不會發生 UB。」編譯器完全信任這個承諾,並在最佳化時理直氣壯地利用它。

flowchart TB
    YOU["你寫了會解參考 p 的程式碼:*p"]
    PROMISE["你對編譯器的『隱含承諾』:
『p 永遠不是 NULL』
(因為對 NULL 解參考是 UB,
而你保證不觸發 UB)"]
    OPT["編譯器最佳化時推論:
『既然他保證 p 不是 NULL,
那後面任何 if(p==NULL) 的檢查
都是多餘的 → 刪掉』"]
    YOU --> PROMISE --> OPT
    style PROMISE fill:#e8a33d,color:#10100e
    style OPT fill:#c2603a,color:#f4ecd8

這就是 UB 的全部祕密:你「使用」了某個只有在「無 UB」前提下才合法的東西,就等於向編譯器擔保那個前提成立。編譯器拿這個擔保去做推論和優化。如果你的擔保是假的(實際上 p 真的可能是 NULL),編譯器基於假前提做的優化,就會做出災難性的事——下一節給你看最經典的一幕。

3. 招牌案例:編譯器刪掉你的 NULL 檢查

這是 UB 最惡名昭彰的演出,真實發生過(包括在 Linux kernel 引發過安全漏洞)。看這段:

void process(int *p) {
    int value = *p;          // (1) 解參考 p
    if (p == NULL) {         // (2) 然後才檢查 p 是不是 NULL
        return;              //     想在 p 為 NULL 時提早返回
    }
    use(value);
}

你的意圖:如果 p 是 NULL 就提早返回,保護後面的程式碼。但看編譯器怎麼想:

flowchart TB
    S1["編譯器看到第(1)行 *p
(解參考 p)"]
    S2["推論:既然這裡解參考了 p,
而對 NULL 解參考是 UB,
程式設計師保證不觸發 UB
→ 所以執行到這裡時 p 一定不是 NULL"]
    S3["看到第(2)行 if (p == NULL)
推論:p 已經保證不是 NULL,
這個條件永遠為假"]
    S4["最佳化:永遠為假的 if
是 dead code → 整段刪除!"]
    S5["結果:你的 NULL 檢查消失了
若 p 真的是 NULL,
第(1)行就崩潰,
而『保護用的 return』根本不存在"]
    S1 --> S2 --> S3 --> S4 --> S5
    style S2 fill:#e8a33d,color:#10100e
    style S4 fill:#c2603a,color:#f4ecd8
    style S5 fill:#c2603a,color:#f4ecd8

讀懂這個因果鏈,你就懂了 UB 的恐怖:不是「*p 算出怪值」這麼簡單,而是你的安全檢查被合法地刪除了。編譯器沒有 bug——它完全按照「程式設計師保證不觸發 UB」這個規則在推論。錯在你「先解參考、後檢查」,這個順序本身就向編譯器擔保了「p 不可能是 NULL」。

正解:先檢查,後使用。

void process(int *p) {
    if (p == NULL) return;   // 先檢查
    int value = *p;          // 確定非 NULL 才解參考
    use(value);
}

這樣編譯器在 *p 之前看到的是「已經排除 NULL」,推論就正確了。這正是為什麼 kernel 程式碼總是「檢查在前、使用在後」——不只是風格,是為了不向編譯器許下假承諾。

把兩種順序並排,看編譯器在每種情況下「決定保留什麼」,差異一目了然:

同一個 NULL 檢查,只因相對於 *p 的位置不同,一個被編譯器刪掉、一個被保留。順序就是一切。

4. 為什麼 -O0 正常、-O2 一開就爆

UB 的災難常常以這種形式出現:「我的程式在開發時好好的,一上正式環境就崩潰。」根源往往是優化等級不同。

flowchart TB
    CODE["一段含 UB 的程式碼"]
    CODE --> O0["用 -O0 編譯(不優化)
編譯器幾乎照你寫的直譯
→ 沒做基於 UB 的推論
→ 看起來『正常』(運氣)"]
    CODE --> O2["用 -O2 編譯(優化)
編譯器積極推論、刪程式碼
→ 基於 UB 的優化生效
→ NULL 檢查被刪、行為崩壞"]
    O0 -.“同一段碼,只因優化等級不同

    style O0 fill:#8a9a5b,color:#10100e

關鍵教訓:UB 在 -O0 下「看起來沒事」完全不代表它沒事——只是優化器還沒來得及利用它。一旦提高優化等級(或換個編譯器版本),潛伏的 UB 就會爆發。

這對你是直接的警告:kernel 永遠是開優化編譯的(-O2 或更高)。你不能用「我在使用者態 -O0 測過沒問題」來保證 kernel 程式碼安全。UB 必須從根本上避免,而不是「測起來沒事就好」。

5. strict aliasing:一個你看不見的 UB

這是個比較隱晦、但在系統程式設計常踩的 UB,值得單獨拉出來。

C 有一條「嚴格別名規則(strict aliasing rule)」:編譯器假設,兩個不同型別的指標,不會指向同一塊記憶體(char* 是例外,它可以別名任何東西)。基於這個假設,編譯器會做優化。如果你違反它(用一個 float* 和一個 int* 指向同一塊記憶體並交錯讀寫),就是 UB。

float f = 1.0f;
int *p = (int*)&f;    // 用 int* 指向一個 float —— 違反 strict aliasing
*p = 42;              // 透過 int* 改寫 float 的記憶體 → UB
// 編譯器可能假設 f 和 *p 無關,優化後行為不可預測


flowchart TB
    MEM["一塊記憶體(原本是 float f)"]
    FP["float* 指向它"]
    IP["int* 也指向它(違規)"]
    FP --> MEM
    IP --> MEM
    OPT["編譯器假設:
『float* 和 int* 不會指向同一塊』

正解:要「重新解讀一塊記憶體的位元」,別用「不同型別指標互指」這種違規手段。合法的做法是用 memcpy(它以 char 層級複製,不違反規則),或用 union(回顧 P0-T04 的 union——它是 C 允許的「同記憶體多解讀」方式)。

跟你的工作的關聯:解析硬體結構、磁碟格式時,常會想「把這塊 bytes 當成另一個型別來看」。要做這件事,用 memcpy 或 union,不要用型別不符的指標硬轉,否則就踩進 strict aliasing 的 UB。kernel 程式碼對此有明確規範(且常用 -fno-strict-aliasing 編譯來放寬,但你不該依賴這點)。

6. UBSan:讓 UB 在執行時現形

你不必只靠肉眼和恐懼來防 UB。GCC/Clang 內建 UndefinedBehaviorSanitizer(UBSan),能在程式執行時偵測許多種 UB(帶號溢位、越界、NULL 解參考等),並印出「在哪一行、什麼 UB」。

gcc -fsanitize=undefined -g prog.c -o prog
./prog    # 跑到 UB 時印出明確的診斷

這是繼 P0-T06 的 valgrind 之後,你工具箱裡的第二件利器。它和 kernel 的 UBSAN(kernel 也有同名機制)精神一致——讓潛伏的 UB 在測試時就現形,而不是在正式環境隨機爆炸。

打通關:把 UB 收攏成一個心智模型

UB 的一切恐怖,都源自一個機制:「使用即承諾」+「編譯器信任並利用承諾」。

一句話總結:UB 不是「結果隨機」,而是「你對編譯器許下的、它信以為真的承諾」;違背承諾時,編譯器會合法地把你的程式碼優化成災難。在永遠開優化的 kernel 裡,避免 UB 不是潔癖,是生存技能——而『先檢查後使用』與 UBSan 是你最重要的兩道防線。

常見誤區與踩雷提醒

誤區一(最核心):以為「UB = 結果不確定,頂多算錯一個值」。 UB 真正的危險是編譯器會假設它不發生、據此刪除或重寫你的程式碼(包括安全檢查)。它的影響範圍遠超「那一個運算」。

誤區二:先解參考指標、後檢查 NULL。 int v = *p; if (p == NULL)... 會讓編譯器推論「p 必非 NULL」進而刪掉檢查。永遠先檢查、後使用。

誤區三:用 -O0 測試 UB「沒問題」就放心。 -O0 只是還沒利用 UB。kernel 開 -O2,潛伏的 UB 會爆。UB 要根除,不能靠「測起來沒事」。

誤區四:用型別不符的指標互指來「重新解讀記憶體」。 違反 strict aliasing,是 UB。改用 memcpy 或 union。

誤區五:依賴帶號整數溢位的「結果」。 帶號溢位是 UB(回顧 P0-T09),不是繞回。需要繞回語意時用無號型別(但小心 P0-T09 的無號陷阱)。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 親眼看「-O0 vs -O2」對 UB 的不同反應 寫第 3 節那個「先解參考、後檢查 NULL」的 process 函式,在 main 裡故意傳 NULL 給它。分別編譯執行:

gcc -O0 prog.c -o prog_O0 && ./prog_O0      # 觀察行為
gcc -O2 prog.c -o prog_O2 && ./prog_O2      # 觀察行為(可能不同)

觀察兩者行為差異(視編譯器版本,-O2 可能直接崩潰於解參考,因為保護用的檢查被優化掉)。然後把程式改成「先檢查後使用」,確認兩個優化等級都安全。寫一句話總結你看到什麼。

任務 B — 用 UBSan 抓帶號溢位

#include <stdio.h>
#include <limits.h>
int main(void) {
    int x = INT_MAX;
    int y = x + 1;     // 帶號溢位 → UB
    printf("%d\n", y);
    return 0;
}

gcc -fsanitize=undefined -g prog.c -o prog
./prog

觀察 UBSan 印出類似「signed integer overflow」的明確診斷,指出是哪一行。

任務 C — strict aliasing 的正確做法 你想把一個 float 的位元當成 uint32_t 來看(例如檢查它的位元表示)。錯的方式是 *(uint32_t*)&f(違反 strict aliasing)。寫出對的方式:用 memcpy:

#include <string.h>
#include <stdint.h>
#include <stdio.h>
int main(void) {
    float f = 1.0f;
    uint32_t bits;
    memcpy(&bits, &f, sizeof(bits));   // 合法:以 byte 層級複製
    printf("float 1.0 的位元 = 0x%08X\n", bits);   // 0x3F800000
    return 0;
}

確認它印出 0x3F800000(1.0f 的 IEEE-754 表示)。寫一句話:為什麼 memcpy 是合法的,而指標硬轉不是?

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 能用「先解參考後檢查 NULL」的範例,解釋編譯器為何可能刪除 NULL 檢查(連結到「使用即承諾」)。 2. ☐ 用 UBSan 抓出一個帶號溢位,並讀懂它指出的行號與錯誤類型。 3. ☐ 用 memcpy 正確地重新解讀一塊記憶體的位元,並能說明為何指標硬轉違反 strict aliasing。

評分量表: - 60(及格):知道 UB 的存在與幾個常見例子。 - 80(熟練):理解「UB = 對編譯器的承諾」,能避開常見 UB,會用 UBSan,堅持「先檢查後使用」。 - 100(精通):能解釋 UB 與優化的交互作用如何刪除安全檢查、為何 -O0/-O2 行為不同,並把這些連結到 kernel 永遠開優化的現實。

延伸與銜接

  • 對應工作場景:直接對應。kernel 一律開最佳化編譯,UB 會直接導致當機或安全漏洞;歷史上 kernel 真的發生過「NULL 檢查被優化掉」的漏洞。你寫 kernel 程式碼必須從根本避免 UB。
  • 這課餵給未來的:「先檢查後使用」的紀律 → 貫穿所有 kernel 程式設計;UBSan → kernel 的 UBSAN;strict aliasing → 解析硬體/磁碟結構時的正確手法。
  • 下一步 → P0-T11 位元操作:離開 UB 這個沉重主題,下一課進入明亮實用的位元運算(& | ^ ~ << >>)。它不只是基礎技巧——XOR 運算正是 RAID-5 同位元(parity)計算的數學核心,而「逐位元獨立」的特性,正是你產品把同位元計算丟給 GPU 平行處理的種子。這是你那條「XOR → parity → GPU 平行」主線的起點。
