P1-T10 · 原子操作、memory ordering 與 memory barrier

一句話:你寫的程式碼順序,不是它實際執行的順序——編譯器和 CPU 都會為了效能「重排」你的記憶體存取。在多執行緒下,這意味著別人可能看到「不符合你程式碼順序」的詭異結果。這一課不求精通,只求讓你建立正確的直覺與恰當的敬畏。

為什麼要先學這個(導讀)

這是 Phase 1 最硬的主題,所以先說清楚目標:這一課只求「建立正確直覺與恐懼感」,不求精通。 真正的深入在 P3-T11(Linux 核心記憶體模型 LKMM)。現在你只要在腦中種下一個正確的、會讓你保持警惕的認知種子。

那個種子是:「程式碼順序 = 執行順序」這個你深信不疑的假設,是錯的。

回顧 P1-T09:你學會用鎖保護共享狀態。鎖能用,是因為它在背後幫你處理了一件你還沒意識到的事——記憶體順序。這一課揭開那層幕布。真相是:為了效能,編譯器會重排你的指令(編譯期重排),CPU也會重排記憶體存取的實際發生順序(執行期重排)。在單執行緒裡,這些重排被保證「不改變你看到的結果」,所以你從沒察覺。但在多執行緒裡,一個執行緒能觀察到另一個執行緒的記憶體操作「以重排後的順序」發生——導致違反直覺的結果。

要駕馭這個,需要兩個工具:原子操作(atomic)(讓 ++ 這類操作不可分割,且不用鎖)和 memory barrier(記憶體屏障)(強制某些順序不被重排)。

為什麼這對你是 scope: direct?因為這是你那條「記憶體順序/可見性」主線的關鍵一站(P1-T03 → 本課 → P3-T11 → P6-T03),而它直接關係你的 DMA 工作:當你準備好一個 DMA 描述子(告訴裝置要做什麼),然後「按門鈴」(寫一個暫存器通知裝置開工),你必須保證描述子的內容在門鈴之前就對裝置可見。如果 CPU 重排了這兩個寫入(門鈴先被裝置看到、描述子還沒),裝置會讀到垃圾描述子——對儲存產品是資料災難。這需要 memory barrier。kernel 的 lock-free 結構、RCU、裝置暫存器存取,全靠正確的 barrier。

開始之前(前置確認)

  • 依賴:P1-T09(你會用鎖)、P1-T03(你已知「coherence ≠ memory ordering」這個伏筆——本課就是 ordering)、P1-T08(race、讀-改-寫)。
  • 自我檢測: 1. 你還記得 P1-T03 第 5 節說「cache coherence 保證單一變數一致,但不保證多變數的可見順序」嗎?本課就是在講那個「順序」。 如果忘了,回去看一眼。 2. 你能接受「我寫 a=1; b=2;,但 CPU 可能讓別的核心先看到 b=2 才看到 a=1」這種事嗎?讀完你會懂為什麼。
  • 心態提醒:這課燒腦是正常的。目標是「直覺 + 敬畏」,不是「全懂」。看不懂某個細節沒關係,記住「重排會發生、需要 barrier」這個核心就夠了。

核心內容

拆成這幾節:(1) 原子操作:不可分割的 ++ → (2) 編譯期重排 → (3) 執行期重排 → (4) store buffer:經典的違反直覺範例 → (5) memory barrier:強制順序 → (6) acquire/release 入門 → (7) 為什麼 volatile 不夠,最後打通關。

1. 原子操作:不用鎖,讓 ++ 不可分割

回顧 P1-T08:count++ 是「讀-改-寫」三步,並行下會交錯出錯。P1-T09 用鎖解決(把三步圍在臨界區裡序列化)。但鎖有成本(取得/釋放、可能阻塞)。對「就是想安全地加個一」這種簡單操作,有更輕量的工具:原子操作(atomic operation)。

原子操作由硬體保證不可分割——CPU 提供特殊指令,讓「讀-改-寫」一氣呵成,中間絕不被打斷,也不需要鎖:

        N1["讀"] --> N2["改"] --> N3["寫"]
        NX["三步可被打斷 → race"]
    end
    subgraph atomic["原子 atomic_fetch_add(&count, 1)"]
        A1["硬體保證:讀-改-寫
一條不可分割的操作
中間不被打斷"]
        AX["→ 不會 race,且不用鎖"]
    end

    style A1 fill:#8a9a5b,color:#10100e
    style AX fill:#8a9a5b,color:#10100e

C11 提供 <stdatomic.h>:用 atomic_int 宣告原子變數,用 atomic_fetch_add(&count, 1) 做原子加。這能修好 P1-T08 的 race,而且比鎖輕量(對單一變數的簡單操作)。

但這只是故事的一半。 原子操作保證「單一操作」不可分割,但當你有多個變數、多個操作,它們之間的順序如何被別的執行緒看見?這就進入本課真正燒腦的核心——重排。

2. 編譯期重排:編譯器會調換你的指令

第一個顛覆直覺的事實:編譯器為了優化,會調換你程式碼裡指令的順序(只要它判斷「在單執行緒下不改變結果」)。

flowchart TB
    SRC["你寫的程式碼順序:
a = 1;
b = 2;"]
    COMPILER["編譯器優化:
判斷 a、b 互不相干,
調換順序不影響單執行緒結果
→ 可能產生『先 b=2 再 a=1』的機器碼"]
    SRC --> COMPILER
    SINGLE["單執行緒:完全無感
(反正最後 a、b 都對)"]
    MULTI["多執行緒:另一個執行緒
可能先看到 b=2,a 還是舊值!
→ 若它依賴『a 先設好』就會出錯"]
    COMPILER --> SINGLE
    COMPILER --> MULTI
    style COMPILER fill:#e8a33d,color:#10100e
    style MULTI fill:#c2603a,color:#f4ecd8

編譯器這樣做完全合法——它的承諾只是「單執行緒的可觀察結果不變」。它不知道、也不保證你的多執行緒意圖。所以在單執行緒下你永遠看不出重排;但多執行緒下,另一個執行緒可能觀察到「b 已更新、a 還沒」這種違反你程式碼順序的中間狀態。

重點:即使是單核心,編譯期重排也存在(它發生在編譯時,與幾個核心無關)。所以「我只有單核就不用擔心順序」是錯的——這是常見誤區。

3. 執行期重排:CPU 也會調換實際發生的順序

第二個顛覆直覺的事實:就算編譯器沒重排,CPU 在執行時也會為了效能,讓記憶體操作的「實際發生順序」與指令順序不同。

現代 CPU 有各種優化(像把寫入暫存在緩衝區、預測執行等),使得「寫入記憶體」這個動作,何時被別的核心看見,不一定按指令順序:

    CPU["CPU 執行:
store a = 1
store b = 2"]

這兩個寫入『被其他核心看見』的順序
可能顛倒
(b 的新值先傳播出去,a 的還在緩衝)"]
    CPU --> REORDER
    OTHER["另一個核心:
可能先觀察到 b=2,
當下 a 還是舊值"]
    REORDER --> OTHER
    NOTE["這與編譯期重排疊加:
兩層重排都可能發生
→ 別人看到的順序,可能跟你寫的差很遠"]
    OTHER --> NOTE
    style REORDER fill:#e8a33d,color:#10100e
    style OTHER fill:#c2603a,color:#f4ecd8
    style NOTE fill:#c2603a,color:#f4ecd8

不同 CPU 架構的「重排有多自由」不一樣(x86 相對嚴格,ARM/POWER 較寬鬆),但重點是:你不能假設記憶體操作以程式碼順序被其他核心看見。這就是 P1-T03 第 5 節埋下的伏筆——coherence 保證「單一變數最終一致」,但多個變數的可見順序,要靠 memory ordering 規範,而預設情況下 CPU 是允許重排的。

4. store buffer:一個經典的違反直覺範例

把前面的抽象變成一個具體、經典、會讓你「啊?!」的範例。兩個執行緒,兩個變數 x、y 初始都是 0:

flowchart TB
    INIT["初始:x = 0, y = 0"]
    subgraph t1["執行緒1"]
        A1["x = 1;  (寫 x)"]
        A2["r1 = y; (讀 y)"]
        A1 --> A2
    end
    subgraph t2["執行緒2"]
        B1["y = 1;  (寫 y)"]
        B2["r2 = x; (讀 x)"]
        B1 --> B2
    end
    INIT --> t1
    INIT --> t2
    style A1 fill:#6fa8b8,color:#10100e
    style B1 fill:#6fa8b8,color:#10100e

直覺推理:「至少有一個執行緒會先寫再讀,所以 r1 和 r2 不可能都是 0」——因為若執行緒 1 先跑完(x=1, 讀 y),執行緒 2 再跑就會讀到 x=1;反之亦然。無論怎麼交錯,似乎總有一個會讀到對方寫的 1。

但實際上,r1 和 r2 可能都是 0! 為什麼?

flowchart TB
    EXPLAIN["重排的解釋(store buffer):
CPU 把『寫 x=1』暫存在執行緒1的 store buffer,
還沒傳播到記憶體/別的核心,
就先執行了『讀 y』(讀到還是 0)"]
    SAME["執行緒2同理:
『寫 y=1』還在它的 store buffer,
就先『讀 x』(讀到還是 0,因為執行緒1的 x=1 也還沒傳播)"]
    RESULT["結果:r1=0 且 r2=0
✗ 違反『先寫再讀就該看到』的直覺
= 兩個『讀』都被重排到各自的『寫』之前(被別人觀察到的效果)"]
    EXPLAIN --> SAME --> RESULT
    style EXPLAIN fill:#e8a33d,color:#10100e
    style RESULT fill:#c2603a,color:#f4ecd8

這就是重排的威力(與恐怖):每個執行緒的「寫」還沒對外可見,「讀」就先發生了,於是兩個都讀到舊值 0。這在現實 CPU 上真的會發生(在允許這種重排的架構上)。它徹底打破了「程式碼順序 = 可見順序」的直覺。你不需要完全推導出細節,只要被這個例子嚇到、記住「重排會導致違反直覺的結果」就達到本課目的了。

5. memory barrier:強制順序不被重排

既然重排會出問題,我們需要一個工具來強制某些順序:memory barrier(記憶體屏障,又叫 fence)。它像一道牆,告訴編譯器和 CPU:「屏障之前的記憶體操作,必須在屏障之後的操作之前完成(且對其他核心可見)」——不准跨過這道牆重排。

flowchart TB
    subgraph without["沒有 barrier"]
        W1["a = 1;"]
        W2["b = 2;"]
        WX["可被重排:別人可能先看到 b"]
    end
    subgraph with["有 barrier"]
        B1["a = 1;"]
        BAR["─── memory barrier ───
(一道不可跨越的牆)"]
        B2["b = 2;"]
        BX["保證:別人看到 b=2 時,
一定也已看到 a=1"]
        B1 --> BAR --> B2
    end
    style WX fill:#c2603a,color:#f4ecd8
    style BAR fill:#e8a33d,color:#10100e
    style BX fill:#8a9a5b,color:#10100e

比喻(借用 Jeff Preshing 的版本級控制比喻):把記憶體操作想成「提交程式碼到版本庫」。沒有 barrier 時,你的多次提交可能以任意順序被別人「拉取」看到。memory barrier 就像一個「同步點」:它保證屏障前的所有提交,會在屏障後的提交「之前」被所有人看到。它強制了一個大家都同意的順序。

直接連到你的 DMA 工作:準備 DMA 描述子、然後按門鈴(寫暫存器通知裝置),中間必須有一道 barrier,保證「描述子的寫入」在「門鈴的寫入」之前對裝置可見。否則裝置可能先看到門鈴、去讀還沒寫好的描述子 → 災難。kernel 提供 smp_mb()、wmb()(寫屏障)、rmb()(讀屏障)等(以及裝置 I/O 專用的屏障)正是幹這個的。你現在懂了為什麼非要它不可。

6. acquire / release:一種常見的順序語意

barrier 有不同「強度」。一種極常用、也較好理解的成對語意是 acquire / release,它特別適合「一個執行緒準備好資料、設個旗標;另一個執行緒看到旗標、就讀資料」這種模式:

flowchart TB
    subgraph producer["生產方(release)"]
        P1["準備資料:data = 42;"]
        P2["release 寫旗標:ready = 1;
(release 語意:保證『此寫入之前的所有寫入』
都先完成且可見)"]
        P1 --> P2
    end
    subgraph consumer["消費方(acquire)"]
        C1["acquire 讀旗標:while(ready==0);
(acquire 語意:保證『此讀取之後的所有讀取』
都在看到旗標之後才進行)"]
        C2["讀資料:use(data);  ← 保證讀到 42"]
        C1 --> C2
    end
    producer -.“release 配 acquire”.-> consumer
    GUARANTEE["配對保證:消費方一旦看到 ready=1(acquire),
就一定也看到 data=42
→ 不會發生『看到旗標卻讀到舊 data』"]
    consumer --> GUARANTEE
    style P2 fill:#8a9a5b,color:#10100e
    style C1 fill:#6fa8b8,color:#10100e
    style GUARANTEE fill:#e8a33d,color:#10100e

直覺: - release(用在「寫旗標/解鎖」):保證「在我之前的所有寫入」都已完成並可見,才讓這個 release 寫入生效。像「我發布前,確保所有準備工作都做完並公開」。 - acquire(用在「讀旗標/上鎖」):保證「在我之後的所有讀取」都發生在我之後。像「我確認拿到入場券後,才開始看裡面的東西」。

這正是鎖背後的魔法:P1-T09 的 mutex,其 lock 帶 acquire 語意、unlock 帶 release 語意——所以鎖不只互斥,還順便保證了「臨界區內的記憶體操作」對下一個拿到鎖的執行緒正確可見。你用鎖時,memory ordering 被鎖默默處理好了;但當你想 不用鎖(lock-free)時,就得自己用 acquire/release 或 barrier 來保證順序——這是 kernel lock-free 結構與 RCU 的核心(P3-T11 深入)。你現在只要有這個直覺即可。

7. 為什麼 volatile 不夠(破除最大的誤解)

C 有個 volatile 關鍵字,很多人誤以為它能解決並行問題。它不能。 這個誤解很危險,單獨拉出來破除。

volatile 的作用只有一個:告訴編譯器「這個變數的值可能在編譯器看不到的地方被改變,所以每次都要從記憶體重新讀,別把它快取在暫存器、別優化掉對它的存取」。它不提供:

✓ 每次從記憶體讀(不被編譯器快取/優化掉)
(用途:讀取會被硬體改變的東西,如某些暫存器)"]
    VOL --> NOT["volatile 不提供的:"]
    NOT --> N1["✗ 原子性
volatile 的 count++ 仍是讀-改-寫三步,仍會 race"]
    NOT --> N2["✗ memory barrier / 順序保證
不阻止 CPU 重排,不保證對其他核心的可見順序"]
    CONCLUSION["結論:volatile 解決不了 race,也解決不了 ordering
→ 並行要用『原子操作』和『barrier』,不是 volatile"]
    N1 --> CONCLUSION
    N2 --> CONCLUSION
    style VOL fill:#6fa8b8,color:#10100e
    style NOT fill:#c2603a,color:#f4ecd8
    style CONCLUSION fill:#e8a33d,color:#10100e

三個「volatile 救不了」的事實: 1. 不保證原子性:volatile int count; count++; 仍是讀-改-寫三步,並行下仍會遺失更新(回顧 P1-T08)。 2. 不是 memory barrier:它不阻止 CPU 重排其他記憶體操作,不保證跨核心的可見順序。 3. 單核也不夠:它連編譯期重排都不全管(它只管「對 volatile 變數本身的存取不被優化掉」,不管別的)。

那 volatile 到底何時用?用在「這個記憶體位置會被編譯器無法預知的外部因素改變」——例如記憶體映射的硬體暫存器(裝置可能改變它的值),你要確保每次都真的去讀那個位址而非用快取的舊值。但並行同步不是它的工作。要解決 race 用原子操作;要解決順序用 barrier。把 volatile 當並行工具是經典錯誤。

打通關:把 memory ordering 收攏成一個心智模型

一句話總結:「程式碼順序 = 可見順序」是錯覺——編譯器和 CPU 都會重排記憶體存取,讓多執行緒看到違反直覺的順序;原子操作解決「單一操作的不可分割」,memory barrier(及 acquire/release)強制必要的順序,而 volatile 兩者都給不了。這課只求你記住「重排會發生、需要 barrier」這份敬畏——它是 kernel lock-free、RCU,以及你 DMA『描述子須在門鈴前可見』的根,真正的精通留待 P3-T11。

常見誤區與踩雷提醒

誤區一(最核心):以為「程式碼順序 = 執行順序」。 編譯器與 CPU 都會重排。單執行緒下無感(結果被保證不變),多執行緒下另一個執行緒可能看到重排後的順序。

誤區二(最危險):以為 volatile 提供原子性或 memory barrier。 都不提供。volatile 只保證「每次從記憶體讀、不被編譯器優化掉」,用於硬體暫存器之類。並行同步要用原子操作(解決 race)和 barrier(解決順序)。

誤區三:以為單核心就不必擔心 ordering。 編譯期重排在單核一樣存在(它發生在編譯時)。而且即使單核,中斷處理常式與被中斷的程式之間也有順序問題。

誤區四:以為原子操作就解決了一切順序問題。 原子操作保證「單一操作不可分割」,但多個原子操作之間的順序,仍需要適當的 memory ordering(acquire/release 等)來規範。原子 ≠ 自動正確的順序。

誤區五:把這課當成「要全部精通」。 本課目標是「正確直覺 + 敬畏感」。記住「重排會發生、需要 barrier、volatile 不是解法」就夠了。完整的形式化模型在 P3-T11。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。需要 pthread 與支援 C11 atomics 的編譯器。

任務 A — 用 atomic 修好 race(對比鎖) 拿 P1-T08 的 race 程式,這次用 C11 原子操作修:

#include <stdatomic.h>
atomic_long counter = 0;
void *worker(void *_) {
    for (int i = 0; i < 1000000; i++)
        atomic_fetch_add(&counter, 1);   // 原子加,不用鎖
    return NULL;
}

確認結果穩定等於 2000000。對比 P1-T09 用鎖的版本——兩種都對,但原子操作對「單一變數的簡單操作」更輕量。寫一句話:原子操作和鎖,各適合什麼場景?

任務 B — 閱讀並解釋 store-buffer 範例 仔細讀第 4 節的 store-buffer 範例(兩執行緒各寫一變數再讀對方)。用你自己的話寫出:為什麼 r1 和 r2 可能都是 0? 這是驗收的核心——要能解釋「兩個讀都被重排到各自的寫之前(就其他執行緒的觀察而言)」。(註:要在真實硬體穩定重現此現象不容易且依架構而定,本任務重點是「理解為何可能」,不是「一定重現」。)

任務 C — 說明為什麼 volatile 救不了 race 寫一段話(驗收點):為什麼把 P1-T08 的 counter 宣告成 volatile 仍然會遺失更新?(提示:volatile 不保證原子性,counter++ 仍是三步。)

任務 D(閱讀,建立直覺)— Preshing 的兩篇 讀指定資源 Jeff Preshing 的兩篇文章(編譯期重排、memory barrier 像版本控制操作)。不要求全懂,目標是強化「重排是真的、barrier 在強制順序」這個直覺。讀完寫一兩句你的理解。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 atomic_int/atomic_long + atomic_fetch_add 改寫計數,兩執行緒各加 1,000,000 後結果穩定為 2,000,000。 2. ☐ 閱讀 store-buffer 範例,用文字解釋為何兩執行緒可能都讀到舊值(都是 0)。 3. ☐ 說出 volatile 為何不能解決 race(不保證原子性,也非 barrier)。

評分量表: - 60(及格):能用原子操作修好 race。 - 80(熟練):能解釋重排現象(編譯期 + 執行期),知道 barrier 在做什麼。 - 100(精通):能說明 acquire/release 直覺,並知道這在 kernel 會以 smp_mb()/wmb()/rmb() 等形式再出現(連結 P3-T11 LKMM),以及它如何關係到 DMA 的可見性。
