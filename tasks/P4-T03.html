P4-T03 · ioctl 與 mmap(user/kernel 控制與零拷貝資料面)

一句話:read/write 適合搬資料流,但「下達一個命令」用 ioctl、「讓 user 直接讀寫核心緩衝區(零拷貝)」用 mmap。這兩者正是你產品的縮影:控制面用 ioctl(設定佇列、提交工作)、資料面用 mmap + DMA(把 I/O 餵給 GPU)。

為什麼要先學這個(導讀)

P4-T02 的字元裝置用 read/write 搬資料。但真實的裝置驅動(包括你的產品)常需要兩種額外的介面:

  • ioctl(I/O control):下達控制命令——不是搬資料流,而是「做一個特定操作」或「查詢/設定一個參數」。例如「設定佇列深度為 64」「查詢裝置狀態」「提交一個工作」。用 unlocked_ioctl callback,命令用 _IOR/_IOW 等巨集編碼(避免命令號衝突)。
  • mmap(memory map):把核心的緩衝區直接映射到 user 空間的位址,讓 user 程式能直接讀寫那塊記憶體——零拷貝(zero-copy)!不必像 read/write 那樣 copy_*_user 搬來搬去。這對高效能資料傳輸極重要。

為什麼這對你是 scope: direct、而且是產品的縮影?想想你的產品架構:「user space app 透過 DMA 把 I/O 餵給 GPU 算 parity」。這個架構分兩面: - 控制面:user app 要告訴 module「做什麼」(設定、提交工作)——這常用 ioctl。 - 資料面:大量資料要在 user、kernel、裝置之間高效流動——這常用 mmap + DMA(零拷貝,避免昂貴的複製)。

所以這一課的 ioctl + mmap,正是你產品「控制面 + 資料面」的雛形。mmap 的零拷貝概念,也直接銜接 P6 的 DMA 與 GDS(GPU Direct Storage)。

一個重要澄清(常見誤區):mmap 不等於 DMA。 mmap 讓 CPU(user 程式)能直接存取那塊記憶體;但要讓裝置(GPU、NVMe)也能直接存取它做 DMA,還需要 P6 的 DMA 映射(把記憶體映射成裝置能用的位址)。mmap 是「零拷貝」的一半(CPU 端),DMA 是另一半(裝置端)。

開始之前(前置確認)

  • 依賴:P4-T02(字元裝置、file_operations、copy_*_user)、P3-T11(memory barrier——mmap 共享記憶體的同步)。也用到 P1-T04(分頁、page、虛擬位址映射)、P3-T06(page、實體位址)。
  • 自我檢測: 1. 你還記得 P4-T02 的 file_operations 和 copy_*_user 嗎?ioctl 和 mmap 是 file_operations 裡再加的 callback。 2. 你還記得 P1-T04 的「分頁:虛擬位址經分頁表映射到實體頁」嗎?mmap 就是建立「user 虛擬位址 → 核心緩衝區的實體頁」的映射。
  • 環境:QEMU 虛擬機。所有測試只在 VM。

核心內容

拆成這幾節:(1) ioctl:下達控制命令 → (2) 命令編碼:IOR/_IOW → (3) ioctl 引數仍需 copy*_user → (4) mmap:零拷貝的原理 → (5) remap_pfn_range:建立映射 → (6) 控制面 + 資料面:你產品的縮影,最後打通關。

1. ioctl:下達控制命令(不是搬資料流)

read/write 是「資料流」語意(讀一串、寫一串)。但很多操作不是資料流,而是「下一個命令」:設定參數、查詢狀態、觸發動作。這用 ioctl。

機制:user 呼叫 ioctl(fd, 命令號, 引數) → kernel 呼叫你的 unlocked_ioctl callback → 你依命令號 switch,執行對應操作。每個命令號代表一個操作(設定佇列深度、查狀態、提交工作……)。

注意是 unlocked_ioctl,不是舊的 ioctl(回顧 P4-T02 的誤區):LDD3 那個年代的 ioctl callback 會持有一把全域大鎖(BKL,已廢除),現代的 unlocked_ioctl 不持那把鎖(所以叫 "unlocked"),你自己負責需要的鎖。寫新驅動一律用 unlocked_ioctl。

ioctl 適合「控制」類操作——這就是你產品控制面的工具(第 6 節)。

2. 命令編碼:_IOR / _IOW 巨集

ioctl 的命令號不能隨便用數字——那容易和別的驅動/別的命令衝突。kernel 提供巨集來編碼命令號,把「方向、裝置類型、編號、引數大小」打包進去:

flowchart TB
    MACROS["命令編碼巨集(把資訊打包進命令號)"]
    MACROS --> IO["_IO(type, nr)：無引數的命令"]
    MACROS --> IOR["_IOR(type, nr, datatype)：讀(kernel→user 回傳資料)"]
    MACROS --> IOW["_IOW(type, nr, datatype)：寫(user→kernel 傳入資料)"]
    MACROS --> IOWR["_IOWR(type, nr, datatype)：雙向"]
    ENCODE["編碼進命令號的資訊:
type(一個 magic 字元,代表你的驅動)
nr(命令編號)
方向(讀/寫/雙向)
引數型別的大小"]
    MACROS --> ENCODE
    BENEFIT2["好處:① 命令號帶 magic + 編號 → 不易和別的驅動衝突
② 帶方向與大小 → kernel 可做基本檢查"]
    ENCODE --> BENEFIT2
    style IOR fill:#6fa8b8,color:#10100e
    style IOW fill:#8a9a5b,color:#10100e
    style BENEFIT2 fill:#e8a33d,color:#10100e

例如定義命令:

#define MYDEV_MAGIC 'M'
#define MYDEV_SET_SIZE  _IOW(MYDEV_MAGIC, 1, int)   // user 寫入一個 int(設定大小)
#define MYDEV_GET_SIZE  _IOR(MYDEV_MAGIC, 2, int)   // kernel 回傳一個 int(查詢大小)

巨集把 magic 字元(代表你的驅動)、命令編號、方向(讀/寫)、引數型別大小打包進命令號。好處:命令號帶 magic + 編號不易衝突、帶方向與大小讓 kernel 能做基本檢查。

常見誤區:ioctl 命令號未用 _IO* 巨集編碼導致衝突——直接用 1、2 這種裸數字當命令號,可能和系統其他 ioctl 衝突、或缺乏方向/大小資訊。一律用 _IO/_IOR/_IOW/_IOWR 編碼。

3. ioctl 引數仍需 copy_*_user

一個容易忽略的點:ioctl 的「引數」如果是個指標(指向 user 空間的資料),那存取它仍然要 copy_*_user——和 P4-T02 的 read/write 一樣的道理。

    WRONG3 --> DANGER3["★ 一樣的危險(P4-T02)★
它仍是 user 指標、在另一個位址空間
→ 直接解參考 → 當機 / 安全漏洞"]
    IOCTL_ARG --> RIGHT3["✓ 用 copy_from_user(&ksize, user_ptr, sizeof(int))
取入;回傳用 copy_to_user"]

    style DANGER3 fill:#c2603a,color:#f4ecd8

關鍵(驗收點:說明 ioctl 引數為何仍需 copy_*_user):雖然命令號用 _IO* 編碼過,但那只是「命令的識別」;引數本身若是 user 指標,它仍在使用者態位址空間,你在 kernel 裡存取它一樣不能直接解參考(回顧 P4-T02 的命門:位址空間隔離 + 安全漏洞)。要用 copy_from_user(取入引數)/ copy_to_user(回傳結果)。

換句話說:_IO* 編碼解決「命令號」的問題,copy_*_user 解決「引數資料跨越 user/kernel 邊界」的問題——兩者都要做。命令號編碼不會讓你免去 copy_*_user。

4. mmap:零拷貝的原理

現在到資料面的主角:mmap。它解決一個效能問題——read/write 每次都要 copy_*_user 把資料在 user 和 kernel 之間複製一份,大量資料時這個複製很昂貴。mmap 讓 user 直接存取核心的緩衝區,免去複製:零拷貝(zero-copy)。

(每次都複製一份,大量資料時昂貴)"]
    end
    subgraph mmap_way["mmap(零拷貝)"]
        MW["核心配置一塊緩衝區(實體頁)
mmap 把這塊的『實體頁』
映射到 user 的虛擬位址(P1-T04 分頁)
→ user 和 kernel 看的是『同一塊實體記憶體』
→ user 直接讀寫,不複製"]
    end
    copy_way -.“mmap 免去複製”.-> mmap_way
    style CW fill:#e8a33d,color:#10100e
    style MW fill:#8a9a5b,color:#10100e

原理(回顧 P1-T04 分頁):核心配置一塊緩衝區(一些實體頁),mmap 把這些實體頁映射到 user 行程的虛擬位址空間。於是 user 的那段虛擬位址,和核心的緩衝區,指向同一塊實體記憶體——user 程式直接讀寫它,kernel 也看得到,不需要任何複製。

機制:user 呼叫 mmap(fd, ...) → kernel 呼叫你的 file_operations.mmap callback → 你在裡面建立「user 虛擬位址 → 核心緩衝區實體頁」的映射(下一節 remap_pfn_range)。映射建好後,user 對那段位址的讀寫,直接作用在核心緩衝區的實體頁上。

零拷貝對高效能資料傳輸(你的領域)極重要——避免大量資料的複製開銷。

把字元裝置的三種介面放一起對照,各自的定位就清楚了:

5. remap_pfn_range:建立映射

mmap callback 裡,你怎麼把核心緩衝區的實體頁映射到 user 空間?主要工具是 remap_pfn_range(或對單頁用 vm_insert_page)。

flowchart TB
    MMAP_CB["你的 file_operations.mmap(file, vma) callback
(vma = user 要映射的虛擬位址範圍)"]
    MMAP_CB --> PFN["取得核心緩衝區的『page frame number(PFN)』
(實體頁的編號,從 virt_to_phys / page 算出)"]
    PFN --> REMAP["remap_pfn_range(vma, vma起始, pfn, 大小, ...)
→ 把 vma(user 虛擬位址)映射到那些實體頁
(在 user 的分頁表建立對應 entry,P1-T04)"]
    REMAP --> DONE["映射完成 → user 對 vma 的存取 = 存取核心緩衝區"]
    NOTE6["★ 常見誤區:mmap 的頁未正確處理 → segfault ★
(PFN 算錯、範圍/權限不對、緩衝區未對齊頁界...)
→ user 一存取就 segfault"]
    DONE --> NOTE6
    style PFN fill:#6fa8b8,color:#10100e
    style REMAP fill:#8a9a5b,color:#10100e
    style NOTE6 fill:#c2603a,color:#f4ecd8

流程: - mmap callback 收到一個 vma(描述 user 要映射的虛擬位址範圍)。 - 取得核心緩衝區的 PFN(page frame number,實體頁編號)。 - 用 remap_pfn_range(vma, ...) 把 vma 映射到那些實體頁——這在 user 的分頁表裡建立對應的 entry(回顧 P1-T04 分頁表)。 - 完成後,user 對 vma 的存取,直接作用在核心緩衝區上。

常見誤區:mmap 的頁未正確處理導致 segfault——PFN 算錯、映射範圍/權限不對、緩衝區沒對齊頁界(page 通常 4KB,緩衝區起點要對齊)等,都會讓 user 一存取就 segfault。建立 mmap 要小心處理頁對齊與 PFN。

另一個關鍵(常見誤區:忽略 mmap 共享記憶體的同步/屏障):mmap 後,user 和 kernel(甚至裝置)共享同一塊記憶體——這是共享可變狀態!如果有同步需求(user 寫完、kernel 要讀),可能需要 memory barrier(回顧 P3-T11)來保證可見順序,就像任何共享記憶體的並行存取。零拷貝省了複製,但沒省掉同步的責任。

6. 控制面 + 資料面:你產品的縮影

把 ioctl 和 mmap 放在一起,你會看到它們正是你產品架構的雛形。

這就是這一課對你最重要的洞察:控制面和資料面分開,各用最適合的工具。 - 控制面(ioctl):小量、需要明確語意的命令——設定、提交工作、查詢。用 ioctl。 - 資料面(mmap + DMA):大量資料要高效流動——用 mmap(CPU 端零拷貝)+ DMA(裝置端直接存取,P6)。

mmap 是零拷貝的「CPU 端」、DMA 是「裝置端」——這呼應第 4 節的澄清(mmap ≠ DMA)。你產品的「user app 透過 DMA 把 I/O 餵給 GPU」這條資料路徑,正是 mmap(讓 user 和 kernel 共享緩衝區)+ DMA(讓 GPU 直接讀那塊緩衝區)的組合。理解這個分工,你就抓住了產品架構的骨架,而 P5(block layer/NVMe)和 P6(DMA)會把資料面補完。

(驗收點:user 端 mmap 後寫入的內容,kernel 端能讀到,證明零拷貝共享;說明零拷貝資料面如何銜接後續 DMA/GDS。)

常見誤區與踩雷提醒

誤區一:ioctl 命令號未用 _IO* 巨集編碼導致衝突。 裸數字當命令號可能衝突、缺方向/大小資訊。用 _IO/_IOR/_IOW/_IOWR 編碼(帶 magic、編號、方向、大小)。

誤區二:以為 ioctl 命令編碼過就不必 copy_*_user。 命令號編碼只解決「命令識別」;引數若是 user 指標,仍在使用者態空間,存取它一樣要 copy_*_user(否則當機/安全漏洞,回顧 P4-T02)。

誤區三:mmap 的頁未正確處理導致 segfault。 PFN 算錯、範圍/權限不對、緩衝區未對齊頁界,都會讓 user 一存取就 segfault。注意頁對齊與 PFN 計算。

誤區四:忽略 mmap 共享記憶體的同步/屏障。 mmap 後 user/kernel(甚至裝置)共享同一塊記憶體——是共享可變狀態。有同步需求時要用 memory barrier(P3-T11)。零拷貝省複製,不省同步。

誤區五:以為 mmap 自動等於 DMA。 mmap 讓 CPU(user)直接存取記憶體;要讓裝置(GPU/NVMe)直接存取做 DMA,還需 P6 的 DMA 映射。mmap 是零拷貝的 CPU 端,DMA 是裝置端。

動手實作

環境:QEMU 虛擬機。所有測試只在 VM。

任務 A — 為字元裝置加 ioctl(驗收點) 在 P4-T02 的字元裝置上,加 unlocked_ioctl: - 用 _IOW 定義一個「設定緩衝區大小」命令、_IOR 定義一個「查詢緩衝區大小」命令。 - 在 ioctl 函式裡 switch 命令號,用 copy_from_user/copy_to_user 處理引數。 寫一個 user 程式呼叫這兩個 ioctl。驗收:user 端 ioctl 成功查到/改到裝置的緩衝區大小。

任務 B — mmap 零拷貝(驗收點,核心) 為裝置加 file_operations.mmap:核心配置一塊緩衝區,用 remap_pfn_range 把它映射到 user。寫一個 user 程式 mmap 這個裝置,直接寫入映射的記憶體。然後在 kernel 端(例如透過一個 ioctl 或 read)確認 kernel 看到了 user 寫的內容(或反向:kernel 寫、user 讀)。驗收:user 端 mmap 後寫入的內容,kernel 端能讀到,證明零拷貝共享。 注意頁對齊。

任務 C — 說明 ioctl 引數為何仍需 copy_*_user(驗收點) 寫一段文字:ioctl 命令號已用 _IO* 編碼,為什麼引數(若是指標)還是要 copy_*_user?驗收:能說明(命令號編碼只是識別命令;引數資料仍跨 user/kernel 邊界,直接解參考會當機/安全漏洞)。

任務 D(連結)— 零拷貝如何銜接 DMA/GDS 寫一兩句話:你的 mmap 零拷貝(CPU 端),如何和後續 P6 的 DMA(裝置端)合起來,達成「user app 透過 DMA 把資料餵給 GPU」?(提示:mmap 讓 user/kernel 共享緩衝區,DMA 讓 GPU 直接存取那塊緩衝區,資料不必反覆複製。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ user 端 ioctl 成功查到/改到裝置的緩衝區大小。 2. ☐ user 端 mmap 後寫入的內容,kernel 端能讀到(或反向),證明零拷貝共享。 3. ☐ 說明 ioctl 引數為何仍需 copy_*_user。

評分量表: - 60(及格):能實作 ioctl。 - 80(熟練):能實作 mmap 零拷貝。 - 100(精通):能說明零拷貝資料面如何銜接後續 DMA/GDS。

延伸與銜接

  • 對應工作場景:直接對應——「user space app 透過 DMA 把 I/O 餵給 GPU」的控制面常用 ioctl、資料面常用 mmap + DMA;這是產品架構的縮影。
  • 這課餵給未來的:ioctl 控制面 → 你產品的設定/提交介面;mmap 零拷貝 → P6 DMA(裝置端)+ P7 GDS(GPU Direct Storage);mmap 共享同步 → 回收 P3-T11 barrier。
  • 下一步 → P4-T04 PCI 子系統(pci_driver / BAR / config space / MSI-X):你已經會寫字元裝置驅動(user 介面)。下一課轉向硬體端——PCI 子系統,這是你 NVMe SSD 和 GPU 的共同基礎(它們都是 PCIe 裝置)。你會寫一個 PCI 驅動骨架:pci_driver(用 id_table 讓 bus match,回顧 P4-T01)、map BAR(裝置的暫存器/記憶體,例如 NVMe 的 doorbell 就在 BAR 裡)、設定 MSI-X 中斷(回顧 P3-T10),以及 pci_set_master(致能 DMA——漏掉它 DMA 就不動)。這是 Phase 4 的出關門檻,也是 P5 NVMe 驅動的直接基礎(NVMe driver 正是建在 pci_driver + BAR + MSI-X 之上)。
