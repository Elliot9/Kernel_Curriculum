P0-T03 · 陣列、字串與指標的關係

一句話:在 C 裡,「陣列」和「指標」是親戚,但不是同一個人。搞混它們,是 C 新手最常踩的坑;搞懂它們,你就握住了 C 字串(以及結尾那個看不見的 \0)的鑰匙。

為什麼要先學這個(導讀)

在 JS 裡,陣列是個有 .length、.push()、.map() 的聰明物件。在 PHP 裡,陣列甚至同時是清單和字典。它們都很「貼心」——你永遠能問出陣列多長,越界存取也只會給你 undefined 而不是災難。

C 的陣列極度原始:它就是「一塊連續的記憶體,裝著同型別的東西」。沒有 .length、沒有方法、沒有越界保護。更詭異的是,C 陣列在大多數場合會悄悄變成一個指標——這個行為叫「退化(decay)」,是 C 最反直覺、也最常坑人的設計之一。

為什麼這課重要?因為 kernel 裡到處是緩衝區(buffer)——一塊記憶體配上它的長度,分開傳遞。NVMe 命令、DMA 緩衝區、network packet,全是「指標 + 長度」的組合。如果你還用 JS 那種「陣列自己知道多長」的直覺,你在 kernel 裡會不斷讀越界、寫爆緩衝區——而 kernel 沒有「給你 undefined」這種溫柔的兜底,只有當機和資料損毀。這課就是要把那個危險的直覺,換成 C/kernel 的正確直覺。

開始之前(前置確認)

  • 依賴:P0-T02(你已懂指標、&、*、以及 p+1 會跳一整個元素)。
  • 自我檢測:你能說出「為什麼 int* 加 1,位址增加 4」嗎?如果不行,回去複習 P0-T02 第 6 節的指標運算——這課整個建立在那上面。

核心內容

拆成這幾節:(1) 陣列是連續記憶體 → (2) arr[i] 其實是 *(arr+i) → (3) 退化 decay → (4) decay 的最大坑:sizeof 在函式裡騙你 → (5) C 字串與 \0 → (6) \0 不見了會怎樣,最後打通關。

1. 陣列:一塊連續的記憶體

int arr[5] = {10, 20, 30, 40, 50};

這在記憶體裡是 5 個緊鄰排列的 int,共 20 bytes(每個 int 4 bytes):

關鍵:元素緊鄰、位址連續、型別相同。這三點是陣列的全部本質。它沒有 JS 陣列那些方法和自我認知——它就是一塊排好的記憶體。

2. 真相:arr[i] 其實是 *(arr + i)

C 的下標語法 arr[i] 只是語法糖(讓你寫起來方便的簡寫)。編譯器看到 arr[i],實際做的是:從 arr 的起始位址,用指標運算跳過 i 個元素,然後解參考。也就是 *(arr + i)。

    style A fill:#6fa8b8,color:#10100e
    style E fill:#8a9a5b,color:#10100e

這就解釋了一個你可能背過但沒想過為什麼的規則:為什麼 C 陣列從 0 開始數。因為 arr[0] = *(arr + 0) = 起始位址本身。第 0 個元素,位移為 0,剛好就是開頭。從 1 開始反而不自然。

變態小知識(可跳過):既然 arr[i] = *(arr+i),而加法可交換(arr+i = i+arr),所以 *(arr+i) = *(i+arr) = i[arr]。沒錯,arr[2] 和 2[arr] 在 C 裡合法且等價。你永遠不該這樣寫,但它赤裸裸地證明了「下標只是指標運算的偽裝」。

3. 退化(decay):陣列名變成指標

這是本課的核心。在大多數場合,當你使用陣列的「名字」時,它會自動「退化」成一個指向第 0 個元素的指標。

int arr[5];
int *p = arr;          // 合法!arr 在這裡退化成 &arr[0]
printf("%d", arr[2]);  // arr 退化成指標,等同 p[2],等同 *(p+2)

arr 在這些場合不再代表「整個陣列這個整體」,而是降格成「指向開頭的一個指標」。

這個自動轉換省了你打字(你不必每次寫 &arr[0]),但它丟失了一個關鍵資訊:陣列的長度。退化後的指標只知道「開頭在哪」,完全不知道「總共多長」。記住這個「長度遺失」——下一節的大坑就源於此。

什麼時候 arr 不退化? 兩個主要例外:sizeof(arr)(這時給你整個陣列的大小)和 &arr(取整個陣列的位址)。除了這類少數場合,arr 幾乎總是退化成指標。

4. decay 的最大坑:sizeof 在函式裡會騙你

這個坑害過無數人,值得拆步驟講清楚。看這段:

void process(int param[]) {
    // 你以為 param 是陣列,其實它早已退化成 int* 指標!
    printf("函式裡 sizeof = %zu\n", sizeof(param));  // 印 8(指標大小),不是陣列大小!
}

int main(void) {
    int arr[10];
    printf("main 裡 sizeof = %zu\n", sizeof(arr));   // 印 40(10 個 int)
    process(arr);
    return 0;
}

main 裡 sizeof(arr) 是 40(完整陣列),但 process 裡 sizeof(param) 是 8。為什麼差這麼多?逐步看:

重點:函式參數寫成 int param[] 是個視覺騙局——C 規定它完全等同於 int *param。 陣列從來沒有「整個」被傳進函式;傳進去的只是開頭的位址(退化的指標)。

這是無數 buffer overflow 的根源:新手在函式裡用 sizeof(param) / sizeof(param[0]) 想算「陣列長度」,在 64 位元系統上得到的卻是 8 / 4 = 2——不管原陣列多長,永遠算出 2,完全錯誤。

結論(請刻進肌肉記憶):C 函式無法從陣列參數得知它的長度。你必須把長度當成另一個參數明確傳進去。 這正是為什麼 kernel(和所有 C API)的函式簽章長這樣:

ssize_t read(int fd, void *buf, size_t count);   // buf 是緩衝區,count 是它的長度

緩衝區(指標)和它的長度,永遠分開傳。你以後在 kernel 裡會看到成千上萬個這種 (buf, len) 簽章——現在你徹底知道為什麼了。

5. C 字串:結尾藏著一個看不見的 \0

C 沒有「字串型別」。所謂 C 字串,就是「一個 char 陣列,結尾放一個值為 0 的 byte(寫作 '\0')當作終止符」。

char s[] = "Hi";   // 實際佔 3 bytes:'H','i','\0'

所有 C 字串函式(strlen、printf("%s")、strcpy…)都靠這個 \0 來判斷「字串到哪裡結束」。它們從字串開頭一路讀,讀到 \0 就停。

所以 strlen("Hi") 回傳 2(可見字元數),但這個字串實際佔 3 bytes(含 \0)。strlen 數的是「\0 之前有幾個字元」,不含 \0 本身。

6. 如果 \0 不見了會怎樣:讀越界

\0 是 C 字串的「邊界標記」。一旦它不見了(被覆蓋掉、或你忘了給它留位置),字串函式就不知道該在哪停,於是一直往後讀,讀過你的緩衝區邊界,讀進不屬於這個字串的記憶體,直到碰巧撞到某個值為 0 的 byte 為止。

結果是讀出一堆垃圾、洩漏不該洩漏的記憶體內容、甚至直接崩潰。這就是為什麼 C 字串操作必須時時刻刻顧好那個 \0:配置空間要記得多留一格給它、複製字串要確保 \0 也被複製過去。

一句話總結:C 的陣列與字串都不會「自我描述邊界」——長度會在退化時遺失、字串結尾靠一個脆弱的 \0。在 C/kernel 的世界,記住邊界是你的責任,不是語言的。 這個教訓會一路跟著你到 buffer 管理、DMA 緩衝區、封包解析。

常見誤區與踩雷提醒

誤區一:以為函式參數 char arr[] 還是陣列。 它已經退化成 char*。sizeof 在函式裡拿到的是指標大小(8),不是原陣列大小。永遠把長度當另一個參數傳。

誤區二:忘記字串結尾的 \0,導致讀越界。 配置字串緩衝區時,容量要比可見字元數多 1(留給 \0)。例如要存 "Hello"(5 字),陣列至少要 char s[6]。

誤區三:用 strcpy 不檢查長度,造成緩衝區溢位。

char small[4];
strcpy(small, "Hello, world");  // 災難:13 bytes(含\0)硬塞進 4 bytes 的空間

strcpy 傻傻地一路複製到來源的 \0 為止,完全不管目的地裝不裝得下。多出來的 byte 會覆蓋掉旁邊的記憶體。在 kernel 裡,這種溢位可能覆蓋關鍵資料結構或回傳位址——是經典的安全漏洞。較安全的做法是用會限制長度的版本(strncpy,或 kernel 裡的 strscpy),並永遠確認目的緩衝區夠大。

誤區四:對退化後的指標用 sizeof 想得到陣列大小。 同誤區一,這是最常見的具體犯法形式。sizeof(指標) 永遠是指標本身的大小(8),跟它指向多大的東西無關。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 自己實作 my_strlen(理解 \0 終止)

size_t my_strlen(const char *s) {
    size_t n = 0;
    while (s[n] != '\0')   // 一路數到終止符為止
        n++;
    return n;
}

用 my_strlen("hello") 驗證回傳 5。再試 my_strlen("")(空字串)應回傳 0——想想為什麼(因為第一個 byte s[0] 就是 \0,迴圈一次都沒進去)。

任務 B — 自己實作 my_strcpy,並確保複製到 \0

void my_strcpy(char *dst, const char *src) {
    size_t i = 0;
    while ((dst[i] = src[i]) != '\0')  // 複製當前字元;若剛複製的是 \0 就停
        i++;
}

測試:複製 "test" 到一個夠大的緩衝區,用 my_strlen 驗證結果長度為 4(代表 \0 也正確複製過去了)。

任務 C — 親眼看 sizeof 的 8 vs 40(decay 的鐵證) 寫出本課那個 process(int param[]) 範例,在 main 對原陣列、在函式對參數各印一次 sizeof。你會看到 40 vs 8。寫一句話:這個 8 是哪來的、它代表什麼?(指標大小,證明陣列已退化。)

任務 D(進階)— 製造一次「\0 遺失」 配置 char buf[5],手動填入 5 個非零字元(不留 \0),然後對它呼叫 printf("%s", buf) 或 strlen(buf)。在 VM/容器裡做,觀察它印出多餘的垃圾字元,或 strlen 回傳一個大於 5 的數——這就是「讀越界」。然後在第 5 格放 \0(改成 char buf[6] 並設 buf[5]='\0'),確認行為恢復正常。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ my_strlen("hello") 回傳 5,且 my_strlen("") 回傳 0。 2. ☐ 在函式內對 char param[] 取 sizeof 得到 8(64-bit),在 main 對原陣列 char s[10] 取 sizeof 得到 10,並能解釋差異(退化)。 3. ☐ my_strcpy 正確複製含結尾 \0(用 strlen 驗證長度正確)。

評分量表: - 60(及格):兩個字串函式正確。 - 80(熟練):能解釋 decay(陣列名退化成指標)與 \0 終止機制。 - 100(精通):能說明為何 sizeof 在函式內拿不到原陣列大小,並把它連結到「為什麼所有 C/kernel API 都是 (ptr, len) 分開傳」。

延伸與銜接

  • 對應工作場景:基礎能力。理解「緩衝區與長度分離」是後續所有 bio / DMA 緩衝區操作的根——kernel 裡你會無數次看到 (void *buf, size_t len) 這種簽章,現在你知道為什麼了。
  • 這課餵給未來的:「連續記憶體 + 起始位址」的觀念 → P0-T04 struct 佈局、以及之後的 DMA 緩衝區;(buf, len) 分離 → 整個 kernel I/O 路徑。
  • 下一步 → P0-T04 struct、union、bitfield 與記憶體對齊:你已經會把同型別的東西排成陣列。下一課我們把不同型別的東西打包成一個 struct,並揭開一個硬體層級的秘密——「對齊(alignment)」與編譯器偷塞的「padding」。這直接關係到你之後怎麼讀懂 NVMe 那種一個 byte 都不能錯的硬體結構。
