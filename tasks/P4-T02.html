P4-T02 · 字元裝置驅動(file_operations / cdev / 註冊)

一句話:字元裝置讓使用者態能用 open/read/write 跟你的 module 溝通——你提供一組 file_operations callback,kernel 在 user 程式操作 /dev/你的裝置 時呼叫它們。最關鍵的鐵則:永遠不能直接解參考使用者態指標,要用 copy_to_user/copy_from_user(它們還可能睡眠)。

為什麼要先學這個(導讀)

P4-T01 你懂了裝置模型的全景。這一課寫第一個真正的裝置驅動——字元裝置(character device)。它是最常見的「user space 和 kernel module 溝通」的方式,而且直接對應你的產品架構。

字元裝置的核心想法:在 /dev 下有一個裝置節點(例如 /dev/mydev),使用者態程式像操作檔案一樣 open / read / write / close 它;而這些操作會被導向你的 module 提供的函式。你提供一組 callback(file_operations,又是 P0-T07 的 ops 結構),kernel 在 user 程式操作裝置節點時呼叫對應的:user 程式 read → 呼叫你的 read 函式;write → 你的 write 函式。

幾個要學的部件: - major/minor 裝置號:識別裝置的編號(major 大致對應「哪個驅動」,minor 對應「該驅動的第幾個裝置」)。 - 註冊三步:alloc_chrdev_region(要裝置號)→ cdev_init/cdev_add(把你的 file_operations 綁到裝置號)。 - file_operations:open/read/write/release 等 callback。 - copy_to_user/copy_from_user:在 kernel 和 user 之間搬資料的唯一正確方式——這是這一課最重要、最關乎安全的部分。 - 裝置節點:用 device_create 讓 udev 自動在 /dev 建出節點(P4-T01 的 uevent/udev)。

為什麼這對你是 scope: direct?因為你產品的 user space app 很可能透過字元裝置 + ioctl/mmap 與自寫 module 溝通——設定佇列深度、提交工作、查詢狀態。這一課的字元裝置是那個溝通管道的基礎,P4-T03 的 ioctl/mmap 則建在它之上。

(書本:LDD3 Ch.3 講字元驅動,概念經典但 API 釘在 2.6.10,要對照新版 API;Madieu 2e Ch.4 也涵蓋。)

開始之前(前置確認)

  • 依賴:P4-T01(裝置模型、device_create/udev)、P0-T07(函式指標/ops 結構——file_operations 就是一組 callback)。也用到 P3-T07/P3-T08(GFP/睡眠/context——copy_*_user 可能睡眠)、P1-T06(user/kernel 邊界)。
  • 自我檢測: 1. 你還記得 P0-T07 的「ops 結構:一個裝滿函式指標的 struct,kernel 透過它呼叫你的實作」嗎?file_operations 就是字元裝置的 ops 結構。 2. 你還記得 P1-T06 的「user space 和 kernel 是隔離的位址空間」嗎?這就是為什麼不能直接解參考 user 指標——它在另一個位址空間。
  • 環境:QEMU 虛擬機。所有 insmod/裝置測試只在 VM。

核心內容

拆成這幾節:(1) 字元裝置的全貌 → (2) major/minor 裝置號 → (3) 註冊三步:裝置號 + cdev → (4) file_operations:你的 callback → (5) 命門:copy_to/from_user → (6) /dev 節點與資源釋放,最後打通關。

1. 字元裝置的全貌:user 操作檔案 → 你的函式

先看整體:使用者態把字元裝置當檔案操作,這些操作被導向你 module 的函式。

機制:使用者態 open/read/write/close 一個 /dev 下的字元裝置節點 → kernel VFS 依裝置號找到你註冊的 file_operations → 呼叫對應的 callback(你的函式)。你寫的就是這些 callback——決定「user 讀/寫這個裝置時,實際發生什麼」。

這一課的範例會做一個「核心內緩衝區」字元裝置:user write 把資料存進 module 裡的緩衝區,user read 把緩衝區內容讀回。麻雀雖小,但涵蓋了字元裝置的所有要素。

2. major/minor 裝置號:識別裝置

每個字元裝置由一對編號識別:major(主編號) 和 minor(次編號)。

它的第 0、1、2 個裝置就是
(240,0)、(240,1)、(240,2)

    MINOR --> EXAMPLE2
    style MAJOR fill:#6fa8b8,color:#10100e
    style MINOR fill:#8a9a5b,color:#10100e
    style EXAMPLE2 fill:#e8a33d,color:#10100e

  • major:大致對應「哪個驅動」——kernel 靠它把對裝置節點的操作,導向註冊了該 major 的驅動。
  • minor:對應「該驅動管的第幾個裝置」——一個驅動可以管多個裝置(例如多個 NVMe namespace),用 minor 區分。

/dev 下的裝置節點各自帶著一對 (major, minor)。你 ls -l /dev 會看到字元裝置(開頭 c)後面有兩個數字,就是 major 和 minor。

3. 註冊三步:要裝置號 + 綁定 cdev

寫字元裝置驅動,核心是把「你的 file_operations」綁定到「一個裝置號」。這分三步(現代寫法):

flowchart TB
    STEP1["① alloc_chrdev_region(&dev, 0, count, "mydev")
向 kernel 動態要一個(或多個)裝置號
(讓 kernel 分配,不要寫死 major——避免衝突)"]
    STEP2["② cdev_init(&my_cdev, &my_fops)
把你的 file_operations 綁到一個 cdev 物件
(cdev = 字元裝置的核心結構)"]
    STEP3["③ cdev_add(&my_cdev, dev, count)
把這個 cdev 註冊到剛要到的裝置號
→ 此後對該裝置號的操作會走你的 file_operations"]
    STEP1 --> STEP2 --> STEP3
    NOTE5["★ 卸載時要反序清理(P4-T01/P0-T06 配對):★
cdev_del → unregister_chrdev_region
(否則裝置號/cdev 洩漏)"]
    STEP3 --> NOTE5
    style STEP1 fill:#6fa8b8,color:#10100e
    style STEP3 fill:#8a9a5b,color:#10100e
    style NOTE5 fill:#c2603a,color:#f4ecd8

三步: 1. alloc_chrdev_region:向 kernel 動態要裝置號(讓 kernel 分配 major,而非寫死——寫死容易和別的驅動衝突)。 2. cdev_init:把你的 file_operations 綁到一個 cdev 物件(cdev 是字元裝置的核心結構)。 3. cdev_add:把這個 cdev 註冊到剛要到的裝置號——此後對該裝置號的所有操作,都會走你的 file_operations。

卸載時要反序清理(資源配對,回顧 P0-T06/P3-T15):cdev_del(移除 cdev)→ unregister_chrdev_region(還裝置號)。常見誤區:裝置號未釋放、cdev 未清除導致洩漏——init 配的,exit 都要對應釋放。

4. file_operations:你提供的 callback

file_operations 是一個裝滿函式指標的 struct(正是 P0-T07 的 ops 結構),你填入要實作的操作:

static struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,       // user open() 時
    .read    = my_read,       // user read() 時
    .write   = my_write,      // user write() 時
    .release = my_release,    // user close() 時(最後一個 fd 關閉)
    // .unlocked_ioctl = my_ioctl,  // P4-T03
    // .mmap = my_mmap,             // P4-T03
};

    FOPS2["struct file_operations(一組 callback,P0-T07)"]
    FOPS2 --> OPEN["open:準備(常配置 per-open 狀態)"]
    FOPS2 --> READ["read(file, user_buf, count, offset):
把資料給 user → 用 copy_to_user(第5節)
回傳『實際讀了幾 bytes』"]
    FOPS2 --> WRITE["write(file, user_buf, count, offset):
從 user 取資料 → 用 copy_from_user(第5節)
回傳『實際寫了幾 bytes』"]
    FOPS2 --> RELEASE["release:清理(對應 open 配的)"]
    style FOPS2 fill:#e8a33d,color:#10100e
    style READ fill:#6fa8b8,color:#10100e
    style WRITE fill:#8a9a5b,color:#10100e

幾個關鍵 callback: - open:user open() 時呼叫,做準備。 - read(file, user_buf, count, offset):user read() 時呼叫——你要把資料透過 copy_to_user 放到 user_buf(第 5 節),回傳實際讀了幾 bytes。 - write(file, user_buf, count, offset):user write() 時呼叫——你要透過 copy_from_user 從 user_buf 取資料(第 5 節),回傳實際寫了幾 bytes。 - release:最後一個 fd 關閉時呼叫,清理。

注意 read/write 的 user_buf 是使用者態的指標——這是第 5 節命門的核心:你不能直接解參考它。

5. 命門:copy_to_user / copy_from_user

這是這一課最重要、最關乎安全的部分。read/write 的 user_buf 指向使用者態位址空間的記憶體——而你的 module 在核心位址空間(回顧 P1-T06 兩者隔離)。

flowchart TB
    PROBLEM2["read/write 收到 user_buf(使用者態指標)
你想把資料搬進/搬出它"]
    PROBLEM2 --> WRONG2["✗ 直接解參考:*user_buf = x; 或 x = *user_buf;"]
    WRONG2 --> DANGER2["★ 災難 ★
① user 指標在另一個位址空間(P1-T06),
核心直接解參考它 → 可能存取非法位址 → 當機
② 安全漏洞:惡意 user 傳一個指向『核心記憶體』的指標,
若你直接解參考,等於讓 user 讀寫核心記憶體!"]
    PROBLEM2 --> RIGHT2["✓ 用 copy_from_user(kbuf, user_buf, n)
/ copy_to_user(user_buf, kbuf, n)"]
    RIGHT2 --> SAFE2["這些函式安全地:
① 驗證 user 指標真的屬於該行程的合法 user 空間
② 安全地跨越邊界搬資料
③ 回傳『沒搬成的 bytes 數』(0 = 全部成功)"]
    style WRONG2 fill:#c2603a,color:#f4ecd8
    style DANGER2 fill:#c2603a,color:#f4ecd8
    style RIGHT2 fill:#8a9a5b,color:#10100e

鐵則:絕不直接解參考使用者態指標,一律用 copy_from_user/copy_to_user。 為什麼(常見誤區:直接解參考 user 指標): - 正確性/當機:user 指標在另一個位址空間(P1-T06),核心直接解參考它可能存取非法位址 → 當機。 - 安全漏洞:這更嚴重。惡意的 user 程式可以傳一個指向核心記憶體的「user 指標」——如果你直接解參考它去讀/寫,就等於讓 user 程式讀寫核心記憶體(任意讀核心機密、或竄改核心)。copy_*_user 會驗證那個指標真的屬於該行程的合法使用者空間,擋掉這種攻擊。

copy_from_user(kbuf, user_buf, n)(從 user 搬到核心)和 copy_to_user(user_buf, kbuf, n)(從核心搬到 user)安全地:驗證指標、跨邊界搬資料、回傳「沒搬成的 bytes 數」(0 代表全部成功——要檢查回傳)。

第二個關鍵(常見誤區:忘了 copy_*_user 可能睡眠):copy_*_user 可能睡眠!因為 user 的那塊記憶體可能被換出(paging),存取時可能觸發缺頁、需要等待(回顧 P1-T06 缺頁、P3-T07 睡眠)。所以不可在持有 spinlock 時呼叫 copy_*_user(持 spinlock 不可睡眠,回顧 P3-T08 的鐵則)——這把 P3-T08 的規則具體化了。要搬資料,在沒持 spinlock 的地方做(或先 copy 到核心緩衝區再進臨界區)。

(驗收點:正確使用 copy_from_user/copy_to_user 且能解釋為何不可直接解參考 user 指標。)

  • 建 /dev 節點:用 class_create + device_create(回顧 P4-T01 的 device_create/uevent/udev)。device_create 發出 uevent,udev 收到後自動在 /dev 建出節點(如 /dev/mydev)——你不必手動 mknod。

一句話總結:字元裝置讓 user 用 open/read/write 操作 /dev 節點來跟你的 module 溝通——你註冊裝置號(alloc_chrdev_region)、把 file_operations 綁到 cdev(cdev_init/cdev_add)、用 device_create 讓 udev 建出 /dev 節點;最關鍵的鐵則是 read/write 收到的 user 指標絕不直接解參考(否則當機或安全漏洞),一律用 copy_to/from_user,而它們可能睡眠故不可在持 spinlock 時呼叫。這是你產品 user app 與 module 溝通的基礎。

常見誤區與踩雷提醒

誤區一(最關鍵,安全):直接解參考使用者態指標。 read/write 的 user 指標在另一個位址空間(P1-T06),直接解參考會當機;更嚴重的是惡意 user 可傳指向核心記憶體的指標,直接解參考等於讓 user 讀寫核心。一律用 copy_from_user/copy_to_user(它們會驗證指標合法性)。

誤區二:忘了 copy_*_user 可能睡眠。 user 記憶體可能被換出,存取觸發缺頁而睡眠。不可在持 spinlock 時呼叫(持 spinlock 不可睡眠,P3-T08)。在沒持鎖處搬,或先 copy 到核心緩衝區再進臨界區。

誤區三:裝置號未釋放、cdev 未清除導致洩漏。 init 配的(裝置號、cdev、class、device、緩衝區),exit 都要反序釋放(資源配對,P0-T06/P3-T15)。

誤區四:LDD3 的 ioctl(舊)應改為 unlocked_ioctl。 LDD3 的 ioctl callback 簽名已過時,現代用 unlocked_ioctl(P4-T03)。舊書看概念、API 對照現況。

動手實作

環境:QEMU 虛擬機。所有 insmod/裝置測試只在 VM。

任務 A — 「核心內緩衝區」字元裝置(驗收點) 寫一個字元裝置 module: - 註冊三步:alloc_chrdev_region → cdev_init(綁你的 file_operations)→ cdev_add。 - file_operations:實作 write(用 copy_from_user 把 user 寫的資料存進 module 裡的核心緩衝區)、read(用 copy_to_user 把緩衝區內容給 user)。 - 用 class_create + device_create 讓 udev 在 /dev 建出 /dev/mydev。 測試:echo "hi" > /dev/mydev,再 cat /dev/mydev。驗收:cat 讀回 "hi"。 也可寫一個小 C 程式 open/write/read 測試。

任務 B — 卸載清理驗證(驗收點) 卸載 module(rmmod),確認:/dev/mydev 節點消失、裝置號釋放(可看 /proc/devices 不再有你的 major)。驗收:卸載後裝置號/節點正確清除。 確認 exit 反序釋放了所有資源。

任務 C — copy_*_user 與安全(驗收點) 在你的 read/write 裡正確使用 copy_to_user/copy_from_user(檢查回傳值)。寫一段文字說明:為什麼不能直接解參考 user 指標(*user_buf)?(提示:位址空間隔離 → 當機;惡意指標 → 安全漏洞。)驗收:正確用 copy_*_user 且能解釋為何不可直接解參考。

任務 D(連結)— 為什麼 copy_*_user 不可在持 spinlock 時呼叫 寫一兩句話:copy_*_user 可能睡眠,所以不可在持 spinlock 時呼叫——這連結到 P3-T08 的什麼規則?(提示:持 spinlock 不可睡眠,否則死結。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ echo "hi" > /dev/mydev 後 cat /dev/mydev 讀回 "hi"。 2. ☐ 卸載 module 後裝置號/節點正確清除。 3. ☐ 正確使用 copy_from_user/copy_to_user 且能解釋為何不可直接解參考 user 指標。

評分量表: - 60(及格):能讀寫字元裝置。 - 80(熟練):能正確處理 user 指標與資源釋放。 - 100(精通):能解釋 copy_*_user 的安全與睡眠語意並實作 ioctl。

延伸與銜接

  • 對應工作場景:直接對應——你產品的 user space app 很可能透過字元裝置 + ioctl/mmap 與自寫 module 溝通(設定佇列、提交工作)。
  • 這課餵給未來的:字元裝置 + file_operations → P4-T03 在它上面加 ioctl(控制)和 mmap(零拷貝資料面);copy_*_user → 你所有 user/kernel 資料交換;copy_*_user 可能睡眠 → 回收 P3-T08 持鎖規則。
  • 下一步 → P4-T03 ioctl 與 mmap(user/kernel 控制與零拷貝資料面):你的字元裝置能用 read/write 搬資料了。下一課加兩個更強的介面:unlocked_ioctl(下達控制命令——查詢/設定參數,如佇列大小,用 _IOR/_IOW 編碼命令)和 mmap(把核心緩衝區直接映射到 user 空間,達成零拷貝——user 直接讀寫那塊記憶體,不必 copy)。這正是你產品架構的縮影:控制面用 ioctl、資料面用 mmap + DMA。mmap 的零拷貝概念也會銜接 P6 的 DMA/GDS。
