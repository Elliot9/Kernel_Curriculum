P6-T03 · DMA 屏障與按門鈴(doorbell)的正確順序

一句話:這是 DMA 正確性最易出錯之處——你 P3-T11 學的「描述子必須在按門鈴前對裝置可見」,在這裡變成具體的 dma_wmb():填描述子 → dma_wmb() → writel(門鈴)。漏一個屏障,裝置先看到門鈴、後看到描述子,讀到半寫的垃圾 → 間歇性資料毀損,且極難重現。

為什麼要先學這個(導讀)

P6-T02 你會把資料映射給裝置 DMA 了。但「映射好了」不代表「裝置會在對的時間看到對的資料」——這一課講 DMA 的可見性順序,是 DMA 正確性最易出錯、後果最隱蔽的地方。

這一課把你 P3-T11 建立的「記憶體屏障命門」,落實成 DMA 的具體工具。回顧 P3-T11 的命門:DMA 描述子必須在按 doorbell 前對裝置可見,否則裝置讀到還沒寫好的描述子 → 資料毀損。P5-T05 你看到 NVMe 提交流程裡有這個屏障。現在這一課深入它的實作:

  • dma_wmb() / dma_rmb():針對「一致性記憶體與裝置」的順序屏障——確保屏障前的記憶體寫入,在屏障後的操作之前對裝置可見。
  • MMIO 寫入(writel/writeq)與屏障的關係:按門鈴是一次 MMIO 寫入;你要確保「描述子的 DRAM 寫入」先於「門鈴的 MMIO 寫入」對裝置可見。
  • 正確的提交順序:填描述子 → dma_wmb() → writel(門鈴)。
  • 完成端的順序:處理 completion 時,先確認 phase bit 再讀完成項內容(回顧 P5-T05 phase bit)。

為什麼這對你是 scope: direct?因為這正是你產品提交 NVMe 命令、處理完成項時的正確性核心。漏一個屏障,就可能間歇性資料毀損,而且極難重現(只在特定時序下發生)。對儲存產品,資料毀損是最嚴重的 bug——這一課是防它的關鍵。

開始之前(前置確認)

  • 依賴:P6-T02(DMA 映射、裝置存取記憶體)、P3-T11(memory barrier/LKMM——這課是它的 DMA 實作)。也用到 P5-T05(NVMe doorbell、phase bit、提交流程)、P4-T04(MMIO/writel)。
  • 自我檢測: 1. 你還記得 P3-T11 的命門「描述子必須在按 doorbell 前對裝置可見,否則資料毀損」嗎?這課是它的具體實作(dma_wmb)。 2. 你還記得 P5-T05 NVMe 提交流程裡「寫命令進 SQ → 屏障 → 寫 doorbell」嗎?這課講那個屏障到底是什麼、為什麼。
  • 心態:這課和 P3-T11 一樣關乎「看不見的順序」,但更具體、更貼近你的程式碼。
  • 環境:QEMU 虛擬機(概念性或模擬裝置上的提交流程,只在 VM)。

問題(回顧 P3-T11):你依序做兩件事——①填描述子(寫 DRAM)、②按門鈴(寫裝置 MMIO)。但裝置看到這兩個寫入的順序,未必和你寫的一樣(CPU 寫入緩衝、記憶體系統、匯流排可能讓門鈴的寫入先傳播到裝置)。

災難情境:裝置先看到門鈴 → 以為有新命令 → 去讀 SQ → 但描述子的寫入還沒到 → 讀到半寫的垃圾命令 → 執行錯誤 I/O → 資料毀損。

解法:在兩個寫入之間插屏障,強制「描述子寫入」先於「門鈴寫入」對裝置可見。這一課就是講「用哪個屏障、怎麼插」。

2. dma_wmb / dma_rmb:對裝置的順序屏障

針對「記憶體寫入對裝置的可見順序」,kernel 提供專門的屏障:dma_wmb()(寫)和 dma_rmb()(讀)。

兩個 DMA 屏障: - dma_wmb()(DMA 寫屏障):確保屏障前的記憶體寫入,在屏障後的寫入之前,對裝置可見。用於「填描述子 → 按門鈴」之間。 - dma_rmb()(DMA 讀屏障):確保屏障前的讀,在屏障後的讀之前完成。用於完成端(先確認 phase bit、再讀完成項內容,第 6 節)。

對象:這些屏障針對一致性記憶體(coherent)與裝置之間的順序——這正是 NVMe SQ/CQ(用 coherent 映射,P6-T01)與裝置之間的場景。它們比一般 CPU↔CPU 的 smp_* 屏障更貼合「CPU↔裝置」(下一節解釋差異)。

這兩個就是你 P3-T11 命門的實作工具——那條「描述子必須在按 doorbell 前對裝置可見」的規則,落實成在描述子寫入和門鈴之間插 dma_wmb()。

3. 為何不能用 smp_wmb 取代 dma_wmb

一個常見錯誤:用 P3-T11 學的 smp_wmb() 來代替 dma_wmb()。它們語意對象不同。

→ 在單核編譯時可能退化(因為沒有別的 CPU)"]
    DMAWMB2["dma_wmb()(本課):
確保寫入順序對『裝置』可見
→ 對象:CPU ↔ 裝置(透過 DMA/記憶體)
→ 處理 CPU 寫入緩衝對裝置的可見順序"]
    SMPWMB --> DIFF["★ 差異:對象不同 ★
smp_wmb 管『別的 CPU 看到的順序』
dma_wmb 管『裝置看到的順序』

差異(常見誤區:用一般 smp_wmb 取代 dma_wmb,語意對象不同): - smp_wmb()(P3-T11):確保寫入順序對其他 CPU 可見——對象是 CPU ↔ CPU(多核心之間)。單核編譯時可能退化。 - dma_wmb()(本課):確保寫入順序對裝置可見——對象是 CPU ↔ 裝置(透過 DMA/記憶體),處理 CPU 寫入緩衝對裝置的可見順序。

關鍵:對象不同。smp_wmb 管「別的 CPU 看到的順序」,dma_wmb 管「裝置看到的順序」。在某些架構上,smp_wmb 對「裝置可見性」的保證可能不足。DMA 場景要用語意正確的 dma_wmb(對象是裝置)。

這呼應 P3-T11 的精神:屏障要選「對象正確」的——CPU 之間用 smp_*,裝置之間用 dma_*。用錯對象的屏障,可能在你測試的架構上「剛好沒事」,但在別的架構上出間歇性毀損。對你產品(跨平台部署),用對屏障至關重要。

兩種寫入: - 描述子寫入:寫到 DRAM(一般記憶體,如 SQ)。 - 門鈴寫入:寫到裝置的 MMIO 暫存器(BAR 裡,P4-T04,用 writel)。

問題:這兩種寫入經過不同路徑——「裝置看到 DRAM 寫入」和「裝置收到 MMIO 寫入」的相對順序不保證(除非有屏障)。

正確做法:writel(門鈴) 之前要有 dma_wmb(),確保描述子的 DRAM 寫入,先於門鈴的 MMIO 寫入對裝置可見。

常見誤區:以為 MMIO 寫入自動有序——writel 之間通常有序,但「writel 相對於 DRAM 寫入」的順序需要 dma_wmb 保證。別假設自動正確。

(細節:Linux 的 writel 在某些架構有內建的排序保證,但「相對於前面的 DRAM 寫入」的可見順序,標準做法仍是顯式 dma_wmb()。寫可攜的驅動,顯式插屏障最安全。)

這正是你產品提交 NVMe 命令的核心程式碼。你把 I/O 變成命令、填進 SQ、按門鈴——這中間的 dma_wmb() 絕不能漏。

完成端的順序(驗收點:說明處理 completion 時為何要先讀 phase bit): 1. 先讀 phase bit,判斷是不是新完成項(P5-T05)。 2. dma_rmb():屏障——確保「讀 phase bit」先於「讀完成項其餘內容」。 3. 確認是新完成項後,才讀其餘欄位(哪個命令完成、狀態)。

為何要這個順序(常見誤區:completion 未先檢查 phase bit 就讀內容):若不保證「先讀 phase bit、後讀內容」,可能在 phase bit 還沒翻轉(完成項還沒寫好)時,就讀了內容 → 讀到舊的/半寫的完成項 → 處理錯誤的完成。

這是提交端的對稱:提交端用 dma_wmb 確保「描述子先於門鈴可見」;完成端用 dma_rmb 確保「phase bit 先於內容讀取」。兩側都是「確認/通知」和「資料」之間的順序——提交端是「資料先於通知」、完成端是「通知(phase bit)先於資料讀取」。你產品處理 NVMe 完成時,這個 dma_rmb 順序同樣不能漏。

一句話總結:這是 DMA 正確性最易出錯處——P3-T11 的「描述子必須在按門鈴前對裝置可見」落實成 dma_wmb():提交順序是「填描述子 → dma_wmb() → writel(門鈴)」（不能用 smp_wmb 代替，對象是裝置不是 CPU；MMIO 相對 DRAM 的順序需屏障保證）；完成端對稱地用 dma_rmb() 確保「讀 phase bit → 讀完成項內容」。漏一個屏障，裝置讀到半寫命令/完成項 → 間歇性資料毀損且極難重現，對儲存產品是最嚴重的 bug。

常見誤區與踩雷提醒

誤區一(最嚴重):省略描述子與門鈴之間的屏障。 裝置先看到門鈴、後看到描述子 → 讀到舊/半寫資料 → 資料毀損(間歇、極難重現)。填描述子和按門鈴之間必須 dma_wmb()。

誤區二:用一般 smp_wmb 取代 dma_wmb。 語意對象不同——smp_wmb 管 CPU↔CPU,dma_wmb 管 CPU↔裝置。DMA 場景用 dma_wmb(在某些架構上 smp_wmb 對裝置可見性保證不足)。

誤區三:completion 未先檢查 phase bit 就讀內容。 可能讀到還沒寫好的完成項。先讀 phase bit → dma_rmb() → 再讀內容。

誤區四:以為 MMIO 寫入自動有序。 writel 之間通常有序,但「writel 相對於前面的 DRAM 寫入」的順序需要 dma_wmb 保證。別假設自動正確。

動手實作

環境:QEMU 虛擬機(概念性或模擬裝置上的提交流程,只在 VM)。

任務 A — 寫出正確的提交順序(驗收點,核心) 寫出(或在模擬裝置的提交流程裡實作)正確的順序:填描述子 → dma_wmb() → writel(門鈴)。對每一步寫一句說明它的作用。驗收:正確寫出順序並解釋每一步(填描述子=準備命令;dma_wmb=確保描述子先於門鈴對裝置可見;writel=按門鈴通知)。

任務 B — 說明省略屏障的後果(驗收點,核心) 用文字說明:如果省略 dma_wmb(),可能發生什麼具體的資料毀損情境?驗收:說明(裝置先收到門鈴、去讀 SQ,但描述子還沒寫好/還沒可見 → 讀到半寫的命令 → 執行錯誤 I/O → 資料毀損;且間歇、極難重現)。

任務 C — 完成端的 phase bit 順序(驗收點) 寫一段話:處理 completion 時,為什麼要先讀 phase bit(再 dma_rmb()、再讀內容)?驗收:說明(若不保證先讀 phase bit,可能在完成項還沒寫好時就讀內容 → 讀到舊/半寫的完成項)。

任務 D(連結)— 對應你的產品 寫一兩句話:你產品提交 NVMe 命令、處理完成項時,這些屏障各在哪裡?漏掉的後果為何對儲存產品特別嚴重?(提示:提交端 dma_wmb、完成端 dma_rmb;漏掉 = 間歇性資料毀損,難重現難 debug。)
