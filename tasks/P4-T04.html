P4-T04 · PCI 子系統(pci_driver / BAR / config space / MSI-X)

一句話:你的 NVMe SSD 和 GPU 都是 PCIe 裝置——它們的驅動共同建立在 PCI 子系統上:用 pci_driver 的 id_table 讓 bus 認領裝置、map BAR 拿到裝置的暫存器(NVMe 的 doorbell 就在這)、設定 MSI-X 中斷、並用 pci_set_master 致能 DMA(漏掉它,DMA 就不動)。

🚪 這是 Phase 4 出關門檻

這是 Phase 4 的關卡(gate)。本 task 達 80 分——能寫出 PCI 驅動骨架(map BAR + MSI-X)——才算掌握了裝置驅動的硬體端基礎,方可進入 Phase 5(block layer / NVMe)。

為什麼設這道關?因為 PCI 子系統是你產品核心硬體的共同基礎:NVMe 控制器和 GPU 都是 PCIe 裝置。Phase 5 的 NVMe 驅動正是建立在 pci_driver + BAR(doorbell)+ MSI-X 之上,Phase 6 的 P2PDMA 也牽涉 BAR。如果你不懂 PCI 驅動怎麼列舉裝置、怎麼拿到裝置的暫存器、怎麼設中斷、怎麼致能 DMA,你就讀不懂也寫不了 NVMe 驅動。這道關確保你有這個基礎。

為什麼要先學這個(導讀)

前三課(P4-T01/P4-T02/P4-T03)偏「裝置的 user 介面」。這一課轉向硬體端——PCI 子系統,你 NVMe SSD 和 GPU 的共同基礎。

PCI/PCIe 是現代電腦連接高速裝置(NVMe SSD、GPU、網卡)的主要匯流排。PCI 裝置有一套標準化的方式被列舉、設定、操作,而 Linux 的 PCI 子系統把這些封裝成一組 API。一個 PCI 驅動(pci_driver)的核心工作:

  • 列舉與 config space:每個 PCI 裝置有一塊標準的 config space(設定空間),記錄它的身份(vendor/device ID)和能力。系統開機列舉 PCI 匯流排,讀每個裝置的 config space。
  • pci_driver:你的驅動,用一個 id_table 聲明「我能認領哪些 vendor/device ID 的裝置」(回顧 P4-T01 的 match——PCI 的 match 就是比對這個 id_table)。probe 時拿到裝置。
  • BAR(Base Address Register):裝置把它的暫存器和記憶體透過 BAR 暴露出來。你 map BAR(pci_iomap/ioremap)拿到一個能存取裝置暫存器的位址。NVMe 的 doorbell 暫存器就在 BAR 裡(回顧 P3-T11 的 doorbell)。
  • MSI/MSI-X 中斷:現代 PCI 裝置用 MSI-X(訊息式中斷)通知 CPU。你用 pci_alloc_irq_vectors 配置中斷向量、註冊 handler(回顧 P3-T10 中斷)。
  • pci_set_master:致能裝置當 bus master(讓它能主動發起 DMA)。漏掉它,裝置的 DMA 就不動——這是最經典的 PCI 驅動 bug。

為什麼這對你是 scope: direct?如上所述——NVMe 和 GPU 都是 PCIe,你產品的驅動建立在這些之上。這一課是 P5 NVMe 驅動的直接基礎。

(書本:這階段 PCI 章節在 Madieu《Mastering Linux Device Driver Development》(9781789342048)Ch.11「Writing PCI Device Drivers」——不是只含字元驅動的 2e。)

核心內容

拆成這幾節:(1) PCI 列舉與 config space → (2) pci_driver 與 id_table → (3) probe:enable + request_regions → (4) BAR:map 裝置暫存器 → (5) MSI-X 中斷 → (6) pci_set_master:致能 DMA,最後打通關。

1. PCI 列舉與 config space

每個 PCI 裝置有一塊標準化的 config space(設定空間)——一塊小小的、格式固定的暫存器區,記錄裝置的身份與能力。系統開機時列舉(enumerate) PCI 匯流排,讀每個裝置的 config space 來認識它們。

config space 記錄:vendor ID(廠商,如 Intel、NVIDIA)、device ID(裝置型號)、class(類別:儲存/顯示/網路)、BAR(裝置暴露的記憶體區域的位址與大小)、中斷能力等。列舉時讀這些,把裝置註冊成 struct device(P4-T01)掛到 PCI bus 上。

存取 config space 用專門的 API:pci_read_config_word/pci_read_config_dword 等。重要(常見誤區:混淆 config space 存取與 BAR MMIO 存取):config space 是「裝置的設定區」,用 pci_read_config_* 存取;BAR 指向的是「裝置的功能暫存器/記憶體」(第 4 節),用 MMIO(記憶體映射 I/O)存取。兩者是不同的東西、用不同的方式存取,別搞混。

2. pci_driver 與 id_table

你的 PCI 驅動是一個 pci_driver 結構。它最關鍵的部分是 id_table——聲明「我能認領哪些 PCI 裝置」(這就是 P4-T01 match 的依據):

static const struct pci_device_id my_ids[] = {
    { PCI_DEVICE(MY_VENDOR_ID, MY_DEVICE_ID) },   // 我認領這個 vendor+device
    { 0, }   // 結尾
};
MODULE_DEVICE_TABLE(pci, my_ids);

static struct pci_driver my_driver = {
    .name     = "my_pci_drv",
    .id_table = my_ids,        // ← match 依據
    .probe    = my_probe,      // match 成功時呼叫
    .remove   = my_remove,     // 移除時呼叫
};

機制(呼應 P4-T01):你用 pci_register_driver 註冊驅動 → PCI bus 把每個裝置的 vendor/device ID 和各 driver 的 id_table 比對(match)→ match 成功就呼叫你的 probe(pci_dev),給你一個 struct pci_dev(代表那個 PCI 裝置)。MODULE_DEVICE_TABLE 讓系統知道你的驅動支援哪些裝置(用於自動載入)。

接下來所有對裝置的操作,都在 probe 裡用那個 pci_dev 進行。

3. probe:enable device + request_regions

probe 裡的第一批工作:致能裝置、佔用它的資源區域。順序很重要:

flowchart TB
    PROBE3["my_probe(pci_dev) 開始"]
    PROBE3 --> ENABLE["① pci_enable_device(pci_dev)
致能這個 PCI 裝置(喚醒它、讓它能回應)"]
    ENABLE --> REQUEST["② pci_request_regions(pci_dev, "mydrv")
佔用(reserve)裝置的 BAR 區域
(宣告『這些區域歸我用』,避免別人搶)"]
    REQUEST --> NEXT2["③ 接著 map BAR(第4節)、設 MSI-X(第5節)、
pci_set_master(第6節)..."]
    NEXT2 --> ERROR["★ 錯誤路徑(P3-T15 配對)★
任一步失敗,要把『前面成功的步驟』反序釋放
(否則資源洩漏)→ 用 goto 錯誤處理鏈是常見寫法"]
    style ENABLE fill:#6fa8b8,color:#10100e
    style REQUEST fill:#8a9a5b,color:#10100e
    style ERROR fill:#c2603a,color:#f4ecd8

順序: 1. pci_enable_device:致能裝置(喚醒它,讓它能回應存取)。 2. pci_request_regions:佔用(reserve)BAR 區域——向 kernel 宣告「這些記憶體區域歸我這個驅動用」,避免別的驅動搶用。 3. 接著才 map BAR、設 MSI-X、pci_set_master(後面幾節)。

常見誤區:BAR 未 request_regions 就 ioremap——應該先 pci_request_regions 佔用,再 map。先佔用是「宣告所有權」,避免衝突。

錯誤路徑處理(回顧 P3-T15 的資源配對):probe 裡每一步都可能失敗,任一步失敗,要把前面已成功的步驟反序釋放(否則資源洩漏)。kernel 驅動常用 goto 錯誤處理鏈:每步成功後設好「失敗時跳到哪個清理標籤」,失敗就 goto 過去依序清理。常見誤區:probe 失敗路徑未正確釋放(資源洩漏)——這是 PCI 驅動的常見 bug,KASAN/檢查工具會幫你抓(回顧 P3-T14)。

4. BAR:map 裝置的暫存器

BAR(Base Address Register) 是 PCI 裝置暴露它的暫存器和記憶體的方式。裝置說「我的功能暫存器在這塊記憶體區域」,透過 BAR 告訴系統那塊區域的位址和大小。你 map 它,拿到一個 CPU 能存取的位址。

pci_iomap(pci_dev, bar編號, 大小)

機制: - 裝置透過 BAR 暴露它的暫存器/記憶體區域(一個裝置可有多個 BAR)。 - 你用 pci_iomap(或 ioremap)map 一個 BAR,拿到一個 CPU 可存取的虛擬位址。 - 透過這個位址做 MMIO(記憶體映射 I/O):用 readl/writel 等讀寫裝置暫存器——看起來像讀寫記憶體,實際是在跟裝置溝通。

對你的領域極關鍵:NVMe 的 doorbell 暫存器就在某個 BAR 裡(回顧 P3-T11)。你 writel 到那個 doorbell 位址,就是「按門鈴通知 NVMe 有新工作」——這就是 P3-T11 那個 doorbell 的實際位置。NVMe 的所有控制暫存器(佇列設定等)也都在 BAR 裡。

再次強調(常見誤區):BAR 的 MMIO ≠ config space。config space 用 pci_read_config_*(裝置的設定區);BAR 指向的暫存器用 readl/writel(裝置的功能暫存器)。

5. MSI-X 中斷

裝置怎麼通知 CPU「I/O 完成了」?用中斷(回顧 P3-T10)。現代 PCI 裝置用 MSI-X(Message Signaled Interrupts eXtended)——一種「透過寫一個特殊記憶體位址來發中斷」的機制,比舊的線路中斷(pin-based)更靈活(可以有很多個獨立的中斷向量)。

機制: - pci_alloc_irq_vectors(pci_dev, min, max, PCI_IRQ_MSIX):向 kernel 要 MSI-X 中斷向量,要幾個(min/max,依裝置能力)。 - 拿到 N 個向量。NVMe 常為「每個佇列一個向量」——多核、多佇列(P1-T03/P2-T07)各自有獨立的完成中斷,提升並行。 - 對每個向量註冊 handler(request_irq + pci_irq_vector)——該向量的中斷來時,呼叫你的 handler。 - handler 就是 ISR(上半部,P3-T10):快、不可睡眠,確認中斷、記錄、把重活排 workqueue。

常見誤區:MSI-X 向量數量假設錯誤——不要寫死「一定有 N 個」;要依裝置能力,pci_alloc_irq_vectors 會回傳實際拿到幾個,據此使用。

(驗收點:成功用 pci_alloc_irq_vectors 取得至少 1 個 MSI-X 向量並註冊 handler。)

最後一個——最經典、最容易漏、後果最讓人困惑的:pci_set_master。

為什麼需要:DMA 是「裝置主動讀寫主記憶體」(不經 CPU 搬,P6 的核心)。要這麼做,裝置必須是 bus master——能主動發起匯流排傳輸。pci_set_master(pci_dev) 致能這個能力。

漏掉它的後果(常見誤區,而且是最經典的 PCI 驅動 bug):裝置的 DMA「悄悄地不動」——你把描述子、doorbell 全設好了(P3-T11),一切看起來都對,但裝置發不出 DMA 傳輸,資料就是沒搬,而且沒有明顯的錯誤訊息。這種「一切看似正確、就是不 work」的 bug 極難 debug。所以記住:裝置要 DMA,probe 裡必須 pci_set_master。

(驗收點:說明 pci_set_master 的作用與漏掉它的後果。)

這對你的產品至關重要——NVMe 透過 DMA 搬資料、GPU 透過 DMA 存取(P6/P7),這些都需要 pci_set_master 先致能。

一句話總結:PCI 驅動是 NVMe/GPU 的共同基礎——用 pci_driver 的 id_table 讓 bus match、probe 裡依序 enable device、request_regions、map BAR(用 readl/writel 存取裝置暫存器,NVMe 的 doorbell 就在這)、配 MSI-X 中斷(依裝置能力、註冊 ISR)、並 pci_set_master 致能 DMA(漏掉它 DMA 會悄悄不動);錯誤路徑要反序釋放。P5 的 NVMe 驅動正是建在這之上。

常見誤區與踩雷提醒

誤區一(最經典):忘記 pci_set_master 導致 DMA 不動。 裝置要 DMA 必須是 bus master。漏掉 pci_set_master,裝置發不出 DMA,資料沒搬卻無明顯錯誤——極難 debug。要 DMA 就要 pci_set_master。

誤區二:BAR 未 request_regions 就 ioremap。 應先 pci_request_regions 佔用(宣告所有權、避免衝突),再 map BAR。

誤區三:MSI-X 向量數量假設錯誤。 不要寫死「一定有 N 個」。依裝置能力,pci_alloc_irq_vectors 回傳實際拿到的數量,據此使用。

誤區四:probe 失敗路徑未正確釋放(資源洩漏)。 probe 每步可能失敗,任一步失敗要反序釋放前面成功的步驟(goto 錯誤處理鏈)。回顧 P3-T15 資源配對。

誤區五:混淆 config space 存取與 BAR MMIO 存取。 config space(裝置設定區)用 pci_read_config_*;BAR 指向的功能暫存器用 readl/writel(MMIO)。不同東西、不同存取方式。

動手實作(出關驗收任務)

環境:QEMU 虛擬機(可用內建 PCI 裝置或 pci-testdev)。所有測試只在 VM。 參考 Madieu 9781789342048 Ch.11、https://docs.kernel.org/PCI/pci.html 、https://docs.kernel.org/PCI/msi-howto.html 。

任務(出關門檻):PCI 驅動骨架

寫一個 PCI 驅動骨架,對一個(QEMU 模擬的)PCI 裝置: 1. 定義 pci_driver + id_table(對應你要認領的裝置的 vendor/device ID),pci_register_driver。 2. probe 裡依序:pci_enable_device → pci_request_regions → map BAR(pci_iomap)→ pci_alloc_irq_vectors(MSI-X)→ 註冊 handler → pci_set_master。每步檢查錯誤,用 goto 鏈處理失敗路徑。 3. 印出資訊:在 probe 裡 pci_read_config_* 讀並印出 vendor/device ID 與 BAR 資訊。

驗收檢核點: - (1) PCI driver probe 成功並印出該裝置的 vendor/device ID 與 BAR 資訊(dmesg 可見)。 - (2) 成功用 pci_alloc_irq_vectors 取得至少 1 個 MSI-X 向量並註冊 handler。 - (3) 用文字說明 pci_set_master 的作用與漏掉它的後果。

(remove 裡記得反序釋放:free irq vectors、unmap BAR、release regions、disable device。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ PCI driver probe 成功並印出該裝置的 vendor/device ID 與 BAR 資訊。 2. ☐ 成功用 pci_alloc_irq_vectors 取得至少 1 個 MSI-X 向量並註冊 handler。 3. ☐ 說明 pci_set_master 的作用與漏掉它的後果。

評分量表(出關門檻,需達 80): - 60:能寫出 probe 並 map BAR。 - 80(出關門檻 🚪):能設定 MSI-X 並正確處理錯誤路徑。達此分數方可進入 Phase 5。 - 100:能解釋 PCI 列舉、BAR、MSI-X 如何被 NVMe driver 使用。

延伸與銜接

  • 對應工作場景:直接對應——NVMe 控制器與 GPU 都是 PCIe 裝置;NVMe driver(P5)正是建立在 pci_driver + BAR(doorbell)+ MSI-X 之上;P2PDMA(P6)也牽涉 BAR。
  • 這課餵給未來的:pci_driver/BAR/MSI-X → P5 NVMe 驅動(直接建在其上);BAR 的 doorbell → 回收 P3-T11,用於 P5 提交 I/O;pci_set_master → P6 DMA 的前提;BAR → P6 P2PDMA。
  • 下一步 → P4-T05 平台裝置與 device tree(概覽):你已通過 Phase 4 的硬體端門檻(PCI 驅動)。最後一課是補充視角——platform device 與 device tree(DT),這在嵌入式系統常見。PCI 裝置靠匯流排列舉被發現(系統掃 PCI bus),但很多嵌入式裝置沒有這種自我描述的匯流排,靠 device tree(一份靜態的硬體描述)告訴 kernel「有什麼裝置、在什麼位址、用哪個中斷」。你的核心硬體(NVMe/GPU)走 PCI 而非 DT,所以這課是 scope: indirect——但理解 platform/DT 能補完 device model 的全貌,知道「裝置除了被列舉,還能被靜態描述」。
