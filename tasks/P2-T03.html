P2-T03 · container_of 慣用法

一句話:給你一個「struct 裡某個成員的指標」,container_of 幫你算回「整個 struct 的指標」。它是純粹的編譯期位址運算(零執行成本),卻是讓侵入式串列、所有 ops 結構、幾乎每個 kernel callback 運作的核心魔法。

為什麼要先學這個(導讀)

上一課 P2-T02 留了一個明確的懸念:侵入式串列把 list_head 成員串起來,但你真正想操作的是外層的資料 struct;list_for_each_entry 走訪時,得從「走到的 list_head 成員指標」反推回「外層 struct 指標」。那個反推的魔法,就是 container_of。

但 container_of 遠不只用於串列。它是 kernel 最核心、最普遍的慣用法之一,解決一個反覆出現的問題:kernel 的通用機制(串列、樹、callback、ops 結構)操作的是「通用的小零件」(像 list_head、rb_node、或某個回呼參數),但你的程式碼需要從那個小零件,回到「包含它的、屬於你的完整資料結構」。

最典型的場景是 callback(回顧 P0-T07 的函式指標與 ops 結構):kernel 呼叫你註冊的回呼函式時,往往只傳給你一個「通用結構的指標」(例如一個 bio 指標、或某個內嵌的成員指標)。但你需要的是「我自己的、包含這個通用結構的私有資料」。container_of 就是從前者算回後者的工具。

為什麼這對你是 scope: direct?因為幾乎每個 kernel callback 都靠 container_of 取回私有資料。你寫 driver、寫 module、處理 I/O 完成回呼時,第一行常常就是 container_of——從 kernel 傳來的通用指標,拿回你自己的結構。看不懂它,你連自己 driver 的回呼函式都讀不懂。

開始之前(前置確認)

  • 依賴:P2-T02(你已看到侵入式串列需要「從成員反推外層」),也強烈建議回顧 P0-T04(struct 成員的記憶體佈局、offset)與 P0-T08(巨集)。
  • 自我檢測: 1. 你還記得 P0-T04 裡 struct 的每個成員,在 struct 內部有固定的「偏移量(offset)」嗎?(例如第二個成員從 struct 開頭算起第幾個 byte。)container_of 的全部原理就建立在這個 offset 上。 2. 你還記得 P0-T02 指標就是位址、位址可以做運算嗎?container_of 就是一個位址減法。

核心內容

拆成這幾節:(1) 問題:從成員指標回到外層 → (2) offsetof 回顧 → (3) container_of 的核心:位址減法 → (4) 巨集展開逐段拆解 → (5) 它是編譯期、零成本 → (6) callback 場景:它真正的舞台,最後打通關。

1. 問題:我手上有成員的指標,想要整個 struct 的指標

先把問題畫清楚。假設:

struct my_data {
    int value;                // offset 0
    char name[32];            // offset 4
    struct list_head list;    // offset 36(假設)
};

現在 kernel 的串列走訪給了你一個指標 struct list_head *lp,它指向某個 my_data 裡的 list 成員。你想要的是指向整個那個 my_data 的指標。

直覺答案已經呼之欲出:如果我知道 list 成員在 struct 裡的偏移量(這裡是 36),那麼「struct 的開頭」就是「lp 的位址減去 36」。 這就是 container_of 的全部祕密——一個減法。剩下的就是「怎麼知道那個偏移量」,那是下一節的 offsetof。

2. offsetof:成員在 struct 裡的偏移量

offsetof(type, member) 是一個標準巨集,回答:「在 type 這個 struct 裡,member 這個成員,從 struct 開頭算起,偏移了幾個 byte?」(回顧 P0-T04,這個 offset 由成員順序和對齊規則決定。)

flowchart LR
    OFF["offsetof(struct my_data, list)"]
    OFF --> ANS["回答:list 成員距離 struct 開頭幾 bytes
(以上例 = 36)"]
    HOW["它的經典實作技巧:
假裝 struct 從位址 0 開始,
那麼 &((type*)0)->member 算出的位址,
數值上就等於該成員的偏移量"]
    ANS --> HOW
    style OFF fill:#6fa8b8,color:#10100e
    style HOW fill:#e8a33d,color:#10100e

offsetof 的經典實作很巧妙:它「假裝」有一個 struct 放在位址 0,然後取該成員的位址——因為 struct 從 0 開始,成員的位址數值就剛好等於它的偏移量。(&((type*)0)->member:把 0 當成 type 指標,取 member 的位址。因為起點是 0,得到的位址就是偏移量。)你不需要自己實作它,知道它「給你成員的偏移量」就夠了。

回顧 P0-T04:當時你學過 offsetof 能告訴你成員的偏移,還用它對照 NVMe 命令格式。現在它有了新用途——當 container_of 的基石。

3. container_of 的核心:成員位址 − 偏移量 = struct 開頭

把第 1 節的直覺和第 2 節的 offsetof 組合,就得到 container_of 的核心邏輯:

flowchart TB
    INPUT["輸入:ptr(指向成員)、type(外層 struct 型別)、member(成員名)"]
    STEP1["① 用 offsetof(type, member) 算出成員的偏移量"]
    STEP2["② struct 開頭位址 = ptr 的位址 − 偏移量"]
    STEP3["③ 把這個位址轉型成 (type*) 回傳"]
    INPUT --> STEP1 --> STEP2 --> STEP3
    RESULT["得到:指向整個外層 struct 的指標"]
    STEP3 --> RESULT
    style STEP2 fill:#e8a33d,color:#10100e
    style RESULT fill:#8a9a5b,color:#10100e

用具體數字走一遍(承上例,list 偏移 36): - 你手上 lp = 0x1024(指向某 my_data 的 list 成員)。 - offsetof(struct my_data, list) = 36。 - struct 開頭 = 0x1024 − 36 = 0x1000。 - 轉型成 (struct my_data *)0x1000 回傳。

於是你拿到指向整個 my_data(開頭在 0x1000)的指標,就能存取它的 value、name 等其他欄位了。整個魔法就是一個減法:「成員的位址,減去成員在 struct 裡的偏移,等於 struct 的開頭」。

4. 巨集展開:逐段拆解

kernel 的 container_of 長這樣(簡化版,真實版多了型別檢查,第 4 節末談):

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

逐段拆解(回顧 P0-T08 讀巨集的方法):

    P2["- offsetof(type, member)

特別注意 (char *) 那一步的用意(這是 P0-T02/P0-T03 指標運算知識的應用):指標做減法時,跨距由指標型別決定(回顧 P0-T03:int* 減 1 跳 4 bytes)。我們要減的是「byte 數的偏移量」,所以先把 ptr 轉成 char*(char 是 1 byte),這樣 - offsetof(...) 才是精確地減掉那麼多個 byte。如果不轉成 char*,減法的跨距會錯(會乘以成員型別的大小),算出的位址就完全錯了。

真實版的型別檢查:kernel 的完整 container_of 還用了一個技巧(透過 typeof 等)在編譯期檢查「你傳的 ptr 型別,真的和 type 裡 member 的型別相符嗎?」——如果你不小心傳錯成員或型別,編譯器會警告。這讓 container_of 在「純位址運算」之外,還多了一層型別安全(否則傳錯成員名,算出的位址會完全錯誤卻無聲無息)。你現在知道有這層保護即可。

5. 它是編譯期、零執行成本

一個常見誤解:以為 container_of 有執行期成本(好像它要「查」什麼)。不是。 offsetof 的值在編譯期就確定了(成員偏移是固定的,編譯器算得出來),所以整個 container_of 在執行期就只是一個減法(把指標減去一個編譯期常數)。

    RUNTIME["執行期:
container_of 只剩『指標 − 36』
= 一個減法指令
幾乎零成本"]
    COMPILE --> RUNTIME
    style COMPILE fill:#6fa8b8,color:#10100e
    style RUNTIME fill:#8a9a5b,color:#10100e

這就是為什麼 kernel 能毫無顧忌地到處用 container_of——它不是某種昂貴的「反射」或「查表」,而是一個編譯期就定好的位址偏移,執行時一個減法搞定。把它當成有執行成本的東西去避免,是不必要的誤解。

6. callback 場景:container_of 真正的大舞台

串列走訪只是 container_of 的小用途。它真正無所不在的地方是 callback / ops 結構(回顧 P0-T07 函式指標與 file_operations 那類 ops 表)。

典型模式:你的資料 struct 內嵌一個 kernel 的「通用結構」(像某個 ops 物件、某個節點、某個工作項),你把它註冊給 kernel。當 kernel 回呼你時,它只給你那個通用結構的指標;你用 container_of 從它回到你自己的完整 struct,拿到你的私有資料。

flowchart TB

struct my_driver_data {
  ...你的私有資料...
  struct some_kernel_obj obj; ← 內嵌通用結構
}
把 &data.obj 註冊給 kernel"]
    CALLBACK["kernel 回呼你的函式時,
只傳來 struct some_kernel_obj *obj
(通用結構指標,kernel 不知道你的私有資料)"]
    RECOVER["你的回呼第一行:
struct my_driver_data *data =
  container_of(obj, struct my_driver_data, obj);
→ 拿回你的完整 struct + 私有資料"]
    SETUP --> CALLBACK --> RECOVER
    style CALLBACK fill:#6fa8b8,color:#10100e
    style RECOVER fill:#e8a33d,color:#10100e

這就是 container_of 的核心價值:它讓 kernel 的通用機制(只認通用結構)能和你的特定資料(內嵌那個通用結構)無縫銜接。kernel 處理一個通用的 obj,你透過 container_of 從 obj 回到「擁有這個 obj 的我」。你日後寫 driver 處理 I/O 完成、處理裝置事件時,回呼函式的第一行極可能就是 container_of——從 kernel 給的通用指標(例如 bio、某個 request、某個 work),拿回你的私有結構。看懂這個模式,你就看懂了 kernel callback 的半壁江山。

一句話總結:container_of 用「成員位址 − 成員在 struct 裡的偏移量」算回外層 struct 的開頭——純編譯期定好的位址運算,執行時只是一個減法;它是侵入式串列走訪、以及幾乎每個 kernel callback「從通用結構取回自己私有資料」的核心慣用法。看懂它,你就握住了讀 kernel 程式碼的一把萬用鑰匙。

常見誤區與踩雷提醒

誤區一:傳錯成員名或型別,算出錯誤位址。 container_of(ptr, type, member) 的 member 必須是 ptr 實際指向的那個成員、type 必須是真正的外層型別。傳錯會算出完全錯誤的位址(指到 struct 外或中間),後續存取就是災難。kernel 真實版的型別檢查能擋掉一部分,但仍要自己傳對。

誤區二:以為 container_of 有執行期成本。 它是編譯期定好的偏移,執行時只是「指標減一個常數」,幾乎零成本。別為了「效能」去避免它。

誤區三:對「不是該 struct 成員」的指標套用。 container_of 假設 ptr 真的指向某個 type 裡的 member。若你傳一個不相干的指標,算出的「外層 struct」根本不存在,屬於未定義行為(回顧 P0-T10 UB)。

誤區四:忘記 (char*) 轉型的意義(若自己手寫)。 減法必須以 byte 為單位,所以要先轉 char*(回顧 P0-T03 指標運算跨距)。直接用原型別指標做減法會錯(跨距被乘以型別大小)。

動手實作

環境:Linux 終端機,使用者態,安全,不需 root、不動系統。

任務 A — 自己實作 container_of(驗收點)

#include <stddef.h>   // offsetof
#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

定義一個 struct,內嵌一個成員(例如一個 struct list_head list; 或任何成員),手動取得那個成員的指標,然後用你的 container_of 從成員指標算回外層 struct 指標。

任務 B — 驗證還原正確(驗收點) 承任務 A:在外層 struct 裡放幾個可辨識的欄位(例如 int value = 42; char name[]="hello";),取得內嵌成員的指標後,用 container_of 還原外層指標,然後透過還原的指標讀出 value 和 name,確認讀到的是 42 和 "hello"——證明還原正確(指標真的指回了完整的外層 struct)。

任務 C — 逐段解釋(驗收點) 用你自己的話,逐段解釋你的 container_of 巨集:offsetof(type, member) 算什麼?(char *)(ptr) - ... 為什麼要轉 char*、減法在做什麼?(type *) 最後做什麼?(對照第 3、4 節。)

任務 D — 結合 list_head(連回上一課) 把任務 A 的 struct 改成內嵌 struct list_head list(用 P2-T02 的精簡 list.h),串幾個起來,走訪時手動用 container_of 從每個 list_head* 取回外層 struct(模擬 list_for_each_entry 內部做的事)。寫一句話:這就是 list_for_each_entry 巨集幫你自動做的事,對嗎?
