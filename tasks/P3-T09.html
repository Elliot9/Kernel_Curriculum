P3-T09 · kernel 同步(二)—— atomic、RW lock、seqlock、per-CPU、completion

一句話:不是所有同步都要用鎖。原子型別讓計數免鎖、refcount_t 防引用計數溢位、seqlock 讓讀多寫少時讀者不阻塞、per-CPU 變數用「每核一份」根本消除共享、completion 讓一個執行緒等另一個的完成訊號——各有最省成本的適用場景。

為什麼要先學這個(導讀)

P3-T08 你學了基本的 spinlock/mutex。但「凡共享就加鎖」不總是最好——鎖有成本(取得/釋放、可能阻塞或忙等)。這一課介紹一組進階同步原語,它們在特定場景下比「加一把鎖」更省、更快。

幾個工具: - atomic_t/atomic64_t:原子整數型別(回顧 P1-T10 的原子操作)——對單一整數的加減、讀寫,不用鎖就保證原子。 - refcount_t:專為引用計數設計的原子型別,內建溢位/歸零保護(比裸 atomic_t 更安全)。 - read-write 鎖(rwlock/rwsem):區分讀者和寫者——多個讀者可同時持有(讀不互斥),只有寫者獨佔。適合讀多寫少。 - seqlock:更激進的讀多寫少優化——讀者完全不阻塞寫者(讀者重試,寫者永遠優先)。 - per-CPU 變數:每個 CPU 核心一份自己的資料——根本不共享,就不需要鎖(回顧 P1-T03 per-CPU 避免 false sharing)。 - completion:讓一個執行緒等待另一個執行緒的「完成」訊號(像條件變數的專用版)。

為什麼這對你是 scope: direct?因為這些原語直接對應你的工作:blk-mq 的 per-CPU 軟佇列(每核一隊,回顧 P1-T03/P2-T07)、I/O 物件的引用計數(用 refcount_t,確保物件在還有人用時不被釋放)、等待 DMA/GPU 完成的事件同步(用 completion)。理解它們,你才能寫出高效、正確的並行 I/O 路徑。

開始之前(前置確認)

  • 依賴:P3-T08(spinlock/mutex、context 規則)。也用到 P1-T10(原子操作、memory ordering)、P1-T03(per-CPU 避免 false sharing)、P2-T07(原子位元操作)。
  • 自我檢測: 1. 你還記得 P1-T10 的「原子操作:硬體保證讀-改-寫不可分割」嗎?這課的 atomic_t 就是 kernel 的原子整數。 2. 你還記得 P1-T03 的 per-CPU 變數「每核一份避免共享」嗎?這課講 kernel 怎麼用它。
  • 環境:QEMU 虛擬機。實驗只在 VM。

核心內容

拆成這幾節:(1) atomic_t:免鎖的原子整數 → (2) refcount_t:安全的引用計數 → (3) read-write 鎖 → (4) seqlock:讀者不阻塞寫者 → (5) per-CPU 變數:消除共享 → (6) completion:等待事件,最後打通關。

1. atomic_t:免鎖的原子整數

對「就是想安全地加減一個整數」這種簡單需求,用鎖(spinlock/mutex)是殺雞用牛刀。kernel 提供 atomic_t——原子整數型別,對它的操作由硬體保證原子(回顧 P1-T10):

flowchart TB
    ATOMIC["atomic_t counter;(原子整數)"]
    ATOMIC --> OPS["原子操作(不用鎖,硬體保證):
atomic_inc(&counter) 原子加一
atomic_dec(&counter) 原子減一
atomic_add(n, &counter)
atomic_read(&counter) / atomic_set(...)"]
    OPS --> WHY["比鎖好在:單一整數的加減/讀寫,
免去鎖的取得/釋放開銷,且不會阻塞
(回顧 P1-T10:這就是 atomic_fetch_add 的 kernel 版)"]
    LIMIT["★ 限制:atomic 只保證『單一操作』原子 ★
不能用一個 atomic 保證『多個變數』的一致性"]
    WHY --> LIMIT
    style ATOMIC fill:#6fa8b8,color:#10100e
    style WHY fill:#8a9a5b,color:#10100e
    style LIMIT fill:#c2603a,color:#f4ecd8

atomic_t 適合「單一整數的計數、旗標」這類場景,免鎖、不阻塞。也有原子位元操作(set_bit/test_and_set_bit,回顧 P2-T07)。

關鍵限制(常見誤區):atomic_t 只保證「單一操作」原子,不能保證「多個變數」的一致性。 如果你需要「同時更新兩個變數、且對別人看來是一致的」,單個 atomic_t 做不到——那需要鎖(把兩個更新放進臨界區)。別用 atomic 去保護「多變數的一致狀態」(那是鎖的工作)。

2. refcount_t:安全的引用計數

一個極常見的場景:引用計數(reference counting)——多個地方共用一個物件,用一個計數記錄「現在有幾個人在用」,計數歸零時才釋放。你可能想用 atomic_t 做,但 kernel 提供更安全的 refcount_t:

flowchart TB
    SCENARIO["引用計數:物件被多方共用,
計數=使用者數;歸零才釋放(避免還有人用時就釋放 → use-after-free P0-T06)"]
    SCENARIO --> ATOMIC_WAY["用 atomic_t 做?可以,但有風險:
計數溢位(加爆)、或在歸零後又被加回(use-after-free)
都不會被偵測"]
    SCENARIO --> REFCOUNT["★ 用 refcount_t(專為引用計數設計)★
refcount_inc / refcount_dec_and_test
內建:溢位保護、歸零後不可再加的保護
→ 偵測並阻止引用計數的經典 bug"]
    style ATOMIC_WAY fill:#e8a33d,color:#10100e
    style REFCOUNT fill:#8a9a5b,color:#10100e

refcount_t vs atomic_t(常見誤區:以為兩者等價): - atomic_t 是通用原子整數,不檢查計數的合理性。 - refcount_t 專為引用計數設計,內建溢位保護(計數不會加爆繞回)和歸零後保護(歸零釋放後不能又被加回——那是 use-after-free 的徵兆)。它會偵測並阻止引用計數的經典 bug。

規則:做引用計數,用 refcount_t,不要用裸 atomic_t。 典型用法:refcount_inc(多一個使用者)、refcount_dec_and_test(少一個使用者,並回傳「是否歸零」——歸零就釋放物件)。

連到你的工作:你 I/O 路徑裡的物件(bio、request、緩衝區)常被多方引用,用 refcount_t 管理它們的生命週期,確保「還有人用就不釋放、沒人用才釋放」——避免 use-after-free(回顧 P0-T06)。

把引用計數的生命週期畫成一條時間線:

flowchart LR
    CREATE2["建立物件
refcount = 1(建立者持有)"]
    CREATE2 --> GET2["別處要用 → refcount_inc
(計數上升:2,3,...)"]
    GET2 --> PUT2["用完 → refcount_dec_and_test
(計數下降)"]
    PUT2 --> CHECK4{"歸零了嗎?"}
    CHECK4 -->|"否(還有人用)"| ALIVE["★ 不釋放 ★(避免 use-after-free)"]
    CHECK4 -->|"是(最後一個放手)"| FREE2["真正 kfree / kmem_cache_free"]
    ALIVE --> PUT2

    style FREE2 fill:#e8a33d,color:#10100e

3. read-write 鎖:讀多寫少的優化

一般的 spinlock/mutex 不分讀寫——任何時刻只有一個持有者,即使大家都只是讀。但很多資料是讀多寫少的(大量讀、偶爾寫)。read-write 鎖優化這個:

flowchart TB
    subgraph rwlock["read-write 鎖:區分讀者與寫者"]
        READERS["多個讀者可『同時』持有讀鎖
(讀不會改資料,彼此不衝突)"]
        WRITER["寫者獨佔(寫鎖):
持寫鎖時,其他讀者、寫者都不能進
(寫會改資料,要獨佔)"]
    end
    BENEFIT["好處:讀多寫少時,多個讀者並行 → 比『一律互斥』高效"]
    rwlock --> BENEFIT
    VARIANTS["變體:rwlock(spinlock 版,讀者寫者都忙等)
rwsem(read-write semaphore,可睡眠版)"]
    BENEFIT --> VARIANTS
    style READERS fill:#6fa8b8,color:#10100e
    style WRITER fill:#e8a33d,color:#10100e

核心:多個讀者可同時持有讀鎖(因為讀不改資料、彼此不衝突),但寫者要獨佔(寫會改資料)。讀多寫少時,讀者並行讓效能比「一律互斥」好。

變體:rwlock(spinlock 版,忙等)、rwsem(read-write semaphore,可睡眠版——選 spinlock 版還是 sem 版,看 P3-T08 的 context 規則:會睡眠/長臨界區用 rwsem,短/中斷用 rwlock)。

注意:read-write 鎖不是萬靈丹——它有自己的開銷,且若寫不夠少,優勢不明顯。而下一節的 seqlock 是更激進的讀多寫少方案。

4. seqlock:讀者完全不阻塞寫者

seqlock(sequence lock) 是針對「讀極多、寫極少」的更激進優化。它的特點:讀者完全不阻塞寫者,寫者永遠優先。

flowchart TB
    subgraph seqlock["seqlock:靠一個『序號』運作"]
        WRITE["寫者:寫前序號+1(變奇數),寫後再+1(變偶數)
→ 序號為奇數代表『正在寫』"]
        READ["讀者:讀前記下序號,讀資料,讀後再看序號
① 若序號變了(或為奇數)→ 表示讀的過程中有人寫過 → ★ 重讀 ★
② 若序號沒變且為偶數 → 這次讀是乾淨的,採用"]
    end
    BENEFIT["好處:讀者不上鎖、不阻塞寫者(寫者隨時能寫)
讀者只是『可能重試』
→ 讀極多寫極少時,讀者幾乎零成本"]
    seqlock --> BENEFIT
    LIMIT["★ 不適合寫多場景 ★(寫多 → 讀者一直重試,反而慢)
且讀者讀的資料不能有副作用(因為可能重讀)"]
    BENEFIT --> LIMIT
    style WRITE fill:#e8a33d,color:#10100e
    style READ fill:#6fa8b8,color:#10100e
    style LIMIT fill:#c2603a,color:#f4ecd8

機制:靠一個序號(sequence number)。寫者寫前後各把序號加一(寫期間序號是奇數)。讀者讀前記下序號、讀完再檢查:若序號變了(代表讀的過程中有人寫),就重讀;若沒變,這次讀有效。

好處:讀者不上鎖、不阻塞寫者——寫者隨時能寫,讀者只是「可能要重試」。讀極多寫極少時,讀者幾乎零成本。

限制(常見誤區:seqlock 用在寫多場景):寫多時讀者一直重試,反而慢。且讀者讀的內容不能有副作用(因為可能重讀)。seqlock 適合「讀極多、寫極少、讀內容可重試」的場景(例如系統時間這類頻繁讀、偶爾更新的值)。

(seqlock 與 RCU 是 kernel 兩大「讀者極低成本」技術。RCU 更複雜,P3-T11 與後續會碰到;這裡先建立「讀多寫少有比鎖更省的方案」的概念。)

5. per-CPU 變數:用「每核一份」消除共享

最徹底的「同步」其實是不共享。per-CPU 變數讓每個 CPU 核心有一份自己的資料,各核心只碰自己那份——根本沒有共享,也就不需要鎖(回顧 P1-T03 per-CPU 避免 false sharing)。

flowchart TB
    subgraph percpu["per-CPU 變數:每核一份"]
        CPU0["CPU 0 的那份 counter"]
        CPU1["CPU 1 的那份 counter"]
        CPU2["CPU 2 的那份 counter"]
    end
    USE["各 CPU 只增減『自己那份』
→ 無共享、無 race、無鎖、無 false sharing(P1-T03)
→ 極快"]
    percpu --> USE
    SUM["需要總數時:把所有 CPU 的份『加總』
(這一步要小心,但平時操作免鎖)"]
    USE --> SUM
    PREEMPT["★ 存取時要停搶佔 ★
get_cpu_var/put_cpu_var(或 this_cpu_* 系列)
避免存取到一半被搬到別的 CPU"]
    SUM --> PREEMPT
    style USE fill:#8a9a5b,color:#10100e
    style PREEMPT fill:#e8a33d,color:#10100e

機制:每核一份資料,各核只碰自己的——沒有共享、沒有 race、沒有鎖、沒有 false sharing(回顧 P1-T03),極快。需要全域總數時,把各核的份加總。

注意(常見誤區:per-CPU 存取未停搶佔):存取 per-CPU 變數時要確保「不會存取到一半被搬到別的 CPU」(否則你以為在碰 CPU-0 的份,結果被搬到 CPU-1)。用 get_cpu_var/put_cpu_var(停/恢復搶佔)或 this_cpu_* 系列正確存取。

連到你的工作:blk-mq 的 per-CPU 軟佇列——每個 CPU 核心有自己的 I/O 提交佇列,各核心送 I/O 到自己那隊,不爭搶(回顧 P1-T03/P2-T07 NVMe 多佇列)。這是 per-CPU「以不共享換效能」的典範,也是你產品多核擴展性的關鍵。

6. completion:等待一個事件完成

最後一個原語:completion——讓一個執行緒等待另一個執行緒發出「完成」訊號。這是「等待事件」的專用工具(比手刻條件變數簡單)。

flowchart LR
    subgraph waiter["等待方"]
        W["wait_for_completion(&done)
睡眠等待,直到收到完成訊號"]
    end
    subgraph signaler["發訊方(另一執行緒)"]
        S["...做完某件事...
complete(&done)
發出完成訊號,喚醒等待方"]
    end
    signaler -.“complete 喚醒”.-> waiter
    USE["典型:主執行緒啟動一個非同步工作(如 DMA、GPU 計算),
wait_for_completion 等它做完;
工作完成時(如中斷/回呼)complete() 通知"]
    waiter --> USE
    style W fill:#6fa8b8,color:#10100e
    style S fill:#e8a33d,color:#10100e

機制: - 等待方 wait_for_completion(&done):睡眠等待,直到收到訊號。 - 發訊方 complete(&done):做完某事後發出完成訊號,喚醒等待方。

典型場景:主執行緒啟動一個非同步工作(發起 DMA、提交 GPU 計算),然後 wait_for_completion 等它完成;工作完成時(在中斷處理或回呼裡)呼叫 complete() 通知。這正是你的工作模式——等待 DMA/GPU 完成的事件同步。例如你提交一個 parity 計算給 GPU,用 completion 等它算完。

(completion 是建立在等待佇列上的方便封裝;它讓「啟動非同步工作 → 等待其完成」這個常見模式變得簡潔。)

打通關:把 kernel 同步(二)收攏成一個心智模型

一句話總結:kernel 的進階同步原語各有最省的場景——atomic_t 免鎖計數、refcount_t 安全引用計數(防溢位/歸零)、rwlock/seqlock 優化讀多寫少、per-CPU 用「每核一份」徹底消除共享(blk-mq 軟佇列)、completion 等待事件完成(等 DMA/GPU);它們直接對應你 I/O 路徑的物件生命週期、多核擴展與非同步等待。

常見誤區與踩雷提醒

誤區一:用 atomic_t 保護「多個變數」的一致性。 atomic_t 只保證單一操作原子。多變數的一致狀態要用鎖(把更新放進臨界區)。

誤區二:以為 refcount_t 與 atomic_t 等價。 refcount_t 專為引用計數設計,內建溢位/歸零保護。引用計數用 refcount_t,不用裸 atomic_t。

誤區三:per-CPU 變數存取未停搶佔。 用 get_cpu_var/put_cpu_var 或 this_cpu_*,避免存取到一半被搬到別的 CPU、碰到別核的份。

誤區四:seqlock 用在寫多場景。 seqlock 適合讀極多寫極少;寫多時讀者一直重試反而慢。且讀者讀的內容不能有副作用(可能重讀)。

動手實作

環境:QEMU 虛擬機。實驗只在 VM。

任務 A — refcount_t 引用計數(驗收點) 寫一個 module,用 refcount_t(或先 atomic_t 再改 refcount_t)實作一個物件的引用計數:refcount_inc 增加引用、refcount_dec_and_test 減少並在歸零時釋放物件。多個 kthread 並行增減,驗證:計數正確、歸零時(且僅一次)釋放。驗收:引用計數多執行緒增減後值正確,歸零行為符合預期。

任務 B — per-CPU 變數加總(驗收點) 用 per-CPU 變數(DEFINE_PER_CPU 或動態 alloc_percpu)讓各 CPU 各自累加,最後把所有 CPU 的份加總得到總數。驗證總和正確。驗收:per-CPU 各核累加、最終加總正確。

任務 C — completion 同步(驗收點) 在 module 裡:主執行緒 wait_for_completion 等待,另開一個 kthread 做一段工作後 complete() 發訊。驗證主執行緒正確被喚醒。驗收:用 completion 正確同步兩執行緒。

任務 D — seqlock 適用場景(驗收點) 寫一句話:seqlock 適合什麼樣的讀寫比情境?為什麼不適合寫多?驗收:能說出(讀極多寫極少;寫多會讓讀者一直重試)。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 atomic_t/refcount_t 實作引用計數,多執行緒增減後值正確且歸零行為符合預期。 2. ☐ 用 per-CPU 變數各核累加、最終加總正確。 3. ☐ 用 completion 正確同步兩執行緒。 4. ☐ 說出 seqlock 適合的讀寫比情境。

評分量表: - 60(及格):能用 atomic 與 per-CPU。 - 80(熟練):能正確選用進階原語。 - 100(精通):能解釋 per-CPU/seqlock 如何以「避免共享」換取效能。

延伸與銜接

  • 對應工作場景:直接對應——blk-mq 的 per-CPU 軟佇列、I/O 物件的引用計數(refcount_t)、等待 DMA/GPU 完成的事件同步(completion)都會用到這些原語。
  • 這課餵給未來的:refcount_t → P5 I/O 物件(bio/request)生命週期;per-CPU → blk-mq 軟佇列、P2-T07 sbitmap;completion → P6/P7 等 DMA/GPU 完成;atomic/順序 → P3-T11 memory barrier。
  • 下一步 → P3-T10 中斷與延後工作(hardirq/softirq/tasklet/workqueue/threaded IRQ):你已經會 kernel 的各種同步。下一課回到「中斷」這個 kernel 特有的維度,深入中斷處理的結構:上半部(ISR,快、原子 context)vs 下半部(延後處理);softirq、tasklet(已淘汰)、workqueue(可睡眠、行程 context)、threaded IRQ。核心問題是「哪些能睡眠、哪些不能」。這直接關係你的工作:NVMe I/O 完成中斷後,parity 計算/GPU 提交這些重活(會睡眠)必須延後到可睡眠的 context(workqueue),選錯機制會死結或拖垮中斷延遲。
