P4-T05 · 平台裝置與 device tree(概覽)

一句話:PCI 裝置能「自我介紹」(系統掃匯流排就發現它);但很多嵌入式裝置不能,得靠一份叫 device tree 的靜態描述告訴 kernel「有什麼裝置、在哪個位址、用哪個中斷」。這是裝置被發現的另一種模型——補完你對 device model 的全貌理解。

為什麼要先學這個(導讀)

你已經通過 Phase 4 的硬體端門檻——P4-T04 的 PCI 驅動。這最後一課是個補充視角,讓你的裝置模型理解更完整。

回顧 P4-T01/P4-T04:PCI 裝置怎麼被發現?系統列舉(enumerate) PCI 匯流排——掃描每條 bus,讀每個裝置的 config space,就知道「這裡有個 vendor X、device Y 的裝置」。PCI 裝置能自我描述(透過 config space),所以系統一掃就發現它們。這是一種「動態探索」的模型。

但很多裝置不能自我描述,尤其嵌入式系統(手機、路由器、開發板)上的周邊——一個 I2C 溫度感測器、一個記憶體映射的 UART——它們沒有像 PCI config space 那樣的標準自我介紹機制。系統怎麼知道它們存在、在什麼位址、用哪個中斷?

答案是 device tree(DT,裝置樹):一份靜態的硬體描述檔,在開機時告訴 kernel「這塊板子上有什麼裝置、各在什麼記憶體位址、用哪個中斷號、相容於哪個驅動」。kernel 讀這份描述,就知道要建立哪些裝置、配給哪些驅動。這些「靠 DT/板子描述而非匯流排列舉」的裝置,在 Linux 裡是 platform device,由 platform_driver 驅動。

為什麼這對你是 scope: indirect(間接對應)?因為你的核心硬體(NVMe、GPU)走 PCI,不走 DT——它們能自我描述,靠列舉。所以你日常不太會直接寫 DT/platform 驅動。但理解這個模型能補完 device model 的全貌:你會明白「裝置被發現有兩種方式——動態列舉(PCI)和靜態描述(DT)」,而且某些周邊(板子上的雜項硬體)可能用到 platform/DT。這讓你對 P4-T01 的裝置模型有更完整的圖像。

(書本:Madieu 2e Ch.5 講 Device Tree、Ch.7 講 Platform Devices and Drivers。)

1. 兩種「裝置被發現」的模型

先把核心對比立起來:裝置怎麼被 kernel「發現」?有兩種根本不同的模型。

  • 動態列舉(PCI/USB):裝置能自我描述(PCI 用 config space,P4-T04)。系統掃匯流排,讀到裝置身份,動態發現它們。插上就被發現。
  • 靜態描述(device tree):裝置不能自我描述(很多嵌入式周邊)。靠一份 DT 檔事先寫好「這塊板子上有什麼裝置、在什麼位址、用哪個中斷」,kernel 讀 DT,照著建立裝置。

兩者互補:有自我描述能力的高速裝置(PCI)用列舉;固定在板子上、無自我描述的周邊用 DT。你的 NVMe/GPU 屬於前者(PCI,列舉);DT 主要用於後者(嵌入式周邊)。

DT 還有一個重要好處——同一份 kernel 配不同的 DT,就能跑在不同的板子上:

2. device tree 是什麼

device tree(DT) 是一份描述硬體的資料結構,以樹狀組織,在開機時傳給 kernel。它不是程式碼,而是資料——描述「這個系統有哪些硬體、它們的屬性」。

flowchart TB
    DT["device tree:一份靜態的硬體描述(樹狀資料)"]
    DT --> CONTENT["描述:
有哪些裝置(node)
每個裝置在什麼記憶體位址(reg)
用哪個中斷(interrupts)
相容於哪個驅動(compatible)
其他屬性(時脈、GPIO...)"]
    CONTENT --> FLOW2["開機流程:
bootloader 把編譯好的 DT(.dtb)傳給 kernel
→ kernel 解析 DT
→ 為 DT 描述的每個裝置建立 platform device(第4節)
→ 等對應的 platform_driver 來 match"]
    style DT fill:#6fa8b8,color:#10100e
    style FLOW2 fill:#8a9a5b,color:#10100e

DT 的角色:它把「這塊硬體板子的配置」從 kernel 程式碼裡分離出來,變成一份資料描述。好處:同一份 kernel 可以支援很多不同的板子——只要給不同的 DT,kernel 就知道每塊板子有什麼硬體,不必為每塊板子改 kernel 程式碼(這對 ARM 等有海量不同板子的生態極重要)。

開機流程:bootloader 把編譯好的 DT(.dtb,device tree blob)傳給 kernel → kernel 解析它 → 為 DT 描述的裝置建立 platform device → 等驅動來 match。

3. DT 基本語法:node、reg、interrupts

DT 用一種類似巢狀大括號的語法描述裝置。你不必會寫複雜的 DT,但要讀得懂基本片段——尤其 reg(位址)和 interrupts(中斷)。

uart0: serial@10000000 {
    compatible = "vendor,my-uart";
    reg = <0x10000000 0x1000>;      // 位址 0x10000000,大小 0x1000
    interrupts = <5>;                // 用中斷號 5
};

    NODE --> COMPAT["compatible = "vendor,my-uart"

    NODE --> REG["reg = <0x10000000 0x1000>
★ 裝置的記憶體位址 + 大小 ★
(裝置的暫存器在這個實體位址)"]
    NODE --> IRQ["interrupts = <5>
★ 裝置用哪個中斷號 ★"]

    style COMPAT fill:#e8a33d,color:#10100e
    style REG fill:#6fa8b8,color:#10100e
    style IRQ fill:#8a9a5b,color:#10100e

讀 DT 片段時,認得這幾個關鍵屬性(驗收點:對給定 DT 片段指出 reg 與 interrupt 號): - compatible:相容字串(如 "vendor,my-uart")——用來和驅動 match(第 5 節)。 - reg:裝置的記憶體位址 + 大小(裝置的暫存器在這個實體位址)。例如 <0x10000000 0x1000> 表示位址 0x10000000、大小 0x1000。 - interrupts:裝置用哪個中斷號。 - 其他屬性:時脈、GPIO、自訂參數等。

對照 P4-T04 的 PCI:PCI 裝置的這些資訊(位址 = BAR、中斷 = MSI-X)是從 config space 讀出來的(裝置自己報告);而 DT 裝置的這些資訊是寫在 DT 裡的(人事先描述)。同樣是「位址、中斷」,來源不同——一個動態讀、一個靜態寫。

4. platform device 與 platform_driver

DT 描述的裝置,在 Linux 裡成為 platform device,掛在一條虛擬的 platform bus 上,由 platform_driver 驅動。

flowchart TB
    DT2["DT 描述一個裝置"]
    DT2 --> PDEV["kernel 解析 DT → 建立一個 platform_device
(掛在 platform bus 上,P4-T01 的 bus 概念)"]
    PDEV --> PBUS["platform bus:一條『虛擬匯流排』
(不是實體匯流排,是給『非列舉式裝置』的容身處)"]
    PDRV["你寫 platform_driver:
.driver.of_match_table(聲明相容哪些 compatible 字串)
.probe / .remove"]
    PBUS --> MATCH4["platform bus 的 match:
比對 platform_device 的 compatible(來自 DT)
和 platform_driver 的 of_match_table(第5節)"]
    PDRV --> MATCH4
    MATCH4 --> PROBE5["match 成功 → probe(platform_device)
(在 probe 裡用 platform 資源 API 取得 reg/interrupts)"]
    style PDEV fill:#6fa8b8,color:#10100e
    style MATCH4 fill:#e8a33d,color:#10100e
    style PROBE5 fill:#8a9a5b,color:#10100e

機制(呼應 P4-T01 的裝置模型): - kernel 解析 DT,為每個裝置建立一個 platform_device,掛在 platform bus(一條虛擬匯流排,專門給「非列舉式」的裝置容身)。 - 你寫 platform_driver,用 of_match_table 聲明「我相容哪些 compatible 字串」。 - platform bus 用 match 比對(compatible)→ 成功就呼叫你的 probe(platform_device)。 - 在 probe 裡,用 platform 資源 API 取得 DT 裡寫的 reg(位址)和 interrupts(中斷),然後 map 暫存器、註冊中斷——和 PCI 驅動的 probe 結構類似,只是資源來源是 DT 而非 config space。

這就是 P4-T01 裝置模型的另一個實例:一樣是 device/driver/bus/match/probe,只是這裡的 bus 是 platform bus、match 依據是 compatible 字串、裝置來源是 DT。

5. compatible:DT 與驅動的 match

platform 世界的 match,靠 compatible 字串——DT node 裡的 compatible 和 driver 的 of_match_table 比對。

機制:DT node 的 compatible(如 "vendor,my-uart")和 platform_driver 的 of_match_table 裡的 compatible 字串比對——相符就 match 成功、呼叫 probe;不符就不 match。

常見誤區:DT 與驅動的 compatible 字串不符導致不 match——如果 DT 寫 "vendor,my-uart" 但驅動的 of_match_table 寫成別的(打錯字、版本字串不同),就 match 不上,你的 probe 不會被呼叫(裝置沒有驅動接管)。這完全呼應 P4-T01 的核心規則:probe 需 match 成功才被呼叫——只是 PCI 的 match 比對 vendor/device ID,platform 的 match 比對 compatible 字串。「probe 沒被呼叫」在 platform 世界,最常見原因就是 compatible 字串對不上。

根本差異(驗收點:說明 platform device 與 PCI device 在「如何被發現」上的根本差異):核心在於「誰來描述這個裝置」: - PCI device:裝置自己描述自己(config space)。系統掃匯流排就能動態發現它、讀出它的位址(BAR)、中斷能力。插上就被發現。 - platform device:裝置不會自我描述,靠人事先寫的 device tree 描述它(在哪、用哪個中斷、相容哪個驅動)。kernel 讀 DT 才知道它存在。

兩者的 match→probe 流程(P4-T01)是一樣的(都是 bus 媒合 device 與 driver),差別只在「裝置資訊的來源」——一個是裝置動態自報(PCI),一個是 DT 靜態描述(platform)。

常見誤區:把 platform device 與 PCI device 混為一談——它們是不同的發現模型(列舉 vs DT/板子描述)。你的 NVMe/GPU 是 PCI(列舉);嵌入式周邊常是 platform(DT)。理解這個區別,你對「kernel 如何認識硬體」就有了完整的圖像。

一句話總結:裝置被 kernel 發現有兩種模型——PCI/USB 靠動態列舉(裝置用 config space 自我描述,你的 NVMe/GPU 屬此),嵌入式周邊靠 device tree 靜態描述(一份事先寫好的硬體描述,給 platform_device/platform_driver 用,match 依 compatible 字串);兩者都走 P4-T01 的 match→probe,差別只在裝置資訊來源——裝置自報 vs 人事先寫。理解這個補完了你對 device model 的全貌。

常見誤區與踩雷提醒

誤區一:把 platform device 與 PCI device 混為一談。 它們是不同的發現模型:PCI 靠匯流排列舉(裝置自我描述),platform 靠 DT/板子描述(人事先寫)。你的 NVMe/GPU 是 PCI;嵌入式周邊常是 platform。

誤區二:DT 與驅動的 compatible 字串不符導致不 match。 DT node 的 compatible 和 driver 的 of_match_table 要完全相符才 match。打錯字、版本不符就 match 不上,probe 不被呼叫(呼應 P4-T01:probe 需 match 成功)。

動手實作

環境:閱讀 DT 片段(安全)+ QEMU(若做 platform driver,只在 VM)。

任務 A — 讀 DT 片段(驗收點) 給定一個 DT node 片段(可參考 https://docs.kernel.org/devicetree/usage-model.html 或自己取一個範例),正確指出: - 該裝置的 reg(記憶體位址)是什麼? - 該裝置用的 interrupt 號是什麼? - 它的 compatible 字串是什麼? 驗收:對給定 DT 片段正確指出某裝置的 reg(位址)與 interrupt 號。

任務 B — 最小 platform driver probe(概念性,選做) 寫一個最小的 platform_driver:定義 of_match_table(一個 compatible 字串)、寫 probe(在裡面 pr_info、並嘗試用 platform 資源 API 取得 reg/interrupts)。(在 QEMU 裡若有對應 DT 的虛擬裝置可實測;否則概念性完成即可。)觀察 probe 在 compatible match 時被呼叫。

任務 C — 說明 DT vs PCI 的根本差異(驗收點,核心) 用文字說明:platform device 與 PCI device 在「如何被發現」上的根本差異是什麼?驗收:能說出核心差異(PCI 裝置自我描述、靠匯流排列舉動態發現;platform 裝置不自我描述、靠 device tree 靜態描述)。

任務 D(連結)— 對照 PCI 的 BAR/MSI-X 寫一兩句話:DT 的 reg/interrupts,對應到 PCI 裝置的什麼?(提示:reg ↔ BAR 指向的位址、interrupts ↔ MSI-X;但 PCI 的是從 config space 動態讀,DT 的是人事先寫。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 對給定 DT 片段正確指出某裝置的 reg(位址)與 interrupt 號。 2. ☐ 說明 platform device 與 PCI device 在「如何被發現」上的根本差異。

評分量表: - 60(及格):能讀 DT 片段。 - 80(熟練):能寫最小 platform probe。 - 100(精通):能清楚對比 DT/platform 與 PCI 列舉模型。

延伸與銜接

  • 對應工作場景:間接對應——你的核心硬體(NVMe/GPU)走 PCI 而非 DT,但理解 platform/DT 能補完 device model 全貌,且部分周邊可能用到。
  • 這課收束了:整個 Phase 4——裝置模型(P4-T01)、字元驅動(P4-T02)、ioctl/mmap(P4-T03)、PCI(P4-T04)、platform/DT(本課)。你現在理解「kernel 如何抽象裝置與匯流排、如何發現裝置(列舉 vs DT)、如何寫驅動操作硬體」。
  • 下一步 → P5-T01 進入 Phase 5(Block Layer、儲存堆疊與 NVMe):恭喜你完成 Phase 4——你的 module 現在能跟硬體裝置打交道了!接下來 Phase 5 是你產品的核心領域:深入從 VFS 到裝置的整條儲存堆疊、blk-mq(多佇列區塊層,你 P2-T07 sbitmap、P3-T09 per-CPU 的用武之地)、以及 NVMe 協定與 Linux NVMe 驅動(正是建立在你這課學的 P4-T04 pci_driver + BAR + MSI-X 之上)。你前面所有的鋪墊——資料結構、同步、中斷、DMA 基礎、PCI——都將在這裡匯聚成「讀懂並修改 block layer 與 NVMe 驅動」的能力。(提醒:到 P5/P6/P7 我會重新查證 NVMe/DMA/P2PDMA/GDS 的版本敏感細節。)
