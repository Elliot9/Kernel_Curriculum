P0-T04 · struct、union、bitfield 與記憶體對齊

一句話:struct 的大小,常常不等於成員大小的總和——中間藏著編譯器偷塞的「填充(padding)」。搞懂為什麼,你就懂了硬體為何挑剔記憶體位址,也就能讀懂 NVMe 那種一個 byte 都不能錯的命令格式。

為什麼要先學這個(導讀)

這一課是 Phase 0 裡第一個標記「直接對應你工作」的主題,值得你多花一倍力氣。

你的產品要跟 NVMe 裝置溝通。NVMe 的每一條命令,是一個精確定義的 64-byte 結構:第 0 個 byte 放什麼、第 4 到 7 byte 是哪個欄位,規格書釘死,差一個 byte 裝置就讀錯、就送錯資料。完成項(completion entry)是 16-byte,同樣錙銖必較。這些在 C 裡都是 struct,而且是對齊極度敏感的 struct。

更廣地說,所有「硬體暫存器佈局」「網路封包格式」「磁碟上的 metadata」都是這種 byte 層級精確的結構。要正確操作它們,你必須能在腦中精準推算三件事:

  1. 這個 struct 在記憶體裡實際長什麼樣?
  2. 每個成員落在第幾個 byte(它的 offset)?
  3. 整個 struct 多大?

而這裡藏著一個會讓你算錯的陷阱:C 編譯器會偷偷插入「填充 bytes(padding)」,讓 struct 的實際大小和你天真把成員相加的結果不一樣。不懂這件事,你算出來的每個 offset 都會錯位,你的程式會把資料寫到 NVMe 命令的錯誤欄位——這在儲存系統是災難級的 bug。

這一課就是要把「struct 在記憶體裡到底長怎樣」這件事,從「編譯器的黑魔法」變成「你能用紙筆精準推算的機械流程」。

開始之前(前置確認)

  • 依賴:P0-T03(你已懂陣列是連續記憶體、sizeof 的意義、指標如何走訪)。
  • 自我檢測(若不確定,先補): 1. sizeof(char) 是多少?(永遠是 1,這是 C 的定義) 2. sizeof(int) 在你的機器上是多少?(現代 64 位元系統通常是 4) 3. 你能用 printf("%zu", sizeof(x)) 印出某型別的大小嗎?(這課會一直用到) 4. 「位址」是什麼?(回顧 P0-T02:記憶體每個 byte 有一個編號)

核心內容

這課的核心內容拆成八個小節,由淺到深:(1) struct 是什麼 → (2) 對齊是什麼、為什麼硬體要它 → (3) padding 怎麼來 → (4) 手算 struct 大小的標準流程 → (5) 重排成員省空間 → (6) offsetof → (7) packed 的威力與代價 → (8) union 與 bitfield。每一節都有圖和帶數字的範例。

1. struct:把不同型別的東西打包成一個整體

陣列(P0-T03)的限制是「裡面只能放同一種型別」。但真實世界的資料常常是混合的:一個「點」有 x 和 y(都是 int),一個「使用者」有年齡(int)、名字首字母(char)、帳戶餘額(double)。struct 就是把這些不同型別的東西黏成一個整體的工具。

struct point {
    int x;
    int y;
};

宣告一個 struct 變數、存取成員,用 .:

struct point p;
p.x = 3;
p.y = 4;

關鍵規則:成員在記憶體裡,依「宣告順序」由低位址往高位址排列。 你寫 x 在前、y 在後,記憶體裡就是 x 在低位址、y 在高位址。

這個例子很乾淨:兩個 int 各 4 bytes,排在 offset 0 和 4,總共 8 bytes。sizeof(struct point) 就是 8。但這是因為「剛好對齊」,下一節你會看到不對齊時會發生什麼。

與你熟悉的語言對照:JS 的物件 {x: 3, y: 4} 概念上類似,但 JS 物件在記憶體裡怎麼擺、佔多大,你完全碰不到也不需要知道——引擎全權處理。C 的 struct 則是「你能、也必須」知道它的精確記憶體佈局,因為硬體會直接讀這塊記憶體。

2. 對齊(alignment):硬體的挑剔,以及為什麼

這是整課最核心的觀念,慢慢讀。

CPU 不是一個 byte 一個 byte 讀記憶體的

直覺上你可能以為,CPU 要讀記憶體裡的某個 byte,就直接去那個位址拿那一個 byte。錯。 現代 CPU 為了效率,是一次讀一整塊(一個「字組 word」,常是 4 或 8 bytes,且這塊的起始位址是該大小的倍數)。

打個比方:把記憶體想成一排棧板(pallet),每塊棧板裝 4 個箱子,堆高機(CPU)一次只能搬整塊棧板,不能只抽中間一個箱子。

CPU 得搬棧板 A、再搬棧板 B、丟掉各自不要的部分、把要的兩半拼起來——兩次記憶體存取加上拼接工作,慢得多。更糟的是:有些 CPU 架構(如部分 ARM)根本拒絕做未對齊存取,直接觸發例外(alignment trap)讓程式當掉。

結論:自然對齊規則

所以編譯器訂了一條規矩,叫自然對齊(natural alignment):

型別 大小 起始位址必須是…的倍數
char 1 1(任何位址都行)
short 2 2
int 4 4
long / 指標 / double 8 8

比喻的極限:棧板比喻很好,但別把它想成「記憶體實體上真的被切成棧板」——記憶體本身是平的、連續編號的。所謂「棧板」是 CPU 存取記憶體時的行為模式(它傾向以對齊的區塊為單位讀寫),不是記憶體的物理結構。對齊規則是「為了配合 CPU 這個行為模式而做的安排」,不是記憶體本身有格線。

3. 填充(padding):為了滿足對齊,編譯器偷塞的空白

現在你懂了「每個型別有它的對齊要求」。問題來了:當 struct 裡混著不同型別,要讓每個成員都落在它該對齊的位址上,編譯器就得在成員之間插入沒有用途的 bytes——這就是 padding。

看這個會嚇到人的例子:

struct mixed {
    char  a;    // 1 byte
    int   b;    // 4 bytes
    char  c;    // 1 byte
};

你天真相加:1 + 4 + 1 = 6。但 sizeof(struct mixed) 在標準 64 位元系統上是 12! 多出來的 6 bytes 是哪來的?

4. 手算 struct 大小:一套你能照著走的流程

這是本課最該練到變成反射的技能。給定一個 struct,照下面的步驟,你就能在紙上算出它的精確佈局,不必靠編譯器。

規則只有兩條: - 規則 A(成員對齊):每個成員的起始 offset,必須是「該成員型別大小」的倍數。不夠就往後補 padding,直到對齊。 - 規則 B(整體對齊):整個 struct 的總大小,必須是「struct 中最大對齊需求成員」的倍數。不夠就在尾端補 padding。

規則 B 為什麼存在? 因為你可能會做一個 struct 的陣列。陣列要求每個元素緊鄰排列,所以「下一個元素的開頭」= 前一個元素的開頭 + struct 大小。如果 struct 大小不是最大成員對齊的倍數,那陣列裡第二個、第三個元素的成員就會錯位、不對齊。規則 B 保證「陣列中每一個元素的每個成員都仍然對齊」。

用 struct mixed { char a; int b; char c; } 走一遍:

再練一個(這次自己先算,再看答案):struct demo { char a; short b; int c; double d; };

逐步: - a(char,對齊1):offset 0。游標→1。 - b(short,對齊2):offset 1 不是 2 的倍數 → 補 1 格 padding 到 offset 2。b 佔 2-3。游標→4。 - c(int,對齊4):offset 4 是 4 的倍數 ✓。c 佔 4-7。游標→8。 - d(double,對齊8):offset 8 是 8 的倍數 ✓。d 佔 8-15。游標→16。 - 規則 B:最大成員 double(對齊8),目前大小 16 是 8 的倍數 ✓,不必補。 - 結果:sizeof = 16,只有 1 個 byte 的 padding(在 offset 1)。

看出來了嗎?這個 struct 幾乎沒浪費,因為它的成員「從小排到大」剛好讓對齊自然滿足。這正是下一節的重點。

5. 重排成員順序:同樣的欄位,更小的 struct

既然 padding 是「為了把後面的成員推到對齊位址」而生,那麼成員的排列順序會直接影響 padding 的多寡,進而影響 struct 大小。

回到那個浪費的 struct mixed(12 bytes)。如果把成員從大到小重排:

struct packed_better {
    int   b;    // offset 0-3
    char  a;    // offset 4
    char  c;    // offset 5
    // 規則B:最大成員 int(對齊4),目前大小 6 → 補到 8
};

同樣三個欄位(一個 int、兩個 char),只是換個順序,從 12 bytes 變 8 bytes,省下 1/3。

口訣:把成員「由大到小」宣告,通常能讓 padding 最少。 直覺是:大的先放好(它們對齊要求高、最挑位址),小的(char)塞在縫隙裡。

這對你的工作的真實意義:當你設計一個會被大量複製的結構(例如每個 I/O 都要帶一份的 metadata、或要塞滿一個 buffer 的描述元陣列),省下的每個 byte 都會乘以「複製的次數」。在高吞吐的儲存路徑上,struct 從 12 變 8 可能就是可觀的記憶體頻寬節省。

6. offsetof:讓編譯器告訴你成員在第幾個 byte

手算很重要(你要有能力驗算),但日常寫程式時,C 標準庫提供一個巨集 offsetof,直接告訴你某成員的 offset,不必自己數:

#include <stddef.h>

struct mixed { char a; int b; char c; };

offsetof(struct mixed, a);   // → 0
offsetof(struct mixed, b);   // → 4
offsetof(struct mixed, c);   // → 8

offsetof(型別, 成員) 回傳「該成員從 struct 開頭算起的 byte 數」。

為什麼這個小工具值得你記住? 因為它是 kernel 裡一個極核心魔法 container_of 的基石——container_of 能「從一個成員的位址,反推出包含它的整個 struct 的位址」。這在 kernel 的鏈結串列(Phase 2 的核心)中無所不在。你現在先記住 offsetof 做什麼;到 P2-T03 你會看到它怎麼變成那個魔法。

7. attribute((packed)):強制取消 padding——以及它的代價

有時你必須讓 struct 的佈局精確符合外部規格(硬體暫存器、磁碟格式、網路協定),一個 padding byte 都不能有,否則欄位就對不上對方的定義。這時用 GCC 的 packed 屬性:

struct mixed_packed {
    char  a;
    int   b;
    char  c;
} __attribute__((packed));   // sizeof = 6,沒有任何 padding

packed 告訴編譯器:「別插任何 padding,照我寫的緊密排。」於是:

注意 packed 版裡,b 落在 offset 1——它是個 4-byte int,卻沒有對齊到 4 的倍數。這正是上一節說的「未對齊存取」。

所以 packed 不是免費的,它的代價正是第 2 節講的那些: - CPU 存取 b 可能要做兩次記憶體存取再拼接 → 變慢。 - 在嚴格的架構上,可能觸發 alignment trap → 當掉。

什麼時候該用 packed? 只在「佈局精確性是硬需求」時——例如你要把一塊記憶體直接當成磁碟上的某個固定格式來解析,欄位位置必須分毫不差。什麼時候不該用? 為了「讓 struct 小一點」這種隨手優化——那應該用第 5 節的「重排成員」來達成,而不是犧牲對齊。

NVMe 的現實:NVMe 命令結構本身是設計成天然對齊的(規格制定者刻意讓欄位落在對齊位址),所以你通常不需要對它加 packed——硬要加反而可能引入未對齊存取。packed 更常用在那些「沒有為對齊著想」的舊格式或緊湊協定上。這個區別很重要:不是「所有硬體結構都要 packed」,而是「當格式本身不對齊、你又必須精確匹配時才 packed」。

8. union 與 bitfield:兩個特殊但你會遇到的工具

union:同一塊記憶體,多種解讀方式

union value {
    int   as_int;
    float as_float;
    unsigned char as_bytes[4];
};

和 struct「每個成員各佔一塊、依序排列」相反,union 的所有成員共用同一塊記憶體(大小 = 最大的那個成員)。你往 as_int 寫一個值,再讀 as_bytes,讀到的是「同一份 4 bytes,用不同型別去解讀」。

用途:當「同一塊資料,視情況要當不同型別看」時。例如解析一個協定欄位,有時要整體當數字、有時要逐 byte 檢查。注意:同時間只有一個成員的解讀是「有意義」的——你寫了 as_int 又去讀 as_float,讀到的是那串 bits 被當成 float 的(通常無意義的)結果,不是型別轉換。

bitfield:控制到「位元」層級

struct status_reg {
    unsigned int ready    : 1;   // 只佔 1 個 bit
    unsigned int error    : 1;   // 只佔 1 個 bit
    unsigned int count    : 6;   // 佔 6 個 bits
};

到目前為止我們的最小單位都是 byte。但硬體的狀態暫存器常把多個旗標擠在一個 byte 的不同 bit 裡:第 0 bit 是「就緒」、第 1 bit 是「錯誤」、接下來 6 個 bit 合起來是一個計數。bitfield 讓你用「成員名字」直接存取這些 bit,不必自己做位元運算(位元運算是 P0-T11 的主題)。

        b1["bit1

reg.ready = 1; 就只設那一個 bit。但有個大坑:bitfield 裡「哪個成員對應到 byte 的高位還是低位、跨 byte 怎麼排」,是實作定義(implementation-defined)的——換一個編譯器、換一種位元序(endianness),擺法可能就不同。所以拿 bitfield 直接對應真實硬體暫存器是危險的,可移植性差。更穩健的做法,是用明確的位元遮罩 + 位元運算(P0-T11)。bitfield 你要認得、讀得懂,但對應硬體時要格外謹慎。

打通關:把這課的概念串成一個心智模型

學到這裡你手上有一堆零件:對齊、padding、重排、offsetof、packed、union、bitfield。它們不是七個獨立知識點,而是圍繞一個核心問題的不同面向:「一塊記憶體,要怎麼擺放與解讀,才能既配合硬體、又精確匹配外部規格?」

常見誤區與踩雷提醒

誤區一:以為 struct 大小 = 成員大小總和。 這是最根本的誤解。{char; int; char;} 不是 6 而是 12,因為有 padding。要算對,必須對每個成員套用「對齊規則 A」、最後套用「整體對齊規則 B」。養成習慣:看到 struct,先在腦中跑一遍第 4 節的步驟流程。

誤區二:為了「讓 struct 變小」就隨手加 packed。 packed 會犧牲對齊,可能讓存取變慢、甚至在某些架構觸發 trap 當掉。想省空間,正解是「重排成員順序」(第 5 節),那是無代價的。packed 只保留給「必須精確匹配不對齊的外部格式」這種硬需求。

誤區三:假設所有硬體結構都需要 packed。 不對。許多現代硬體結構(如 NVMe 命令)本身就設計成天然對齊,你直接定義對應 struct 即可,硬加 packed 反而引入未對齊存取。判斷準則是「這個外部格式本身對不對齊」,不是「它是不是硬體」。

誤區四:假設 bitfield 的位元排列跨平台一致。 不保證。同一份 bitfield 定義,在不同編譯器/位元序下,bit 的擺放可能不同。要對應真實硬體暫存器時,務必查清楚目標平台行為,或改用明確的位元遮罩(P0-T11)。

誤區五:忘記「struct 裡放指標」時,指標本身是 8 bytes(64 位元)。 新手有時以為指標很小。在 64 位元系統上,任何指標都是 8 bytes,且對齊到 8。一個 struct 裡放了指標,它的整體對齊就被拉高到 8,可能產生比你預期更多的 padding。

動手實作

環境:任何 Linux 終端機,使用者態,全程不需 root、不會動到系統。

任務 A — 預測再驗證(練手算) 先用紙筆,照第 4 節的步驟流程,手算下面 struct 的 sizeof 與每個成員的 offsetof,寫在紙上。然後才用程式驗證:

#include <stdio.h>
#include <stddef.h>
struct mixed { char a; int b; char c; };
struct demo  { char a; short b; int c; double d; };
int main(void) {
    printf("mixed: size=%zu  a@%zu b@%zu c@%zu\n",
        sizeof(struct mixed), offsetof(struct mixed,a),
        offsetof(struct mixed,b), offsetof(struct mixed,c));
    printf("demo : size=%zu  a@%zu b@%zu c@%zu d@%zu\n",
        sizeof(struct demo), offsetof(struct demo,a), offsetof(struct demo,b),
        offsetof(struct demo,c), offsetof(struct demo,d));
    return 0;
}

驗收你的手算:mixed 應為 size=12 (0,4,8);demo 應為 size=16 (0,2,4,8)。算錯的話,回第 4 節找出你哪一步漏了對齊。

任務 B — 重排省空間 把 struct mixed 的成員重排成 {int b; char a; char c;},印 sizeof(應為 8)。寫一句話說明:省下的 4 bytes 是哪來的(原本哪些 padding 消失了)?

任務 C — 見證 packed 的威力與代價 對原本的 struct mixed 加 __attribute__((packed)),印 sizeof(應為 6)與 offsetof(b)(應為 1)。然後寫兩句話:(1) 這 6 bytes 比 12 省在哪?(2) b 現在落在 offset 1,這帶來什麼風險?

任務 D — union 的「同記憶體多解讀」

#include <stdio.h>
union value { int as_int; unsigned char as_bytes[4]; };
int main(void) {
    union value v;
    v.as_int = 0x41424344;   // 寫入一個整數
    printf("as_int = 0x%X\n", v.as_int);
    for (int i = 0; i < 4; i++)
        printf("as_bytes[%d] = 0x%X ('%c')\n", i, v.as_bytes[i], v.as_bytes[i]);
    return 0;
}

觀察:同一份 4 bytes,當 int 讀是 0x41424344,當 byte 陣列讀則拆成四個 byte。注意印出的 byte 順序——它會洩漏你機器的「位元組順序(endianness)」:小端序(x86)會看到 44 43 42 41,大端序則是 41 42 43 44。(endianness 之後會再深入,這裡先親眼見一次。)

任務 E(進階)— sizeof 一個含指標的 struct 定義 struct withptr { char c; int *p; };,印 sizeof(在 64 位元系統應為 16,不是 9)。用第 4 節流程解釋為什麼:指標對齊到 8,所以 c 後面補了 7 bytes padding。

驗收與自我評分

驗收檢核點(量化,逐項通過): 給定 struct { char a; int b; char c; };—— 1. ☐ 不靠工具,用紙筆手算其 sizeof(12)與 offsetof(b)(4),再用程式驗證一致。 2. ☐ 重排成員後 sizeof 降為 8,並能說明省下的 padding 來源。 3. ☐ 加上 __attribute__((packed)) 後 sizeof 變為 6,並能解釋差異與代價(犧牲對齊 → 可能變慢或 trap)。 4. ☐ 用 union 寫入一個 int、逐 byte 讀出,並能說明這展示了「同記憶體多解讀」。

評分量表: - 60(及格):能用工具(sizeof / offsetof)看出佈局,知道 padding 存在。 - 80(熟練):能徒手算出任意 struct 的佈局(含 padding 推理),能解釋 packed 的代價與重排的好處。 - 100(精通):能解釋對齊對硬體 I/O 結構為何重要、能判斷「何時該/不該用 packed」,並把整套概念連結到 NVMe 命令格式與 container_of。

延伸與銜接

  • 對應工作場景:直接對應。NVMe 的 64-byte 命令、16-byte 完成項都是嚴格定義的對齊結構;DMA 緩衝區也常有對齊要求。這一課是你日後(P5-T05、P5-T06)讀懂 nvme.h 裡那些結構定義的前置。等你真的看到 NVMe 命令 struct,你會慶幸現在把對齊弄懂了——你能一眼看出每個欄位在第幾個 byte。
  • 這課餵給未來的:offsetof(第6節)→ P2-T03 的 container_of 魔法;對齊概念 → P6-T01 DMA 緩衝區的對齊要求。
  • 下一步 → P0-T05 行程記憶體佈局:你已經會看「一個 struct 在記憶體裡的佈局」。下一課把尺度放大,看「一整支程式在記憶體裡的佈局」——程式碼、全域變數、heap、stack 各住哪一區,以及它們的生命週期。這是理解虛擬記憶體(Phase 1)與 user/kernel 邊界的起點。
