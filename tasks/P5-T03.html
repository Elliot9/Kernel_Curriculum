P5-T03 · 多佇列 block layer(blk-mq)

一句話:舊的單佇列 block layer 卡在「一把鎖」——多核全擠在同一個佇列搶鎖,高速 NVMe 跑不滿。blk-mq 改成兩層:每核一個 software staging queue(免爭搶)+ 對應裝置的 hardware dispatch queue,用 tag(sbitmap)管 in-flight request。而每個硬體佇列 1:1 對應 NVMe 的一對 SQ/CQ。

為什麼要先學這個(導讀)

P5-T02 你懂了 bio/request 這些 I/O 物件。這一課看它們怎麼被多佇列地管理——blk-mq(multi-queue block layer)。這是理解你產品 I/O 並行模型的關鍵。

先理解問題:舊的單佇列(single-queue)設計有個擴展瓶頸。所有 CPU 核心提交的 I/O 都進同一個請求佇列,而那個佇列要用一把鎖保護(回顧 P3-T08)。當你有很多核心、又有超高速的 NVMe(每秒百萬級 IOPS),所有核心擠在同一把鎖上爭搶——鎖競爭成為瓶頸,NVMe 的速度根本跑不滿(回顧 P1-T03 多核爭搶的代價、P3-T09 per-CPU 的解法)。

blk-mq 的解法是兩層佇列: - software staging queue(軟體暫存佇列):每個 CPU(或每個 NUMA node)一個——各核心把 I/O 先放進自己的軟佇列,不爭搶(回收 P3-T09 per-CPU「以不共享換效能」)。 - hardware dispatch queue(硬體派發佇列):對應裝置的佇列——軟佇列的 I/O 派發到硬體佇列,再送給裝置。 - tag(sbitmap):管理 in-flight request——每個正在處理的 request 佔一個 tag,完成釋放(回收 P2-T07 的 sbitmap!)。

為什麼這對你是 scope: direct?因為blk-mq 的每個硬體佇列 1:1 對應 NVMe 的一對 SQ/CQ(提交佇列/完成佇列)(P5-T05)。你產品的 I/O 並行模型——多核各自提交、每核一條到 NVMe 的佇列——正是建立在 blk-mq 上。理解 blk-mq,你才理解你產品如何在多核上擴展、如何把 I/O 高效送到 NVMe。

(這一課大量回收你前面的功課:P1-T03 per-CPU/cache、P2-T07 sbitmap/tag、P3-T09 per-CPU 變數——它們在 blk-mq 裡匯聚。)

開始之前(前置確認)

  • 依賴:P5-T02(bio/request/request_queue)、P2-T07(sbitmap/tag——blk-mq 的 tag 就是 sbitmap)、P1-T03(per-CPU/cache——軟佇列是 per-CPU)。也用到 P3-T08(鎖競爭)、P3-T09(per-CPU)。
  • 自我檢測: 1. 你還記得 P2-T07 的「bitmap 配置器:find-first-zero + set = 配一個 tag;clear = 釋放」、以及 sbitmap 是它的多核優化版嗎?blk-mq 的 tag 就是這個。 2. 你還記得 P3-T09 的「per-CPU:每核一份、消除共享、免鎖」嗎?blk-mq 的軟佇列就是 per-CPU 的應用。
  • 工具:null_blk 模組(modprobe null_blk——一個純記憶體的 blk-mq 後端,用來實驗)。
  • 環境:QEMU 虛擬機。null_blk 實驗只在 VM。

核心內容

拆成這幾節:(1) 單佇列的瓶頸 → (2) blk-mq 的兩層佇列 → (3) software staging queue → (4) hardware dispatch queue → (5) tag(sbitmap)管 in-flight → (6) 佇列數與 CPU/裝置的對應,最後打通關。

1. 單佇列的瓶頸:一把鎖

先看 blk-mq 要解決的問題——舊的單佇列設計為什麼在高速裝置上卡住。

舊單佇列的問題:所有 CPU 提交的 I/O 進同一個佇列、用一把鎖保護。當核心多、裝置快: - 鎖競爭隨核心數惡化(回顧 P3-T08:多核搶一把鎖,大家排隊等)。 - cache line 彈跳(那把鎖、那個佇列的資料在核心間來回,false sharing,回顧 P1-T03)。

結果:高速 NVMe(每秒百萬級 IOPS)根本跑不滿——瓶頸不在裝置,在那把鎖。這在 HDD 時代不明顯(裝置本身慢),但 NVMe 快到讓「軟體的鎖競爭」成為主要瓶頸。blk-mq 就是為此而生。

2. blk-mq 的兩層佇列

blk-mq 的核心設計:兩層佇列——把「各核心提交」和「派發給裝置」解耦。

兩層: - 第一層 software staging queue:每個 CPU 一個。各核心把 I/O 放進自己的軟佇列——不和別的核心爭搶(per-CPU,回收 P3-T09)。 - 第二層 hardware dispatch queue:對應裝置的硬體佇列。軟佇列的 I/O 派發到硬體佇列,再送給裝置。

關鍵洞察:把「提交」和「派發」分兩層,讓提交端(各核心)免鎖爭搶。各核心忙自己的軟佇列(快、無競爭),再有序地匯到硬體佇列派發。這就是 blk-mq 擴展性的來源——消除了單佇列那把全域鎖。

blk_mq_tag_set(描述這組佇列的配置:幾個硬體佇列、佇列深度等)和 blk_mq_ops(驅動提供的操作,如 queue_rq 提交函式——又是 P0-T07 ops 結構)是驅動接入 blk-mq 的介面。

3. software staging queue:每核一個,免爭搶

深入第一層。software staging queue 是 per-CPU 的——這是 blk-mq 消除鎖競爭的核心。

software staging queue 是 per-CPU(回收 P3-T09):CPU N 提交的 request 放進 CPU N 自己的軟佇列,只有 CPU N 碰它——不需要和別的核心搶鎖。好處正是 per-CPU 的好處(回收 P1-T03):無鎖競爭、cache 友善(佇列資料在本核心 cache、不彈跳)、隨核心數線性擴展。

「staging(暫存)」的意思:I/O 先在這層累積,可以在此做合併(回顧 P5-T02 bio→request 合併)、排序(I/O 排程器在這層運作,P5-T04),再派發到硬體佇列。所以軟佇列既是「免爭搶的入口」,也是「合併/排程的暫存區」。

hardware dispatch queue 對應裝置的一個硬體佇列——驅動的 queue_rq 函式(P0-T07 ops)從這裡取 request 送給裝置。

對你產品最關鍵的對應(驗收點之一,精通目標):對 NVMe,一個 blk-mq 硬體佇列 1:1 對應 NVMe 的一對 SQ/CQ(提交佇列 + 完成佇列,P5-T05 會深入)。NVMe 裝置可以有多個佇列對,常見配置是「每個 CPU 核心一對 SQ/CQ」——於是整條路徑都並行:CPU N 的軟佇列 → 對應的硬體佇列 → 對應的 NVMe 佇列對,各核心一路到底不互相爭搶。

這就是你產品 I/O 並行模型的骨架:多核、多佇列、每核一路到 NVMe。理解這個 1:1 對應,你就懂了為什麼 NVMe + blk-mq 能在多核上跑出極高的 IOPS。

5. tag(sbitmap):管理 in-flight request

blk-mq 用 tag 管理「同時有多少 in-flight(處理中)的 request」——而 tag 的底層正是你 P2-T07 學的 sbitmap!

flowchart TB
    SUBMIT4["要提交一個 request"]
    SUBMIT4 --> ALLOC3["配置一個 tag:
在 tag 的 sbitmap 找一個空閒 bit(find-first-zero)
設為已用,回傳 tag 編號(P2-T07 的配置器!)"]
    ALLOC3 --> USE2["這個 request 帶著它的 tag 去處理
(tag = 它在 in-flight 集合裡的身份)"]
    USE2 --> COMPLETE2["I/O 完成 → 釋放 tag(clear bit)
→ 這個 tag 可被新 request 重用"]
    DEPTH["★ 佇列深度 = tag bitmap 有多少個 bit ★
= 同時最多多少個 in-flight request
(tag 用完 = 佇列滿 → 新 request 要等)"]
    ALLOC3 --> DEPTH
    NOTE17["常見誤區:忽略 tag 耗盡(佇列深度滿)對延遲的影響
→ tag 用完時,新 I/O 被擋住等待 → 延遲上升
(佇列深度是效能調校的一個關鍵參數)"]
    DEPTH --> NOTE17
    style ALLOC3 fill:#e8a33d,color:#10100e
    style DEPTH fill:#8a9a5b,color:#10100e
    style NOTE17 fill:#c2603a,color:#f4ecd8

tag 機制(完全是 P2-T07 的 sbitmap 配置器): - 配置 tag:提交 request 時,在 tag 的 sbitmap 找一個空閒 bit(find-first-zero)、設為已用、回傳 tag 編號——這就是你 P2-T07 親手做的 bitmap 配置器! sbitmap 是它的多核優化版(切成多塊、配 per-CPU,減少競爭)。 - tag 的意義:每個 in-flight request 佔一個 tag(它在「處理中集合」裡的身份)。 - 釋放 tag:I/O 完成 → 釋放 tag(clear bit)→ 可被新 request 重用。

關鍵(驗收點:解釋 tag 如何限制 in-flight request 數):佇列深度 = tag bitmap 有多少個 bit = 同時最多多少個 in-flight request。tag 用完(佇列滿),新 request 就要等。常見誤區:忽略 tag 耗盡(佇列深度滿)對延遲的影響——tag 用完時新 I/O 被擋住,延遲上升。佇列深度是效能調校的關鍵參數(太小限制並行、太大可能增加延遲)。

對你產品:你的 in-flight I/O 數受 tag/佇列深度限制;這正是 P2-T07 結尾說的「blk-mq tag = 你產品 in-flight I/O 管理」的兌現。

硬體佇列數(nr_hw_queues)取決於裝置能提供幾個佇列 + 驅動配置: - 理想:硬體佇列數 = CPU 數 → 每核一個硬體佇列(NVMe 每核一對 SQ/CQ)→ 完美並行。 - 但不一定:裝置只能提供較少佇列(例如 4 個),但有 16 核 → 多個 CPU 的軟佇列共享較少的硬體佇列。

常見誤區:以為硬體佇列數一定等於 CPU 數——不對,取決於裝置能力與 nr_hw_queues。高階 NVMe 常能每核一佇列;低階裝置可能較少。

另一個常見誤區:混淆 software queue 與 hardware queue——software queue 是 per-CPU 暫存(一定每核一個);hardware queue 對應裝置佇列(數量看裝置)。兩層不同,別混。

還有一個誤區:以為 blk-mq 一定比舊單佇列快——對高速裝置(NVMe)blk-mq 大勝;但對低速裝置(慢速 HDD),單佇列的瓶頸本來就不明顯,blk-mq 的多佇列開銷未必划算。blk-mq 的優勢在「裝置快到讓軟體成為瓶頸」時才顯著(正是你的 NVMe 場景)。

常見誤區與踩雷提醒

誤區一:以為硬體佇列數等於 CPU 數。 取決於裝置能力與 nr_hw_queues。高階 NVMe 常能每核一佇列;低階裝置可能較少(多個 CPU 共享較少硬體佇列)。

誤區二:混淆 software queue 與 hardware queue。 software queue 是 per-CPU 暫存(一定每核一個);hardware queue 對應裝置佇列(數量看裝置)。兩層不同。

誤區三:忽略 tag 耗盡(佇列深度滿)對延遲的影響。 tag 用完時新 I/O 被擋住等待,延遲上升。佇列深度是效能調校的關鍵參數。

誤區四:以為 blk-mq 一定比舊單佇列快。 對高速裝置(NVMe)blk-mq 大勝;對低速裝置(慢 HDD)單佇列瓶頸不明顯,多佇列開銷未必划算。blk-mq 的優勢在「裝置快到讓軟體成瓶頸」時。

動手實作

環境:QEMU 虛擬機。null_blk 實驗只在 VM。

任務 A — 用 null_blk 建 blk-mq 裝置(驗收點) modprobe null_blk(可帶參數設定佇列數,如 nr_hw_queues、submit_queues)。建立一個 null_blk 裝置(如 /dev/nullb0)。看 /sys/block/nullb0/mq/——裡面每個編號目錄是一個硬體佇列。驗收:用 null_blk 建立裝置並在 /sys/block/<dev>/mq/ 看到多個硬體佇列。

任務 B — 說明兩層佇列(驗收點) 用文字說明:software staging queue 和 hardware dispatch queue 各自的角色?(提示:軟佇列 per-CPU 免爭搶/暫存合併;硬佇列對應裝置、派發。)驗收:說明兩者各自的角色。

任務 C — 解釋 tag 限制 in-flight(驗收點) 寫一段話:tag(sbitmap)如何限制同時 in-flight 的 request 數?佇列深度和 tag 數的關係?驗收:解釋 tag(sbitmap)如何限制 in-flight request 數。(連結 P2-T07 你做的 bitmap 配置器。)

任務 D(連結)— blk-mq 對應 NVMe 佇列 寫一兩句話:blk-mq 的硬體佇列如何 1:1 對應 NVMe 的 SQ/CQ?這對你產品的多核並行有什麼意義?(提示:每核一條路到 NVMe、不爭搶;P5-T05/P5-T06 會深入。)

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 用 null_blk 建立裝置並在 /sys/block/<dev>/mq/ 看到多個硬體佇列。 2. ☐ 用文字說明 software staging queue 與 hardware dispatch queue 各自的角色。 3. ☐ 解釋 tag(sbitmap)如何限制 in-flight request 數。

評分量表: - 60(及格):能用 null_blk 建裝置。 - 80(熟練):能解釋兩層佇列與 tag。 - 100(精通):能說明 blk-mq 如何對應到 NVMe 的多佇列(P5-T06)並利用 per-CPU 避免鎖競爭。

延伸與銜接

  • 對應工作場景:直接對應——blk-mq 的每硬體佇列正是 1:1 對應 NVMe 的 SQ/CQ 對;理解 blk-mq 是理解你產品 I/O 並行模型的關鍵。
  • 這課餵給未來的(I/O 物件流動主線):P5-T02 bio/request → 本課 blk-mq(request 在多佇列)→ P5-T05 NVMe 佇列(硬體佇列 ↔ SQ/CQ)→ P5-T06 NVMe driver(nvme_queue ↔ blk-mq 硬體佇列)。tag/sbitmap → 回收 P2-T07;per-CPU 軟佇列 → 回收 P3-T09。
  • 下一步 → P5-T04 I/O 排程器(mq-deadline / BFQ / Kyber / none):blk-mq 的軟佇列那層會做 I/O 排程——下一課看各種排程器的取捨。為什麼需要排程(合併、排序、公平、延遲)?mq-deadline(以期限避免飢餓,用紅黑樹排序,回收 P2-T05)、BFQ(公平、互動友善)、Kyber(低延遲)、以及 none(高速 NVMe 常用——因為裝置夠快,重量級排程反而是負擔)。這直接對應你的效能調校:你產品在 NVMe 上的延遲/吞吐,和排程器選擇相關。
