P3-T14 · kernel 除錯(二)—— KASAN、KCSAN、lockdep、kgdb、crash/kdump

一句話:有些 bug——use-after-free、資料競爭、死結——時有時無、極難用 printk 抓。kernel 有一組「自動偵測器」:KASAN 抓記憶體錯誤、KCSAN 抓 race、lockdep 抓死結,它們在問題釀成災難前就指出「在哪、怎麼錯的」。對你的高並行 I/O 路徑,這些是保命工具。

為什麼要先學這個(導讀)

P3-T13 的 printk/Oops/ftrace 對付「會崩潰、可重現」的 bug 很好。但 kernel 開發最難纏的 bug 是時有時無、極難重現的那種——use-after-free(回顧 P0-T06)、資料競爭/race(回顧 P1-T08)、死結(回顧 P3-T08)。這些可能跑一萬次才錯一次,用 printk 幾乎抓不到。

這一課的工具是自動偵測器(sanitizers/checkers)——它們在 kernel 裡埋下檢查機制,自動偵測這些難纏的 bug 並報告「在哪、怎麼錯的」: - KASAN(Kernel Address Sanitizer):自動偵測 use-after-free、越界存取等記憶體錯誤——它會給出「配置在哪、釋放在哪、現在在哪用」三個堆疊。 - KCSAN(Kernel Concurrency Sanitizer):自動偵測資料競爭(data race)——兩個執行流沒同步地存取同一資料。 - lockdep:自動偵測死結與鎖順序問題(回顧 P1-T09 死結、P3-T08 持鎖規則)——它在「可能死結」真正發生前就警告。 - kgdb/kdb:對 kernel 做源碼級除錯(在 module 函式設中斷點、看變數,延伸 P1-T11 的 gdb)。 - crash/kdump:當機後的事後分析——kdump 在 panic 時把記憶體 dump 下來,crash 工具分析它。

為什麼這對你是 scope: direct?因為你的產品是高並行 I/O 路徑——多核、中斷、共享狀態,正是 use-after-free、race、死結的高發區。KASAN/KCSAN/lockdep 是抓出你 module 這些 bug 的主力工具。重要紀律:這些工具開銷大,只在 debug build 開、production 絕不開。你會用 KASAN 抓一個 use-after-free、用 lockdep 觸發一個鎖順序警告、用 kgdb 在 module 裡設中斷點。

開始之前(前置確認)

  • 依賴:P3-T13(基本除錯、Oops、CONFIG_DEBUG_INFO)、P3-T08(鎖、持鎖規則、死結)。也用到 P0-T06(use-after-free)、P1-T08(race)、P1-T09(死結)、P1-T11(gdb)。
  • 自我檢測: 1. 你還記得 P0-T06 的 use-after-free、P1-T08 的 race、P1-T09 的死結嗎?這課的工具就是自動抓這三類。 2. 你還記得 P1-T11 用 gdb 連 QEMU 設中斷點嗎?kgdb 是它的延伸(在運行的 kernel/module 裡設中斷點)。
  • 環境:QEMU 虛擬機,且需重編帶 instrumentation 的 kernel(KASAN/KCSAN/lockdep 都要)。

核心內容

拆成這幾節:(1) 為何需要自動偵測器 → (2) KASAN:記憶體錯誤 → (3) KCSAN:資料競爭 → (4) lockdep:死結偵測 → (5) kgdb:源碼級除錯 → (6) kdump/crash:事後分析,最後打通關。

1. 為何需要自動偵測器:抓時有時無的 bug

先理解這類工具解決什麼。回顧 P1-T08:race「時有時無、難重現」,是並行最可怕之處。use-after-free、死結也類似——可能潛伏很久才爆發。

    PROBLEM --> SOLUTION["自動偵測器的做法:
在 kernel 裡『埋檢查』(instrumentation):
每次記憶體存取/每次取鎖,都自動檢查規則
→ 違規當下就抓出來、報告現場"]
    SOLUTION --> COST["★ 代價:開銷大(每次存取都檢查)★
→ 只在 debug build 開,production 絕不開
(且需重編帶 instrumentation 的 kernel)"]
    style PROBLEM fill:#c2603a,color:#f4ecd8
    style SOLUTION fill:#8a9a5b,color:#10100e
    style COST fill:#e8a33d,color:#10100e

核心做法:instrumentation(插樁)——編譯時在 kernel 裡埋入檢查程式碼,讓「每次記憶體存取」「每次取鎖」都自動檢查規則,違規當下就抓出來。代價是開銷大(每次存取都多做檢查)。

重要紀律(常見誤區:在 production 開 KASAN/KCSAN):這些工具開銷極大(KASAN 可能讓記憶體用量、執行時間顯著上升),只在 debug build 開、production 絕不開。而且它們需要重編帶 instrumentation 的 kernel(常見誤區:忘了這些工具需重編 kernel)——不是裝個工具就好,是編 kernel 時開對應的 CONFIG。

2. KASAN:抓 use-after-free 與越界

KASAN(Kernel Address Sanitizer) 自動偵測記憶體錯誤——主要是 use-after-free(用了已釋放的記憶體,回顧 P0-T06)和越界存取(讀寫超出配置範圍)。

flowchart TB
    KASAN["KASAN(CONFIG_KASAN,重編 kernel)"]
    KASAN --> HOW["做法:用『shadow memory』記錄每塊記憶體的狀態
(已配置/已釋放/越界紅區)
每次存取前檢查 shadow → 違規就報告"]
    HOW --> CATCH["抓到的:
use-after-free(存取已釋放的)
out-of-bounds(讀寫超出配置範圍)
等"]
    CATCH --> REPORT["★ KASAN 報告的價值:三個堆疊 ★
① 這塊記憶體在哪『配置』的
② 在哪『釋放』的
③ 現在在哪『使用』的(出錯點)
→ 完整還原 use-after-free 的來龍去脈"]
    style KASAN fill:#6fa8b8,color:#10100e
    style REPORT fill:#8a9a5b,color:#10100e

KASAN 怎麼運作(概念):它用 shadow memory(影子記憶體)記錄每塊記憶體的狀態,每次存取前檢查——存取到「已釋放」或「越界紅區」就報告。

KASAN 報告最有價值的是三個堆疊(驗收點:KASAN 報出一處 use-after-free 並指到配置/釋放/使用三個 stack): - 配置堆疊:這塊記憶體在哪被配置(kmalloc)。 - 釋放堆疊:在哪被釋放(kfree)。 - 使用堆疊:現在在哪被(非法)使用——出錯點。

這三個堆疊完整還原 use-after-free 的來龍去脈:你能看到「在 A 配置、在 B 釋放、卻在 C 又用了」。對你 I/O 路徑裡物件生命週期的 bug(回顧 P3-T09 refcount),KASAN 是抓 use-after-free 的利器。

常見誤區:以為沒有 KASAN 報告就沒記憶體錯誤——KASAN 覆蓋率有限(只能抓「執行到的、被插樁的」存取),沒報告不代表絕對沒問題。它是強力工具,但不是百分百保證。

3. KCSAN:抓資料競爭

KCSAN(Kernel Concurrency Sanitizer) 自動偵測資料競爭(data race)——兩個執行流沒有適當同步地存取同一塊資料,且至少一個是寫(正是 P1-T08 的 race 定義)。

flowchart TB
    KCSAN["KCSAN(CONFIG_KCSAN,重編 kernel)"]
    KCSAN --> HOW2["做法:在記憶體存取插樁,
偵測『兩個執行流並行存取同一位址、
無同步、至少一個寫』的情況"]
    HOW2 --> CATCH2["抓到的:data race
(回顧 P1-T08:未受保護的共享可變狀態)
→ 報告兩個衝突的存取在哪"]
    CATCH2 --> VALUE["價值:race 時有時無、難重現(P1-T08),
KCSAN 能在它還沒釀成可見災難前就抓出
→ 對你高並行 I/O 路徑的隱藏 race 特別有用"]
    style KCSAN fill:#6fa8b8,color:#10100e
    style VALUE fill:#8a9a5b,color:#10100e

KCSAN 在記憶體存取插樁,偵測「兩個執行流並行存取同一位址、無同步、至少一個寫」——也就是 P1-T08 的 race。它報告兩個衝突的存取在哪。

價值:race 時有時無、極難用一般方法重現抓出(P1-T08),KCSAN 能在它還沒釀成可見災難前就主動偵測出來。對你的高並行 I/O 路徑(多核、中斷共享狀態),隱藏的 race 是大威脅,KCSAN 是抓它們的主力。

(相關的還有 UBSAN——偵測未定義行為,回顧 P0-T10;kmemleak——偵測記憶體洩漏。它們也是這類 sanitizer,debug 時可開。)

4. lockdep:抓死結與鎖順序

lockdep(lock dependency validator) 自動偵測死結與鎖順序問題(回顧 P1-T09 死結四條件、固定加鎖順序;P3-T08 持鎖規則)。它最強大的地方是:不需要死結真的發生,就能警告「這樣下去可能死結」。

flowchart TB
    LOCKDEP["lockdep(CONFIG_PROVE_LOCKING,重編 kernel)"]
    LOCKDEP --> HOW3["做法:記錄每次取鎖的『順序』,
建立鎖之間的相依圖
→ 偵測『鎖順序不一致』(可能形成循環等待,P1-T09)"]
    HOW3 --> CATCH3["抓到的(在真正死結前就警告):
① 鎖順序反轉(一處先 A 後 B、另一處先 B 後 A → 可能死結)
② 持 spinlock 時做了不該做的(如可能睡眠的操作,P3-T08)
③ 在中斷 context 用了不安全的鎖
等"]
    CATCH3 --> VALUE2["★ 價值:在死結真正發生前就抓出『潛在死結』★
(死結一旦發生系統就卡死,事後難查;
lockdep 提前警告,即使這次沒真的死結)"]
    style LOCKDEP fill:#6fa8b8,color:#10100e
    style VALUE2 fill:#8a9a5b,color:#10100e

lockdep 怎麼運作:記錄每次取鎖的順序,建立「鎖之間的相依圖」,偵測鎖順序不一致(回顧 P1-T09:一處先 A 後 B、另一處先 B 後 A,就可能循環等待死結)。

它能抓(在真正死結前就警告): - 鎖順序反轉(possible deadlock)——違反固定加鎖順序(P1-T09)。 - 持 spinlock 時做了不該做的事(回顧 P3-T08 持鎖不可睡眠等)。 - 在中斷 context 用了不安全的鎖。

價值:死結一旦真的發生,系統就卡死、事後極難查。lockdep 在潛在死結真正觸發前就警告——即使你這次測試運氣好沒真的死結,只要鎖順序有問題,lockdep 就會抓出來(驗收點:觸發一次 lockdep 的 possible deadlock 警告並解釋鎖順序問題)。常見誤區:lockdep 警告當雜訊忽略——lockdep 報的往往是真正的死結風險,別忽略它。對你的多鎖 I/O 路徑,lockdep 是防死結的保命工具。

5. kgdb:對 kernel 源碼級除錯

kgdb/kdb 讓你對運行中的 kernel 做源碼級除錯——在 kernel/module 函式裡設中斷點、單步、看變數。這是 P1-T11 那個「gdb 連 QEMU」的延伸與深化。

(在 QEMU 場景,常配合 -s -S,回顧 P1-T11)"]
    KGDB --> WHAT["能做:
在 kernel 函式 / 你 module 的函式設中斷點;
命中時單步、看區域變數、看 call stack
(像 P0-T01 除錯使用者態程式,但對象是 kernel)"]
    WHAT --> KDB["kdb:kgdb 附帶的簡易命令列除錯器
(不需另一台機器,直接在 console 下簡單命令)"]
    WHAT --> NEED2["前提:CONFIG_DEBUG_INFO(符號)+ kgdb 相關設定
(沒符號就只有位址,呼應 P0-T01/P3-T13)"]
    style KGDB fill:#6fa8b8,color:#10100e
    style WHAT fill:#8a9a5b,color:#10100e
    style NEED2 fill:#e8a33d,color:#10100e

kgdb:kernel 端的 kgdb stub + 主機端的 gdb,透過序列/網路連接(在 QEMU 場景常配合 -s -S,回顧 P1-T11)。能在 kernel/你 module 的函式設中斷點、命中時單步、看區域變數、看 call stack——就像 P0-T01 除錯使用者態程式,但對象是運行中的 kernel(驗收點:用 kgdb 在自寫 module 函式命中中斷點並檢視區域變數)。需要 CONFIG_DEBUG_INFO(符號,否則只有位址,呼應 P3-T13)。

kdb 是 kgdb 附帶的簡易命令列除錯器,可直接在 console 下簡單命令(不需另一台機器)。

kgdb 適合「需要互動式地停下來看狀態」的 debug(比 printk 更深入)——當 Oops/KASAN 還不夠、你想實際停在某行看變數時用。

6. kdump/crash:當機後的事後分析

最後一組:kdump + crash,用於事後分析(post-mortem)——當系統 panic(致命崩潰,P3-T13)時,把當下的記憶體狀態保存下來,事後慢慢分析。

flowchart TB
    PANIC2["系統 panic(致命崩潰)"]
    PANIC2 --> KDUMP["kdump:
panic 時,透過預先載入的『備援 kernel』
把當下記憶體 dump 成一個檔案(vmcore)
→ 保存崩潰瞬間的完整狀態"]
    KDUMP --> CRASH["crash 工具:
事後載入 vmcore + 符號,
分析崩潰當下的:
call stack、各 task 狀態、記憶體內容、鎖狀態..."]
    CRASH --> VALUE3["價值:對『難重現、一崩就整個系統沒了』的問題,
kdump 保住現場,crash 讓你事後完整解剖
(像把崩潰瞬間冷凍下來慢慢驗屍)"]
    style KDUMP fill:#6fa8b8,color:#10100e
    style CRASH fill:#8a9a5b,color:#10100e
    style VALUE3 fill:#e8a33d,color:#10100e

  • kdump:預先載入一個「備援 kernel」;當主 kernel panic 時,跳到備援 kernel,把當下記憶體 dump 成檔案(vmcore)——保存崩潰瞬間的完整狀態。
  • crash:事後用這個工具載入 vmcore + 符號,分析崩潰當下的 call stack、各 task 狀態、記憶體內容、鎖狀態等。

價值:對「難重現、而且一崩潰整個系統就沒了」的問題,kdump 保住崩潰現場,crash 讓你事後完整解剖(像把崩潰瞬間冷凍下來慢慢驗屍)。這對生產環境的疑難當機特別有用——你不能在生產機上掛 kgdb 互動除錯,但可以靠 kdump 收集 vmcore、事後用 crash 分析。

(這是最進階的工具,你現在知道「有這套事後分析機制」即可;真正用 crash 分析複雜 vmcore 是 100 分的精通目標。)

常見誤區與踩雷提醒

誤區一:在 production 開 KASAN/KCSAN。 開銷極大,只在 debug build 開、production 絕不開。

誤區二:忘了這些工具需重編 kernel 帶 instrumentation。 KASAN/KCSAN/lockdep 都要編 kernel 時開對應 CONFIG,不是裝個工具就好。

誤區三:以為沒有 KASAN 報告就沒記憶體錯誤。 KASAN 覆蓋率有限(只抓執行到的、被插樁的存取)。沒報告不代表絕對沒問題,它是強力工具但非百分百保證。

誤區四:lockdep 警告當雜訊忽略。 lockdep 報的往往是真正的死結風險(即使這次沒真的死結)。別忽略,要查清鎖順序問題。

動手實作

環境:QEMU 虛擬機,需重編帶對應 CONFIG 的 kernel。

任務 A — KASAN 抓 use-after-free(驗收點,核心) 重編一個開啟 CONFIG_KASAN 的 kernel。寫一個故意 use-after-free 的 module(kmalloc 一塊 → kfree → 之後又存取它,回顧 P0-T06)。在 QEMU 載入觸發。驗收:KASAN 成功報出 use-after-free,並指到配置(kmalloc)、釋放(kfree)、使用三個 stack。 對照 P0-T06 你用 valgrind 抓使用者態 use-after-free——KASAN 是 kernel 版。

任務 B — lockdep 抓鎖順序反轉(驗收點,核心) 重編開啟 CONFIG_PROVE_LOCKING(lockdep)的 kernel。寫一個 module,故意製造鎖順序反轉(回顧 P1-T09:一個路徑先取 A 後 B、另一路徑先取 B 後 A)。觸發後看 dmesg 的 lockdep 警告。驗收:觸發一次 lockdep possible deadlock 警告,並能解釋鎖順序問題(哪兩把鎖、順序如何不一致)。

任務 C — kgdb 設中斷點(驗收點) 用 kgdb(經 QEMU,配合 -s 或 kgdb 設定)在你自寫 module 的某函式設中斷點,命中後檢視區域變數。(延伸 P1-T11 的 gdb 連 QEMU。)驗收:用 kgdb 在自寫 module 函式命中中斷點並檢視區域變數。

任務 D(連結 + 觀念)— 為什麼這些不在 production 開 寫一兩句話:為什麼 KASAN/KCSAN 只在 debug build 開、不在 production 開?(提示:插樁讓每次存取都檢查,開銷大。)並寫一句:對你的高並行 I/O 路徑,KASAN/KCSAN/lockdep 各抓哪類 bug?

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ KASAN 成功報出一處 use-after-free 並指到配置/釋放/使用三個 stack。 2. ☐ 觸發一次 lockdep 的 possible deadlock 警告並解釋鎖順序問題。 3. ☐ 用 kgdb 在自寫 module 函式命中中斷點並檢視區域變數。

評分量表: - 60(及格):能開啟並讀懂一種工具的報告。 - 80(熟練):能用 KASAN + lockdep 定位真實 bug。 - 100(精通):能用 kgdb/crash 對複雜問題做源碼級/事後分析。
