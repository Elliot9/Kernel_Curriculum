P2-T08 · 整合驗收:讀懂一個真實 kernel 子系統的資料結構使用

一句話:不再學新結構,而是把 Phase 2 學的全部——list_head、container_of、雜湊/hlist、紅黑樹、XArray、bitmap——拿去讀一段真實的 kernel 程式碼,逐段認出它用了哪些結構與慣用法。能做到這件事,你就真正具備了讀 kernel 原始碼的能力。

🚪 這是出關門檻

這是 Phase 2 的關卡(gate)。本 task 達到 80 分(完整註解一段真實 kernel 程式碼、正確指認其中所有資料結構慣用法),並且具備閱讀 kernel 資料結構的信心,才算真正掌握了進入 Phase 3(核心 kernel 與 module 開發)所需的能力。

為什麼設這道關?因為從 Phase 3 開始,你要真正寫 kernel module、讀大量 kernel 原始碼。如果 list_for_each_entry、container_of、rb_node 這些東西出現時你還要停下來查,閱讀會寸步難行。這道關確保你已經能「一眼認出」這些慣用法——這是 Phase 2 整個階段的目的:讓 kernel 原始碼裡的資料結構「一眼可讀」。

為什麼是「讀真實程式碼」(導讀)

Phase 2 前七課,你逐一學了 kernel 的核心資料結構。但「分開學會每個」和「在一段真實程式碼裡同時認出它們」是兩回事。真實的 kernel 程式碼會把這些結構混在一起用——一個函式裡可能同時有 list_for_each_entry 走訪、container_of 取私有資料、操作一棵 rbtree。能在交織的真實 code 裡認出每一個,才是真本事。

這一課就是這個整合練習:挑一段約 100–200 行的真實 kernel 函式或結構,逐段註解它用到的每一個資料結構與慣用法。這不只是 Phase 2 的驗收,更是你日後工作的核心技能——你讀自家 module、讀 block layer 程式碼、追 bug,靠的就是這個「看著陌生的 kernel code,認出它在用什麼結構、做什麼事」的能力。

建議挑與儲存相關的子系統(從 block 目錄開始),這樣同時為 P5(Block Layer 與 NVMe)暖身——你會提前接觸到日後深入的程式碼。

為什麼這對你是 scope: direct?因為這正是你日後讀自家產品 module 與 block layer 程式碼的核心技能。沒有它,Phase 3 之後寸步難行;有了它,kernel 原始碼對你敞開。

開始之前(前置確認)

  • 依賴:整個 Phase 2(P2-T01 ~ P2-T07)。動手前,確認這些對你都已「一眼可讀」: 1. list_head 與 list_for_each_entry / list_for_each_entry_safe(P2-T02)。 2. container_of(P2-T03)——尤其「從成員指標反推外層 struct」。 3. 雜湊與 hlist(P2-T04)、紅黑樹 rb_node(P2-T05)、XArray(P2-T06)、bitmap(P2-T07)。
  • 工具:Bootlin Elixir(https://elixir.bootlin.com/linux/v6.12/source ）——線上瀏覽 kernel 原始碼,能點擊跳轉到定義(查 struct 宣告、巨集展開)。這是讀 kernel code 的利器。
  • 環境:純閱讀 + 註解,無系統風險。

核心內容:讀 kernel 程式碼的方法

這一課的「核心內容」不是新結構,而是讀 kernel 程式碼的系統方法。拆成:(1) 辨識的心法 → (2) 認出 list_head 走訪 → (3) 認出 container_of → (4) 認出樹/雜湊/XArray/bitmap → (5) 對照 struct 宣告 → (6) 警惕 _safe 這類「不是普通迴圈」的慣用法,最後打通關。

1. 辨識的心法:結構 + 慣用法 = 看懂意圖

讀 kernel code 不是逐字讀,而是辨識模式。每段程式碼都在用某些「資料結構 + 操作慣用法」做某件事。你的任務是認出「用了什麼結構、什麼操作」,從而推出「它在做什麼」。

(例:走訪一個 request 串列,

做某事)"]

心法:先認「招牌字樣」(API/巨集名),再推意圖。 你 Phase 2 學的每個結構都有它的招牌 API——看到 list_for_each_entry 就知道「走訪串列」,看到 container_of 就知道「取外層 struct」。認出這些,程式碼的骨架就浮現了。下面逐一複習每種結構的「招牌字樣」。

2. 認出 list_head 走訪

最常見的招牌。看到這些字樣,就知道在操作侵入式串列(P2-T02):

讀成『走訪 q 的 list 串列,
e 依次指向每個內嵌 link 成員的外層 struct』"]
    signs --> READ

    style READ fill:#8a9a5b,color:#10100e

關鍵:list_for_each_entry(entry, head, member) 的三個參數告訴你——entry 是迴圈變數(外層 struct 指標)、head 是串列頭、member 是 list_head 成員在 struct 裡的名字。讀到它,你就知道「這裡在逐一處理串列上的每個元素」。在 block layer,你會看到大量 request、bio 用串列串接並這樣走訪。

3. 認出 container_of(以及它的偽裝)

container_of(P2-T03)是 kernel callback 的招牌。但要注意它常常藏在其他巨集或 inline 函式背後:

    DIRECT["直接形式:
container_of(ptr, struct foo, member)
→ 從 member 指標取回 struct foo"]
    DISGUISE["偽裝形式(更常見):
很多子系統定義自己的包裝,
例如 to_foo(ptr) 這類 helper
內部其實是 container_of"]
    DIRECT --> RECOGNIZE["辨識訣竅:
看到 to_xxx(ptr) 或某 helper
把『一個通用指標』變成『一個特定 struct 指標』,
背後幾乎都是 container_of"]
    DISGUISE --> RECOGNIZE
    EXAMPLE["典型場景:callback 第一行
struct my_dev *dev = container_of(work, ...);
→ 從 kernel 給的通用結構取回自己的資料"]
    RECOGNIZE --> EXAMPLE
    style DIRECT fill:#6fa8b8,color:#10100e
    style RECOGNIZE fill:#e8a33d,color:#10100e
    style EXAMPLE fill:#8a9a5b,color:#10100e

辨識訣竅:container_of 常被包成 to_xxx() 這類 helper(例如把一個通用的 device* 轉成你的 my_device*)。看到「把通用指標變成特定 struct 指標」的 helper,背後幾乎都是 container_of。它最常出現在 callback 函式的開頭——kernel 回呼你時給通用結構,你第一件事就是用 container_of(或其 helper)取回自己的私有資料(回顧 P2-T03 第 6 節)。這是你讀 driver 程式碼最常遇到的模式之一。

5. 對照 struct 宣告:別只看函式

一個關鍵的讀碼紀律:光看一個函式不夠,要對照它操作的 struct 宣告。因為侵入式設計(P2-T02)的本質是「結構內嵌在 struct 裡」,你得看 struct 定義才知道「這個 struct 內嵌了哪些 list_head/rb_node,所以它會被掛到哪些串列/樹」。

flowchart TB
    FUNC["你在讀一個函式,
看到 list_for_each_entry(req, &q->requests, queuelist)"]
    QUESTION["疑問:req 是什麼型別?queuelist 是什麼?"]
    FUNC --> QUESTION
    LOOKUP["★ 去查 struct 宣告 ★
(用 Bootlin 點擊跳轉)
看 request 的定義:
struct request { ...; struct list_head queuelist; ... }
→ 原來 request 內嵌 queuelist,
用來掛到佇列的串列上"]
    QUESTION --> LOOKUP
    UNDERSTAND["現在才真懂:
這個迴圈在走訪佇列上的每個 request"]
    LOOKUP --> UNDERSTAND
    style LOOKUP fill:#e8a33d,color:#10100e
    style UNDERSTAND fill:#8a9a5b,color:#10100e

「只看單一函式而忽略它操作的結構定義」是讀碼常見錯誤。 看到一個走訪或 container_of,務必去查相關 struct 的宣告(Bootlin 能點擊跳轉),確認「這個 struct 內嵌了什麼、那個成員是什麼型別」。同樣地,巨集背後展開的真正動作也要留意(必要時看巨集定義)——別把 list_for_each_entry 當黑盒,要記得它內部用 container_of 反推(回顧 P2-T02 第 6 節)。

6. 警惕「不是普通迴圈」的慣用法:_safe 與其他

最後一個關鍵警覺:kernel 有些慣用法長得像普通程式碼,但語意不同,不能用直覺讀。最典型的是 _safe 走訪(P2-T02 第 7 節):

flowchart TB
    TRAP["陷阱:把 kernel 特有慣用法當普通迴圈讀"]
    TRAP --> SAFE["list_for_each_entry_safe(e, tmp, head, member)
★ 不是普通走訪 ★
那個多出來的 tmp 參數,是『預先存下一個』
→ 代表『這個迴圈裡會刪除節點』
(回顧 P2-T02:邊走邊刪必用 _safe)"]
    TRAP --> OTHER["其他要警覺的:
rcu 版走訪(list_for_each_entry_rcu)
→ 涉及 RCU 同步語意(P3 會學)
各種 _lock/_unlock 包裹
→ 臨界區(回顧 P1-T09)"]
    SAFE --> READ["讀到 _safe,要讀成:
『這裡會在走訪中刪除節點,
所以用了安全版本』,
而非普通的逐一處理"]
    style TRAP fill:#c2603a,color:#f4ecd8
    style SAFE fill:#e8a33d,color:#10100e
    style READ fill:#8a9a5b,color:#10100e

「把 kernel 特有慣用法當普通迴圈」是常見且危險的誤讀。 看到 list_for_each_entry_safe,要立刻意識到「這個迴圈會刪除節點」(那個 tmp 參數就是線索);看到 _rcu 版本,要意識到涉及 RCU 同步(P3 會深入);看到 _lock/_unlock 包裹,要意識到那是臨界區(P1-T09)。這些慣用法承載了「普通迴圈沒有的語意」,讀碼時要認出它們,才不會誤解程式碼的行為。

把前六節的方法,套用在一個示意片段上走一遍,你會看到「辨識 → 查定義 → 推意圖」如何串起來:

    SNIPPET --> A3["③ 查 struct 宣告:rq 是什麼?qlist 是什麼?

走一遍就懂:不是逐字讀,而是認出「鎖 + _safe 走訪 + list_del」這組招牌,再查 struct 確認 rq/qlist 是什麼,就推出「鎖保護下移除已完成的 request」——這就是你要在真實 code 上做的事。

常見誤區與踩雷提醒

誤區一:只看單一函式,忽略它操作的 struct 定義。 侵入式設計下,要看 struct 宣告才知道它內嵌了哪些 list_head/rb_node、會被掛到哪。讀到走訪或 container_of,務必用 Bootlin 跳去查相關 struct。

誤區二:漏看巨集背後展開的真正動作。 list_for_each_entry 內部用 container_of 反推、rb_entry 也是 container_of。別把巨集當黑盒;必要時看它的定義,理解它真正做了什麼。

誤區三:把 kernel 特有慣用法當普通迴圈。 list_for_each_entry_safe(會刪節點)、_rcu(RCU 同步)、_lock 包裹(臨界區)都有普通迴圈沒有的語意。認出它們,別用直覺誤讀。

誤區四:看到不認識的 helper 就放棄。 很多 helper(如 to_xxx())背後是熟悉的慣用法(如 container_of)。用 Bootlin 點進去看它的定義,常常發現是你已學過的東西的包裝。

動手實作(這就是出關驗收任務)

環境:Bootlin Elixir 線上瀏覽 kernel 原始碼(https://elixir.bootlin.com/linux/v6.12/source ),純閱讀 + 註解,無系統風險。

任務(出關門檻):挑一段真實 kernel 程式碼,完整逐段註解

  1. 選一段程式碼:從 block 目錄(https://elixir.bootlin.com/linux/v6.12/source/block ）挑一段約 100–200 行、結構清晰的真實程式碼(建議與儲存相關,為 P5 暖身)。可以是一個函式,或一組相關的 struct + 操作它們的函式。挑「你能看出它在用多種資料結構」的片段。 - 提示方向:I/O 排程器相關(會用 rbtree、list)、request/bio 處理(會用 list_head、container_of)、tag 配置(會用 bitmap/sbitmap)都是好選擇。

  2. 逐段註解(這是驗收核心):對選定的程式碼,逐段寫註解,正確指認其中每一處: - ☐ 每一處 list_head 走訪(是 _safe 嗎?在走訪什麼串列?) - ☐ 每一處 container_of(或其 helper 如 to_xxx/rb_entry)——從什麼成員取回什麼外層 struct? - ☐ 任何 rbtree / hlist / xarray / bitmap 的使用——在做什麼? - 並說明每個的目的(這段為什麼用這個結構)。

  3. 對照 struct 宣告:對程式碼裡操作的關鍵 struct,用 Bootlin 跳去看它的定義,確認它內嵌了哪些結構成員(list_head、rb_node 等),把這個對照寫進你的註解。

  4. 辨識至少 3 種不同慣用法:你的註解要涵蓋至少 3 種不同的 kernel 資料結構慣用法(例如:list 走訪 + container_of + rbtree;或 list + bitmap + hlist)。

驗收標準:產出一份逐段註解文件,正確指認選定程式碼裡的每一處資料結構慣用法、說明各自目的,並辨識出至少 3 種不同的慣用法。能對著你的註解,向別人講解「這段程式碼如何用這些結構達成它的目的」。

驗收與自我評分

驗收檢核點(量化,逐項通過): 1. ☐ 對選定的 100–200 行程式碼,產出逐段註解,正確指認其中每一處 list_head 走訪、container_of 取用、以及任何 rbtree/hlist/xarray/bitmap 使用,並說明各自目的。 2. ☐ 至少辨識出 3 種不同的 kernel 資料結構慣用法。 3. ☐ 對照了相關 struct 的宣告(確認內嵌的結構成員)。

評分量表(出關門檻,需達 80): - 60:能認出程式碼裡的多數結構。 - 80(出關門檻 🚪):能完整註解選定程式碼、正確指認每一處慣用法、辨識≥3 種,且具備閱讀 kernel 資料結構的信心。達此分數方可進入 Phase 3。 - 100:能向他人完整講解這段程式碼如何運用這些結構達成其目的(不只認出,還能說清「為什麼這樣設計」)。

延伸與銜接

  • 對應工作場景:直接對應——這正是你日後讀自家 module 與 block layer 程式碼的核心技能。Phase 2 的所有結構知識,在這一課匯聚成「讀懂真實 kernel code」的實戰能力。
  • 這課收束了:整個 Phase 2 的資料結構能力(list_head、container_of、雜湊/hlist、紅黑樹、XArray、bitmap),整合成「在真實程式碼裡認出它們」。
  • 下一步 → P3-T01 進入 Phase 3:恭喜你通過 Phase 2!你現在能讀懂 kernel 的資料結構慣用法了。Phase 3 是整個課程的重頭戲——你將真正進入 kernel 內部:理解 kernel 的整體架構、親手寫你的第一個 kernel module(LKM)、深入 kernel 的記憶體管理(SLUB 配置器)、同步機制(spinlock/mutex 選型、RCU)、中斷處理、以及 kernel 除錯。你在 Phase 1 建好的 QEMU 環境(P1-T11)終於要全面派上用場(記得:module 只在 VM 裡測試!),Phase 2 練就的讀碼能力會讓你讀懂那些 module 範例與 kernel 機制。從這裡開始,你就是在做真正的 kernel 開發了。

🚪 出關提醒:確認你能完整註解一段真實 kernel 程式碼(80 分門檻),並且對「讀 kernel 資料結構」有信心,再進入 Phase 3。這個能力是後面所有 module 開發與原始碼閱讀的基礎——地基穩了,Phase 3 的重頭戲才走得動。
